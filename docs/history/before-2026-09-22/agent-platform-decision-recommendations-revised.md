**优先采纳的方向**

本产品优先延续合适的既有 Session，复用角色已经积累的认识与可复用前缀，通过追加消息、工具查询和局部材料补充推进工作。Session 留存实际交互与执行记录；架构图把模块、文件夹、负责 Agent 和相关 Session 关联起来，以工具、摘要和图结构支持编排。首版由一个协调者提交正式调度，多名 Agent 参与调查、方案和审查；组织行为主要通过 Skill／Prompt 约定，执行沿用既有 Kernel 边界。上下文重组和更复杂的协调层级都需要实际收益支持。

应先联合处理 P-2、P-5、P-6、P-7、P-8、P-9、P-14、P-16、P-17、P-19。它们共同决定事实如何记录、图如何参与编排、角色怎样协作以及工作如何连续推进。P-11、P-15 则固定验收口径，把上下文处理自身的编排、运行与工程成本纳入比较。

**贯穿各项建议的四个约定**

1. **Session 记录已经发生的事情，架构图提供编排入口。**消息、工具调用及返回、讨论、决定和交接保存在对应 Session；记录某人说“已完成”，只证明这条陈述发生过，完成结论仍需结果支持。架构图保存模块结构和关联，同时提供索引、摘要与操作工具。新事实可及时记录并刷新相关视图；改变模块责任边界、接口或存续状态时，再按变更影响和现有决定流程处理。
2. **连续复用是默认方案，上下文重组需要证明收益。**按用户反馈，实际测试已有很高的缓存命中，如何选取和重新组织 Context 本身又需要大量编排及工程投入。本文将这一反馈作为方案取舍依据，不将其写成已独立复跑的结论。首版不建设每轮决定如何重组上下文的通用机制；优先续用 Session、追加信息、按需查询，确有容量或任务变化问题时才显式压缩、分叉或交接。
3. **Skill／Prompt 承担组织行为，Kernel 保持既有执行边界。**调查、拆解、派发、上报、咨询负责人和模块变更等流程优先通过 Skill 规划并以真实任务验证。平台不再叠加一套细粒度权限／审批体系。已有的工具访问、项目边界、取消机制和唯一 Writer 继续沿用；只有某条规则反复失效且影响显著时，再评估有针对性的工具前置检查。
4. **区分角色身份、Session、Run 与 Context，但保持工作连续性。**角色模板规定职责，角色实例承担责任；Session 保存连续工作历史，Run 是其中的一次执行，Context 是某次模型调用实际可见的内容。一次响应、一次派发或一次 Run 结束都不自动触发新 Session。归档、压缩和换手须交代未完成义务与来源；Agent 退出活跃运行不意味着模块或图节点应被销毁。

**P-1：产品图——采纳轻量能力与验收视图。**

建议采用候选 (a)，但明确最小内容：用户要完成的事情、产品能力、范围边界、关键用户路径、验收依据。产品图表达“为什么做、用户得到什么”；架构图表达“由什么构成”；任务图表达“当前如何交付”。三者可相互引用，首版不为产品图建设独立图数据库或一套新的状态机。

产品图可以先由文档内的表格或 Mermaid 生成。改功能范围才更新相应内容，不要求每次函数调整都改产品图。C4 对架构的多层表达可作为分层呈现的参考，但这里的产品图是本产品的轻量定义，并非 C4 的标准图种。[S21]

**建议定稿句：**“产品图是产品能力、用户路径、范围与验收依据的结构化视图；首版复用产品文档中的版本化记录，不单独承担运行时状态。”

**验收观察：**从一条真实用户路径能追到相应能力、架构范围与交付任务；没有正式承诺的功能不会因图上一个草稿节点自动进入执行。

**P-2：两张图——Session 记录事实，架构图提供编排操作入口。**

架构图应按“工具＋摘要信息＋图结构”设计，并与 Agent、文件夹及 Session 建立可查询的联系。建议明确以下逻辑分工，存储与接口优先复用现有模块：

| 对象 | 主要承载内容 | 与编排的关系 |
| --- | --- | --- |
| Session | 消息、工具调用与返回、观察、讨论、决定、交接及相关执行记录 | 回查发生了什么、谁提出什么、依据是什么；区分陈述、提案和已核验结果 |
| 文件／文件夹 | 当前代码、文档与产物；必要时定位到版本 | 核对实现现状，确定修改和检索范围 |
| Agent／角色 | 责任范围、适合回答的问题、相关工作 Session | 找到已积累认识的负责人，继续工作或完成交接 |
| 架构图 | 正式模块标识、职责、接口和依赖；文件夹、Agent、Session 的关联；摘要与索引 | 查询局部结构、定位证据、咨询负责人、确定委托范围及提出结构变更 |
| 任务图 | 工作包、负责人、依赖、进度及决定／证据引用 | 编排交付顺序，追踪阻塞和完成依据 |

图中的正式模块结构和关联需要持久保存；查询索引、展示布局和部分摘要可以更新或重建。不能因此把整张架构图都视为可以丢弃的派生物，也不要求在 Session 之外再建一套平行的事实来源。图上结论引用对应 Session 片段、执行记录或文件版本；架构约定与当前代码不一致时，保留差异及其依据。

对协调者，工具至少覆盖查询模块及邻接关系、定位目录与相关 Session、联系负责 Agent、读取摘要以及提出模块变更。常规工作先利用这些入口，必要时读取原始记录或代码。任务依赖子图保持 DAG；Agent 之间的咨询、反馈和讨论可以往返，两种关系分别表达。

不同变化应区别处理：

| 变化 | 建议处理方式 |
| --- | --- |
| 新工具结果、进度、阻塞或文件变化 | 写入对应 Session，按影响刷新索引、引用、状态和摘要；不把记录事实变成审批动作 |
| Agent 暂停、换手或归档 | 更新活跃状态及责任关联，记录交接；保留模块与历史负责人关系 |
| 在已确认方案范围内创建模块 | 依现有计划和 Skill 执行，补齐模块标识、职责、目录、负责人和相关 Session 引用 |
| 新增责任边界、拆分／合并模块或改变跨模块接口 | 说明依赖、任务、目录和责任影响；在既有授权内推进，超出已定范围时提交具体决定事项 |
| 删除模块或正式节点 | 先确认代码、依赖、未完成任务和责任的处理方式；记录迁移／替代关系与删除理由，保留历史引用 |

隐藏一个视图节点、Agent 结束一次运行、删除代码目录和撤销模块是不同操作，应在工具与界面中明确区分。结构变更记录关联其决定和实际执行结果；基于旧版本提交的变更不能覆盖已经生效的新关系。DSH 的任务版本检查和 DAG 校验可供参考，但不据此引入额外权限体系或指定新的存储组件。[S03][S04]

**建议定稿句：**“Session 留存交互、执行与决定记录；架构图持久关联模块、文件夹、Agent 和相关 Session，并以工具、摘要和图结构支持编排。记录事实与更新索引及时进行；模块的创建、拆分、合并和删除按现有计划、Skill 及变更影响处理，保留可追溯关系。”

**验收观察：**协调者能从一个模块定位目录、负责人及相关 Session；Agent 换手不会导致模块消失；模块删除能查明依赖和责任去向；图中摘要可以回到来源核验。

**P-3：秘书常驻——沿用 D-1，只澄清可用性的含义。**

不用再次表决是否常驻。身份、最近进度与入口应持续可用；打开应用即可输入和查看已有状态。若模型进程或缓存需要恢复，界面展示恢复状态，并优先呈现已有事实。持续可用的产品入口不等于模型响应零延迟，也不要求为了等待一句追问而长期保持昂贵运行。

**建议定稿句：**“打开应用即可与秘书交互并读取已有项目状态；必要的会话恢复由系统完成并可见，不要求用户重新讲述项目。”

**P-4：主 Agent 写能力——沿用 D-2，并与唯一 Writer 统一。**

主 Agent 可以具备写能力。默认委托承担该范围的角色；主 Agent 自己执行时同样要获得当前任务的写权限与 checkout 租约。负责人不在线时，通过显式接管更换执行者，不能为了保持模块归属而令工作永久等待。

这里没有引入多 Writer，也没有要求“主 Agent 所有写操作都重新问人”。既有授权足够的普通工作按既有规则执行，只有范围或权限变化才进入新的决定流程。

**P-5：首批能力——摘要入产品文档，Skill 组织协作，复用 Kernel。**

建议采纳候选 (b)：产品文档列出首批能力及对应用户路径；具体工具接口、Skill 用法和既有 Kernel 映射放入设计文档。只列行为类别，不将每项行为扩成新的权限或审批节点。

| 首批能力 | 典型承担者 | 执行约定 |
| --- | --- | --- |
| 查目标、任务、决定、证据、角色与历史 | 秘书、协调者、执行者 | 优先查相关图节点、摘要和 Session；沿用现有访问范围 |
| 提出目标／计划／架构变更并解释 | 参谋、主 Agent | 用 Skill 说明依据、影响和待决事项；既有范围内按计划推进 |
| 领取、派发、等待、报告阻塞、请求决定 | 协调者及相应执行者 | 通过 Skill 明确责任、依赖、交付和升级条件 |
| 读取文件、rg 搜索、查看差异；按需接入语义分析 | 调查者、执行者、审查者 | 调用已有工具，按问题补充材料 |
| 修改代码、运行项目命令和测试 | 相应执行者 | 沿用 Kernel 的执行控制与同 checkout 唯一 Writer |
| 提交产物／完成声明、检查 Evidence | 执行者、Reviewer、框架 | 按既有完成规则核对产物和证据 |
| 人的暂停、取消、接管、换手与恢复 | 人＋协调者＋框架 | 复用已有控制接口，由 Skill 组织交接和结果说明 |
| 查询参考资料、记忆与知识库 | 调查角色 | 按需取材，保留出处；不可用时说明 |

上述是能力类别，并非八个新 Agent。每类能力映射到现有 Kernel 或平台接口；缺失的能力明确标记待实现。调查路径、是否征询模块负责人、如何拆解和上报等组织规则，由 Skill／Prompt 承担并通过实际任务调优。Skill 的逐层披露和按需资源读取可参考现有规范及客户端指南。[S13][S14]

平台不新增一套细粒度权限矩阵来替代这些协作判断。既有 Kernel 的访问、工具执行和 Writer 规则继续生效。若某项规则在优化 Skill 后仍反复失败，且已造成明确影响，再针对该问题评估工具前置检查，并比较它对自由度和任务成功率的影响。

**建议定稿句：**“首批能力以用户路径为依据，组织行为主要由 Skill／Prompt 定义并验证，工具执行复用既有 Kernel；首版不新增平台级细粒度权限／审批体系。”

**P-6：目标变更——采纳安全点切换，但先禁止继续走旧目标。**

既有 D-3 保留。建议不采用“等所有运行自然结束后才处理”，也不采用“每次变更全项目杀停”。具体行为为：

1. 用户确认新目标／计划版本时，在对应 Session 记录新版本和变更范围；停止受影响任务的后续派发，并使用现有取消／写入控制阻止继续执行旧目标。
2. 对正在执行的受影响 Run 发出取消／切换信号；到 Kernel 可识别的安全边界停止。无关工作继续。
3. 若无法迅速确定影响范围，先暂停该 Goal 的新派发，再完成影响判断；不能把“暂时不知道”当作“没有影响”。
4. 已启动的工具或外部副作用不能被假定撤销。在对应 Session 记录已知结果、检查实际代码和环境；不确定时保留结果未知，继续核对，并更新相关图节点的状态摘要。
5. 对受影响依赖进行局部计划修订并展示差异；保留未变任务的身份和可复用证据，不全量删除重建。
6. 旧 Run 的结果可以保存，但只有通过新版本适用性检查后才能推进当前状态。切换 Writer 前确认原 Writer 已停止可写活动；若做不到，则不交出新的写租约。

LangSmith Deployment 明确提供排队、拒绝、中断等多种并发输入策略，并指出中断可能遇到未结束的工具调用；这些是策略选项，不是“任何操作都能撤回”的保证。LangGraph 的恢复文档也提示副作用重放需要幂等处理。本建议借鉴这些边界，不要求引入其服务。[S07][S08]

**建议定稿句：**“目标变更立即停止受影响工作的后续派发，并通过既有取消／写入控制在安全点切换；已发生操作在 Session 中保留记录并核实，无关工作继续，旧结果经当前版本适用性检查后方可使用。”

**验收观察：**在任务执行中改变目标后，旧结果不会把新任务误标完成；暂停期间无两个 Writer；取消后保留实际已发生的修改。

**P-7：共同编排——并行研究与审议，首版单一提交正式调度。**

建议选择 (a)，但“一个协调者”只限制正式调度的归属，不把调查、方案、状态说明、接口审查都压在同一个 Context。秘书整理事实，参谋可并行提出方案，协调者把采纳结果提交给框架；任务可自动执行到既有授权边界。

Cursor 的实践说明规划者可以派生子规划者；Claude Agent Teams 展示了独立上下文、成员通信和共享任务。两者支持“多人参与规划”的可行性，但不提供“所有项目从第一天都该多层指挥”的结论。[S01][S02]

首版建议：一个正式调度提交者；研究和审查 Agent 按任务参与，连续工作优先续用对应角色的既有 Session，必要的独立调查或审查才开子 Session。同一议题先独立产出，再进行一轮针对具体分歧的质疑，有新证据才追加调查。采用什么方案、谁负责执行、何时结束，应形成 Session 中可定位的决定或待决事项，并关联相应图节点。协调者按需读取摘要、产物和来源，不要求汇入全部工具历史。

**增加领域协调者的重审条件：**持续出现互相独立的工作流；同一协调者的待处理事件、重复加载和派发等待已构成可测瓶颈；领域边界和交付接口能够稳定说明；增加层级后需要证明总成本、遗漏和进度至少有一项实际改善，并控制其他指标退步。先不设任意 Token 百分比或 Agent 数量为普遍阈值。

人仍保留目标与未授权取舍的决定权；协调者的决定权只在已授权的责任范围内。定时轮询、超时计数、预算检查、邮箱恢复可交给确定性框架，不必增加“监督监督者”的模型链。

**建议定稿句：**“允许多 Agent 对编排提供调查、计划和审查；首版由一个协调者在已授权范围内提交正式调度。出现可测的信息或调度瓶颈后，再按工作领域增加有明确责任边界的协调者。”

**P-8：承担范围——责任按领域保持，交付按工作包组织。**

不要在模块、工作包、目标中选一个取代其余所有粒度。建议定义三个不同的范围：

- **角色的长期责任范围：**一个领域或模块组，以及适合回答的问题。它便于复用认识，不要求每个目录常驻一个 Agent。
- **本次委托与验收范围：**一个可交付工作包，可以跨模块，包含目标、涉及接口、输入、输出、完成依据与升级条件。
- **执行资源范围：**本次任务涉及的目录、接口与工具；访问和 Writer 租约沿用现有 Kernel 规则，不为模块协作新增一套权限模型。

Goal 可以跨多个工作包，但首版仍只绑定一个 Workspace。跨模块任务指定一个交付负责人，相关模块角色按 Skill 提供意见；模块、目录、负责人和相关 Session 的关系记录在架构图中。这里是职责关系的定义，不要求新增一个工作包子系统。

**建议定稿句：**“角色在项目的领域或模块组内持续积累认识；执行以可验收工作包委托，必要时跨模块；每个工作包有唯一交付负责人，图关联其目录与 Session，访问和写入沿用既有 Kernel 规则。”

**P-9：生命周期——默认延续 Session，按实际需要处理压缩和换手。**

连续承担同类职责或推进同一工作时，优先使用既有 Session。新要求、查询结果和必要材料增量加入，不因一次 Run 结束或一次派发就重新组装整套 Context。首版不建设每轮判断如何重组上下文的通用编排器。

| 动作 | 建议触发条件 | 必须保留或检查 |
| --- | --- | --- |
| 产生 | 新工作确需独立责任或并行调查，现有合适角色／Session 无法承担 | 范围、输入、预算和交接来源；能复用既有认识时明确如何引用 |
| 拆解 | 存在可独立调查或交付的子任务，接口和完成依据可说明 | 父任务继续承担汇总义务；子任务有负责人、依赖和结果回流路径 |
| 压缩 | 上下文容量确实不足，或已观察到历史噪声影响任务质量 | 当前决定、证据引用、未决事项、失败原因和版本；原始 Session 记录可回查 |
| 归档 | 没有未交接的活跃义务，且近期不再需要参与；由明确操作触发 | 身份、范围、Session、产物和图中历史关联；释放运行资源 |
| 重新启用 | 新请求需要该角色，现有身份和责任范围仍合适 | 优先恢复合适的原 Session，补充期间变化；确需新 Session 时保留交接来源 |

“拆解角色”指拆解其承担的工作；“压缩角色”指压缩会话工作集，身份与责任不因压缩而消失。角色归档更新活跃状态和责任关联，不删除模块；模块撤销另按 P-2 处理。

首版保持显式压缩和归档。框架可以提示容量压力；确实无法继续时，提供压缩或交接所需的材料与操作。是否进一步自动化，应在真实任务上比较效果、缓存、延迟、上下文选择开销及维护成本后决定。

Anthropic 的压缩、外部笔记、子 Agent 隔离，以及 Gas Town 对持续身份与短期会话的区分，可作为遇到具体问题时的手段参考。它们不构成本产品频繁重建 Session 的依据。[S10][S15]

**建议定稿句：**“连续工作默认延续既有 Session，以增量信息和按需查询补充认识；仅在容量、质量或任务分工确有需要时显式压缩、分叉或交接。归档保留身份、Session 和重新启用能力，模块存续另行处理。”

**P-10：五类参考来源——统一出处，检索路线随问题而变。**

| 来源 | 何时取用 | 进入 Context 的形式 |
| --- | --- | --- |
| 工作区文件／代码 | 回答现状、定位符号、核对修改 | 当前版本相关片段＋路径／内容版本 |
| 人提供的需求和反馈 | 目标、价值取舍或主观要求不明确 | 原始要求／决定的引用；保留是否已确认 |
| 网络资源 | 问最新事实、框架行为、已有工程实践 | 官方资料优先的短摘录／结论＋链接和取用日期 |
| 记忆与知识库 | 需要历史理由、约定、经验或已研究材料 | 小段命中内容＋适用范围和原始证据 |
| 模型自身知识 | 提出搜索方向、候选解释、方案草稿 | 标注为待核实假设；不能直接充当项目事实 |

统一要求：能说明来自哪里、适用什么范围、基于哪个版本、何时获得、哪些尚未验证；不是每项都强制具有同一种时间戳或代码哈希。检索到事实也不自动提升该材料的授权级别。

这些检索用于补充正在延续的 Session，不要求每轮重新选择整套上下文。对于模块职责、依赖、负责人和历史理由，优先通过架构图的工具、摘要和关联定位，再按需咨询负责角色或回查 Session。对于“这个函数在哪里”可直接 rg／符号搜索；对于“现在是否完成”查当前状态及其执行依据。原 Agent 离线时仍可利用其 Session、图中引用和文件继续调查。

找不到时在预算内扩大检索范围，明确标注仍未知的部分；只在关键缺口影响决定时向人提出具体问题，不为五类渠道逐一打断人。Anthropic 的即时检索实践支持用文件与搜索工具按需获取材料；其研究系统也通过外部产物和引用减少信息转述。[S10][S11]

**建议定稿句：**“参考资料以带出处与适用性的片段增量补充既有 Session；模块关系和责任问题优先利用架构图，其他问题按需使用状态查询、静态搜索、Session 回查或角色咨询。”

**P-11：验收数字——保留历史口径，以连续复用为比较基线。**

建议保留 §6 的旧验收陈述和适用范围，标记为附件中记载的历史结论；本次无法访问其证据，不予重新认定。用户本轮反馈实际测试已有很高的缓存命中，本文据此调整方案优先级；这与独立复跑验收是两回事。新增要求建立新的验收说明，不能由文字改动直接把旧门禁变成通过。

| 原表述／关注点 | 建议新口径 |
| --- | --- |
| 状态查询准确率 100% | 在指定测试集上，结构化查询应与对应 Session／Kernel 记录及图中正式关系一致；自然语言解释另测事实错误、来源覆盖、过期信息和恰当“不知道”，并统计回答覆盖率 |
| 成功率不下降 | 在同一冻结任务集、模型／工具条件和预算策略下配对比较并记录重复运行；样本不足不能声称统计上的不退步 |
| 缓存命中率 99% | 保留为明确条件下的热调用目标；同时报告全量输入 Token 命中率、热调用命中率、可复用前缀利用情况及实际费用，不改变旧数字的分母 |
| 压缩／重组是否值得 | 以原 Session 连续复用为基线；同时测量质量、延迟、重组决策调用、检索、读写、压缩、缓存变化及后续恢复成本 |
| 上下文组装的工程投入 | 单列选择／编排逻辑的实现、调试和维护成本；说明新增组件解决的实际问题，不只核算模型 Token 账单 |
| 任一失败归因 | 保留主要原因、伴随原因及暂未确定原因，不为满足分类而猜定原因 |

上一版仅复算了用户文档提供的价格假设与输入规模，并未核实该价格当前适用于哪个供应商／模型，也未复跑所谓“当前实测”。按 2,854,860 输入 Token、命中 0.02 元／百万、未命中 1 元／百万，89.99%、99%、75% 对应约 0.3371533、0.0850748、0.7565379 元，与原表四舍五入吻合。这组计算保留为原表的算术核对。

本轮撤回用长／短上下文的单次 Token 费用反例支持重新组装 Context 的论证。重组决定本身属于编排工作，需要选择材料、处理遗漏、维护引用并验证后续效果；已有高缓存命中时，更不能忽略这些投入。默认延续 Session；只有出现容量、质量、分工或恢复方面的具体问题，才比较相应的压缩、分叉或交接方案。

运行费用使用互斥分类：普通未缓存输入、缓存读取、供应商单列计费的缓存写入、输出，再加工具／检索与环境费用；计入失败、重试、压缩及决定如何处理上下文的调用。没有单列缓存写入的供应商不额外重复计费。端到端延迟和工程维护投入分别报告，不强行折算成一个缺少依据的金额。

新定义必须和旧 89.99%／89.10% 的分母、样本、模型配置一起保留，不能更换分母后宣称目标达到。缓存的前缀匹配等机制可参考供应商文档，但这些机制本身不能证明主动重组 Context 对本项目划算。[S09]

**建议定稿句：**“保留历史验收证据、范围与缓存指标，以既有 Session 连续复用为比较基线；上下文策略的变更须结合任务质量、缓存与延迟、编排运行成本、工程投入和恢复可靠性判断，首版不默认建设通用上下文重组机制。”

**P-12：接管入口——侧栏为统一工作区，其他入口只负责定位。**

建议主对话保持默认入口；点击 Agent 名册、任务节点或在对话中点名，都打开同一个侧栏。侧栏显示：负责人、任务与版本、最近进度、已有证据、待决项、当前是运行／等待／恢复，以及“询问、追加要求、暂停、取消、替换／接管”等明确动作。

查询状态首先读取图中状态／摘要及相关 Session 的记录和证据。确实需要原执行者补充时，在其既有 Session 中接收询问并于合适边界回复；只有独立问答确有需要时才开单独 Session，并标注依据。普通查询不隐式改变执行目标。查看“当前 Context”展示实际材料目录、版本和可公开记录，不承诺跨供应商提供完整内部思维过程。

直接修改子任务时，该指令写入对应 Session 并通知协调者，相关任务状态和责任关联随之更新；涉及其他任务、跨模块契约或超出既有授权时，走已有决定路径。换手按钮只有在原执行者的写活动已终止并完成交接后，才显示新执行者开始写入。

**建议定稿句：**“用户通过统一 Agent 侧栏查看和介入工作；图、名册和对话点名共享这一入口。查询默认读取已有状态，执行控制和任务变更通过正式路径回流。”

**P-13：共享载体——Session 留存协作，图关联责任与材料。**

建议复用四类已有职责：Session 留存请求、讨论、决定和执行回报；图关联模块、任务、负责人及相关记录；版本化文档／产物保存详细方案和结果；定向邮箱把消息送给需要处理的 Agent。它们可在同一界面呈现，无需建设独立群聊产品或平行的事实库。

消息到达不等于任务成功，讨论同意不等于某个操作已经执行，文件存在不等于已通过验收。工具返回和 Agent 陈述都可以如实进入 Session，但图上的完成摘要应关联相应结果与验收依据。跨 Agent 消息保留发送、接收及原材料引用，避免反复转述丢失来源。

协作文档允许反复修改，但一次被审阅或用于决定的版本必须可以定位。DSH 的持久邮箱和任务版本机制可参考；不用引入其插件，也不能把其 advisory writeScopes 当成独占锁。[S03][S04]

同类／竞品材料只在具体决策或接口问题需要时检索，先读官方文档和许可证，记录版本与采用的部分。参考设计不等于整仓导入或获得使用授权；来源无法取得时保留缺口，不用相似项目冒充。

**建议定稿句：**“协作过程留存在相关 Session，图关联责任、状态与材料；详细方案和结果使用版本化文档／产物，信息通过定向消息送达。协调者依据任务和分歧组织讨论，并将结论关联到对应工作。”

**P-14：Skill／Prompt 资产——以流程组织协作，轻量版本化。**

建议自研平台特有的调查、计划提案、拆解派发、咨询模块负责人、状态上报、争议处理、交接和 Evidence 提交流程；补充模块创建、拆分、合并、删除时的影响检查。代码调查、审查、测试、资料检索等通用做法参考现有实践并适配。Skill 数量由真实工作需要决定，不按 Agent 数量或目录数量铺开。

Skill／Prompt 应说明适用场景、工作目标、可用工具、输入与交付、何时咨询和上报，并给 Agent 留出选择调查路径与方案的空间。连续工作默认续用已有 Session；只有具体需要才新增独立调查或交接。模块变更区分已确认方案内的执行与新的责任／接口决定，避免每次常规编辑都重新审批。

项目访问、工具执行、取消和唯一 Writer 等沿用现有 Kernel。平台不因引入 Skill 再叠加一套细粒度权限框架，也不把每条协作规则都固化成运行时闸门。先用真实任务观察规则是否有效，反复出现且影响显著的问题再评估局部工具前置检查。

Skill 正文和资源按相关性加载；已有会话中可复用的内容保持连续，不将逐层披露解释为每轮重建上下文。Agent Skills 规范和实现指南可作为资产格式与加载方式的参考。[S13][S14]

每项资产记录来源、版本、适用范围、已验证的真实任务及失败例；在 Run 中记录用到的版本。修改需能回退，格式合法不等于行为有效。不建设独立技能市场、自动生成技能工厂或新的注册体系。

**建议定稿句：**“Skill 与 Prompt 以自研和参考适配相结合的方式规定组织流程，按版本维护并用真实任务验证；保留 Agent 的规划与调查自由度，工具执行复用现有 Kernel，仅对实际反复失效的问题考虑针对性补强。”

**P-15：真实项目验收——两类项目，任务和环境先冻结。**

建议首批使用：自己的 coding-platform（验证秘书、图、接管、目标变更等整条交互回路）；一个技术栈可运行、维护历史清楚的外部开源项目（检验是否依赖平台自身的特殊知识）。此处未检查候选仓库，因此不虚构已选定项目。

选取标准是可安装、可运行、原问题可重现、修复有可独立检查的依据、改动范围可控制。SWE-bench 用真实仓库、候选补丁和项目测试构建验收，值得借鉴其可重现方式；它本身不能覆盖本平台的人机交互和生命周期承诺。[S17]

每个验收任务至少固定：起始代码版本、环境／依赖、需求与授权、验收依据、预算与超时、是否允许网络、哪些参考材料可见。历史修复任务应遮住最终补丁和直接泄露答案的材料，同时披露公开任务可能已被模型见过，不能把全部成功归功于编排。

任务包覆盖真实修复／修改、状态查询、目标中途变化、跨模块接口争议、暂停恢复与换手。可以在真实任务上注入断网或进程终止来检查恢复；这仍使用真实任务，不等于用玩具任务替代验收。机制单元测试作为补充，不冒充端到端成功。

成功定义既含项目结果，也含责任／证据／授权闭环。模型自评、运行退出码、最终补丁与人类补丁相似度，都不能单独代表成功。有限任务先用于发现退步与校准门禁；需要统计声称“不退步”时，再根据观测方差和容忍差异确定样本量。

**建议定稿句：**“首批在自有项目与外部维护项目上运行可重现任务，冻结版本、环境、授权、材料和验收条件；真实交互回路与结果质量同时验证，人工故障注入只用于补充恢复检查。”

**P-16：Session 与 Run——默认连续复用，一个 Session 可包含多次 Run。**

一个持久角色身份可以拥有多个 Session；一个 Session 可以包含多次 Run；每次 Run 的调用和结果归属于明确 Session。同一职责的连续工作优先在既有 Session 中推进，不因模型响应结束、工具返回或再次收到任务就新建 Session。首版以追加消息、查询工具和补充局部材料为主要方式。

为避免出现两份相互矛盾的当前历史，首版同一 Session 只允许一个拥有执行控制权的活跃 Run；新要求默认排队，明确的改变／停止按 P-6 在安全点处理。Kernel 内部一个 Run 的并行工具调用不受这一规则禁止，仍遵守工具自身并发和写入规则。LangSmith 的并发输入策略可作为排队与中断的参考；其 double-texting 是 Deployment 能力，不据此声称开源 LangGraph 自带完整服务。[S07]

确需独立并行调查或独立审查时使用子 Session。继续已有调查可选择适当继承；独立审查可使用新上下文并传入任务、产物和验收依据。选择以任务需要为准，不为每次委托引入通用上下文策划过程。Deep Agents 的 isolated／fork 形式可供参考，但不改变本产品连续复用的默认选择。[S05]

Session 保存可获得的消息、工具输入输出、材料版本、公开决定与交接，保留类型和来源，不把完整内部思维链作为恢复必需数据。确需压缩时保留原记录及续接关系；归档后可恢复合适的 Session。供应商会话 ID 和请求传输方式由 Kernel 适配，与平台是否主动重组工作 Context 分开处理。

**建议定稿句：**“Session 属于一个 Agent 身份并可包含多次 Run，连续工作默认续用；同一 Session 的执行控制与历史提交串行化，必要的独立并行工作使用子 Session。容量或任务变化需要压缩、分叉或交接时，显式处理并保留来源。”

**P-17：历史状态——复用 Session／Kernel 记录，持久保存图的结构与关联。**

消息、调用、工具返回、观察、讨论、决定和交接在 Session 中留存，结构化运行信息复用 Kernel 已有的 Run／Attempt 记录并与 Session 关联。平台不再建设另一套平行事实来源。已有记录可按类型、对象和版本查询，避免每次都让模型从完整 transcript 中重新推断状态。

架构图持久保存模块身份、职责、接口、依赖及文件夹／Agent／Session 关联；任务图保存交付结构及进度依据。记录一次正式结构变更时，关联相应 Session 中的决定、执行结果和相关文件版本。索引与展示摘要可刷新或重建，正式模块关系与变更历史须保留；不能把整个图的存续寄托于以后重新阅读全部会话。

恢复优先使用 Kernel 已有的持久 Session、执行记录和检查点，平台补充必要的跨任务／模块关联。LangGraph 的检查点及跨线程 Store、DSH 的可恢复任务与邮箱可作参考；具体复用方式由现有 Kernel 能力决定，不预先引入第二套事件存储与恢复框架。[S06][S04]

代码历史使用 Git 版本；尚未提交但必须跨恢复保存的修改记录为补丁／内容快照，并附基线和哈希。Git tree 不自动包含未提交修改，gitignore 排除的运行记录也不会因此获得备份。可回溯承诺应明确覆盖正式代码版本和交接／恢复检查点，不默认为每次临时写入都保存完整快照。

Session 中的操作记录与文件系统修改不是天然原子的一件事。遇到崩溃，先检查实际产物、工具结果与现有记录，再决定是否继续或补做；“准备写入”和“已成功写入”必须区分。恢复框架状态也不能自动撤销已完成的外部操作。[S08]

首版不引入 Kafka、分布式共识或完整通用 Event Sourcing 框架。新发现通过后续更正记录说明，保留此前观察及其来源。归档退出活跃使用，模块删除保留历史关联；保留和删除政策不由一次 Agent 生命周期动作隐式决定。

**建议定稿句：**“项目历史复用 Session 与 Kernel 的持久记录及恢复机制，图保存正式结构、责任关联和可回查摘要；派生索引可重建，正式关系与历史来源持续保留。代码和产物以 Git 版本及必要快照关联记录。”

**P-18：静态工具检索——搜索是渠道，索引是可选加速层。**

原来的 (a)/(b) 不必互斥。建议 rg／grep、文件读取直接面向当前文件；架构图可提供路径范围和候选模块。需要符号引用、跨文件关系时，再用已有 LSP／语言解析器的索引。AST 也可能现场解析，无需先统一建设全仓索引。

索引必须绑定代码内容版本或明确标注更新时间。语义索引失效时重新解析或回到直接搜索，不能仅因查询没有命中就断言不存在。搜索调用及返回按既有工具记录机制留存在 Session；采纳为 Evidence 的结果再关联到相应图节点、任务或决定。记录一次搜索发生过与确认搜索结果支持某项结论是不同事情，不需另建容纳所有命中的事实数据库。

因此保留三种查询能力：角色咨询、静态搜索、状态／记忆查询；两种或更多索引只是各自的实现。Anthropic 的即时检索案例为“直接搜索＋按需材料”提供参考，不能由此推断 AST 或索引一律无用。[S10]

**建议定稿句：**“静态搜索直接针对当前文件和代码，按需利用架构范围与版本化语义索引；搜索渠道不强制归属于 Agent 索引或事实索引，已核验结果可成为 Evidence。”

**P-19：Run 如何归类——独立可查询，归属于 Session／Kernel 记录。**

保留“Agent 状态、文件、Session 集合”作为平台内三类采集根。Run／Attempt 是 Session 中执行过程的结构化表达；若 Kernel 已单独存储相关记录，平台通过稳定引用关联。它们应能查询状态、时间、工具结果、费用、取消和恢复情况，无需把 Run 提升为第四类独立事实来源，也不依赖模型临时解析整段 transcript。

采集根、材料出处与图中结构属于不同层次。人确认、外部回执、代码观测和模型陈述都可能记录在 Session 中，必须保留各自出处及验证状态。§7.14 的五种参考来源用于说明材料来自哪里，无需与三类采集根一一对应。图中正式模块关系由相应变更操作维护，其讨论、决定与执行依据链接回 Session 及相关文件。

**建议替换 §7.2.1：**“两张图通过 Agent 状态、文件和 Session 集合获取项目内的活动与实现信息。Session 留存交互、观察、决定和执行事实，保留原始出处及验证状态；Run／Attempt 通过 Session／Kernel 的结构化记录独立查询。架构图维护模块结构及文件夹、Agent、Session 的关联，并提供索引、摘要和编排工具。”

知识库与网络资料经工具读取后，其使用过程和来源进入对应 Session；需要作为依据时建立明确引用。材料进入 Session 不自动证明内容正确，当前文件也仍需按版本核对。这里复用现有记录与关联，不新增平行日志库或改变已有访问范围。

**P-20：跨项目形态——维持后置，当前只固定作用域。**

保留 D-1 和 §11 的项目内复用边界。首版所有状态、角色、Session、产物和检索都能确定当前 Workspace；越界请求给出明确原因，不从另一个项目默默补材料。用户切换项目时呈现相应状态，不延续前一个项目的执行权限。

当前只需在现有对象上维护可靠的项目归属与出处，必要时支持用户明确选中的资料导入；不提前建设跨项目向量库、共享角色池或跨项目 Agent 网络。以后用只读工具按明确授权范围检索，返回带来源片段；“同一用户所有项目”不自动等于精确历史授权。

启用时机是出现反复的真实跨项目问题，而且用户已能说明允许读取哪些材料。跨项目检索、跨项目 Agent 通信、跨项目执行是三个不同范围，不能用开启前者顺带开放后两者。

**建议定稿句：**“首版以项目作用域隔离角色复用、执行与检索；跨项目能力后置，未来先以显式授权的只读工具开放，不自动扩展通信或执行权限。”

**下一步的审阅顺序**

先确认本轮修订的三条主线：连续工作默认续用 Session；Skill／Prompt 组织协作，执行沿用既有 Kernel；Session 留存事实，架构图以工具、摘要和结构支持编排。再核对一个正式调度提交者与多 Agent 研究／审议的分工，以及模块创建、拆分、合并和删除的处理方式。

接口审阅先覆盖图的查询与责任定位、Session 增量续接、必要的压缩／交接、任务派发与换手、模块变更及 Evidence 关联。复用现有模块和 Kernel，暂不冻结通用 Context 组装器、新权限体系或平行事件库的接口。

验收先在真实工作中跑通“查询状态—中途改目标—安全停写—换手恢复—核对旧结果适用性”，并检查模块变更的任务、依赖和责任去向。随后以既有 Session 连续复用为基线，比较首版协作以及确有必要的上下文策略／协调层级改动，合并评估质量、缓存、延迟、运行费用和工程维护投入。有具体瓶颈和实际收益后，再增加复杂度。
