**优先采纳的方向**

本产品适合以持久状态为基础，复用角色身份与项目认识，以有边界的会话承接工作；首版由一个协调者提交正式调度，多名 Agent 参与调查、方案和审查。需要先固定的是责任、状态、授权和交接契约；Agent 数量及层级可以后续调整。

应先联合处理 P-2、P-6、P-7、P-8、P-9、P-16、P-17、P-19。它们决定“谁负责、谁能改、什么是事实、换人如何继续”，不能分别选择相互冲突的方案。P-11、P-15 则在实现前固定验收口径。

**先修正四处会影响所有 P 项的表述**

1. “方案确认前不改两张图”与“事实自动回流”冲突。区分草案、批准基线、观测事实：草案能讨论和编辑；目标／范围／正式义务的改变按人已授予的权限生效；工具返回、失败、阻塞和证据等事实自动记录。已经发生的事实不能等待人批准后才显示。已授权范围内的调度执行可自动推进，不能悄悄把新的目标或正式任务义务当作调度细节放行。
2. “每次重新装配＝缓存未命中”不成立。应用读取记录、构造请求是本地工作，模型端缓存是否命中另由实际前缀、缓存可用性和模型策略决定。会话身份持续也不保证缓存命中。原文禁止重复无意义探索的目标可以保留，但应按实际请求和账单判断。[S09]
3. “Skill 决定这次准不准”需要补充执行责任。Skill 可声明要求并指导行为，是否允许调用工具仍由框架根据当前授权、任务、资源和写租约判断。Skill 规范存在实验性的 allowed-tools 字段，其支持依实现而异，不能把一段 Markdown 当成可靠权限边界。[S13]
4. “角色”“角色身份”“Session”“Context”需分开。角色模板规定职责；角色实例在项目中承接责任；Session 保留有界工作历史；Context 是某次模型调用实际可见的内容。复用身份、认识、记录与模型端缓存是相关但不同的事情。归档与压缩不能删除尚未转交的工作义务。

**P-1：产品图——采纳轻量能力与验收视图。**

建议采用候选 (a)，但明确最小内容：用户要完成的事情、产品能力、范围边界、关键用户路径、验收依据。产品图表达“为什么做、用户得到什么”；架构图表达“由什么构成”；任务图表达“当前如何交付”。三者可相互引用，首版不为产品图建设独立图数据库或一套新的状态机。

产品图可以先由文档内的表格或 Mermaid 生成。改功能范围才更新相应内容，不要求每次函数调整都改产品图。C4 对架构的多层表达可作为分层呈现的参考，但这里的产品图是本产品的轻量定义，并非 C4 的标准图种。[S21]

**建议定稿句：**“产品图是产品能力、用户路径、范围与验收依据的结构化视图；首版复用产品文档中的版本化记录，不单独承担运行时状态。”

**验收观察：**从一条真实用户路径能追到相应能力、架构范围与交付任务；没有正式承诺的功能不会因图上一个草稿节点自动进入执行。

**P-2：两张图——权威记录在外，图承担读取和编辑入口。**

建议明确以下分工。这里是逻辑上的责任划分，不要求新增服务或模块：

| 内容 | 权威依据 | 图如何使用 |
| --- | --- | --- |
| 目标、批准计划、任务责任与状态、决定 | 框架接受的正式记录 | 任务图投影与版本比较 |
| 架构意图、模块职责、接口约定 | 批准的架构基线及决定记录 | 架构图的设计层 |
| 文件、符号、依赖的真实情况 | 对应版本的代码及可复查工具结果 | 架构图的观测层 |
| Agent 认为存在的关系或影响 | 带来源、范围与不确定性的提案 | 作为待核实内容展示 |

架构图要能同时显示“批准的设计”与“观察到的代码”，二者不一致时保留漂移，不让模型为了画得整齐而覆盖任何一方。任务图的依赖子图保持 DAG；协作和消息关系可以有往返，不能为了显示通信关系而破坏调度依赖的无环性。

工具负责确定性采集，Agent 负责语义候选，框架校验并提交正式变更。人拖拽节点、Agent 调整任务、聊天里说“改一下”都经过同一变更入口，不能直接改 UI 内存就算正式生效。DSH 的任务版本检查和 DAG 校验提供了实际参考，但不要求复制其存储位置。[S03][S04]

**存放建议：**运行状态沿用现有 Kernel／平台的持久机制；若确实尚无合适实现，单机首版可选 SQLite 事务表保存小型状态、事件和邮箱，大产物保存为文件并记录引用，代码与正式设计文档使用 Git。SQLite WAL 支持读写并行，但仍然只有一个数据库写者；它不替代代码 checkout 的 Writer 租约。[S16]

**建议定稿句：**“两张图是正式记录与观测证据的可检索投影；图上编辑产生带版本依据的变更请求，经现有授权与状态规则校验后提交。图形视图可重建，批准基线与观测事实分别保存。”

**验收观察：**清空派生视图后可以重建；旧图上的编辑不会覆盖新决定；架构漂移能够定位到对应代码版本。

**P-3：秘书常驻——沿用 D-1，只澄清可用性的含义。**

不用再次表决是否常驻。身份、最近进度与入口应持续可用；打开应用即可输入和查看已有状态。若模型进程或缓存需要恢复，界面展示恢复状态，并优先呈现已有事实。持续可用的产品入口不等于模型响应零延迟，也不要求为了等待一句追问而长期保持昂贵运行。

**建议定稿句：**“打开应用即可与秘书交互并读取已有项目状态；必要的会话恢复由系统完成并可见，不要求用户重新讲述项目。”

**P-4：主 Agent 写能力——沿用 D-2，并与唯一 Writer 统一。**

主 Agent 可以具备写能力。默认委托承担该范围的角色；主 Agent 自己执行时同样要获得当前任务的写权限与 checkout 租约。负责人不在线时，通过显式接管更换执行者，不能为了保持模块归属而令工作永久等待。

这里没有引入多 Writer，也没有要求“主 Agent 所有写操作都重新问人”。既有授权足够的普通工作按既有规则执行，只有范围或权限变化才进入新的决定流程。

**P-5：首批能力——摘要入产品文档，工具和权限矩阵留给设计。**

建议采纳候选 (b)：如果产品文档不列首批能力，无法判断“配齐”到底覆盖哪些用户路径。只列行为类别，不写具体 API 字段。

| 首批能力 | 典型承担者 | 边界 |
| --- | --- | --- |
| 查目标、任务、决定、证据、角色与历史 | 秘书、协调者、执行者 | 按项目、任务和历史授权取材 |
| 提出目标／计划／架构变更并解释 | 参谋、主 Agent | 提案与正式生效分离 |
| 领取、派发、等待、报告阻塞、请求决定 | 协调者及相应执行者 | 限定责任范围、依赖与预算 |
| 读取文件、rg 搜索、查看差异；按需接入语义分析 | 调查者、执行者、审查者 | 读取权限不自动包含跨工作历史权限 |
| 修改代码、运行项目命令和测试 | 获授权的执行者 | 唯一 Writer、执行权限与既有安全边界 |
| 提交产物／完成声明、独立检查 Evidence | 执行者、Reviewer、框架 | 自述完成不能直接推进完成状态 |
| 人的暂停、取消、接管、换手与恢复 | 人＋协调者＋框架 | 明示作用范围与执行结果 |
| 查询参考资料、记忆与知识库 | 获授权的调查角色 | 不可用时说明；不虚构已检索结果 |

上述是首批能力类别，并非八个新 Agent。每条能力必须能映射到现有 Kernel 或平台接口；未提供的标记待实现。Skill 正文决定方法与质量约定，宿主授权决定工具能否执行；可信 Skill 的结构化声明只能在既有授权内被解释，不能自行授予更大权限。[S13][S14]

**P-6：目标变更——采纳安全点切换，但先禁止继续走旧目标。**

既有 D-3 保留。建议不采用“等所有运行自然结束后才处理”，也不采用“每次变更全项目杀停”。具体行为为：

1. 用户确认新目标／计划版本时，记录新版本和变更范围；受影响任务先停止新的派发与后续副作用许可。
2. 对正在执行的受影响 Run 发出取消／切换信号；到 Kernel 可识别的安全边界停止。无关工作继续。
3. 若无法迅速确定影响范围，先暂停该 Goal 的新派发，再完成影响判断；不能把“暂时不知道”当作“没有影响”。
4. 已启动的工具或外部副作用不能被假定撤销。记录已知结果、检查实际代码和环境；不确定时保留结果未知，继续核对。
5. 对受影响依赖进行局部计划修订并展示差异；保留未变任务的身份和可复用证据，不全量删除重建。
6. 旧 Run 的结果可以保存，但只有通过新版本适用性检查后才能推进当前状态。切换 Writer 前确认原 Writer 已停止可写活动；若做不到，则不交出新的写租约。

LangSmith Deployment 明确提供排队、拒绝、中断等多种并发输入策略，并指出中断可能遇到未结束的工具调用；这些是策略选项，不是“任何操作都能撤回”的保证。LangGraph 的恢复文档也提示副作用重放需要幂等处理。本建议借鉴这些边界，不要求引入其服务。[S07][S08]

**建议定稿句：**“目标变更立即阻止受影响工作的继续派发和新的副作用，正在进行的运行在安全点切换；已发生操作保留记录并核实，无关工作继续，旧结果经当前版本适用性检查后方可使用。”

**验收观察：**在任务执行中改变目标后，旧结果不会把新任务误标完成；暂停期间无两个 Writer；取消后保留实际已发生的修改。

**P-7：共同编排——并行研究与审议，首版单一提交正式调度。**

建议选择 (a)，但“一个协调者”只限制正式调度的归属，不把调查、方案、状态说明、接口审查都压在同一个 Context。秘书整理事实，参谋可并行提出方案，协调者把采纳结果提交给框架；任务可自动执行到既有授权边界。

Cursor 的实践说明规划者可以派生子规划者；Claude Agent Teams 展示了独立上下文、成员通信和共享任务。两者支持“多人参与规划”的可行性，但不提供“所有项目从第一天都该多层指挥”的结论。[S01][S02]

首版建议：一个正式调度提交者；研究和审查 Agent 按任务临时参与，身份与资料仍可复用；同一议题先独立产出，再进行一轮针对具体分歧的质疑，有新证据才追加调查。采用什么方案、谁负责执行、何时结束，必须形成决定或明确待决事项。

**增加领域协调者的重审条件：**持续出现互相独立的工作流；同一协调者的待处理事件、重复加载和派发等待已构成可测瓶颈；领域边界和交付接口能够稳定说明；增加层级后需要证明总成本、遗漏和进度至少有一项实际改善，并控制其他指标退步。先不设任意 Token 百分比或 Agent 数量为普遍阈值。

人仍保留目标与未授权取舍的决定权；协调者的决定权只在已授权的责任范围内。定时轮询、超时计数、预算检查、邮箱恢复可交给确定性框架，不必增加“监督监督者”的模型链。

**建议定稿句：**“允许多 Agent 对编排提供调查、计划和审查；首版由一个协调者在已授权范围内提交正式调度。出现可测的信息或调度瓶颈后，再按工作领域增加有明确责任边界的协调者。”

**P-8：承担范围——责任按领域保持，交付按工作包组织。**

不要在模块、工作包、目标中选一个取代其余所有粒度。建议定义三个不同的范围：

- **角色的长期责任范围：**一个领域或模块组，以及适合回答的问题。它便于复用认识，不要求每个目录常驻一个 Agent。
- **本次委托与验收范围：**一个可交付工作包，可以跨模块，包含目标、涉及接口、输入、输出、完成依据与升级条件。
- **执行权限范围：**任务实际允许访问／修改的资源，以及当前 Writer 租约，不由“熟悉这个模块”自动推导。

Goal 可以跨多个工作包，但首版仍只绑定一个 Workspace。跨模块任务指定一个交付负责人，相关模块角色提供意见；不让每个角色分别改一段接口、最后才发现契约不同。这里是职责关系的定义，不要求新增一个工作包子系统。

**建议定稿句：**“角色在项目的领域或模块组内积累认识；执行以可验收工作包委托，必要时跨模块；每个工作包有唯一交付负责人，访问和写权限按任务单独绑定。”

**P-9：生命周期——四个动作明确，压缩对象应为会话工作集。**

| 动作 | 建议触发条件 | 必须保留或检查 |
| --- | --- | --- |
| 产生 | 新工作需要独立责任／上下文，现有合适角色无法承担 | 范围、当前授权、输入、预算和交接来源 |
| 拆解 | 存在可独立调查或交付的子任务，接口和完成依据可说明 | 父任务义务、子任务负责人、依赖和汇总责任 |
| 压缩 | 预计下一段工作会超出上下文预算，或历史噪声已影响工作 | 决定、证据引用、未决事项、失败原因、当前版本；原记录可回查 |
| 归档 | 没有未交接的活跃义务，且近期不再需要参与；由明确操作触发 | 身份、范围、历史、产物和可检索索引；释放运行资源 |
| 重新启用 | 新请求需要该角色，现有身份和责任范围仍合适 | 当前授权、代码与计划变化、资料有效性；创建或恢复合适会话 |

“拆解角色”实际应指拆解其承担的工作；“压缩角色”实际应指压缩其会话工作集。角色身份本身不因压缩而变化。原文已承诺归档后可重新启用，建议正式保留，不再把能否重新启用悬空。

首版遵守“显式压缩和归档”，不偷偷加上自动回收服务。框架可提示接近预算上限；真正无法安全继续时暂停并提供续接操作。未来在明确预授权策略下再自动执行。

Anthropic 将压缩、外部笔记、子 Agent 隔离列为不同的长任务手段；Gas Town 则区分持续身份与短期会话。本产品可采用这个分离，而不要求所有角色永久保存同一串原始 Context。[S10][S15]

**建议定稿句：**“角色身份与责任可持续复用，工作可拆解，会话工作集可显式压缩；归档退出当前执行并保留检索和重新启用能力。恢复时重新核验现行权限与资料适用性。”

**P-10：五类参考来源——统一出处，检索路线随问题而变。**

| 来源 | 何时取用 | 进入 Context 的形式 |
| --- | --- | --- |
| 工作区文件／代码 | 回答现状、定位符号、核对修改 | 当前版本相关片段＋路径／内容版本 |
| 人提供的需求和反馈 | 目标、价值取舍或主观要求不明确 | 原始要求／决定的引用；保留是否已确认 |
| 网络资源 | 问最新事实、框架行为、已有工程实践 | 官方资料优先的短摘录／结论＋链接和取用日期 |
| 记忆与知识库 | 需要历史理由、约定、经验或已研究材料 | 小段命中内容＋适用范围和原始证据 |
| 模型自身知识 | 提出搜索方向、候选解释、方案草稿 | 标注为待核实假设；不能直接充当项目事实 |

统一要求：能说明来自哪里、适用什么范围、基于哪个版本、何时获得、哪些尚未验证；不是每项都强制具有同一种时间戳或代码哈希。检索到事实也不自动提升该材料的授权级别。

对于“现在是否完成”先查正式状态；对于“这个函数在哪里”直接 rg／符号搜索；对于“为什么这样设计”查决定和相关工作记录；有局部知识缺口再咨询负责角色。图是可用的路由入口，不能把“查图→必须问到原 Agent”写成唯一通路。否则原 Agent 离线、索引缺失时又会出现文档所批评的死板问题。

找不到时在预算内扩大检索范围，明确标注仍未知的部分；只在关键缺口影响决定时向人提出具体问题，不为五类渠道逐一打断人。Anthropic 的即时检索实践支持用文件与搜索工具按需获取材料；其研究系统也通过外部产物和引用减少信息转述。[S10][S11]

**建议定稿句：**“参考资料以带出处与适用性的片段按需进入上下文；系统按问题选择状态查询、图定位、静态搜索、历史检索或角色咨询，不强制每个问题依次经过全部渠道。”

**P-11：验收数字——历史保留，新口径单独版本化。**

建议保留 §6 的旧验收陈述和适用范围，标记为附件中记载的历史结论；本次无法访问其证据，不予重新认定。新增要求建立新的验收说明，不能由产品文字改动直接把旧门禁变成通过。

对于新版指标，建议如下：

| 原表述 | 建议新口径 |
| --- | --- |
| 状态查询准确率 100% | 结构化状态与正式记录的一致性在指定测试集上要求全部通过；自然语言解释另测事实错误、来源覆盖、过期信息和恰当“不知道”，并统计回答覆盖率，防止靠全部拒答达标 |
| 成功率不下降 | 同一冻结任务集、模型／工具条件、预算策略下做配对比较并记录重复运行；样本不足不能声称统计上的不退步 |
| 缓存命中率 99% | 保留为明确条件下的热调用目标；同时报告全量输入 Token 命中率、热调用命中率、可复用前缀利用情况及实际费用，不改变旧数字的分母 |
| 压缩不能破坏前缀，否则就是亏 | 比较压缩调用、重建／缓存写入、后续输入、输出和检索成本，以及质量／恢复表现，再判断是否划算 |
| 任一失败归因 | 保留主要原因、伴随原因及暂未确定原因；不能为了满足分类而猜定一个原因 |

本次仅复算了用户文档提供的价格假设与输入规模，并未核实该价格当前适用于哪个供应商／模型，也未复跑所谓“当前实测”。按 2,854,860 输入 Token、命中 0.02 元／百万、未命中 1 元／百万，89.99%、99%、75% 对应约 0.3371533、0.0850748、0.7565379 元，与原表四舍五入吻合。

这张表能证明“相同输入规模下更高命中率更便宜”，不能证明“保留更长上下文永远更便宜”。例如按相同假设，10 万 Token 全部命中是 0.002 元，1000 Token 全部未命中是 0.001 元。这只是成本反例，不代表短上下文能完成同一任务；是否采用仍要验证任务质量。

建议成本统计使用账单互斥分类：普通未缓存输入、缓存读取、供应商单列计费的缓存写入、输出，再加工具／检索及环境费用。没有单列缓存写入的供应商只统计普通输入与缓存读取，避免重复计费。完整任务费用还包含失败、重试和压缩。

新定义必须和旧 89.99%／89.10% 的分母、样本、模型配置一起保留；不能用“缓存前缀利用率”替换“全量输入命中率”后宣称目标达到。OpenAI 官方文档明确区分会话连续性与缓存，并建议压缩后比较总费用；这是判断方法的依据，不意味着本项目采用 OpenAI 的价格。[S09]

**建议定稿句：**“保留历史验收证据及范围，新增行为独立验证；99% 为指定热调用条件下的优化目标，是否接受上下文与生命周期改动，以任务质量、恢复可靠性和完整工作成本共同决定。”

**P-12：接管入口——侧栏为统一工作区，其他入口只负责定位。**

建议主对话保持默认入口；点击 Agent 名册、任务节点或在对话中点名，都打开同一个侧栏。侧栏显示：负责人、任务与版本、最近进度、已有证据、待决项、当前是运行／等待／恢复，以及“询问、追加要求、暂停、取消、替换／接管”等明确动作。

查询状态首先读取已保存的投影和证据，不向正在执行的 Session 追加一个高优先级新任务。确实需要原执行者回答时显示“已请求补充”，由安全点回复，或启动独立只读问答并标注它所依据的快照。查看“当前 Context”应展示实际材料目录、版本和可公开记录，不承诺跨供应商提供完整内部思维过程。

直接修改子任务时，该指令也写入正式记录并通知协调者；涉及其他任务、跨模块契约或新权限时，走已有决定路径。换手按钮只有在原执行者的写活动已终止并完成交接后，才显示新执行者开始写入。

**建议定稿句：**“用户通过统一 Agent 侧栏查看和介入工作；图、名册和对话点名共享这一入口。查询默认读取已有状态，执行控制和任务变更通过正式路径回流。”

**P-13：共享载体——三类职责足够，不建设独立群聊产品。**

建议共享载体包括：正式任务／决定／Evidence 引用；协作文档与版本化产物；定向邮箱。一个载体可以在现有界面合并展示，数据责任仍需明确。

邮箱负责把信息送给相关人或 Agent，任务状态由框架维护，文档负责保存详细方案与产物。消息到达不等于任务成功，讨论同意不等于已获授权，文件存在不等于已通过验收。消息只保留短说明和稳定产物引用，必要时再读正文。

协作文档允许反复修改，但一次被审阅或用于决定的版本必须可以定位。DSH 的持久邮箱和任务版本机制可参考；不用引入其插件，也不能把其 advisory writeScopes 当成独占锁。[S03][S04]

同类／竞品材料只在具体决策或接口问题需要时检索，先读官方文档和许可证，记录版本与采用的部分。参考设计不等于整仓导入或获得使用授权；来源无法取得时保留缺口，不用相似项目冒充。

**建议定稿句：**“平台通过正式协作记录、版本化文档／产物及定向消息共享信息；共享载体不限定为某个外部留言板实现，消息与材料均不直接替代正式状态和授权。”

**P-14：Skill／Prompt 资产——混合来源，轻量版本化。**

建议自研平台特有的计划提案、交接、状态解释、冲突上报、Evidence 提交流程；代码调查、审查、测试、资料检索等通用做法参考现有实践并适配。首批可围绕这几类流程组织，数量由真实任务决定，不按角色数或模块数铺开一大批 Skill。

平台核心约束放在稳定系统规则和运行时：项目隔离、授权、唯一 Writer、完成规则。Skill 保留触发条件、工作方式、必要材料和示例；只在相关时加载正文。Agent Skills 规范和实现指南支持逐层披露，适合控制常驻上下文。[S13][S14]

每项资产记录来源、版本、适用范围、已验证的真实任务及失败例；在 Run 中记录用到的版本。修改需能回退，格式合法不等于行为有效。不建设独立技能市场、自动生成技能工厂或新的注册体系。

**建议定稿句：**“Skill 与 Prompt 采用自研和参考适配相结合的方式，按版本维护并用实际任务回归验证；平台特有契约由运行时和稳定规则保证，领域方法按需加载。”

**P-15：真实项目验收——两类项目，任务和环境先冻结。**

建议首批使用：自己的 coding-platform（验证秘书、图、接管、目标变更等整条交互回路）；一个技术栈可运行、维护历史清楚的外部开源项目（检验是否依赖平台自身的特殊知识）。此处未检查候选仓库，因此不虚构已选定项目。

选取标准是可安装、可运行、原问题可重现、修复有可独立检查的依据、改动范围可控制。SWE-bench 用真实仓库、候选补丁和项目测试构建验收，值得借鉴其可重现方式；它本身不能覆盖本平台的人机交互和生命周期承诺。[S17]

每个验收任务至少固定：起始代码版本、环境／依赖、需求与授权、验收依据、预算与超时、是否允许网络、哪些参考材料可见。历史修复任务应遮住最终补丁和直接泄露答案的材料，同时披露公开任务可能已被模型见过，不能把全部成功归功于编排。

任务包覆盖真实修复／修改、状态查询、目标中途变化、跨模块接口争议、暂停恢复与换手。可以在真实任务上注入断网或进程终止来检查恢复；这仍使用真实任务，不等于用玩具任务替代验收。机制单元测试作为补充，不冒充端到端成功。

成功定义既含项目结果，也含责任／证据／授权闭环。模型自评、运行退出码、最终补丁与人类补丁相似度，都不能单独代表成功。有限任务先用于发现退步与校准门禁；需要统计声称“不退步”时，再根据观测方差和容忍差异确定样本量。

**建议定稿句：**“首批在自有项目与外部维护项目上运行可重现任务，冻结版本、环境、授权、材料和验收条件；真实交互回路与结果质量同时验证，人工故障注入只用于补充恢复检查。”

**P-16：Session 与 Run——一对多，同一工作历史串行提交。**

建议关系：一个持久角色身份可以先后拥有多个 Session；一个 Session 可以包含多次 Run；每次 Run 的调用和结果归属于明确 Session。Session 不在每个模型响应后结束，同一任务的连续推进优先在适用的 Session 中继续。

为避免出现两份相互矛盾的当前历史，首版同一 Session 只允许一个拥有执行控制权的活跃 Run；新要求默认排队，明确的改变／停止按 P-6 在安全点处理。只读状态查询走投影，独立问答或并行调查另开子 Session。Kernel 内部一个 Run 的并行工具调用不受这一规则禁止，仍遵守工具自身并发和写入规则。

LangSmith 的并发输入机制将排队和中断显式区分，说明这里需要产品策略，而不是由消息偶然抵达顺序决定；其 double-texting 是 Deployment 能力，不应声称开源 LangGraph 自动具备完整服务。[S07]

子 Session 两种初始化：继续已调查工作时选择受控继承；独立审查时选择新上下文并传入任务、产物和验收依据。继承先核验权限和版本，不默认把父 Session 所有材料复制给所有人。Deep Agents 提供 isolated／fork 两种形式，可作为该选择的参考。[S05]

Session 应记录可获得的消息、工具输入输出、材料版本、公开决定与交班；不把完整内部思维链作为可恢复或跨模型兼容的必需数据。压缩保存新的上下文检查点和来源关系，是否保持供应商会话 ID 留给 Kernel 适配。

**建议定稿句：**“Session 属于一个 Agent 身份并可包含多次 Run；同一 Session 的执行控制与历史提交串行化，并行工作使用独立子 Session。长期连续性由持久记录和有界交接保证。”

**P-17：历史状态——变更记录＋投影＋检查点，限定覆盖面。**

建议采用两者结合，但只对 Goal／Plan／Task／责任／授权相关版本／Evidence／Decision 等影响正确性的状态保存正式变化记录。日志、模型输出、文件内容不全部转成一种巨型业务事件。

一次正式状态变化同时留下来源与版本、更新当前可查询状态；检查点用于加速重启。恢复以最新可用检查点和后续记录为依据，不重跑模型来猜出历史。若现有 Kernel 已有 Session／Run 日志和单次恢复机制，平台引用其记录并维护跨任务关系，不再复制一套 Kernel。

LangGraph 的检查点与跨线程 Store，以及 DSH 的可恢复任务／邮箱记录，展示了运行恢复和长期状态需要明确持久机制；“关键事件＋投影”的具体组合是对本产品的建议，并非这些项目完全相同的实现。[S06][S04]

代码历史使用 Git 版本；尚未提交但必须跨恢复保存的修改记录为补丁／内容快照，并附基线和哈希。Git tree 不自动包含未提交修改，gitignore 排除的运行记录也不会因此获得备份。可回溯承诺应明确覆盖正式代码版本和交接／恢复检查点，不默认为每次临时写入都保存完整快照。

项目状态事务与文件系统修改不是天然原子的一件事。遇到崩溃，先检查实际产物与操作记录，再决定是否继续或补做；不能把“日志里打算写”当作“磁盘一定写完”。暂停或恢复框架状态也不能自动撤销已完成外部操作。[S08]

首版不引入 Kafka、分布式共识或完整通用 Event Sourcing 框架。删除或重算的是派生索引；正式历史以更正记录解释旧结论，保留原事实。归档代表退出活跃使用，不等于自动删除历史；保留与删除规则另有明确策略。

**建议定稿句：**“正式状态保留可追溯变更记录与当前投影，检查点加速恢复；代码和产物按版本及必要检查点关联保存。平台复用 Kernel 的运行记录，不靠重放完整会话恢复项目事实。”

**P-18：静态工具检索——搜索是渠道，索引是可选加速层。**

原来的 (a)/(b) 不必互斥。建议 rg／grep、文件读取直接面向当前文件；架构图可提供路径范围和候选模块。需要符号引用、跨文件关系时，再用已有 LSP／语言解析器的索引。AST 也可能现场解析，无需先统一建设全仓索引。

索引必须绑定代码内容版本或明确标注更新时间。语义索引失效时重新解析或回到直接搜索，不能仅因查询没有命中就断言不存在。只有“被接受为 Evidence 的搜索结果”进入事实记录；不要把全部搜索命中复制到事实数据库。

因此保留三种查询能力：角色咨询、静态搜索、状态／记忆查询；两种或更多索引只是各自的实现。Anthropic 的即时检索案例为“直接搜索＋按需材料”提供参考，不能由此推断 AST 或索引一律无用。[S10]

**建议定稿句：**“静态搜索直接针对当前文件和代码，按需利用架构范围与版本化语义索引；搜索渠道不强制归属于 Agent 索引或事实索引，已核验结果可成为 Evidence。”

**P-19：Run 是否单列——单列执行记录，解除‘只有三类来源’的硬约束。**

建议逻辑上单列 Run／Attempt：它们必须能独立查询运行状态、时间、工具结果、费用、取消与恢复情况，不能依赖模型从 transcript 推断。若 Kernel 已提供结构化执行记录，平台只建立引用、关联与投影，不复制全部日志。

“谁提供材料”和“材料最终放哪里”不是同一个分类问题。人确认、外部回执、代码观测、运行日志都可能被存入正式状态或 Session；不能因为最终落在某个容器中，就把它们的出处抹掉。§7.14 的五种参考来源也无需与 §7.2.1 的三种容器强行一一对应。

**建议替换 §7.2.1：**“两张图从正式项目与执行状态、代码／文件观测、角色与会话记录中形成，保留各记录的人、工具或外部来源。Run／Attempt 独立可查询；知识库与网络材料经授权检索和适用性检查后，可作为有来源的参考或 Evidence 引用。”

这里不增加未经授权的数据来源，也不把一份知识库材料自动升级为事实。它修正的是概念层级，避免未来每接入一次测试回执都要改写‘除此以外不存在’这一产品声明。

**P-20：跨项目形态——维持后置，当前只固定作用域。**

保留 D-1 和 §11 的项目内复用边界。首版所有状态、角色、Session、产物和检索都能确定当前 Workspace；越界请求给出明确原因，不从另一个项目默默补材料。用户切换项目时呈现相应状态，不延续前一个项目的执行权限。

当前只需在现有对象上维护可靠的项目归属与出处，必要时支持用户明确选中的资料导入；不提前建设跨项目向量库、共享角色池或跨项目 Agent 网络。以后用只读工具按明确授权范围检索，返回带来源片段；“同一用户所有项目”不自动等于精确历史授权。

启用时机是出现反复的真实跨项目问题，而且用户已能说明允许读取哪些材料。跨项目检索、跨项目 Agent 通信、跨项目执行是三个不同范围，不能用开启前者顺带开放后两者。

**建议定稿句：**“首版以项目作用域隔离角色复用、执行与检索；跨项目能力后置，未来先以显式授权的只读工具开放，不自动扩展通信或执行权限。”

**下一步的审阅顺序**

先采纳产品语义：草案／基线／事实如何区分，谁可提交正式调度，哪些变更仍需人决定，角色与会话如何分离。随后在既有模块文档里审阅以下接口行为：变更与版本校验、任务派发与接管、定向消息与恢复、Context 选择与交接、Evidence 适用性与费用记录。具体函数、表结构和新目录现在不需要冻结。

验收顺序建议：先在真实工作中跑通“查询不打断执行—中途改目标—安全停写—换手恢复—旧结果适用性检查”；再比较单长会话、首版协作、增加协调层后的质量与费用。只有出现具体瓶颈，才引入更多层级或索引。
