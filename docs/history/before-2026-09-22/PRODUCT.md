## 1. 产品陈述

Agent Platform 为一个用户提供长期、统一的协作界面：在同一处讨论需求与架构、查看多个隔离 Workspace 的进度与状态图、协调不同角色的 Agent。图形与文本说明共同帮助用户掌握当前工作、依据和待决事项。

在这套界面背后，产品由两层组成：**面向人的主 Agent**（承担"类超长上下文"的角色，接收需求与目标、回答问题、把项目状态稳稳传给执行方）和**面向执行的子 Agent**（承担被拆解出来的工作单元）。主 Agent 面是默认界面；人默认不需要关心下面有几个 Agent，而不是被禁止知道——界面上有一个入口，可以列出当前有哪些子 Agent、各自在做什么（见 §4 第 13 条）。这一层修正的记录：旧版写"人只面对主 Agent 面，不需要知道下面有几个 Agent"；现改为"默认不需要关心，但必要时可直接介入"。

平台框架组织整个工作生命周期：Agent 承担规划、集成、语义审查与解释，工具承担可机械化的采集、检查与更新，框架依据规则维护持久状态、验证和展示。进度更新是正常执行路径的一部分，不依赖额外的人工或模型提醒。

`coding-agent` 继续作为 Execution Kernel。Agent Platform 不重写其模型循环、工具、安全或单次 Run 恢复能力。

产品的两条主张：

1. **可读性与注意力约束**：结构本身限制 Agent 一次要承担多少注意力——Agent 侧只装配这次工作真正需要的上下文，人侧靠界面把相关信息收拢；负担更小，效率更高，有了可复用的角色才能管理更多 Agent。
2. **成本是设计的一部分**：成本在架构设计阶段就要算进去，而不是实现完再优化；上下文怎么装配、角色怎么回收，都要先算钱再动手。**连续复用是默认方案**：实际测试已有很高的缓存命中，而"选取和重组上下文"本身又要大量编排与工程投入，所以默认延续既有 Session、追加消息、按需查询；重组要拿出实际收益（§7.5、§7.14、§9.2）。

> 此处替代旧版表述：旧版写注意力约束是"Agent 侧靠模块边界只留相关上下文"。现改为：**判据是必要性，不是模块边界**——只装配这次工作真正需要的上下文，而"必要"本身就跨模块边界。旧的"限制注意力负担"这一层含义保留。
>
> 此处替代旧版表述：旧版把 Agent 描述为"用完即弃"的一次性执行者（角色模板即"短生命周期 Agent"），并允许"按任务配置短生命周期角色"。现改为：**角色必须复用**，复用后角色有自己的生命周期（产生／拆解／压缩／归档，见 §7.1）。
>
> 此处替代旧版表述：旧版问题域以"一个不断增长的会话"为背景。现改为：产品以**有生命周期管理的多 Agent 编排**为形态，会话不再作为增长的容器；但**连续工作默认续用既有 Session**，不因一次 Run 结束或一次派发就重建整套上下文（§7.5）。
>
> 此处替代旧版表述：旧版把"不符合持久化"直接对应"每次从零组装"，并以"重建更便宜"为默认立场。现改为：**连续复用是默认，上下文重组需要证明收益**——选取与重组上下文本身有编排、运行与工程成本（依据：2026-09-20 决策意见 P-1～P-20，见文首来源）。

## 2. 问题来源：Context、状态、人的注意力，以及两个毛病

### 2.1 原来的起点

产品从一次执行的 Context 与跨执行的状态如何协作出发：Context 是模型本次判断能使用的材料，需要保持相关、有效且有界；Goal、角色责任、计划、执行事实与决定则需要跨 Run 和 Agent 持续维护。长期系统还要管理这些状态的版本、适用性和生命周期，并把相关部分送回每次执行与人类界面。

当这些责任集中在一个不断增长的会话中、缺少框架约束时，会出现下列现象——这些现象共同指向 Context 管理、外部状态、框架控制和协作反馈的工程问题。

- 长任务中的 Todo 与实际进度脱节；
- Context、Run 或 Agent 更换后丢失工作前沿；
- 用户询问状态会打断正在执行的 Agent；
- 多 Agent 的依赖、写入冲突和完成依据不可见；
- Worker 的"已经完成"容易被误当作系统完成；
- 项目架构随长期开发漂移，却缺少持续对账和决策记忆。

### 2.2 毛病一：死板

**人想了解一个关于项目的问题时，机制把用户拒绝掉。**

典型场景：人问"这个模块现在到底怎么回事"，系统因为当前没有可问的对象、没有可用的检索入口、或能力未被配置，直接拒绝。用户观感很差：产品明明在管理这个项目，却答不上来这个项目的事。

这不是一个边界问题，而是**产品能力缺口**：没有可复用的 Agent 主体，人就没有可以追问的人。

### 2.3 毛病二：不符合持久化

**靠 context 不断组装，导致缓存命中低 + 持久的 IO 消耗，性能差。**

典型表现：每开一次运行就重新装配一次完整上下文；后继运行不继承前驱已经读过的内容；已经查过的事实再查一遍。代价直接体现在钱与时间上（见 §9）。**本产品的默认解法是连续复用**——延续既有 session、增量补充，而不是发明一套更聪明的重建方式（§7.5、§7.15）。

### 2.4 两个毛病是同一个问题的两面

没有可复用的 Agent 主体：既没人可问（死板），也每次从零组装（不符合持久化）。因此本产品的核心改造是**让主体可复用、让上下文可增量刷新**，而不是单独修两个症状。

### 2.5 本次确立的转变

把"每次运行重新装配上下文、Agent 用完即弃"，改成**有生命周期管理的多 Agent 编排**：主 Agent 面向人，子 Agent 面向执行，靠架构图与任务图做编排与检索，靠角色复用提高缓存命中、降低成本。

目标与计划可以随时修改；**目标一变，任务图跟着变，编排也跟着变**（§5.5）。

## 3. 术语

| 术语 | 含义 |
| --- | --- |
| **Project / Workspace** | 隔离的工作单位；首版单用户、单机，可同时管理多个 Project/Workspace |
| **Goal** | 人提出并可修改的目标；一个 Goal 首版绑定一个 Workspace |
| **Runtime Task / Attempt / Run** | 目标落到任务图后的执行单位与一次具体运行 |
| **主 Agent（超长上下文那个面）** | 面向人的一层：接收需求与目标、回答问题、把项目状态传给执行方；它不需要装下整个项目，而是**知道去哪里问** |
| **子 Agent** | 面向执行的一层：承担被拆解出来的工作单元 |
| **角色（Role）** | 可被复用、有生命周期的承担主体：可产生、被拆解、被压缩、被归档 |
| **两张图** | 架构图（项目是怎么构成的）与任务图（要做什么、由谁协作完成），见 §7.2 |
| **秘书／参谋** | 与人协作的角色：整理状态、规划与上报、承接编排派发、产出方案、接受反馈、解释自己的方案（职责分工见 §7.7.1） |
| **Evidence / Decision / Handoff** | 证据、决定与交班记录；三者都是跨 Run 保留的可追溯事实 |
| **A（agent-team）** | 外部参考实现，**只作参考**：只复用"编辑机制"与"编排通信（Roster / mailbox）"两处；不作为依赖、不作为基座 |

> 【待批阅】"主 Agent"与"超长上下文那个面"在讨论中常被并称，本文按同一层理解。秘书／参谋／协调者的职责分工与"避免变群聊"的约束见 §7.7.1；外部实践参考清单见附录 A。

### 3.1 概念澄清：状态、历史、知识库、skill、context、session

本节把这组概念各自是什么、彼此什么关系写死。**架构、模块状态与接口文档里再出现这几个词时，含义以本节的界定为准，不再重新解释。**

#### 3.1.1 定义

**项目状态**：项目此刻是什么样——目标、任务与计划、当前进展、角色分工、两张图上的位置。由框架与 Agent 的工作共同产生（事实由框架归约、语义判断由 Agent 提供），自项目建立起存在，随项目归档而结束。

**代码状态**：代码此刻是什么样——某个时点上代码树的实际内容与结构。由真实写入产生（谁写、由写租约约束），自第一次写入起存在，随项目归档而结束。

**历史的项目状态与代码状态**：上面两者在时间上的轨迹——某次决定之前的项目状态、某个提交之前的代码状态。它**可回溯**，且不覆盖：读取历史不改变当前状态。由状态变更与代码变更产生，与项目同寿。

**知识库**：跨项目、跨时间沉淀下来的资料与经验——编码规范、架构说明、验证方法、经过选择的案例，以及从实际工作里复核出来的经验。由人或系统沉淀产生，长期存在；它可以持续更新。

**skill**：一类被命名、被版本化的做事方式——它决定"这次被允许做什么、以及做到什么算好"，也是可复用的产品资产（§7.6）。由产品设计或参考产生并维护，长期存在。

**agent 的上下文（context）**：某个 agent 在**一次装配中实际拿到手**的材料——已核验的事实、按图取回的内容、共享载体上的材料、相关的 skill 与知识库片段、本次指令与工具定义。它在运行时才产生，每次装配结束就消失；下一次装配重新产生。

**session**：一段有边界的工作过程的载体，由一次委托或一次交互开启。它承载这段边界内产生的记录、以及这段边界内的上下文装配结果，自开启时存在，随这段边界结束而关闭。

它的实质是：**session 就是一个 agent 的历史上下文**（即 dsh 的 session）。它可以包含多个请求与多次交互，但**始终属于同一个 agent**。

一个持久角色身份可以拥有多个 session；**一个 session 可以包含多次 Run**，每次 Run 的调用与结果归属于明确的 session。首版同一 session 只允许一个拥有执行控制权的活跃 Run：新要求默认排队，明确的改变或停止在安全点处理（§5.5）；确需独立并行调查或独立审查时使用子 session。

session 与 agent 的 context 相近，但不是同一个东西：**context 是在这次工作里被装配出来、供这次使用的那部分**；session 除此之外还包含**部分思维链以及工具的详细结果**。

> 此处替代旧版表述：旧版只把 session 写成"一段有边界的工作过程的载体"，没有说它的实质。现改为：**session 是一个 agent 的历史上下文（dsh 的 session），属于同一个 agent；context 是它在这次工作里被装配出来的那部分**。

> 【已决】session 与 Run 的对应关系已定（§12.1 D-5）：**一个 session 可以包含多次 Run**；同一 session 首版只允许一个拥有执行控制权的活跃 Run。session 是否跨越工作边界开启，仍按"连续工作默认续用"处理（§7.5）。

#### 3.1.2 一张小表：谁持久、谁随 session 生灭、谁只在运行时存在

| 概念 | 何时存在 | 何时消失 | 是否进入 agent 的上下文 |
| --- | --- | --- | --- |
| 项目状态 | 项目建立起 | 项目归档 | 稳定事实按需进入 |
| 代码状态 | 第一次写入起 | 项目归档 | 只按取用的片段进入 |
| 历史的项目状态与代码状态 | 与项目同寿、可回溯 | 项目归档 | 只按检索结果进入 |
| 知识库 | 长期存在 | 不随 session 消失 | 只按检索到的条目进入 |
| skill | 长期存在 | 不随 session 消失 | 只有这次选中的 skill 进入 |
| agent 的上下文 | 运行时装配时 | 本次装配结束 | —（它本身就是上下文） |
| session | 一次委托或交互开启时 | 这段边界结束时归档，但保留可恢复 | 它的装配结果按需进入；连续工作默认续用既有 session（session 集合同时是两张图的输入之一，§7.2.1） |

#### 3.1.3 关系（不是并列名词，是一张层级）

- **持久层**：项目状态、代码状态、历史状态、知识库，以及 skill 的资产本体。它们跨 session、跨 Run 存在，不因某次装配结束而消失。
- **session 层**：session 是这段工作过程的载体，也是一个 agent 的历史上下文；上面持久层的事实与资产**进入** session，但不等同于 session。session 的集合本身又是两张图的三类输入之一（§7.2.1）。
- **运行时层**：agent 的上下文是 session 内的**装配结果**，不是 session 本身；它是装配的产物，随装配结束而消失。
- **当前状态与历史状态是同一事实的两条读法**：当前状态是"现在这一刻"，历史状态是"可回溯的轨迹"。读取历史不改变当前状态。
- **知识库与项目/代码状态是双向的**：它**沉淀**两者的产物（经过复核的经验与资料），同时也是**检索入口**——查它不改变项目与代码本身。
- **skill 处在能力与资产的交叉位置**：它是**能力约束**（决定这次准不准），也是**资产**（可设计、可参考、可版本化）。它不属于上下文，除非这次被选中装配进来。
- **context 与 session 不是一回事**：context 是 session 内的装配结果，**不随 session 自动继承**；跨 session 继承的是持久事实与资产，而不是上一轮的原文装配结果。
- **四者要分清**：角色模板规定职责，角色实例承担责任；**session 保存连续工作历史，Run 是其中的一次执行，context 是某次模型调用实际可见的内容**。一次响应、一次派发或一次 Run 结束，都不自动触发新 session。
- **归档退出活跃，不等于删除**：归档保留身份、session、产物与重新启用能力（角色退出活跃运行不意味着模块或图节点应被销毁）；模块的撤销另按结构变更处理（§7.2.4）。
- **哪些进入上下文、哪些只在外部被检索**：进入的是"这次必要"的那一部分——稳定事实、相关历史增量、按图取回的内容、共享载体上的材料、选中的 skill、检索到的知识库条目、本次指令与工具定义；只在外部被检索的是完整历史轨迹、完整知识库、完整代码树，以及这次没选中的 skill。**知道去哪里问，比把全部东西装进来更符合本产品**（§7.8、§7.15、§9.2）。注意 session 不直接进入上下文：可作为输入被检索到的是 session 集合（§7.2.1），装配出来的是 context。

> 此处替代旧版表述：旧版在"连续执行"一节写的是"工作不属于某个模型 Context"，但没有区分 session 内装配结果与跨 session 继承的持久事实。现改为：**context 不随 session 自动继承；可继承的是持久事实与资产**（见 §7.4、§7.5）。

> 【已决】历史状态的承载已定（§12.2 P-17）：**复用 session／Kernel 的持久记录与恢复机制**，图持久保存正式结构与关联，代码历史用 git 版本 + 必要快照；产品要求仍是"必须可回溯、不覆盖"（§3.1.3、§7.2.2）。

> 【已定】知识库按**两者都是**写（沉淀 + 按需检索），与 §7.8 一致；知识库与网络资料经工具读取后，其使用过程与来源进入对应 session，需要作为依据时建立明确引用。

## 4. 产品承诺

用户能够：

1. 在同一协作界面查看和切换多个 Project/Workspace；
2. 创建 Goal，通过状态图和文本说明查看由框架维护的计划、进度、阻塞及其依据；
3. 查询或讨论正在进行的工作，而不必打断源 Worker；
4. **随时询问项目的状态，且不被机制拒绝**：要么得到回答，要么得到明确的"不知道 / 依据不足 / 缺谁的材料"，而不是被挡回；
5. 在安全边界暂停、继续、取消，并**直接修改目标与计划**——包含目标、任务计划、任务与计划三层；自动化对目标的改动必须经过人；
6. 看见 Agent 分工、当前 Run、Evidence、Handoff 和失败原因；
7. 与秘书／参谋 Agent 共同确立需求、形成架构方案并讨论变动，理解关键选项、影响与已接受决定；
8. **秘书／参谋给出的方案可以被人追问并被解释**：能问"为什么这么定、依据是什么、还有哪些备选"，解释基于已产出的那份方案与它依据的材料，不另起一份新方案；追问在对话框或侧边栏里就能进行；
9. **Agent 可复用**：一个角色探索过、改过某个模块之后，它对该模块有可用的认识；之后问它，它能回答。复用是常规路径，不是特例；
10. 在 Run、Context 或 Agent 更换后继续工作；
11. 追溯当前架构为什么如此，以及哪些漂移尚未处理；
12. 在需要人选择的需求／架构取舍、风险授权和未预授权变化上决策；普通已授权工作由框架与 Agent 闭环推进，并提供可见结果；
13. **在必要时直接介入子 Agent**：看到当前有哪些子 Agent、各自在做什么；直接对某个子 Agent 下指令、追问它当前的上下文与状态；暂停、替换或收回某个子 Agent 手上的活；处理完之后把状态交回主 Agent 面（路径见 §5.6）。

方案在人确认之前只是方案：不落到执行、不改目标、不改两张图。这一点适用于秘书／参谋产出的所有方案与修订。

回答带来源与事实校验：检索到的东西要能说清来自哪里、是否仍然有效；校验不通过时明说"不确定"，不补全。

拿不到就说拿不到：材料、能力、网络、记忆任意一类缺失时显式说明，不静默跳过、不用空内容顶上。

成本口径透明：任何"重新装配上下文"的做法都要能算出金额并说明是否划算；**上下文选择与编排本身的实现、调试和维护成本要单列**，不能只核算模型 Token 账单（见 §9.2）。

能力可配、边界可控：能力不写死、不在编译期定死为不可用；用 skill 约束"这次准不准"；首批能力先配齐，超出编排范围的需求按需显式扩展（见 §7.6）。

> 此处替代旧版表述：旧版第 4 条为"在安全边界暂停、继续、取消或修改目标"。现改为：**人可直接改目标与计划，自动化改动必须经过人**；"能改目标"是产品的一等能力，不是附在暂停／取消之后的补充（依据：2026-09-19 需求对话 turn 19 §六、turn 18 第 11 条）。
>
> 此处替代旧版表述：旧版第 3 条只承诺"不必打断源 Worker"。现扩展为"不被拒绝"——不打断是不够的，拒绝回答本身就是毛病一（依据：需求对话 turn 19 §九）。

## 5. 核心用户路径

本节列出的路径是**产品机制的验收用例**，某种意义上就是测试：路由与状态机必须能真实跑通它们。

**不要把例子的形状照抄成实现**——实现里的路由与状态机设计可以与例子不同，但必须通过这些例子。这些路径同时是 §9 成功标准的输入。

### 5.1 主回路：人 → 秘书 → 人反馈 → 秘书修订 → 人确认 → 执行 → 状态回到主 Agent 面

1. 人在主 Agent 面里给出目标范围；
2. 秘书 agent 给出方案（此时只是方案）；
3. 人在对话框或侧边栏里说明：哪里不太对劲、哪里值得再想；
4. 秘书再给方案，可多轮；
5. **人确认——唯一生效点**：确认之后才落到执行、才允许改目标、才允许改两张图；
6. 目标落到任务图，编排子 Agent 执行；
7. 执行过程中，相关事实与状态**及时记录到对应 session、并刷新相关视图**，再回到主 Agent 面；人可以随时询问进展；
8. 人可以对秘书的方案直接追问，秘书基于原方案与材料解释。

这条路径要避免的两个失败形态：中途被机制拒绝（死板）；每一步都从零组装（不符合持久化）。

### 5.2 从零开始

1. 人提出产品需求；
2. 备好参考项目与参考材料，按三档来源取用（见下方展开）；
3. 得到**产品图**；
4. 再得到**架构图**——架构图由 agent 生成，但**人要参与、和 agent 讨论**，不是人自己手写；
5. 人确定目标之后，生成任务图；
6. 进入 §5.1 的执行与反馈回路。

**参考材料的三档来源**：

- **有现成的就用现成的**，而且要成规模——参考材料要有一堆，否则很难做；
- **没有现成的**，先用模型自身的知识、网络搜索、以及当下工作区里的文件探索，形成一个初步的参考集合；
- **在这个初步集合上迭代**：靠相关的 skill 与 prompt 逐步打磨，越用越准。

**skill 与 prompt 是这条路径上的关键件**：它们要针对本产品做适配，不能拿通用的凑合；它们是被正式重视的产品资产，不是可有可无的附属品（另见 §7.6）。

> 此处替代旧版表述：旧版只写"提供参考项目与参考材料（参考材料一定要有一堆，否则很难做）"。现改为：**三档来源 + 没有现成材料时的起步与迭代方式**，并明确 skill 与 prompt 是这条路径上的关键件。

**产品图**定义为产品能力、用户路径、范围与验收依据的结构化视图：用户要完成的事情、产品能力、范围边界、关键用户路径、验收依据。它表达"为什么做、用户得到什么"；架构图表达"由什么构成"；任务图表达"当前如何交付"——三者可相互引用。

首版复用产品文档中的版本化记录（表格或 Mermaid 即可），**不单独承担运行时状态，也不新增第三套运行时图系统**；改功能范围才更新，函数级调整不必改产品图。

> 【已决】产品图已有定义（§12.1 D-8）。

### 5.3 找 bug（已有项目）

1. 与已有项目一样，agent 先探索项目；
2. 探索生成**架构图**；
3. 人确定目标之后，生成**任务图**；
4. 进入 §5.1 的执行与反馈回路。

### 5.4 问项目状态（死板在这里被消除）

1. 人问："某个模块是怎么回事？"
2. 系统从**架构图**入手，推断哪些候选模块与这个问题有关；
3. 找到**负责那个模块的 agent**，问它，而不是把项目重读一遍；
4. 返回相关回应，并附**事实校验**（来源、是否仍然有效）；
5. 拿不到或校验不通过时，明确说明，不补全。

这条路径的价值：不做全量探索；复用该 agent 已经持有的上下文；省 token、也更清晰。

**原 agent 离线时，工作不因此中断**：仍可利用它的 session、图上的引用与当前文件继续调查；离线不等于该模块或图节点消失。

### 5.5 目标变更

人改目标（含任务计划与任务）之后，两张图跟着变，**编排也跟着变**——但**按受影响范围更新，不必重写全部架构与任务**：任务图按受影响范围修订并展示差异，保留未变任务的身份与可复用证据；架构图只在模块关系受影响时更新；旧版本保留可追溯，不被覆盖。

**变更行为（已决）**：确认新目标／计划版本时，在对应 session 记录新版本与变更范围；**停止受影响任务的后续派发**，并用既有取消／写入控制阻止继续执行旧目标；对正在执行的受影响 Run 发出取消／切换信号，到可识别的安全边界停止；**无关工作继续**。若一时无法确定影响范围，先暂停该 Goal 的新派发再完成判断——**不能把"暂时不知道"当作"没有影响"**。

已启动的工具或外部副作用**不能被假定撤销**：记录已知结果、检查实际代码与环境，不确定时保留"结果未知"并继续核对，同时更新相关图节点的状态摘要。受影响依赖做局部计划修订并展示差异，保留未变任务的身份与可复用证据，不全量删除重建。旧 Run 的结果可以保存，但**只有通过新版本适用性检查后才能推进当前状态**；切换 Writer 前确认原 Writer 已停止可写活动，做不到就不交出新的写租约。

### 5.6 人的直接介入与接管

1. 人在主 Agent 面上看到当前有哪些子 Agent、各自在做什么；
2. 直接对某个子 Agent 下指令，或追问它当前的上下文与状态；
3. 必要时暂停、替换或收回某个子 Agent 手上的活；
4. 接管处理完之后，把状态交回主 Agent 面，后续工作从交接后的状态继续。

这条路径与秘书回路（§5.1）并列：秘书回路负责方案的形成与确认，直接介入负责执行过程中的当面处置。

**统一入口**：主对话是默认入口；点击 Agent 名册、任务节点，或在对话中点名，都打开**同一个侧栏**。侧栏显示：负责人、任务与版本、最近进度、已有证据、待决项、当前是运行／等待／恢复，以及"询问、追加要求、暂停、取消、替换／接管"这些动作——图节点、名册与点名只是同一入口的导航。

> 【已决】接管入口形态已定（§12.1 D-6）。界面细节仍可迭代，但"统一到一个侧栏"这一点不再重新表决。

## 7. 产品能力

### 7.1 生命周期管理：一个角色怎么被管起来

产品回答四个问题——**一个角色如何产生、什么时候被拆解、什么时候压缩、什么时候归档**。

| 动作 | 产品含义 |
| --- | --- |
| **产生** | 一个角色被建立起来并绑定到它的承担范围（项目 / 模块 / 目标）。**触发**：新工作确需独立责任或并行调查，而现有合适角色／session 无法承担 |
| **拆解** | 把角色要承担的事分成可交给多个子 Agent 的工作单元。**触发**：存在可独立调查或交付的子任务，接口与完成依据可说明；父任务继续承担汇总义务，子任务有负责人、依赖与结果回流路径 |
| **压缩** | 在不破坏"可复用前缀"的前提下缩小角色当前持有的会话工作集，并留下可追溯的记录。**触发**：上下文容量确实不足，或已观察到历史噪声影响任务质量 |
| **归档** | 让角色退出当前装配，但保留身份与可检索的记录。**触发**：没有未交接的活跃义务，且近期不再需要参与；由明确操作触发 |
| **重新启用** | 新请求需要该角色且现有身份与责任范围仍合适时，**优先恢复合适的原 session**，补充期间变化；确需新 session 时保留交接来源 |

为什么要这么管：角色必须复用；一旦复用，它的上下文会增长、项目会变多，所以它必须有自己的生命周期。

**"拆解角色"指拆解它承担的工作；"压缩角色"指压缩会话工作集——身份与责任不因压缩而消失。归档更新活跃状态与责任关联，不删除模块；模块撤销另按结构变更处理（§7.2.4）。**

生命周期要消除的两个毛病：产生与归档消除"没人可问"（死板）；压缩与复用消除"每次都从零组装"（不符合持久化）。

**首版保持显式压缩与归档**：框架可以提示容量压力；确实无法继续时，提供压缩或交接所需的材料与操作。是否进一步自动化，要在真实任务上比较效果、缓存、延迟、上下文选择开销与维护成本后决定。

> 【已决】四个动作的触发条件与"归档后可重新启用"已定（§12.1 D-7）。

### 7.2 两张图：架构图与任务图

架构图与任务图是 **Agent session 的结构化管理与可视化机制**，与生命周期管理直接相关（见 §7.1）：图变了，角色的产生、压缩、归档与回收策略跟着变。

Agent 是执行者，同时它对项目的感知也在图里；**Agent 的上下文就包含这些 state**。

本节先定义两张图的**输入输出与功能**；形态由这些功能决定，而不是先定形态再倒推功能。

#### 7.2.1 输入：数据基础只有三类

1. **agent 状态**：含当下状态与历史状态。历史状态存在两处——**agent 的上下文**，以及 **git 管理的 tree**（§7.8、§3.1）；
2. **当下的静态文件**：文件树、work-tree 这类；
3. **session 的集合**：作为可检索的数据来源（session 的定义见 §3.1.1；批量 session 即"一批 agent 的历史上下文"）。

**这三类是平台内的三类采集根**：Run／Attempt 不是第四类独立事实来源，而是 session 中执行过程的结构化表达（可查状态、时间、工具结果、费用、取消与恢复）；session 保留原始出处与验证状态——人确认、外部回执、代码观测和模型陈述都如实记录，但**记录某人说"已完成"只证明这条陈述发生过，完成结论仍需结果支持**。

**除这三类之外不存在其他数据来源。**

> 【已决】Run 不作为第四类输入（§12.2 P-19）：它是 session 内可查询的结构化执行记录，通过稳定引用关联 Kernel 已有记录（§7.2.1）。

#### 7.2.2 输出与功能：索引加数据，靠 tool 使用

两张图本质上是**索引加数据**，可存储、可检索。它们被这样使用：

- **按索引与历史组装初始 context**；
- **在协作过程中通过 tool 指引协作、获取所需信息**。

这是"利用架构图、走数据面"的方式：图不是给人看的说明图，而是可以操作的能力。

两张图的存续方式：**正式模块结构与关联持久保存**（§7.2.4），索引与展示摘要可刷新或重建；**代码历史使用 git 版本**，尚未提交但必须跨恢复保存的修改记录为补丁／内容快照并附基线与哈希（git tree 不自动包含未提交修改）。恢复优先复用 Kernel 已有的持久 session、执行记录与检查点，平台补充跨任务／模块的关联；**首版不引入第二套事件存储、消息队列或共识框架**。

session 中的操作记录与文件系统修改不是天然原子的一件事：遇到崩溃，先检查实际产物、工具结果与现有记录，再决定继续或补做——**"准备写入"和"已成功写入"必须区分**，恢复框架状态也不能自动撤销已完成的外部操作。

> 此处替代旧版表述：旧版写"两张图不只是显示，而是一种能力与依托"，只列了"可被检索／有版本／是集合视图"等属性，没有说清输出是什么。现改为：**输出是索引加数据，通过 tool 使用——组装初始 context、指引协作、取回信息**。

#### 7.2.3 检索、约束与编排

检索保留三种查询能力：**角色咨询**（直接问相应的 agent，这本身也是管理机制的组成部分，§5.4）、**静态搜索**（rg／grep、文件读取直接面向当前文件；需要符号引用或跨文件关系时，再用已有 LSP／语言解析器的索引，索引绑定代码内容版本或标注更新时间）、**状态与记忆查询**（查状态、查记忆、查历史，§7.8）。两种或更多索引只是各自的实现，不是新增的查询能力。

约束与编排也落在图上：**编排依据是模块边界划分与角色划分**，图承载这些划分。因此两张图是编排与成本决策的依据，不是摆着好看（§7.14）。

#### 7.2.4 架构图：承载模块边界与角色划分

架构图把模块边界与角色划分承载下来，并被**以数据面的方式**利用，而不只是当说明图看：它把问题定位到模块，由模块推断候选模块与负责该模块的 agent，进而返回上下文与事实校验（与 §7.8 互相回指）。

它按 **"工具 + 摘要信息 + 图结构"** 设计，并与 Agent、文件夹及 session 建立可查询的联系：

| 对象 | 主要承载内容 | 与编排的关系 |
| --- | --- | --- |
| session | 消息、工具调用与返回、观察、讨论、决定、交接及相关执行记录 | 回查发生了什么、谁提出什么、依据是什么；区分陈述、提案与已核验结果 |
| 文件／文件夹 | 当前代码、文档与产物；必要时定位到版本 | 核对实现现状，确定修改与检索范围 |
| Agent／角色 | 责任范围、适合回答的问题、相关工作 session | 找到已积累认识的负责人，继续工作或完成交接 |
| 架构图本身 | 正式模块标识、职责、接口与依赖；文件夹、Agent、session 的关联；摘要与索引 | 查询局部结构、定位证据、咨询负责人、确定委托范围、提出结构变更 |

**正式模块结构与关联要持久保存**；查询索引、展示布局与部分摘要可以更新或重建。但**不能因此把整张架构图视为可丢弃的派生物**，也不要求在 session 之外另建一套平行的事实来源。图上的结论引用对应 session 片段、执行记录或文件版本；架构约定与当前代码不一致时，保留差异及其依据。

**不同变化区别处理**：

| 变化 | 处理方式 |
| --- | --- |
| 新工具结果、进度、阻塞或文件变化 | 写入对应 session，按影响刷新索引、引用、状态与摘要；**不把记录事实变成审批动作** |
| Agent 暂停、换手或归档 | 更新活跃状态与责任关联，记录交接；保留模块与历史负责人关系 |
| 在已确认方案范围内创建模块 | 依现有计划与 skill 执行，补齐模块标识、职责、目录、负责人与相关 session 引用 |
| 新增责任边界、拆分／合并模块、改变跨模块接口 | 说明依赖、任务、目录与责任影响；在既有授权内推进，超出已定范围时提交具体决定事项 |
| 删除模块或正式节点 | 先确认代码、依赖、未完成任务与责任的处理方式；记录迁移／替代关系与删除理由，保留历史引用 |

**隐藏一个视图节点、Agent 结束一次运行、删除代码目录和撤销模块是不同操作**，界面上要明确区分。结构变更记录关联其决定与实际执行结果；基于旧版本提交的变更不能覆盖已生效的新关系。

**架构图上的两类索引**：

| 索引 | 承担什么 | 与检索的对应 |
| --- | --- | --- |
| **agent 的索引** | 哪个 agent 负责哪个模块、它对哪个模块有认识 | 对应"角色咨询"：按模块路由到 agent，直接问它 |
| **事实的索引** | 事实落在哪个模块、来自哪次状态或哪段历史 | 对应"状态／记忆查询"：按模块与版本取回事实与校验结果 |

**静态搜索不强制归属于这两类索引**：rg／grep、文件读取直接面向当前文件，架构图只提供路径范围与候选模块（§7.2.3）。

#### 7.2.5 任务图：monitor + 可编辑的参谋部白板

**任务图不替代编排决策本身**——编排决策仍由模块边界与角色划分决定；任务图承载**编排结果与状态**。

它的目的：执行任务时 **agent 不跑偏**，同时让负责编排的 agent 与开发者（人）**能获取当下的状态，而不为此过度消耗**（成本口径见 §9.2）。

据此，它的基础功能偏向 **monitor**：task 编排确认之后，跟踪任务状态。在 task 编排确定之前，属于人与各 agent 协作、**辅助确认 task** 的环节——这个环节**可以自动放行**。

因此任务图的基础形态是：**monitor + 可编辑的参谋部白板**——白板可供人与 agent 共同改写。

任务图不是 to-do list。区别在于：to-do list 只标注有哪些任务、做完没有；任务图还要标注 **agents 之间的协作关系**，以及"agent 从哪里得到相关状态、到哪里去请求相关状态"。

**两种关系要分别表达**：任务依赖子图保持 DAG（调度顺序）；Agent 之间的咨询、反馈与讨论可以往返（通信关系）。结构变更关联决定与实际执行记录。

#### 7.2.6 两张图共同的属性

- **可被检索**：查一个模块，取它的邻域，而不是把整张图塞进上下文；
- **有版本**：目标或项目发生大改时产生新版本，旧版本保留；
- **是项目当前状态的集合视图**：角色被生命周期回收之后，图要跟着改；
- **反过来决定编排**：任务落在哪些模块上，决定由谁承担、谁需要向谁要状态、改到哪一层；
- **跟着 agent 走**：agent 改过、生成过哪些模块，图上要能反映。

#### 7.2.7 存在形式：仍待人定，但由输入输出推导

本文按**可检索、有版本、是 session 集合视图、跟着 agent 走又反过来决定编排**这一路写下去。

"**谁生成、落在哪里、谁是权威**"仍是待批阅项：它由本节列出的输入输出与功能推导得出，而不是先定形态。候选理解可以给出（例如"权威在图之外、图是投影"或"图自身即权威"），但本文不作定论（见 §12 P-2）。

#### 7.2.8 与记忆搜索互相回指

**状态记忆的感知与历史状态存在两处**：agent 的上下文，以及 git 的 tree（§7.8）。

**两张图是索引，也是一系列查找与搜索工具的集合**；三类检索方式见 §7.2.3（§7.8）。

### 7.3 状态真实性

Goal、Runtime Task、Attempt 和 Run 的当前状态，以及 Evidence、Decision 和状态变化的来源，由框架持久维护。当前状态可以按规则推进，历史事实和证据保留可追溯记录。工具报告确定性结果，Agent 提供语义判断，框架校验适用性并提交状态转换。Todo、状态图、Plan Matrix、Dashboard 和 Timeline 据此投影。

工程上必须证明：重复输入不重复写入、过期依据不能推进当前状态、中断后可以恢复、视图可以重建、投影延迟可见。相关候选机制见 [ARCHITECTURE](ARCHITECTURE.md) 与 [状态实现复核](dev_docs/design/human-framework-role-review.md)。

### 7.4 连续执行

工作不属于某个模型 Context。同一连贯工作中的调查、实现、测试和返工可以持续积累理解；一次模型响应不自动结束工作 Context。新 Run 或新 Agent 从持久事实、关键理由与有界交接接续，暂停、换手或重启不能悄悄丢失义务和待决项。

已完成工作留下可供相关新任务继承的记录。后续执行者结合当前代码／规范核对历史适用性；连续性不依赖原模型、原进程或完整 transcript。

连续执行与角色复用是同一件事的两面：角色复用（§7.5）让认识不必每次重建，连续执行保证义务与待决项不丢。按 §3.1 的界定：可继承的是**持久事实与资产**，不是上一轮的原文装配结果。

### 7.5 角色复用、压缩与归档

- **复用的载体**：角色的身份 + 承担范围 + 可复用前缀（跨请求不变的部分）+ 可检索的既往记录；
- **复用的前提**：可复用前缀保持稳定。前缀一变，复用就失效，成本按未命中计（见 §9.2）；
- **默认动作是延续，不是重建**：连续承担同类职责或推进同一工作时，优先使用既有 session，把新要求、查询结果与必要材料**增量加入**；不因一次 Run 结束或一次派发就重新组装整套上下文；
- **复用要可解释**：为什么选中这个角色、复用了哪些材料、哪些因为过期或撤权被排除；
- **压缩**：压缩是一次有记录的写操作，不是内存里的临时整理；压缩不能把推断写成事实、不能丢掉关键的不确定性、不能把历史授权带进新任务；压缩后仍要能构成可复用前缀，否则压缩本身是亏的；
- **归档**：归档的是"当前不参与装配"的部分，不是"装配还要用的可复用前缀"。归档省下的存储，不能换来更大的输入成本。**归档退出活跃管理，但保留身份、session、产物与重新启用能力**；角色归档不删除模块（§7.1、§7.2.4）。

> 【已决】承担范围已定（§12.1 D-10、§7.10）：三层范围并存，工作包有唯一交付负责人。

### 7.6 能力参数化与 skill 约束

- **能力可配**：能力不写死、不在编译期定死为不可用；
- **skill 约束边界**：能力层决定"物理上能不能"，skill 决定"这次准不准"；
- **首批必须先配上、配齐**：为了行为可控，不能因为"以后可以扩展"就先不配；
- **超出编排范围的需求**：走显式扩展，记录谁扩的、扩给谁、依据是什么、有效期多长，不静默放开；
- **能力"配上"不等于"放开"**。

**skill 的作用是让模型的能力充分发挥、不发散、不模糊。** 因此产品要设计或参考一批优秀的 skill，而不是只声明一套机制。skill 与 prompt 的适配是本产品的正式工作项（§5.2）。

**组织行为主要由 skill／prompt 承担**：调查、拆解、派发、上报、咨询模块负责人、模块变更、争议处理与交接，优先由 skill 规划并用真实任务验证；**执行沿用既有 Kernel 的工具执行、访问、取消与唯一 Writer 规则，首版不叠加平台级细粒度权限／审批体系**。skill 应说明适用场景、工作目标、可用工具、输入与交付、何时咨询与上报，同时给 Agent 留出选择调查路径与方案的空间。

每项资产记录来源、版本、适用范围、已验证的真实任务与失败例；Run 中记录用到的版本，修改要能回退。**格式合法不等于行为有效**。不建设独立技能市场、自动生成技能工厂或新的注册体系。

> 【已决】首批能力采用候选 (b)：**能力类别与对应用户路径进本文，工具接口与 Kernel 映射留设计文档**（§12.2 P-5）；能力类别见 §7.6。
>
> **首批能力类别**（每类映射到现有 Kernel 或平台接口，缺失的能力明确标记待实现）：
>
> | 能力类别 | 典型承担者 |
> | --- | --- |
> | 查目标、任务、决定、证据、角色与历史 | 秘书、协调者、执行者 |
> | 提出目标／计划／架构变更并解释 | 参谋、主 Agent |
> | 领取、派发、等待、报告阻塞、请求决定 | 协调者及相应执行者 |
> | 读取文件、rg 搜索、查看差异；按需接入语义分析 | 调查者、执行者、审查者 |
> | 修改代码、运行项目命令与测试 | 相应执行者 |
> | 提交产物／完成声明、检查 Evidence | 执行者、Reviewer、框架 |
> | 人的暂停、取消、接管、换手与恢复 | 人 + 协调者 + 框架 |
> | 查询参考资料、记忆与知识库 | 调查角色 |

### 7.7 秘书回路与解释交互

- **回路**：人给目标范围 → 秘书出方案 → 人在对话框或侧边栏反馈 → 秘书修订 → 人确认后生效；
- **确认前不生效**：不执行、不改目标、不改两张图；
- **解释交互**：人能问"为什么这么定""依据是什么""还有哪些备选"；秘书基于已经产出的那份方案和它依据的材料解释，不另起新方案；
- **就地可用**：在对话框或侧边栏里就能问、就能看到，不需要切换界面；
- **解释也要便宜**：解释复用同一份方案与材料，不能每问一次就重新装配一遍上下文；
- **常驻可用**：打开应用即可与秘书／参谋交互，并读取已有项目状态——既关于它自身，也关于项目；必要的会话恢复由系统完成且**可见**，不要求人重新讲述项目。持续可用的入口**不等于模型响应零延迟**，也不要求为了等待一次追问而长期保持昂贵运行（见 §7.7.1）。

#### 7.7.1 秘书／参谋／协调者：职责分工与"避免变群聊"

**常驻化的含义（已决）**：只要打开应用，就可以与它对话——既关于它自身，也关于项目；不需要等它冷启动。跨项目对话**后置**（已决，§12.2 P-20）：把跨项目检索封装为工具，加一个带简要索引的库（记忆库 + 知识库 + 用户画像 + 近期工作 + 偏好记忆）留作未来形态；首版以项目作用域隔离（§10）。

**一个 agent 未必干得好这三件事。** 秘书／参谋可以被拆成三种职责，再决定是否分成三个 Agent：

| 职责 | 主要处理什么 | 应当输出什么 |
| --- | --- | --- |
| **秘书／状态整理者** | 发生了什么、谁在做、哪里阻塞、哪些信息过期 | 状态快照、变更摘要、待决事项及原始证据引用 |
| **参谋／规划者** | 有哪些方案、缺少什么信息、方案之间如何取舍 | 候选方案、假设、证据、风险和推荐理由 |
| **协调者／包工头** | 谁负责、依赖如何安排、何时重试或升级 | 任务分配、责任边界、验收结果、升级请求 |

**参与提出方案，不等于所有成员都可以随时改全局计划**：多个 Agent 可以共同研究，但每个决策范围仍要有明确负责人。

**允许并行研究与审议，但首版只有一个正式调度提交者**："一个协调者"只限制正式调度的归属，**不把调查、方案、状态说明和接口审查都压在同一个 Context**：秘书整理事实，参谋可并行提出方案与审查，协调者把采纳结果提交给框架；任务可自动执行到既有授权边界。同一议题先独立产出，再进行一轮针对具体分歧的质疑，有新证据才追加调查；采用什么方案、谁负责执行、何时结束，都形成 session 中可定位的决定或待决事项，并关联相应图节点。协调者按需读取摘要、产物与来源，不要求汇入全部工具历史。

**增加领域协调者的重审条件**：持续出现互相独立的工作流；同一协调者的待处理事件、重复加载与派发等待已构成可测瓶颈；领域边界和交付接口能够稳定说明；增加层级后需要证明总成本、遗漏或进度至少有一项实际改善，同时其他指标不退步。**先不设任意的 Token 百分比或 Agent 数量阈值**。人的目标决定权与未授权取舍不变；协调者的决定权只在已授权的责任范围内。定时轮询、超时计数、预算检查与邮箱恢复交给确定性框架，不增加"监督监督者"的模型链。

> 【已决】"多 Agent 参与编排"已定（§12.1 D-9）：允许多 Agent 提供调查、计划与审查，首版由一个协调者提交正式调度。

**避免变成"agent 群聊"**：给讨论规定输入、产物与结束条件——

1. **确定议题**：需求、约束、决策截止点与方案负责人；
2. **独立形成意见**：各 Agent 先提交方案、证据与未知项，避免一开始就互相跟随；
3. **秘书提取分歧**：说清争议到底在需求、恢复，还是开发成本；
4. **只针对分歧验证**：没有新证据就停止循环；
5. **负责人裁决并留档**：记录选项、理由、未解决风险，以及什么条件出现时应重审，然后转成任务。

消息围绕**具体工作**（任务完成、发现阻塞、接口冲突、请求决策），每条消息关联任务、证据或版本，按收件人发送；大份产物提供引用，不内联。否则只是把单 Agent 的上下文膨胀，变成多个 Agent 同时膨胀。

**三件事的生命周期要分开**：

| 对象 | 应有的生命周期 |
| --- | --- |
| 项目目标、任务、决策、产物 | 长期保留，作为恢复工作的依据 |
| 角色身份（如"前端协调者"） | 可以长期存在，由不同会话接任 |
| 一次 Agent 会话及其上下文 | 有限，可以压缩、结束或重新启动 |

交接时，下一任角色读取：当前目标、有效决策、任务状态、阻塞、未验证假设与产物位置，再按需查看原始记录。摘要保留证据引用，因为摘要本身也可能遗漏信息。

### 7.8 记忆、经验复用与领域知识支持

记忆用于让系统适应用户的沟通方式、项目与团队的工作环境，并从有来源的实际工作中改进后续协作。其用途包括：

- **交互适配**：秘书、参谋、书记通过适用 Context 了解用户习惯、偏好的信息密度、解释深度，以及对具体主题的熟悉程度。明确表达与推测分开，不给用户固化笼统的认知能力标签；
- **项目与团队背景**：保留工具链、工作约定、架构决定及理由、环境限制和验证过的处理经验；正式规范保持权威，不由记忆摘要替代；
- **编排与工具选择**：积累何时定向读取、调用解析器、集中探索或并行分工的条件与效果，保留实际结果和适用范围；单次成功不代表通用最优策略；
- **协作与反馈**：复用任务拆分、进度检查、阻塞上报、产物交接和反馈组织的经验，减少重复调查、信息遗漏与无效打断；
- **工作连续性与决定追溯**：在换手及后续任务中保留关键理由、已接受取舍和未决事项。实时进度、授权和完成状态仍由正式持久事实维护；
- **失败恢复与方法复用**：保存有证据的失败条件、纠正和有效方法；可重复执行的过程可以整理为 Skill，并保留其经验来源。

经验可以在工作中增量记录，也可以通过阶段结束后的运行记录复核和跨任务整理形成；不要求每次重读完整会话，不把普通聊天摘要自动认作可靠经验。用户应能查看、纠正和移除可维护记忆。后续运行应能追溯哪些版本被检索、哪些实际进入 Context；是否改善结果需要独立效果证据。

记忆库可以增长，每次实际加载的材料必须相关、适用且有界：少量必要背景、按需经验与 Skill、可回查的原始来源分层使用，不将全部记忆或知识库常驻注入。角色决定职责与材料使用范围，不需要为每个知识领域新增一个 Agent。

**记忆搜索从图入手，不做全量探索。** 链路为五步：查某模块 → 从架构图入手推断候选模块 → 找到负责该模块的 agent → 问它 → 返回相关上下文与事实校验。这条链路不重读整个项目，复用 agent 已经持有的认识，回答带来源与校验；它也是"类超长上下文"的实现方式——主 Agent 不需要装下整个项目，只需要知道去哪里问。

**状态记忆的感知与历史状态存在两处**：Agent 的上下文，以及 git 的 tree 里。两者都要能被查到，不能只依赖其中一处。

这一条与 §3.1 的概念界定一致：**历史状态是持久层、可回溯**；agent 的上下文只是它在这一次装配里的呈现，**不是历史状态本身**。

**两张图是索引，也是一系列查找与搜索工具的集合**；它们的输入是"agent 状态 + 当下静态文件 + session 的集合"三类，见 §7.2.1、§7.2.8。

这张图也是索引与搜索工具的集合（角色咨询、静态搜索、状态与记忆查询三类，见 §7.2.3）。

**"在哪里"类型的问题可以直接 rg／符号搜索；"现在是否完成"要查当前状态及其执行依据。** 找不到时在预算内扩大检索范围，明确标注仍未知的部分；只在关键缺口影响决定时向人提出具体问题，不为五类渠道逐一打断人。

知识库是领域冷启动与基础质量支持的一种手段。软件工程场景可接入框架资料、编码规范、架构说明、验证方法和经过选择的案例，使系统在尚无自身经验时获得必要背景。知识库支持基本质量要求，但不能仅凭接入资料保证结果或替代实际验证；其内容可以持续更新，不限于静态文档集合。

知识库也可以按个人用途、项目和领域组织，作为广义记忆的外部知识来源，与经验记忆和 Skill 共同为 Context 提供材料。资料本身不自动证明用户身份、职业或偏好。个人化知识库的完整采集、编辑、组织和独立产品体验属于后续探索；本次只确认产品定位并预留接入方向，不将其纳入当前交付或 MVP 验收。

### 7.9 通用角色模板与工具组合

平台以通用角色模板组织协作，首个已验证执行场景仍为 coding。秘书、参谋、书记、规划、集成及领域执行者是可命名、可配置的职责组合；同一模板可产生多个有独立作用域和运行记录的实例。

用户应能创建、查看和选择版本化 Agent 模板，以名片展示名称、简介和职责，并查看材料要求、工具能力及模板版本。模板声明的能力与具体任务实例实际获准的能力必须区分；多个名片不代替任务分工、材料路由、冲突处理和结果整合。

Agent 可在已授权范围内选择和组合工具，新增能力申请须经框架按任务、资源范围和现有授权校验，不得自行扩权，也不要求每次普通工具调用都询问人。模板设计优先复用既有角色规格、角色绑定与治理，具体字段、工具协议和模板生命周期另行设计，不在产品文档中冻结第二套并行注册系统。角色产出期望仍是声明性要求，不能擅自增加完成门禁。

> 此处替代旧版表述：旧版写"秘书、参谋、书记……不是必须常驻或写死的特殊 Agent 类型"。现改为：**秘书类角色要常驻化**——指身份持续、不必每次冷启动，而不是进程永远在线（见 §11 非目标）。"不是写死的特殊类型"这一层含义保留。
>
> 此处替代旧版表述：旧版写"角色名称不是封闭枚举，可按任务配置短生命周期角色"。现改为：角色可配置、可扩展，但**短生命周期不再是产品主张**；角色的生命周期由 §7.1 统一管理。

上述方向依据 2026-09-11 用户讨论及本次正式落盘委托；[讨论记录](dev_docs/design/2026-09-11-agent模板与通用协作角色-对话记录.md)保留来源与候选建议。它不表示通用模板编辑器、跨领域工具宿主或持续多工作包协作已经实现。

### 7.10 角色协作

规划／集成者负责理解已明确的目标、拆分工作、整合结果、识别冲突与返工；执行者／Coder 在有界 Context 和权限内实现。秘书／参谋参与人与 Agent 的协作，并与规划／集成职责共同承担分工、耦合分析、测试设计和结果协调。

这些协调职责可按需要拆分 Agent 实例与 Context；普通已授权协调通过框架直接驱动执行，必要取舍才升级给人。平台按真实依赖、角色所需信息和权限派发工作，维护执行与状态。并行、只读和写入权限是执行机制，不能代替角色定义；MVP 的核心是证明规划、执行、集成与验证闭环。

同一 checkout 的写入安全以唯一 Writer 写租约（不变量 #7，P1-07 competing-writer-lease-test）验证；真实 checkout 写入由 P1-12/13 验证。多个规划／集成者可分别负责工作包，并通过有界交流协调接口、依赖与职责冲突。

秘书／参谋贯穿执行反馈，书记整理各方依据与分歧；角色按需组合，不要求所有消息串行经过每个角色。确定性框架校验授权、路由、派发并维护状态，语义角色负责判断、方案与影响。

**承担范围分三层，不互相取代**：

- **角色的长期责任范围**：一个领域或模块组，以及适合回答的问题——便于复用认识，**不要求每个目录常驻一个 Agent**；
- **本次委托与验收范围**：一个可交付工作包，可以跨模块，包含目标、涉及接口、输入、输出、完成依据与升级条件；**每个工作包有唯一交付负责人**；
- **执行资源范围**：本次任务涉及的目录、接口与工具；访问与 Writer 租约沿用既有 Kernel 规则，不为模块协作新增一套权限模型。

Goal 可以跨多个工作包，但首版仍只绑定一个 Workspace；跨模块任务指定一个交付负责人，相关模块角色提供意见。模块、目录、负责人与相关 session 的关系记录在架构图中（§7.2.4）。

### 7.11 证据驱动完成

Worker 只能提交 CompletionClaim。平台组合静态、运行、测试与语义 Evidence，再按当前义务判断 Task 和 Goal 是否完成。

对通用业务，框架区分可证明的运行／提交／回执事实与业务目标达成。业务完成依据具体任务正式绑定的规则、外部权威回执、领域验证、独立审阅或必要用户确认；模板默认要求不能覆盖正式义务和政策。缺少可靠判据时保留业务结果待确认，不从 Run 结束、工具调用成功或模型自述推断目标完成。这是行为边界，不新增统一状态枚举。

事件驱动协调优先处理失败、新材料和冲突；心跳可按需要补查进展、发现停滞并整理公开事实，模型总结不是每次心跳的必选项。周期摘要不能替代验收 Evidence，不能把反复推测积累为事实。

### 7.12 Human Collaboration

主对话、状态图、面板、提醒、查询、参谋和控制入口在同一界面中协作，事实展示具有共同来源，语义说明标明其事实依据。人和 Agent 共同明确需求、参与架构生成与变更讨论；系统呈现选项、影响、决定和执行反馈，确保人知情。

知情不等于每步审批：普通已授权实现和验证由框架与 Agent 闭环完成。

### 7.13 架构治理

架构治理包括最初建立、持续对账与变更演进。秘书／参谋协助人形成需求和架构方案，已接受决定进入版本化规范与 ArchitectureBaseline。此后与实际代码对账；局部、确定、可逆且已授权的漂移进入正常修复流程，重大或含糊变化由人和 Agent 讨论选项、影响与迁移方法，并记录决定和反馈。

架构、模块职责或跨模块接口契约变化必须通过统一界面向人上报，不能只存记录等待人主动查询。已明确授权内的变化可汇总通知并继续执行；需要新取舍或权限的变化提交具体选项等待决定。冲突可在调查、协商或对账时提出，无需等测试失败；人的决定经正式变更路径回到全部受影响工作。

架构图与任务图是这项治理的日常载体：图的版本与基线（§7.2）承载"为什么如此"与"哪些漂移未处理"；目标变更后图随新版本重生成，旧版本保留可追溯。

### 7.14 成本约束：贯穿以上所有能力

成本不是事后优化项，而是设计时的硬约束，约束三件事：

1. **缓存命中率的目标**（见 §9.1）；
2. **上下文装配方式**：稳定前缀复用、能命中就不要重算、装配失败要显式报缺料；
3. **生命周期的回收策略**：压缩与归档不得破坏可复用前缀（§7.5），且必须与两张图联动——图变了，角色的产生、压缩、归档、回收策略跟着变（§7.2）。

**成本在架构设计阶段就要算进去**，不是实现完再优化。这也是本次改动重新强调架构图与任务图实际作用的原因：它们是**编排和成本决策的依据**，不是摆着好看（§7.2）。

任何"每次重新装配上下文"的做法，都要按 §9.2 的判据算一遍金额，并说明为什么划算。**比较的基线是"既有 session 连续复用"**：上下文策略的变更要同时看任务质量、缓存与延迟、编排运行成本、工程投入与恢复可靠性——已有高缓存命中时，尤其不能只拿 Token 价格论证重组收益。

从零开始时的参考材料来源，每一类都要有明确取用方式，拿不到要明说：

| 来源 | 何时取用 | 进入 Context 的形式 | 拿不到时 |
| --- | --- | --- | --- |
| 工作区文件／代码 | 回答现状、定位符号、核对修改 | 当前版本的片段 + 路径／内容版本 | 说明该项目无可用文件 |
| 人提供的需求与反馈 | 目标、价值取舍或主观要求不明确时 | 原始要求／决定的引用；保留是否已确认 | 说明在等谁提供什么，不猜 |
| 网络资源 | 问最新事实、框架行为、已有工程实践 | 官方资料优先的短摘录／结论 + 链接与取用日期 | 说明网络不可用或未搜到，不静默跳过 |
| 记忆与知识库 | 需要历史理由、约定、经验或已研究材料 | 小段命中内容 + 适用范围与原始证据 | 说明无相关记忆，不把推测当已记录事实 |
| 模型自身知识 | 提出搜索方向、候选解释、方案草稿 | 标注为待核实假设，不能直接充当项目事实 | 不适用（总是可用） |

统一要求：能说明**来自哪里、适用什么范围、基于哪个版本、何时获得、哪些尚未验证**；检索到事实不自动提升该材料的授权级别。检索用于**补充正在延续的 session**，不要求每轮重新选择整套上下文；模块职责、依赖、负责人和历史理由优先经架构图的工具、摘要与关联定位，再按需咨询负责角色或回查 session。

> 【已决】五类来源的取用方式已定（§12.2 P-10）：统一出处与适用性，按问题选渠道；细节（谁触发、以什么形式进入）留给设计文档。

### 7.15 上下文装配：装什么，以及怎么传

**装配的判据是必要性**：只装配这次工作真正需要的上下文。"必要"跨模块边界，不按模块边界切。

**默认动作是延续而不是重组**：连续工作优先在既有 session 上追加消息、用查询工具、补局部材料；**首版不建设"每轮决定如何重组上下文"的通用编排器**。确有容量不足、质量下降或任务分工变化时，才显式压缩、分叉或交接，并保留来源（§7.5）。

一次工作至少需要这几类信息：

- 协作模块的目的；
- 与本模块相关的接口；
- 本模块自身的目的；
- 产品整体的目的；
- 可能的同类或竞品实现。

这些信息可以经由**共享载体**传递，而不是每次都从零组装。共享载体有四类：

- **session**：留存请求、讨论、决定与执行回报；
- **图**：关联模块、任务、负责人及相关记录；
- **版本化文档／产物**：保存详细方案与结果，一次被审阅或用于决定的版本必须可以定位；
- **定向邮箱**：把消息送给需要处理的 Agent（如 dsh-agent-team 里的留言板）。

本文只写到"存在这样的共享载体、共享哪些内容"这一层；接口契约与字段留给后续文档。

**四件事不能互相代替**：消息到达不等于任务成功；讨论同意不等于操作已经执行；文件存在不等于已通过验收；图上摘要不等于事实本身——**摘要要能回到来源核验**。跨 Agent 消息保留发送、接收与原材料引用，避免反复转述丢失来源。

这些载体与 §3.1 的层级一致：它们是**持久层**上的共享材料，装配时被取用，而不是 session 内存活的一次性副本。

> 此处替代旧版表述：旧版写注意力约束是"Agent 侧靠模块边界只留相关上下文"。现改为：**判据是必要性，不是模块边界**；并补上共享载体这一层（见 §1 主张 1）。

> 【已决】共享载体已定（§12.1 D-11、§7.15）：四类载体；同类／竞品材料只在具体决策或接口问题需要时检索，先读官方文档与许可证，记录版本与采用的部分，来源无法取得时保留缺口（§7.15）。

## 8. MVP 必须证明

- 单用户、单机管理多个隔离 Project/Workspace；
- 一个 Goal 首版绑定一个 Workspace；
- Goal → Runtime Task → Attempt → Run 的状态可重建；
- Worker A 的 Run/Context 结束后，Worker B 能仅靠持久状态和 HandoffPacket 接续；
- 规划／集成与执行角色依靠有界输入、结果交接和框架状态完成闭环；并发和写入安全有独立验证；
- Task 和 Goal 不能因自称完成、空计划或过期 Evidence 变绿；
- 用户可查询、暂停、继续、取消和安全修改目标；
- 同一界面以图形和文本展示 Goal、Task、Agent、Timeline 与依据，状态模型可直观查看；
- 人能与秘书／参谋共同明确需求、参与架构建立或变更，并获知决定及执行影响；
- 一次架构漂移可以被发现、解释并进入修复或决策路径；
- 崩溃恢复不把未知副作用猜成成功或失败；
- 同工作多轮推进、暂停恢复与换手保留关键理由和待决项；
- 已完成工作在重启后供相关新任务继承，并识别不再适用的历史前提；
- 两个工作包在测试失败之前提出接口／架构冲突，经秘书／参谋上报、人的决定与版本更新回到受影响 Context；拒绝、延后与过期决定不会偷偷推进变更。

> 此处替代旧版表述：旧版"用户可查询、暂停、继续、取消和安全修改目标"中，查询与修改目标的语义已按 §4 第 4、5 条扩展（不被拒绝、可直接改目标与计划）。

## 9. 成功标准（含成本口径）

### 9.1 产品结果的量化口径

**最终验收标准是 §5 核心用户路径里的每一条回路，在真实项目上跑通。** 针对不同路线各自提供**真实项目**作为测试对象，不用构造的小例子顶替。

首批使用两类项目：**自己的 coding-platform**（验证秘书、图、接管、目标变更等整条交互回路）与**一个技术栈可运行、维护历史清楚的外部开源项目**（检验是否依赖平台自身的特殊知识）。选取标准是可安装、可运行、原问题可重现、修复有可独立检查的依据、改动范围可控制。

每个验收任务至少固定：起始代码版本、环境／依赖、需求与授权、验收依据、预算与超时、是否允许网络、哪些参考材料可见；历史修复任务要遮住最终补丁与直接泄露答案的材料。任务包覆盖真实修复／修改、状态查询、目标中途变化、跨模块接口争议、暂停恢复与换手；可在真实任务上注入断网或进程终止来检查恢复。

**成功既含项目结果，也含责任／证据／授权闭环**：模型自评、运行退出码、最终补丁与人类补丁的相似度，都不能单独代表成功；需要声称"不退步"时，按观测方差确定样本量，不用有限任务直接下统计结论。

- 状态查询准确率为 100%；
- 每个 completed Task 都能追溯到当前适用 Evidence；
- 依赖未满足、revision 过期或写入冲突会被确定性拒绝；
- Handoff 后不需要重放完整 transcript；
- 同一真实任务与单长会话基线相比，成功率不下降；
- 用户必要决策与无效打断分别度量，并记录总时间、Token、重复探索和恢复结果；
- 任一失败可以归因于计划、执行、验证、权限、预算、环境或恢复。

**口径细化（与既有陈述并列生效）**：

| 关注点 | 口径 |
| --- | --- |
| 状态查询准确率 | 在指定测试集上，结构化查询应与对应 session／Kernel 记录及图中正式关系一致；自然语言解释另测事实错误、来源覆盖、过期信息与恰当的"不知道" |
| 成功率不下降 | 在同一冻结任务集、模型／工具条件与预算策略下配对比较并记录重复运行；样本不足不声称统计上的不退步 |
| 缓存命中率 | 99% 保留为明确条件下的热调用目标；同时报告全量输入 Token 命中率、热调用命中率、可复用前缀利用情况与实际费用，**不改变旧数字的分母** |
| 压缩／重组是否值得 | **以原 session 连续复用为基线**；同时测质量、延迟、重组决策调用、检索、读写、压缩、缓存变化与后续恢复成本 |
| 上下文组装的工程投入 | 单列选择／编排逻辑的实现、调试与维护成本，说明新增组件解决的实际问题 |
| 失败归因 | 保留主要原因、伴随原因与暂未确定原因，不为满足分类而猜定原因 |

### 9.2 成本口径

**缓存命中率目标**：目标 **99%**（产品提出的期望值，不是行业合格线）。该目标的唯一精确适用面是"可复用的热调用"，不适用于冷启动，也不能被冷启动的低命中掩盖。

**可复现的当前实测**：89.99%（9 次运行 / 85 次请求 / 2,854,860 输入 Token）与 89.10%（版本化证据，8 trials）。旧诊断中的 77.48% 在当前快照不可复现，不作为本文基线；三组数字数据集不同，不能直接比较。

**两个必带口径**：缓存命中率目标，以及"每次重新装配上下文"在金额上的判据。**比较的基线是"既有 session 连续复用"**：上下文策略的变更要结合任务质量、缓存与延迟、编排运行成本、工程投入和恢复可靠性一起判断，首版不默认建设通用上下文重组机制。

**价差（硬约束）**：缓存命中 0.02 元 / 百万输入 Token，未命中 1 元 / 百万输入 Token——50 倍。一句话判据：**未命中一次 = 命中 50 次的钱**。

**按可复现实测规模（2,854,860 输入 Token）折算**：

| 命中率 | 输入成本 | 相对 99% |
| --- | --- | --- |
| 实测 89.99% | 0.3372 元 | 3.96 倍（多花 0.2521 元） |
| **99%（目标）** | **0.0851 元** | 1.00 倍 |
| 75% | 0.7565 元 | 8.89 倍（多花 0.6715 元） |

**"每次重新装配上下文"的金额判据**：重新装配 100 万 tokens 的稳定内容 = 1 元；命中同样内容 = 0.02 元。任何改动若可能把命中率从 ≥99% 拉低到 ≤95%，必须先用上面的算法算出每轮多花的金额并写进变更说明；算不出金额的改动不予受理。金额按请求规模等比放大，上表是同一规模下的相对比较。

压缩与归档之后，要用同一范围重跑一次对照，比较可复用前缀是否变化；变了就要算钱并说明理由。

### 9.3 可观察的产品标准

- 人询问项目状态不被拒绝：要么有回答，要么有明确的"不知道 / 缺什么 / 找谁"；
- 角色真的被复用：后续请求命中既有角色的上下文，而不是每次全新装配；
- 秘书方案可被解释：追问"为什么、依据、备选"能得到基于原方案的回答；
- 目标可改，且改完两张图跟着更新，旧版本可追溯；
- 任务图能说明协作关系与状态来源，而不只是任务清单；
- 问题回答带来源与事实校验；校验不通过时明确说不确定；
- 材料缺失时显式说明，不静默跳过；
- 成本可归因：任一"重新装配"的做法都能算出金额，并给出划算或不划算的结论。

## 10. 边界

- **A（agent-team）只作参考**：只复用"编辑机制"与"编排通信（Roster / mailbox，含异步并行）"两处；A 作为外部项目的那些约束不进入本产品；
- **方案在人确认前不生效**：不改目标、不改两张图、不执行；
- **能力配上 ≠ 放开**：以 skill 约束这次是否允许；
- **人可直接改目标与计划**，不能被限制成只能靠自动化改；自动化改动必须经过人；
- **主 Agent 面向人**，它的产出是目标与计划；它**具备项目内写能力，但需要权限管理**；项目内的写操作最好由**负责该模块的 agent** 执行，便于架构图的检索、管理与编排（见 §7.2.4）。此处替代旧版表述：旧版写"项目内的写操作由面向执行的角色承担"（推断）；现改为"主 Agent 有写能力但受权限管理，写好由模块 agent 执行"（§12.1 D-2）；
- **不做全量探索**来回答项目问题；
- **不要求永久、无限**的上下文；
- **首版以项目作用域隔离**角色复用、执行与检索：所有状态、角色、session、产物和检索都能确定当前 Workspace；越界请求给出明确原因，不从另一个项目默默补材料；用户切换项目时呈现相应状态，不延续前一个项目的执行权限；
- 旧版保留的边界：Human Collaboration 只提醒、讨论与安全打断，不直接改写状态；验证默认由系统与 Reviewer Agent 闭环，人参与需求与架构生成、重要取舍、主观事实及授权；跨工作历史按精确历史授权取材，不因只读或写权限自动获准。

## 11. 非目标

- 多 Writer 同时修改同一 checkout；
- 跨 Project/Workspace 的自由 Agent 通信；
- 跨机器共识、高可用或多租户权限系统；
- 通用工作流 DSL；
- 完整 IDE；
- 无限自主 spawn；
- 让完整 transcript、Memory 或 RAG 独立承担进度与完成判定；它们可以辅助 Context 检索，状态模型及其图形化展示属于 MVP；
- 为目标架构中的每个方框提前创建目录和抽象；
- 不承诺"永久在线"的常驻进程式 agent：秘书类角色的常驻化指身份持续、不必每次冷启动，不是进程永远在线；
- 不靠一个巨大的上下文窗口装下整个项目；
- 不做跨项目角色共享（先做项目内复用；跨项目请求显式拒绝并说明原因，不静默降级）；
- 不做自动压缩调优与自动回收（先用显式的压缩与归档）；
- 不把 agent-team 作为依赖或基座；
- 不把"每次重新装配上下文"当作可接受的默认做法；
- 首版不建跨项目向量库、共享角色池或跨项目 Agent 网络：跨项目检索、跨项目 Agent 通信、跨项目执行是三个不同范围，未来先以显式授权的只读工具开放，开启前者不顺带开放后两者。
