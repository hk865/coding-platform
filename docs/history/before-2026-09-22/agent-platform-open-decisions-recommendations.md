# Agent Platform 待决项修订：角色复用、Session 执行与平台边界

更新：2026-09-21，本轮用户澄清后修订。  
本文替换上一版建议，直接记录本轮已经明确的方向，并解释剩余工程问题。接口字段示例是设计建议，不代表已有实现。ARCHITECTURE.md、PRODUCT.md 和源码本轮未被直接改写。

## 1. 本轮采用的产品模型

首版以可复用的角色／能力配置、持久的 Session 工作上下文，以及两张图中的工作关系组织系统。**不以“每个 Agent 都是一名持续存在的员工”为前提。**

具体执行由 Kernel 驱动模型与工具完成，Session 承载这条工作的对话、读取历史和恢复记录；角色配置提供能力、规范和工具。长期领域专家可以作为后续形态：在角色配置上接入领域知识库与可积累记忆，再按需提供给各次 Session。当前预留接口和积累方案，不宣称已经具备该能力。

| 对象 | 首版含义 | 需要保留的内容 |
| --- | --- | --- |
| Role／能力配置 | 秘书、参谋、执行者等可复用配置 | 指令、工具、Skills、默认执行权限；预留记忆／知识来源接入 |
| Session | 一条可继续的工作上下文 | 对话、工具结果、必要历史及 Kernel 恢复记录 |
| Run | Session 内的一次执行 | 开始／结束、结果、错误、必要的关联和控制状态 |
| 任务／Work | 要完成什么，以及依赖、状态和产物 | 优先使用任务图已有标识；是否另设 Work 身份由实际语义决定 |
| Agent | 产品中对“按某种配置工作的执行实例”的称呼 | 如需通信地址可有实例标识，不默认要求跨任务的独立持久主体 |
| 记忆／知识库扩展 | 面向长期领域专家的知识与经验来源 | 当前仅预留接入接口与积累方案，不列为已交付能力 |

工程标识用于区分收件人、运行和记录，不证明存在长期人格。即使未来接入记忆，记忆也可以属于项目、用户或模块，由多个 Session 复用；仍不必自动增加独立 Agent 聚合。

同一角色可以同时启动三个独立 Session，它们分别做自己的工作。首版保留的并发限制是：**同一 Session 不接受互相冲突的并发执行；同一共享工作区的写入沿用现有协调机制。** 不再根据“模板相同，所以是同一个主体”禁止并行。

### 现有规划和实现究竟有什么

- PRODUCT.md §7.7 的生命周期表已经写明：角色身份可以长期存在，由不同会话接任；一次会话可以压缩、结束或重启。
- PRODUCT.md §7.8 已规划记忆、经验和领域知识支持；完整个人知识库的采集、编辑及独立产品体验明确不属于当前 MVP。
- ARCHITECTURE.md §6.4 明确不新增记忆模块，使用既有 HumanMemory／历史路径。
- source-analysis.md 记录了 HumanMemory.maintain、MemoryContextCompiler、记忆读取等已有代码线索。这不等于已经实现自动学习、完整知识库或“领域专家长期主体”。

因此，项目有相关规划和代码线索，但不能据此将长期领域专家、知识库接入或跨任务记忆积累列为已交付能力。**本轮明确：长期可以做；当前留下知识库、记忆接入接口及积累方案，不声明已经包含这些能力。**

### 长期领域专家的扩展预留

领域专家的目标形态是角色／能力配置结合领域知识库与持续积累的记忆；具体任务过程仍属于 Session，不默认把整段旧任务历史带入新任务。

| 预留项 | 方案需要说明的内容 | 当前交付边界 |
| --- | --- | --- |
| 知识读取接口 | 根据当前任务查询资料，返回相关片段、位置与必要来源信息 | 只定义接口及接入位置；不宣称已有知识库提供方 |
| 记忆读取接口 | 按项目、模块或角色的适用范围读取经验，供当前 Session 按需使用 | 不宣称已有自动记忆检索或完整跨任务记忆能力 |
| 积累与维护方案 | 在工作结束或关键节点提炼候选经验，保留来源；整理、去重、修正后供后续使用，并能更新或移除 | 是后续实施方案，不宣称已经自动执行 |
| 启用与能力状态 | 接入实际提供方后，按真实实现声明可用范围 | 未接入时标为未配置／未实现；类型、占位接口或配置项不等于能力已启用 |

无需为接口预留提前建设独立数据库、长期主体状态机或完整记忆模块。后续接入并验证后，再更新产品能力清单和验收范围。现有相关代码可以复用，但代码存在与完整能力成立分别说明。

## 2. A1–A8 的修订结论

| 项目 | 本轮结论 | 上一版需要撤回或收窄的内容 |
| --- | --- | --- |
| A1 · U11 | 角色配置可复用、可并行实例化；具体工作由 Session 承载；长期领域专家保留为知识库＋记忆扩展，当前只预留接口和积累方案 | 不把长期身份设为首版前提，也不宣称已有长期专家／知识库／记忆积累能力 |
| A2 · U7 | 执行记录、压缩和恢复由 Kernel 实现，平台提供适配接口 | 不再问是否采用 Kernel；真实桥接验证属于实现责任，不是再次决策 |
| A3 · U1 | AgentLifecycle 按目标职责正式落地，并替换旧的重复职责 | 不以一个演示闭环作为重构完成标准，不把旧体系长期包在适配层下面 |
| A4 · 恢复 | 区分 Kernel 恢复与平台状态同步；平台处理自己拥有的运行关联、调度和两张图状态 | 删除通用外部副作用对账系统、复杂自动接管平台等首版扩大项 |
| A5 · 创建 | 创建／解析 Session、选择配置、关联必要任务并启动执行 | 不新增“身份登记→参与关系→绑定签发”作为所有工作的额外必经仪式 |
| A6 · pause | 平台发控制请求，Kernel 负责执行停止及恢复点；平台接收成功／失败并同步调度与显示 | 平台不逐个检查工具和子进程是否停下，不复制 Kernel 的取消机制 |
| A7 · agent-team | 可以吸收概念，也可以选择性移入可用实现；是否保留外部包依赖单独看待 | 不把“借鉴／复制代码”一律说成引入实验包运行时依赖，不设泛化审批项 |
| A8 · 文档与记录 | 直接记录已经明确的决定；权威副本与指针由文档维护流程处理 | 不把编号、索引和常规文档同步继续作为产品拍板事项 |

### A2：Kernel 与平台的具体分工

| Kernel／执行适配器负责 | 平台负责 |
| --- | --- |
| 模型和工具循环、执行取消、暂停边界 | 选择配置与 Session，提交执行／控制请求 |
| Session 日志、检查点、压缩、实际恢复 | 保存平台引用与 Kernel Session 的映射 |
| 工具权限、沙箱与执行层校验 | 管理调度状态、任务依赖及图上的工作关联 |
| 返回执行进展、最终结果与错误 | 消费这些结果，更新任务和展示，不重复编写执行日志 |

平台适配面应能表达创建或打开 Session、开始或继续执行、发送消息、控制、查询状态及读取增量事件。这是一组需要覆盖的语义，不预设恰好几个新接口；优先收敛现有端口。

不同 Kernel 的能力可由适配器翻译。平台不依赖它的私有检查点格式，也不把一种 Kernel 的全部内部状态搬到平台。已决定使用 Kernel，不再反复提出“要不要用”；只确认接线没有丢失已有能力。

### A3：怎样才算真的重构

AgentLifecycle 管的是运行实例和 Session 工作线的创建、复用、上下文处置与归档等生命周期选择，不需要先制造一个长期 Agent 人格。普通消息不因此每次重新走一套生命周期决策。

重构完成应以职责和路径变化为依据：

1. 创建／复用／上下文处置在目标模块有唯一职责落点。
2. 普通执行、Reviewer、Handoff 等生产路径采用同一套必要运行规则。
3. 旧的重复选择、重复身份推导和重复取材路径迁出或删除；兼容层有明确终点。
4. 不再因普通消息、模型每轮调用或状态查询重复全账本／全工作区扫描。
5. Kernel 能力通过实际适配器工作；新的职责分工确实支撑完整产品路径。

可以分批实施，但最终交付按目标架构验收，不能以“又加了一层 wrapper，演示可以运行”代替重构。也不能为守住旧的 13 个模块、38 条边而保留已无必要的依赖。

### A4／A6：平台只处理它拥有的状态

平台恢复的首版路径可以很直接：读取必要映射 → 向 Kernel 查询／恢复 → 消费已有结果和未同步事件 → 更新任务、关联及展示。成功就继续；失败就显示原因并保留可查询记录，按能力重试或重新开始。

两张图不需要参与每一个执行步骤的审批。任务图接收任务与执行结果；架构图接收结构或关联变化。可重建的视图用事件游标或按需刷新维护，不与每次工具调用建立跨模块强事务。

平台暂停分两部分：暂停指定范围内的新派发，并把已运行实例的控制请求交给 Kernel。Kernel 确认成功后更新显示；失败则报告失败，不把失败显示成成功。暂停整个任务分支时，不必停掉项目里无关的分支。

**“直接报错”适用于表达暂停失败，但不能替代暂停本身。** 若 Kernel 的接口承诺成功返回就已达到停止边界，平台直接信任该契约，无需复查每个工具。若它只返回“收到请求”，适配器等待最终结果即可。这不是要求重造恢复系统。

错误、终止通知、执行令牌、数据库事务和版本字段等既有机制按需要使用。它们通常不需要每轮扫描整个历史，实际代价取决于接法；本文不无依据承诺绝对零开销。

首版不承诺还原全部崩溃现场、不做通用外部事务补偿。仍未知的执行不自动标为完成，也不因平台没收到结果就盲目重复提交同一项操作；同一 Session 是否还能运行主要由 Kernel 判断。

## 3. Session、任务与通信标识

### A5：哪些 ID 真有必要

| 标识 | 作用 | 推荐 |
| --- | --- | --- |
| role／配置引用 | 这次用什么能力和规范 | 保留、可复用；不是独占主体 |
| sessionRef | 消息发往哪里，继续哪段上下文 | 保留；多 Kernel 时能够定位 provider 与原生 Session ID |
| runId | 区分这一次执行、结果和重试 | 保留，沿用可满足需求的现有表示 |
| taskId | 任务图上做什么、依赖谁、产物属于哪里 | 保留；有协作、换手或重试时仍须追踪任务 |
| workId | 是否存在独立于图节点的一项持续工作 | 不先宣布必需；若仅重复 taskId 就合并，若跨计划／任务仍有明确消费者再保留 |
| agentId | 标记运行实例或通信参与者 | 有消费者可保留轻量标识；不为它扩建跨任务长期身份体系 |

配置、会话和任务是不同维度，但不需要为了每个维度再造一套审批、注册和全量校验。

工具与能力默认来自角色／运行配置。任务必要时可附本次目录、资源或工具限制，不要求所有消息都先验证 Work 身份。实际工具权限继续由执行端落实。

如果现有 workId 与 taskId 真正重复，应消除重复记录和解析；如果 workId 正在维系跨 Run 或换手后的任务连续性，删除时必须把这种关系移到任务图或等效的既有记录中。不能把“删掉 ID 字段”与“去掉开销”直接画等号。

source-analysis.md §7.2 P10 记录：现有 bindWorkContext 查找任务工作关系时会扫描账本，扫描上限为 200,000 条。P9 还记录了模型调用准入中的类似扫描。这是源码结构推断，不是本次实测耗时。

优先重构为直接键查询、必要索引和稳定关联；有效配置只在相关版本改变时更新。普通消息按目标 Session 和请求标识投递，不重跑创建流程，不重新装配全部上下文。

### R-3：相关任务可以接着用同一 Session

本轮明确允许：两张图和当前工作状态显示后续工作与已有上下文相关，就可以延续原 Session。**不能因为换了 Work ID 就强制新建。**

例如同一模块的实现、修复其测试、根据审查意见调整，通常可以连续进行。图关系用于帮助判断，不必建设另一个重型相似度判定服务；已有上下文是否有用、是否混乱、是否快满，也要一起看。

相关就延续；有价值但拥挤时压缩；失效或混乱时重组；不再需要时归档。一个 Session 可以先后承担多个相关任务，任务关联及时更新即可。并行任务需要独立上下文时，使用同一角色的不同 Session。

### R-5：平台引用与 Kernel ID，和幂等有什么关系

两种 ID 的映射本身不是幂等；**创建请求重试后不产生两份会话**才是幂等问题。

例子：Kernel 已创建成功，但平台没有收到响应。如果平台用同一个创建请求标识重试，能够找回那次结果，就不会额外创建第二个 Session。能直接采用 Kernel 的幂等／查询能力就采用；平台只保存必要映射和请求关联。

映射设计先保持轻量：明确由谁发起创建、由谁产生原生 ID、平台何时记录；遇到一边成功一边失败时，能够查到或报告未完成绑定。不要为这件事新增跨系统事务框架。

## 4. L-1：复用范围与三种记录，用普通话解释

### “复用范围”到底是什么

它本来应回答：**这次继续或重组时，推荐从哪里拿已有资料。** 上一版把这个问题与完整材料授权体系绑在一起，扩大了当前需求。

按本轮要求，首版将其定义为推荐线索。例如：

> 这次修改登录流程。先读当前认证模块和测试；需要了解最近改动时看列出的提交／diff；设计理由在这份架构说明；仍有疑问再查询关联 Session 的历史。

这些是 Skill／prompt 中的工作方法和推荐材料。执行者能用工具自主查找、按需扩大阅读，不被一个固定 selectedRefs 白名单卡住。

文件当前状态是主要依据，diff 和修改历史帮助解释变化；差异本身不能代替完整当前文件。早期探索失败、被放弃方案等未进入 Git 的过程，需要时再查 Session 历史。不是每次一开始都把这些东西全部读出来。

**需要区分的只有两层：**

| 层次 | 例子 | 处理方式 |
| --- | --- | --- |
| 阅读建议与注意力控制 | 先看登录模块；不要无关地读遍整库 | Skill、prompt、推荐索引；允许合理扩展 |
| 实际工具访问边界 | 某目录工具打不开；当前运行没有写权限 | 沿用 Kernel／工具／沙箱已有规则 |

因此，按 Skill 指导阅读是本轮采用的方案；它不会自动改变工具实际能访问的范围。**不为推荐阅读范围新增平台的逐条材料授权系统，也不把每轮继承历史复核设为新增必经门禁。**

已有执行权限不能由 prompt 绕过。若以后确实增加跨用户资料隔离或严格撤权需求，再针对真实需求设计历史处理；当前文档不应同时承诺“只靠 Skill”与“形式化保证撤权材料永不再次进入模型”。

### 三种记录不是三套新系统

| 名称 | 普通话 | 首版承载 |
| --- | --- | --- |
| 初始化清单／manifest | 开始时给了哪些指引和资料入口 | 本次初始消息／编译结果中的引用，必要时记录配置版本 |
| 实际读取记录 | 运行中真的读了哪些文件、得到哪些工具结果 | 使用 Kernel 已有会话和工具日志；平台不重复抄一份 |
| 可用历史索引 | 需要更多背景时，到哪里找 | Git、文档索引、两张图、Session 查询入口；优先使用现有检索能力 |

这三者的区别是“推荐了什么”“实际读了什么”“还可去哪里找”。不要求新增三个数据库，不要求把每次读取送回 ContextCompiler 更新清单。

压缩由 Kernel 保留有用前沿与历史。重组时平台提供目标、角色／Skill、当前文件入口、相关 diff／提交、图关系和必要历史引用；执行者按需读。ContextCompiler 在这里负责有界整理和格式化，不承担完整知识调查。

初始清单可以精简，但目标、已经确认的重要限制及未完成事项不能只藏在一条“自己去找”的链接里；这几项应直接说清，细节再按索引展开。

## 5. L-2／L-4：元数据就是工作卡片和关系

可以把 UI 中的执行实例理解为“工作卡片”，但它是运行信息展示，不要求背后存在一位长期员工。

| 卡片内容 | 来自哪里 |
| --- | --- |
| 角色、模型、工具、Skills | 配置 |
| 当前任务、关联模块、依赖和协作者 | 任务图与架构图的关联 |
| 使用哪个 Session、当前 Run | 运行映射 |
| 正在运行／空闲／暂停／归档 | Kernel 运行结果与平台管理状态 |
| 产物、历史与继续工作的入口 | 文件、任务结果及 Session 引用 |

角色配置、Session 映射和任务关联利用现有数据库／记录保存；卡片由这些数据查询生成。状态更新、索引、唯一键等使用常规工程机制，不需要先设计新的“身份治理聚合”。

谁负责哪个模块、哪个 Session 接了哪个任务，属于普通工作事实。结构边界和接口设计的变更仍需按实际开发流程处理，但普通关联更新不变成架构审批。

归档沿用你此前的语义：Session 工作线退出默认视图和调度，经专门入口只读；解除后才能启用，保留历史与模块节点。角色模板仍可供新的 Session 使用。

因此，四态优先描述 Session／工作卡片的状态。角色模板可用性与执行状态分开，不再默认把 working／paused 等四态强塞进持久 AgentInstance。

## 6. L-5：没有 baseline，就是项目还没有第一份已采用的架构

“baseline”在这里仅指后续比较所用的那份已采用架构。它不应该成为第一次创建项目之前必须已有的东西。

首版采用正常开发路径：

1. 主 Agent 根据需求与相关 Skill 形成草案，列出目标、模块、目录和关键未知项。
2. 在普通工作区权限下创建文件夹、说明文件和模块／接口文档。
3. 分配合适的角色／Session；确认需要稳定下来的模块边界和接口。
4. 开始开发，按任务反馈修订草案和相关图。
5. 当某一版架构被采用，将它登记为第一份基线，用于后续比较。

这些步骤可以迭代，不要求每一步安装、激活或审批一轮。主 Agent 创建文件夹是普通工具操作，不应等一个不存在的旧 baseline。

已有代码库的认知初始化，可以先只读探索；新项目创建目录和写草案，则需要普通写权限。两者不能被一个“探索永远只读”的流程混成一件事。草案和原型可以先存在，正式结构与完成状态仍按实际确认和验证更新。

Skill 指导怎么做；工具负责实际创建文件与执行命令；平台记录任务和结果。草案不是当前实际代码的证据，图可以区分“计划中”与“已实现”，但不用因此建立一套草案治理平台。

默认查看 3 层、必要时展开到 5 层或更深的预算可以保留。是否完成初始化，取决于关键目录、入口、模块和未知区能否被理解，不取决于机械扫满几层。

## 7. A7／A8：复用代码与文档工作直接处理

吸收概念、选择性复制实现、依赖外部包，是三种不同接法。将少量实现纳入本项目维护后，不再依赖外部实验包在运行时提供它；项目承担这部分代码的维护即可。复制内部关联很多的代码可能连带引入额外复杂度，所以以真正节省实现工作为准，保留必要来源说明。

不要求为了借鉴 mailbox、任务通信或编辑方式先写一份“覆盖禁令”的决定。若具体组件另有实际访问或使用限制，针对那一项处理；不把尚不存在的限制推广成所有概念复用的审批流程。未找到的实现，不写成已经确认可复制的能力。

文档方面直接维护当前决定、统一名称与引用。副本降为指针时保留独有内容和历史，不再问“要不要写 ADR”。本稿第 10 节已给出可回填的决策记录正文。原仓库副本和 ADR 索引本次未在工作区提供，故未声称已经修改它们。

## 9. 进入接口设计需要的具体输出

不再把 A 组八项逐条作为“请用户批准”的流程。下一步直接产出与重构有关的四份契约内容，可放入已有文档：

### 决策：以 Session 承载执行上下文，复用角色配置，Kernel 持有运行恢复

**背景。** 先前建议将可复用配置、会话历史和长期主体身份捆绑，进一步引入创建、复核及恢复责任。这超出了当前产品需要，也可能让重构继续保留重复状态和重复读取。

**本轮已明确的方向。**

1. 首版不要求独立跨任务 Agent 主体；角色／能力配置可复用并并行实例化，Session 承载具体工作上下文。
2. 相关任务可以复用已有 Session；是否延续依据工作关系和上下文适用性，不由 Work ID 变化决定。
3. Kernel 实现执行记录、暂停、压缩与恢复；平台提供跨 Kernel 适配、任务编排、图关系和结果同步。
4. AgentLifecycle 正式落地并接收目标职责；重构同时替代旧的重复路径，不能以长期 wrapper 叠加完成。
5. 复用范围表达推荐资料和检索入口。Skill／prompt 指导阅读，真实访问沿用执行端权限；首版不新增普遍逐材料准入体系。
6. 从无 baseline 状态可正常形成草案、创建目录、编写模块接口文档并启动开发；基线记录第一份已采用架构，不作为开始工作的先决条件。
7. 允许吸收外部项目概念与选择性移入实现；区别于运行时依赖。文档副本、索引及本决策记录直接维护。
8. 长期领域专家可以做，方向是角色配置接入知识库与可积累记忆。当前预留接口、接入位置和积累方案，不声明具备已接入知识库、自动记忆积累或长期专家能力。

**本稿的实施建议。** 相关记忆代码作为后续复用线索；本次定义知识读取、记忆读取及积累维护的接口与方案，完整实现不新增为此次交付。只有实际接入并验证后才更新能力声明。taskId 与 workId 是否合并，按真实消费者和语义检查执行，不保留无用途的重复身份。Session 卡片及两图关联使用已有记录与查询机制。

**影响。** 需要同步 ARCHITECTURE.md 的 U11、R 系列、创建／四态定义、L-1、U7、恢复责任、首基线流程和对应接口；必要时撤回先前新增不变量，重新核对真实 DAG。现有历史记录保留可查，Kernel 执行安全边界继续有效。

**完成标准。** 新的对象模型和模块职责成为真实生产路径，重复职责和高成本扫描被移除或收窄；平台能使用 Kernel 已有能力，两图与正常项目开发可用。仅文档增加类型、仅 Fake 演示通过或仅加适配壳，不视为完成重构。
