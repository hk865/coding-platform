# 012 结构改动自动批准：开关按项目存在 Host 设置里，冻结或写入那一刻读一次；平台用固定身份走人批准的同一条写入

状态：采用（乙′ 第一段落设置、结构提案和只因结构性待审的理解注记；第二段落结构性修补和“扣下”，以及同 pin 上晚到的待批提案关成 stale）
日期：2026-11-13

## 背景和约束

- 121-106 第 5 条、121-109：结构提案和结构性修补可以由平台自己批准，两个开关分开管，出厂默认自动；在冻结或暂存那一刻定，之后改开关不影响已经在等的卡（62-6）。
- PRODUCT §7：初始架构（冷启动和加入的粗切分）仍然找你；会盖掉不是平台写的文件、或写后会新增冲突时，仍然出卡。
- 用户答复：开关不是自治规则，不进规则列表（设置页草图）。规则层（`structural_patch` 在第 1 层）不动。
- 答卡只认配置的操作者，并排除平台自动化身份。平台不能“替你答卡”。
- architecture 子模块只能依赖 model、state、persistence、knowledge；项目通知的写者在 communication。

## 选项

开关存哪：

| 选项 | 好处 | 坏处 |
|---|---|---|
| **A. Host 设置，按 projectId 存一张表（选）** | 和 `knowledge-local` 同一套存、推、快照；Host 每次现读最后一份快照，没有新记录、没有新核心路由 | 同一项目在另一台 Host 上是另一份（一个人一台 Host，不处理） |
| B. 项目记录（照 `projects/role-limits`） | 跟着项目库走，提交里能 guard 记录版本 | 新记录格式、两条核心路由、穷举测试；121-109 定了冻结时判，用不上写入时再核 |

平台不传开关时：

| 选项 | 好处 | 坏处 |
|---|---|---|
| **A. 从不自动批准（选）** | 和 `knowledgeLocalOnly` 一样；直接建平台的夹具不用动 | 出厂默认只在 Host 一处 |
| B. 用出厂默认“自动” | 平台自己就有默认 | 十几个直接建平台的注记测试都要加选项 |

怎么批准：

| 选项 | 好处 | 坏处 |
|---|---|---|
| **A. 平台固定身份 `structural-auto-approval`，直接走批准写入（选）** | 和人批准共用 `prepareApproval`：同一份计划、同一次提交、同一套成员和指针 guard；不写答复，不冒充人 | 卡在冻结提交和采用之间短暂存在（同一次调用里） |
| B. 平台去答卡 | 卡的路径不变 | 要么冒充操作者，要么放宽唯一挡住自动化答卡的核对 |

“已自动采用”的通知：

| 选项 | 好处 | 坏处 |
|---|---|---|
| **A. 采用提交之后另发（选，改 4-21）** | 和现有所有 `automatic_adjustment` 一样走 `knowledge.write.notify`，不绕模块边界 | 两步之间崩溃只丢这一条通知；改动本身在架构历史里看得到 |
| B. 并进同一个提交 | 不会丢 | communication 要导出通知片段，经组合根注入两个 owner |

## 选了什么，为什么

- 冻结那一刻读一次开关：立即冻结（工作轮、窗口关着的问答轮）在读窗口之前读，生命周期冻结在提交之前读，只试这次新冻结的批，按批号顺序，采用了一个就停。写入时不再读，卡源也不读开关，所以后存的开关不会放行已经在等的卡。
- 粗切分照旧出卡：问答轮的提案事实带上它在操作里的 `segment`。
- 保护和防循环在账本那一半之前读文件：改写或删除的文件，按记录投影判“不是平台写的”就不采用；写前写后各算一次模块文件的冲突，只看新增的。写前就有的冲突不挡，否则一处旧的双认领会让之后所有自动采用都出卡。按冲突的身份 `(kind, moduleId)` 比：同一处冲突少了参与文件（删掉一个认领者）是变小，不算新增；多了原来没有的文件才算。
- 任何一步不过都不重试，卡留着；被保护挡下时发一条“没有自动采用”说明原因。采用的提交已经落了、知识文件没写成时不算“留卡”（成员已经采用，卡出不来）：两个入口都回 `unavailable`，文件由写日志恢复。
- 理解注记只放“原因恰好只有结构性”的：矛盾、替换要人看；`quota_full` 不在开关范围里，而且人的卡源每次都按注记头重算原因，放给书记也收不了。
- 自动采用的命令身份只由批号定，崩溃后再来按回执重放；提案工具的回放也回 `applied` 和同一个 pin。
- 结构修补（第二段）在暂存那一刻读 `repairs`，判定记在注记头上：修补卡是每次读都重算的投影，头的 revision 就是版本、轮次按版本绑着它，事后写不回去。只改名的修补也算（Q5）。激活时做同样的保护；挡下时发一条“没有自动采用结构修补”，这条通知记录就是“扣下”标记（Q6 (a)，身份固定，一次 `readMany` 看在不在），卡源和激活都读它：在就出卡，人批准后照人批准的路径激活、不再判保护。每步确认的目标和 footprint 未知照旧要卡，人批准的那次激活不做保护。
- 自动采用让冻结的同一次调用就移动 pin，同一个 pin 上晚到的待批提案再冻结时试算回 `source_stale`；改成在冻结里关成 `stale`，冷启动、加入和后续探索不再每一趟都失败在冻结上（第一段遗留 (a)）。

## 代价

- Work Run 里提案工具可能当场写知识文件，工具超时从 10 秒改成 60 秒；超时中止算失败，卡留着。
- 同一个工作轮里自动采用之后再拿旧 pin 提案会回 `source_stale`，工具说明让它换新 pin。
- `architecture.json` 被人手改过后，在下一次经卡批准的写之前，所有自动采用都会出卡。
- 修补卡出不出取决于那条通知记录在不在：通知发不出时，下一趟激活重判、重发，在那之前既不出卡也不激活。
- 晚到的提案关成 `stale` 时不出卡、不发通知；参谋要在新 pin 上重新提。
