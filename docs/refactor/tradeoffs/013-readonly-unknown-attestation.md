# 013 只读查询里结果未知的调用由平台认定：用固定平台身份走人认定的同一个入口，状态机按工具名放行

状态：采用（第十七批 `4cadb538`，决定 121-142）
日期：2026-11-17

## 背景和约束

- Host 被强行关掉时，正在跑的工具调用可能只记了“开始”、没记结果。重启核对把这一轮 QueryRun 记成结果未知（QRR-05），之前只能等人从 `queries/resolve-unknown` 认定（QRR-06）。
- 规划轮、探索轮大多在读文件、读图，这个窗口很常见；每次都等人，人就成了重启后的瓶颈。
- 用户 11-17：“可行，两条一起做吧”。只读工具的结果未知由平台认定，不交参谋，也不交人。
- 用户的标准是“不改东西、没有外部影响”。跑命令、联网抓取和搜索都不算只读，照旧走两层。
- Work Run 那边已经由 RUN-25 自动收尾（只读条目 `no_review_needed`），这次不动。
- 平台的自动化身份不能答卡（取舍 012 同一条规矩）。

## 选项

| 选项 | 好处 | 坏处 |
|---|---|---|
| **A. 固定平台身份，走人认定的同一个 Host 入口和 QRR-06；工具名作为事实由入口读出，状态机判断（选）** | 结果和人认定完全一样（关成 `failed`、放开 Session、保留游标、用量照预留计）；租约、理由、版本钉照旧核对；只改一条迁移的守卫 | 平台身份要加进 `PLATFORM_AUTOMATION_ACTORS` |
| B. 启动核对里加一条自动关闭，QRR-05 直接关 | 不经入口，少一次读 | 另写一套关闭，和人认定的结果可能走偏 |
| C. 交参谋判断 | 和 Work Run 的两层一致 | 只读调用没有可判断的后果，白跑一轮查询 |

## 选了什么，为什么

- **名单只在一处。** `src/core/work-graph/state/query-run-recovery.ts` 的 `PLATFORM_ATTESTED_READ_TOOLS`，共 24 个，显式列名，不从 K3 表推（K3 表的 read_only 里有联网和命令）。名单有三类：
  - Kernel 的读文件；
  - 和它一起挂上的探索工具；
  - 平台的读（收件箱、消息、任务图、执行历史等）。
- **一个不是就整次不认定。** 没出结果的调用里只要有一个不在名单上，就不拆开，照旧等人。
- **名字读不到就不认定。** Kernel 读不到、没有 Turn 时名字为空，返回 `forbidden`，什么都不写。
- **平台身份先判名单，再动东西。** 入口先只读地取 Kernel 事实和工具名，用同一个函数 `platformAttestsUnknownCalls` 判断名单；成立了才确认消息、提交（Codex 审查第 1 条）。状态机的守卫用同一个函数再判一次。
- **排除的工具：** `run_readonly_command`、`check`（都会起进程跑命令）、`web_fetch`、`web_search`、一切写入和提交。
- `python_index` 在名单里。它会起分析子进程、加载 Jedi、在临时目录里建源码副本，但不改工作区、没有外部影响。Codex 审查第 2 条主张把它拿掉，lead 驳回，因为这符合用户的标准。

## 代价

- 名单要人工维护：新加一个读工具，不加进名单就照旧等人。
- 被认定的一轮算失败，不自动重跑；要重做，由上层照常再发。
- 用量不当 0，按预留量计，可能比实际多。
- “写文件按现场核对”这次没做：Work Run 已经由 RUN-25 在下一轮对照现场接着做，照原计划改反而更严。

## 什么情况变了要重新考虑

- 名单要加工具，尤其是会起进程的（例如 `check`）。
- Query 被认定以后要自动重跑。
- Work Run 被 RUN-25 的护栏挡下时（工作区不是 git、同一任务连续第二次自动收尾等），也想自动认定。
- 008、009 讲的是核对记录的两层；Query 的结果未知没有核对记录，所以那两篇不用改。如果以后 Query 也建核对记录，三篇要一起看。
