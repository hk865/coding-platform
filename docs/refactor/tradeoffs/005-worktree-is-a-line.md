# 005 worktree 是同一工作区的一条线，不算扩张

状态：采用（决定 121-68、121-75）
日期：2026-11-09

## 背景和约束

- 第二个文件夹有两种：另一种代码（另一个仓库）是项目的扩张，按 121-36 加工作区、路径带前缀；同一份代码的另一个版本（分支、worktree）不是扩张。`worktree` 是 git 的另一个检出：同一个仓库、共用 `.git` 对象库，各自有工作目录和分支。
- 如果把 worktree 当扩张，每个模块会在图上出现两遍（`src/auth` 和 `/@ws:v1/src/auth`）；加入时要把整份代码重新探索一遍，白花钱；注记分两份；参谋多占一批线的席位；平台也表达不了“这个修复两边都要做”（[HANDOFF 121-64](../HANDOFF.md)）。
- 这里的“线”是版本线：一个工作区（一个仓库）里的一条检出/分支。不是角色线，也不是任务图上的工作线。工作区按 git 仓库认，线按检出认，两者不是一回事。
- 前提是第 2 步：代码知识进仓库文件，文件为准，库只是索引（[HANDOFF 121-68](../HANDOFF.md)）。没有这个前提，线读不到自己文件夹里的知识，下面的做法不成立。
- worktree 共用 `.git` 对象库；缓存规则是按内容哈希共享，所以同一份内容在不同检出里只算一份（[HANDOFF 121-75](../HANDOFF.md)）。
- 121-64 当时是 lead 的建议、等用户定；121-68 用户 11-09 让数据分层的三步（每个项目一个库、代码知识进仓库、线）都改到 MVP 之前，worktree 是第 3 步的一部分（[HANDOFF 121-64](../HANDOFF.md)、[HANDOFF 121-68](../HANDOFF.md)）。
- 这一篇只定“worktree 怎么建模”；数据分层见 001，路径前缀见 004，具体施工排在 KLS-3a、3b。

## 选项

四个选项和否掉的理由来自决定 121-64、121-68。

| 选项 | 怎么做 | 好处 | 坏处 |
|---|---|---|---|
| 当扩张 | 按 121-36 给 worktree 加工作区、路径加前缀、重新探索 | 隔离简单，每个检出像一个独立工作区 | 每个模块出现两遍、整份代码重新探索、注记分两份、参谋多占席位、表达不了“两边都修” |
| 自己做版本线 | 每条线一个当前基线指针；开分支写时复制；注记按出生线继承；合并时自己做三方合并 | 当时没有记录 | 等于重做 git；rebase/cherry-pick（git 的变基和挑提交）跟不上 |
| 拒绝，提示单独开项目 | 加入时判断“和已有工作区是同一个 git 仓库”（`git rev-parse --git-common-dir` 相同；另一份克隆再比第一个提交），是就拒绝并提示作为单独项目打开 | 不重复，改动小 | 用户想在同一项目里同时看两个版本时做不到；当时没有记录更多代价 |
| **一条线** | 工作区 = 一个仓库；线 = 一个检出（文件夹 + 分支）；每条线读自己文件夹的知识文件 | 模块号仍是同一个，不为每个检出再造一套模块身份；缓存按内容哈希共享；分支、合并交给 git | 目标、Session、Run 要绑线；冲突只按线算；线多时界面要按线分组 |

## 选了什么，为什么

- 选“一条线”：工作区是一个仓库，线是一个检出（文件夹 + 分支）。每条线读自己文件夹的 `.workbench/`；目标、Session、Run 三处带线（[HANDOFF 121-75](../HANDOFF.md)）。
- 为什么：git 已经会做分支、合并、写时复制和内容哈希；自己做版本线等于重做 git，rebase/cherry-pick 跟不上。把 worktree 当扩张则会把同一份代码的模块、注记和参谋席位都翻倍，还要重新探索（[HANDOFF 121-64](../HANDOFF.md)、[HANDOFF 121-68](../HANDOFF.md)）。
- 线不是“再开一个工作区”：工作区仍是项目登记的那个仓库；线只是这个仓库里的一个检出。这样项目只有一张架构图、一套模块身份，版本差异由 git 的树和线的分支表达（[HANDOFF 121-64](../HANDOFF.md)）。
- 架构图仍按项目一份（身份是项目 + 基线 + 修订号），不为每条线各建一张图；线只决定读哪个检出的知识、目标绑哪条线（[HANDOFF 121-64](../HANDOFF.md)）。
- **目标、Session、Run 三处带线。** 目标绑一条线，目标栏按线分组；Session 和 Run 从目标继承线；Run 的执行根取目标所在线的文件夹，不再取项目的根（[HANDOFF 121-72](../HANDOFF.md)、[HANDOFF 121-75](../HANDOFF.md)）。
- **模块编号按工作区限定，不按线。** 同一工作区的两条线同号、同 claim（区域认领）；不同工作区的同号在项目视图里是两个编号（前缀见 004）。语义冲突只在同一个工作区/线内算（[HANDOFF 121-75](../HANDOFF.md)）。
- **合回要有条件。** 一条线算“已合回”要同时满足：这条线不是 base 线（合回的目标分支所在的线）；它的 HEAD（git 当前提交）不等于分叉点；它是 base 分支的祖先（也就是有新提交进了 base）；它的工作树没有未提交改动（代码和知识文件都算）。base 线自己提交后仍是 open，不判成已合回（[HANDOFF 121-72](../HANDOFF.md)、[HANDOFF 121-75](../HANDOFF.md)）。
- **线建时记分叉点。** 刚开的线 HEAD 等于分叉点，不算已合回；合回用的 base 分支取主工作区在项目创建时的分支，记在工作区状态里（[HANDOFF 121-72](../HANDOFF.md)、[HANDOFF 121-75](../HANDOFF.md)）。
- **线状态放项目库。** `forkPoint`、`status`、`closedAt` 进项目库的 `LineSnapshot`，不进 Host settings；线是项目状态，能审计（[HANDOFF 121-75](../HANDOFF.md)）。
- 合回后：线状态 `merged`，平台对这条线的文件夹做一次对账、动过的注记标待核实，然后这条线只读；不删记录（[HANDOFF 121-75](../HANDOFF.md)）。
- 今天树里没有 `--git-common-dir` 的实现（`grep -rn "git-common-dir" src` 0 命中），线模型排在 KLS-3a、3b（[HANDOFF 121-75](../HANDOFF.md)）。

## 代价，以及因此要守的规矩

- **必须先有第 2 步。** 代码知识在仓库文件里，文件为准；线才能读自己文件夹的知识。知识只在库里时，不要先上线模型（[HANDOFF 121-68](../HANDOFF.md)）。
- **不要把 worktree 建模成第二个工作区、扩张或第二套模块号。** 不要为每个检出重新探索整份代码，不要复制模块身份（[HANDOFF 121-64](../HANDOFF.md)）。
- **不要自己写三方合并、rebase、cherry-pick 或“当前基线指针”。** 这些交给 git。平台只记录“这条线是哪个检出、哪个分支、分叉点在哪、目标绑哪条线”（[HANDOFF 121-64](../HANDOFF.md)）。
- **目标绑一条线。** 跨线的“两边都修”是另一条线上的新目标，链到原目标，不把一个目标同时挂到两条线（[HANDOFF 121-64](../HANDOFF.md)、[HANDOFF 121-75](../HANDOFF.md)）。
- **冲突只在同一条线里算。** 不同线的同一模块不因为路径相同就报冲突，跨线的协调靠目标和接续，不靠冲突检测（[HANDOFF 121-75](../HANDOFF.md)）。
- **合回判定排除 base 线自身。** base 线自己提交后仍 open，不能因为它的 HEAD 是 base 分支的祖先就判成 merged（[HANDOFF 121-72](../HANDOFF.md)）。
- **合回后结束这条线、重新索引、动过的标待核实。** 不要留着线继续写，也不要把旧索引当现行（[HANDOFF 121-75](../HANDOFF.md)）。
- **缓存按内容哈希共享。** 同一内容在两个检出里只算一份，不要按线各建一份缓存；否则线一多，缓存就成倍长（[HANDOFF 121-75](../HANDOFF.md)）。
- **界面按线分组显示目标和线。** 线多时不能把所有线的任务混成一张没有归属的列表（[HANDOFF 121-64](../HANDOFF.md)）。
- **`workspaceId` 仍是项目内的 id。** 不把路径塞进账本；线的文件夹路径只用于读写和 git，不替代 id（[HANDOFF 121-64](../HANDOFF.md)、[HANDOFF 121-75](../HANDOFF.md)）。

## 什么情况变了要重新考虑

- 用户要用 Perforce 一类非 git 的版本管理：没有 worktree 和内容哈希，要版本管理适配层，线模型和缓存共享都要重写（[HANDOFF 121-69](../HANDOFF.md)）。
- “同一个 git 仓库”的判断不可靠时（例如浅克隆、两个独立根、第一个提交不同），要重新定加入时的判断和提示；今天的做法是 `git rev-parse --git-common-dir` 相同，另一份克隆再比第一个提交（[HANDOFF 121-64](../HANDOFF.md)）。
- 线多到目标栏按线分组不可用，或者合并/重索引经常漏标“待核实”时，要重新看线的显示和合并后的重索引规则（[HANDOFF 121-75](../HANDOFF.md)）。
- 用户需要同一条分支的多个检出、或者一条线里再分工作目录时，今天的“线 = 一个检出”可能不够；当时没有记录这种需求（[HANDOFF 121-64](../HANDOFF.md)）。
- 如果第 2 步没有按计划落地（知识仍在库里），线模型要暂停，不能在没有“文件为准”的情况下先上线（[HANDOFF 121-68](../HANDOFF.md)）。
- 一条线长期不合并时，知识文件和注记会分叉（起草方推断）；什么时候提示合并、结束线或把线归档，当时没有记录。
- 项目需要同时看两条线的完整图并做跨线冲突：这时再加“线视图合并”，不改“线 = 检出”这个定义（起草方推断）。
