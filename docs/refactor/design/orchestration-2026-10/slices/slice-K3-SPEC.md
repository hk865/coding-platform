## 0. 给用户看的要点

**问题。** 一次执行被中断时，可能有一个工具调用“开始了、没结果”。今天平台把它记成“结果未知”，等你点“认定”。认定以后，接续说明里只有一句笼统的提醒：

> “结果未知”的工具调用可能已经产生副作用，重做之前先核实当前状态。

这一句不够：不同的工具，核对的办法和风险都不一样。

**K3 之后，按工具种类分别核对：**

| 种类 | 例子 | 怎么核对 | 谁来判断 |
| --- | --- | --- | --- |
| 只读 | 读文件、搜索、列目录、只读命令 | 没有副作用，不用核对 | — |
| 平台工具 | 发消息、改任务图、写注记 | 平台按这次调用的请求号查记录：提交了就是“已做”，没提交就是“没做” | 平台 |
| 改文件 | 编辑、写入 | 接续说明附上这几个文件的 git diff；模型对照原本要改成什么 | 下一轮的模型 |
| 跑程序、动环境 | `shell` 命令：构建、装依赖、迁移、生成文件、起进程 | 先跑一轮只读的“核对轮”，查清这条命令的效果；判断不了就交给你 | 核对轮的模型，判断不了交给你 |

**核对轮。** 只要有“跑程序”类的结果未知，接着做的第一轮就是一次只读执行：
- 能读文件、能跑只读命令（例如 `git status --ignored`、看生成的文件、看本地数据库），不能写，也不能再跑那条命令。
- 它对每一条结果未知的命令写一条核对结论：已做 / 没做 / 做了一半 / 判断不了，附上依据。
- 每一条都是“已做”或“没做”：自动接着做，结论放进下一轮的接续说明。
- 有一条是“做了一半”或“判断不了”：发一张“请你决定”，附上依据。你选：
  - 重做；
  - 当作已做，跳过；
  - 我来处理（任务暂停，等你）。

**这套核对用在两处：**
1. **你认定以后**（决定 51 的那种线）：认定以后不再直接接着做，先走上面的核对。你不用自己去翻工作区。
2. **重启后的自动收尾：** Host 崩溃或被关掉，重启时新 Host 凭实例租约证明旧进程已经不在（`src/app/host-instance-lease.ts`），也就证明了那个工具不在跑了。平台不再等你认定，直接收尾，再走上面的核对。

**自动收尾的两道限制（因为平台只知道 Host 停了，不知道为什么停）：**
- **同一个任务，连续只自动收尾一次。** 如果正是那条命令把 Host 弄崩了，接着做又会在同样情况下中断。第二次就照今天的做法等你认定，不会无限循环。
- **只在看得清改动时才自动收尾：** 工作区是 git 仓库，改动清单采集得到。采集不到就照今天等你。

**仍然等你认定的：**
- Host 一直活着，执行中途出了“结果未知”（旧进程还在，证明不了已停）；
- Kernel 记录读不了；
- 让出等回复的那一轮，等待重建不了；
- 那次执行身上挂着还没生效的暂停或取消；
- 上面两道限制挡下来的；
- 查询（秘书回合、问一问）：本片和 K 片一样只做 Work。

**要你同意的：**
1. 改掉 10-03 的 D-4 和决定 45 的一部分：符合上面条件的“重启后结果未知”，不再一律等你认定。
2. 自动收尾这一次按“被中断”算，不占普通的返工上限，由“连续一次”这道限制兜底。
3. 核对轮判断不了时，用“请你决定”卡，三个选项如上。

## 1. lead 的技术选择（草稿）

**A. 结果未知的调用怎么分类、平台能定的先定**

- **L1 分类。** 每个结果未知的调用，按它在 Kernel 里的工具名和工具定义的效果分类：
  - **只读：** 效果分类 `read_only` 的内置工具和扩展工具，以及 `run_readonly_command`；
  - **平台工具：** 名字在平台协作工具清单里（消息、任务图、白板、注记、看/找/记）；
  - **改文件：** 内置 `edit`、`write`；
  - **跑程序：** 内置 `shell`；
  - 其它不认识的：按“跑程序”处理，最谨慎。
- **L2 平台工具由平台定结果。**
  - 这些工具的请求号由 Kernel 工具调用的 `callId` 加绑定的 Run 推出（`execution-driver.ts:requestIdForCall`），模型给不了。
  - 收尾时平台按这个请求号查提交回执：有回执就是“已做”，结果照回执；没有就是“没做”。
  - 结论写进核对记录（L4），来源标“平台查记录”。
- **L3 改文件附 diff。**
  - 接续说明对这些调用列出目标路径，以及这些路径在工作区里相对基准提交的 diff（有界，超长截断并标出）。
  - 不由平台判断“改没改”，由下一轮模型对照调用参数判断。
  - 工作区不是 git 或采集失败：照 L7 处理。

**B. 核对轮**

- **L4 核对记录。** 每次收尾（人认定或自动收尾）给这次 Run 建一份核对记录，逐条列出结果未知的调用：
  - 种类；
  - 参数摘要（命令、cwd、路径）；
  - 结论（平台已定 / 待核对 / 已做 / 没做 / 做了一半 / 判断不了）；
  - 依据；
  - 谁定的。

  记录的写入经 `state/` 的构造器，和原执行的事实分开存。
- **L5 有“跑程序”的待核对条目时，先跑核对轮。**
  - 核对轮是同一个 Session 上的一次只读 Work（写范围为空）。工具只有只读工具和 `run_readonly_command`，外加一个新的平台工具 `record_unknown_call_review`，入参 `{ callId, verdict, evidence }`。
  - 它的输入是核对说明：每条待核对调用的完整参数、开始时间、当时的工作区事实，以及“不许重跑这条命令”。
  - 核对轮结束时，每条待核对调用都要有结论；没有的记成“判断不了”。
  - 核对轮本身不改工作区，不算一次返工。
- **L6 核对之后。**
  - 全部是“已做”或“没做”（含平台已定的）：照 K 片接着做，核对记录放进接续说明。
  - 有“做了一半”或“判断不了”：发一张“请你决定”（新的来源种类 `unknown_call_review`），附核对记录。选项是：
    - 重做：把这条调用当作“没做”，接着做；
    - 当作已做：接着做，不重做；
    - 我来处理：任务暂停，等你。

    答复照第 5 片的决定卡流程落实。
- **L7 看不清改动时。** 有“改文件”或“跑程序”的待核对条目，而工作区采集不到（不是 git，或读取失败）：
  - 自动收尾不做，照今天等人认定；
  - 人认定之后的核对轮照做，只是接续说明标明“改动清单拿不到”。

**C. 重启后的自动收尾**

- **L8 新的结束行 RUN-25。** 启动核对里，一个 Run 满足下面全部条件时，直接结束为 `crashed`，不进入 `outcome_unknown`：
  1. 这个 Host 持有实例租约，而且是接手来的（HL-01，或 HL-03 旧进程已不在；内存存储时总成立）；
  2. Kernel 探测 `ready`，这个 Run 的 Turn 存在，至少一个工具调用是“已开始、没结果”或已是 `outcome_unknown`（今天 RUN-20 的第 (i) 种）；
  3. 指针上没有排队的暂停或取消；
  4. 已接受的输入核对过来源；
  5. 工作区采集得到（L7）；
  6. 这个任务上一次接续的来源不是 RUN-25（“连续一次”的限制）。
- **L9 一次提交写完。**
  - 核对观察是新的一种 `takeover_unresolved`，内容：结果未知的调用 ID、观察到的位置，以及接手证明（租约行号、旧进程号、旧实例 ID）。
  - `terminalPayload` 写 `host_takeover: <N> tool call(s) with unknown results`。
  - Attempt、Outbox 结算，租约释放，Session 释放成 `unavailable/kernel_turn_open`（SES-06）。
  - 同一提交建立核对记录（L4），其中平台工具一类已按 L2 定好。
- **L10 任务按“被中断”算。** 失败类别推导加一行：`crashed` + `takeover_unresolved` → `interrupted`，`interruption: 'executing'`，不比较“无进展”的键，不占普通返工上限。自动化照常重排，在“请知悉”里以“自动恢复”出现。
- **L11 接上 K 片。**
  - K 片 L4 第 2 条的结束方式表加一行：`takeover_unresolved` 不要 TaskRequeue。
  - K 片 L7 维护插入点的第 3 条加上它。
  - 关闭悬空 Turn、留在原 Session，都照 K 片；然后按 L5–L6 核对。
- **L12 不变的：**
  - RUN-08；
  - RUN-20 的 (ii)、(iii)，以及被 L8 第 3、5、6 条挡下的 (i)；
  - RUN-22 的人工认定入口（认定之后多了核对，L4–L6）；
  - Query 的恢复行；
  - RUN-21 迟到证据在 RUN-25 之后不再改结果。
