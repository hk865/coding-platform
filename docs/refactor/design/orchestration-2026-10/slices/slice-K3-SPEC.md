# K3 片规格（草稿）：重启后的“结果未知”自动收尾

> **状态：lead 起草，2026-10-13，先给用户看（决定 51）。用户同意以后再交 Codex 审查、确认测试入口、冻结。** 依据：HANDOFF 决定 45、51，10-03 的 D-4（U-4）；STATE-MACHINES-SPEC 的 RUN-08、RUN-20、RUN-22、§12.8 HL-01..HL-07；K 片规格（关闭悬空 Turn，已冻结）。K3 要在 K 片 A 部分合入以后施工。

## 0. 给用户看的要点

**今天：** Host 中途崩溃或被关掉，重启时如果某个工具调用开始了、没有结果，这次执行就记成“结果未知”，线停在“待核对”，一直等你点“认定”。

**为什么可以不用你点：**
- 重启时新的 Host 能接手，靠的是实例租约。只有旧 Host 进程确实已经不在，它才接得了手（`src/app/host-instance-lease.ts`）。所以“那个工具还在不在跑”已经有了答案：不在跑。
- 命令在沙箱里跑，跟着 Host 一起退出，也不能联网。平台自己的写入（发消息、改任务图）是数据库事务，查得到有没有提交。
- 剩下真正不知道的，只有“工作区里的文件改没改、改了多少”。这件事交给下一轮先核对再做。接续说明里本来就有这句：“‘结果未知’的工具调用可能已经产生副作用，重做之前先核实当前状态”。

**K3 之后：**
- 重启时遇到这种执行，平台自己收尾：记下哪几步结果未知，结束这次执行，用 K 片的关闭把悬空 Turn 收掉，线回到可用。任务按“被中断”处理，自动接着做，不算一次返工。
- 你会在“请知悉”里看到一条“自动恢复”（已有的自动返工通知），执行详情里写着“重启后自动收尾，N 步结果未知”。

**仍然等你认定的（证明不了，或者情况不对）：**
- Host 一直活着，执行中途出了“结果未知”（少见；旧进程还在，证明不了已停）；
- Kernel 记录读不了（不知道到底进没进 Turn）；
- 让出等回复的那一轮，等待没法重建；
- 那次执行身上挂着你或目标发出的暂停、取消，还没生效；
- 查询（秘书回合、问一问）的结果未知：本片不改，和 K 片一样只做 Work。

**要你同意的两件事：**
1. **改掉 10-03 的 D-4 和决定 45 的一部分：** 上面那种“重启后、旧进程已证明不在、Kernel 读得到”的结果未知，不再一律等你认定。
2. **这种自动收尾按“被中断”算，不按“失败”算：** 自动接着做，不占返工上限（和今天的“重启时中断、没有在途工具”一样）。另一种做法是按“失败”算，占一次返工上限，到上限就停下等你。我建议按“被中断”算，因为原因是 Host 崩溃，不是工作做错了。

## 1. lead 的技术选择（草稿）

- **L1 新的结束行 RUN-25，不经过“结果未知”。** 启动核对里，一个 Run 满足下面全部条件时，直接结束为 `crashed`，不进入 `outcome_unknown`：
  1. 这个 Host 持有实例租约，而且是接手来的（HL-01 锁不存在，或 HL-03 旧进程已不在；内存存储时总成立）；
  2. Kernel 探测 `ready`，这个 Run 的 Turn 存在，至少一个工具调用是“已开始、没结果”或已经是 `outcome_unknown`（今天 RUN-20 的第 (i) 种）；
  3. 指针上没有排队的暂停或取消（有的话照今天走 RUN-20，等人）；
  4. 已接受的输入核对过来源（和 RUN-19 一样，§10.3）。
- **L2 一次提交写完，记下证据。**
  - 核对观察是新的一种 `takeover_unresolved`，内容：
    - 结果未知的工具调用 ID；
    - 观察到的位置；
    - 接手证明：租约行号、旧进程号、旧实例 ID。
  - `terminalPayload` 写 `host_takeover: <N> tool call(s) with unknown results`。
  - Attempt 照 RUN-22 的方式结算，Outbox 结算，租约释放，Session 释放成 `unavailable/kernel_turn_open`（SES-06）。
- **L3 任务按“被中断”算。**
  - 失败类别推导加一行：`crashed` + `takeover_unresolved` → `interrupted`，`interruption: 'executing'`，不比较“无进展”的键，不占返工上限。这和今天的 RUN-19 一样。
  - 自动化照常重排，在“请知悉”里以“自动恢复”出现（已有的 `automatic_rework` 通知，`automatic && !counted`）。
- **L4 接上 K 片。**
  - K 片 L4 第 2 条的结束方式表加一行：`takeover_unresolved` 不要 TaskRequeue。
  - K 片 L7 维护插入点的第 3 条加上它。
  - 之后关闭悬空 Turn、留在原 Session、接续说明列出结果未知的那几步，都照 K 片。
- **L5 不变的：**
  - RUN-08（Host 活着时的结果未知）；
  - RUN-20 的第 (ii)、(iii) 种，和指针上有暂停或取消的第 (i) 种；
  - RUN-22 的人工认定入口；
  - Query 的恢复行（QRR-*）。
- **L6 迟到的证据（RUN-21）。** RUN-25 已经结束的 Run，之后再读到 Kernel 的新事实，不再改结果（和 RUN-22 之后一样）；原记录照常可读。
