## 1. 要解决什么

用户原话（11-01）：

> 我们任务图作为白板的指导，规划的意义没有用上……它应该具备自动分解任务，处理分解任务的核对，以及实操中发现前提错误/超出预算/矛盾/等的处理，以及并发顺序的安排。

> 这就是产品原来的设计……这严重影响了我们的产品的最终的功能和展现，它这样子的话肯定会自动化实施不了我们的目标的，所以说肯定要改。

原始设计里写定的：任务图是“monitor + 可编辑的参谋部白板”（`PRODUCT-history.md:413`，R01）；未来节点逐步细化（R20）；只支持 Host 提交计划不算自动化完成（R22）；无 ready 时“能在授权内补足的继续细化”（`MVP-BEHAVIOR.md:115`，B03）；范围内细化由 Workflow 以平台身份自动采用（`DESIGN.md:517`，决定 15、35）。

**现状：闭环的下半圈通了，上半圈没通。**

| 环节 | 今天 | 用户要的 |
|---|---|---|
| 执行、检查、同义务返工、完成 | 通 | 不变 |
| 分解、逐段细化 | 只有一次性初始计划 | 自动分层，参谋逐段细化 |
| 核对分解 | 只查格式 | 处理分解任务的核对（R40），写任务书时让模型核查（R46） |
| 执行中发现问题 | 有停止，有问答，不回计划 | 回到计划，列影响 |
| 并发顺序 | 软排序；模块门在 W2 | 参谋安排，派发围绕它 |

根因：我们按状态机和 owner 切片，计划只有“采用”这一个入口。用户的施工流水线（lead 切片写书、Codex 审书、DSH 写码、Codex 审查、lead 定返工、裁定矛盾）正是产品要做的事，但没人把它当作产品流程设计过。

不做的事：

- 不自动拆目标（决定 49）。
- 不新增层级，不新增记录种类。
- 不把语义判断做成平台拒绝规则（`PRODUCT.md:325`，R50、R52）。
- 不做事前并发证明（R52）。
- 不默认启动四个 Agent（AGENTS）。

## 3. 设计原则

沿用 v3 的五条（平台机械触发、用现成链路、等待只挡那一支、沉默不扩权、读不到写未知），再加四条：

6. **计划的东西都在白板上。** 任务书就是细化提案，不另建文档体系。
7. **采用只有一个入口：目标循环。** 不管提案从哪来。
8. **平台只判事实，语义交给模型。** 平台的诊断不拒绝入图，只影响能不能自动采用。
9. **所有偏差走一条路。** 入口可以多，判断只有一处。

## 4. 闭环

```
目标采用：骨架 + 第一段（人采用）
    ↓
执行这一段 → 检查 → 同义务返工
    │              │
    │ 下一段只有占位 │ 发现偏差
    ↓              ↓
参谋规划轮：写这一段的任务书，或者改计划并列影响
    ↓
候选 → 机械诊断 → 审阅轮 → 采用（范围内自动，范围外出卡）
    ↓
回到执行
```

用户的施工流水线在产品里的对应：

| 施工 | 产品 | 今天 | 本设计 |
|---|---|---|---|
| lead 切片写书 | 参谋规划轮 | 没有 | 第 5 节 |
| Codex 审书、演练 | 审阅轮 | 没有 | 第 6 节 |
| DSH 写码 | 执行者 | 有 | 不变 |
| 测试 | 检查 | 有 | 不变 |
| Codex 审查 | 独立审阅 | 第 9 片 | 不变 |
| lead 定返工 | 参谋 + `request_rework` | 7C-1 R | 不变 |
| 三轮后换人 | 到上限开参谋轮 | 只停 | 第 7 节 |
| lead 裁定矛盾 | 参谋判断，需要时升级给人 | 没有闭环 | 第 7 节 |
| lead 排并行 | 参谋写依赖和约定 | 部分 | 第 8 节 |

**闭环的前提：** 产品和架构已经定了。用户原话：“产品决定了，架构等搭好了之后几乎是全自动的”。

上层的次序（`ARCHITECTURE.md:6`：先定数据结构与行为，再设计状态机，最后推导模块和方案）：

| 层 | 在哪 | 谁定 |
|---|---|---|
| 产品 | `PRODUCT`、`MVP-BEHAVIOR` | 人 |
| 数据和行为 | `CORE-DATA-OPERATIONS` | 随设计定 |
| 状态机 | `STATE-MACHINES-SPEC`，代码在 `state/` | 随设计定 |
| 模块和方案 | `ARCHITECTURE`、`modules/`、`module-dag`；产品里是正式架构图 | 人采用；之后的结构改动走 8C，两档都出卡 |
| 目标、骨架 | 计划 | 人采用 |
| 段的任务书 | 计划 | 第 6 节 |
| 代码 | 工作区 | 检查和返工 |

本设计只管后三层。第 6.3 节“每层只审一次”对前四层同样成立；架构图会随工作变，按每次改动审。

## 5. 分解

### 5.1 目标采用、触发、分段输出

沿用 v3 的 5.1、5.2、5.4、5.5：规划输出“阶段骨架 + 第一段”；阶段 gate 按阶段验收；Workflow 走到等待、存在活动的必需 `plan_only` 任务时，发一条系统 `action_request` 给参谋；模型只输出这一段，平台合并成完整草稿。

没有参谋时出 `adviser_creation` 卡给人，不发给秘书（决定 103-1）。7D2 的 L26 开局就建秘书、参谋、书记三条线，所以之后通常有参谋。

### 5.2 系统轮

v3 的细化请求改成通用的“系统轮”：系统发 `action_request`，请求号固定，前缀决定这一轮做什么。

| 前缀 | 收件 | 这一轮做什么 |
|---|---|---|
| `refine:` | 参谋 | 写下一段的任务书 |
| `deviation:` | 参谋 | 判断偏差（第 7 节） |
| `planreview:` | 审阅者 | 审候选（第 6 节） |
| `planfix:` | 参谋 | 按审阅意见改候选 |
| `planresume:` | 参谋或秘书，原规划线 | 人答完问题卡后接着规划 |

N 组的约定请求也走这条消费路径（第 8 节）。

- 消费这一侧的改法同 v3 5.4：`offerKindOf` 和 `proveInterventionSource` 接纳 Host 系统身份的 `action_request`；`handleIntervention` 不走 `latestWork` 回退，用 `message.goalRef`；不走 `claimFirstReady`。
- 执行者、审阅者发给参谋的 `action_request` 走同一分支。按发信身份和收件线职责判断这不是“让这条线继续任务”；消息的 `taskRef` 只作规划上下文，不进领取分支（`intervention.ts:75`、`:104`）。
- 不新增消息字段。前缀在已有的请求号里。
- 一轮的收尾按 v3 5.3：系统轮的消息一定结束，有候选就结束在“候选已写入”，不等采用。执行者在等的消息例外，见 7.3。
- **人答完问题卡后接着规划（IV2 留下的）：** 目标循环发下一条系统规划请求 `planresume:`，内容带原问题和已存答案，开新 Query。旧 Query 留着不重跑（Query 身份按消息固定，`query-job.ts:104`）。原消息的等待不变。
  - **谁发：** 目标循环每轮读这个目标“已答、还没续轮”的规划问题，和第 6.1 节读候选放在一起。规划问题待答时，目标循环用读前游标登记等待，依据含 `SessionMessage`；答卡的提交就是这种记录（`decision-service.ts:833`、`goal-wait-wakes.ts:31`），所以提交叫醒目标。重启时，有待答或已答未续轮规划问题的目标都重新登记（第 6.1 节）：还没答就重启，之后答卡照样叫醒目标；答案已存、请求还没发就重启，也补得回来。请求号固定，重复发不会多一轮，不加记录。
  - **怎么回原消息：** 续轮的 Query 来源是它自己的消息 R，邮箱要求答案和被回复的消息精确对上（`mailbox-service.ts:1104`），不能直接回 M。所以 `intervention_planning` 这一臂加一个字段 `repliesToMessageRef`：只有 `planresume:` 填，值是原消息 M，建 Query 时冻结，只有 Host 路径能写。邮箱检查比这个值，仍是精确相等。这是本设计加的唯一一个字段，依据是第 7.3 节“回答”这一行：人答完之后的结论要回到在等的执行者。

### 5.3 任务书放在哪

**用户已定 A，条件见下（D7）。** 我之前向用户提的是“每阶段第一个任务写任务书，产出文档，下游声明 artifact 依赖”。盘点后不建议这样做：

| | 方案 A：任务书就是细化提案 | 方案 B：单独文档任务 |
|---|---|---|
| 内容放哪 | 每个任务的 `assignment.instruction`，接口约定写模块注记，阶段说明只作说明 | 工作区文件 |
| 送到执行者 | `{{task}}`，现成 | 第 2 节第 6 行断了，要补按标签发布产物 |
| 怎么算写完 | 提案写入就是写完 | 第 2 节第 7 行：要注册命令检查 |
| 怎么审 | 审候选，不碰完成归约 | 第 2 节第 7 行：审阅证据要第 9 片 |
| 版本和冻结 | 计划版本；已执行定义不能改，Run 记着 `definitionPlan` | 要另记 |
| 写权限 | 规划轮 Query，只读 | 参谋要写权限 |
| 人怎么看 | 导出 Markdown，见下 | 文件本身 |
| 需要新东西 | 放宽规划答案的上限；导出 | 产物发布、见证、审阅、授权 |

**定 A，条件是能导出 Markdown、查找和阅读都方便。** 它就是用户说的“任务图白板需要有这个能力”。B 不禁止：任务书太长时，参谋可以开一个普通文档任务，在 `instruction` 里写路径。这条路今天能走，只是平台不绑版本。

任务书内容的去处：

| 内容 | 放哪 |
|---|---|
| 要改哪些文件 | `instruction`；模块放 `scope` |
| 要看哪些记忆 | `{{notes}}` 按模块自动带上；要点名的写进 `instruction` |
| 怎么做、伪代码 | `instruction`，难点才写伪代码（R42） |
| 接口约定 | 模块注记（决定 89），`instruction` 里写名字 |
| 验收 | 义务和检查 |
| 依赖 | `executionDag` |
| 这一段的总说明、顺序、取舍理由 | `PlanStage.description`，给人和审阅者看 |
| 执行必需的共用内容 | 展开写进各任务的 `instruction` |
| 预估改动行数 | 任务的可选字段 `estimatedLines`（D3） |
| 复用什么、哪些错误不会发生 | `instruction`（清单 A、B 的规则进参谋技能） |

**除预估行数外不加结构字段。** 模板写进参谋技能：范围、先看什么、怎么做、接口、验收、不做什么、复用什么。是否写全由审阅轮看，平台不查。

**要改的地方：**

1. **规划轮放宽答案上限。** 只放宽规划轮，建议 256 KiB，普通答案不变。提交工具、观察器、持久校验三处一起改，`answer.answer` 仍存全文（`answer-tools.ts:571`、`query-observation.ts:546`、`query-record-codecs.ts:578`）。单次输出 token 同时放宽。
2. **规划轮能写注记。** `noteAdmission` 放到参谋的规划轮，这样细化时能记接口约定，N 门也才有人写。

**阶段说明不进 `{{task}}`。** 它不受执行定义冻结保护（第 2 节第 18 行），进了之后同一任务的后续 Run 可能拿到不同的内容，冻结就不成立了。执行必需的内容都写进 `instruction`。

**人怎么看、怎么找（用户的条件，MVP 必做）：**

- 采用后，Host 把这一段任务书渲染成一份 Markdown，写进项目的任务书目录。目录在工作区外，不进 Git，不动工作区版本，所以不影响检查和版本核对。
- 候选转卡时也导出一份，人批准前能读。
- 文件名含目标、阶段和计划版本，编辑器打开、全文搜索都行。路径写在“请知悉”和卡上。
- 源头是计划版本，文件是导出物，丢了可以重建。导出失败不挡采用，只提示。
- E3 的任务详情显示同样的内容。
- Agent 用现有的 `find`，任务说明已经算在内（`graph-context-reader.ts:1869`）。

### 6.1 目标循环统一处理候选

把 v3 5.6 从 `intervention.ts` 移到 Workflow 的目标级决定里。一轮规划结束时候选已写入，后面的事由目标循环做。这同时补上第 2 节第 2 行，也符合 `DESIGN.md:517`。

**候选**就是还没采用的计划修改。参谋细化一段、改一次计划，都产生一份候选。

目标循环每轮先看这个目标最新的 agent 候选。人的请求槽里的候选（6C L7）不在此列，仍由人采用。两者用 `sourceMessageRef` 和 Query 来源区分（`plan-service.ts:1136`）；不能只看 `requestRef`，干预候选也填它。

| 候选的情况 | 动作 |
|---|---|
| 没审过，有审阅线 | 发 `planreview:`，带机械诊断 |
| 没审过，没有审阅线 | 转候选卡，带诊断 |
| 审阅 `fix`，返修没到上限 | 发 `planfix:`，带意见 |
| 审阅 `fix`，到上限 | 转候选卡，带意见 |
| 审阅 `pass`，诊断无问题，`refine_future` 判定 `automatic` | 平台身份采用，交回决定循环。动到已细化的任务时，“请知悉”写明改了什么、影响哪些任务（D14） |
| 审阅 `pass`，其余情况 | 转候选卡，带审阅结论和诊断 |
| 采用回 `busy` | 保留候选，等相关 Run 和等待的事实，目标循环重试 |
| 采用被拒绝（越界、过期） | 转候选卡，写原因 |

- **绑定候选：** 审阅请求和 Query 号用 `planreview:<proposalId>:<proposalRevision>`，结论只对这一版候选有效。
- **返修上限 3（D13）：** 和任务返工默认值一样。数法：同一 `basedOn` 上已经出过 `fix` 的候选，读现有候选和 Query，不加字段。
- **阶段超线只提醒（D2）：** 不挡采用，写进“请知悉”和卡。参谋觉得要人定，就问人，会出卡。阶段线见第 10 节。

**叫醒：**

- 目标循环走到“等审阅”时，用读前游标登记等待，依据含 `SessionMessage` 和 `PlanProposal`，然后才发请求，顺序同 v3 5.4。
- 审阅轮结束时回复 `planreview:` 消息，这次 `SessionMessage` 提交叫醒目标（`goal-wait-wakes.ts:31` 已含这种记录）。参谋写新候选时，`PlanProposal` 提交叫醒目标。所以目标没有任何可推进工作时也走得到。
- 重启：`goal-wait-wakes.ts:173`、`:187` 的重建只扫 Work 等待和已放行的行动请求。加一步：有待处理 agent 候选、或有待答、已答未续轮规划问题的目标也登记，读现有事实，不加记录。重启中断没解除时按决定 97-9 不开轮。

### 6.2 机械诊断

纯函数，只读事实，随候选写进审阅输入和候选卡。不拒绝入图（PRODUCT §3），也不单开返修循环：有问题时不能自动采用，审阅者看得到，可以让参谋改；改不了就转候选卡给人。

只有一条：**每条必需验证要求都有注册检查能覆盖；`reviewer` 类在第 9 片前算不覆盖。** 它防的是第 2 节第 7 行：任务采用后永远完不成。复用 `compileVerificationPlan` 的覆盖算法（`verification-plan.ts:85`）。它今天接收已采用快照，要把算法抽出来，不能伪造快照。

义务映射、依赖环、模块存在（`plan-service.ts:2991`）现有校验已经查，不重复。

**不做：** 文件是否存在（`instruction` 是自由文本）、任务书写没写全、重叠模块有没有约定。这些交审阅者，N 门在派工时兜底。

### 6.3 审阅轮

- **谁审：** 审阅者职责的一条线（审阅线），只读 Query，和写候选的不是同一条线。审阅者是单独的第五种职责（`PRODUCT.md:130`）。书记协助准备审查，不启动正式审阅（决定 49 第 22 项，`PRODUCT.md:128`）；这里由 Workflow 启动。
- **读什么：** 目标、阶段 gate 和义务、这一段的差异和任务书、诊断结果；可以读代码、注记和图。
- **审什么：** 用户的 R40、R46：任务边界是否合适、任务书够不够让执行者不猜、依赖和并行安排、前提对不对、有没有漏掉义务、有没有该复用的。
- **出什么：** 用答案工具提交 `{ verdict: 'pass' | 'fix', findings: [...] }`，形状校验照 `answer-tools.ts` 现有写法。
- 这是计划链上的一步，**不是**检查证据，不碰完成归约，所以不依赖第 9 片。第 9 片审的是执行结果。
- **每层只审一次（用户 11-01）。** 审这一版新写的内容；上一层已采用的东西（目标、骨架、已采用的段）是依据，不是被审对象，不重审。下层或施工发现上层有缺陷，走第 7 节，只审改动的部分。

**审阅线怎么来（D9）：** 在 7D2 里和参谋线一起做。现有入口都不收审阅者：`member_creation` 只支持执行者（`7c1-start-rulings-v2.md:778`），`role-lines/open` 只收秘书、参谋、书记（`slice-7-SPEC.md:491`）。所以 7D2 的 `role_line_add` 要加审阅者，人用的 `role-lines/open` 不用改。底下都走 6A 的共用建线入口（`slice-7-SPEC.md:42`），上限已算进执行者组（`:514`）。出不出卡按 L36：自动档 `automatic_notice`，「每步确认」出卡。内建设置发布路径要加参谋、审阅者的 binding、Query profile 和只读工具（`host.ts:1829`、`runtime-configuration.ts:481`）。7D2 之前可以用外部配置或人手动建线。没有审阅线就转候选卡给人，不跳过（沉默不扩权）。

**和 PRODUCT §3 的关系（D8）：** `PRODUCT.md:319` 写“不能为了确定计划或开始并行，先做一次近似实际任务的全量语义分析、读写范围证明或模型审批”；`PRODUCT.md:130` 写审阅者只在采用的计划要求时启动。审阅 `pass` 才能自动采用，是采用前的模型审批，**改变了这两处的边界**，定了要改 PRODUCT。不同之处：候选照常入图；人采用不受它挡；审的是一段计划，不是近似实际任务的全量分析。用户的 R40、R46 和 D8 的答复是这个方向的依据。

**首个方案（D15）：** 工作区已有代码就审一次，空工程不审。第一版完整方案出来后审，意见交给写方案的秘书，同时写在卡上给人看。不挡人采用（决定 15），所以不碰 `PRODUCT.md:319`。之后改稿由人带到收敛，不每轮审，人要求时再审。落在 6C L7。

### 6.4 让人知道

自动采用后出一条“请知悉”：改了什么、影响哪些任务、审阅结论。用现成的差异计算，走投影，不新增记录。这条落实决定 15“说明修改”，也是 103-1 的一般规则。

### 6.5 对象和状态

候选就是现有的 `PlanProposal`（`STATE-MACHINES-SPEC` §3）。**不加持久状态，不加记录。** 第 6.1 节的表是一个纯函数，放 `state/`，输入是读齐的事实，输出下一步，按“读事实 → 状态机判断 → 共用执行器写”（`HANDOFF.md:1597`），用表格测试。**动作只写在第 6.1 节，这个函数是它唯一的实现。** 下面的派生状态只给结果归类，不另定规则。

| 派生状态 | 归哪些情况 |
|---|---|
| 待审 | 候选待决（`findPendingProposal`），这一版没有审阅 Query，有审阅线 |
| 审中 | 这一版有审阅 Query，没结束 |
| 待改 | 审阅 `fix`，没到上限 |
| 待采用 | 第 6.1 节“审阅 `pass`，诊断无问题，判定 `automatic`”这一行；`busy` 时留在这里 |
| 待人 | 第 6.1 节转候选卡的各行 |

目标显示沿用 `CHANGE_PENDING`（GOAL-26）：候选待决期间不算当前工作失效。

## 7. 执行中的偏差

### 7.1 入口

| 偏差 | 谁发现 | 今天 | 本设计 |
|---|---|---|---|
| 前提错、任务书和代码对不上、范围不够 | 执行者 | 能问，没有规则 | 技能写明：不猜，发 `action_request` 给参谋，让出 |
| 两个任务矛盾 | 执行者、审阅者 | 同上 | 同上（E09） |
| 超预算：任务过 2 倍线 | 平台 | v3：出“请知悉” | 系统轮 `deviation:`，同时告诉人 |
| 改动行数超过任务书预估的 2 倍 | 平台 | 没有 | 同上（D3） |
| 超预算：Run `budget_exhausted` | 平台 | 只停 | 系统轮 `deviation:` |
| 到返工上限、`no_new_basis` | 平台 | 只停 | 系统轮 `deviation:` |

- 提醒线仍是 `notify`，不开模型轮。
- 行数线用 2 倍，是因为实测超预估 25%–35% 是常态（R 561/450、P 925/735、L 286/210、DRV 957/775）。初值，可配置。
- 第二次返工仍是 7C-2 的通知，不改（决定 42）。
- 请求号：`deviation:<goalId>:<taskId>:<kind>:<planRevision>`，同一版只发一次。
- 执行者的上报走现有发信，收件人按 L35（7D2 前用 `resolveDutyRecipient`）。

### 7.2 只挡那一支

- 执行者让出后，等的只是它自己。
- 已有停因的（返工上限、`no_new_basis`、`budget_exhausted`），任务已经停了。
- 软超线（增长量或行数过 2 倍）不停任务：告诉人，参谋判断，照常推进。
- 依赖它的任务按现有规则被挡（`MVP-BEHAVIOR.md` B03 第三段），别的继续。

不新造停止机制。

**告诉人时带什么（D6）：** 这个任务用了多少、改了哪些文件多少行、任务书在哪。人看得到改动（现有的执行历史和文件差异）。怎么暂停看当时的状态：Run 在跑或让出等待时，用 `controls/submit` 暂停、继续（`PRODUCT.md` §5.6）；Run 已结束、下一个还没开时，把任务设为延后（走计划草稿，`E3-UI-ITEMS.md:227`），或暂停整个目标（`goals/control`）。任务是某项必需义务的唯一承担者时不能设延后（`plan-validation.ts:514`），只有暂停整个目标或改计划两条路，不为这个角落加新机制。然后和秘书讨论，需求确认后再继续或改计划。不做硬刹车，平台和参谋都不替人决定。

### 7.3 参谋的答复

一个规划轮。同一种答复，按消息来源后果不同：

| 答复 | 执行者发来的（在等） | 系统，软超线（任务照常推进） | 系统，已有停因 |
|---|---|---|---|
| **改计划** | 写候选，进第 6 节。**先不回复，执行者继续等** | 写候选，进第 6 节 | 同左 |
| **回答** | 回复原消息，执行者在新 Run 继续 | 这一轮结束，判断写进给人的“请知悉” | 不适用：回复解除不了返工上限、`no_new_basis` 和预算停因 |
| **问人** | 出卡，这一支继续等 | 出卡，任务不停 | 出卡。人用现有的重排、重查、加预算入口 |

执行者在等时，候选的结果：

| 结果 | 动作 |
|---|---|
| 采用，原任务不动 | 采用后回复，执行者在新 Run 继续 |
| 采用，原任务被替代 | 先取消这个让出的 Run（`controls/submit`），再采用，然后回复原消息收尾。自动档由平台做，卡上由人做 |
| 转候选卡 | 继续等，人处理 |

- `plan-machine.ts:677` 看的是 Run 的控制状态，`controls/submit` 的取消写的就是它（`control-intent-machine.ts:187`）。`waits/dispose` 不能用（第 2 节第 17 行）。
- **这里新放开一处（D14）：** 平台身份可以取消，只限“候选明确替代这个任务，且等待的消息就是候选的来源消息”。不算人的停止。
- **人停在先：** 这个 Run 已被人暂停或取消时不走这条放开，候选转卡。`control-intent-machine.ts:200` 允许暂停后再取消，平台取消会盖掉人的停止指针（`task-failure.ts:116`），所以要先判。取消仍 pin 同一 Run 版本。
- **返修后的来源：** 候选的来源消息是 `planfix:` 时，沿返修链往回读：`planfix:<proposalId>:<revision>` 指上一版候选，一直到第一版，用第一版的来源和等待的消息精确比较。不改 Query 的来源（一条消息只有一个 Query），不加字段，不给所有 `planfix:` 候选取消权。
- **续轮后的来源：** 候选的来源消息是 `planresume:` 时（包括返修链读到第一版后），读那条消息的 Query，用 `repliesToMessageRef` 和等待的消息精确比较。平台取消的放开（D14）和采用后回复都按这个结果。回复用续轮保存好的答案，不用 M 自己那一轮的。
- 消息等候选期间不再提供给这条线，否则挡住线上后面的消息。回复用保存好的答案。
- 影响清单写进 `reason.affectedTaskIds` 和一句话说明，干预路径补上这个字段（第 2 节第 16 行）。
- 平台不算语义影响（`slice-6-SPEC.md:428` 已写明抓不到），平台给差异，模型给判断。
- 已执行的任务不改定义，用替代任务。

### 7.4 范围内和范围外

| 改动 | 走哪 |
|---|---|
| 只细化占位、新增任务 | 第 6 节，自动档可自动采用 |
| 动到已细化的任务，包括已执行的要换做法 | 第 6 节，自动档可自动采用，人知悉、可干预；已执行的用替代任务 |
| 动到在跑的任务 | 采用前先停，决定 102-4，归 6C L13。之前是 `busy`，等它结束再采用，不抢 |
| 改目标、验收、范围 | 6C L13，人答复，带完整影响清单 |
| 动到正式架构 | 8C 结构改动，两档都出卡，D14 不改变这一条 |
| 要加预算 | 人，`tasks/requeue`（决定 62） |

**E09 的限定场景由这条路走完：** 上报 → 参谋解释 → 需要时人决定 → 正式版本 → 替代任务带着新定义进入受影响上下文。完整验收还要 6C（改目标、验收、在跑切换）和第 8 片（正式架构变更）。

### 11.1 架构书和它的可视化（用户 11-01）

用户原话：“不是实际的取代架构图，只是把架构书变成可视化的和目前的可架构图的可视化类似的东西。”

| | 描述什么 | 在哪 |
|---|---|---|
| 任务图 | 接下来要做什么 | 计划 |
| 架构图 | 现在或这个目标做完后由什么组成 | 正式架构 |
| 架构书 | 远期的整体结构是什么样 | 今天只有文档 |

正式架构沿用决定 61-5：描述现在或这个目标做完后的结构；远期的整体目标架构先写成文档，不急着改正式架构。平台的提醒、改动范围检查、任务所属模块检查都按正式架构的内容判断。

**现在就做的约定（不改代码）：**

- 架构书的模块部分，用和架构图同样的结构写：系统 → 模块 → 子模块，带职责、接口、依赖。这条进参谋和书记的技能。
- 有复杂生命周期的对象才写状态机，挂在对应模块下面，写清状态、事件、不允许的变化。不是每个模块都要有。

**MVP 之后做：**

- 用架构图同一套画法显示架构书，是一个单独的只读视图，界面上切换“当下”和“目标”。不取代架构图，平台的检查不读它。
- 复用现有比较，显示“目标对当下”还差多少，思路同决定 61-5 的“正式对观测”。
- 状态图挂在模块节点下显示。
- 任务连到目标架构的节点。今天任务的所属模块必须已在正式架构里，否则采用时回 `unknown_module`（`slice-8-SPEC.md:169`、`plan-service.ts:3050`），所以新模块的任务先挂在上级模块下，说明写在文字里。这不挡 MVP。

视图的数据从哪来、存哪，到时候再定。
