# 结构草案：编排、记忆、生命周期（设计第一轮）

- 基线：HEAD `42604b3`。只写文档，没有改代码、没有跑测试、没有调用模型。
- 本稿合并了两份独立草稿：一份从现有结构出发（“复用优先”），一份从你看到和做的事出发（“行为优先”）。每处取舍的理由在 `drafts/COMPARE.md`。之后又按一轮对抗审查改过。
- 取舍规则：选更小的结构；除非它让某个 MVP 项没地方放，或让你看到的行为变差。

**标记：**
- 【已定·决定 N】= HANDOFF 顶部的决定 N。
- 【已定·文档】= 你早先认可的设计文档，后面写出处。ORCH = `docs/refactor/ORCHESTRATION-STATE-MACHINES.md`（协作主图）；UIW = `docs/UI-WORKBENCH.md` §0；MVP = `docs/MVP-BEHAVIOR.md`；PRODUCT = `docs/PRODUCT.md`。
- 【之前的建议】= lead 或本轮调查提过，没有定。
- 【本草案提议】= 本稿新提，没有定。
- 【见 Qn】= 要你定，问题在 QUESTIONS.md。

**几个词：**
- **工作线**：一个 Session 加上接续它的 Session【已定·决定 25】。
- **只读副本**：「问一问」时派生的副本，只回答不动手。
- **Workflow**：按规则推进的部分，没有自己的循环。**Host**：常驻进程，跑循环和接口。
- **WorkGraph**：记录事实的核心；状态变化都经过 `work-graph/state/` 里的状态机【已定·决定 20】。
- **子模块**：WorkGraph 里的一个目录，任务 D 给它们定上下层。
- **提交**：一次写入，要么全部生效，要么全部不生效。
- **索引**：让读取不必扫全部记录的查找表。
- **纯函数**：只按输入算结果、不读也不写任何存储的代码。状态机都是纯函数。
- **守卫**：状态机在一次改动前检查的条件，不满足就拒绝。
- **编解码**：记录存进数据库、再读出来时的格式转换和校验。
- **锚点**：一条注记挂在哪个节点上，例如一个模块、一个文件、一个任务。
- **游标**：记住“你上次看到哪儿”的一个位置标记。
- **让出执行**：agent 停下这次执行，等回复；Session 空出来，回复到了再接着做。
- **退役**：Session 被中断后不能再执行，原历史仍可读【已定·决定 8】。

## 0. 一页总览

1. **不加模块，也不加模块之间的依赖。** 五个模块、八条边不变【本草案提议】。
2. **不加调度引擎，不加常驻循环。**
   - 判断由三方做：你；agent，在它自己的执行里；Workflow 的默认规则。
   - 判断写成一条记录，经 WorkGraph 写入，由状态机把关。
   - Host 看到这次提交，再叫 Workflow 走一步。
   - 依据：“沿用当前宿主、持久待执行记录与按事件触发的驱动”【已定·文档 ORCH §1 第 8 条，第 257 行】。
3. **agent 的工具不直接调用 Workflow。** 工具只写事实，或调用 AgentRuntime 自己的动作；Workflow 由 Host 叫来处理后续【之前的建议】。这样不会多出一条反向依赖。
4. **新增的东西：**

   | 种类 | 数量 | 内容 |
   | --- | ---: | --- |
   | 新记录种类 | 2 | 注记；“当前理解”指针 |
   | 已有记录上的新字段 | 15 | Session 1 个；目标 3 个；消息 7 个（其中 1 个看 Q2）；答复 1 个；已用掉的等待 1 个；执行 2 个。逐条见附录 A |
   | 新索引 | 8 | 见附录 A |
   | 新状态机文件 | 1 | 注记的状态机；其余是已有状态机里加行 |
   | WorkGraph 新子模块 | 2 | 注记 `notes`、读模型 `views` |
   | agent 工具 | 新 7 / 退役 4 | 另有 3 个已有工具开始授予，1 个不授予。见 §4.3 |
   | 新接口 | 读 13 / 写 9 | 另改已有的 5 个（Q16 选甲再加 1 个）。见 §5 |
   | 新循环、新模块边 | 0 | — |

5. **刻意不加的**（已有的记录已经能装下）【本草案提议】：
   - 不加“决定记录”：请你决定的事是一条消息；你的决定落到具体对象上，写明依据。理由：“先映射已有 Task/消息/来源关系，不据此立即新增独立状态库”【已定·文档 ORCH 第 99 行】。
   - 不加“等待记录”：等待就是那条消息，加上让出执行的那次执行。
   - 不在 Session 上另存“正在等”“最近一次工作执行”：都从新加的“按 Session 找执行”的索引读出来（§3.2）。这样同一个事实只存一份。
   - 不加“交接包”：交接材料 = 已有事实 + 一条“当前理解”。
   - 不加成员目录、工作线记录：“成员”是推导出来的【已定·决定 25】。
   - 不加“派工记录”：派工是一条带任务的“请动手”消息。

### 1.4 决定怎么走一圈

【本草案提议】，对应 MVP 场景 E09“工具/消息 → 参谋解释 → 需要时人的具体决定 → 正式版本 → 受影响上下文”【已定·文档 MVP 第 210 行】。

1. **提问。** agent 发一条“请你决定”给它所在目标的对话线，带 2–4 个选项和所涉对象。它可以让出执行，等答复。
2. **显示。** 「需要你决定」读五个来源，只读未完成的，分页：
   - 未答的“请你决定”（“工作区 + 状态”的消息索引；消息消费也用它）；
   - 目标上已有的“需要你决定”原因，例如返工到上限；
   - 等你采用的候选计划；
   - 等你审的注记：结构性修补、矛盾；
   - 规划器提出的初始问题。
3. **解释。** 卡片上的“问秘书”，就是带着这张卡的对象，在秘书那条线上问一次【已定·文档 UIW 新增 4】。
4. **决定。** 你在界面上答。“拒绝”“延期”也是选项。
5. **送达。** 提问的 agent 如果在等，就按已有的“等回复”路径，在原任务、原 Session 里接着做。
6. **落实。** 提问者或你去改对应的东西，写明依据这条消息。决定过期了（对象已经变了），改动会因版本对不上被拒，不会悄悄推进【已定·文档 MVP 第 171 行】。
7. **收口。** “已落实”记在这条消息上：改了哪个对象、改到哪一版【已定·文档 ORCH 第 96 行“消息已保存、已交付、实际答复、相关行动已落实分别记录”；第 99 行要能追溯“决定和落实情况”】。
   - 谁记：做改动的一方。agent 用已有的“确认消息”工具；你在界面上改的，由那个接口顺带记【本草案提议】。
   - 改动和记落实是两次提交，因为改动在任务那边、消息在通信那边，任务不能写通信的记录。第二次没写上时，卡片显示“已答复，落实未记”，可以补记【本草案提议】。
   - 拒绝、延期本身就是答复，不需要落实。
   - 以后对象又被改了，这条记录仍说明当时做了什么。

**请知悉**：你上次看过之后发生的、选定类别的事实。用一个“已看到”游标读出；游标是工作区设置，不是记录【本草案提议】。

### 1.6 精确输入：从哪来，什么时候查

要查【已定·决定 11：“消费时检查精确输入”仍是未完成的 MVP 项】。行为【已定·文档 MVP 第 113 行：“明确采用的具体产物消费条件在真正需要该输入时检查；生产者 Task 尚未整体完成，但所需产物已合法可用时，不机械等待整个 Task”】。下面的做法【本草案提议】。

- **为什么今天走不通。** 今天要求规划时就写明“下游要哪个产物的哪一版”。规划时这一版还不存在，所以这类输入本来就在准备执行时失败【之前的调查：10-05 设计核对 CROSS-CHECK C-14】。决定 6 把这个字段从规划提示里去掉【已定·决定 6】。
- **声明。** 依赖边上已经写着“要什么”：产出约定、产物、决定、环境版本或检查结果，各带一个标签 [src/contracts/plan.ts:171-180; src/core/agent-runtime/query-preparation.ts:56]。保留它，规划时只写这个。
- **定版本。** 下游真要用时，平台把“要什么”对到上游已有的事实上：
  - 检查结果 → 上游最近一次通过的检查；
  - 产物、产出约定 → 上游执行留下的产物；
  - 环境版本 → 工作区版本。
  - 对上了，就把精确版本记进这次执行的入口记录。这个字段已有 [src/contracts/core/prepared-execution.ts:44]，但今天它要求计划里事先写好，要改成“依据计划里的依赖边”。
  - 对不上，或有好几个候选，就把上游的状态和产出列给 agent，由它判断。
- **什么时候查。** 执行准备时查一次；agent 用“看”读上游产出时再查。不在领取时查【已定·决定 11】。
- **没好怎么办。** 不拒绝执行。装配器在提醒段写“输入 X 还没好，上游任务 A 现在是……”。agent 决定先做不依赖它的部分、让出执行等 A 的结果，还是上报。
- **读上游产物不靠材料授权。** `tasks` 先按计划核对“这确实是这个任务要的输入”，再用受信任的读取打开产物。只用 `tasks → materials` 这个已经允许的方向；`materials` 不读计划。
- **对简化的影响（lead 要在简化前定）。** 今天按精确输入读产物的代码以“当前”方式读，只有授权能满足 [src/core/work-graph/tasks/plan-service.ts:1704-1763]，正在“只有授权才能满足的读取分支”这张删除清单上（STATUS“剩余”的简化一项）。两种处理：删掉，第 3 片按上面重做；或者留下，改接新的读取。相关的还有入口核对 [tasks/execution-entry-service.ts:640-664] 和准备时的读取循环 [agent-runtime/execution-preparation.ts:413-433]。
- **放在哪一片：** 第 3 片。

### 1.7 独立审阅者怎么读材料

只在采用的计划要求独立审阅时才起审阅者【已定·文档 MVP B06“没有独立审阅要求时不强加 Reviewer”】。材料授权会在简化阶段删掉【已定·决定 6】，STATUS“缺口”写着“独立审阅者以后要另想办法读材料”。下面的做法【本草案提议】。

- 审阅者读三样，都不用材料授权：
  1. **代码**：工作区里的当前文件，用普通的只读文件工具。
  2. **被审工作的事实**：用“看”读任务、执行、改过的文件、检查结果。
  3. **被审 Session 的原历史片段**：和 Q6 的“下钻到原历史”用同一个只读读取。平台以 Host 身份、按项目和工作区读，今天已经允许，只作“历史说明” [src/core/work-graph/materials/applicability.ts:40-86]。

- **对简化的影响。** 删材料授权时，要留下两条路：Host 读取 [applicability.ts:40-86]，和“执行读自己的材料” [applicability.ts:93-98]。只删靠授权的分支 [applicability.ts:100-128]。
- **放在哪一片：** 第 9 片。

## 2. 记忆

### 2.1 已定的

- 进 MVP：节点注记、目标和阶段上的“当前理解”、大小上限、按代码版本失效，随编排后端一起做【已定·决定 23】。
- 事实用指针，指向固定版本；理解写成文字；任务图不另建记忆【已定·决定 23 设计要点，标“未定稿”，按方向用】。
- WorkGraph 是唯一写入通道；记忆不能改执行状态；书记做审查【已定·决定 20】。
- agent 用“看 / 找 / 记”；冲突时只问“取代还是并存”【已定·决定 22】。语义修补随工作生效【已定·决定 21】。
- 更新时机：任务结束、采用新方案、返工、Session 归档或重组【已定·文档 MVP B09】。
- 你能看、能改、能移除；你说的和 agent 推测的分开；记忆不能代替授权和完成状态【已定·文档 PRODUCT §6.4】。

### 2.2 不另存的（“过去的节点就是记忆”）

注记只指向它们，不复制【本草案提议】。

| 事实 | 现在放在哪 |
| --- | --- |
| 失败、返工、处置变化及原因 | 任务行 |
| 计划为什么改 | 候选计划上的改动原因 |
| 模块职责、依赖的理由 | 架构目录的各版本 |
| 上一次执行做了什么 | 接续说明（单个任务、短期） |
| 问过什么、答了什么 | 查询回答；消息 |
| 原始对话 | Session 原历史，按窗口读 |

### 2.3 新记录：注记

【本草案提议】。一种记录装三类内容：注记、当前理解、语义修补。它们的锚点、来源、版本、上限、审查、失效规则都一样，一个状态机就够。

- **锚点**：一个主锚点，另外最多 4 个。可以是模块、接口、文件、目标、阶段、任务或整个项目。
- **种类**：注记（约定、坑、取舍、待解问题、偏好、决定）；当前理解；语义修补。
- **话题**：一个短关键词，用来判断“同一锚点、同一话题”。
- **文字**：结论约 200 字；正文约 1 KB，当前理解约 2 KB。
- **事实**：最多 16 个指针，指向固定版本：文件和摘要、提交、计划版本、目录版本、检查结果、原历史区段、消息。
- **依据**：写的时候的计划版本、目录版本，以及最多 32 个文件的摘要。
- **来源**：哪个 agent（哪次执行、哪个 Session），还是你，还是平台。
- **存下的状态**：暂存、收下、待审、拒绝、已取代、已撤下。
- **读的时候算出来、不存的状态**：
  - 需复查：依据的文件或计划变了（§2.7）；
  - 来源不可用：指向的原记录读不到；
  - 作废：暂存的修补，所属执行的任务已被取消或替代。这样任务那边取消任务时，不用去写注记（任务不能依赖注记，见 D-PLACEMENT §4）；
  - 该更新了：见 §2.5。
- **可见范围**：所属目标【见 Q7】。
- **当前理解**：每个锚点有一个“当前”指针，指向最新一版。用指针，是为了两个 agent 同时写时不会都成为“当前”（`drafts/COMPARE.md` D9）。
- **索引**：按锚点；按审查状态（给书记和队列）；按暂存它的那次执行（检查通过时一起生效）。

为什么不写进计划版本：那样每改一次理解就要出一个计划版本，还把“打算做什么”和“学到了什么”混在一起【之前的建议】。
为什么不放进 `configuration/`：会重新长出拆分要消掉的依赖环【之前的建议】。

### 2.4 挂在哪

判断办法：“这个任务明天取消，这条还对吗？”还对，就挂在架构节点上【之前的建议】。

| 锚点 | 放什么 |
| --- | --- |
| 模块、接口、文件 | 约定、坑、依赖为什么存在 |
| 目标 | 当前理解：跨计划版本的取舍、试过什么、定了什么、还没定什么 |
| 阶段 | 当前理解；也当作已完成子树的折叠摘要（UIW 被替换的条目第 2 行“给折叠的子树写摘要”） |
| 任务 | 只对这个任务有用的坑 |
| 项目 | 你的偏好、工具链、长期有效的决定 |
| 工作线 | 不挂【见 Q9】 |

### 2.5 谁写、谁读、何时

**“该更新了”只有一种做法：读的时候算出来，不存【本草案提议】。** 规则：理解写下之后，它所在的目标或阶段又有任务结束、返工、采用新方案，或有 Session 归档。比较的是理解写下的时间，和这个目标最近一次这类事件的时间；每个目标一次按索引的读。

| 时机 | 谁看到“该更新了” | 谁写 | 标记 |
| --- | --- | --- | --- |
| 任务结束、返工 | 装配器把它放进提醒段 | 在那里工作的 agent，顺手写，不多调模型 | 【见 Q8】 |
| 采用新方案 | 旧理解同时显示“需复查”；下一个在这个目标里工作的 agent 收到提醒 | 同上 | 【本草案提议】 |
| 换手 | 换手前必须写 | 交出的 agent，在它这次执行里写 | 【本草案提议】 |
| 你手动归档，没有 agent 在场 | 进书记的待办计数 | 书记补写 | 【见 Q8】 |
| 积压超过阈值 | 心跳上加两个计数：待审条数、该更新的理解条数 | 书记收到通知 | 【本草案提议】 |

Workflow 不写文字，也不写“该更新了”的标记【本草案提议】。

读的一方：装配器只放索引行（约 4 KB，可配置）；“看”能下钻到正文；界面的节点详情；书记。

### 2.6 状态规则

| 规则 | 内容 |
| --- | --- |
| 写入 | 锚点不存在、超长、没来源 → 拒绝。同一锚点同一话题已有、又没说“取代还是并存” → 拒绝，原因写“已有 n 条，请说明取代还是并存”，写的人说明后再交【已定·决定 22】。结构性修补 → 待审，由你审。锚点满了 → 待审，“请取代或合并”。其余 → 收下 |
| 取代 | 新的一条点名旧的那条，同一次提交里旧的变“已取代” |
| 撤下 | 写的人、书记或你都可以 |
| 审 | 待审的由书记审；结构性修补和矛盾由你审 |
| 修补 | 暂存在那次执行上；那一轮检查通过时，和架构修订一起生效；所属任务被取消或替代时读作“作废”（不存） |
| 当前理解 | 每个锚点只有一个“当前” |
| 上限 | 每个锚点约 5 条收下的 + 1 条当前理解；每个目标有总额度。超了不悄悄删，交给书记合并 |

记忆从不改任务、执行、目标的状态，也不授予任何工具或路径【已定·决定 20；已定·文档 PRODUCT §6.4】。数字都是讨论稿里的数字，没有实测，做成可配置【之前的建议】。

### 2.7 按代码版本失效

【之前的建议】，边界数字【本草案提议】。
- 读的时候比对：每条注记依据的文件，按路径读当前摘要，对不上就“需复查”，并列出哪些文件变了。
- 每条最多查 32 个文件，每次读最多 256 个；超过就写“未核对 n 条”，不当作仍然有效。
- 锚定的任务在当前计划里定义变了或没了 → 需复查。锚定的模块在目录里变了 → 需复查。
- 装配器记下这次给 agent 看了哪些注记、哪一版。以后能回答“这次执行看到了什么”。

### 2.8 和原历史、接续说明的关系

- 注记指向原历史片段，不复制。原历史默认折叠，可以按需看【已定·文档 AGENTS.md 第 4 条】。
- 了解前人做过什么的默认顺序【见 Q6】。
- 接续说明仍是单个任务的短期事实，不是记忆，不合并进注记【之前的建议】。

### 3.1 谁决定、谁执行

“什么时候、为什么”由编排决定；“动作和事实”由生命周期和 Runtime 负责【已定·决定 34（AG6）】。

| 选择 | 谁决定 | 谁执行、记在哪 | 新东西 |

| 复用哪个 Session | Workflow 排序；agent 可改 | 领取 | 排序和排除 |

| 等多久、到期怎么办 | 等待的 agent | 消息上的时限和到期事实 | 【见 Q20】 |

| 一开始有哪些长期线 | 编排规则 | 第一次需要时建 | 【见 Q22】 |

### 3.2 Session 上加一个事实，另外两个读出来

【本草案提议】

| 事实 | 存还是读 | 解决什么 |
| --- | --- | --- |
| 来历 | 存。建的时候写一次，不再改。取值：新建；对话线（哪个目标）；接续（从哪个 Session、什么原因）；换手接任（从哪个 Session）；只读副本（从哪个 Session、哪条消息） | 工作线；只读副本不再被拿去干活；从旧 Session 找到接续它的 |
| 等回复 | 读。这个 Session 最近一次工作执行已让出、它等的消息还没用掉 | 等回复的不被派别的活；状态词“等回复”；归档前检查；重启后续上 |
| 最近一次工作执行 | 读。按 Session 找执行的索引里最新的一次。查询是另一种记录，不会盖掉它 | 状态词“已暂停”等 |

- 新索引：按来历找接续它的 Session；按 Session 找它的执行；按 Session 找它的查询。
- **归档前的“不在等”检查不需要存副本。** 归档本来就要带 Session 的版本号，版本对不上就拒绝 [src/core/work-graph/sessions/session-lifecycle.ts:158-218]。让出执行会释放占用，并把 Session 的版本号加一 [src/core/work-graph/state/session-availability.ts:313-330]。所以 Workflow 读完“不在等”之后，如果这个 Session 又让出执行开始等，归档会因版本对不上被拒。
- 代价：派工排序时，每个候选多一次按索引的读；候选一页最多 100 个。实测太慢时，再考虑存一份同步副本；那时作为提议单独提出，写明理由。

### 3.3 中断后接续：修补

【已定·决定 7、8】不变。修补【本草案提议】：
1. 建接续 Session 时，记下来历“接续”，把负责关系转过去，而不是再开一个。
2. 然后 Workflow 归档退役的 Session。原历史仍可读。它从此不再算活跃，启动时也不用再探测它，不占启动核对的扫描名额。
3. 退役的 Session 正在等回复的话：按决定 7，回复不自动转到接续 Session。线上显示“n 条未送达”，转交【见 Q20】。
4. 在等的 Session 不再直接跑查询，要问它就走只读副本。它就不会因为一次被中断的查询而退役，第 3 条的情况会少很多。

### 3.4 换手（也用来拆分、合并）

【本草案提议】不加新的操作记录。每一步都可以重做。

**换手动作在 AgentRuntime 里，只有一份。** agent 的“换手”工具、你在界面上的换手、Workflow 的规则，都调用这同一个动作。它做第 2、3 步。之后的事（第 4、5 步）由 Workflow 在看到这次提交后做。这符合 AG6：何时、为何由编排定，动作由生命周期和 Runtime 做【已定·决定 34】。

1. 交出的 agent 写好目标或阶段的“当前理解”。其余交接内容已经在各处：目标和义务（计划）、决定（注记、消息）、改过的文件、原历史引用【已定·文档 MVP 第 173 行】。你发起、没有 agent 在场时，理解由书记补写（§2.5）。
2. 建接任者（来历“换手接任”），或选一个已有的 Session。
3. 在一次提交里转负责关系：关掉旧的，开新的。旧 Session 还有同一任务的执行在跑时拒绝：“切换前旧写者必须停妥”【已定·文档 ORCH 第 363 行】。
4. 旧 Session 的执行结束、不再负责任何东西、也不在等时，Workflow 归档它（全部交出），或保留（部分交出）。
5. 接任者第一次执行时，输入里有“接手自 …”，带上最新的理解和原历史引用。

**重组用同一个动作【本草案提议】，对应 ORCH S5“重组/拆分/合并职责”：**
- 全部任务交给一个新 Session = 换手；
- 一部分任务交给一个新 Session = 拆分；
- 全部任务交给一个已有的 Session = 合并。

中途崩溃：重启时从事实判断做到哪一步（接任者在不在、负责关系转了没、旧的归档没），接着做。

### 3.5 归档前处置

【本草案提议】，用户可见的选择【见 Q1】。
- Workflow 做一个组合动作：
  1. 负责的任务已完成、已取消或已被替代的，负责关系自动结束。依据：ORCH 只拦“未接手责任”（第 364 行），要求“需承接的责任已交接或明确处置”（第 231 行）；
  2. 还没完成的，按你或 agent 的选择：交给某个 Session / 放下（任务变成没人负责，等派工）/ 保留（不归档）；
  3. 正在等的，要说明怎么处理等待：取消（当作到期）或转走；
  4. 然后归档，带上第 1 步读到的 Session 版本号（§3.2）。
- 界面的归档按钮走这个组合动作，只有一条路。
- 为什么放在 Workflow：Session 子模块不能读任务状态，否则会形成依赖环。

### 3.6 等待：时限、到期、转交、重启

【本草案提议】，时限和转交方式【见 Q20】。

| 部分 | 做法 |
| --- | --- |
| 时限 | 消息上可选的“答复期限” |
| 发现到期 | 让出执行的：驱动本来就每 0.5 秒看那条消息，顺带比对期限 [src/app/collaboration-driver.ts:147]。没让出的：心跳循环在有期限时也启动。不会因为时间到了就释放占用【已定·文档 ORCH §0.6 第 214 行“不据超时、缺记录或进程失联自动释放占用”】 |
| 到期事实 | 消息上写“已到期”（只在没答复、时间已过时） |
| 到期后 | 让出了的：在原任务、原 Session 接着做，输入是“到期没答复”，由 agent 决定再问、换人还是放弃。没让出的：通知发信的线。同一个请求第二次到期 → 请知悉 |
| 到期后才来的回复 | 照常保存，下一个安全点作为普通输入送达；不重开已用掉的等待 |
| 等待的 Session 退役了 | 按决定 7，回复不自动转到接续 Session【已定·决定 7】；见下一行和 Q20 |
| 发给退役 Session 的消息 | 工作线上显示“n 条未送达”；转交 = 发一条新消息给线上当前的 Session，引用原消息 |
| 在等的 Session | 不直接跑查询，要问它走只读副本（§3.3 第 4 条） |
| 重启 | 启动核对也推动“等待已答复或已到期”的目标 |
| 归档 | 在等的不能归档（§3.5） |

### 3.7 只读副本

【本草案提议】，副本活多久【见 Q2】。下面按 Q2 的建议（甲）写。
- 来历记为“只读副本”；不再被拿去干活。
- 一问一个，答完就由 Workflow 归档。这和 ORCH 第 235 行“A′是一次隔离派生咨询……完成后……结束该次执行”一致【已定·文档】。
- 你追问时，建一个新副本，问题里带上前一问一答；用“追问自”把它们连起来，画在一起。新副本从原 Session 最新的已完成位置派生，所以能看到原 Session 后来做的事。
- 画在被问的那条线上，不单独成线【已定·决定 25】。
- 界面上的「问一问」改发“询问”意图。今天它发的是“请动手”，却得到只读回答 [src/ui/views/conversation/member-mail.ts:83-84]。（2026-10-21 补注：这里引用的 `src/ui` 各行是已删除的代码（决定 86-2）；它们说的是 2026-10-21 之前的状态。）

### 3.8 状态词

纯计算，不存【已定·文档 ORCH §0.6】。每个 Session 最多读 3 次，只读活跃的，分页【本草案提议】。

| 词 | 依据 | 标记 |
| --- | --- | --- |

### 3.9 工作线

【本草案提议】，哪些 Session 算一条线【见 Q3】。
- 一条线 = 线头的 Session，沿“来历”往回找到的前任（最多 32 个，超过写“省略 n 个”）。
- 列表：分页读活跃的 Session，去掉只读副本，去掉已有同线接续的；剩下的每个都是一条线的线头。
- 每条线带上排序和分组要的数据【已定·决定 25】：
  - 需要关注的标志：需要你决定 > 失败 > 受阻 > 待核对；
  - 职责、所属模块、负责的任务（按这些分组）。今天普通界面所有 Session 都是同一个角色 [src/app/runtime-configuration.ts:90-96]，按职责分组要等第 3 片的职责配置。
- 详情：沿来历往回走；每个 Session 的执行和查询走新索引。
- 计数：工作中、待命按状态词数。已归档的线数分开显示【已定·决定 25、30】；怎么数（存储层加一个计数方法）【本草案提议】。
- 不另存“线”的编号。这样“哪些算一条线”只是读的规则，以后改答案不用改数据。

### 3.10 职责和冷启动

- 每种职责一个角色配置：执行者、秘书、参谋、书记、审阅者。每个 = 执行者基础行为 + 一种职责行为【之前的建议】。
- 职责在建 Session 时定，不会运行中换【已定·文档 AGENTS.md 第 4 条】。
- 对话线：每个目标一条【已定·文档 UIW 新增 2“每个目标一条对话线”】。要不要再有一条项目级的线【见 Q15；原型第 14 版没有画，建议按原型不加】。
- 其他长期线什么时候建【见 Q22】。不默认起四个【已定·文档 AGENTS.md】。
