## 1. 要解决什么

用户的判断：一个目标可以大到整个产品，这个产品的 DSH 用量已经到 403 亿 token（不含 Claude 和 Codex）。这种目标不可能一次写完方案、一个预算管到底，下面必须有自动分层、分阶段的机制。

现状有三类问题：

- **预算的数量级不对：** Work Run 的上限过小，只有 Run 一层有账。
- **有存放分层的结构，没有驱动分层的东西：** 没人触发细化，普通提案没人自动采用，阶段 gate 也不按阶段调度。
- **规划链本身有断点：** 闲置线上的干预规划领取 Query 后没人继续推进。这不只影响本设计，人的干预也走这条路。

不做的事：

- 不自动拆目标（决定 49）。
- 不给目标设固定上限。
- 不用公式算预算，平台自己还没有数据。
- 不新增层级、不新增记录种类。
- 不做每天花费额度（决定 62 暂缓）。

## 3. 设计原则

1. **平台机械触发，模型决定怎么分。**
2. **用现成的链路，能不加就不加。** 规划、提案、采用都走干预规划链，先把它修通。
3. **等待只挡那一支**（决定 62）。
4. **沉默不扩权。** 超线就不自动采用，转成候选卡等人。
5. **读不到写未知，不写 0。**

## 4. 层和尺子

### 4.1 三层

| 层 | 对应我们的施工 | 预算 |
|---|---|---|
| 目标 | 整个产品 | 不设上限，只累计 |
| 阶段 | 切片 | 上下文增长量 1,500 万，约 1B token（初值） |
| 任务 | 组 | 按档位，最大 4M（初值） |

- **波不是一层。** 它是依赖图里能同时开工的一批任务，由 `executionDag` 算出来。
- **更大的工程拆成多个目标**，用决定 49 的标准。先不做阶段嵌套。
- **小目标不用分。** 一个阶段放得下，骨架就是完整计划，流程和今天一样。

### 4.2 三把尺子

| 尺子 | 回答什么 | 定义 |
|---|---|---|
| 累计 token | 花了多少 | 输入加输出，含重发和缓存 |
| 上下文增长量 | 工作量多大 | 一次 Run 里，相邻两次请求的输入涨了多少，只累加上涨的部分，再加最后一次输出 |
| 改动行数 | 产出多少 | 一次 Run 里已确认的 `edit` 调用的增删行，用 `lineDelta` 算 |

**上下文增长量的算法：** 输入序列 100、180、90、150，增长量是 80 + 0 + 60 = 140，再加最后一次输出。

- **裁剪时是近似值：** 输入下降不计，之后再涨才计。同一步里新增和裁剪互相抵消时会少计，所以这是工作量的近似读数，不是精确账。
- **Session 复用不影响：** 每个 Run 的第一次输入不计，所以 B 不会算上 A 的历史。
- **能直接相加：** 任务是它的 Run 之和，阶段是任务之和，目标是全部之和，不用按 Session 去重。每个成员的 Run 都计入，这就是用户说的“包括子 agent”。
- **有未知时：** 某次请求没报用量就跳过这一段，读数标“不全”。

**实测校准（282 次 DSH 运行）：**

| | 上下文增长量 | 各 Session 峰值之和 |
|---|---|---|
| 中位数 | 0.93M | 0.93M |
| 75% 分位 | 1.63M | 1.62M |
| 90% 分位 | 3.18M | 3.17M |
| 95% 分位 | 6.22M | 6.20M |
| 最大 | 32.8M | 32.6M |

两者的比值从 10% 分位到 90% 分位都是 1.00，累计 token 约是增长量的 64 倍。校准时算上了每个 Session 的第一次输入，平台按 Run 计时不算，读数会略小一些。这是一个项目、一个模型的数据，只作初值。

三个读数都按 Run 记，所以同一工作区并行时也分得清归属。`shell` 改的文件算不到行数，沿用现有的 `command_ran` 标“不全”。被拒绝的调用不算，不明副作用标“不全”。

### 4.3 任务档位

计划里的任务加一个可选字段 `sizeClass`。没有档位时只累计，不提醒。

| 档 | 提醒线 | 请人看的线（2 倍） | 对应实测 |
|---|---|---|---|
| `small` | 1M | 2M | 约中位数 |
| `medium` | 2.5M | 5M | 75% 到 90% 分位之间 |
| `large` | 4M | 8M | 90% 分位以上 |
| `explore` | 4M | 8M | 探索方向 |

**探索不加新字段。** 一路方向就是一个 `explore` 任务，并行探索就是几个并行任务。提醒线在这里是额度：到线先交现有结论，参谋提建议，由人决定加不加（决定 62）。

档位由参谋选，平台对账。阈值放在 Host 设置里，都是初值，可配置。

## 5. 流程

### 5.1 目标采用：骨架加第一阶段

- 规划输出改成“阶段骨架 + 第一阶段细方案”。第 2 节第 14 行的限制决定了首个计划也只能这样。
- 骨架的每个阶段有说明、一个阶段 gate 及其义务，以及至少一个 `plan_only` 占位任务。占位任务带档位，表示这一段的预估大小。
- 第一阶段的任务写全：指派、验收、依赖。
- 这些用现有计划结构都能表达，不改 `PlanStage`。
- 人采用的是这一版，所以骨架也过了人的眼（决定 15）。

### 5.2 阶段按顺序验收

阶段 scope 的 gate，在这个阶段的必需普通任务全部满足时就可以被选中，不等整个目标。

- 改在 Workflow 的目标级选择里，排在“未完成普通任务”的分支之前，用 `gateCoveredTaskIds` 判断。
- 目标 scope 的 gate 规则不变。Goal 完成仍检查全部必需任务和目标 gate。
- 后面阶段如果要等前面的验收，用已有的 `gate-result` 依赖表达。

### 5.3 先修通规划链

这一步独立于分层，人的干预也需要。

1. 消费调用领取 Query 后，由同一调用在后台继续推进到终态，再提案和采用。不能每一步都要求 Session 空闲，也不能占住 Host 的心跳循环。
2. 按 Query 和提案的终态收尾：
   - 已采用或已转成候选：消息结束，不再被选中。等人采用时只等已有候选。
   - `needs_decision`：把问题展示给人。
   - 拒绝或失败：把原因展示给人。

固定的 Query 号只能避免重建 Query，消息本身要有收尾，否则每次心跳都会重新进入，还会挡住这条线后面的请求。

### 5.4 触发细化

**条件：** Workflow 这一轮走到等待结果，没有可推进的步骤，且存在“活动的、必需的、`plan_only` 的普通任务”。

- 延期（`deferred`）的任务不算，保持不推进。
- 自动返工和重新检查本身是可推进步骤，会先走现有选择，不会被抢。
- 有任务在跑时也可能触发。这是有意的：上一阶段最后几个任务在跑时，提前细化下一阶段，和我们“每一波施工时演练下一波”是同一个做法。

**实现：** 不新增等待分支。在目标级等待结果的共同收口附加 `refinement`：`result = collected ?? gap; return attachRefinement(result)`。这样覆盖 L46、收集等待和普通缺口，等待原因和唤醒依据照旧合并。

**动作，顺序不能换：**

1. 驱动用读前游标登记等待，再让现有 Goal 等待队列 drain 一次，处理登记前已发生的提交。
2. 找这个目标的参谋：7D2 之前用 `resolveDutyRecipient`，7D2 之后换成 L35。
3. 用 `systemActionRequest` 发一条带 `goalRef` 的 `action_request`，文字写明要细化的阶段或任务。
4. 请求号固定为 `refine:<goalId>:<阶段或任务 id>:<planRevision>`。同一版计划只发一次；细化后还有占位任务时，新版本会再发。
5. 没有参谋时出 `adviser_creation` 卡，trigger 加一种 `refinement`（决定 103-1）。这时等待依据加上 `Session`，建线后能重新触发。

**消费这一侧：**

- `offerKindOf` 和来源证明 `proveInterventionSource` 都接纳 Host 系统身份的 `action_request`，其余检查保留。
- `handleIntervention` 用已有的发送身份识别它：不走 `latestWork` 回退，直接用 `message.goalRef` 进规划；采用后不走 `claimFirstReady`，交回 Goal 决策。不新增消息字段。

**重启：** Host 重启中断还没被人解除时，`handleIntervention` 已经会拒绝，消息留在队列里（决定 97-9），不用另写。

**不做超时重发。** 参谋没动静时，目标显示“等参谋细化”，人可以直接干预。

### 5.5 细化只输出这一段

第 2 节第 14 行决定了不能让模型每次重写整份计划。

- 这一轮模型只输出这一段：新任务、指派、义务、依赖，以及对占位任务的细化。答案形状不变，数组里只放这一段，所以沿用 `parseInitialPlanningResponseV2`。
- 平台用 `mergeStageRefinement` 把它合并进当前计划，得到完整草稿，再走现有的 `proposePlan`。

**合并规则：**

| 情况 | 做法 |
|---|---|
| 一个占位细化成一个任务 | 沿用原 id，改成 `request_execution` |
| 一个占位细化成多个任务 | 原任务设为 `superseded`，新增实际任务 |
| 已有 gate 和义务 | 保持原语义，不改定义 |

合法性全部由现有校验判断，合并函数只做合并。

### 5.6 采用

沿用 `intervention.ts:274`–`:281`：提案写入后，`refine_future` 判定为 `automatic` 就用平台身份采用，否则等人。

只加一个条件：**阶段的档位合计不能超过 1,500 万。** 超线时提案照常保存，进图不受影响（PRODUCT §3），只是不自动采用，转成候选卡，卡上写明超线的数字。参谋可以再分，也可以写明为什么分不开，由人决定。

**非法提案：** 删除或改变原义务、改有执行痕迹的定义，这类提案可能先存成带诊断的候选，但采用时会被拒绝，人也不能绕过（`plan-service.ts:3024`、`plan-validation.ts:501`）。候选卡要把拒绝原因写清楚。

普通 Work Run 里的 `propose_future_plan` 也接上同一个采用判断，抽成共用函数，补上第 2 节第 5 行的缺口。

### 5.7 执行中的读数和刹车

活动记录在 Run 结束时写入，所以读数判断都在 Run 边界做，不中断正在跑的 Run。

| 时机 | 判断 | 动作 |
|---|---|---|
| Run 进行中 | 累计 token 到 Run 上限 | 现有路径：任务记 `budget_exhausted` 停因，Goal 按现有规则显示 |
| Run 结束 | 任务增长量过提醒线 | 给参谋一条 `notify`，同一任务同一条线只发一次 |
| Run 结束 | 任务过 2 倍线 | 给人一条“请知悉”，同时告诉参谋 |
| 读不到用量 | 读数未知 | 不提醒，显示“未知” |

**不做任务层硬刹车。** 单个 Run 有上限，但任务总量没有：让出等待后的接续 Run 不计返工次数，多次接续能超过任何固定倍数。硬刹车要新造一整条出卡、答复、解除、重启重读的闭环。第一版先让人看得见，要不要做见 D6。

加额度归人（决定 62）：沿用 `tasks/requeue` 带更大预算的现有路径。

### 5.8 阶段结束

阶段的必需任务和 gate 都满足时，出一条“请知悉”，不挡工作：

- 这一段用了多少 token、增长量和行数，有未知或不全时写明；
- 完成了哪些任务，返工几次；
- 下一阶段的预估档位。

### 5.9 目标层

目标只累计，在目标栏显示。不设默认上限。人手动设目标上限留到 MVP 之后。
