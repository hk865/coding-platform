# Agent 通用行为与按需分工

2026-09-27。本文展开[Agent 行为计划](AGENT-BEHAVIOR-PLAN.md)中的角色职责，对应**架构图、Task 图**，并对应计划中的[当前模块交互图](AGENT-BEHAVIOR-PLAN.md#21-与当前模块的交互)和[咨询路径图](AGENT-BEHAVIOR-PLAN.md#22-当前已跑通的咨询路径以及缺的下一段)。这是行为定义与当前入口对账，不是新增模块、权限配置或完成声明；交付状态仍以[能力索引](IMPLEMENTED-CAPABILITIES.md)与实际验收为准。

依据：[产品定位](../PRODUCT.md)、[MVP 用户行为](../MVP-BEHAVIOR.md)、[双图与生命周期对齐](../AGENT-GRAPH-LIFECYCLE-ALIGNMENT-2026-09-25.md)。表中的动作不自动授予权限，也不新增强制验收条件。

## 1. 使用方式与共同边界

**2026-09-28 用户六条批注纠偏：保留秘书、参谋、书记三个人用视角，不再把它们抹平成只有一个通用角色。** 秘书承担用户交流与项目掌控，参谋承担技术调查、决策辅助和总监工，书记承担事实核查、历史与设计文档及流程支持。这些有区别的行为可组合、按需实例化；不要求启动三个、四个或六个 Agent，也不形成固定角色权限链。

当前 Agent 能完成的具体动作可以直接完成；需要分开承接时，优先复用已有合适 Agent，依据上下文负担、独立判断和具体工作安排选择。协调默认由参与者利用双图、邮箱直接沟通；上下文受限时才临时委托局部“小参谋”，设计反馈回参谋、负责架构决策者或用户，而不是多加一道常驻转发角色。

UI 沿 [MVP 工作台](../UI-WORKBENCH.md)保持一个统一通用交互面，用户可像查看成员一样逐个打开 Agent 的 Session、状态和历史。秘书、参谋、书记是职责侧重，不新增三套 UI 入口。

并行执行可以使用多个同种工作 Agent，不需要新增 Role 类型。图中有可拆任务只是安排依据，不是自动派生指令。保留同工作区多 Agent 并行能力，不把“默认复用”变成一个全局串行主 Agent。

独立审查的价值在于评估上下文和责任相对独立，而非名称叫 Reviewer。仅让实现者切换审查措辞不构成独立意见；另一个 Agent 也不保证无偏。应给其要求、产物、来源和待核问题，让其核对结论，而不是只复述实现者的结论。普通自检仍由工作 Agent 完成，已采用的独立审查义务保留。

每项行为区分三部分：Agent 根据上下文做语义判断；工具执行具体操作；已有 owner 保存正式事实。角色不维护第二份 Task、架构或 Session 状态。没有增加判断、执行或必要事实职责的纯转发角色，不应成为必经站点。

- 文件已定位时直接使用 Kernel 文件/进程工具；图用于定位、关联和协作，不是每次文件读取的审批层。
- Task 节点可先记录未来意图，暂时没有验收条件或承担者；存在、就绪、已分配、执行结束、验收完成分别表达。
- 架构包含树、模块依赖、任务拆分树、预期依赖和消息往返是不同关系。不能把它们都解释为“上游完成后下游才准开始”。
- 模块数量或代码行数增加不自动创建 Agent。责任和交付边界帮助组织工作；只有具体上下文负担、独立判断或执行安排需要另一个主体时才分工，不从图结构直接推出 Agent 数量。
- 新受控动作服从工具自身的当前权限和提交约束；已发生结果、原回执和历史不因之后撤权而被抹除。不为正常生命周期不可达的角色热切换增加检查。

2026-09-28 用户已认可[单张协作主图](ORCHESTRATION-STATE-MACHINES.md#shared-mechanism-review)：只读背景问A′，实际承诺/行动变更交给原A；冲突按双方→相关Task/接口/模块责任人→必要时上层/用户定位有权负责者，再确认决定落实。具体[角色触发、参谋全局判断和决定/双图回流](ORCHESTRATION-STATE-MACHINES.md#project-guidance-loop)及[共同状态与转换条件](ORCHESTRATION-STATE-MACHINES.md#agent-state-transitions)已补充。职责不同体现在输入、判断与产出，不各设状态机或常驻Agent；已有角色资源不等于全局变化交付已接通。A′派生与完整协调消费者仍有实现缺口，后续沿原owner补齐。

## 2. 通用行为与双图的对应

下表保留用户关心的职责视角，由当前具备相应授权的 Agent 组合或按需分工承担。它说明产品行为，不表示每种图操作已经暴露为 Agent 工具；具体接线状态见第 3 节。动作之间可以有数据前后关系，不因此要求换一个角色来执行。

| 职责视角 | 架构图：读取和判断 | Task 图：读取和判断 | 可产生的变化及边界 | 执行主体安排 |
| --- | --- | --- | --- | --- |
| 秘书：用户交流与项目掌控 | 定位模块、参与者及来源，组织用户可理解的项目说明 | 掌握目标、进度、阻塞、待决与长程方向 | 按需形成可视化、文档、提示词和具体问题；保存须有实际工具，不自动采用计划 | 保留面向人的交流职责，可与其它职责组合；不另建独立 UI 入口或为每次提问再启动 Agent |
| 参谋：技术调查与决策辅助、总监工 | 调查技术选型、实际实践和 tradeoffs，对照架构职责/接口判断方案 | 拆分、检查计划是否仍服务目标，接收执行反馈 | 带依据的建议、候选及重审条件；架构 writer 消费者未接时只报告建议 | 按上下文与独立视角安排，不把每项实现细节升级为参谋审批 |
| 协调：直接沟通或临时局部参谋 | 依据模块关联找到相关参与者，设计分歧反馈负责决策者/人 | 处理局部依赖、等待和交接，安排具体工作 | 使用邮箱与双图沟通；授权范围内推进，不建立全局必经协调链 | 默认参与者直接协调；上下文受限时临时委托有范围的小参谋 |
| 执行：实施、自检、报告 | 读文件和设计，判断改动范围；发现设计问题向参谋/人反馈 | 理解交付目标、输入与检查要求 | 工具真实结果及来源；Run 成功不自动完成 Task | 复用合适主体，独立工作按实际需要分开，不固定一模块一 Agent |
| 审查：按任务核对 | 按委托检查复杂度、架构符合性及具体产物 | 核查实际完成和计划符合性，给出证据与缺口 | 审查报告不自动登记 Evidence；只有既定义务决定是否进入完成门槛 | 普通自检直接做；需要独立判断时委托，不要求常驻 Reviewer |
| 书记：事实、历史、设计文档与流程支持 | 核查设计文档与实现/明确决定是否一致，管理来源与历史 | 整理流程、待决与交接背景，辅助派发、审查和对话 | 文档/摘要/提示材料由实际工具保存；不另造权威状态，不把推断写成决定 | 可组合或按范围委托；不是只做摘要，也不成为新的图 owner |

架构节点的拆分止于有用的职责、接口、检索和协作边界；一个叶节点可以覆盖多个文件或文件内代码片段。这是行为方向，不能由此声称当前目录契约已经完整实现所有代码片段级映射。现有 `ModuleDefinition` 主要记录职责、路径与接口；包含关系与依赖分别保存。

## 4. 各项通用行为的动作明细

以下动作保留三个人用视角及执行/审查/临时协调的区别，可以组合，不是六份必须分别执行的任务书。Skill 约束行为，不证明必须另开执行主体。

### 4.1 接待与查询：把用户问题落实到事实、相关人或具体待决

| 触发/动作 | Agent 判断 | 实际动作与双图对应 | 产出、停止或转交 |
| --- | --- | --- | --- |
| 用户询问状态或解释已有决定 | 当前事实是否足够回答，缺的是事实还是意见 | 查询 Task 局部图、正式结果及关联材料；按架构模块定位来源，已知文件直接读取 | 带引用的答复；事实足够即结束，不为读状态调用另一个模型 |
| 问题需要既有参与者的语义判断 | 谁参与过相关工作，当前上下文和可用状态是否适合 | 用 Task/Module/Work 引用发现 Session、读卡片，发送带问题与来源的咨询；对应 AG1 | 已提交的咨询及未回答状态；不将发送回执写成答案，不抢占 busy Session |
| 发现原目标中遗漏的未来事项 | 属于既有目标还是需要用户确认的新范围 | 形成工作意图/计划建议；当前 Agent 有相应授权即可处理，没有验收条件也可保留未来节点 | 意图、理由和未确定部分；是否可采用取决于操作授权，不取决于是否叫规划者 |
| 用户需要可视化、文档或可执行提示词 | 怎样帮助用户理解并掌控项目，哪些内容需引用正式依据 | 读取局部双图与必要来源，生成说明/图示/文档/提示词；仅用实际可用工具保存 | 可用内容与保存结果；没有保存工具时不声称文件已写入 |
| 用户需要作出取舍 | 是否超出当前授权，具体分歧和影响是什么 | 汇集候选、对应模块/Task 和原材料，提出一个可决定的问题 | 用户决定或明确待决；不把模型偏好写成用户已批准 |

当前可复用 [Secretary Skill](../../resources/skills/platform-secretary/content.md)。AG1 已证明发现并发送；AG2b 已验原存活 Work Run 等待回复后继续，完整中断恢复仍待接线。

### 4.2 调查与规划：把目标转成有依据、可逐步细化的工作

| 触发/动作 | Agent 判断 | 实际动作与双图对应 | 产出、停止或转交 |
| --- | --- | --- | --- |
| 技术选型、实践或方案需要比较 | 可行性、代价、适用前提及 tradeoffs；当前实施是否偏离目标 | 调查具体来源与实践，对照架构图和计划，接收执行反馈 | 带依据的决策建议、重审条件与具体待决；总监工不等于逐工具审批 |
| 新目标或已有方案不再适用 | 哪些事实必须先调查，哪些假设需要标注 | 定向读文件、材料、局部双图；必要时咨询相关 Session；初始规划复用现有 Query 入口 | 候选方案或具体待决，保留引用与假设；候选不等于采用 |
| 拆分任务和安排关系 | 子工作是否能独立交付，依赖的是哪份具体输入 | 建议 Task 子节点、相关模块、输入与验收；未来模糊事项仍留在图上 | 可理解的拆分及待细化部分；不要求所有未来任务提前具备完整依赖和验证条件 |
| 修订未来工作 | 新事实影响哪些尚可变更的任务，是否在授权内 | 读当前计划后调用 `propose_future_plan`；只有既有授权允许时调用 `apply_future_plan` | 候选回执或正式新版本；不修改已领取工作来掩盖执行结果 |
| 判断架构分支或调整 | 是否出现独立职责、接口或变更边界；继续细分是否有检索/协作价值 | 对照架构目录与源码观察，提出模块、路径、接口、包含/依赖关系修订；沿已有采用入口落地 | 有来源的架构建议；Agent 目录修订消费者尚缺，不写成已自动改图；无新信息时停止重复讨论 |

当前可复用 [Adviser Skill](../../resources/skills/platform-adviser/content.md)。初始规划与未来计划工具已有，不能据此推断架构治理、自动派生和所有规划结果消费者已完成。

### 4.3 分工与协调：选择谁继续什么工作，并处理真实阻塞

参与者默认通过双图和邮箱直接沟通；只有上下文承载不了局部协调时才临时委托小参谋。设计分歧回到参谋、负责架构决策者或用户；不要求所有消息返回一个总协调者。

| 触发/动作 | Agent 判断 | 实际动作与双图对应 | 产出、停止或转交 |
| --- | --- | --- | --- |
| 已采用工作需要承担者 | 原 Session 是否相关、可用；是否确需独立上下文或独立意见 | 结合 Task 工作、架构关联和 Session 卡片，明确复用或创建的选择；由原创建/关联/领取/执行入口落实 | 承担者、工作边界、必要输入和真实派发回执；Agent 选择驱动派发的完整链待 AG3 |
| 发现可独立推进的子工作 | 是否能独立交付，哪些输入现在已可用；当前或已有同伴能否承接 | 提出或采用授权范围内的任务拆分；确需另一个执行上下文才分配 Session。同 Workspace 可并行，不先证明不存在所有潜在冲突 | 明确分工和局部关系；并行 Agent 行为待 AG4，可拆 Task 本身不强制新增 Agent 或 Role |
| 工具报告实际冲突、缺输入或需要改方案 | 谁受影响，应该调整、等待、咨询还是升级 | 根据具体文件/版本/任务和消息来源处理受影响工作；需要变更时走相应正式入口 | 调整结果或明确等待原因；无关工作继续，消息回复不自动满足 Task 输入或验收 |
| 取消、失败、交接或重复无进展 | 实际执行是否已停，结果是否已知，是否有新信息 | 读取原 Run/控制结果；核对未知提交，整理接任所需义务和来源；必要时请求授权决定 | 已确认状态与下一动作；未知结果不安全重跑，未确认停止不移交相交写入；失败新 Attempt/完整恢复待补 |

协调是授权职责，不是所有工具动作的中央审批节点。当前 Workflow 已推进过限定正常链，但其代码选择 Session 不等于 Agent 已完成上述判断与派发闭环。

### 4.4 实施与自检：调用工具完成明确工作，提交实际结果

执行者利用已有工作上下文判断影响：发现涉及接口、约束或其他成员工作的变化，应附来源主动反馈，不必等行数/双图变化量达到阈值。平台不再运行额外模型替每次改动筛选“关键性”；机械触发与参谋后续判断见[注意力触发说明](ORCHESTRATION-STATE-MACHINES.md#attention-triggers)。

| 触发/动作 | Agent 判断 | 实际动作与双图对应 | 产出、停止或转交 |
| --- | --- | --- | --- |
| 收到工作与材料入口 | 交付范围和具体输入是否清楚，已有上下文是否够用 | 查当前 Task、相关模块及必要来源；已定位文件直接读；不足时提出具体问题 | 可执行理解或明确缺口；不为开始工作全量重读历史/遍历全图 |
| 实施修改或调查 | 下一步需要哪个原子动作，是否仍属当前工作 | 调用有效授权下的 Kernel/WorkspaceTools 工具，消费真实结果；必要时异步咨询 | 文件/命令/调查结果及来源；工具约束由工具和原 owner 处理，不另经所有角色审批 |
| 发现需要细化任务或调整模块边界 | 属于局部实现细节、计划变化还是架构责任变化 | 局部实现继续执行；计划变化提出未来修订；架构变化提出有来源的候选 | 实际发现与建议分别记录；读过文件或模型描述新模块，不自动产生正式图节点 |
| 工作结束或遇到阻塞 | 实际完成了什么、适用检查有哪些、哪些结果仍未知 | 执行必要检查，报告产物、来源、失败与未决；Runtime 观察 Run，原服务提交执行和验收事实 | 可定位的结果与检查；Run 结束通常回待命，Task/Goal 完成走正式入口，不由正文“完成了”决定 |

已存在真实模型与工具执行链；授权、装配和执行者 Skill 应复用它。失败后的同 Task 新 Attempt、Agent 自主接续和完整恢复不能用新的随机 Session 冒充完成。

### 4.5 独立审查：在需要不同判断视角时委托核对

| 触发/动作 | Agent 判断 | 实际动作与双图对应 | 产出、停止或转交 |
| --- | --- | --- | --- |
| 已采用义务/用户要求独立审查，或已有方案倾向使独立核对有必要 | 审查对象、范围、标准，以及被委托者是否独立于该项实现/决定 | 从 Task/ReviewWork 关联定位产物、架构版本、diff 与证据；请求真正缺失的材料 | 明确范围、依据和材料缺口；按需咨询不自动增加验收门槛，也不需要常驻 Reviewer |
| 核对设计与实现 | 按本次任务判断复杂度、架构符合性、实际完成与计划符合性；区分问题和个人偏好 | 对照架构职责/接口、计划、实际代码和执行证据，必要时运行相关检查 | 问题、位置、影响与依据；不把假设的新需求变成阻塞条件 |
| 返回意见或复核修复 | 证据支持接受、返工还是暂不能判断；问题是否被实际解决 | 通过原审查结果/证据路径关联被审工作；仅围绕原问题及实际新增风险复核 | 审查结论与缺口；正式完成仍由既有义务和完成入口决定，无理由不扩大测试循环 |

**当前 ReviewWork 相关契约和来源绑定检查存在，创建、派发、结果消费的完整生产闭环仍缺。** 配置 Reviewer Role/Skill 不会自动补齐此链；`authorizeReviewWork` 也不是创建或完成审查的工具。

### 4.6 整理与交接：让已有事实和决定可恢复、可追溯

| 触发/动作 | Agent 判断 | 实际动作与双图对应 | 产出、停止或转交 |
| --- | --- | --- | --- |
| 历史、设计文档或流程需要维护 | 哪些事实可核查，文档和实现/决定是否一致，派发/审查/对话缺哪些背景 | 定向读取双图、文档和来源，核查差异，使用实际授权工具更新文档或准备提示材料 | 带来源的文档和流程支持；不把辅助派发说成已启动执行，不替代正式 owner |
| 一批工作或讨论结束 | 哪些是正式事实、明确决定、建议、分歧和未决 | 读取原回执、Task 状态、消息与对应架构版本，定向取必要历史 | 带来源的分段摘要；不把 Run 结束、邮件已回或模型推测当作 Task 完成 |
| 信息需要在双图中便于查找 | 现有正式引用是否足够，缺的是摘要还是实际关联 | 引用 Task/Module/Session/Run 与材料；当前 Agent 有相应授权时直接经原入口提交必要关联，无需交给专用书记 | 来源索引或明确待补关联；不维护第二套图状态，不凭摘要改写正式事实 |
| 压缩、交接、归档或恢复准备 | 下一承担者真正需要哪些义务、决定、成果与未决项 | 整理当前采用版本和历史入口，形成交接材料；执行生命周期操作仍归原服务 | 接任可用的材料及缺口；摘要不替代原历史，读取归档材料不唤醒 Agent |

当前可复用 [Scribe Skill](../../resources/skills/platform-scribe/content.md)。Skill 指导整理，不意味着自动触发整理、持久化全部整理产物或完整交接消费者已实现。

## 5. 与两张运行路径图的对应

这里对应行为计划的两张运行路径图；第 2 节对应产品本身的架构图与 Task 图。**同一角色可以走多条路径，一条路径也可以被不同角色复用。**

| 角色动作 | 当前模块交互图中的路径 | 咨询路径图中的位置与缺口 |
| --- | --- | --- |
| 秘书解释进度、书记整理事实 | Agent → 平台工具 → WorkGraph；已有文件引用直接走 Kernel 文件工具 | 事实足够时不进入咨询；需要意见才发现、选人、发消息 |
| 参谋调查与提出未来计划 | Agent → 文件/WorkspaceTools 读取；Agent → 白板工具 → 计划 owner | 可作发送方，也可承担被咨询的规划职责；AG2a 已接收件方显式 Query/Answer 回复关联；AG2b 已验回复进入原存活Work Run再决策，中断后恢复仍待接 |
| 协调选择承担者和派发 | 发现工具读取关联；已有 Host/Workflow → Runtime 与 WorkGraph 执行路径 | 咨询回复不等于派发；消费 Agent 的复用/创建选择并真正派发待 AG3 |
| 执行者做工作与报告 | Runtime → Kernel Agent → 工具；Kernel 历史 → Runtime 观察 → WorkGraph 正式事实 | Work Run 已可读信/回复；不因此推断收件箱会自动启动 idle Session 或抢占 busy Session |
| 审查者读取产物并返回结论 | 复用材料、工具、执行和证据入口；原完成 owner 消费适用结果 | 可以咨询相关人，但意见消息不能冒充正式审查结果；Reviewer 完整消费者仍待接 |
| 书记准备交接 | 定向读图、原回执、材料和历史，输出引用与摘要 | 可整理原请求/回复及未决；不把消息往返伪装成已交接或任务已完成 |

普通咨询可能由任一种职责承担，并不自动获得原工作执行权。AG2a 已将原咨询、接收方显式执行和正式 Answer 回复关联；不是要求每个咨询先造一个 coding Task，或让 Query 获得全部写工具。

## 6. 如何装配，而不是为每个角色另造执行框架

这些表用于约束**现有配置 + 通用 Runtime 装配 + 可组合 Skill**。秘书、参谋、书记保留各自人用职责；通用执行与按任务审查可组合，不建立六套执行器或永久 Agent 状态 owner。

2026-09-28：AG6 已按两阶段工作法导入生产配置与五份提示词资源。`grant.skills = { bundle: 'platform', behaviors: ['secretary', 'adviser', 'scribe', 'reviewer'] }` 按需选择行为，默认共同指令为 `platform-work`；数组展示可选项，不要求全部启用，不启动额外 Agent 或扩大工具授权。旧 `resourceRoot + enabledIds` 配置保持可用。

已通过 19 项检查、types、build 和模块边界检查；提示词修正后的 8 项检查与资产摘要复验通过，见[本批证据](reviews/evidence/agent-behavior-2026-09-28/ag6/README.md)。真实 DeepSeek 两轮、每轮 4 次调用均机械完成，但语义抽查仍出现无来源连线、过强的消费者结论，以及不必要的授权/检查建议。**这只证明配置装配和真实调用已接通，不证明语义可靠，也不证明正式 Reviewer 结果消费者完成。** AG6 本身不完成咨询、派发和恢复消费者；后续 AG2a 的交付见本文末尾，其余缺口不因 Skill 装配或模型返回正文转为已交付。

用户使用**一个通用工作台，按项目与成员查看 Agent、切换 Session 和历史**；秘书、参谋、书记是职责视角，不是三套人用 UI 入口。

项目规模与复杂度自适应、1–2 万行/500K 等讨论属于[架构文档](ARCHITECTURE.md)记录的未来方向，不作为自动派生阈值或本轮门槛。

| 变化 | 应放的位置 |
| --- | --- |
| 职责、目的、预期产出、成功/停止/交接条件 | 现有 RoleSpec 内容；声明存在不代表所有条件已有自动消费者 |
| 如何判断相关性、问谁、拆分、选择并行、停止重复讨论 | Skill/Prompt，使用上表约束；Skill 文本本身不授予工具权限 |
| 模型、预算、有效工具、写范围、启用哪些 Skill | 现有 RoleSpec/Host 配置与 Runtime 装配；Role 与 Skill 不假定一对一绑定 |
| 真正启动接收者、创建/复用并派发、提交审查结果、失败新 Attempt | 现有 owner 上缺失的具体动作消费者，逐批补接；不能靠增加一段角色说明代替实现 |

对一个新增行为先问：**能否组合已有动作完成？** 可以则增加配置或 Skill 约束；缺少真实操作才补共享入口。创建、复用、派生、并行、停止和恢复的共同条件继续使用[行为计划第 3 节](AGENT-BEHAVIOR-PLAN.md#3-创建复用派生与停止条件)，不在每个角色内复制一套生命周期。

授权与职能名称分开：当前配置缺少工具，不自动证明需要一个专用协调者或书记；应核对该工作本就需要的授权与装配。本页记录行为设计与 AG6 限定装配状态；不修改已绑定 Session 的 Role，不进行运行中角色热切换，也不删除已有 Skill 或绕过工具权限。已有 AG1/后续缺口仍按原限定范围记账。

AG2a 当前工程验收：两阶段生产导入及独审三修收口，12 文件 / 115 项、Node/UI types、边界和隔离 build 通过；限定真实模型/浏览器接线验收通过：首条含两次参数错误后恢复，第二条浏览器路径无工具失败；不保证普遍语义可靠。见[AG2 证据](reviews/evidence/agent-behavior-2026-09-28/ag2/README.md)。AG2a 本身不代表自动调度或 Work 续接；后续 [AG2b](reviews/evidence/agent-behavior-2026-09-28/ag2b/README.md)已验存活Host原Run多轮往返，AG3–AG5缺口保持。
