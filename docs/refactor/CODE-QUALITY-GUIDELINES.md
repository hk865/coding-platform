# 代码规范、重构目标与质量验收

```yaml
status: active-for-refactor-docs
updated: 2026-09-23
scope: 本轮重构的模块设计审查及后续实现审查
authority: 不替代 PRODUCT、ARCHITECTURE、接口契约或既有实现状态记录
enforcement: 本轮模块文档与后续实现审查的共同要求；自动化门禁另行配置
```

本规范的目的：在保持已确认功能与边界的基础上，让代码更容易阅读和修改，消除同义重复，减轻过大的实现职责，并能证明重构收益。用户已要求将代码规范、重构目标、接口和职责清晰度落实到模块文档；本文件据此作为本轮共同要求。当前五个目标模块在各自的职责、接口、迁移与验收内容中承接专项目标，不要求沿用旧 13 篇文档的章节编号。依据与外部资料取舍见 [调研报告](CODE-QUALITY-RESEARCH.md)；其中旧划分的调研结论保留为历史线索，不能替代当前目标设计。

阅读时先看 [§7 重构目标与完成条件](#7-重构目标与完成条件)，再按 §2 的 CQ 规则审查怎样实现；具体模块承担什么、怎样验收，回到 [模块索引](modules/README.md)。要求已写入不表示源码已满足，也不表示已回填旧文档仓的权威版本。

## 1. 适用方式与规则级别

- **已有约束**：已确认的产品行为、状态权威、模块依赖、协议兼容性及当前编译配置继续适用。[R2 评估标准](../../my-coding-platform-docs/agent_platform/dev_docs/decision/01-evaluation-criteria.md) 维度 2 已有文件 >1000／>500、函数 ≥120／≥80 等不达标／警戒口径，继续按其原有范围用于评估，本稿不撤销它们。引用本文件不会改变既有权威关系。
- **本轮共同要求**：CQ-01～CQ-12 约束实现与审查方式，RG-01～RG-06 约束重构结果；每个模块写清适用目标、改动边界、旧路径和验收要求，实际进展与证据集中到[实施方案](IMPLEMENTATION-PLAN.md)及其指向的验证记录。未逐项引用不免除适用的通用规则；新增模块说明从哪些旧实现承接能力，不编造自身旧副本。未列 RG-06 的模块不作独立性能收益承诺；若实际改动影响性能或提出收益声明，仍须按 CQ-09 验证。尚未配置自动阻断，不能据此宣称现有代码已合格。
- **新指标建议**：行数、嵌套、复杂度、重复率等可以辅助发现风险位置；本轮不依据外部默认值新增或替换全仓门禁。对既有指标的重新校准应保留原评估结果，并同步规则来源与测量口径。

文档审查检查“职责和接口是否可实施”；源码审查检查“实现是否做到”。通过第一种不等于通过第二种。只审查文档时，源码质量与性能结果记为待验证。

**依据顺序**：本轮用户确认的需求与[原作者意见](../history/before-2026-09-22/agent-platform-user-replies-numbered.md)确定意图，[当前意图与决定](intent/INTENT-AND-DECISIONS.md)确定本轮采用结论，[历史 PRODUCT](../history/before-2026-09-22/PRODUCT.md)保留功能承诺来源，[核心数据与操作](CORE-DATA-OPERATIONS.md)和[编排状态机](ORCHESTRATION-STATE-MACHINES.md)明确对象、操作及行为，[ARCHITECTURE](ARCHITECTURE.md)、[模块文档](modules/README.md)和[模块 DAG](module-dag.md)据此确定实现边界，[实施方案](IMPLEMENTATION-PLAN.md)承接迁移与验证。现有契约与当前源码分别用于核对约定和实现事实。外部实践提供方法，不覆盖这些依据。出现冲突须登记并回到对应正文解决，不能在模块质量章节内悄悄改权威归属或新增依赖。

## 2. 统一审查规则

| ID | 审查要求 | 必要证据／适用边界 |
| --- | --- | --- |
| **CQ-01 功能保真** | 先列真实调用者、用户路径和必须保持的不变量；分开现状、目标与未接能力。删除接口前确认消费者迁移。 | 受影响入口 → 调用链 → 用户可观察结果；stub／夹具／真实适配器的验证结果分开。产品变化另有依据，不能伪装成内部重构。 |
| **CQ-02 内部职责** | 按变化原因拆解编排、领域规则、I/O 适配等内部工作；入口可以组合步骤，不独揽所有实现。 | 说明内部单元负责什么、共享什么、谁调用。单元可以是函数或文件，不强制每层一类、每函数一文件或新增 Module。大文件先分析职责，再决定是否拆。 |
| **CQ-03 接口可读性** | 按真实消费者暴露最小必要能力，写清输入、结果、失败、状态副作用与兼容方式；避免只为转发再造门面。 | 对照模块的能力／消费者表、核心操作契约及状态转换。不要要求调用者依赖整个实现对象才能调用一个功能；不要用大量布尔开关掩盖不同业务。字段及 schema 由核心设计与对应代码契约共同维护，模块页不另写一份。 |
| **CQ-04 共享与去重** | 同义规则保留明确 owner；同模块先内部复用。跨模块共享须有合法依赖及稳定语义。 | 原副本 → 共同实现 → 实际消费者 → 旧路径删除或有期限的兼容适配。相似代码先核对身份、授权、失败、事务和生命周期，语义不同不能硬合并。当前去向见[承载与迁移表](modules/ownership-map.md)和[实施方案](IMPLEMENTATION-PLAN.md)；旧 [S01～S12](archive/2026-09-23-before-core-design/modules/ownership-map.md#13-共用实现与旧路径去向)仅作为问题来源与历史对应。 |
| **CQ-05 类型与数据边界** | 外部输入在边界解析；保持类型收窄和可区分结果，避免无依据的 `any`、非空断言或多重断言掩盖问题。对借入数据说明是否可修改。 | 区分协议结构验证与有权威的业务受理。只读标注表达约束，不能假定它自动实现深度运行时不可变；保留必要的复制、验证与版本核对。 |
| **CQ-06 状态、错误与副作用** | 读写归属、事务边界、并发顺序、取消、重试与幂等必须可追踪；预期拒绝与非预期故障不能混淆。 | 错误保留范围、来源与原因；不用空 catch、默认成功或空结果隐藏失败。I/O 前后重新核对的版本／授权条件不因“去重”移出正确时点。沿用现有结果与异常契约，不一刀切改成新错误体系。 |
| **CQ-07 易读性与局部一致** | 名称使用领域词典，函数名表达动作；主流程顺序清楚，减少无意义跳转、隐式依赖和嵌套。注释解释原因和不变量。 | 审查者应能从入口追到决策与副作用。注释数量、短变量名、文件数量都不是成绩；格式沿用项目既有约定，格式调整与行为修改分开。 |
| **CQ-08 有效验证** | 按变更风险验证行为、不变量及真实接线；测试应在目标行为错误时失败。 | 共用实现的契约测试＋关键消费者接线检查；并发、恢复或存储变化验证相应边界。避免仅测试新 helper 被调用，或测试逐行复写实现。文档／纯格式变化不强行新增行为测试。 |
| **CQ-09 成本与性能** | 涉及重复读取、全量扫描、上下文重建或运行记录副本时，比较同一场景下的实际工作量。 | 报告输入规模、调用／读取／写入次数、耗时或 token 口径、适配器、缓存状态。区分代码推断、历史记录与本轮复测；不能用新增缓存类、文件减少或接口减少代替收益。 |
| **CQ-10 指标与例外** | 已有评估阈值按原规则报告；拟新增／调整的自动指标按代码类别及现有分布校准。例外要有具体理由和复查触发条件。 | 生产代码、测试、生成物、迁移脚本、第三方代码分组；保留分母和工具配置。禁止为达行数把耦合搬到多层转发中；重复率不叫复用率。 |
| **CQ-11 适度扩展** | 对已有需求，能在明确职责内增加策略／步骤／适配并保留已有消费者；抽象应减少实际变更成本。 | 用一个真实变化说明改动范围。没有具体需求时不预建插件引擎、万能状态机或通用 Repository；“将来插入记忆／知识”目前只是方向，不能变成本轮交付要求。 |
| **CQ-12 变更可审查** | 每次变更有单一可解释目的，记录行为变化、兼容期、旧代码退役和验证结果。 | 允许跨多个文件完成同一功能，不机械限制文件数；对未完成项如实登记。兼容层须有消费者、删除条件，不能无限保留两个业务权威。 |

### 2.1 校验须与操作后果匹配（2026-09-26）

新增运行路径校验和反例测试必须说明触发它的公开输入或合法生命周期操作。当前 Session 角色在创建/绑定后稳定，暂停、恢复、归档与重新启用不更换角色；没有运行中换 Role 的产品操作。仅靠直接篡改内部持久记录制造的角色变化，不增加热路径重读、补救分支或验收测试；已经为此添加的测试和要求应删除。材料授权撤销、真实占用变更、外部不可信输入及存储协议解析仍按各自边界验证。见[本次用户纠正](intent/INTENT-AND-DECISIONS.md#2026-09-26-补充只验证真实生命周期可达状态)。

审查新增或保留的硬校验时，说明它保护什么正式不变量、在哪个操作边界生效、移除会造成什么具体错误，以及需要读取哪些局部对象。已有领域规则在 owner 内复用，不在工具、Runtime 和 UI 各复制一遍；跨异步边界确有权限或所有权变化风险时，保留必要重核。

| 场景 | 适用检查 | 不应扩大的门槛 |
| --- | --- | --- |
| 模型/工具新动作、领取及正式变更 | 实际权限、精确身份、当前所有权/代际、幂等和提交所需局部版本 | 全账本版本锁、全工作区单写者、未来冲突完整证明 |
| 普通查询、原历史与观察/终态事实记录 | 访问范围、原执行身份和来源、去重及必要顺序；释放占用另核对当前 owner/generation | 每次重走完整新动作准入；后来撤权导致已发生事实无法记录 |
| 未来意图节点与规划修订 | 基本结构、已填写引用、授权范围及受影响正式状态；采用的硬依赖保持合法 | 必须先有完整验收、完整依赖或分配；由数据库证明规划最优或语义无冲突 |

增量关系变更优先核对受影响范围；整版计划受理可以运行一次共享结构校验，不要求任意查询/节点编辑遍历整个系统。正式引用、CAS 和硬依赖无环不因白板定位而撤销。语义判断交给角色/Skill，工具返回缺口和事实。验收围绕独有失败风险，不为同一个不变量逐层重复通用测试矩阵。依据见[用户补充](intent/INTENT-AND-DECISIONS.md#2026-09-26-补充未来意图节点与校验边界)。

**本批验收收敛：**依[架构结论纠偏](intent/INTENT-AND-DECISIONS.md#2026-09-26-补充架构结论与完整产品路径优先)，保留骨架/测试STOP中审→实现/独审的两阶段流程。中审确认骨架职责、共享接口和真实消费者不带偏；实现验收确认正常公开路径可跑，以及真实权限、正式状态和副作用边界正确。骨架首红遮挡的后段不得记为已验证。发现真实越权、重复副作用、回执/unknown事实错误仍须修复；仅让覆盖、断言或排列组合更漂亮，不得作为新增返修轮次的理由。

测试投入优先完整端到端用户路径。邻接只选受本次修改实际影响的必要集合；既有共同规则复用已有证据，不为每层或每次中审重建矩阵。目标与必要邻接通过且无未解决真实缺陷后，进入实现或下一产品链，不继续循环补测。整合后保留既定物理隔离验收；不以少测为由放松真实权限、所有权、已发生事实或未知执行窗口的约束。

## 3. 行数、层级、复用率的处理

| 用户关心的指标 | 本项目建议 | 不采用的做法 |
| --- | --- | --- |
| 单文件／单函数多少行 | 先按既有 R2 阈值报告；结合职责数、分支、I/O 与变更频率分析原因。后续自动门禁可针对新增及实质修改代码，但不能擅自改变原评估口径。 | 仅为达到数字而拆分；把 Google 的 CL 规模例子误当文件上限；把本项目警戒线误称行业强制线。 |
| 依赖层级 | 模块依赖按架构 DAG；内部层次以调用可追踪、无反向越权、无无效转发为准。引入中间层应说明所解决的变化或边界。 | 把控制流嵌套层数当依赖深度，或给所有模块统一套固定层数。 |
| 复用率 | 追踪每项同义规则从几份实现收敛到哪一处，哪些真实消费者复用，哪些旧路径已退役。 | 规定“复用率必须达到 X%”；把文本重复率的补数当复用率。 |
| 圈复杂度／嵌套 | 用作函数风险信号，与顺序依赖、并发和读者理解成本一起看。 | 为降低工具分数把一个难理解函数改成多个难追踪函数。 |
| 测试覆盖率 | 优先覆盖关键分支和契约；若后续设阈值，明确新代码／全量、行／分支及排除范围。 | 把达到覆盖率当作接口装配、业务正确或性能达标的证明。 |

ESLint 的默认参数和 Sonar 的预置质量门槛只在 [调研报告 §3](CODE-QUALITY-RESEARCH.md#3-数字的含义与本项目的取舍) 列作参考，本文件未把它们采用为项目门禁。

## 4. 融入模块文档的最小写法

当前模块页围绕职责、能力与消费者、依赖与状态归属、旧实现迁移、验收组织内容，不强制统一章号。数据字段和操作在 CORE-DATA-OPERATIONS 中定义，允许转换和执行恢复在 ORCHESTRATION-STATE-MACHINES 中定义；模块页负责说明谁实现、谁消费、为什么这样分界和旧路径怎样退出。

接口变化仍需能追踪到具体消费者、依赖边动作、理由及适用约束，但不再要求每个模块保留旧 §7 的单行交接格式。DAG 必须与模块能力表一致，包含端口注入产生的长期依赖；不能仅因没有静态 import 就遗漏实际依赖。若沿用历史 I／S／不变量编号，应链接历史来源并说明当前对应，不能把已失效的章节编号当成现行契约。

| 落点 | 要写清什么 | 内容边界 |
| --- | --- | --- |
| 职责与内部划分 | 模块负责／不负责、内部责任单元、功能与副作用、共同步骤和专用分支 | 内部单元按变化原因组织；可以是函数或文件，不默认新增类、服务或 Module。 |
| 能力与消费者 | 提供者、真实消费者、输入输出、拒绝／失败、状态副作用、现状与目标 | 引用核心操作和状态机中的契约；内部共用逻辑给出映射。实际接线和 wire schema 随迁移同步代码契约，不推给无明确负责人的未来阶段。 |
| 依赖与状态归属 | 消费哪些能力、长期依赖方向、正式记录与派生结构、事务及外部执行边界 | 与当前五模块 DAG 一致；WorkGraph 不因读取 Kernel 历史而暗中反向依赖 AgentRuntime，核心不回调 Workflow 策略。 |
| 迁移与接口变化 | 旧路径 → 共同实现 → 消费者迁移 → 删除／兼容条件 | 以[承载与迁移表](modules/ownership-map.md)和实施批次为入口；没有旧代码的能力明确为新增，不通过改名假装去重完成。 |
| 实现差距与例外 | 未接能力、必要实现前提、尚未验证的结果及对应批次 | 不把目标写成已实现；真实设计缺口归回核心／状态机／模块正文解决，实施前须有具体处理，不能默认通过。 |
| 专项验收 | 当前问题 → 本次目标及边界 → 共同实现与旧路径去向 → 验收证据 | 按模块实际风险列要求，引用 RG／CQ；共同命令和通用规则不逐模块复制，性能目标与实测结果分开。 |

需要专项对照表时，可用：`当前问题／依据｜本次目标与改动边界｜共同实现与旧路径去向｜验收证据（关联规则）`，不要求为了格式另加一层重复章节。写“已验证”必须指向实际证据；待实现能力、目标接口和性能目标继续标待验证。生命周期的策略、状态和 Kernel 操作分别按当前归属说明，不保留一个未实现的独立 AgentLifecycle 模块作为默认前提。

历史写法可参考归档的 [ReadModelIndex §9](archive/2026-09-23-before-core-design/modules/data/read-model-index.md#9-重构目标与质量验收) 和 [WorkerRuntime §9](archive/2026-09-23-before-core-design/modules/execution/worker-runtime.md#9-重构目标与质量验收)，其中旧 owner／依赖／章节约定不再作为当前目标。当前专项要求见[五模块索引](modules/README.md)；实现证据在对应迁移／验收记录中维护，模块页只保留要求和稳定入口，避免每次测试结果抄进多篇文档。

## 5. 审查流程与结果表达

1. **确认范围**：源码版本／工作区状态、模块、变更入口和上位依据。历史 `source-analysis.md` 用于找线索，结论回到当前源码核实。
2. **审查设计**：功能保真、内部职责、公共接口、合法共享、状态写者和旧路径退役；将阻碍实施的缺口归回对应文档。
3. **审查实现**：沿真实调用链检查本次改动；涉及共用核心时覆盖关键消费者，包含失败和兼容行为，不只检查抽出的函数。
4. **适量验证**：使用当前类型检查、相关测试与架构检查；性能声明另需同条件测量。执行结果记录日期、命令／场景及局限。
5. **分类输出**：① 可证实的行为／契约缺陷；② 有维护成本证据的质量问题；③ 可选风格建议。每项给位置、影响、依据和可执行修正；不把个人风格当阻断理由。

问题记录最少包含：`模块＋当前文件/符号/行号 → 触发条件或维护困难 → 影响 → CQ／契约依据 → 修正方向 → 验证方法`。不能仅以“代码太长”“不够优雅”判不合格。

本项目现有检查入口见 [package.json](../../coding-platform/package.json)：`typecheck`、`test`、`check:architecture`；其中 `check` 当前仅组合前两者。调用名、文件名与静态 import 检查不能证明宿主已注入真实实现，也不能证明共享语义正确。

## 6. 本稿的完成边界

本文件为当前“核心数据与操作 → 编排状态机 → 五模块与 DAG → 实施方案”链条提供共同质量要求。设计产物是目标，完整源码迁移、Session 生命周期接线、UI 联动、基线测量、工具配置和 CI 接入按实施方案记录实际进度；文档落地不表示这些工作已完成。调研过程见 [调研报告](CODE-QUALITY-RESEARCH.md)，各模块最新专项要求以当前模块页为准，旧 13 模块页及 S 项保留为历史来源。

## 7. 重构目标与完成条件

以下目标来自用户确认的需求、现有产品／架构与 [作者意图修订结论](../history/before-2026-09-22/agent-platform-open-decisions-recommendations.md)中“A3：怎样才算真的重构”一节：真实路径采用共同必要规则、旧重复路径退出并保留完整产品路径。外部评审方法用于帮助验证这些结果，不增加未经确认的功能承诺。

| 目标 | 本轮要求的结果 | 完成证据 | 对应质量规则 |
| --- | --- | --- | --- |
| **RG-01 功能与意图保真** | 已确认功能和关键用户路径保持；本次确需变化的行为有产品／架构依据，现有能力、目标能力和未接能力分清。 | 受影响入口与真实消费者清单；普通运行、初始确认、Query、Reviewer、Handoff、失败／恢复等适用路径的行为验证；真实适配器与夹具分开。 | CQ-01、CQ-06、CQ-08 |
