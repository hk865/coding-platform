# 测试好坏的核对尺子（用户 2026-10-13 要求；lead 与 Codex 共用）

用户原话："好的测试是针对业务流程，不是那种只用读就能够清楚的小的单元测试。"

## 三个层级，按这个优先顺序

1. **业务流程（首选，每条用户/agent 可见的行为至少一条）**
   - 从真实入口出发：生产组合 `createTargetPlatform`、Host 路由、Workflow、Runtime 工具（脚本模型）。
   - 经过真实 owner 和真实 RecordStore（内存 + SQLite 两种后端）。
   - 断言用户或 agent 看得见的结果：决定队列里的卡、“请知悉”提醒、上下文里的行、消息能否发出、回执重放的结果。
   - 包括失败分支：拒绝、读坏、重放、同库重开、两次提交的先后。
2. **模块契约（必要时）**
   - 一个 owner 或读模型的公开接口，用真实依赖。
   - 覆盖规则表里的分支：拒绝、分页、容量、旧数据。
3. **局部单元（少量，只在规则本身复杂时）**
   - 纯函数状态机的边界表，例如进入/恢复/再进入的转换。
   - **不写读一眼代码就知道答案的测试。**

## 红旗（发现就删、并或改写）

- **自证：** 测试替身预置了被测结果，比如 mock 返回什么，就断言什么。
- **测实现，不测结果：** 断言调用了某个内部函数、调用了几次、私有结构的形状，而不是看得见的结果。
- **只测成功路径：** 没有失败、重放、重开、竞争提交的用例。
- **太碎：** 一个用例只覆盖一行代码，比如字段拷贝、常量、getter。
- **重复：** 同一个行为在几层都测了一遍。
- **造数据：** 夹具直接改数据库制造状态（仓库规则：不要靠篡改数据库才能触发的测试）。
- **调真实模型、联网、依赖墙钟顺序。**

## 接线包 2 必须有的业务流程

| 线 | 业务流程 | 至少看到 |
| --- | --- | --- |
| I-2 | 有秘书职责的成员在真实 Run 里用工具发“请你决定” | 进了你的队列；执行者被政策拒绝；只读副本被拒绝；角色读失败时拒绝，不降级；重放返回原结果 |
| I-4 | 你改了自治级别，成员下一次准备执行 | 上下文目标段是新值；已绑定的执行不变（G 不动） |
| I-6 | 队列里有待答卡，成员下一轮执行 | 提醒段出现这张卡；答完后消失；卡源缺席时有明确提示行，不说“没有待决” |
| I-5 | 成员回复后，它的 Session 因中断或 Host 重启变成不可用 | “请知悉”里出现一条新提醒，标看过后不重复；恢复可用后从列表消失；再次不可用又出现新提醒；先不可用、后回复，回复时出提醒；旧数据缺位置只影响相关目标，其它目标照常 |
| 组合 | 上面四条走生产组合（PI 行），同一个后端实例 | 读取零写入、零模型调用 |

## 怎么用

- **审 Codex 写的测试时：** 每个用例标出层级 1/2/3。层级 3 的逐个问“读代码就知道吗？”，是就删或并入流程用例。
- **上表每行业务流程，** 都要找到覆盖它的用例 ID；没有就补。
- **数量不是目标：** 76 个用例里如果有很多层级 3，宁可少而全。删减要同步改规格 §5 和 §0.5 的计数。
