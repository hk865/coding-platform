## N0 Store lane 续修报告：JSON 值语义统一编码

### 1. 缺陷与修复

Lead 复现属实，基线 RED 精确定位：

```
× sqlite: indexes follow decoded JSON values for duplicate fields and numeric literals
  lookup(['shared','open']) 期望 duplicate 行，实得 []
```

根因：SQLite 直接持久化了 `EncodedRecord.json` 原始文本，表达式索引按**原始字节**解析——重复键取首值（`"wrong"`），`9007199254740993` 按 64 位整数精确保留；而 memory 索引来自 `JSON.parse` 后的对象（重复键 last-wins、数字按 JS double）。冻结澄清：`EncodedRecord.json` 是 JSON 值编码而非精确字节，`JSON.parse` 后的对象才是共享值语义。

修复（本 turn 只改两个文件）：

| 文件 | 位置 | 修复 |
| --- | --- | --- |
| `next/src/core/record-store/in-memory-record-store.ts` | `commitPrepared` 写入循环 | `upsertSnapshot(refKey, record.record.json)` → `upsertSnapshot(refKey, JSON.stringify(record.parsed))` |
| `next/src/core/record-store/sqlite-record-store.ts` | `commitInsideTransaction` 写入循环 | `upsertSnapshot(record.record.refKey, record.record.json)` → `upsertSnapshot(record.record.refKey, JSON.stringify(record.parsed))` |

两处均加了边界注释。单行即可，无需 helper；两后端都从同一个 `planned.record.parsed` 派生，天然满足“索引值与存储值一致”，未引入抽象。

### 2. 保持不变的边界

- **应用于所有 snapshot 写入**（含 `lookups` 为空时），因此先以空注册建的库在后续注册/重开时索引看到的是同一编码。
- **逻辑内容不变**：`ref` 身份、`schemaId`、`revision`、事件、receipt、guard、幂等 `aggregateRevisions` 全部沿用 `record.record.*`/`record.ref`，只有存储文本按 `JSON.stringify(parsed)` 规范化。
- **不重写既有库**：只在注册时 `CREATE INDEX IF NOT EXISTS`；既有行字节不动，保留旧 schema 的 canonical 快照。
- **边界记录**：既有旧 writer 本就输出 `JSON.stringify` 快照；本批不把 SQL 之外的 ad-hoc 写入当作受支持生产者（`lookup.test.ts` 的 damaged-row 用例仍按读取损坏检测为 `corrupt`）。未加表/连接/UDF/通用层。
- 上一轮 UTF-8 排序与排他 `after` 修复保留：`lookup-index.ts` 的 `compareRefKeys` 仍是 `Buffer.compare(Buffer.from(...,"utf8"))`，memory `after` 与 SQLite `COLLATE BINARY` 均未回退。
- 测试只读未动。
