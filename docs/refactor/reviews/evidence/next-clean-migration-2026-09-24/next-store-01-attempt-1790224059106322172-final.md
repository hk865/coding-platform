### 2. 实现要点

**共享 `lookup-index.ts`（契约 §3/§4/§7）**
- `createRecordLookupRegistry`：在 backend 打开数据库/建立状态**之前**校验并深拷贝注册。拒绝：非数组、空/重复名、非空串字段、无对应 record schema 的 `aggregateType`、空 `paths`、空路径段、`__proto__`/`constructor`/`prototype`、不安全路径（段仅允许 `[A-Za-z_][A-Za-z0-9_-]*`）。
- `decodeLookupRequest`：未注册 → `unsupported`；非对象/值数不符/非标量/limit 非 1..200 整数/`after` 非完整 canonical refKey 或跨 aggregateType → `invalid`。
- `lookupIndexKeyOf`/`encodeLookupValues`：dotted path 取值，缺字段→`null`，`undefined`/`null`→`null`，复合对象/数组→不可索引（返回 `null`，绝不字符串化伪装标量）；类型保留的键编码。
- `lookupMatcherOf`：把 `true/false` 与 `1/0` 分开分类，供 SQLite 谓词使用。

**Memory（契约 §4/§5/§7/§8）**
- 每注册索引一个 `buckets: valueKey→refKey 集合` + `keyByRef` 反查；lookup 直接取桶、按完整 refKey 稳定排序、`after` 排他、`limit+1` 判 `next`。**不做全量 snapshot 扫描**。
- 索引仅在 commit 写入阶段、依据已校验的 `record.parsed` 更新；`beforeWrite` 失败/guard 冲突/幂等重放都不触及索引；catch 里用 `previousLookupEntries` 原地回滚。
- 移除了 `legacyAccess`、`InMemoryLegacyRecordAccess`、`mechanics`、`nextEventSeq`、`idempotencyRecord`，以及 stale 注释；内部仍是同一 `eventLog/snapshots/idempotency/identityClaims/cursorSeq` 对象与同一 CAS 流程。
- 关闭后 `lookup` 沿用 `assertOpen` 抛错。

**SQLite（契约 §4/§5/§6/§8）**
- 每个注册索引建一个安全表达式索引：`(json_extract(ref_key,'$.aggregateType'), 每个路径的 json_type+json_extract, ref_key)`。用 `json_type` 区分布尔与 1/0，并用 `json_type`/`json_extract IS NULL` 谓词把复合对象挡在结果外。`EXPLAIN QUERY PLAN` 实测：`SEARCH snapshots USING COVERING INDEX next_lookup_... (<expr>=?... AND ref_key>?)`，即谓词与 keyset 都走索引，无全表扫描。
- lookup 只用索引查出候选 `ref_key`（≤ limit+1），随后**复用既有 `readManyInside`** 读 canonical 行；损坏行（如 ref 与 ref_key 不符、JSON 破坏）→ `corrupt`。复用唯一 `DatabaseSync` 与同一 snapshot reader，无第二条连接、无嵌套异步事务。
- 复用同一个事务内 snapshot 写入，索引由 SQLite 自动维护；打开已有库时 `CREATE INDEX IF NOT EXISTS` 自动回填（按定义派生索引名）。
- 同样移除 legacy backdoor、`mechanics`、`nextEventSeq`、`idempotencyRecord` 与 stale 注释。

### 4. 剩余限制（如实报告，未越界修复）

1. **`next-types` 无法在本 lane 变绿，原因在写范围之外。** 缺 `next/vendor/coding-agent/dist/public-api.js`（`next/vendor/coding-agent/` 只有 `package.json` + `node_modules`；父目录 `coding-platform/vendor/coding-agent/dist` 完整存在，且有 `public-api.d.ts`）。报错只落在 `next/src/core/workspace/access.ts` 与 `tests/data/workspace-capture-access.test.ts`；`access.ts(74,47)` 的 implicit any 是该 import 解析失败的连带结果。该目录只读、不在三个写文件内，无法也不应在本任务修复。**建议主 Agent 在派发前将冻结 Kernel `dist` 复制/链接到 `next/vendor/coding-agent/dist`**；已用该链接在一次性副本中复现 `tsc` 0 error。
2. **索引路径文法的解释**：按“安全 dotted JSON key”采用保守段文法 `[A-Za-z_][A-Za-z0-9_-]*`；这比 JSON 允许的键更严格，但可安全嵌入表达式索引 DDL，且现有注册均为驼峰/短横线键。
3. **复合对象语义的解释**：注册的标量路径解析为对象/数组时，该行**不进入候选索引**（memory 不入桶；SQLite 由 `json_type` 谓词排除），既不被强制转成标量，也不因此拒绝 commit。这是对“复合对象不可伪装标量”的实现选择；若主审期望改为写路径 `invalid` 拒绝，需要新的冻结测试再改。
4. **`after` 约束的解释**：要求 `after` 为该索引 `aggregateType` 的完整 canonical refKey；跨 aggregateType 的 cursor 视为 `invalid`（`lookup-ports.ts` 注释亦要求 “values/index must remain the same”）。
5. 未实现能力保持未实现：`materialRecordReaders`/`materialRecordSchemas` 等骨架未顺手填充。
