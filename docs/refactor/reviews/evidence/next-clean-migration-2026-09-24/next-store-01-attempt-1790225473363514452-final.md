## N0 Store lane 续修报告：UTF-8 字节序统一

### 1. 缺陷与修复

Lead 复现的缺陷属实：memory 的排序与排他 `after` 用 JS UTF-16 code unit 比较，会把增补平面字符（U+10000，代理对首元 D800）排在 BMP 字符（U+E000）之前；SQLite BINARY 按 UTF-8 字节序，正确顺序为 U+E000 < U+10000。冻结澄清要求两后端统一为 canonical refKey 的 **UTF-8 字节序**。

修复（仅三个在范围文件，未碰测试/schema API，未加新层）：

| 文件 | 修复点 |
| --- | --- |
| `next/src/core/record-store/lookup-index.ts` | 共享 `compareRefKeys` 改为 `Buffer.compare(Buffer.from(left,"utf8"), Buffer.from(right,"utf8"))`，注释说明为何不能用 UTF-16 code unit |
| `next/src/core/record-store/in-memory-record-store.ts` | `lookup` 排他游标由 `refKey > after` 改为 `compareRefKeys(refKey, after) > 0`；排序继续用同一个 `compareRefKeys` |
| `next/src/core/record-store/sqlite-record-store.ts` | keyset 显式写成 `ref_key COLLATE BINARY > ?` 与 `ORDER BY ref_key COLLATE BINARY ASC`，与 memory 语义对齐（默认即 BINARY，此处显式化） |

SQLite 侧用 `EXPLAIN QUERY PLAN` 复核：显式 `COLLATE BINARY` 后仍走 `SEARCH snapshots USING COVERING INDEX ... (<expr>=? AND ref_key>?)`，无退化。
