# L3a results: DSH on the middle-size move (2026-10-07)

Level L3a: move 8 WorkGraph files (TARGET-DAG M5, M7, M8, M9, M10, M12, M16, M17; five of them are renamed, M16 and M17 go to existing directories), then fix every reference. 76 files have to change: 8 moved files, 66 importer files and 2 data files. The reference move changes 114 specifiers in 70 files (3 of them inline `import('…')` types) and 7 path strings in `production-reach-allowlist.json` and `state-writes.test.ts`. L2 is a subset of L3a, and L3a is a subset of L3. The checker is `L3a/check.sh` (`check-move.mjs`): score = files right / 76, plus the gates from `ORACLE.md`.

DSH 0.1.7-rc.2, headless profile, default model **deepseek-flash** for every run. Every run went through `run-dsh.mjs` in bubblewrap, on a fresh copy made by `L3a/setup.sh`. The feedback rounds reused the same copy and the same Session (`--session-id`). Run artifacts (run.json, scan.json, events.jsonl, final.md, check JSON) are in `_results/L3awork/runs/`. The variant books and follow-ups are in `_results/L3awork/`.

## Result in one paragraph

L3a is still within DSH's reach. All 5 independent runs passed: 3 baselines, role framing and the detailed book. All 5 had score 1 (76/76 files), every gate green and 5203/5203 tests unchanged. Unlike L2, the diffs were not all identical. 3 runs (baseline-1, baseline-2, detailed book) are byte-identical to the reference move. 2 runs (baseline-3, role) left 3 specifiers inside two moved files as they were. The task book's rule 2 asks for exactly that, but the reference move does not do it, and the checker accepts both. A baseline took 3.7–4.9 minutes and 1.7–2.8M tokens (96% cache reads, 33–40k output). Compared with L2, that is 2.2× the files for 1.6× the time and 2.9× the tokens. In every run the first draft of DSH's bulk edit (its helper script, or an inline Node command) had a bug, a different one each time. DSH caught every one of them itself, with its own dry-run listing, a grep or the typecheck, before it finished. Role framing again made it much slower. The detailed book was a little cheaper than the baseline mean but still inside the baseline spread, and DSH ignored one of its explicit rules. A guided review round moved the tree to the book's literal rule and found 9 comment lines nobody had listed. Raw check output got a four-section "no discrepancy".

## Spread across the three baselines

- **Outcome: no spread in score.** 3/3 pass, score 1, the same 76 files, all gates green.
- **Diff: a split on one rule.** Baselines 1 and 2 are byte-identical to each other and to the reference move (sha256 `267b6988…`; 114 specifiers in 70 files). Baseline-3 differs in 3 lines in 2 files (`9b7273e7…`; 111 in 69). ## What DSH did well

- **It followed the spec where the spec was clear.** The diffs contain only specifier text and the 7 path strings. No reformatting, no comment or title edits, no shims, no `docs/` change and no re-serialized JSON. `decodeRun` stayed in `run-state-service.ts`. All 3 inline `import('…')` types, the `vi.mock` arguments and the double-quoted importers were handled in the end.
- **It resolved paths instead of matching text.** The same-directory traps were handled in all 5 runs: `./contracts.js` changes in `configuration/`, `materials/`, `sessions/` and `communication/` but stays in `tasks/` and `evidence/`. The moved `execution-history-contracts.ts` needs `./contracts.js` → `../tasks/contracts.js`. The moved `message-record-codecs.ts` needs `./contracts.js` → `../model/communication-contracts.js`, although `sessions/` now has no `contracts.ts` of its own. The same-basename file `src/core/agent-runtime/execution-history-contracts.ts` was left alone.
- **Its own checks were a reliable safety net.** In 5/5 runs, a dry-run listing, a grep or the typecheck caught the bug in the first draft before the run finished. The book's checks give a location (`file(line,col): error TS…`), and DSH used it directly.
- **Its reports were mostly true and useful.** The CHECKS sections match what the checker measured. The UNSPECIFIED sections found the comments that still name old paths, 7–9 lines depending on the run. Baseline-2 and the role run also explained the same-basename file.

## Where it went wrong

- **The rule-2 split, mostly unreported.** 3 of 5 independent runs rewrote the 3 still-resolving specifiers (baseline-1, baseline-2, detailed book), and 2 kept them (baseline-3, role). Only the role run said so in its report: "left as-is per the 'specifiers that still resolve to the same file must stay' rule". Baseline-2's reasoning even claims the opposite of its diff. It thought "I didn't, which is correct per 'Specifiers that still resolve to the same file must stay as they are'", then wrote in the same thought that the two `evidence-coverage.ts` imports were "changed to `./...`", and its tree has all three changed.
- **Detailed book: an explicit rule overridden, and a false claim.** Step 6 of its book says: "A specifier that still resolves to the same file as before stays exactly as it is, in moved and in unmoved files". Its first script was an under-reach: it changed only specifiers whose target moved, and so it missed the required `./contracts.js` → `../tasks/contracts.js` in the moved `execution-history-contracts.ts`. Its dry run showed 110 changes, and it read the book's approximate hint as confirmation: "Good sign that 110 is the right magic number. Let me trust 110." When it found the gap, it recomputed every specifier in the moved files, which also rewrote the 3 it was told to keep. The report does not mention this. Its NOTES also say "Helper scripts/logs … were created only in the working directory", but it had written `/tmp/nope` and then deleted it ("Let me clean up my accidental /tmp write").
- **Role run: missed inline `import()` types, then slow.** Its AST walker had no `ImportTypeNode` case. The typecheck stopped it with 3 × TS2307 (`src/app/attention-observer.ts:440`, `src/app/host.ts:946`, `communication/mailbox-service.ts:1540`). It added a `--repair` mode and reported the miss honestly. It also had the dry-run over-reach of baselines 1 and 3. After its edit it ran the vitest command three times. Its UNSPECIFIED says "No test title names an old path (searched all `tests/**/*.ts`)". Yet `tests/state/verification-machine.test.ts:970` names `coverage.ts:96-101`, which 3 of the other 4 runs listed. The claim holds only if a bare file name does not count as a path.
- **Incomplete "nothing else" lists.** Baselines 1 and 3 and the role run missed the comment `state/verification-machine.ts:838` (`coverage.ts:76-121`), because they searched only directory-qualified paths. No independent run found the 8 bare `contracts.ts:<lines>` comments in `state/message-machine.ts`; the guided round did.
- **Scope letter vs sandbox.** Every session used `/tmp`. One run used a git command outside the allowed list. One report made a false claim about where scratch files went.

## A conflict between the book and the reference (for the lead, before task D)

Rule 2 of the book says that a specifier inside a moved file that still resolves to the same file stays as it is. The reference move (`oracle/wg-move.mjs`, and so `data/expected.json`) instead rewrites every specifier in a moved file to the `path.relative` spelling. Here that means `'../tasks/plan-task-basis.js'` becomes `'./plan-task-basis.js'` inside `tasks/`. The checker normalizes specifiers by the file they resolve to, so it accepts both, and only `exactAsReference` differs (76 vs 74). DSH split 3:2 on it, and an explicit sentence in the detailed book did not settle it. For task D, pick one rule and state it with an example. The rule that matches what most runs did on their own, and what the reference does, is: "inside a moved file, write every relative specifier as `path.relative` gives it from the new directory; in every other file, change only specifiers that named a moved file." Keep the second half in any case. In 3/5 runs (baseline-1, baseline-3, role), DSH's first draft also canonicalized unrelated non-canonical specifiers (`../../core/workspace/…`), and that rule is what made each of them narrow the script.

## Feedback rounds: (a) raw and (b) guided

As at L2, no run failed, so both rounds were reviews of passing work in the same Session. Neither shows how DSH repairs a failure the checker finds. The only real failures at this level were mid-run, and DSH's own check commands caught all of them (role: 3 × TS2307 with file:line; baseline-3: TS1110 syntax errors). Those error lines are effectively raw feedback with a location, and DSH fixed the cause each time.

- **(a) raw, on baseline-2.** The follow-up was the `visible-check.mjs` output alone: two exit 0s, then vitest with 73 files and 4286 tests, 8 failing. DSH answered in 8 s with no tool call and 83k tokens. This time it kept the four sections, with "The externally run checks match the results in my report exactly; no discrepancy". The tree stayed byte-identical. It did not use the chance to re-examine anything; the rule-2 lines it had silently changed stayed unreported.
- **(b) guided, on baseline-1.** The follow-up was written like a lead's review with three points, each a location plus a line of thought, with no answer and no verdict:
  1. The 3 specifiers at `tasks/evidence-coverage.ts:26-27` and `sessions/message-record-codecs.ts:30`: "resolve each OLD specifier from the file's NEW directory… read the last sentence of rule 2 … and the spelling sentence at the end of rule 1. Decide whether the book tells you to change these three … or leaves it open, and name the sentence you rely on."
  2. Comments that name a moved file by file name alone, with a line reference.
  3. Its guess about the hint's "about 80 files": support it with git numbers or drop it.

  The review also said: change a file only if the book requires it, and name the rule. DSH took 131 s, 11 tool calls and 0.88M tokens, mostly because it re-ran all three checks after editing. It restored the 3 specifiers, citing rule 2 verbatim. It found `verification-machine.ts:838` plus 8 bare `contracts.ts:<lines>` comments in `message-machine.ts` (checked: line 58 there says "communication/contracts.ts:36-145", and the later lines are the same file). It dropped the guess: "the hint's file count is not reproducible from `git` in this copy". The re-check passed: 76/76, now 74 exact as reference, the same diff as baseline-3 and the role run.
- **Comparison.** Raw output on passing work produces a confirmation and nothing else, cheap at 83k tokens. The guided review produced the most complete UNSPECIFIED list of the level, and a change that follows the book's literal text. It also shows how strongly a review steers DSH: it treats a pointed question as a reason to edit. Here that edit was right by the book, but against the reference. A lead's review must therefore be right itself, and should say whether an edit is wanted.

## Lessons for writing tasks for DSH

1. **A fully specified mechanical edit of 76 files is still within reach of the plain smoke-shaped book.** It passed 3/3 with no help in about 4–5 min and about 2.4M tokens. Do not add role framing (+84% time again) or step lists (no gain, and the rules in them were still broken).
2. **Make every rule consistent with the reference and with DSH's natural algorithm, or the runs split.** The one place where the book's literal rule and the reference disagreed split 3:2, and was reported only once. Before handing a book over, run the reference move against the book's own rules. Where a rule has to go against what DSH would naturally compute, state it with an example from the actual files, and have the checker report that rule separately.
3. **Keep "change only specifiers that named a moved file; leave every other specifier as it is" in the book.** In 3/5 runs the first draft canonicalized unrelated specifiers, and that sentence is what made DSH narrow its script. At L2 the same slip happened in the role run.
4. **Require a dry-run listing before applying, and the typecheck after.** Every first draft had a bug: over-reach, under-reach, quote stripping, a missed `import()` type or a shell-quoting slip. Every one was caught by DSH's own listing, grep or typecheck. That self-check, not the first draft, is what makes it reliable. Say "print the full list of planned changes and compare its count with N before writing anything".
5. **Give exact numbers, or none.** The approximate hint ("about 110 … about 80 files") became a target. One run trusted a wrong count of 110 for a while because it matched. Several runs spent thought on the "80". Give the exact counts the reference produces, as numbers to compare with, and the test numbers (73 files and 4286 tests, 8 failing).
6. **Name the allowed scratch place, and expect `/tmp` anyway.** All 6 sessions that used tools touched `/tmp`, even with "never in `/tmp`" in the book. Either allow it explicitly ("helper files under /tmp are fine and not part of the change") or run in a sandbox, as here. List forbidden git commands as well as allowed ones (`git checkout`/`restore`/`stash` were not named, and one run used `git checkout`).
7. **Verify every "nothing else" and "only in X" claim.** One false claim (detailed book) and one doubtful one (role) this level, after one at L2. The missed comments and the silent rule-2 edits show that the report is not a complete list of what DSH did. Check with `git diff` and a cheap grep on the lead's side.
8. **Follow-ups: a lead's review with location + line of thought + "edit only if the book requires it, name the rule".** That fixed all three points at the cost of a short run. Expect DSH to act on a pointed question, so the review must be right. Raw check output on passing work only yields "no discrepancy".
9. **For task D:** run L3 with the plain book plus lessons 2–6: one stated rule for specifiers inside moved files, the "leave every other specifier" sentence, a dry run before writing, exact counts, and explicit rules for scratch files and git. Raise `--max-tokens` above the 10M default or use the batched L3. Keep guided review rounds ready.
