# L4 results: DSH implements the D-2 fold to a frozen interface (2026-10-07)

Level L4: implement the body of `finalizeRoundOutcome` (the D-2 fold, `src/core/work-graph/state/verification-machine.ts`, a pure 79-line function) from its frozen signature and types, the spec rows quoted verbatim (VR-07, VD-4, D-2) and an output contract that fixes every code, text and order. It must reuse `foldSteps` and keep the pure-directory rules. It must also write its own tests in `tests/state/finalize-round-outcome.test.ts`. Setup replaces the body with `throw new Error('not implemented')`, removes its 16-line JSDoc and removes `tests/state/verification-machine.test.ts` (149 tests). The checker is `L4/check.sh` (`check-hidden.mjs`). Score = passed / 15 hidden target tests. The gates are typecheck, architecture, scope, the other 134 hidden tests, and own tests that are at least 8, pass on the agent's code and on the real code, and of which at least 8 fail on the stub. `ownTests.mutantScore` is reported and not gated: it counts how many of 5 one-line bugs of the real fold the own tests kill: OM1 VD-4 dropped, OM2 a stale source does not override a decision, OM3 uncovered gaps placed before the step gaps, OM4 the last PASS admitted instead of the first, OM5 blockers in walk order.

DSH 0.1.7-rc.2, headless profile, default model **deepseek-flash** for every run. Every run went through `run-dsh.mjs` in bubblewrap, on a fresh copy made by `L4/setup.sh`, with the default limits (20 min, 10M tokens). Feedback rounds used the same copy and Session (`--session-id`). Run artifacts (run.json, scan.json, events.jsonl, final.md, git-status.txt, check JSON) are in `_results/L4work/runs/`. ## Result in one paragraph

L4 is well within flash's reach. All 7 tool-using runs ended with verdict **pass** and score 1 (15/15 hidden targets, 134/134 other hidden tests, 40/40 visible targets, every gate). That is 3 baselines, the role run, the detailed book, and baseline-3 before and after its feedback rounds. In each of the 5 first runs, DSH wrote the body in **one edit**, and that edit passed typecheck, the architecture check and the 30 visible tests at once. No run needed a second try on the function. A run took 3.0–4.5 minutes and 0.7–3.0M tokens. The spread was in the own tests, not in the code. The mutant scores were 1, 1 and 0.8 for the baselines, 0.6 for the role run and 1 for the detailed book. Both weak test files missed a case that the book's own case list did not name ("INCONCLUSIVE where a gap is the only reason", VD-4), and the role run also never put step gaps and uncovered gaps in one case. A guided review naming the test lines, the contract clause and a "which input would make it fail?" question fixed baseline-3 in 46 s. Its mutant score went from 0.8 to 1, and it touched nothing else. The raw check output answered "Confirmed" in 4 s and changed nothing. The detailed book (files to read with line ranges and excerpts, a numbered step list with "until it passes", and a 14-case test list) gave the best run: mutant score 1, the fewest steps, and **0.71M tokens, less than half of any other first run**. The role preamble was the cheapest of the plain-book runs (1.56M, 183 s) but wrote the weakest tests.

## Where it went wrong

- **Own tests that skip a case the book did not name.** baseline-3 never isolated the gap clause (OM1). The role run missed OM1 too, and also split the gap order into two cases that never meet. One case has step gaps only ("lists missing, pending and interrupted gaps in walk order"), and the other has uncovered and context gaps only ("appends the uncovered requirements and then the context gaps"). So putting the uncovered gaps first (OM3) passes all 11. The book said "the gap order", and the run tested each half of it. Both misses are cases that the plain book's checklist leaves implicit. Every case the checklist names was covered in every run.
- **The spec/contract tension went unnamed in 3/5 first runs.** baseline-1: "no discrepancies found between the specification and the implemented behaviour". Role: "the spec was implementable literally". Detailed: "no contract contradiction was found". The behaviour was correct in all five, because each followed the contract. Only the report differs.
- **Small process slips.** baseline-2 made a `/tmp` backup that its report did not mention ("No other file was created, edited, or deleted"), and typed a wrong path once (`dsw-work`). baseline-3 and the guided round printed `EXIT=$?` after `npm run typecheck 2>&1 | tail -5`, which reports tail's status, not the command's. baseline-1, baseline-2 and the role run used `${PIPESTATUS[0]}` correctly. The exit codes they reported were still right. The guided round claimed its new cases kill a gap-ignoring fold without running one. The claim is true, but it is reasoning, not a check.
- **Reading more than needed.** The plain book says "Everything you need is in this copy" and quotes the spec. The baselines still read the evidence service, the R3e fixture, the work-graph tests and (2/3) the spec. That was harmless, but it is where the tokens went (1.8–3.0M against 0.71M for the detailed book).

## Lessons for writing tasks for DSH

1. **A frozen interface plus an exact output contract is DSH's sweet spot.** It covered signature, types, the spec rows quoted verbatim, and every code, text and order. With that, flash implemented a 79-line pure fold correctly in 5/5 independent runs, each with a single edit, in 3–4.5 minutes. The user's view ("good executor for very clear tasks") holds, and L4 is not the upper limit. The next information is at L5, L5b and L6.
2. **DSH tests exactly the case list it is given; anything beyond it is hit or miss.** The baselines covered every named case in every run. The two unnamed ones (a gap as the only reason, step gaps and uncovered gaps in one case) were missed in 1/3 baselines and in the role run. When a rule is an "or" of several conditions, ask for one case per condition in which it is the only reason. When a rule is an order of several parts, ask for one case that contains all the parts. Ask for whole-value assertions. That one sentence ("assert whole values") was followed in every run that wrote tests (6/6).
3. **"Read only these files, with line ranges, plus short excerpts" halves the cost and loses nothing.** 0.71M against 1.56–3.03M tokens, at equal quality. The plain book's "Everything you need is in this copy" invites a tour of the repository. Tokens grow with steps × context, so a narrow reading list cuts both. For task D, list the move table, the files to read, and nothing else.
4. **Spell out the self-checks you want, and say how to do them without scratch files.** The detailed book's step 7 (insert and remove one `throw` line; no backup anywhere; no `/tmp`) was done cleanly. baseline-2 invented the same check with a `/tmp` backup. Steps such as "run the checks first and expect N failed" and "the final `git status` shows exactly these two lines" were followed literally and cost nothing.
5. **A follow-up must point.** A guided review names the location (line numbers), the rule or clause, and a "which input would make it fail?" question, and fences the edit scope. It fixed the weakness in 46 s and touched nothing else. Raw check output on green checks gets "Confirmed" in 4 s, every time (L2, L3a, L3, L4). For the lead: weak tests can be found without a mutant run by checking each "or" clause for a case where it stands alone.
6. **If you want conflicts surfaced, ask for them explicitly.** For example: "compare the quoted spec rows with the output contract and list every sentence where they disagree". 3/5 runs wrote "no discrepancy" even though their own UNSPECIFIED list contained one. Read NOTES as "nothing blocked me", not as "the spec is consistent".
7. **Role framing is not a lever for quality.** It was cheaper this time, but the tests were weaker, and it never helped at L2 or L3a. Spend the words on a case list and a reading list instead.
8. **Consistency:** flash's unevenness at L4 shows in the test design and the report, never in the code. Repeat runs gave the same correct behaviour by three different routes. If a task's quality depends on what DSH chooses to test or flag, write that choice into the book.
