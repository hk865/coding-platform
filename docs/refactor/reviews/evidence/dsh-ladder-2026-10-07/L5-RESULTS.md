# L5 results: DSH writes the `roundChainHead` tests from a 14-case list (2026-10-07)

Level L5 tests fidelity: DSH must turn a 14-case list into exactly one test file, `tests/state/round-chain-head.test.ts`. The list gives every situation and every expected value in words, including the exact `reason` strings. DSH must use six frozen fixture helpers (`tests/ladder/round-chain-fixture.ts`) and assert whole values. The code under test is `roundChainHead` (`src/core/work-graph/state/verification-machine.ts:525-566`, VD-14), which is correct and frozen. Setup removes `tests/state/verification-machine.test.ts`, adds the fixture and seals the history.

The checker is `L5/check.sh` (`check-mutants.mjs`). It works in a throwaway clone. Its gates: only the one file added, no commit or tag move, no skip/todo/only/fails/skipIf/snapshot, 14 tests all passing on the real code, at least 14 `expect(` calls, and the sanity mutant S0 killed. The score is mutants killed / 8: MU1 runId ignored, MU2 ordinal 0 accepted, MU3 duplicate ordinal unnoticed, MU4 loop off by one, MU5 root with a predecessor accepted, MU6 predecessor compared without roundId, MU7 clean-PASS predecessor accepted, MU8 head = first round. The oracle predicted that L5 would saturate: only MU2 and MU3 need the exact reasons.

All runs used DSH 0.1.7-rc.2, the headless profile and the default model **deepseek-flash**. Every run went through `run-dsh.mjs` in bubblewrap, on a fresh copy made by `L5/setup.sh`, with the default limits (20 min, 10M tokens). Feedback rounds used the same copy and Session (`--session-id`). The run artifacts are in `_results/L5work/runs/`: run.json, scan.json, events.jsonl, final.md, git-status.txt, the check JSON, and each run's test file. Also in `_results/L5work/` are the two variant books (`task-role.md`, `task-detailed.md`), the two follow-ups (`feedback-raw-base3.md`, `feedback-guided-base3.md`), the summaries (`runs-summary.txt`, `checks-summary.txt`) and the helper scripts. The kept copy is `~/dsh-work/ladder/L5-detail-1`; its diff is `L5/best.diff`.

## Result in one paragraph

L5 saturates, as the oracle predicted. All 5 first runs passed with score 1 and every gate: 3 baselines, the role run and the detailed book. Each killed 8/8 mutants, with per-mutant pass counts identical to the reference file (MU1 13/14, MU2 13/14, MU3 12/14, MU4 5/14, MU5–MU7 13/14, MU8 12/14). After normalising whitespace, line wrapping, the gap object's text and the explicit default `'run-1'`, **the 14 test bodies are identical across all 5 runs**: same inputs, same helpers, same whole `toEqual` values, every reason string character for character. Only the titles, the header comment and the gap literal differ. Each run wrote the file in **one `write`**, and the first vitest run printed `Tests 14 passed (14)`. No run iterated, and no run touched anything else. A run took 23–40 s and 0.08–0.32M tokens, about a tenth of an L4 run. The detailed book (reading list with line ranges, a step list) was the cheapest: 84k tokens and 5 tool calls against 232–321k and 11–12, and 23 s against 32–40 s. The role preamble changed nothing measurable. The only real weakness at this level was the UNSPECIFIED list in the reports. Each first run listed a different sample of 6–8 true items, out of 15 that exist. A guided review gave a method (walk each `return`, each side of each `||`/`??`, each loop that can return on its first pass) and the function's line range. With that, baseline-3's list went from 6 to 17 true lines, with correct line numbers. The round took 70 s and 0 tool calls, and the test file was untouched. The raw check output got "Confirmed" in 3 s and changed nothing.

## What DSH did well

- **Perfect transcription, 5/5.** Every run built each case exactly as worded. `r1` was finalized before `successor(r1, …)` where the case says "finalized FAIL". The input order was `[r3, r1, r2]` and `[r1, r2, r2b]`. `withChain(chainRoot('r1'), { ordinal: 0 })` and `withChain(chainRoot('r1'), { predecessorRoundRef: roundRef('r0') })` were used where the case says "a chain root with …", and `successor(g1, 'g2', { runId: 'run-2' })` for case 14. Every run asserted the whole value with the same round objects it passed in, and copied all 9 reason strings (8 distinct) exactly. No run added a test, a `beforeEach`, shared state or a conditional, and none used `toStrictEqual` or `toBe`.
- **Right the first time.** One `write` and one green vitest run in every first run. There was nothing to iterate on, so the detailed book's "if a case fails, fix the INPUT … never change an expected value" never fired (its report: "all 14 cases passed on the first run, so no input needed adjusting").
- **Discipline.** All 5 first runs stayed in scope, used no `/tmp`, ran no git command except `status`, and made only true CHECKS claims. This is the cleanest level so far. At L2, L3a and L3 every run used `/tmp`, and at L4 1/5 did.
- **The UNSPECIFIED lines are true.** 33 of the 35 lines in the first runs name a real uncovered behaviour, and the other 2 are half redundant, not false. No run invented behaviour or tested an unspecified case. Each confirmed it had added no test for them.
- **It acts on a pointed review and stays inside the fence.** The guided round did exactly what was asked, with zero tool calls: it worked from the function it had already read, kept every line of the file, and named its scope ("the book's 'No other tests' and 'Do not touch … `src/`' require no change").

## Where it went wrong

- **Incomplete, varying UNSPECIFIED lists.** This is the only weakness, and it is in the report, not the tests. With the plain instruction ("each case … this list does not cover that you noticed"), each run produced a 6–8 item sample of 15 true items. The 5 first runs together found 13, and each one alone found at most 8. Baseline-3 missed "no round with ordinal 1", which 4 other runs found. Only the guided round found N (precedence of several violations) and O (reasons for k > 2). The role run alone found M among the first runs.
- **Two half-redundant lines** (role, detailed-book; see above). They cite the covering case themselves, so they are imprecise, not false.
- **Reading more than needed (plain book).** Every plain-book run read the whole 1,750-line source file and a sample test file, although the book quotes the function's contract and fixes the style. That reading is where the tokens went (fresh input about 31k and context about 25–30k per step, against 14.7k fresh for the detailed book). It is harmless, and at this size it is cheap in absolute terms.
- Nothing else. No false claims, no scope slips and no process errors in any run.

## Feedback rounds: (a) raw and (b) guided, on the same state

No run failed a gate or lost a mutant, so there was no test failure to feed back. The comparison therefore uses the one real weakness: baseline-3's 6-line UNSPECIFIED list. To give both rounds exactly the same starting point, I first copied the baseline-3 copy and its private DSH state (`_runs/_state/L5-base-3`) aside. I then ran the raw round, restored both, and ran the guided round. Each round is the only follow-up its Session saw. The saved state was deleted afterwards.

- **(a) raw:** the follow-up was the `visible-check.mjs` output alone (`Tests 14 passed (14)`). DSH answered in 3 s, with 0 tool calls and 40k tokens: "Confirmed — the task book's check reproduces on my copy … nothing else was created or edited." It dropped the four-section format, and the tree was byte-identical afterwards. This matches L2, L3a, L3 and L4: green check output carries no signal, so DSH changes nothing, every time.
- **(b) guided:** the same output plus a lead's review in two points, with no answer given. Point 1 said what was weak (the UNSPECIFIED list, "your list has 6 lines, and walking the function shows more"). It said where (`verification-machine.ts` lines 525–565). It gave the line of thought: go through each `return`, each side of each `||` and `??`, and each loop that can return on its first pass, and name the case numbers that reach each one; then ask, for each reason text, which input decides what goes into it. Point 2 fenced the scope: edit no file, and name the book sentence if a change seems needed. DSH reasoned for one step (about 15k output tokens) without opening a file. It enumerated R1–R12 ("R2: line 530 another-subject — case 14. R3: line 537 invalid ordinal — case 13 …"), then the operand sides ("Line 536 left operand `!Number.isSafeInteger(ordinal)` … case 13 only reaches the `ordinal < 1` operand"), and replied with all four sections. **17 lines, all true; every cited line number is right** (529, 536/537, 541–543, 548/550, 556/557, 559/560). It changed no file. The re-check gave pass with 8/8 and an identical tree. Cost: 70 s, 55k tokens.
- **Comparison:** as at L3 and L4, only the pointed review changes anything. What made it work here was the **method**, not the location alone. The review did not list a single missing item; it named the way to enumerate them, and DSH applied that method completely. The raw round cannot help, because nothing visible is wrong.

## Lessons for writing tasks for DSH

1. **A case list with every expected value is transcribed perfectly and consistently.** 5/5 independent runs gave the same 14 test bodies, all whole-value, all exact strings, killing 8/8 mutants. No run added, skipped or reinterpreted a case. When DSH writes tests from a precise list, the tests are exactly as good as the list. The quality of the tests is the lead's job (the case list), and the transcription can be trusted. L5 is not the upper limit; the information is at L5b (expected values derived from the code) and L6.
2. **Test-writing from a list is cheap.** It took 23–40 s and 0.08–0.32M tokens, about a tenth of L4, because the work is one `write` and one check. Splitting is pointless at this size.
3. **A reading list with line ranges cuts cost again (3–4× fewer tokens, about 35% less time) at equal quality.** This is the third level showing it (L4, L5). "Everything you need is in this copy" makes flash read the whole source file and a style sample even when the book quotes the contract and fixes the style. For task D, list exactly what to read.
4. **"List what is unspecified" gives a varying sample, not a complete list.** The runs found 6–8 of 15 true items each, a different subset every time, and 2 items common to all three baselines. If you need a complete list (for task D: every comment or title that names a moved file, every specifier left unchanged), **write the enumeration method into the book**. For example: "walk each `return`, each side of each `||`/`??`, each loop that can return on its first pass, and name the case that reaches it", or for a move, "for every file name in the table, run `git grep -n <name>` and account for every hit". When DSH was given a method, it applied it completely and accurately in one step.
5. **A follow-up must point, and the best pointer is a method plus a location.** Raw green output gets "Confirmed" (3 s, no change) at every level so far. The guided review gave no answer, only a place, a way to enumerate and a scope fence. It turned a 6-line report into a 17-line exact one, with the test file untouched, in 70 s. A lead can write such a review without a mutant run: read the function's branches against the case list.
6. **Role framing: no effect here** (same cost, same tests, shortest report). Spend the words on a reading list, a case list and an enumeration method instead.
7. **Consistency:** flash's unevenness at L5 shows only in what it chooses to report (which uncovered cases it notices), never in the transcription. The same holds at L4. Anything whose completeness matters must be specified, with a method, in the book.
