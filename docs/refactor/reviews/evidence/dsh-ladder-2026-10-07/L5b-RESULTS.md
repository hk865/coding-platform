# L5b results: DSH writes the `roundChainHead` tests from case situations only (2026-10-07)

Level L5b tests judgement and code lookup when DSH writes tests. The task is the same one test file as L5, `tests/state/round-chain-head.test.ts`, with the same 14 cases in the same order. This time the book gives only the **situations**. It states the contract in words and says that the reason texts are built in the function's code from the round ids and ordinals, and that the first failing check decides. It gives no expected values and no reason strings. DSH has to read or run `roundChainHead` (`src/core/work-graph/state/verification-machine.ts:525-565`, 41 lines, 8 refusal texts behind 7 checks in a fixed order), find each exact result, and assert the whole value, including the exact `reason` string. Setup, fixture, checker and mutants are L5's. MU2 (ordinal 0 accepted) and MU3 (duplicate ordinal unnoticed) still return `invalid`, but with a different reason, so only an exact reason string kills them. Those two show whether DSH derived the reasons exactly.

All runs used DSH 0.1.7-rc.2, the headless profile and the default model **deepseek-flash**, through `run-dsh.mjs` in bubblewrap, each on a fresh copy made by `L5b/setup.sh`, with the default limits (20 min, 10M tokens). Feedback rounds used the same copy and the same Session (`--session-id`). Run artifacts are in `_results/L5bwork/runs/`: run.json, scan.json, events.jsonl, final.md, git-status.txt, the check JSON, and each run's test file. `_results/L5bwork/` also holds the variant books (`task-detailed.md`, `task-role.md`), the two follow-ups (`feedback-raw-base2.md`, `feedback-guided-base2.md`), the summaries (`runs-summary.txt`, `checks-summary.txt`), the helper scripts, and `norm.cjs`, which compares test bodies across runs.

## Result in one paragraph

L5b saturates too. All 5 first runs passed with score 1 and every gate: 3 baselines, the detailed book and the role run. Each killed 8/8 mutants, with per-mutant pass counts identical to the reference (MU1 13/14, MU2 13/14, MU3 12/14, MU4 5/14, MU5–MU7 13/14, MU8 12/14). Every run derived all 8 distinct reason strings exactly, so MU2 and MU3 died in every run. `norm.cjs` normalises comments, titles, whitespace, trailing commas, the gap literal and the explicit `'run-1'` default. After that, **the 14 test bodies are identical across all 5 L5b runs, and identical to the bodies of the L5 runs, whose book gave every expected value** (one hash, `657841864dfc`, for 5 L5b and 3 L5 files). Every run found the values the same way. It read the function, traced each of the 14 cases by hand in its reasoning, check by check, before writing a line. Then it wrote the file in one `write`, and its single vitest run printed `Tests 14 passed (14)`. No run executed the function to discover a value, and none copied a received value from a failing test. Deriving the values cost almost nothing. Against L5, the baselines took the same wall time (32–40 s), +7% total tokens and +11% output tokens. The detailed book (a reading list with line ranges, a hand-trace step, self-checks) was again the cheapest: 98k tokens, 7 tool calls and 28 s, against 249–322k, 10–13 and 32–40 s. The role preamble changed nothing measurable. The only weakness was again the UNSPECIFIED list: each run named 5–9 of the 15 uncovered behaviours, a different sample each time. A guided review that gave a method and a line range raised baseline-2's list from 5 items to 10. All 11 lines were true, and every line number was right. That took 34 s and 0 tool calls, and left the file untouched. It was not complete, though, and it dropped one true item from DSH's own first list. The raw check output changed nothing (4 s).

## What DSH did well

- **Exact derivation, 5/5.** Every run turned "the first failing check decides" and the template literals into the exact strings, including the traps. Case 7 gives "no round with ordinal **2**", although the round carries ordinal 3, because the loop runs only to `rounds.length`. Case 6 takes the `ordinal === 1` branch ("are both chain roots", not "share ordinal 1"). Case 8 names `r2` before `r2b`, case 14 names `g2` before `g1`, and case 13 prints the ordinal as `0`. Every run traced these in its reasoning before writing; the green first vitest run confirmed the traces, it did not produce them.
- **Same tests as the fully specified book.** The test bodies are byte-identical after normalisation to L5's, where every value was given. For a pure 41-line function with a fixed check order, "situations + contract in words + read the code" gave the same tests as a complete case list. It also cost the same: +7% tokens and +11% output against the L5 baselines.
- **Transcription of the situations, 5/5.** Every run built each case exactly as worded: `finalized(chainRoot('r1'), 'FAIL')` before `successor(r1, …)`, `successor(r1, 'r2', { ordinal: 3 })`, `successor(r1, 'r2', { predecessorRoundRef: roundRef('r0') })`, `withChain(chainRoot('r1'), { ordinal: 0 })` and `withChain(chainRoot('r1'), { predecessorRoundRef: roundRef('r0') })`, `successor(g1, 'g2', { runId: 'run-2' })`, and the input orders `[r3, r1, r2]` and `[r1, r2, r2b]`. All runs asserted whole values with the same round objects they passed in. None used `toStrictEqual`, `toBe`, `expect.any` or a regex, and none added a test, a `beforeEach` or shared state.
- **Discipline.** Every run stayed in scope, used no `/tmp`, ran no git command that changes anything, and made only true CHECKS claims.
- **It acts on a pointed review and stays inside the fence.** The guided round worked from memory with zero tool calls. It quoted the function body with correct line numbers (525–565) in its reasoning, kept the file byte-identical, and answered in the four sections.

## Where it went wrong

- **Incomplete, varying UNSPECIFIED lists.** As at L5, this is the only real weakness, and it lies in the report, not the tests. Each run found 5–9 of 15 items, a different subset each time. Baseline-2, the shortest list, missed B, E, F, H, I, K, L, M, N and O.
- **One wrong example.** Baseline-3's "names 1 and 4 with n = 2" (footnote ⁴).
- **One format slip.** The detailed book's report packed its UNSPECIFIED items into one semicolon-separated paragraph, although the book says "one line each". The plain book's runs all used one line per item.
- **The guided round lost an item.** It rebuilt the list from its walk of the function, and baseline-2's own true item D ("a missing ordinal at a position other than the end") did not come back.
- **Reading more than needed (plain book).** Every plain-book run, and the role run, read the whole 1,747-line source file and a sample test, although the book quotes the contract and fixes the style. Baseline-1 and the role run also read `package.json`, and the role run read `vitest.config.ts` as well. That reading is where the tokens go: about 31k fresh input and 211–281k cache reads per run, against 15k and 76k for the detailed book.

## Lessons for writing tasks for DSH

1. **For a small pure function, flash derives exact expected values from the code as reliably as it transcribes given ones.** All 5 runs found all 14 whole values and all 8 reason strings exactly. That includes the template traps: the loop bound, the ordinal-1 branch, argument order in the text, and the first failing check. Their tests are identical to the ones written from a complete case list. The cost is nearly the same (+7% tokens). So for task-D-like work, the lead need not precompute every expected value or string when the code is in the copy and deterministic. "Situations + contract in words + 'the first failing check decides; the texts are in the code'" was enough here. The measured scope is a 41-line function with 7 ordered checks; L6 tests a larger one.
2. **flash traced by hand; it did not probe.** Every run wrote all 14 assertions from a reasoning trace before running anything, and was green on the first run. No run executed the function to read off a value. A "never copy a received value" rule costs nothing to include (the detailed book's never fired), and it matters when a first run fails. Then the failure is either a wrong input or a wrong trace, and copying the output would hide a wrong input.
3. **A reading list with line ranges cuts cost again.** It used 3× fewer tokens and about 20% less time, at equal quality. That is the third level to show it (L4, L5, L5b). Without it, every run reads the whole 1,747-line source file plus a sample test, and some also read `package.json` and `vitest.config.ts`. List exactly what to read, by range.
4. **"List what is unspecified" gives a varying sample, not a complete list,** at L5b as at L5. Each run found 5–9 of 15 items; A and G were common to all three baselines, as at L5. If completeness matters (for task D: every comment or title that names a moved file, every specifier left unchanged), put the enumeration method into the book and ask for the enumeration itself, one line per item with its location, rather than a summary.
5. **A follow-up must point. A method plus a location helps, but it does not guarantee completeness.** Raw green output gives no change (4 s), now at six levels. The same guided review that reached 15/15 at L5 reached 10/15 here, and dropped a true item from DSH's own first list. Every one of its lines was true and every line number right, so its claims can be trusted, but not its silences. The lead must still check "nothing else" against their own list.
6. **Role framing: no effect** on the tests or the cost. Its report was at the top of the baseline spread, but at L5 the role report was at the bottom. Spend the words on a reading list, the contract and an enumeration method.
7. **Consistency:** there was none to measure in the work product. 5/5 identical tests, and identical to L5's 5. The run-to-run unevenness of flash shows only in what it chooses to report, as at L4 and L5. Specify, with a method, anything whose completeness you depend on. Check formatting rules ("one line each") on the lead's side; the detailed run broke one.
8. **Upper limit:** L5b is not it. Test writing from situations, with lookup in a short function, is fully within flash's reach. The information now lies at L6 (implementing a 94-line owner-service write from a spec plus whatever the repository holds).
