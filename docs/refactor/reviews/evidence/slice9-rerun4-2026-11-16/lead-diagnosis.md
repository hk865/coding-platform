## 原因

**1. 检查不按任务挑选（E05 正式目标）。** 种子目标的 README 检查套到了正式目标的 `t-users` 上，每轮都失败。返工没有新依据，平台在 00:08 拒绝返工（`no_new_basis`）。
- 这个停止只在界面上显示为任务的“需要你决定”（`src/ui/adapters/goals.ts:185`），决定队列里没有卡片。驱动只答卡片，所以一直等到超时。
- 平台侧：`check.taskIds` 只做校验，不用来挑检查（修复包 G7P-1）。
- 驱动侧：遇到要人决定的停止，应当提前结束等待（G7W-3）。
- E06 依赖 E05 留下的线，因此整行没有跑。

**2. 规划轮交表时没有按完整计划校验（E08、E12 的第二个目标）。** 两次都要到采用时才被拒。
- E08：改需求时沿用原义务编号，却改了它的验收要求。
- E12：新目标的计划缺目标关口。
- 修法：交表时就按合并后的完整计划校验，问题当场退回秘书，在同一轮改好（G7P-2，同 97-3 的思路）。

**3. 单个 Run 看护路径登记等待后不处理队列，漏掉唤醒（intervention、C-221、B06）。**
- 三处一样：任务做完、检查跑完，平台发现没有审阅线就自己开一条（这一步对），目标随后进入 `no_review_line` 等待，账本此后再无事件。
- 等待是要“会话或消息有变动”才会被叫醒，可开线这个变动发生在登记等待之前。
- 主路径登记后会处理一遍队列（`src/app/collaboration-driver.ts:1155-1162`），能补上这种提前发生的变动。看护路径只登记、不处理（`:1272-1283`），于是标记了却没人取。
- E05 的种子目标没卡住，是因为同项目还有别的任务在提交，顺带叫醒了它（G7W-1）。

**4. 发给线的系统轮次每步等一次心跳（全部场景）。**
- 审阅、顾问、开执行线这类轮次，只由 Host 心跳里的 `consumeIdle` 推进（`src/app/host.ts:2985`，心跳循环 `:3830-3862`）。`planOnIdleLine`（`src/business/workflow/intervention.ts:451-520`）每次只走一步。
- 实测（e05、int、iter 共 7 轮）：提交到领取 116–118 秒，领取到准备 117–119 秒，加上消息到提交的一拍，每轮约 6 分钟空等。
- 心跳设计值是 60 秒，实测接近两倍，原因待查（G7W-2）。

**5. 秘书给改代码的任务挂了只读见证（C-216）。**
- 计划里 `t1-remove` 是普通工作任务，它的必需义务却带 `witness` 要求（`requiredReadPaths` 为 store.js 和测试）。
- 见证检查要求 Run 不改任何文件，否则判 FAIL（`src/core/work-graph/state/witness-check.ts:37-41`），所以每次返工必然失败，最后 `no_new_basis`。
- 顾问提的新方案也没去掉这一项。
- 提示词写明 witness 只用于探索（只读）任务，计划校验没有拦住（G7P-3）。

**6. 驱动手写的计划还是 CPL 之前的写法（waiting）。** 一条必需义务覆盖两个任务，却只有一条验收要求，`plans/propose` 按现行规则拒了（`empty_verification_requirements`）。这是驱动的问题（G7W-4）。
