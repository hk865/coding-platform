# Structure round night 1, part P5 (S3 / D3a: the 31 tool descriptions)

Your part is `P5`: `./.lead-ref/parts/P5.diff` and `P5-files.txt` (the 31 files `resources/prompts/platform/tools/*.json`
and the ten tool modules in `src/core/agent-runtime/`); base `./.lead-ref/base/`. The shared whiteboard pin schema's
descriptions are the `toolSchema.whiteboardPin.*` keys of `resources/prompts/platform/strings.json` (in the tree). The
book §5.1 rulings 5 and 6; the inventory `inv-d3.out.md` rows 30–44; DSH's reply `replies/s85-reply-S3.md` §4.3 (the
table tool → base location) and §5.2 (its probes are lost).

**Look hardest at:**

- **Each of the 31 tools:** the description in its JSON file equals the base text byte for byte (where the base built
  it from parts, for example the six `Session mailbox: <name>` strings or the three user-decision tools, the file
  holds the final expanded text); every parameter description equals the base `.describe(…)` argument byte for byte;
  every `.describe(…)` of the base that the tool's input schema has is now read from the pack (none left as a literal,
  none dropped, none added).
- **Parameter keys** (ruling 6): paths from the tool's input object, fields joined by `.`, an array element as `[]`,
  an object's own description at the object's path, a description after `.optional()` at the same path. A schema
  shared by several tools (`whiteboard-tools.ts:195–243` of the base) has its descriptions in `strings.json` under a
  key named for the schema, not in a tool file.
- **Only the string argument changed:** the Zod chains, field order, optionality, defaults, validation, refinements
  and `toJSONSchema()` output are the same; the tool names, the registration order and the definition order are the
  same; no tool gained or lost a field.
- **Lookups:** every key the code reads exists in the pack (does a wrong key fail the typecheck through the generated
  literal types, or give `undefined` to `.describe` at run time?); every key in the 31 files is read by some code.
- **Timing and sharing:** a description read at module load vs at definition time — does any tool now read its text
  at a different time, or share one object between definitions where the base built a new one each time (and could a
  caller mutate it)?
