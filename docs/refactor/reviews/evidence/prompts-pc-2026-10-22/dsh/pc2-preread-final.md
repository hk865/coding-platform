## 2. Unclear

1. **Read/cache model.** Does preparation read user packs synchronously (renderer is sync) or asynchronously before assembly, and cache by pack id + mtime/digest? Smallest options: async read once per preparation, no cache; or `readFileSync` + a per-pack cache keyed by directory mtime. The spec’s “每次都按当时的包解析” forbids a stale process-wide cache but not per-preparation caching.
2. **PC-1 dependency.** `packId`, `sectionOrder` and `base` are part of `PromptSetV1` (§2), which PC-1 builds. PC-2 cannot record them before that type/manifest slot exists. Smallest split: PC-1 owns `PromptSetV1` + `base` injection + body freezing; PC-2 passes `packId`/`resolved pack` into it. Confirm that PC-2 may add `sectionOrder` to `ContextAssemblyBindingV1` independently.
3. **`base`’s “four cases”.** The spec lists `read`; source-only; no read; “有、没有 edit、shell”. That is three read states plus an edit/shell pair, i.e. ambiguous between four and six renderings. Smallest option: three read blocks, with independent `{{#tool:edit}}` and `{{#tool:shell}}` blocks; confirm whether `write` also appears.
4. **Final tool list at preparation.** P9 requires rejection during preparation, but the true list includes review-source substitution and extension names known only at start (`observed-model-run.ts:275–283`, after prepare). Options: (i) compute a planned list in preparation from `manifest.permissions.tools` + `selectWorkToolGroup` and recheck at start; (ii) move the check to entry admission (then PE8 is not “through preparation”); (iii) check only `mentionsTools ⊆ permissions.tools ∪ builtins`.
5. **`sectionOrder` coverage.** `PromptSetV1.sectionOrder` is keyed by every `ContextCallKindV1`, but only `work`/`continuation`/`handoff` (work-input), `planning` and `copy` have templates. What should `review`, `secretary`, `attention` record? Smallest: omit them (`Partial`), and for `work` derive from work-input with `unknown_call_review` only when legal.
6. **History detection.** Because P8’s reminder is inside the prepared `input`, preparation must read the completed boundary itself; today that read is at start. For ordinary Query runs `assembleQueryContext` has no signal at all. Smallest: read `completedBoundary` in preparation (Work and Query) and record a boolean in the binding/manifest; note the prepare→start boundary race is benign because the Session is not running.
7. **`extends` chains.** Only “new pack inherits platform” is stated. Smallest: allow `extends` only `"platform"`; reject other ids/cycles. Confirm `packId` character rules.
