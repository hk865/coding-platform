## 每个失败的根因和归属

### E05（连带 E06）

- **根因。**
  - 种子请求是“检查用 node --test。只改 README.md。”。冷启动时秘书把只属于这次请求的 `readme-tail`、`file-set`（整个工作区恰好 5 个文件）写成了 `taskIds: "all"`，采用后装成了项目级的已批准检查清单。
  - E05 的任务要新增 `test/*.test.js`，`file-set` 每轮必然 FAIL。执行者拒绝为了过检查删测试，这是对的。返工没有新改动，平台按规则判 `no_new_basis`，判得也对。
- **归属。**
  - 触发是模型：违反了提示词里已有的规则（`initial-planning-answer.txt:17`、`skill-platform-secretary.txt:19`、MVP-BEHAVIOR:159）。
  - 停死在平台：
    - 已批准清单里的单条检查谁都撤不掉（G8B-1b 的裁定，`host-settings.ts:1488-1491`）；
    - 整批替换要一份一字不差的已保存回答；新计划带同名检查算冲突；界面没有入口；
    - 偏差消息和停止卡都不点名哪条检查没过。参谋撞了 7 次 `look_graph`，最后用只读命令直接读 `.git/workbench` 下的 `ledger.sqlite` 才找到。
  - 驱动把停因记到了 overlap 上，记错了。其实重叠已经发生过：两个 Run 在不同 Session 上重叠约 63 秒。
- **E06。** 它接 E05 的项目（`e06.mjs:58`）。就算驱动放它去接，项目里那条 `"all"` 的 `file-set` 还在，E06 新增文件一样过不去。所以 E06 跟着 E05 的平台修正走。
- **已知还是新：**
  - 已知：STATUS:107“没有能操作的卡”现在已部分不成立：卡和按钮都在，只是治不了根因。
  - 新：单条检查撤不掉；偏差消息不写失败检查；只读沙箱能读平台自己的库（要 lead 确认）。

### E09

- **根因。**
  - 秘书写的 `static-api-exports` 是 `node -e "…new RegExp('export\\s+…')…"`：bash 在双引号里把 `\\` 吃成 `\`，JS 再把 `'\s'` 读成 `s`，所以永远报缺 export。诊断在运行目录文件的副本上复现了，结果和四轮报告一字不差。
  - 返工输入只给检查名和报告摘要（`continuation-brief-render.ts:646-649`）；参谋的偏差轮只有“stop cause: no_new_basis”；没有工具能读检查报告。
  - 两个执行者从 JSON 里抄了一份多一层反斜杠的命令，复跑得到“exports ok”，一行没改。`no_new_basis` 照规则停下。参谋猜错原因，换上的新检查犯了同样的转义错（也复现了）。
- **归属。**
  - 触发是模型：写坏了检查，秘书一次，参谋又一次。
  - 变成死局在平台：检查输出进不了返工输入和偏差轮。E09F 只补了审阅那一半。
  - 驱动有两处：
    - executor-reports 的 fail 是记账错位，它的判法根本没跑到；真跑到了，`/parseDate/` 又会把 B 那条“A 还没落地”的 notify 误判成 pass；
    - 7 张候选卡和 goal_cause 卡都没有选项，驱动跳过，2 分钟后结束。这次采用了也救不回来，因为新检查也是坏的。
- **场景前提不稳。** 秘书开工前就用 `parseDateParts` 消掉了冲突（符合决定 49），“执行时发现冲突、执行者上报”这一格就没有机会发生。
- **新发现：** 检查输出到不了返工者和参谋；executor-reports 记账错位。
