## Rules (by case, with an example from this repository)

1. **Scope and authority.** Check the caller's project and workspace before reading any record: another workspace is `forbidden`, a missing record in the same workspace is `not_found`. The actor, the duties, the operator and the request id never come from the model's or the browser's JSON. The operator is the exact configured `operatorActor` and not any member of `PLATFORM_AUTOMATION_ACTORS` (`src/contracts/task-requeue.ts:49`); without a configured operator the new user write entries return `unsupported`.
2. **One request, one current candidate.** The first candidate of a request, its replacement, its adoption and its abandonment change the candidate records, their events and the unique claim `s5-request-candidate:…` in one commit (`UniqueClaimChange`, `src/core/record-store/ports.ts:85`); candidates of other requests get zero writes; “stale” is derived from `basedOn` against the active pointer, never written. Do not read “the” pending candidate with `findPendingProposal` (`src/core/work-graph/tasks/plan-readers.ts:476`): it returns one candidate per Goal.
3. **Answer, change, record are three facts.** Answering never changes a Plan or a Task; a change done by its owner but not yet recorded keeps the card in “answered, pending application”; recording an application reads the original receipt and event (`lookupCommit` then `eventAt`, as `src/core/work-graph/persistence/graph-repository.ts:94` `readCreatedGoal` does) and never trusts a caller's “current version” or “PASS”. The acknowledgement ref is attribution, not authority.
4. **Paused and cancelled Goals.** A paused Goal's card can be answered; its application waits for “continue” and may move to the current Goal revision only when the captured content basis is field-by-field equal to the current Goal (spec §2.8, `goalDecisionBasisMatches`); only the captured and the current content are compared, so content changed and changed back during the pause counts as equal (SS15), and no Goal event history is read. A cancelled Goal's cards are read-only, its candidates closed, and an answer never revives it.
5. **Waiting for a predecessor.** `waitForGoalRef` stores the predecessor chosen at answer time; the predecessor's completion or cancellation releases the wait; every entry that starts changing work (claim, entry, new continuation, small task, action dispatch) checks it and adds the read versions as guards to its commit (SS08, SS13, SS16). Conflict hints are never a gate, and running work is never stopped by a new setting.
6. **Accepted parallel risk.** Identified by the unordered Goal pair plus both full Plan refs; stored on the later Goal at answer time; reordering keeps it; a change of either Plan pointer ends it; `null` is “no plan”, not a wildcard.
7. **Footprint.** A planned module and an executed file are compared only after the file is mapped to a module by the adopted catalog's paths (longest segment match); equal names alone are not a match; unknown or unavailable executed files make the result “possibly incomplete”, never “no conflict” (GS11–GS13). In this slice executed files come only from `tasks/executed-files-stub.ts` (`not_available`).
8. **Notice positions.** A notice is ordered by the commit that created its source (the `since` binding of spec §2.5), not by the last acknowledgement, not by wall clock and not by key; `markNoticesSeen` moves only the categories and positions that the display token says were really returned, and never changes a message's status, response or application (NR02–NR06).
9. **Automatic rework notices.** System and agent requeues share the existing Run-chain count (`src/core/work-graph/state/task-failure.ts:446` `nextRequeueAutoCount`); a reverification is read from the whole round chain (`src/core/work-graph/state/verification-machine.ts:479` `roundChainHead`), one notice per automatic successor round; human requeues are not listed; the cap, no-progress and human-stop fences do not change (NR01, NR07, NR08).
10. **Answer text.** The free text and the annotations are stored exactly (no trim) in the response body as `canonicalJson(UserDecisionBodyV1)`; the input supplied to the asking Run is `'用户答复\n' + canonicalJson(body)` once, with the original `inputId` and the existing `acceptedInputs` (TU04, TU05).
11. **Protected fields.** Only `state/` constructors write the protected fields of spec §2.7; `state/` imports only `src/contracts/` and uses no clock, random number or crypto. The HMAC of the display token lives in `views/notice-display-token.ts`, not in `state/`.
12. **Receipts.** Replay is looked up before any new business read and returns the original event's value and cursor, even if the Goal was later cancelled, the sender archived or the message answered (`src/core/work-graph/communication/mailbox-service.ts:1235` `replayMessage`); the same identity with different content is `idempotency_conflict`; a new identity never overwrites an answered slot.
13. **Old data.** A record without the new fields decodes and returns exactly its old public shape; defaults are applied only by the new readers (`readGoalSettings`, the effective workspace settings); the `since` origin never leaks into an old port's result or receipt (UM12, RC09, RC11). Do not backfill.
14. **No initial-adoption proofs** (§0.2 L1): `recordDecisionApplication` for a change to the architecture catalog or the completion policy returns `unsupported`; the goal-cause card for a missing initial architecture or completion policy still appears with its adopt actions (DQ03).
15. **Card options.** A conflict card has exactly the three options of spec §4.3 (`wait`, `order`, `parallel`, with the labels given there) and its answer records a `conflict_*` selection; goal-cause, candidate and planning-question cards have `options: []` and are answered with free text and annotations only (`other`, `requiresApplication: true`); their buttons are the card `actions` (spec §4.1, the paragraph after the type block).
16. **Workflow gates.** Under `every_step` the Workflow returns the decision cause instead of running an automatic requeue or reverify (WF01); `orderGoalAdvances` orders by `Goal.settings.order`, then Goal key, then flow/task id, and changes nothing (WF02).
