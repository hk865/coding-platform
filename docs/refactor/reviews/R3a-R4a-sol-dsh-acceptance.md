日期：2026-09-24。状态：**R3a / R4a 本批修复通过独立验收，已合入当前工作树；未提交。**

本轮按用户要求实际使用 GPT‑6 Sol 补骨架及独立契约测试，主 Agent 审阅并冻结，再用本地 dsh 的两个独立 Session 并行实现。执行环境、文件清单与可调用检查见 [DSH-EXECUTION-HARNESS](../DSH-EXECUTION-HARNESS.md)。之前[9 月 23 日的失败报告](R3a-R4a-independent-acceptance.md)保留当时事实，本页记录其后续修复。

## 实现范围

- R3a：RecordStore 两后端在事务内解码并核对实际存储身份 / schema / revision；合法幂等重放顺序不变。WorkGraph 命令、Host 请求及旧 raw batch 无法被独立复制时在异步读取 / 写入前拒绝，不回退到调用者原对象。真实 RAT-03 库副本经新 GoalTaskPort 重放原 Goal@1、追加新提交及重启，原证据库字节不变。
- R4a：唯一 Core Turn 选择算法服务公共执行身份重试与内部恢复；新执行保存实际生效的预算、工作区 / 进程限制与宿主工具授权。恢复核对原约束、配置、工作区；旧已结束记录继续可读，无法证明原限制的旧执行恢复明确拒绝。checkpoint 带新字段时须与原 Turn 一致，不可理解的候选回退至其他快照或正式事件。
- Sol 在现有 sandbox 增加读取实际有效值的 getter；SQLite/Memory 共用已有 codec 的 guard helper。没有新增 DataEngine、第二套状态归约或独立事务系统。目标五模块 / 八边未改；仍有旧模块等待后续迁移。

## 独立检查暴露并处理的问题

1. 一个早期沙箱测试未创建受限文件，可能以 ENOENT 假装权限拒绝；主 Agent 修正前提后重新得到真实 RED。
2. 两个既有 core 夹具用非法 Goal@0 测试“合法版本 0”。Sol 保留缺失与 0 的区分，新增 Goal@0 corrupt 断言，并用合法 Project@0 验证真实 0；没有放宽 schema。
3. dsh 报告范围外 raw batch 同类克隆 fallback；Sol 先补可复现的调用后篡改目标 / 正文测试，主 Agent 再精确增加一个可写实现文件。
4. R4a 原 10 项全绿后，独立源码审阅仍发现 paused 配置 / 工作区检查遗漏和未知版本 checkpoint 被采用。补测试复现为 14 项中 3 RED，再返修。
5. 后续 14 项全绿仍不够：dsh 为避免 Session SQLite 自身写入污染 revision，跳过 paused revision 检查。主 Agent 拒绝该放宽，Sol 补 strict 模式普通文件变化 / 内置数据库正常恢复 / 数据库同目录普通文件变化三项对照。最终方案只精确排除已配置数据库及 SQLite sidecar，恢复原版本检查。

这些用例和契约由测试方维护；实现方能够读取和执行，操作系统不允许它修改。文件哈希、初始失败和中途全绿记录均保留，不能把最后通过倒写成一开始就正确。

## 边界与后续

- 这是当前 R3a Goal 子集与 R4a Kernel 公开扩展的修复；不是全部源码迁移完成，也不代表平台连续 Session、资源范围并行或 UI 已接通。R2e.1 仍按其独立验收推进。

- 所有修复保留在当前工作树；不提交、不推送，不覆盖用户已有无关改动。最终结果由主 Agent 独立检查决定。
