**用户决定（续前一节的 1–19）。** 讨论全文在 lead 临时目录的 `DISCUSSION-2026-10-05.md`，要点已写在下面各条里。

20. **图由 agent 们在约束下共同维护。**
    - 图的内容由各 agent 在约束下共同维护。WorkGraph 是唯一写入通道：版本、校验，状态迁移只走 `work-graph/state/`。
    - 执行状态（Task、Run 的状态和原因）只能由状态机按证据改，摘要和记忆不能改。
    - 书记是审查型维护者：核对语义与代码、历史是否一致，合并去重，标过时，提修订。原书记 Skill 说的“不成为另一个任务图的 owner”，指的是不另建第二张图或存储，与本条不冲突。用户：“事实如此”。
21. **语义层修补随工作进行。**
    - 在那里工作的 agent 顺手提交语义修补，作为工作结果的一部分，和代码改动一起检查、一起生效，范围限于本次足迹。
    - 平台机械发现可能过时的地方（声明的依赖与 import 不符、新文件没归组、文件移动），在准备执行时提醒。
    - 小改随工作生效；结构改动（增删模块、改依赖规则）进「需要你决定」，界线按自治级别。
    - 架构目录修订入口（A.2 之后接线）按“从工作结果进入”来接。
    - 用户说以前提过这一点；仓库和本机对话记录里没找到书面原话，按 10-05 决定补记。
22. **agent 用图要简单，复杂性在内部。**
    - agent 不用调用就能带上：任务卡、足迹节点的语义与注记（有上限）、顺手看的提醒。
    - 两张图通用三个工具：
      - 看：节点或路径 → 卡片，可下钻；
      - 找：文字或路径 → 节点；
      - 记：节点 + 文字。平台补来源、版本、类型，返回收下 / 待审 / 拒绝及原因；冲突时只问“取代还是并存”。
    - 与决定 18 是同一件事。
23. **记忆核心进 MVP。**
    - 进 MVP 的：节点注记、目标与阶段上的“当前理解”、大小上限、按代码版本失效，随编排后端一起做。用户的理由：它们涉及两张图的语义层，以及编排的进入、维护、决策和生命周期。
    - MVP 之后：检索排序调优、关键词搜索、真实 bug 效果评估。更后：长期知识库、经验积累 Skill。
    - 行为写在 [MVP-BEHAVIOR](../MVP-BEHAVIOR.md) B09“交接与归档时的当前理解”。
    - 设计要点（lead 与用户讨论的结果，未定稿，进下一阶段计划）：
      - 语义层是锚点，记忆挂在锚点上；
      - 事实用指针，且指向固定版本；理解写成文字。用户纠正：只用指针，会指向互相矛盾的节点，逻辑也连不起来；
      - 任务图不另建记忆：过去的节点本身就是记忆，缺的是压缩，以及目标和阶段上的当前理解。

25. **时间视图（轨道）的画法。** 用户认可：“其它的都很好”。
    - **一条轨道 = 一条工作线**：一个 Session，加上它被中断后接续它的 Session；不是角色，也不是“成员”。
      - 按角色（默认）/ 模块 / 任务分组。
      - 长期角色（秘书、参谋、书记、模块维护）通常一两条线。
      - 执行者等短期线在组内压缩：互不重叠的共用一行，行数等于最多同时有几条。收起的组画成一行并发强度。
      - 只读咨询副本画在被问的那条线上。
    - **已归档的线**默认隐藏，底部一行“已归档 n 条”，点开显示。
    - **排序**：置顶 → 需要关注（需要你决定 > 失败 > 受阻 > 待核对）→ 最近活动。用户选的是“需要关注优先”。
      - 打开视图，或换范围、筛选、置顶时排一次；看的时候不跳。顺序过时时显示“顺序已变 · 重新排序”。
      - 按阶段分组时保持计划顺序。
    - **滚动**：轨道可滚动，时间轴和日历固定在上面，名字固定在左边。
      - 这段时间没有活动的线折成一行。
      - 可按名字、角色、模块筛选，可只看需要关注的，有归档开关。
      - 主画面右栏最多 8 行，另有“整页查看”。
      - 正式实现只渲染看得见的行。
    - **时间窗**：今天 / 本周 / 全部保留。跨度超过 14 天时，日历换成年历式（一列一周，一格一天）；点一天放大到那天，再点一小时放大到那小时，有路径退回。
    - 背景：“成员”只是推导出来的投影，Session 才是工作实体。执行者短期、并行，长期的只有秘书、参谋、书记和模块维护。规模上，任务上千、Session 上万不难，其中大多数已归档。
26. **任务图整页 = DAG + 大纲 + 轨道。**
    - **DAG 是默认视图**：上面是起点，最下面是目标验收。
      - 一条线表示下面的任务需要上面任务的某个产出，不是“等上面整个任务完成”，也不是领取条件。
      - 没有连线不等于可以放心并行：两个任务改同一个文件的风险，在详情里提示。
      - 其他元素：
        - 关键路径开关；
        - 底部“未排定”带，放没有依赖、也没有验收条件的未来意图；
        - 已取消、已替代的任务只计数；
        - 600 个任务时按阶段折成框。
    - **点一个任务**：看它在当前架构里涉及哪些节点（计划要改 / 实际改过），以及有哪些工作线参与过。
    - **时间竖条**可拖动：DAG 显示那一刻各任务的状态，右栏列出那时在进行的任务。真实回放需要后端提供“按时间读取任务状态”的接口。
    - **大纲**保留语义分组（目标 → 阶段 → 任务）。用户：“语义分组也是可以的，可以保留在树/大纲其一”。
    - 本条替换决定 16、17 和 UI-WORKBENCH §0 里“任务图画成目标 → 阶段 → 任务的方格树”的整页画法。方格的外观（不放符号，状态用颜色和填充表示）不变；方格树留作主画面的缩略（决定 28）。
27. **还没开始的任务一律空心（10-06）。**
    - 待执行：灰色虚线框；可领取：蓝框；未来意图：稍粗的灰框。
    - 所有画板的任务方格都改；阶段、目标这些组方格不变。
    - 用户的理由：深灰半填格在深色底上，高亮和不高亮分不清，“因此需要你来给颜色”。所以颜色由 lead 定，每种状态在高亮、变暗、深浅两种主题下都要分得清。
28. **主画面右栏的任务图是缩略（10-06）。**
    - DAG 像完整架构图一样，放在整页上看全景。
    - 主画面右栏用方格树做缩略：一次最多显示 3 层，点一个节点就在它下面再展开 3 层，可以拖动。
    - 放不下时，像架构图的聚焦视图那样，只显示树或图的一部分，完整的到整页；也可以按阶段一个框。
    - 用户：“你的理解没错。实在不行可以像架构图那样，只展示树/部分图，完整的到完整页面”。

33. **点工作线，中间切到它的对话（10-06）。** 用户看第 14 版时问：“为什么我点击左边的那些角色的卡片，我不能够直接跳转到他那边的对话？然后我也发现不了他那边的对话可以被我进行交互。” 原因是原型沿用了旧的“点成员卡片原地展开”，入口藏在展开后的小按钮里，而且只有两条工作线画了自己的页面。这也漏做了 [UI-WORKBENCH §1](../UI-WORKBENCH.md) 第 2 条早已定下的“中心可切到指定 Agent 对话”。用户选了“中间切到它的对话”：

34. **先删再拆；编排、记忆、生命周期的设计现在开始（10-06，用户：“我同意”）。** 用户问：接下来本来就要做编排，任务 D 的拆分还有没有必要？是不是该先删减，只留下有用的？编排、记忆、生命周期管理的设计是不是也该开始了？lead 的建议，用户同意：
    - **拆分仍做。** 拆分理顺的是核心服务之间方向反了的依赖：9 个子目录互相依赖，持久层反过来依赖任务层。编排建在这些服务上面，不替换它们。缠在一起的任务、通信、查询都是有用的核心服务，删减解决不了。
    - **先删再拆。** 把收尾“是否有意义”审查里的“有用”一项提前到简化阶段：从生产入口走不到、也不对应 MVP 行为的代码先删，再拆。

      - MVP 必需但还没接线的照旧保留，例如角色规格、架构目录修订。

    - **设计从 10-06 晚开始，和本批并行，只写文档。**

## 1. 用户要什么

用户认为项目应以数据结构和算法为核心：当前/历史Session与当前/历史文件提供数据；架构图、任务图和Agent工作关联组织检索与编排；原子工具维护结构并查询、比较、生成和更改；业务组合工具决定如何推进。工具结果反向维护图与状态，本来就是用户方案的一部分。

重构目的：消除重复扫描、重复材料准备、重复状态和绕行；保持连续工作与真实状态，改善可读性、代码量和UI。不是为模块数更少而合并，也不是把所有业务交给一个主Agent。独立图/数据组件可以有自己的正式结构，不天然变成第二权威；同一正式事实的修改路径需要一致。

具体工作由Session承载，Role/Skill是可复用配置。同一Session不能被执行和维护同时修改，不同Session可并行。状态类型可循环，执行事件向前追加；明确采用的产物消费前置DAG、目标模块DAG、源码观测图和通信图分别表达；预期依赖不是自动启动门槛。

架构图还必须能找到正在工作或待命未归档的 Session/角色，便于咨询与继续相关工作；任务图保留承担过工作的 Session/Run 与来源。归档只退出当前活跃发现，不删除模块、任务或历史。现有 SessionRecord/SessionWorkLink 是首选承载，用户未要求新增永久 Agent 主体。working/standby 的展示来自当前占用及真实执行/健康事实，不能因为有 active/busy 字段就声称模型已经启动，也不能把 Task 完成与 Session 归档绑定。

用户已经授权工程细化，不需要再次询问是否采用这些基本方向。遇到真实的新产品范围或无法由既定要求决定的取舍，才提出具体方案；普通文件划分、接口命名、必要索引和文档同步由实现者承担。

## 7. 无需重新讨论的边界

- 普通查询、精确文件读取、历史读取不要求LLM、Run或baseline。
- 图是数据与索引基础；不同专用结构可以分别持久化，业务不手工同步各张表。
- 图上的 Agent 关联必须可写、可维护、可发现；运行/待命未归档者可作为咨询候选，归档后仍保留历史。关联是职责/熟悉度线索，不是锁或执行授权。
- 业务决定做什么；核心负责合法性、版本、幂等、原子更新和有界查询。
- 生命周期策略归 Workflow/角色工具；正式状态与关联归 WorkGraph；物理执行/控制归 AgentRuntime/Kernel。没有独立 AgentLifecycle 顶层模块不意味着这些职责可以消失，也不需要新增中间总管。
- Kernel拥有模型循环、原始Session日志和恢复机制；平台保存自己的映射、运行技术记录与工作状态。
- 创建Session不启动模型，先有映射再领取；领取与已领取继续入口互斥，不能重复占用。
- 模型执行返回/进程退出与Task完成分开；缺失、失败、过期检查不能被其他PASS遮盖。
- 维护操作与Run/QueryRun占同一个Session独占槽；未知副作用先核对，不盲目启动第二执行者。
- 长期知识/专家积累保留接口；有限记忆按既定范围补实现与消费者，不凭 RoleSpec、接口或历史代码声明 next 已有完整 Memory/知识库。
