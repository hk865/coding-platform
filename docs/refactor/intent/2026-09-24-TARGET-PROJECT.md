- 实际代码一直在 `coding-platform/` 原 Git 仓中迁移。`src/core/workspace/`、`record-store/`、`work-graph/` 已有实现；不是空白重写，也尚未形成一个独立目标工程。

- 已通过的 Goal、Workspace、材料与 Kernel 行为验证仍是可复用证据；移入新工程后必须重新核对依赖和接线，不能原封不动宣称新工程已验收。

## 3. 后续工程原则

1. 先建立独立目标工程的五模块代码骨架、契约、独立构建与测试入口，再派发后续功能实现。沿用已定模块和接口设计，不重新发明产品架构。
2. 旧工程作为行为、必要算法、数据格式和回归用例的参考；目标生产代码不得通过 import、路径别名、符号链接或注入旧服务继续依赖旧业务模块。共享 Kernel 可作为明确的版本化依赖，不因此被误算为旧业务模块。
3. 优先迁入已验收且符合目标边界的代码；兼容旧数据格式可以保留在目标存储边界，但兼容读取不等于继续调用旧 Ledger/Index。不把整棵旧源码复制为目标工程。
4. 独立性验证在隔离副本中进行：不提供旧业务源码，目标编译、契约与相关真实集成仍可运行；禁止真的移动或破坏用户当前旧目录来做实验。
5. 继续采用 Sol 骨架/测试 → 主审冻结 → dsh 按独立范围并行填充 → 主审的方式。dsh 对旧代码和冻结测试只读，只写目标实现。
6. 每批分别记录目标功能、依赖独立性、旧消费者切换状态。目标内部重复代码当批清理；旧产品可以作为参考保留至切换，但不得把新旧总代码量当作新产品复杂度。目标源码、过渡适配、旧源码、测试分开统计。
7. 后续 R 编号保留能力归属，修改派发位置和前置验收；不继续以“先接回旧系统再长出新模块”为默认路径。产品、原话、架构与模块契约仍共同约束迁入行为。
