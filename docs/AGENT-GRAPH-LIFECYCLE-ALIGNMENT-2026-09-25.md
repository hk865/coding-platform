## 1. 本次对齐结论

### 1.1 已经明确，不应反复重新讨论的方向

1. **双图是 Agent 工作环境，不只是图算法或 UI。** 架构图同时支持 Agent 索引与事实索引；任务图是可编辑白板、状态监控、协作与执行历史定位入口。[S1 §7.2；S2 §5]
2. **架构区域要能关联 Agent、角色、Session 与事实来源。** 正在工作和待命未归档的 Agent 参与当前发现；归档不删除模块和历史。[S2 §4.6、§5.1–5.3；S4]
3. **AgentLifecycle 必须落地。** 不能以“先让一次模型执行跑通”为由，长期搁置身份、装配、状态、图关联、咨询与恢复。[S3 第 03 段 A3/U1]
4. **组织行为主要由角色的 Skill/Prompt 与工具调用承担。** 秘书、参谋、书记/状态整理者及协调职责不需要硬编码成多个新系统，也不要求每条消息串行经过所有角色。[S1 §7.6、§7.7.1、§7.10；S4]
5. **确定信息沿现有结构定位与更新，语义问题才交模型。** 不重复扫描全部 Session，不复制历史库，不让模型重复确认机器已经掌握的事实。[S1 §7.2、§7.8；S4、S5]
6. **现有 Kernel 负责真实执行、历史与它实际支持的恢复/控制。** 平台保留桥接、关联与正式状态责任，不重写 Kernel。[S3 第 02、04、06 段]
7. **相关工作允许复用；无关工作不默认继承整段历史。** 可依据两张图判断工作连续性。模板复用、Session 复用与长期专家身份不是同一件事。[S3 第 01、09、14 段；S2 §4.5]
8. **知识库和长期领域专家不虚报为已有。** 保留接入接口与经验积累方案；完整知识库产品、自动学习闭环不因本文被追加为当前交付。[S3 第 14 段；S1 §7.8]

## 3. 双图必须向 Agent 提供什么

### 3.1 架构图的两个侧面

**结构与事实侧**回答：模块是什么、职责与接口是什么、相关目录/文件在哪里、有哪些依赖、哪些关系尚未解析、当前代码与约定有什么差异、依据来自哪个版本。

**Agent 与协作侧**回答：哪个 Agent 正在或最近在此工作、它的角色是什么、当前能否咨询、相关 Session/Run 在哪里、没有活跃 Agent 时能沿什么历史继续调查。

这两侧可以由同一个查询能力组合输出；不意味着新增两套图或两份权威数据。持久关联由现有记录承载，查询索引按真实访问模式维护。

最小查询结果应覆盖以下信息类别，优先映射已有字段而不是照表新造实体：

| 查询对象 | 必要信息类别 |
| --- | --- |
| 模块 | 稳定引用、职责/接口、路径映射、局部依赖、来源版本与未知项 |
| 关联 Agent | Agent 引用、Role 引用、关联的含义、生命周期状态、Session 引用 |
| 咨询可用性 | 是否有活动 Run、是否需恢复、是否归档/暂停、可用的消息或咨询操作 |
| 历史依据 | 相关 Task/Run、历史区间或文件版本、更新时间/适用性 |

**关联不是锁，也不自动授予权限。** 负责模块、熟悉模块、执行当前任务、获准修改资源是不同概念。不得自动把“一模块一个 Agent”写成唯一基数；一个 Agent 可以关联相关区域，一个模块也可能有执行者、维护者与审查者。

### 3.2 任务图不能退化成 Todo

任务图除任务、依赖与状态外，还要能定位：交付责任人、相关模块、当前/历史 Agent/Session/Run、输入与结果引用、正在等待谁、向哪里请求材料，以及哪些是提案、哪些已生效。

任务依赖与通信关系分别表达。依赖子图可保持 DAG，咨询可以往返。未确认的依赖是未知，不是无依赖；但不要求模型在执行前证明一切潜在并行冲突均不存在。[S1 §7.2.5；S4]

### 3.3 避免两种相反的偏移

不能把图做成纯展示，也不能把所有检索都强迫绕过图。已有引用就定向读取；查文件内容可直接用读取/搜索工具；语义问题才咨询相应 Agent。图的价值是降低定位成本，不是增加每次操作的必经层。

## 4. 谁管理：语义决策、确定性更新、实际执行分开

### 4.1 结论

**不需要先增加“图与生命周期之间的中间模块”。需要补齐的是现有模块之间的操作协议与职责映射。**

- 角色 Agent 根据 Skill 和双图工具提出组织决策：问谁、派谁、是否拆分、是否相关到足以复用、哪些分歧要调查或升级。
- 图/状态的所有者执行确定性规则：建立关联、校验当前状态、提交状态转换、刷新索引、保留历史。
- Runtime/Kernel 执行真正的模型调用、消息送入、暂停/取消、恢复与压缩，并如实报告结果。

因此，“图不替代编排决策”不等于“图工具不能管理关联”；“生命周期需要管理”也不等于“每次状态变化都要调用模型”。

### 4.2 映射到当前五模块的建议

以下是**工程归属建议**，须与当前模块文档和允许依赖核对后采纳；不是恢复旧 13 模块。

| 当前模块 | 承接职责 | 不应承担 |
| --- | --- | --- |
| **WorkGraph** | Agent/Role/Session/Task/Module 的正式关联与查询；生命周期状态的正式写操作；图索引更新；任务/通信/完成事实的受理 | 自行发明语义规划、直接驱动模型、另存完整 Kernel 历史 |
| **AgentRuntime** | Role 与工具/Skill/材料引用装配；执行准入与 Kernel 适配；消息实际送入 Session；控制与恢复；把真实观察回传正式状态 owner | 自行成为任务/Agent/图事实的第二 owner，暗自决定全局计划 |
| **Workflow** | 组织流程与被授权的正式调度；调用秘书/参谋/书记等角色策略；执行已明确的等待/唤醒/派发规则 | 复制图状态、重写 Kernel、把所有语义决策硬编码，或反过来用模型处理每个机械事件 |
| **WorkspaceTools** | 文件/代码/产物操作与观测；架构来源、差异、确定性检查 | Agent 身份或生命周期权威 |
| **RecordStore** | 复用持久化、事务、CAS、幂等及实际所需索引 | 业务选人、角色策略、语义上的生命周期判断 |

旧名称的职责应这样保留而不是删掉：`AgentLifecycle` 的**策略部分**进入 Workflow/角色策略，**正式状态转换部分**由 WorkGraph 的生命周期操作承接，**物理执行部分**在 AgentRuntime/Kernel。可以用模块内部子目录保持清晰，但不能因为没有独立顶层模块就让职责消失。

同理，旧 `ControlEngine` 的正式状态责任、`ReadModelIndex` 的查询责任、`ArtifactVault/StateLedger` 的保存责任应映射到当前 owner；不要在五模块旁再建旧体系。

### 4.3 每种变化由谁触发

| 变化 | 谁作决定/提供事实 | 谁正式更新 | 是否必须调用模型 |
| --- | --- | --- | --- |
| Kernel 开始或结束一次执行 | Kernel/Runtime 真实观察 | WorkGraph 对应命令，RecordStore 提交 | 否 |
| Agent 的 working/standby 变化与活跃索引刷新 | 已确认的执行/占用事实 | 同一正式状态路径 | 否 |
| 选择相关 Agent 咨询、拆分工作、提出换手 | 被授权角色的 Skill/工具调用，或人 | 正式操作受理者 | 需要语义判断时才调用 |
| 归档、暂停或恢复 | 人、被授权角色或显式配置的规则 | 状态 owner；必要时等待 Runtime 结果 | 不固定要求 |
| 调整模块职责、拆分/合并架构区域 | Agent 提案与适用的人类决定 | 既有结构变更路径 | 通常涉及语义判断 |
| 更新反向关联、检查版本、读当前状态 | 既有结构与版本事实 | 图/状态工具 | 否 |

结构变化通常先产生受影响范围、过期标记和待处理事项；不能仅因图上删边就静默销毁 Agent、丢弃任务或结束执行。

## 5. Agent 生命周期与能力装配

### 5.1 状态与图上表现

沿用 S2 §4.6 的语义，不把下面的名称直接宣称为 next 已有枚举。

| 状态 | 当前架构视图 | 工作与咨询 | 必须保留 |
| --- | --- | --- | --- |
| `working` | 可见 | 已有活动执行；查询持久事实不打断它，新的语义咨询按通信协议处理 | 当前任务、Session/Run、来源定位 |
| `standby` | 可见 | 未执行任务但仍属当前协作体系；可在许可下继续相关工作或接受咨询 | Role、模块关联、已有 Session 与上下文来源 |
| `paused` | 可见，但标明暂停 | 不冒充可立即执行；恢复请求与真正恢复要区分 | 未完成义务、实际暂停结果、恢复信息 |
| `archived` | 默认不出现在活跃候选中 | 历史可读，读取不自动唤醒；显式解除归档后重新检查适用性 | 身份、历史关联、Session/Run、产物与来源 |

**待命不等于进程常驻，也不等于某个付费模型一直运行。** 能否联系与能否恢复由真实能力说明；ID 仍存在不能代替可用性判定。

Agent 的生命周期、Run 的终态、Task 的完成状态分别解释。一次 Run 结束通常只提供更新 Agent 忙闲的事实，不能直接推出 Task/Goal 完成。暂停的请求受理也不能冒充工具已停止。

### 5.2 生命周期操作族

总体契约必须覆盖创建、角色与图绑定、开始/结束工作、待命、暂停/继续、取消、恢复、交接、压缩/重组、归档/解除归档。不是每个动作都要新 API；优先映射已有操作。

角色拆解是拆解职责和工作，不是销毁角色。相关工作允许依据图和当前材料继续原 Session；独立并行工作使用独立上下文/Session。换独立工作不默认携带旧完整对话。

对同一工作，默认延续；容量或噪声问题优先复用 Kernel 的压缩能力；任务目标变化、历史失效或上下文明显失控时才重组。Kernel 已经提供可继续的上下文时直接使用，不再加一次平台重组。

### 5.3 角色装配不是建立新总管

一次工作装配应能够说明：**采用哪个 Role 版本、哪些 Skill/Prompt、哪些实际可用工具、挂靠哪几个图引用、使用哪个 Session、哪些材料入口和记忆来源可用，以及预算与既有执行授权。**

RoleSpec 存在不代表这些东西已经装进了真实模型调用。验收应检查实际请求/运行记录中的版本与工具集合，不能只检查配置对象形状。

普通消息和连续推进不重新做全量装配。必要的初始化/交接提供指引和引用，让 Agent 按需读取；不为每次任务都构造庞大的“世界快照”。

### 5.4 知识库、记忆和历史必须分开

| 对象 | 作用 | 当前交付口径 |
| --- | --- | --- |
| Session 历史 | 保存工作过程及原始事实来源 | 复用 Kernel，平台保存定位 |
| 经验记忆 | 经过选择、可复用的理由、经验、约定 | 按当前实现范围建立有来源的记录、读取、纠正/停用与实际消费证据 |
| 知识库 | 外部资料、领域知识与案例 | 预留可接入接口及来源/版本信息；未接入则明确 unavailable/unsupported，不以空数组冒充已有 |
| Role/Skill | 职责、能力配置与工作方法 | 交付实际可用版本；不是只留空模板 |

知识与记忆的正文不必为每个 Agent 复制。Agent/Role/模块可以持有适用的引用；是否共享、选择哪些内容按工作需求决定。完整知识库、自动经验提炼与长期专家效果属于明确登记的后续范围，不混进本轮“生命周期已完成”的声称中。

Skill 约束组织行为；真实工具访问、隔离与取消仍沿用 Kernel 机制。不要以 Skill 为由宣称已有安全隔离，也不要因此再加一整套平台细粒度审批。

## 6. 通信与按图咨询

### 6.1 通信应复用现有身份与记录

消息至少能够定位发送方、目标 Agent/Session、消息自身的去重/关联依据，以及需要时关联的 Task/Run/图节点/材料引用。具体字段复用当前协议，不新增平行 ID 体系。

普通消息不必先转成 Evidence、正式决定或新 ContextBundle；正文或来源可由现有 Session/正文机制承载。涉及真正的计划修改、授权和完成声明时，再走相应正式操作。

大材料以引用传递；收件人按需取原文。咨询关系不自动升级为阻塞任务依赖。消息已送达、已读、已回答、所请求工作已完成不是同一件事，不必为此一次建立庞大状态机，但消费者不能混淆其含义。

### 6.2 按状态选择咨询路径

| 请求 | 首选路径 |
| --- | --- |
| 进度、当前负责人、已接受决定在哪里 | 直接读取图和正式状态，不启动一个 Agent 来复述 |
| 需要解释，目标处于 standby | 定向咨询并续用合适的 Session |
| 需要解释，目标处于 working | 异步咨询；可先用已落盘事实回答。确需独立调查时用已有 Query/独立 Session 能力，不争抢原 Session |
| 目标暂停或暂不可恢复 | 返回状态与可用历史，明确等待或改由其他角色调查 |
| 目标已归档 | 不自动解除归档；可读历史或显式请求恢复 |
| 图上没有合适 Agent | 从事实索引/当前文件调查，或由被授权角色决定创建；不以“没人可问”终止整个产品路径 |

无论问谁，Agent 的回答是带来源的解释，不天然取代当前代码、正式状态或验收证据。

### 6.3 外部 agent-team 的复用边界

用户允许选择性吸收概念，也允许直接复制合适的源码。[S3 第 07 段 A7/C-1]

下一批可以对照 DSH agent-team 的通信、成员发现与工作分派实现，核对来源版本、许可文件、依赖和适配成本后决定复用范围。本轮没有读取该项目的当前源码，因此不声称已经核验其具体协议或可直接兼容。

复用不得带入第二套成员事实库、全量历史广播、主 Session 汇总所有正文，或绕过本平台的图关联与 Kernel 执行控制。不要为了参考外部实现，反过来改变已经确认的产品模型。

## 7. 基于图的编排：交付角色行为，而不只是 Workflow 函数

### 7.1 职责以 Skill/Prompt + 图工具组织

| 职责 | 输入与工具 | 应有产出 |
| --- | --- | --- |
| 书记/状态整理 | 已提交事实、图状态、消息与来源区间 | 忠实摘要、分歧、未决事项与引用；不把自己的推断写成已接受事实 |
| 秘书 | 用户请求、当前状态、任务/架构索引 | 解释、提醒、材料路由、具体待决问题；不把所有正文常驻装入自己的 Session |
| 参谋/规划 | 目标、约束、局部子图、相关角色意见 | 方案、工作拆分、假设、影响与重审条件 |
| 被授权协调职责 | 已采纳方案、候选 Agent、资源/工作状态 | 派发、等待、交接、重试或升级决定及其来源 |

这些是可组合职责，不强制变成四个常驻 Agent，也不是固定枚举。首版正式调度提交归属保持清晰；多 Agent 可并行调查和审议，不要求主对话 Agent亲自承担全部调度。[S1 §7.7.1]

### 7.2 编排是工具调用闭环

```text
人 / 被授权的角色
    → 读取任务图与架构图的局部状态
    → 必要时咨询相关 Agent 或读取事实
    → 提出/选择方案
    → 调用创建、绑定、派发、等待、交接等已有操作
    → 框架提交正式状态并驱动 Runtime
    → Kernel 真实执行与留痕
    → 正式状态及图关联随结果更新
    → 人和后续 Agent 继续按图工作
```

这是运行信息流，不是源码 import DAG。

图不负责“思考最佳计划”；Workflow 不负责“另存一份世界状态”；生命周期操作不负责“从头理解整个项目”。

### 7.3 Skill 必须有行为验收

首批至少覆盖：读图定位、按需材料读取、咨询负责人、工作拆解与派发、阻塞上报、解释已有方案、交接与归档。每项说明输入、可用工具、输出、何时结束或升级及禁止行为。

确定性的测试证明工具和状态语义，真实模型场景验证 Skill 是否让 Agent 正确使用这些能力。不能以 JSON 格式合法、单测通过或角色文件存在代替行为效果。

## 8. 后续施工约束：只细化接缝，不重造架构

### 8.1 每项能力按一条完整数据路径审阅

采用固定审查表：

| 产品场景 | 已有正式记录/符号 | 谁产生事实 | 谁消费 | 状态/索引如何更新 | 验收与证据 |
| --- | --- | --- | --- | --- | --- |
| 示例：按模块咨询待命 Agent | 先填当前真实承载，不预设新表 | 生命周期/绑定操作 | 架构图查询、消息入口 | Agent 状态与图关联使用同一正式依据 | AT-03、AT-04、AT-06 |

字段不是重点，**写入端—读取端—真实消费者必须一起出现**。缺少消费者的通用模块不作为默认新增项。

### 8.2 本轮已报告可复用的入口

S5 中已出现且下一批应先核对的符号：`WG11 readExecution`、`WG12 recordExecutionHistory`、`WG13 Source reader`、`RT1/RT3/RT7/RT8`、RoleSpec、TaskInput、Claim、Session 映射、RecordStore 的 CAS/幂等/事务及现有架构查询。

这些名字来自施工记录；确切导出、签名与文件归属由下一批源码审阅确认。禁止只在提示词里写“注意复用”，却不给出当前符号与调用链。

### 8.3 不应新增的重复设施

没有具体缺口证明，不新增 History DB、AgentDirectory/ExpertDirectory 的平行真相源、ContextManager 总管、消息中间件、第二张任务图或统一权限审批系统。

“不要新增重复设施”不等于“禁止补缺失的索引或内部服务”。若现有记录无法高效支持“按模块找 Agent”，就在原 owner 内补必要关联/索引；不能以复用口号让消费者继续全量扫描。

### 8.4 性能与可靠性只测真实路径

记录每次咨询的图查询范围、原历史读取范围、读取记录数、模型调用次数、输入量与等待。已有 S5 的 Kernel 范围读证据只证明该底层读取有界，不等于整条图查询为固定成本；WG11 完整 Plan 等既有成本仍应如实登记。

重复请求与观察应复用现有幂等；执行结果未知先核对 Kernel 事实，不盲目重跑模型。暂停/恢复依赖真实能力，不凭 UI 标签宣布完成。不为追求无限故障覆盖扩建通用分布式框架。

## 9. 实施顺序与分工

### 9.1 先整体对齐，再分路径实现

**先交付一张完整能力与职责映射表，以及对应骨架。** 创建/绑定、状态、装配、通信、图发现、控制恢复都必须有位置和消费者；不能只冻结一次 startRun，再把其余称为“以后再考虑”。

随后可以分批实施，但每批明确属于整体范围的哪个部分，不重新定义产品：

| 工作包 | 主要内容 | 产品验收 |
| --- | --- | --- |
| A：双图—Agent 关联与生命周期骨架 | 对账 Agent/Role/Session 现有承载；补模块关联、状态、查询与状态写操作；冻结所有生命周期动作的责任 | 创建后可沿图发现；待命仍可见；归档不删模块与历史 |
| B：真实执行与能力装配 | Role/Skill/工具与引用进入现有 Kernel；真实观察自动写回历史定位和状态 | Agent 从图上的工作入口执行，结束后图反映真实状态，原历史可直接定位 |
| C：通信与角色编排 | 定向咨询、消息/等待/回复；秘书/参谋/书记 Skill 与正式调度入口 | 能按模块问到待命 Agent，协调角色能基于图派发与汇总，不汇入全部历史 |
| D：控制、连续性与产品完成 | pause/resume、恢复、压缩/重组、交接、归档恢复；计划调整、Evidence 与薄人用入口 | 控制动作真实有效；相关工作复用；范围变化只影响相关工作；完成有依据 |

A 与 B 的共同契约先审；其实现可以按不重叠文件范围并行。C 的消息/状态协议、D 的控制协议同时进入前期设计，不在最后临时发明。完整知识库仍按已确认边界后置；这不等于生命周期可以后置。

### 9.2 Astra / DSH 分工不变，交付单位改变

`Astra 对齐产品与跨模块契约 → DSH 骨架及测试 → Astra 中间审核 → DSH 实现 → Astra 独立反例审阅 → 隔离验收`。

按用户路径切批，不只按目录切批。组合根、公共 schema、共享契约与跨模块验收由单一集成负责人维护；各施工者宽读窄写。每次骨架审核检查真实调用链、owner、复用符号和拒绝/缺能力路径，避免通过大量替身绕过真正入口。

## 10. 跨模块验收场景

| 编号 | 场景 | 最低判据 |
| --- | --- | --- |
| AT-01 | 从角色模板创建并挂靠 Agent | 正式关联可查；实际 Role/Skill/工具版本可追踪；无需新建第二份成员目录 |
| AT-02 | 真实执行后自动回写 | 原有 writer 由 entry/观察调用；Task/Run/Session 定位正确；不靠人工填区间 |
| AT-03 | 执行结束转待命 | Agent 仍在架构模块下可发现；无活动 Run；不会被误标为归档或任务必然完成 |
| AT-04 | 沿模块咨询待命 Agent | 图定位 → 定向调用 → 复用合适 Session → 回复附历史/文件来源；不扫描所有会话 |
| AT-05 | 咨询正在工作的 Agent | 查持久状态不打断；语义请求排队/异步或走独立只读调查；不并发占有同一 Session |
| AT-06 | 显式归档 | 活跃候选不再出现；模块、旧任务、Run、Session 与历史关联仍可查；读历史不自动解除归档 |
| AT-07 | 暂停、取消、恢复与交接 | 请求受理和真实结果区分；Kernel 不支持时如实返回；未完成义务及来源不丢 |
| AT-08 | 相关工作复用与独立工作隔离 | 两图能提供复用依据；相关工作可续用；独立并行工作不共享同一活跃上下文 |
| AT-09 | 压缩与重组 | Kernel 已压缩可继续时不二次重组；目标变化或材料失效时局部交接/重组；原事实可追溯 |
| AT-10 | 编排与解释 | 角色按图查询、咨询、派发、报告；解释旧方案不生成新方案；只有需要新取舍时升级给人 |
| AT-11 | 重试和中断 | 重复状态/消息受理不重复推进；结果未知不盲目重跑模型；不能只靠 ID 声称防重复 |
| AT-12 | 记忆与知识库边界 | 可追踪实际使用的版本；已停用条目不继续选入；未配置知识库不伪造可用结果 |
| AT-13 | 图变化与并行工作 | 图变化给出关联影响，不静默删除 Agent；不把架构依赖自动当全局锁；实际变更后的核对保留依据 |
| AT-14 | 性能与人用可见性 | 观察局部读取量、准备开销、调用次数；人能看到 Agent、忙闲、任务、来源和控制结果 |

AT-01–14 是目标验收清单，**不是本轮已执行结果**。已有 620 项测试的通过不自动覆盖这些用户路径；应逐项关联已有测试，缺的补测试，避免重复造同类用例。

最重要的示例是：**创建挂靠模块 B 的 Agent → 执行任务 → 进入 standby → 另一个 Agent 沿架构图找到它并咨询 → 回复带来源 → 显式归档后从活跃查询消失，但模块与历史仍在。** 这条路径同时检验双图、角色装配、生命周期、通信和事实复用。

## 12. 交接摘要

原设计已经要求双图、角色、Agent/Session 生命周期、按图咨询和 Skill 驱动的协作。已有底层能力应当保留；当前要避免的不是“模块还不够多”，而是**只验收局部记录与工具，遗漏它们共同服务的 Agent 工作路径**。

下一批先核对五模块对原职责的承接，冻结状态与关联的单一 owner、图查询输出、生命周期操作和真实 Kernel 接缝；随后按跨模块场景实施和验收。**不以一轮执行结束代替产品完成，不以增加 Manager/Store 代替缺失的连接，也不以“只剩接线”掩盖尚未定义的必要契约。**
