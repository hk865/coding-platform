采用两个验收层次，避免把施工顺序误写成产品裁剪：

- **E2E 首通**：用户在真实入口给出 Goal，无预置 Plan，经调查/规划、正式采用、执行、真实检查、Task/Goal 完成，最终在工作台查看产物与依据。先选一条窄而真实的 coding 路径，允许该样例顺序执行；它不证明全部 MVP 已完成。
- **产品 MVP**：首通之外，还通过本文的并行、失败返工、控制恢复、换手、变更、双图追溯和项目隔离路径；记忆核心与 B11–B20 的新增行为也属于 MVP（[HANDOFF 决定 13、15、23、49](refactor/HANDOFF.md)）。界面可以朴素，但不能用手工 seed、脚本代改数据库或假成功填补用户路径。

首版仍是单用户、单机、coding-first，多 Project/Workspace，一个 Goal 绑定一个 Workspace。不建设跨机器共识、多租户、完整 IDE、通用工作流 DSL 或长期专家知识库；压缩（K2）进 MVP：两轮之间先清旧工具结果，不够再摘要；做好以前按真实能力显示 unsupported，用换手接续（[HANDOFF 决定 39、113-7](refactor/HANDOFF.md)；[STATUS](refactor/STATUS.md)“缺口”）。（K2 冻结注，2026-11-03：秘书“太长就换手”今天其实够不着：平台按字节计量，Kernel 在约 26.8 万 token 就开始裁，最近一次输入到不了 50 万的阈值；K2 的计量（K2-M）做完以后够得着，见 [K2 规格](refactor/design/orchestration-2026-10/slices/slice-K2-SPEC.md) F5、M5，决定 116-1。）已有生命周期、并行与恢复承诺不能以“最小化”为理由永久后置。

## 2. 用户入口与结果

布局、视觉与控件规范见[工作台 UI 设计 §0](UI-WORKBENCH.md#ui-decisions-2026-10)和[冻结原型](ui-reference/workbench-2026-10/README.md)。左栏按职责分组列出工作线（卡片），“成员”只是推导出的视图；工作中、待命、已归档按工作线计数。点工作线，中间切到它的对话，可「问一问」或「直接干预」。主对话是交互面，目标栏切换显示内容，不等于一个 Session。右侧辅助区可收起，用多页签承载双图、文件、命令和 Diff；节点详情、任务过程和原历史按需展开（[HANDOFF 决定 15、17、25、33、35、37](refactor/HANDOFF.md)，替换早先主对话只按传统 Session 展示的说法）。

用户在同一工作台选择或创建 Project/Workspace，输入目标、约束与已有授权。工作台至少提供主对话、任务图、架构图和统一详情入口；图和列表可以简化布局，但两种结构必须真实可查看。

| 用户动作 | 应看到的结果 |
| --- | --- |
| 输入“修复问题并验证”或“实现这个功能” | 原目标被保存；系统说明正在调查、规划、执行或等待什么。授权内细化和验证自主推进 |
| 查看任务图 | 未来意图、当前工作、历史尝试同时可找；展示 required/optional、延期/取消/替代和缺项，不能只列 ready 节点 |
| 查看架构图或点名工作者 | 区分正式结构与源码观测，定位文件、职责、关联 Session 和历史；归档不删历史 |
| 查看任务详情 | 当前计划/义务、负责人和 Session、Run/Attempt、变更、检查、证据、阻塞原因与下一触发条件 |
| 查询状态、打开文件或历史 | 直接读已有事实，不因展开/分页启动模型；解释需求才使用必要的 QueryRun |
| 暂停、继续、取消或追加要求 | 显示受理回执、作用范围和实际生效状态；未支持、拒绝、未知分别可见 |
| 查看最终结果 | 产物位置、修改摘要、当前有效验收证据、未完成/排除事项；能追到原始结果和来源版本 |
| 关闭后重开 | 找回原目标、计划、执行与控制状态；不要求重述项目，不凭 UI 缓存重建正式状态 |

“已受理”“已进入执行”“执行结束”“检查通过”“Task satisfied”“Goal COMPLETED”分别表达。下文中文阶段是用户语义，不新增全局状态枚举；具体映射遵守[状态机规格](refactor/STATE-MACHINES-SPEC.md)。

```mermaid
flowchart TD
    U[用户目标与授权] --> I[登记项目和工作区 / 保存 Goal]
    I --> P[定向读事实 / 必要时 QueryRun 规划]
    P --> D[保存候选与来源]
    D --> A{采用条件与授权是否具备}
    A -->|范围内且条件齐备| B[采用计划 / 保留未来意图]
    A -->|资料缺口或新取舍| Q[说明缺口或具体待决]
    Q -->|新信息或明确决定| P
    B --> O[Workflow / Agent 选择下一动作]
    O -->|细化 / 分工 / 咨询| B
    O -->|执行| R[选择或创建 Session / 领取 / Kernel 执行]
    R --> V[记录真实结果 / 更新关联与来源]
    V --> C[按采用要求检查]
    C -->|失败且有修正方向| O
    C -->|缺项 / 过期 / 未知| Q
    C -->|适用证据覆盖义务| T[正式 Task / Gate 归约]
    T --> O
    T --> G{Goal 完成条件满足}
    G -->|否| O
    G -->|是| F[正式 Goal 完成 / 工作台显示结果与依据]
```

此图是有反馈的业务流程，不是源码依赖 DAG，也不要求所有任务串行经过同一常驻模型。主路径有变化才推进，无新依据时等待明确条件。

| 责任方 | 本路径负责什么 | 不得替代什么 |
| --- | --- | --- |
| Host/UI | 真实作用域、配置、交互、局部刷新、持久待办唤醒和展示；空闲时消费所有可用 Session 的邮件（按 Session 键分批、按 profile 选模型，`notify` 不开轮） | 不自行置 Task/Goal 完成，不把浏览器状态当正式事实 |
| Workflow / 角色 Skill | 规划、采用授权判断、Session 选择、并行安排、检查/返工与待决选择 | 不复制图算法、事务、完成归约或模型循环 |
| WorkGraph | Goal/Plan/Task、Session 关联与占用、Query/消息/证据的正式操作和完成归约 | 不调用模型或 shell，不证明未来语义无冲突 |
| AgentRuntime / Kernel | 实际执行、只读查询执行、检查执行适配、控制与恢复、原历史观察 | 不凭模型结束宣布产品完成，不另建一套 Kernel 日志 |
| WorkspaceTools | 文件、来源版本、捕获、比较与结构观测 | 不自动采用架构或授予执行权限 |
| RecordStore | 条件提交、正文、事件与索引持久化 | 不决定业务方案 |

## 4. 行为契约

### B01：从空状态建立真实项目

**触发**：用户选择已有目录或要求在授权位置创建项目，提交目标。

Host 提供真实目录映射、存储与 Kernel 配置；经正式 Project/Workspace、Goal writer 保存引用。目录创建、登记、文件可访问是不同事实；不存在或无权访问时显示准确原因，不静默换到别的目录。空目录是合法观察。

没有 Plan、正式架构 baseline 或 CompletionPolicy 不阻止调查、回答和候选保存。正式采用才检查实际治理前提；首次架构通过已有初始采用能力登记真实候选，不能塞空 baseline 或测试 policy 冒充初始化。相关角色、政策与授权来自明确配置和正式 writer。

**结果/失败**：成功后能重开同一项目和 Goal；重复同一创建请求返回原回执。初始化中断仅续办未完成步骤，保留已经成功的登记，不盲目重建 Goal。

### B02：无 Plan 调查、规划与采用

**触发**：Goal 存在但尚无采用计划，或用户要求解释/修订现有方案。

主对话写明请求交给了哪个秘书。秘书先给 2–3 个思路，用户选一个后继续在对话中迭代，每轮说明改了什么；目标卡和第一个方案由用户确认后才推进。同一目标可以有多个请求，候选方案按请求分开；采用一个后，其他基于旧计划的候选显示过期（[HANDOFF 决定 15、37、42](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.1）。

规划输出是阶段骨架加第一段：每段写一条阶段 gate，按这一段的验收归约，不等后续段；平台不新增入图 gate 校验，有 gate 就按现有归约验收；后续段先放必需、活动的 `plan_only` 占位（PL-1 已落地）。有活动的必需 `plan_only` 任务时，平台发一条系统轮请参谋写这一段；模型只写这一段，平台把它合并成完整草稿（PL-1 已落地）。

优先读已有目标、文件、图和材料；需要模型判断时使用真实 QueryJob/QueryRun。Query 不伪装 Task/Attempt，不借 Work Run 权限；与其他执行共用 Session 占用和唯一 Kernel 循环。只读规划不获得文件编辑权限；后续初始化写入通过已授权写路径。

模型回答经真实来源提取和边界解析成为候选，保留 Goal/Workspace/回答及来源版本。候选中允许未来 `plan_only` 节点暂缺分配和验收；不沿用“所有节点必须立即可执行”的假设。解释旧方案复用原版本与理由，不能每次追问重新生成计划。

agent 候选由目标循环统一处理：先过机械诊断，再由独立审阅线审阅；审阅 `pass`、诊断无问题且自治级别允许才自动采用；审阅 `fix` 且未到 3 次上限时发起或等待返修，达到上限、返修无效（含 `fix_invalid`）或 `pass` 但策略/诊断不满足等情况才转候选卡（PL-1 已落地）。人采用第一版、人的请求槽候选仍走原路，不受这条影响。

秘书的正式回答按填表式回答。请求轮冻结 `submit_secretary_answer`；初始化轮冻结 `submit_initial_plan`、`submit_initial_questions`。工具按表单生成今天的 v1 秘书对象或 v2 信封，模型不写 JSON 正文。提交前查五层里的前三层：表单结构（Kernel 的 zod，参数不符合 schema 时逐条列出 `<路径>: <消息>`，码仍是 `invalid_arguments`）、回答自身按采用的规则、对着当前状态；所有问题一次列出，带小节和原因，模型改完在同一轮再调。提交后会变的事实由采用时照旧再查，判断不归表单。接受后这一轮在接受处结束，不再请求一次模型。模型只写文字、不调工具时按旧读法（`formalAnswerOf`，代码框权宜保留）；文字坏了照旧算这轮失败。普通 Query 和普通 Work 不变。

秘书的请求轮能拿六个工具：四个邮箱工具（`send_session_message`、`ack_session_message`、`respond_session_message`、`withdraw_session_message`）、`create_member`，以及只读的 `read_requests`；其他 Query 仍然全部禁用这些工具。`read_requests` 读工作区任一目标或无目标的请求，最新在前，每页 20 条，每轮回答截到 2 KiB；它不返回卡和通知，也不挪“看到哪儿”。

已有授权覆盖的细化在审阅 `pass`、诊断无问题且自治级别允许后自动采用（PL-1 已落地）；缺治理或来源过期时说明具体对象并修复。实质改变目标、验收或越权必须由人决定；其他候选按候选循环转卡时，也展示相应差异和待决内容。用户确认绑定具体候选版本；过期确认不批准新版本。只有 Host 能采用计划：模型只能提议（`plans/propose`），采用只经 Host 的 `applyPlanChange`；`apply_future_plan` 和所有 agent 采用分支已删除。自动采用也走 Host 的同一入口，身份是平台自动化，不由模型或参谋代采用（PL-1 已落地）。模型来源不能伪装 Host 来源绕过采用。

采用时缺治理，回答要说清缺的是初始架构、完成标准还是两者（`missingInitializationGovernanceReason`）：只有明确的 `not_found` 算缺失，码仍是 `incomplete`，不自动安装治理。

**结果/失败**：采用通过原 Plan writer 切换版本和关系；拒绝不部分修改活动计划。规划轮的回答不能形成可采用的计划，或提议被下一趟也改变不了的码拒绝时，走第二种结局 `invalid_plan`：原回答仍留作正式回答，并成为对这条消息的回复；Host 加一条固定通知，不写候选，这一轮到此结束。只有 `unavailable`、`cancelled`、`busy`、`revision_conflict`、`source_stale` 仍是可重试的拒绝。这条只走干预规划路径；即使尚无采用计划，这份首份候选也适用。请求初始化的首方案仍返回解析、规范化或采用拒绝，不走“消息回复 + 固定通知”收尾。回答超时或结果未知先查询原 Query，不通过另建一次规划掩盖不确定状态。详细生产链见 R5b（已归档：`docs/refactor/tasks/R5b-query-planning-skeleton.md`）。

### B03：从白板选择行动并保留长程方向

**触发**：计划采用、执行/检查结果到达、消息有实际业务响应、控制/条件变化或用户补充。

Workflow 读取触发涉及的对象及当前计划，选择细化、分配、咨询、执行、检查、返工或等待。目标循环每轮统一处理这个目标的 agent 候选，按待审、审中、待改、待采用、待人、已采用未回复归类；候选的等待只挡那一支，别的任务照常推进（PL-1 已落地）。ready 是候选提示；分配不等于激活，激活不等于领取，领取不等于 Kernel 已开始。具体执行资格使用当前正式契约。意图是 `notify` 的“请知悉”永不开模型轮，留着跟下一个真实轮进上下文；秘书请求轮的供给只带排队的 `notify`，不收人的消息、接续和 agent 的“请回答”“请动手”，接受时才算送达；打不开轮的消息留在队列、跳过，不结束这次扫描，也不挡住后面的提问和发件箱。

无 ready 时同时查看未来意图、未完成 required 工作、缺分配/说明/义务、实际输入缺口、忙碌 Session、检查与未知执行。能在授权内补足的继续细化；需要外部信息的保存原因和唤醒条件；不能宣布完成或无变化地重复调用模型。执行中的偏差回到计划：执行者上报、过 2 倍线、预算用尽、返工到上限或无新依据时，参谋改计划或说明不改；改计划产生新版本，受影响上下文按新定义继续（待 PL-2）。

预期依赖、架构相关和计划显示顺序不自动成为硬前置。明确采用的具体产物消费条件在真正需要该输入时检查；生产者 Task 尚未整体完成，但所需产物已合法可用时，不机械等待整个 Task。失败、等自动返工确认的 Task 挡住它自己；只有卡/等待的传递闭包挡下游，依赖边本身不挡领取，不加新闭包（D-V1）。预期依赖和协作关系不挡。目标里别的任务照常往下走；全挡住时目标等待，相关的事一变就叫醒。阻塞每次推进重新算，不存。目标范围的 `selectNext` 跳过正由看守推进的 Task；碰到在等的候选，记下它的等待依据继续看后面的，全部不能推进时才返回合并后的等待依据。被唤醒的后继照常领取并进入，不停在领取。看守失败结束、且目标已接受、未停止时，目标再看一次，接上 Task 被 hold 时看不见的回复等待；带依据的等待只登记，不再看一次。

**结果/失败**：每次行动可定位依据与结果。未来 required 意图不会因暂不可执行而从 Goal 未完成解释消失；一次局部失败不撤销其他独立工作。

### B04：真实执行、连续 Session 与结果回流

**触发**：选择了可执行工作和当前有效分配。

按任务/模块关联寻找合适 Session，核对角色、范围、健康和占用；相关工作优先延续，独立调查/审阅或并行使用独立 Session。创建 Session 本身不启动模型；创建成功后领取失败保留合法闲置 Session。

领取正式写入 Task/Session、Attempt/Run 与待执行项。Runtime 准备真实角色/Skill/工具及必要材料，经新鲜执行准入进入 Kernel。每个 Work Run 的 token 上限从 Host 设置取：默认 4 亿，可存 1 到 6 亿的整数，也可清回默认；领取时定下，已在跑的 Run 保留领取时的预算。设置入口是 `run-budget/save`，快照给已存、实际和最大值；还没有设置页和超支卡，归 E3 和 PL-2。相同领取重放只能读原执行，不再次启动。Session ID 相同不足以证明连续性：后续模型输入必须真正包含必要前文与增量要求。

工具和执行结果带真实身份、来源及历史引用入账，局部更新相关图或标明尚待刷新。Run 结束释放匹配代次的占用，保留历史与工作关联；不归档 Session、不自动完成 Task。失败有具体修正方向才能开新 Attempt；未知先核对。

### B05：同工作区并行与协调

**触发**：存在可独立推进的多项工作。

Workflow/Agent 根据规范、架构和白板分工；允许同一目录中多个独立 Session 同时工作。不要求事前完整未来读写范围证明，不把模块、Workspace 或所有传递依赖加成一把锁。实际工具操作仍执行适用权限、文件版本和必要资源约束；同一 Session 保持一个对话修改占用。一个目标内也这样：一个目标只有一个决定循环，长步骤交给每个在跑任务的看守后不等它，符合选择规则的多个任务可以同时推进。

发现冲突时返回真实对象、来源和已知影响，由 Agent 调整共享步骤、协调、等待或采用已有隔离能力。保留无冲突成果；不自动推翻两个分支全部工作，也不假称尚未实现的三方合并已经可用。通信的已读、回复、正式输入满足和任务完成分别表达。

**结果/失败**：独立工作继续，冲突只阻塞相关步骤。涉及新的产品/架构取舍才向人提交方案；普通文件协调不增加同义审批。并行结果经实际检查与整合后才能用于完成。

### B06：检查、返工与 Task/Goal 完成

**触发**：真实执行产生待验收结果，或已有检查需要补齐。

按已采用义务冻结本轮检查要求和实际来源；使用真实命令、只读报告见证及要求中明确存在的独立审阅。没有独立审阅要求时不强加 Reviewer。报告、正文材料、Evidence、检查轮次和正式完成是不同事实。

这里分开两类审阅。计划候选审阅在采用前，结论只影响自动采用还是转候选卡，不写检查证据，也不碰 Task/Goal 完成归约（PL-1 已落地）。执行结果审阅仍是原来的独立审阅：只在采用的计划要求时起审阅者，结论进检查证据，归第 9 片，本片不改。

- 缺验收定义、required requirement 或有效证据时返回具体缺项，不利用空集合得到 PASS；允许此前合法调查已发生。
- FAIL 保留原轮次和证据；义务不变时返工保留 Task、新增 Attempt/Run，优先延续合适 Session。义务变化走正式计划演进，不偷改已经执行的定义。
- 返工和重查由 agent 发起时走 `request_rework`、`request_recheck`：先跑预算、返工上限等护栏；「方案确认后自动」下照旧执行并计数，「每步确认」下写成一条 `ReworkRequest@1`，出一张“要决定”的卡（批准/拒绝），回执就是这张卡；到了上限仍在护栏里直接拒，不出卡。批准后按 agent 身份应用，计进同一上限；任务已取消或被替代就记 `stale`。
- 缺项、INCONCLUSIVE、过期、执行中断或未知副作用均不完成；检查曾通过只证明对应来源版本。仍适用的结果可复用，不为补报告重复未知命令。
- WorkGraph 完成归约核对当前义务、覆盖、来源和局部版本，正式提交 Task satisfied；gate 只归约证据，不派发伪 Work Run。
- Goal 单独归约：无活动计划、空完成要求、required 尚未解决、相关未知执行均不能 COMPLETED。optional、延期、取消和被替代事项明确列出；required 取消不能自动算完成。明确接受部分结果记录 ACCEPTED_PARTIAL 与取舍依据。

**结果**：用户可从 Goal 完成进入每项义务、适用证据、原检查和文件版本。Run 成功、exit=0、模型说“完成”、消息回复或 ready 为空都不能替代此链。实现边界见 R3e（已归档：`docs/refactor/tasks/R3e-completion-skeleton.md`）。

### B07：查询、解释与统一导航

已知路径或引用可以直接读，不强制全图扫描。图用于缩小检索范围并关联模块、任务、Session、产物和历史；查询与分页不改状态、不 ack 消息、不启动模型。缺失、未授权、不支持、历史版本与当前结果分别返回。架构模块的悬停卡读真实维护者；只有目录里只剩这一个模块、且它声明的路径正好是 `['.']` 时，才标“未细分”，旁边还有别的模块时不标。

agent 用两张图共用的“看、找、记”：看节点或路径，得到可下钻的紧凑文本卡片；按文字或路径找节点；给节点记一段话，由平台补来源、版本和类型，返回收下、待审或拒绝及原因。读图不必先装入全图，记注记不代替正式状态写入（[HANDOFF 决定 18、22](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §5.3）。

用户追问理由时使用已保存的明确决定、选项与依据，不要求保存模型隐含思维过程。需要咨询才向适合的 Session 发消息或建立 Query；忙碌、离线或归档不妨碍读取已有事实，不冒充原工作者作答。

UI 用提交回执和读取水位刷新相关视图。投影延迟保留带版本旧视图或显示待刷新，不把已提交动作显示为未发生；节点、名册与对话定位到同一详情。

### B08：暂停、继续与取消

用户或授权策略发起作用域明确的控制，平台先持久记录期望，并停止相关新派发；Runtime 经真实 Kernel 能力投递并观察。控制请求、信号送达、安全点生效和终态分别展示；迟到旧 ack 不覆盖新控制。

继续需读取原控制、Session/Run/Turn、占用及恢复能力，按正式恢复入口处理；不能把重复 start 或创建新 Session 当作原 Run 恢复。取消不撤销已写文件或删除历史。终态后晚到控制按真实回执说明，不把已经结束的工作改写成“取消成功”。

部分 Run 仍未知或能力不支持时显示各自原因，不显示整个 Goal 已停；确认原写入停止或正式交接后才允许相交接管。R4.1 意图持久化、R4.2 安全点与后续投递/恢复必须共同贯通，不能单凭其中一项开启完整 capability。

### B09：目标/架构变更与安全换手

目标变更先保存要求并定位受影响任务、结构、Session 与证据；候选不立即作废现行计划。已有授权的变化按正式操作采用，新增取舍展示具体差异。停止受影响旧后续派发，运行中的相关操作按 B08 控制，无关任务继续。

正式架构与源码观测分别保存。发现漂移后能定位版本、相关文件和工作者，解释影响并进入修复或正式架构变更；不得自动把观测 imports 当作已采用职责，也不得隐藏观测环。拒绝、延期和过期决定不偷偷推进采用。

换手保存目标、当前义务、有效决定、未决项、未验证假设、文件变化和历史引用。接任者仅靠持久材料就能按需接续；责任切换前核对原写入和交接状态。交接失败不丢旧义务；归档保留全部历史，重新启用与另建接续如实区分。

交接有一条入口：`hand_off` 工具经平台的交接入口受理，记录这次交接；需要人决定时出一张 `handoff_approval` 卡。审批卡的 subject 跟着 assignments 覆盖的 Goals 走：只涉及一个 Goal 就是该 Goal，否则是项目；项目 subject 的卡也能服务 `handoff_approval`。简报记成 `HandoffBrief@1`，只在真正进入 Kernel 的 Run 上消费一次；没进入的尝试不消费，留给下一次 Run。`hand_off` 已真实接通：`handoffs` 已在组合根绑定到交接入口，真实调用到 H，审批卡的应用行和 H-01、H-02 的公开链路都已跑通。

交接按链接走。先移交派给接任者的任务：每个任务一次转移，只写负责链接的转移，任务链接没有范围 claim；范围 claim 随后续范围链接的转移在同一次提交换手。源线没有开着的负责 task/work 链接以后，才移剩下的范围：负责 goal/project 链接，以及参谋、书记的 module 区域链接，每条一次；每次只移一个目标，输入先存、再提交，崩溃后按存下的输入重放。源线还有开着的 task/work 链接就是部分交接：不做范围子步骤，源线留着范围、claim 和席位。席位不在交接里换；完整交接且接任者借了席位时，等源线正式归档那一次提交再换持有。

**交接与归档时的当前理解**（用户 2026-10-05 决定：记忆核心进 MVP，见 [HANDOFF](refactor/HANDOFF.md) 顶部决定 23）：
- 目标和阶段节点上保存一段“当前理解”：跨计划版本的取舍、试过什么、定了什么、还没定什么。
- 事实用指向固定版本的引用给出（代码路径与提交、计划版本的改动原因、检查结果、原始历史区段）；理解写成有大小上限的文字，不只放指针。
- 任务结束、采用新方案、返工、Session 归档或重组时更新。接任者和下一个在那里工作的 agent，不必重读全部历史就能拿到。
- 所引代码或计划版本变了，条目标为“需复查”，不当作仍然成立。
- 两张图的节点还可保存注记，带来源、版本和复查状态。用户可看、改、撤下；历史仍保留，注记不能代替授权或完成状态（[HANDOFF 决定 20、23、35](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.7）。
- 查找工具按明确字段和固定规则读取，工具内部不调用模型；相同输入、权限、数据和规则版本得到同一结果。关键词全文查找提前到第 4 片，注记只加一个全文索引；这替换决定 23 原来放在 MVP 之后的排期（[HANDOFF 决定 49](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §3.1）。
- 检索排序调优、真实 bug 效果评估仍放 MVP 之后；长期知识库更后（[HANDOFF 决定 23、49](refactor/HANDOFF.md)）。

### B10：中断、重启与无进展

| 可达中断/重复窗口 | 必须采取的行为 |
| --- | --- |
| 受理响应丢失 | 用原请求身份查询回执；同输入回放，改输入冲突，不再写一份候选/执行 |
| 已领取但确证未进入 Kernel | 续办原持久待执行项，不重新规划或领取 |
| 可能已进入，结果未知 | 保留身份与占用，核对原 Kernel 记录；日志暂缺/超时不能证明未执行 |
| 工具已发生，平台入账失败 | 依据原结果补账，不能重新执行工具取得“另一份结果” |
| 检查后文件或计划改变 | 保留历史证据；只在当前适用性成立时复用，缺口明确列出 |
| 同输入、同版本、同动作重复失败 | 没有新信息则换方法或等待具体条件，不无限增加 Attempt/模型调用 |
| 模型服务连不上（断网、网关不通、限流、服务端错误） | 可重试错误最多试五次，失败后等 2、4、8、16 秒；没有 HTTP 状态的连接失败可重试，429 和 5xx 照旧，不可重试的其他 4xx 第一次就结束。五次都失败才算被中断（FC-7m），运行中当场记成被中断（失败类别 `interrupted`），来源 `model_service`，带 Kernel 的码和时间；不计自动返工次数、不比依据、不自动返工；目标显示原因和卡，Task 那一行照旧显示失败；只有人能继续（`tasks/requeue`，驱动已停时再 `workflow/driver-start`）。预算挡住重试时，以最后的模型服务错误提前结束（`retryable: false`），这次 Run 按模型服务中断结束，不走预算终态；首次请求预算不够的行为不变。接受等待期间到期或关 Host 最多晚 16 秒。哪一档都一样：下次 Host 启动也不续，没有定时器，也没有联网后自动恢复（GAP-48）。按 Kernel 的三个码认：`provider_request_failed`（400/404/422 一类的请求错误也在里面）、`rate_limited`、`provider_unavailable` |
| Host 重开 | 先恢复持久待办、映射与未决观察，再允许相关新执行；Kernel 恢复自身日志，平台恢复关联。之后按“启动时自动续做”的三档处理还有没做完的必需工作的活跃目标：`auto` 直接续做；`ask`（默认）和 `off` 列出目标，显示“被中断，等你继续”，写下来源（Host 重启，干净或不干净）、时间和涉及的 Task 与 Run，给一张卡，等你点继续；`ask` 的请求队列和抓取照旧，`off` 不启动队列、不重试抓取。重启后从事实只读重建等待登记表；有待处理重启中断的 Goal 不登记、不叫醒，等它的驱动启动（`resumeOnStartup` 为 `auto` 时不扣），判据读 Goal 显示里的 `interruption` |

**结果未知以后谁来定（决定 52、53，121-109 改，未做）。** 平台先按种类核对；跑程序的先跑一轮只读核对。核对后定不下来的（做了一半、判断不了、自查“可能导致崩溃”的第一次），由负责那一块的参谋从“照原样重跑 / 换个稳妥的跑法 / 跳过当作已做 / 我来处理”里选一个、写理由，稳妥方案也由参谋批；人在“请知悉”里看到一句大白话，技术细节可展开。只在同一任务同一步连续第二次中断、参谋定的处理又失败或返工到上限、没有参谋可问、目标是“每步确认”、参谋自己上报时问人；问法是结果层面的三选一（照参谋的建议 / 先暂停这项任务 / 我自己来看），“每步确认”时仍是四选一。这张卡要选一项才能往下走，可以附一句话。原命令照样被拦，人随时能“我来处理”。

重启恢复还要覆盖候选、审阅、返修、续轮和偏差这些已有事实：有待处理候选、待答或已答未续轮的规划问题、已发未收尾的审阅或返修轮时，按原记录续做（PL-1 已落地）；偏差按当前正式计划和同一请求号重读，不新开第二条（待 PL-2）。Query 已终态、收尾（回复、候选或关联）还没写时只补收尾：不重发、不重开模型轮、不建第二个候选（PL-1 已落地）。

不增加另一个恢复引擎或承诺外部副作用恰好一次。不根据直接改坏内部记录构造不存在的运行时 Role 热切换生命周期；反例来自公开入口、真实并发与可达故障窗口。

### B11：「需要你决定」的闭环

**触发**：出现需要用户选择的事项，或有工作结果需要用户知悉（[HANDOFF 决定 13、15、37、42](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.4）。

全局队列分“要决定”和“请知悉”，目标栏显示计数。主对话中的卡与队列是同一项，处理一次，两处同步。秘书、参谋、书记可请用户决定；执行者和审阅者只发“请知悉”，需要用户选择时由参谋转成决定卡。

项目主体的卡不属于某一个工作区：在一个工作区答了，同项目的其他工作区读到同一张卡、同一条答复和同一份计数；答复正文留在答复它的工作区，别的工作区能读，但不能在那里再落实一次（写侧的 pin 按工作区拒 `invalid`）。每个工作区的“看到哪儿”仍各记。项目级通知是「请知悉」自己的一个来源（`project_notice`），按提交游标读，一条记录一项，不属于某个目标；7D1 只做记录、写入口和读，还没有生产者。

每张卡可以先问秘书，再选项、写自己的话或给对象加批注；只写话也能答复。拒绝、延期也是答复，不需后续落实。其余已答复而未落实的卡移到“已答复、待落实”，不再算待答；发卡的线归档了也不能丢掉它。落实后能看到改了哪个对象、哪一版；落实没记上时显示“已答复，落实未记”，可补记。通信断开时，「需要你决定」队列的「请知悉」里也出一条断开项：谁、什么时候、活由谁接，或“没人接，等你定”。

返工通知由 Host 自己的系统发件箱发：记下来才发送或出卡，失败留到下一趟，同一条不会发两次。没有参谋时，这里只记卡的来源，卡由读模型派生。收件人读真实目录：没有固定职责的 Session 跳过，读失败这一趟不处理、下一次重试，不投给别人。提醒按配置的真实来源扫描；提醒自己的收件人先问参谋，没有才用配置的 `targetSession`，和返工通知的收件人是两处。执行者能发 `request_rework`、`request_recheck`。

**结果/失败**：对象已经变了，旧答复不能批准新版本；暂停目标可以答卡，但修改工作等继续后重核版本。“请知悉”只把实际展示过的条目算作看过，不能因看了一页就漏掉其他通知。队列完整分页，待答和待落实项不因时间久而丢弃（决定 42、[决定 49 第 14、28 项](refactor/HANDOFF.md)；设计书 §1.4、§1.6、§6）。

### B12：按 Goal 设置自治级别

**触发**：用户确认目标和首个方案，或调整该 Goal 的自治级别（[HANDOFF 决定 15、21、35、37、42、49](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.3、§1.6、§2.7、§4.10）。

默认「方案确认后自动」：范围内细化、返工和重新检查自动推进，返工受上限约束；小的语义修补随工作生效，秘书的“请动手”“请回答”自动发出，短期线自动换手并进“请知悉”。结构性修补，改目标、验收或范围，超预算及上报，长期线换手或换职责，两档都进「需要你决定」。「每步确认」下，范围内细化、返工、重新检查、小的语义修补、秘书派出的“请动手”“请回答”、短期线换手、干预新建的小任务和创建成员，都先等用户确认。秘书因太长换手是例外，两档都自动换手并进“请知悉”；目标卡和第一个方案在两档下都由用户确认。

**结果/失败**：不同 Goal 按各自级别推进。改级别只影响之后的动作，不中断已在做的工作，也不自动发出原先待放行的消息。自动返工要让用户和秘书知道，不能悄悄反复重试（决定 42；[UI-WORKBENCH §0](UI-WORKBENCH.md#ui-decisions-2026-10)“自动返工的通知”）。通知的计数把两臂相加：重新检查那一轮自己的计数，加上它接着的重新入队；接着干的 Run 自己没有入队记录时，往前找到那次重新入队再算。

### B13：Goal 顺序与冲突提示

**触发**：项目有多个 Goal，用户调整顺序，或目标之间可能共享文件、模块（[HANDOFF 决定 15、17、35、42](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.2）。

目标顺序可见、可调整；争用同一个成员时，排前的先用。冲突提示说明依据，只作建议，不自动阻止领取或执行。“等前一个目标 / 调整顺序 / 接受风险并行”并列，不默认推荐等待；没提示也不代表已经证明无冲突。

用户选“等前一个”后，后一个 Goal 不开始新的修改工作；已在做的和只读问答、查找、出方案照常。等的是选择当时的前一个 Goal，后来调顺序不换等待对象；它完成或取消后解除等待。

**结果/失败**：接受并行风险后能查到针对哪两个 Goal、哪两版计划；任一计划变化且仍有冲突时重新提示。调顺序不停止正在做的工作，也不把已接受风险当作永久授权。

### B14：成员活动状态与可用动作

**触发**：用户查看工作线卡片、悬停信息卡或工作线详情（[HANDOFF 决定 13、25、30、33、35、38、45、49](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.5、§4.8）。

活动状态说明它正在做什么，不能只用“可用”代替。工作中、等回复、待命、已暂停、待核对、启动中分别显示；停止请求发出而尚未停下时带“停止中”。线自己的状态和需要关注的原因一起显示，三处一致；暂停不能盖掉待决定，退役不能盖掉结果待核对。

“已做完”表示还能接新任务；“已退役”表示不能再执行，原历史仍可读，也可以从保存记录派生「问一问」：由一次咨询 Query 读这条线的结构化历史窗口，准备好的那一轮冻结它读到的正文；Kernel 历史读不到时用平台事实模式，回答里写明看不到原历史。工作中、待命、已归档按工作线计数，不与职责配置数或正在运行的模型数混用。计数里的“待命”包括没有正在工作的未归档线，不只包括状态词为“待命”的线（设计书 §1.5“计数”；[UI-WORKBENCH §1](UI-WORKBENCH.md)）。

**结果/失败**：点工作线切到它的对话，显示实际可用动作；已归档或已退役的线只读。已做完的线可以直接干预，内容作为新任务，不重开已验收任务；所属 Goal 已完成时，先请用户确认成新 Goal。退役、没有接续且执行结果未知时，自动维护先保留待核对，用户认定后才归档；Turn 还开着时，认定后关闭悬空 Turn、回到可用、留在原 Session，不归档，只有读不到、关不掉或失败才归档（决定 38、45、51、[决定 49 第 21 项](refactor/HANDOFF.md)；设计书 §1.6）。

### B15：计划候选审阅与执行结果审阅

**触发**：有两类独立审阅，触发和归属分开（[HANDOFF 决定 13、35、49](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §2.9，承接 B06）。

计划候选审阅：所有 agent 候选在自动采用前必须由独立审阅线审阅 `pass`；没有审阅线时转候选卡，不发明“审阅通过”（PL-1 已落地）。已有代码工作区的首个方案审一次；首案判定和实现归 6C L7，空工程不审；意见交给写方案的秘书并写在卡上，不挡人采用（首案部分待 6C L7）。

执行结果审阅：仍只在采用的计划要求时起审阅者，结论进 B06 的检查证据，归第 9 片，原样不变；没有这个要求时不强加审阅者。

计划候选审阅在独立上下文里看目标、已采用计划、这一版新写的任务书、义务和依赖差异、机械诊断，这些是审阅输入；审阅者另可只读代码、注记和图，仍不执行任务、不修改工作区、不写证据。不读执行历史或证据；只审这一版的改动，不重审已采用的段（PL-1 已落地）。执行结果审阅看当前代码、被审任务和执行事实、改动与检查结果，以及对应执行的原历史片段。被审成员忙碌或已归档，不妨碍在授权范围内读取这些已有记录；来源缺失或不可读时明确说明，不靠执行者自述代替。

**结果/失败**：审阅结论带依据。计划候选审阅的结论只用于自动采用或候选卡，不是完成证据（PL-1 已落地）。执行结果审阅怎样进入 B06 的检查证据归第 9 片。缺少要求的审阅或证据过期不能算通过。两类审阅的一轮都只出结果，不替被审成员返工或修改计划（[HANDOFF 决定 49](refactor/HANDOFF.md)；设计书 §2.9“审阅与工作权限”）。

### B16：持久等待、超时与转交

**触发**：成员请求答复并等待，等待到期，或等待中的工作需要换手、归档（[HANDOFF 决定 13、35、42、49](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.9、§4.6）。

等待保留问题、收信人和期限。项目设置默认答复时限，发信成员可以另给；重启后继续核对原等待。等待从消息读出：一条已放出、`waitAfterSend` 的询问，加上让出执行的那次运行；状态是未回、已回、已到期、已消费或已撤回。到期告诉发信成员，由它决定再问、换人或不等；同一问题的追问链第二次实际到期进“请知悉”，到期输入写“第 2 次到期”。到期先记下，不算消费；Kernel 接受到期输入才消费。Work 的到期在原任务、原 Session 按 `expiry` 接续。秘书的回复和到期各开一轮：请求轮队列领取并启动，在请求现在的秘书上追加 `reply` 或 `expiry`；同一处理点的几条并成一轮，每条保留自己的 `relatedMessageRef`；`entered` 时按这一轮的 manifest Session 判，交接后的接手者也能答，并在同一提交里拿 `wait-consumed` 认领。到期先唤醒请求轮队列（队列开着时），由驱动追加 `expiry` 轮。重复读取不重复算到期，超时本身不证明原执行已停下。三种提交可以叫醒在等的目标：答卡（`SessionMessage`）、重新排队（`TaskRequeue`）、未知调用复核（`UnknownCallReview`）；订阅名单 `GOAL_WAIT_WAKE_AGGREGATE_TYPES` 加了后两类。自动返工确认的等待把依据写成 `['SessionMessage', 'TaskRequeue', 'Goal']`。

请求“还在处理”时能读出四种收尾：轮、回复、释放、候选（`readRequestMessageReasons` 读消息侧的回复和释放；理由顺序 round→reply→release→candidate）；读取失败是 `unavailable`，不能当成两项皆无。

同一处理点已经有回复，不再按到期未答处理。到期处理后才来的回复照常保存，在下一个安全点作为新输入送达，不重开旧等待。已让出、等回复的 Session 收到用户新输入时，在安全点优先处理，原等待默认保留，并通知相关委托者；新指令不冒充旧问题的答复。人插手正在等回复的线时，Host 以系统身份给等待的两侧、目标当前的秘书和参谋（有的话）各发一条“请知悉”，不开模型轮；开的那一轮是认领的干预自己的驱动（决定 49 第 17–20 项；7B-3 落地）。

归档仍在等待的普通工作线前，先取消等待，或转给用户选的另一条线，问题和期限不变。秘书的等待跟着请求交给接任者；退役线归档不用先选等待去向，结果未知时仍按 B14 等用户认定。发到退役线的回复保留为未送达，提示用户选择转交，不能自动换收信人。同一项目里，转交可以落到另一个工作区的线：副本写在收件线的工作区，正文仍是原消息；只有另一个项目的收件线拒 `cross_workspace_forward`。取消或转移等待（`waits/dispose`）仍要求同一工作区，跨工作区同样拒。

**结果/失败**：用户可查到原问题、回复、到期或转交的经过。通信确实断开时，等待方、发送方和用户能知道原因与接管情况；断开项从事实派生，不另存通知；Host 在生命周期处理里给断开的两侧各发一条系统“请知悉”，不开模型轮。暂停或结果待核对时，输入可以排队，但不能据此启动修改（决定 49；设计书 §1.6、§4.6）。

Work 线中断后真的接上了才告诉人：新 Run 实际入场，接续说明 `mode='resume_after_interruption'`，同 Session 和新 Session 都算；普通返工、只建 Session 没入场、Goal 驱动重启本身、RUN-25 之后的自动恢复都不发（`createContinuationNoticeSource`）。

### B17：A.2 之后用真实模型重跑编排验收

**触发**：A.2 及后续编排能力完成，准备验收 MVP 的编排路径（[HANDOFF 决定 13](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §8.2 第 9 片）。

经用户授权调用真实模型，从正式入口重跑 E05、E06、E08、E09、E12，以及方案迭代、直接干预和等待。用户能看到实际并行与冲突处置、换手后的连续工作、变更落实、原历史与证据，并能沿记录核对结果。脚本模型、单项工具成功和旧版本的成功记录都不能代替这次验收。

**结果/失败**：逐场景记录通过、失败与未覆盖范围；未跑的不能标通过。当前进度见 [STATUS](refactor/STATUS.md)“缺口”；完成本项也不能代替其余 MVP 行为和新界面验收。

### B18：归档前处置责任

**触发**：用户归档一条工作线，或平台准备自动归档（[HANDOFF 决定 13、35 · Q1、42 第 1 条、43、45](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.8、§4.5）。

任务已完成、已取消或已被替代，负责关系自动结束。还有没做完的任务时，当场选择“交给…”或“放下”；放下后任务仍在，只是暂时没人负责，等重新派工。等待的处置见 [B16](#b16持久等待超时与转交)。

归档的提交同时放掉这条线的责任：开着的负责 goal/project 链接、参谋和书记的 module 区域链接一起关，它们的 `role-scope:` claim 一起释放，席位也释放；直接 `sessions/archive` 和归档步的提交带同一份释放计划。执行者的 module 链接不在这里处理，归维护者一支：一条执行者线对某个模块开着的负责链接就是该模块的维护者，一个模块只有一个维护者，链接和 `module-maintainer:` claim 在同一次提交换手；人可以经卡或路由指定、改派，成员用 `assign_module_maintainer`。归档这个链接时，第一条合格接续只限自动维护的 `handoff_complete` 默认选择：按当前职责解析结果判断，要求这条线还在活动、当前职责解析为执行者，不看建线时保存的席位；职责为 `unknown` 不算合格，职责读取失败拒绝这次维护。没有合格接续就放下，不沿接续链继续找。人直接归档按其保存的 `transfer`/`drop` choice 处理，可以明确指定转交的目的线。参谋、书记的 module 链接不做选择，由归档计划关闭。模块因此失去维护者时不另发通知或卡。重新启用一条归档的线，在同一次提交里重新准入并加回持有，不写预留；到上限一样拒 `capacity`。

有工作执行在跑时，先请求停止；停下前显示“归档中 · 停止中”，不能转移负责关系或完成归档。结果未知时须由用户认定，平台不能自行当作已停下。退役、没有接续且结果未知的线，自动维护先保留“已退役”和“待核对”，等用户认定（决定 45）。认定以后，Kernel Turn 还开着的线由维护关闭悬空 Turn、回到可用，不归档；关闭不了才归档（决定 51）。

异常锚点按 lead 的做法处理，设计书 §1.8、§4.5 仍标为【提议】：平台在任务及所属 Goal 上记录谁、在做什么、为何中断、改过哪些文件和结果尚未核对；拿不到改动就写“改动未知”，可能混有别的执行的改动也要说明。改动留在工作区，不撤销，也不算通过；任务显示“中断，待核对”，接手执行带上锚点。原来暂停的任务仍等用户点“继续”。

**结果/失败**：任务重新派工时，先复用合适的其他 Session，没有才新建；「方案确认后自动」下自动再派，「每步确认」下先确认。归档或退役中断不算失败、不占返工上限，是决定 43 下 lead 的做法，设计书仍标为【提议】。归档中途失败时，已经完成的处置保留，并说明“处置已完成，归档没成功”；归档不删除历史。

### B19：agent 派工与建成员

**触发**：agent 要挑选工作者、派工，或现有工作线不适合、需要创建成员（[HANDOFF 决定 13、35 · Q19、49 第 16、22 项](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §2.5 的 J1、J2，§2.11、§4.10“创建权限”）。

平台先按事实排序，agent 可以改派；先复用合适的成员。选线按六键依次比：负责本任务、负责本任务模块、同目标历史、职责相符（今天在筛后为常量）、最近活动、Session 键（`projectId`、`sessionId` 升序）；有明确负责本任务的线时，先按同一过滤和键读它，再进同一排序。比较结果随推进返回（`PickBasisV1.rank`），不另存。目录一页 50 个、最多 8 页；可恢复的补充读取失败记 `incomplete` 后继续，负责链接或目录读不到时等待；读超上限也记 `incomplete`，不冒充完整。普通派工只从可用的线里挑，排除只读副本、等回复、退役和归档中的线，不按显示名猜责任。

没有合适的线时，有参谋先发给参谋；没有参谋出成员卡，人批准后建线；建线之后才领取 Task，绝不先领取。

所有有权派工者发“请动手”前，都核对活动计划版本、当前理解指针版本和目标派工序号；首次允许明确表示“尚无当前理解”。自动模式下过期就退回重读；「每步确认」下在放行时核对，过期则重出或不发。成功重试回原回执，不重复派工；“请回答”不做这三项核对。

参谋、具明确委托权限的执行者可在职责内创建成员，说明职责、范围和理由；「每步确认」下先出一张建成员卡，「方案确认后自动」下直接建、带一条“请知悉”。创建是一条 `member_create` 操作，带阶段，每次写入一个键，重放只读投影、不写第二次；建出的成员记 `MemberCreated`，`createMember` 只取 Host 授予和建线者上限的交集，秘书建出的执行者固定为 false。固定工人、秘书、书记和独立审阅轮不继承创建权限，秘书、书记需要时请参谋；平台挑选或新开秘书仍属请求分配。

每条角色线占一个席位，按项目、按职责算。准入读这个项目的 `open` 上限，判 `holders + reservations < open`；默认秘书 8、参谋 8、书记 4、执行者 16。到上限拒 `capacity`，原因一句写职责、持有数、预留数和上限；不先收回，也没有结构化明细（收回和明细归 7D2）。准入写一条预留，注册时换成持有，同一请求重放不再写。审阅者算在执行者的池子里。只读副本和职责 `unknown` 的线不计席位：不写预留，也不写持有。完整的交接里，第一个建出的接任者可以借源线的席位：不写预留、不写持有、不进上限计数；部分交接的接任者自己过准入，可能撞上 `at_cap`。上限由人读、人改（`projects/role-limits`、`projects/role-limits/set`），写带 `expectedRevision`，可以只改一项；调低不撤已有的持有，下一次准入按新值判。

**结果/失败**：能查到派给了谁、依据哪版计划；过期派工不能发出，无创建权限不能自行建成员。优先并行文件、模块不重叠的任务。同一目标里，两个任务声明同一模块、另一个正在跑，就是重叠：先挑不重叠的，只有没有不重叠候选时才看重叠任务的门。门按（目标、任务、模块）一条记录，请这个目标的参谋（没有就秘书）给该模块写一条约定或决定的注记，注记要晚于冲突 Run 的开始游标才算满足；人也可以带理由释放。门的服务和记录已落地，L1 已接进选任务的推进步骤。版本检查不证明语义相容，实际冲突仍由正式检查和返工处理。

### B20：直接干预

**触发**：用户在工作线对话里选择“问一问”或“直接干预”（[HANDOFF 决定 10、35 · Q18、38、49 第 21 项](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.6）。

“问一问”从保存的记录派生只读副本，不打扰原线的工作。“直接干预”把消息发给原成员，在下一个安全点送达，分别显示已排队、已送达、已生效或被拒绝。

空闲线手上有没做完的任务，就带着消息继续；没有任务的活跃目标，在这条线上开一次只读的干预规划 Query（`intervention_planning`），回答带完整计划草稿，平台交 `plans/propose` 照常校验和采用；采用后领取第一个可做的任务。已做完的执行者线也可这样接新任务，已验收的任务不动。新建小任务会多一个计划版本：「方案确认后自动」下自动采用，「每步确认」下先确认，见 B12。

干预的四种收尾都要让人看见：模型反问，问题出卡、不发通知，模型的原回答作为对这条消息的回复（送达投影把已有回复算作已送达）；人答卡只保存答案，不续开模型轮，要继续需再发消息；回答不合法（含 `questions: []`），一条固定通知加回复，没有提案；Query 没答就结束（含崩溃重开），一条固定通知，消息撤回；人放弃或替代了方案（`not_adopted`），一条固定通知加回复，不沿 `replacedBy` 追。方案还在等采用（`candidate`）时消息留着，采用后照旧 `claimFirstReady`。放弃干预候选和提议入口用同一条来源规则（`isInterventionSource`），不再只认 request 根。通知先写，再写回复或撤回；系统 Host 只为“正式终结、没有答案、同一条收件线”的干预来源撤回消息。

**结果/失败**：所属 Goal 已完成时，先请用户确认接续的新 Goal（`intervention_new_goal`），再建小任务并正常采用计划；原 Goal 的完成事实保留。已归档或已退役的线只能“问一问”。目标暂停、取消或执行结果待核对时，干预保留排队及原因，不能代替继续或认定；恢复或核对完成后重读版本，取消目标须先复制成新目标。复制目标时勾过的干预，等新目标首个方案采用后转发；原收件线没了时停在“待你指定收件线”，由用户选新的收件线（`FORWARD_DESTINATION_GONE`）。

E01–E04 通过只报告“首条 E2E 已贯通”。产品 MVP 还须覆盖 E05–E22，并在[当前 PRODUCT §10](PRODUCT.md#10-验收与成功标准)约定的本项目与一个外部维护项目上保留真实任务证据。新增项的依据见 B11–B20 和 [HANDOFF 决定 10、13、15、17、18、21–23、25、30、33、35、37–39、42、43、45、49](refactor/HANDOFF.md)。项目与样本在验收时选择；不把尚未运行的场景写成结果，也不强加大型模型对照实验。

**E05 加核对（决定 89，去重 skill）。** 两个任务实际并行、时间上重叠，都需要同一条校验规则；副本在任务开始之后才埋入，这样它总能被查到。分三处核对：

| 核对项 | 期望 |
| --- | --- |
| 接口约定 | 只交给一个任务写，另一个任务引用它 |
| 比对工具 | 机械候选里列出埋入的副本 |
| 审阅者 | 独立判断它是同一条规则 |

另外三项也要核对：一组“名字不同、规则相同”应报；一组“名字相同、规则不同”不报；临时件在做完之前已经收回。脚本模型的渲染测试证明不了模型的判断，不拿它冒充这一项。

重复候选由 `project_source` 的 `compare` 带 `duplicates: true` 给出（`files/compare` 的同一输入也透传）：两份捕获、两个 Git 提交、一个提交对当前工作树三种比较都适用，只从这一次比较之后那份材料里找，列新加的顶层定义和新加的达到 `DUP_MIN_STRING_CHARS` 的字符串字面量，各带两处位置；扫描数、跳过数和输出截断分开报；只给候选，不判断两条是不是同一条规则（`src/core/workspace/duplicate-candidates.ts:66`）。

每份验收报告记录：代码/文档版本、环境和真实配置、目标/授权、初始文件版本与必要未提交快照、实际入口操作、对象引用链、产物/检查/证据版本、最终状态、故障与恢复结果，以及明确未覆盖项。模型和命令调用次数用于证明查询/重放没有额外执行；性能或成本提升另需同输入实测。

## 6. 骨架测试与实现验收的交接

本节将引用讨论中的失败来源问题落实到现有[两阶段施工方式](refactor/DSH-WORKFLOW.md)，不启动本次文档任务之外的源码施工。

1. 每个行为测试标出本文行为/场景编号、真实目标入口和关键用户结果。夹具通过公开生命周期建立必要前置；纯单元测试可隔离依赖，但不宣称它证明生产链。
2. 骨架红测须报告实际到达的未实现入口、失败类型及调用路径。fixture 缺字段、依赖注入错误、无解释超时不计为有效红灯，应先修测试环境或定位问题。
3. 逐项区分已执行断言、被未实现入口阻断的后续断言、尚未有用例的行为。首行抛 NotImplemented 不能证明后续持久化、历史、覆盖或完成已经受测。
4. 中审核对后续断言能识别“返回空对象”“只改 UI”“把 Run ended 当 Task 完成”“seed PASS 绕过真实检查”等假实现；不只断言 defined/status 字符串。必要时用针对性错误实现验证测试敏感性，不要求每批建设通用变异测试系统。
5. 冻结接口与测试后再实现；最终重跑确认后续断言实际到达、无跳过，并从真实生产者→正式记录→消费者→用户结果核查接线。测试 fake、类型检查和总测试数不替代 E2E。
6. 按既定独立副本流程验收，记录目标能力和限制。校验遵守真实可达生命周期；不引入全账本屏障、未来完整语义证明或已授权动作的额外审批。
