## 1. 产品定位

Agent Platform 为一个用户提供长期、统一的项目协作界面：讨论需求与架构，查看多个 Project/Workspace 的工作，组织多个 Agent 实现、调查、审阅与交接。图形、文本和可定位的依据共同说明正在做什么、为什么这样做、哪些事项需要人决定。

面向人的主对话是默认入口；它是一个交互面，不是一个 Session（§1.1）。秘书、参谋、书记、执行者与审阅者表达业务职责，可以按工作需要组合（每个 Session 承担一种职责，建 Session 时定，运行中不换，见 §1.2）；不要求每种职责对应一个永远运行的模型，也不要求所有成员通信和工具调用经过一个主 Agent。不再单列“协调者”职责，协调由秘书和参谋做（[HANDOFF 决定 37](refactor/HANDOFF.md)）。人默认不必管理每个 Agent，但可以查看、点名询问、追加要求或接管具体工作；各职责怎样和人打交道、为什么这样设，见 §1.2。

2026-09-28 用户进一步明确：简化执行主体不抹平面向人的职责侧重。**秘书**帮助用户理解、表达与掌控项目，可形成可视化、文档和改进后的提示词；**参谋**调查技术选型、实践与 trade-off，辅助架构决策并监看实施方向；**书记**核查事实、管理历史/设计文档、整理开发流程并辅助准备和派发审查。这三种侧重都可以与用户对话，可组合于当前 Agent，也可因上下文或判断独立性分开，不要求启动即创建三/四/六个 Agent。**协调**优先由相关工作者经双图和邮箱直接解决；确因上下文限制需辅助时作为临时局部参谋，涉及设计取舍反馈架构决策者和用户。**审查**按任务选择复杂度/架构、实际完成、计划符合等重点，不固定每次全查。详细动作见[行为与按需分工](refactor/AGENT-ROLE-ACTIONS.md)。职责指令不自动授予工具，也不以名称强制角色转交。

**上段按后来的决定读（2026-10-13 补记）。** 上段是 9-28 的原文，照旧保留；其中三处要按后来的决定和既有规则读。“可组合于当前 Agent”：主对话不再是一个 Agent，而是一个交互面；三种侧重由秘书、参谋、书记各自的 Session 承担，职责在建 Session 时定，运行中不换（[HANDOFF 决定 37](refactor/HANDOFF.md)；AGENTS.md 第 4 条；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §4.10）。协调“作为临时局部参谋”：不设单独的协调者，协调由秘书和参谋做（决定 37）。书记“辅助准备和派发审查”：书记协助准备审查，但不自行启动正式审阅；正式的独立审阅只在采用的计划要求时由 Workflow（按规则推进工作的部分）启动（决定 49 第 22 项；设计书 §2.5 J13；依据 [MVP 行为](MVP-BEHAVIOR.md) B06）。另外，书记不建成员，返工、重新检查和改工作计划要转给执行者或参谋（决定 49 第 22、24 项；设计书 §2.9、§4.10）。上段链接的[行为与按需分工](refactor/AGENT-ROLE-ACTIONS.md)已标历史，也按这些决定读；当前分工见 §1.2。

产品以**数据结构及其原子操作**作为共同基础。工具维护和查询真实文件、工作结构、历史、来源与关联；业务规则、Skill 和 Agent 使用这些能力决定下一步。工具结果反过来更新相关状态和图，这一闭环属于用户原始设计。复杂的查询、比较、范围检查和一致性维护封装在核心中，不让每条业务流程重复实现。

连续相关工作默认复用合适的 Session，并增量补充材料；独立工作需要独立上下文时并行使用不同 Session。**同一工作区内按实际范围支持多 Agent 并行是产品要求**。减少重复取材、准备、扫描和状态维护，应同时改善效率与成本；不能先把它们当作只能二选一的目标。

`coding-agent` 是当前选定的执行内核，继续承担模型循环、实际工具执行、原始会话记录和执行恢复。平台保存自己拥有的工作状态与关联，并提供桥接；不另造一套内核日志或恢复系统。所需能力有真实缺口时允许必要扩展，配置项或相同 Session ID 不能冒充已实现。

### 1.1 人的交互体验：为什么重要，应当是什么感觉

**为什么重要。**

- **人的注意力是产品要解决的问题之一。** 早期定稿把“人的注意力”列为问题来源，第一条产品主张就是“可读性与注意力约束”：agent 一侧只装这次必要的上下文，人一侧靠界面把相关信息收拢（历史 PRODUCT §1、§2，2026-09-20 用户确认定稿）。§1 写的秘书职责，也是帮你理解、表达与掌控项目（2026-09-28）。
- **你几次明确的不满，有不少出在交互上，设计因此改过：**
  - 被机制挡住。当时的未决清单里有一项“首个 baseline 之前的探索路径、草案准入及初始化入口”（第 13 段的“对应原清单事项”），要你回答。你的原话：“什么叫没有baseline？怎样开始？哎，我红温了”（第 13 段）。设计改成：没有 baseline 不是不能开始的理由（§5.1）。早期定稿也把“人想了解一个关于项目的问题时，机制把用户拒绝掉”叫作“毛病一：死板”（历史 PRODUCT §2.2），另把“用户询问状态会打断正在执行的 Agent”列为问题来源（历史 PRODUCT §2.1）。
  - 找不到成员的对话。你看原型时问：“为什么我点击左边的那些角色的卡片，我不能够直接跳转到他那边的对话？”（决定 33）。设计改成：点任一条工作线，中间就切到它的对话。
  - 被反复问工程问题。你的原话：“那你直接写啊，我我也不知道为啥我要问这个问”（第 08 段）。设计改成：职责落点、文件划分、索引、接线由工程负责人自己处理，不包装成你的取舍（§7）。
- **你是客户，可以挑交互来看。** 决定 46 记下你的答复：你是新手，看不过来全部规格；但你也是客户，可以挑交互体验和行为感受来看。决定 50 把这写进了分工。所以 §10 列了 lead 提议的交互验看项【提议】，你可以增删。

**原则：你做决定，不当调度员。** 按设计书 §2.2 的四类判断者（决定 13、15、20）：

- 你：提目标，采用方案，答复决定，暂停、取消，手动归档；随时问，随时插话。
- agent：谁来做，何时换手，出什么方案，要不要上报。
- 平台状态机（按明确条件改状态的规则）：按证据判断“能不能”，从不挑活。
- Workflow：排顺序、给默认人选，按机械规则处理生命周期，不调模型。

所以你不用分派每个 agent。停下的工作在回复到了、有成员空出来时自己往下走，不用你点“推进”（决定 35 · 推出 1；做法【提议】，设计书 §2.10）。

**为什么这样设。**

1. **职责是配置，不是人。** 你的原话：“我觉得Agent他不是人，不是员工，他只是一段contacts”（第 01 段；同段前文说 Agent 的本质是“LLM+contact context”，这里的 contacts 指 context）。同段里你说，agent 最核心的东西就是它的角色，具体做的工作、读到的信息属于 Session。所以职责可以复用，同一职责可以有几个 Session 并行，平台不建永久的 agent 名册。
2. **卡片按职位说明来读。** 界面上一条线仍像一张员工卡：负责什么、现在什么状态。你的原话：“就跟现实的JD以及分工，以及当下状态一样的逻辑就好了”（第 12 段）。决定 15 定了“成员是卡片”；决定 25、33 之后，卡片是一条工作线，“成员”只是从线推出来的视图。
3. **三种对人，两种干活。** 你 9-22 描述架构时说，直接面对人的是“秘书、参谋、书记这一部分暴露在外，负责架构决策以及和人类进行回应的东西”（DLG-037）；10-10 你又把这三种称为“和人类交互的Agent”（10-10 回复第 22 条）。执行者和审阅者专心干活，不直接要你决定（决定 37）。这样向你要决定的 agent 只有这三种，为的是主对话不被工作细节淹没（这个理由是 lead 在设计书 §1.5“真正的挑战在主对话”的答复；真实规模下还没看过，设计书 §9.4 风险 15）。
4. **要你决定的事，先经一个负责的成员。** 执行者、审阅者的事要不要问你，由参谋判断，再转成卡，卡上写明来源（决定 37、49；设计书 J18）。卡和「需要你决定」里的是同一项，在哪处理都算处理完（决定 37）。
5. **没有主 agent，也没有协调者。** 你参考 Cursor 的做法：成员各自领取、分工，“而不是一个主Agent管所有的子Agent来实现大的代码仓库的协作”（DLG-037）。与此一致，没有单独的协调者，协调由秘书和参谋做（决定 37）；成员经两张图和邮箱直接沟通（§5.2）；相关任务并行前由参谋定接口约定（决定 49 第 16 项）；不设主秘书、子秘书，也不另设固定的上下级（决定 49 第 10、19 项）。你 10-10 问过是不是还有集成、协调职责（10-10 回复第 22 条；lead 答复页第 22 条核到早先 PRODUCT §6.2 写过）；决定 49 定为不加新职责，协调、集成由参谋或执行任务承担（设计书 §4.10）。
6. **秘书只读，但能派工。** 你的请求交给秘书，由它决定交给谁，你不必管每个 agent（决定 37）。“只读”保证它自己不改代码、计划和目标；采用计划、改目标、记下你的话，仍由你点（决定 37）。派工受自治级别管：「方案确认后自动」下直接发，「每步确认」下先成卡，等你放行（决定 37）。发出前核对计划版本、当前理解版本和派工序号（目标每成功派出一次活就加一的编号），挡住拿着过期计划派工（决定 49 第 16 项）。
7. **秘书可以有几个。** 几个请求可以同时处理，不用排队；一个秘书太长就换手，带上当前理解接着做（决定 37、49）。
8. **不默认起一队 agent。** 项目开始只建一个秘书；参谋、书记第一次需要时建；执行者按任务建（决定 35 · Q22、37）。建成员只给参谋和有委托权限的执行者；秘书、书记需要时请参谋；独立审阅者不建（决定 49 第 22 项）。这一项你当时倾向放宽（除了被确定的 worker，其他都可以派子 agent，10-10 回复第 22 条），决定 49 选了答复页的 (a)。
9. **参谋、书记和秘书分开。** §1 记的 9-28 说法：三种侧重可以组合，也可以因上下文或判断独立性分开；决定 37 之后它们由各自的 Session 承担（§1 的补记）。书记审 agent 写的注记，审过才全项目可用（决定 35 · Q7），并核对图上的语义和代码、历史是否一致（决定 20）；参谋判断技术方向，也替执行者、审阅者把关要不要问你（决定 37、49；设计书 J18）。这样写的和审的、做的和把关的分开，是 lead 对“为什么分开”的理解【提议】。

### 1.3 两张图是核心：架构图和任务图

两张图的数据来源、一致性和维护规则见 §3。本节写它们各是什么、为什么是核心，以及哪些关键设计在构成它们、哪些依赖它们。

**各是什么。**

- **架构图**：项目现在由什么组成。系统 → 模块 → 子模块 → 文件；节点上有职责、接口、依赖、一句话语义，以及谁负责、谁在这里工作。已采用的结构、源码里观测到的关系和历史修订分开（§2、§3）。你的原话：“架构图是偏向当前的空间的”，用到 AST（代码依赖）、文件夹路径和语义标签（DLG-037）。
- **任务图**：工作是怎样一步步走过来的，接下来要做什么。目标 → 阶段 → 任务，加上每次执行、检查、返工、决定和证据；有计划、当前和历史，也留着还没细化的未来意图。基础定位是“monitor + 可编辑的参谋部白板”（§3）。你的原话：“任务图就偏向于历史的状态以及演进”（DLG-037）。
- **为什么分两张**：你的原话：“这两个图就包含了时间上的历史演进以及空间上的一些结构”（DLG-037）。架构图偏空间：项目由什么组成、谁在这里工作。任务图偏工作的演进：要做什么、谁在做、做过什么、结果和原历史在哪，还没细化的未来意图也放在这里。这只是侧重：两张图都有当前和历史，不把架构图限成只管空间、任务图限成只管过去（[意图与决定](refactor/intent/INTENT-AND-DECISIONS.md) U14）。你的原话：“架构图的历史需要存储，任务图本身其实就部分包含时序”（DLG-044 批注 5）。落到工作者上，[架构](refactor/ARCHITECTURE.md) §7.1 写的是：架构图的关联回答“现在谁在此工作或仍可咨询”，任务图的关联回答“谁承担过这项工作、结果和原历史在哪里”。

**为什么是核心。**

  - 工作区沙箱单个文件默认上限 2 MiB。编辑要把整个文件读入，超过 2 MiB 就改不了；新写或改完超过 2 MiB 也被拒（同一沙箱文件的 `maxFileBytes`）。平台没有改这两个默认值（`src/core/agent-runtime/observed-model-run.ts` 只传了排除路径）。
  - 平台自己的只读探索工具（按字面文字搜、解析符号、按段读源码）也按 256 KiB 读；搜索遇到更大的文件就跳过，在结果的 skipped 里列出（跳过），一次最多读 500 个文件（默认 200）（`src/core/agent-runtime/exploration-tools.ts` 的 `maxBytes`、`search`）。列文件和搜索一次最多扫 2 万个目录条目，超出的结果标 truncated（没列全），要缩小目录再查（同一文件的 `list_files`）。
  - 所以今天 agent 用读文件和搜索工具读不了、也搜不到超过 256 KiB 的文件。有命令行的工作执行（工作区既允许写、又允许命令时才有，而且机器上要有 bubblewrap，即 Linux 或 WSL；直接在 Windows 主机上没有命令行，设计书 §5.3、§9.4 风险 14）可以用命令分段看；秘书和「问一问」今天没有命令行（设计书 §5.3）。界面的目录浏览里，二进制和大文件不挡文件名显示（HANDOFF 2026-09-29“文件资源管理器修复”）。
  - 大文件分段读、按段建索引或摘要，目前都没有设计。
- 换手、归档多了以后，原始历史长期保留多少，还没定（[STATUS](refactor/STATUS.md)；设计书 §9.5）。

**方向、还没交付：不只是软件。**

- 有可能的依据（都是已有的设计，不是验证过的能力）：
  1. 四种基础数据（会话/工作 × 文件/产物，当前 × 历史，§3）里没有只属于代码的维度。这是 lead 的推断，没有验证。
  2. 架构图按探索出的语义分组，文件是叶子，不按文件夹（决定 17）；非代码材料按路径、文本、语义建索引，不对所有文件硬套 AST（[意图与决定 §3](refactor/intent/INTENT-AND-DECISIONS.md#3-核心概念接手时直接采用)）。
  3. 注记失效按文件摘要比对，不看文件类型（设计书 §3.7，【提议】）。注记的全文查找不用模型，中文先切成 2 字片段再建索引（决定 49），所以中文写的注记也能用关键词查；工作区里的文件没有这种索引，只能按字面文字搜（上限见上面“超大文件”）。
  4. 交接靠索引加修改历史，接手的按需去读。你当时说的就是代码或文档：“因为你是一个代码或者说文档的，然后就就把索引给他”（第 11 段）。
  5. 领域专家 = 知识库 + Skill + 配置，不是一种新的 agent。你的原话：“领域专家这个东西，在我看来，就是外界知识库加上skill，加上这样一个配置的”（第 01 段）。长期知识库和自动积累经验是后续方向（§6.4、§9）。
- 换到别的领域，下面这些要找替代，目前没有设计：代码依赖（import、AST、符号）、测试作为检查证据。这是 lead 的判断。
- 你给过三个真实工作区候选，材料正好不同：中文 Markdown 加 CSV 论文索引的资料库，Markdown 课程加 Python 的学习库，C++、Python、YAML 的 ROS2 机器人工程（[端到端](refactor/skeleton/END-TO-END.md) §8.1）。三个都没选作验收工程，也没跑过它们的检查。ROS2 那个 2026-09-29 做过只读浏览和打开文件，平台里这个项目也有过几次只读查询（HANDOFF 2026-09-29 的“文件资源管理器修复”和“历史核对”两段）；另两个只在 2026-09-26 核对过目录。

## 2. 共同概念

| 概念 | 产品含义与区别 |
| --- | --- |
| Project / Workspace | Project 组织项目工作，Workspace 对应登记的工作目录。首版单用户、单机可管理多个项目/工作区；同一 Workspace 内也必须支持合理并行。 |
| Goal / Plan | Goal 表达用户目标，Plan 表达已采用的推进安排及完成要求。用户可以修改；变更有范围、版本与依据。首版一个 Goal 绑定一个 Workspace。 |
| Task / Attempt | Task 表达工作意图及逐步明确的完成条件，未来节点允许暂缺验收或分配；Attempt 是一次尝试。返工可继续同一 Task 并新增尝试，不能抹掉旧失败。 |
| Run / QueryRun | 一次真实执行；QueryRun 用于实际需要模型的查询。文件、图和历史的普通读取不必创建其中任何一种。执行结束不等于任务完成。 |
| Role / Skill | 可复用、可版本化的职责、能力配置、工作方法与指令。相同配置可以服务多个独立 Session，不表示它们是同一个永久主体。 |
| Agent / Session | Agent 是参与工作的执行或协作角色；具体对话、读取结果和连续工作由 Session 承载。Session 可含多次 Run，也可先后承担相关任务。平台保留其角色、任务、模块和内核记录的可查询关联。 |
| Context | 本次模型调用实际可见的指令、历史与材料。它与完整 Session 历史不同；连续执行必须证明必要历史真正进入后续输入，不要求每轮全部重装。 |
| 架构图 | 项目由什么组成、职责/接口/依赖是什么、涉及哪些文件及工作者；区分已采用结构、当前源码观测和历史修订。 |
| 任务图 | 协作白板、状态监测及历史索引：目标、当前意图、分工、关系、执行与结果；包含计划、当前和历史，不替代 Agent 的编排决策。 |
| 工具结果 / 证据 / 决定 / 交接 | 工具结果记录实际观察；证据关联适用来源和完成要求；决定保留选项与明确理由；交接保留义务、前沿及来源。模型的完成陈述不自动成为完成证据。 |
| 记忆 / 知识库 | 有来源的经验、偏好和资料，可按需使用、纠正和维护；不替代正式授权、当前进度或验收记录。完整长期领域专家与自动积累是后续扩展，当前不宣称具备。 |

角色配置、Session、Run 与 Context 分开管理。归档表示退出活跃使用，不等于删除历史；项目归档也不自动销毁文件、会话和证据。需要清理时使用明确的数据处置操作。

### 2.1 未来方向：按项目复杂度逐步展开工作者

2026-09-28 用户提出的未来方向：面对约 10 万、100 万行等规模项目，从少量必要上下文开始调查，逐步形成架构及工作分工，不先为角色名或目录创建整队 Agent。架构初始化应从入口、包/模块边界、现有设计和代表文件取得粗粒度地图，标注未探索部分，再围绕实际工作展开；不需要先读完所有文件才能开始。这个方向在产品里的位置、和已定的 MVP 能力怎样分开，见 §1.4。

用户 9-28 给出的“一个 Agent 关注约 1–2 万行、上下文接近 500K 时考虑换手/压缩”作为**待验证的容量规划参考**保留，不是当前默认硬阈值。这句是转述，仓库里没有逐字原话（转述另见[架构 §7.3](refactor/ARCHITECTURE.md#73-未来方向渐进架构初始化与按复杂度分工)末段和[行为计划](refactor/AGENT-BEHAVIOR-PLAN.md) §1）；[行为计划 §6](refactor/AGENT-BEHAVIOR-PLAN.md#6-对齐注意力与异步感知)引用的 9-28 外部分享对话可能是出处，没有核实。决定 49 另定：换手的“太长”按最近一次模型输入量算，可配置，不超过实际模型容量，约 500K 只是待验证参考；压缩条件另外配置（[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.1、§4.11）。代码行数不等于上下文 token；可用容量还取决于实际模型配置、材料相关性、历史/工具结果占用和任务耦合。图节点可保留而不配 Agent；已有相关且可用的 Agent 优先复用，需要独立上下文/判断时再增加。

目标能力包括局部探索与地图逐步展开、按工作/上下文负担分配模块、接近实际容量时定向取材或压缩/交接，并保留义务、决定、产物和未决引用。这需要编排、容量反馈与生命周期管理，**仅配置提示词不能实现**。大规模容量规划仍是待验证方向；按含义挑成员、按需建成员和换手已由[决定 13](refactor/HANDOFF.md)列入 MVP，不能因早期 AG6 只做职责装配而继续后置。压缩按决定 39 不算 MVP 门槛，未支持时用换手接续（[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §4.11）；实现状态见 [STATUS](refactor/STATUS.md)。架构落点见[架构 §7.3](refactor/ARCHITECTURE.md#73-未来方向渐进架构初始化与按复杂度分工)。

## 3. 数据基础与两张图

本节写两张图的数据来源、一致性和维护规则；两张图为什么是核心、哪些设计在构成和依赖它们，见 §1.3。

用户提出的四种基础数据，是“会话/工作与文件/产物 × 当前与历史”两个维度：

| 来源 | 当前 | 历史 |
| --- | --- | --- |
| 会话与工作 | 活跃 Session、角色配置、正在承担的工作、可调用性与占用 | 原始会话、工具结果、执行记录、明确决定与理由、交接和责任演进 |
| 文件与产物 | 当前代码、文档、路径、内容与可解析关系 | Git 版本、必要的未提交内容快照/补丁、产物版本和来源 |

四种数据互相关联，进一步形成架构、任务、Session 关联、通信、证据等专用结构。它们可以使用不同索引、算法和持久形式；不要求全部压成一张通用图，也不等于要新建四套完整事实副本。人的明确要求、外部回执、确定性工具观察及模型提案都记录真实出处，不能用“只有三类采集根”否认这些来源。

图是数据、关系与操作能力，不只是展示层：正式职责、采用关系、责任和版本需要保存；查询索引、布局及部分摘要可以重建。图按邻域定位相关文件、任务、Session 与历史，工具再按精确引用取回内容。已知文件路径或记录引用时可以直接读取，不强制先查全图。

架构图同时表达采用结构与实际观测，两者不一致时展示差异，不能为了满足目标形状删除真实观测边。明确采用的硬产物消费前置保持无环；预期依赖、分组、消息、责任关联与这类前置分别表达，图上有边不自动阻止启动。实现→检查→返工可以重复，通信也可往返；执行历史按事件追加。时间线增长不自动证明工作有进展。

工具结果应局部维护相关结构、引用与状态；不能把普通事实记录变成审批动作。目标或正式结构变更按已授权范围受理并保留历史，而不是全图删除重建。Git 不自动保存未提交内容，Session 摘要也不代替当时文件版本。

两张图由成员在约束下共同维护。书记核对语义与代码、历史是否一致，合并重复内容、标出过时内容并提出修订。成员在本次工作范围内提交语义修补，与代码改动一起检查。小的语义修补在「方案确认后自动」下随工作生效，「每步确认」下先确认；结构性修补两档都进「需要你决定」。摘要和记忆不能改任务或执行状态（[HANDOFF 决定 20、21](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.3、§3.1、§3.6）。

任务图的基础定位是 **monitor + 可编辑的参谋部白板**，同时提供 Session、工具结果、变更与证据的检索入口。它记录编排意图与结果，不替代模型基于规范和架构作出的编排决策。不能为了确定计划或开始并行，先做一次近似实际任务的全量语义分析、读写范围证明或模型审批；实际完成后的核对仍然需要。图中的预期依赖、可能影响、未知范围只作为信息；明确采用的具体产物消费条件在需要该输入时检查，不自动要求对方整个 Task 完成。此处恢复[历史产品 §7.2.5](history/before-2026-09-22/PRODUCT.md#725-任务图monitor--可编辑的参谋部白板)的定位，并按[最新用户纠正](refactor/intent/2026-09-23-PARALLEL-AND-PRODUCT.md#4-2026-09-24任务图不是事前并行安全证明)澄清其边界。

“产品图”保留为产品能力、用户路径、范围和验收依据的轻量版本化表达，可使用本文件的表格或图示；不要求另建第三套运行时图系统。

**2026-09-26 补充：未来意图必须留在任务图中。** 只有基础预设、尚无完整验收条件的任务，也应能作为未来节点保存、查询和继续细化。记录已知的标题、意图、来源和范围即可；依赖、角色分配及验证办法允许暂缺。这样长程执行在反复拆分局部工作后，仍能找回原目标中尚未推进的方向。节点存在、条件已备、已分配、取得执行权和正式完成是不同事实；不能因节点没有依赖就自动视为可执行，也不能把待细化节点从整体范围或未完成说明中隐藏。

校验按具体操作的后果设置：实际模型/工具副作用与正式提交保留权限、身份、所有权、代际、幂等及局部版本条件；普通查询和历史事实记录不机械重走新动作的整条准入链。规划是否充分、拆分是否最优、未来依赖是否完整由 Agent/Skill 判断，不成为未来节点入图的硬门槛。记录已经发生的终态仍核对原 Run/Attempt 与来源，不能因为后来撤权就抹掉事实；释放占用另核对当前 owner/generation。详细依据见[本次用户补充](refactor/intent/INTENT-AND-DECISIONS.md#2026-09-26-补充未来意图节点与校验边界)。

## 4. 用户应得到的能力

| 能力 | 用户可观察的结果 |
| --- | --- |
| 统一工作台 | 在一处切换项目、讨论需求、查看架构/任务/Agent/历史及其依据；打开应用即可接上已有工作，无需重新讲述项目。 |
| 直接查事实 | 问状态或定位文件不必打断执行者，也不因缺少 Run、baseline 或在线 Agent 被人为阻塞。材料缺失、未授权、能力不可用与确实不知道分别说明。 |
| 共同形成方案 | 能与秘书/参谋讨论需求、架构、依赖和取舍，追问既有方案的理由、依据及备选，而非每次重写方案。 |
| 自主推进已授权工作 | 实现、验证、进度更新和普通协调在已有范围内闭环；不反复确认同一授权，新的实质取舍才交给人。 |
| 同工作区多 Agent 并行 | 根据架构和任务分工，核心工具检查真实范围和冲突，编排 Agent 修正安排；独立部分继续，共享步骤有明确协调。 |
| 连续工作与生命周期 | 相关工作延续合适 Session；需要时创建、打开、控制、重组、归档、重新启用，保留工作前沿和历史。压缩/恢复只按真实内核能力显示。 |
| 目标与计划可修改 | 人可直接提出修改，看到影响和差异；受影响执行安全切换，无关工作继续，历史决定与证据可追溯。 |
| 可见并可介入 | 查看谁在做什么，点名询问、追加要求、暂停、取消、换手或接管；知道动作是已请求、已生效、失败还是结果未知。 |
| 完成可核对 | 显示当前要求、有效证据与缺口；Run 结束、文件存在或 Agent 自称完成不能直接使任务变绿。 |
| 架构持续演进 | 发现、解释和处理已采用结构与实际实现的差异，记录决定、理由及影响，避免长期无声漂移。 |
| 能力与经验可复用 | 选择版本化角色/Skill，按需使用已有材料和有限记忆；看清配置能力、实际授权与当前可用能力的区别。 |
| 成本与性能可解释 | 看得到重复工作是否减少、必要调用与恢复成本；不将旧实验数字或预测金额当成本次实测。 |

“能询问”不表示强行编造答案或越权取材。优先读已有事实，必要时再咨询合适 Agent；没有在线负责人时仍可通过文件、图和历史继续调查。已知缺口应带可理解的原因和后续路径。

## 5. 核心用户路径

下列路径是用户结果与验收依据，不要求路由或源码逐步照抄。普通步骤可由确定性工具完成，只有需要判断或生成时才调用模型。

### 5.1 从零开始或进入已有项目

用户提出目标、约束及授权范围。系统优先复用已有项目、资料和 Skill；缺少现成材料时，在可用能力与授权内探索当前文件、查参考或形成待核实方案，明确资料缺口。新项目可先形成草案、创建必要目录和文档、安排分工，再逐步采用正式结构；没有 baseline 不是无法开始的理由。

人参与需要确认的需求与架构取舍。秘书先给 2–3 个简短思路，用户选一个后它出完整计划，在对话中迭代；每轮说明改了什么，满意后再采用（见 §1.1）。目标卡和第一个方案由用户确认，之后按该目标的自治级别推进（[HANDOFF 决定 15、35 · Q16、37](refactor/HANDOFF.md)；[UI-WORKBENCH §0](UI-WORKBENCH.md#ui-decisions-2026-10)“新增”第 1、3 条）。已获授权的实施可直接细化并推进；未经授权的目标/验收范围变化仍是候选。首次正式计划或架构采用具有可定位的版本，后续执行与之关联。

一个项目可以有多个 Goal，用户可调整先后顺序；争用同一个成员时，排前的先用。可能共享文件或模块的目标显示冲突提示，只作建议。“等前一个目标 / 调整顺序 / 接受风险并行”并列，不默认推荐等待，也不因提示自动拦住工作。只有用户选了“等前一个”，后一个目标才停止开始新的修改工作，已在做的和只读查询照常（[HANDOFF 决定 17、35、42](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.2）。

修复已有项目时先定向核实问题和相关结构，不要求先完整重读全仓、重建全图，再允许修一个已定位的问题。

### 5.2 多 Agent 并行实现

编排 Agent 结合规范、架构职责、任务白板和已有事实决定分工、顺序及并行，在**同一工作目录**也可同时推进。核心提供定向查询、比较、更新和执行工具；权限、数据版本及同一 Session 的占用在适用操作处检查。已观察到的冲突返回具体对象与依据，Agent 决定调整、隔离、协调或等待；不要求每个 Task 先提交完整未来读写范围并预占资源，也不因语义影响尚不能确定而统一禁止启动。

**注释：模块不同不自动证明互不影响，模块相同也不代表必须整体串行。** 共享接口、配置、生成目录、Git 操作或命令副作用可能相交；图用于定位与影响分析，不直接变成模块锁。预测影响与已发生的文件版本冲突分别表达。不能把所有传递依赖都锁住，也不能用 Agent 一句“允许并行”豁免实际冲突。不同 worktree 可以作为某项工作的隔离手段，但不是产品支持并行的前提。

局部编辑冲突不使整个任务或两个 Session 的成果作废。需要隔离时保留各自共同基线与实际变更，机械合并无冲突部分，协调冲突范围并核验受影响结果。编排结合任务前置、架构影响和实际副作用安排顺序；预测范围重合不直接等于禁止隔离执行，也不自动新增任务前置边。运行时隔离/集成与开发期 DSH 施工隔离分别设计，当前未实装能力不得显示为已支持。

同一 Session 的对话变更仍需避免竞争，独立并行使用不同 Session。争用某个资源是协调/等待原因，不自动等于任务失败。修改结果、阻塞、证据与责任变更回流到相关图和历史，成员按需直接交流，不要求逐条经全局主 Agent 转发。

### 5.3 连续实现、检查与返工

系统从任务/模块关联查找合适 Session，核对当前范围与能力。相关工作优先继续原会话，补入新要求、差异和必要材料；一次 Run 结束不自动创建新 Session。并行调查、独立审查或不兼容工作使用独立 Session。

检查依据绑定实际文件/产物版本。失败时保留原结果，在有新信息或可说明的修正方向时继续；长期没有进展要改变方案或提出具体待决，不能无限追加相同尝试。完成只按当前采用要求与适用证据判定。

### 5.4 询问状态、追问方案与查历史

用户问“某模块现在怎样”，系统可按图缩小范围，直接查结构、文件、工具结果和相关 Session；需要该工作的理解或解释时，再咨询适合的 Agent。回答区分当前事实、历史观察、推断与未知，并能定位来源。历史查询不改当前状态，也不启动无关 Run。

追问“为什么选这个方案、依据是什么、还有哪些备选”时，复用已产出的方案版本、明确理由与材料。原 Agent 离线或 Session 归档不使模块和记录消失；完整历史不必每次全部装入模型。

### 5.5 修改目标、计划或正式架构

用户提出变更后，系统展示受影响任务、接口、工作者和证据，按授权范围形成并采用修订。停止受影响工作的旧后续派发，对已在执行的相关操作请求停止或切换；无关工作继续。暂时无法判断影响时明确保留缺口，不把未知解释为无影响。

已发生的文件修改和外部副作用不能假定撤销。旧结果可以保留，但通过新版本适用性检查后才能推进当前状态。接管相交资源前确认原写入已停止或已有可核对的交接；不以超时、界面状态或新负责人姓名代替实际确认。

### 5.6 直接介入、暂停与交接

主对话、图节点、成员卡片和点名操作都能定位相关工作与成员。点左栏工作线，中间切到它的对话；输入分「问一问（只读）」和「直接干预」，暂停、继续、取消也在这里。原来点工作线只展开摘要的做法按[决定 33](refactor/HANDOFF.md)替换，详见 [UI-WORKBENCH §0](UI-WORKBENCH.md#ui-decisions-2026-10)“新增”第 13 条。用户仍可查看负责人、任务/版本、最近进度、证据、待决项和真实运行状态，并追加要求、替换或接管。问一问怎样不打扰成员、直接干预怎样像用 coding agent 一样在安全点送达，见 §1.1。

控制请求与实际生效分开显示；不支持的控制有明确原因。交接保留目标、有效决定、未完成义务、阻塞、未验证假设、当前文件及历史引用。新执行者按需读取，不能要求人重新复述，也不能假称新 Session 就是旧 Run 原地恢复。

### 5.7 崩溃恢复和长期回查

内核恢复自己的会话/执行，平台恢复工作状态、关联和未决操作，并检查实际结果。请求重放不重复产生同一副作用；结果不确定时显示未知并核对。恢复并不等于回滚文件。

已完成工作在重启后可被相关新任务查询，保留原来源与适用范围；过期前提不能凭摘要重新成为当前事实。

## 6. 关键能力的产品边界

### 6.1 生命周期与持续可用

| 操作 | 何时需要 / 用户看到什么 |
| --- | --- |
| 创建或打开 | 新工作需要独立责任/上下文，或查到可用旧 Session。创建本身不意味着模型已经启动。 |
| 延续 | 相关工作与范围适合，必要历史进入后续执行；界面能追溯继续了谁及依据。 |
| 拆分或重组 | 工作可独立交付、原承担范围不合适或需要交接；新旧任务/模块/Session 关系明确，失败不丢原义务。 |
| 压缩 | 容量或质量确有问题时缩小当前工作集，保留关键事实、不确定性和来源；按实际内核能力执行，缺能力明确不可用。 |
| 归档 / 重新启用 | 无未交接活跃义务时显式退出活跃管理；后续需要时核对并重新启用合适会话，或保留来源后另建会话。归档不删除模块。 |

显式操作可以由已授权 Agent/业务流程发起，不等于每次要求人点击批准。首版不默认建设每轮都重组上下文的通用优化器。面向人的入口持续可用，不承诺永久在线进程或模型零延迟。

压缩不算 MVP 门槛；能力不足时明确说明，线太长时换手。已做完的执行者线还能接新任务，已退役的线只能查历史或「问一问」。已完成 Goal 上再加工作，先确认成新 Goal；取消 Goal 的“重新入队”也复制成新 Goal，保留原记录和终态（[HANDOFF 决定 38、39、49 第 21 项](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.5、§1.6、§4.11）。

### 6.2 角色、协作与责任

各职责管什么、怎样和用户打交道、能改什么、为什么这样设，统一见 §1.2（[HANDOFF 决定 37、49](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) J3、§4.10）。角色可复用和组合，不要求每个目录常驻一个 Agent，也不把同模板的多个 Session 当成一个不可并行的主体。

区分角色配置及长期适用范围、本次委托/验收范围、实际执行资源范围。每个工作包有明确交付负责人；不同工作包可以并行承担。跨模块任务保留一个可定位的交付责任，相关参与者提供意见或结果。共同决策有明确负责范围与版本，不保留“所有领取和提交只能经全局一个协调者”的产品限制。

讨论围绕具体问题、已有材料、分歧和结束条件。独立意见可以先并行产生，再针对分歧验证；没有新信息不继续循环讨论。消息携带任务、材料和版本引用，大产物按引用读取。读到、已读、正式回复、操作执行与任务完成分别表达，不能互相替代。

2026-09-28 补充：双图还用于定位变化应让谁知道。何时通知主要依靠心跳机械补查、文件增删行量和双图节点/边/状态变化量，达到配置阈值或待处理变化达到合并期限再交付；无变化不调用模型。相关Agent和用户可主动报告接口影响、失败、冲突或决定，不等待数量阈值。参谋收到线索后才判断意义，平台不持续语义筛选“关键变化”；大改动不证明重要，小改动也不证明无影响。按作用域合并变化，待命者处理必要增量，忙碌者在真实可用边界响应；用户暂停不因心跳解除，控制沿实际Runtime/Kernel入口执行。具体策略及尚未接通部分见[异步感知与冷启动](refactor/AGENT-BEHAVIOR-PLAN.md#6-对齐注意力与异步感知)，不要求事件全部汇集到一个全局Session。

### 6.3 Skill、工具与权限

Skill/Prompt 是正式产品资产，指导调查、规划、分工、解释、协商、验证和交接；按来源、版本、适用范围与实际效果维护，优先参考和适配已有优秀做法。用户应能查看和选择角色配置/模板及其职责、工具和材料要求；完整模板编辑器是否已交付以实际验收为准。

“物理上能做”“本次实际被授予”“推荐怎样做”是三件事。真实访问、写入与副作用由核心/执行端检查；Skill 不能自行扩权，也不因某个方法被配置就宣称其实现可用。已有范围内的普通工具使用不逐次问人，越过范围时给出明确需要的能力与理由。

推荐阅读范围、图邻域和材料清单是注意力引导，不新增一套逐条材料审批来限制合理调查。它们不改变真实项目/工作区权限。首批应接通目标/任务/历史查询、方案操作、领取协调、文件与源码搜索、合法编辑/命令、产物/证据、控制与交接等实际工作能力；未接通部分明确标出。

### 6.4 记忆、经验与知识扩展

有限记忆用于复用明确偏好、工具链、约定、决定理由和有来源的经验；用户可以查看、纠正和移除可维护条目。明确表达与模型推测分开，不给用户固化笼统能力标签。历史授权、当前完成状态和正式规范不能由记忆摘要代替。

知识和经验按相关性与适用性检索，不全部常驻加载。可重复方法可整理为 Skill，保留来源与失败条件；单次成功不证明通用最优。网络、知识库或材料不可用时说明缺口，不用空内容或模型常识冒充项目事实。

**记忆核心属于 MVP。** 包括两张图的节点注记、每个 Goal 和阶段上的“当前理解”、大小上限，以及按代码版本失效。事实指向固定版本，理解写成文字；所引代码或计划变了，标“需复查”。用户可以查看、修改、撤下，撤下后历史仍可查。书记做审查型维护，不另建一张任务图，也不能用注记改完成状态（[HANDOFF 决定 20、23、35](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.7、§3.1）。

查找工具按明确字段和固定规则读取；相同输入、权限、数据和规则版本得到相同结果，工具内部不调用模型。模型只决定查什么、怎样使用结果。注记的关系写在自身字段上，独立关系记录留作升级方案；注记只加一个全文索引，关键词全文查找提前到第 4 片。这替换决定 23 中“关键词搜索在 MVP 之后”的排期（[HANDOFF 决定 49](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §3.1）。

检索排序调优、真实 bug 效果评估仍放在 MVP 之后；长期领域专家、完整个人知识库、自动学习/经验积累及跨项目角色或记忆共享仍是后续方向。以上写的是已定范围，不是已建成的能力；交付情况只看 [STATUS](refactor/STATUS.md) 和[能力索引](refactor/IMPLEMENTED-CAPABILITIES.md)（[HANDOFF 决定 23、49](refactor/HANDOFF.md)）。

### 6.5 证据、状态与架构治理

平台维护 Goal/Task/Attempt/Run 的正式状态及证据、决定和来源。工具报告可机械核对的观察，Agent 提供带依据的语义判断，核心按采用要求受理状态变化。计划采用、完成和正式架构变更有版本条件；重复输入、陈旧依据和无效身份不能静默覆盖新状态。

关键判断保留可回查的原始来源与观察范围，摘要不替代原文；引用本身也不证明解释正确。缺少完成证据不能直接改写为代码未完成。模型能力、来源复核与人在重要取舍/证据冲突中的参与共同承担语义判断，不通过无限增加平台校验、Reviewer 或日常审批来承诺语义无误。

验证默认由工具、框架与必要的独立审阅闭环。缺失、失败或过期的必要证据不能被其它 PASS 遮盖；角色模板的建议产出不擅自变成新的完成门禁。没有可靠判据时保留待确认结果，不从模型自评或退出码推断业务成功。

架构持续对账保留已采用与观测的区别。已授权且明确的局部修正正常推进；职责、接口或范围变化通过统一界面让人知情，新的实质取舍才等待决定。隐藏节点、删除目录、结束 Agent 和撤销正式模块是不同操作。

### 6.6 上下文与检索成本

上下文按本次工作必要性选用，不按模块边界机械截断。稳定工作默认延续会话、增量补充；通过图、Session、版本化文档/产物和定向邮箱传递材料，而不是反复重述全部历史。

来源包括当前文件、人的要求、历史记录、工具/外部回执、相关资料与模型提出的待核实解释。它们的事实性质不同；工具应提供内容、范围、版本及可解释缺口，业务不手工重复整理多个索引。

Session 的原始记录与当前模型输入分开；保留明确表达的决定、理由和证据即可，不要求保存或还原模型未公开的内部思维过程。缓存是否命中与会话是否连续也是不同事实，不能只凭前缀相同或 Session ID 相同宣称延续已实现。

## 7. 人的授权与必要取舍

用户拥有目标、需求、主观标准和超出既定范围的取舍权。Agent 可以提出方案、解释影响，也能在已有授权内实施、细化任务和记录事实。人机入口不直接绕过核心改正式状态。主对话不是一个 Agent；秘书只读，不改代码、计划和目标，它出的方案是候选：第一个方案由用户采用，之后范围内的细化按自治级别采用。具体修改由有权的执行者承担，返工、重新检查和工作计划修改只由有权的执行者和参谋做，都遵守实际权限（[HANDOFF 决定 37、49](refactor/HANDOFF.md)；§1.2）。这替换早先“主 Agent 具备项目内写能力”的说法。

确认是**尚未授权决定**的生效依据，不是每次图刷新、查询、分工、测试或已授权变更的重复门槛。候选方案与已采用版本分别展示；真正改变目标/验收承诺、越过权限或存在无法自主解决的业务矛盾时，先准备可审阅方案，再说明选项、影响与推荐，请人作一次具体选择。

自治级别按 Goal 设置，目标卡和第一个方案在两档下都由用户确认。默认「方案确认后自动」：范围内细化、返工和重新检查自动推进，返工受上限约束；小的语义修补随工作生效，秘书的“请动手”“请回答”自动发出，短期线自动换手并进“请知悉”。结构性修补，改目标、验收或范围，超预算及上报，长期线换手或换职责，两档都进「需要你决定」。「每步确认」下，范围内细化、返工、重新检查、小的语义修补、秘书派工、短期线换手、干预新建的小任务和创建成员都先请用户确认。秘书因太长换手是例外，两档都自动换手并进“请知悉”。改级别只影响之后的动作，已有待放行消息仍逐条等用户处理（[HANDOFF 决定 15、21、35、37、42、49](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.3、§1.6、§2.7、§4.10）。

「需要你决定」是全局队列，分“要决定”和“请知悉”，目标栏显示计数。卡也出现在所属目标的主对话中，是同一项。每张卡可以先问秘书，再选项、写自己的话或给对象加批注。答复与落实分开显示；已答复、待落实的卡不再算待答，落实后可查改了什么。对象已经变化时，旧答复不能悄悄批准新版本（[HANDOFF 决定 15、37、42](refactor/HANDOFF.md)；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.4）。

工程负责人应自行处理职责落点、文件划分、索引/事务、冲突检查和接口接线，不把这些遗漏反复包装成人类产品取舍。人知情不等于人逐步审批。

## 8. 界面与信息组织

界面以[冻结原型](ui-reference/workbench-2026-10/README.md)和 [UI-WORKBENCH §0](UI-WORKBENCH.md#ui-decisions-2026-10)为准（[HANDOFF 决定 35](refactor/HANDOFF.md)）；冻结后的修改按该节和 [E3 界面待办](refactor/design/orchestration-2026-10/E3-UI-ITEMS.md)读取。项目导航、中心对话与观察、可隐藏和新建多页签的右侧双图/文件/命令区继续保留。

主对话是交互面，不是一个 Session。目标栏切换显示内容，每个请求写明交给了哪个秘书；秘书可以有多个 Session。这替换早先“主对话是传统 Session”“每个目标一条对话线”的说法（[HANDOFF 决定 37](refactor/HANDOFF.md)）。为什么这样设、怎样保持安静，见 §1.1；两张图在界面上怎样画、怎样看，见 §1.3。

左栏按职责分组列出工作线（卡片），“成员”只是推导出的视图；工作中、待命、已归档按工作线计数。卡片展示职责、负责范围和活动状态。点工作线切到它的对话，可回到主对话；摘要放在悬停信息卡中，「问一问」与「直接干预」分开。工作线卡片及其入口替换早先“角色信息按需展开而非常驻卡片”的要求（[HANDOFF 决定 15、25、30、33](refactor/HANDOFF.md)；[UI-WORKBENCH §0](UI-WORKBENCH.md#ui-decisions-2026-10)“新增”第 5、6、13 条）。任务过程仍默认折叠，节点点开看详情，原历史按需可读。

主对话和统一侧栏服务同一项目状态。架构图呈现职责、文件与当前/历史结构；任务图呈现计划、依赖、当前工作、历史尝试与结果；Agent/Session 入口展示角色、关联工作、真实状态与可用动作。图、名册和对话点名共享导航，不造彼此不同的接管界面。

图形与文字共同解释进度、阻塞、版本、依据与下一步。用户能从文件/模块定位任务、证据和相关 Session，也能从任务回到产物与来源。当前观察、历史结果、尚未采用方案和能力缺口有明确标识。

控制操作显示已请求与实际观察，不用假成功提示掩盖未停止的工具；查询界面不因打开面板就启动模型或拉取全量日志。进度/消息按实际变化更新，机械唤醒与检查不默认付出模型调用成本。

## 9. 当前范围与后续方向

| 跨项目 | 首版按项目/工作区作用域隔离；不默默从别的项目取材料或继承执行权限。跨项目只读检索、通信和执行是不同能力，未来明确授权后分别开放。 |

## 10. 验收与成功标准

产品必须用真实路径证明：普通事实查询不触发无关模型运行；相关工作真实延续；同工作区独立范围并行；冲突被发现并反馈给编排处理；目标变更只影响相关工作；暂停/交接/恢复保留真实状态；完成依据可追溯；统一界面可定位工作和历史。

**交互体验，按客户的眼光验看。** 决定 46 记下用户的答复：用户是新手，看不过来全部规格；但也是客户，可以挑交互体验和行为感受来看。决定 50 把这写进分工（[HANDOFF 决定 46、50](refactor/HANDOFF.md)）。下面是 lead 提议的验看项【提议】，用户可以增删；每项都出自已有决定，不是新的验收要求，也不是已通过的结果。新界面做好后，用真实路径看：

1. 从左栏或主对话上的“交给 秘书 n”，一步进到任一条线的对话（决定 33、37；[UI-WORKBENCH §0](UI-WORKBENCH.md#ui-decisions-2026-10)“新增”第 13 条；[MVP 行为](MVP-BEHAVIOR.md) E16）；从图节点能找到相关的线（§5.6）。
2. 「问一问」不打断那条线手上的工作（决定 4、15；UI-WORKBENCH §0“新增”第 6 条；E22）。
3. 「直接干预」在下一个安全点送达，状态按 已排队 → 已送达 → 已生效 / 被拒绝 如实显示；被干预的线真的收到（UI-WORKBENCH §0“新增”第 6 条；决定 49；E22）。
4. 打开应用就接上已有工作；换手以后，接手的不要求用户重新讲项目（§4；决定 35 · Q6；E04、E06）。
5. 默认不弹浏览器通知；“请知悉”只列上次看过之后的新事（UI-WORKBENCH §0“新增”第 4 条；决定 42 第 10 条；E13）。
6. 失败和受阻不被折叠藏掉，能点到证据和相关对话（决定 49；E12）。
7. 查询、悬停、展开、切页面不启动模型（决定 17；UI-WORKBENCH §3 第 7 条；E04、E12）。

另外，主对话在真实规模下挤不挤还没看过（见 §1.1“还没验证的”；[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §9.4 风险 15）。验看时同时记录观察，供以后定，不列为验收要求。

整体产品验证保留历史提出的两类真实项目：本项目，以及一个可运行、问题可复现、变更范围可控的外部维护项目。记录起始版本、环境、要求/授权和验收依据；行为夹具与单元测试用于覆盖边界，不能冒充真实用户路径已经跑通。具体项目与样本在对应验收任务选择，不把本文件写成已完成实验报告。

确定性状态查询在其声明范围内应与正式记录一致；未知、缺失、过期与投影延迟必须可见。自然语言解释另看事实依据、来源覆盖与恰当的不确定性，不笼统承诺所有回答 100% 正确。每个完成结论有当前适用依据，失败能说明已知原因与尚未确定部分。

**本轮重构验收**按用户最新要求，重点对照可读性、调用跳转、重复规则/实现、代码变化及 UI 行为，并执行与所改行为相关的必要检查。不另把大规模模型对照或删减编排实验作为开工/每批验收前置。若声称性能提升，就提供相同输入下捕获、解析、读取、写入或调用量的实际对照；若声称统计不退步或金额收益，再提供支持该结论的测量，不能由模块数/行数推断。

独立模块、真实接线、整体产品分别验收。文档接口、编译通过、空目录、总返回 unsupported 的占位实现及测试 fake，都不能作为目标能力完成的证据。旧实现退役与真实消费者切换必须可核对。

## 11. 成本口径与历史数字

成本从设计阶段考虑，默认以合适 Session 连续复用为比较起点。关注重复探索/输入、模型调用、检索与解析、持久读写、等待、失败重试、压缩/重组及恢复；实现、调试和维护成本也要说明，不只看输入 Token 单价。

对可能明显增加上下文重建或编排调用的策略变更，应按真实模型配置、请求规模和有效计费信息说明成本影响。缓存输入、非缓存输入、输出及供应商实际单列项目不重复计费；延迟和维护投入单列。缺少数据时明确缺口，不虚构金额；不把与上下文成本无关的目录/接口重构全部变成“先计算模型账单才能受理”的流程。

交互体验也有成本，都还没实测：秘书先给 2–3 个思路再出计划，一条指令至少两次模型调用，每轮修改再加一次（[编排设计书](refactor/design/orchestration-2026-10/DESIGN.md) §1.1、§9.4 风险 10）；「问一问」每次追问都新建只读副本（决定 35 · Q2）；目标暂停期间也能只读问答（决定 49；10-10 回复第 14 条），每次问答都要调用模型；几个秘书同时派工时，版本核对会把秘书退回重读，每次重读多花模型调用（风险 13）。要说这部分成本，按实测补数，不估金额。

历史文档的 **99% 可复用热调用缓存命中期望**保留为有条件的性能方向，不是所有请求、模型或操作的统一门槛，也不意味着达标便代表任务质量合格。测量必须说明分母、冷/热调用、模型配置和范围，不能更换分母宣称达标。

历史 89.99%/89.10%、相应样本及“命中 0.02 元、未命中 1 元/百万输入 Token”的计算，只保存在[原稿 §9](history/before-2026-09-22/PRODUCT.md#9-成功标准含成本口径)作为当时记录和假设。**本次没有复跑那些实验或核实当前价格，不称它们为当前实测或当前报价。** 保留历史不等于要求先重新做一套实验才能进行本轮已授权重构。

## 12. 实现状态与共同审阅

本稿整合有效产品承诺与用户后续纠正，不宣称完整 Session 生命周期、同工作区范围并行、全部图/历史/UI 路径已经交付。当前状态、缺口和下一步统一看 [STATUS](refactor/STATUS.md)，源码和证据入口看[能力索引](refactor/IMPLEMENTED-CAPABILITIES.md)。[实施方案](refactor/IMPLEMENTATION-PLAN.md)、[执行计划](refactor/archive/2026-10-13-old-entry/refactor-plan.md)和[逐批验收](refactor/reviews/implementation-batches.md)保留为历史，不能据此判断当前完成范围；历史 P1 PASS 只覆盖其当时范围。

当前五模块/八条允许依赖、持久适配划分、Session 映射及运行恢复协议是[架构与模块](refactor/ARCHITECTURE.md)中的**工程选择**，不是用户预设的产品数量目标。目标使用源码依赖 DAG，不把它误作业务反馈图或开发串行顺序。产品同工作区并行与开发期共享文件负责人同样是两层不同问题。

每次产品或工程变更都共同检查：

1. 对应哪条用户原话、有效承诺或已采用工程决定；后续是否有明确纠正。
2. 用户可观察结果是否保留；普通查询、已授权推进、连续性与并行是否被新增流程阻断。
3. 架构职责、模块 Port、状态机与真实消费者是否一致；实现缺口有没有如实标注。
4. 是否复用了适用实现、删除了无消费者副本，界面能否解释当前状态与历史依据。

若当前产品、架构、模块或原话互相矛盾，记录具体位置和处理理由并同步当前文档，原始记录保持不动。接手者应通过这些共同依据继续工作，不靠聊天记忆，也不靠旧文档的“已决”字样覆盖用户后来的明确要求。
