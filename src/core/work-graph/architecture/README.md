# src/core/work-graph/architecture：正式架构目录与观测架构的纯算法、编解码和读写服务（L2）

## 负责什么，不负责什么
- L2，允许依赖 `model`、`state`、`persistence`、`knowledge`；另用 `workspace` 与 `record-store` 的端口。不得 import `sessions/queries/tasks/notes/evidence/communication/views`、`src/core/agent-runtime`、`src/app`、`src/business`、`src/composition`。
- 管两个不同的面：观测架构是某一次有界源捕获的证据，永远不是正式 baseline；正式 catalog 是已采用的模块/依赖结构，有单独的 `baselineId`/`revision` 和 active pointer。正式架构的初始接受（`adoptInitialArchitecture`）和修订由 `catalog-service.ts` 负责；`architecture-service.ts` 只做观测捕获/查询/比较，不做正式接受。
- 写入只经注入的 `GoalRecordTransactionPort`（`src/core/record-store/ports.ts:192`）一次提交，记录/事件编解码复用 `persistence/`；自动捕获请求/失败的受保护状态经 `state/architecture-capture.ts` 构造，状态迁移只经 `state/`（根 `AGENTS.md` 第 9 条）。
- 记录/图 DTO 的正本在 `src/contracts/architecture-*.ts`、`src/contracts/governance.ts` 与 `src/contracts/core/`（身份/结果/拒绝）；本层只声明端口和转出的 `GraphWrite`（`src/core/work-graph/architecture/contracts.ts:16` 只是转出；正本在 `src/core/work-graph/model/task-contracts.ts:28`），不另建平行身份或结果类型。
- 只做形状、身份、版本与纯图算法：不抓源码（`WorkspaceTools` 做）、不写 SQL/事务、不做 UI 读模型、不做决定/迁移门。
- 读失败、损坏或缺失保持 `unavailable`/`rejected`，不猜空目录；路径和名字只是标签，不能证明语义移动或依赖关系。

## 文件
- `architecture-file.ts` — 正式架构的知识文件格式（纯）：`architecture.json`（本工作区的根模块、跨工作区的依赖和包含、baseline 字段只写在主工作区的文件里；按第二工作区读时接受并略过 baseline，因为同一个检出可以是别的项目的主工作区（R6），这个项目的 baseline 取它自己主工作区的；写第二工作区的文件时 `architectureFilesOf` 的第四个参数给这个文件现在的字节，里面原有的 baseline 原样写回，不读、不改）和一个模块一个 `modules/<fileId>.json`；`prettyJson` 写键排序、两格缩进、末尾换行的字节；模块文件里的编号是本工作区的原样编号，路径和指向别的工作区的引用按文件帧写。读回 `architectureOfFiles`：精确的键 → 冲突（同一编号两个文件、指向不存在的编号就整份不可用；同一路径两个模块认领只通知、照常读）→ 包含关系全有或全无 → 从根经包含可达 → 在原样编号上跑 `validateAdoptedArchitecture` → 转项目视图，模块按编号、依赖按 (from, to)、包含按 (parent, child) 排序；任何一步不过整份 `invalid` 带路径，不给半张图。 `architectureFileOf`、`moduleFileOf` 是单个文件的解析（索引按文件建行时用）。
- `architecture-delta.ts` — 纯观测图差异（结构 key 与 digest 的增删改）、SCC 环成员与 `compareObservedGraphs`；不产出 baseline 或规则结论。
- `architecture-record-codecs.ts` — observed capture 的 body/chunk/记录/事件 codec、schema 注册与 `mergeObservedFileGraphChunks`。当前格式是 v3（决定 79-1，只读 v3）：正文 `schemaVersion: 3`（`architecture.edges[]` 每条带必填 `count`），文件块 `schemaVersion: 3`、边是 `[i, j, count]`，记录里的清单 `schemaVersion: 3`；v1/v2 的正文、块、清单直接拒（`invalid`/`unavailable`），不迁移、不补 `count`。正文的成员复核用和写入同一套分两层的归属（`ownershipRuleOf`/`ownerNodesOf`，快照里的完整映射）：模块节点含它接口里的文件，接口节点只含该接口的文件。
- `architecture-service.ts` — `ObservedArchitecturePort` 实现：源捕获、历史读、邻域/影响/比较、自动捕获、文件图分页与 chunk 打包、文件/分组搜索（`findArchitecture`）。省略 `mappings` 的捕获（手动捕获和自动捕获都走这条）读当前 catalog、投影到工作区、用 `mappingsOf`（模块和模块内接口）；“处数”在捕获时算一次、存下，读时只读：`architecture/query` 的 `edges[].count` 原样给出（跨模块是 `module_dependency`，同模块不同接口组之间是 `interface_uses`），文件页的 `edges[].count` 来自块里的第三项。
- `architecture-search-index.ts` — 纯搜索投影：basename/路径/模块名的匹配面、tier 排序、路径去重、正式 containment 祖先与搜索 cursor；不读记录，来源由 service 一次载入。
- `catalog-contracts.ts` — 正式 catalog 的 adoption/revision 端口、revision 快照与 module facts DTO。
- `catalog-record-codecs.ts` — catalog 记录/事件 codec、adoption 闭包校验、`architectureBaselineDigest` 与 schema 注册。
- `catalog-service.ts` — 正式架构的初始接受（`adoptInitialArchitecture`）、catalog 修订（`reviseArchitectureCatalog`）、revision 读取、当前 catalog 的 module facts、revision 的完整 pin（`catalogPinOf`）与 guards。 KLS-2b：当前读 `readCurrentCatalogWindow` 读项目每条线的文件、经 `projectArchitectureOf` 合成项目视图；`readCatalogModuleFacts` 带 `knowledge`；`reframeRepairOps` 是 R16 入口和注记文件帧共用的一次遍历（模块编号和路径），`opsInProjectView` 把调用者帧的 op 编号转成项目视图。
- `contracts.ts` — observed architecture 的记录/端口/DTO，以及本文件的 `GraphWrite` 转出（`src/core/work-graph/architecture/contracts.ts:16` 只是转出；正本在 `src/core/work-graph/model/task-contracts.ts:28`）。
- `file-graph-index.ts` — 纯文件级图分页：listFiles/neighbors/impact 与 cursor 绑定；边按 `(from,to)` 去重时累加 `count`。
- `formal-comparison.ts` — 正式 catalog 与观测文件图的纯比较（ownership/ambiguous/SCC 等 finding）；给了 `workspaceId`/`mainWorkspaceId` 时先经 `catalogForWorkspace` 投影，旧调用不给时行为不变。
- `graph-index.ts` — 纯观测图遍历：邻域、反向影响闭包、分页与 `encodeCursor`。文件锚点用和写入同一套分两层的归属（`ownershipRuleOf`/`ownerNodesOf`）：文件的模块节点，在接口里再加接口节点；模块平手时照旧返回所有平手的模块节点；没观测到的节点之后才丢。没解析的行只归给模块节点。
- `proposal-record-codecs.ts` — `ArchitectureProposal@1`/`ArchitectureProposalBatch@1` 记录与 `ArchitectureProposalChanged@1` 事件 codec、两个按项目 lookup 与 schema 注册；提案内容不可变，只有 `state`/`batchRef` 由状态机改，批冻结后不可变。
- `proposal-service.ts` — 结构提案 owner：pinned propose、批冻结、答复应用/关闭与读（规划回 `source_stale` 时先按应用命令的身份查回执，关闭提交或应用提交回 `replayed` 时也重放原结果，快速核对 5、8；进队前读到批成员已不是 `pending` 时也先查一次回执，写队列里排在前面的同一命令已提交就重放它的结果，不回 `invalid`）；唯一写提案/批记录并在提案路径调 catalog planner 的地方，试算复用 `planCatalogRevision` 后丢弃其 contribution；试算和职责读用 `platformCheckContext` 换成固定的内部 Host 身份，提案记下的作者仍是 Run。提议者只经 `proposerOf`：Work Run 读 `runFacts`，冷启动的探索 QueryRun 读必填的 `queryRunFacts`（只认 `role_exploration`）；冷启动的批窗口 `proposalBatchWindow` 只在冷启动停在 `proposals`、且提议的 `baseCatalogPin` 等于冷启动的 `baseCatalogPin` 时开着，此时新提案进 `pending_batch`，由冷启动一次冻结；提议提交带读窗口时冷启动记录的 revision guard，冷启动完成在待批读取前取 ledger horizon 并随完成提交。冷启动用的三个读：`readPendingArchitectureProposals`（项目未入批的待批提案）、`readFrozenArchitectureBatches`（同一 pin 上已冻结的批，恢复冻结后没存下的批）和它们共用的 `readProjectBatches`（项目全部批，结构提案卡的读源也用）。提案批的文件清单读 `readProposalBatchFiles` 只做一次只读试算（裁定 4-9）：在当前 pin 上跑 `draftCatalogRevision`，按每条线的文件判来源，未命名的新模块文件给 `path: null`，不入队、不取租约、不提交。
- `project-architecture.ts` — KLS-2b（A8）的纯合并 `projectArchitectureOf(parts, projectId)`：主工作区的 baseline 必须在；各工作区的模块和区内边直接并起来；跨工作区的边只在对端工作区也在项目里时进视图；包含关系全有全无；合并后在项目视图上跑 `validateAdoptedArchitecture`（查跨工作区的环和悬空）。还没写过架构文件的加入工作区不加模块。
- 7D2 XA 的批窗口（`createColdStartProposalWindow`）读两条探索操作：`cold_start:projectId`，以及调用方工作区非空时的 `workspace_join:projectId:workspaceId`；窗口只在所属操作处在 `proposals`、其 `baseCatalogPin` 与提议相同且记录未完成时开，返回该记录自己的 `{open, operationRef, revision}`，提交守卫用窗口自己的 `operationRef` 和 `revision`，不比较两条记录的 revision。
- `repair-ops.ts` — 唯一的 repair 操作纯解析/试算路径：note 写入、catalog 修订规划与结构提案共用；不读 catalog/baseline、不提交、不查 footprint。
- `revision-planner.ts` — 唯一的非提交 catalog 修订规划：校验 expected pin、跑 op 引擎、套删除与职责移动规则，返回整个 contribution；提交 owner 是 `reviseArchitectureCatalog`。

## 不要做
- 不要把观测 capture 当正式 baseline 或 adopted architecture；两者是不同聚合，正式采用（`adoptInitialArchitecture`）和修订只由 `catalog-service.ts` 负责，`architecture-service.ts` 不做这件事。
- 不要另写图遍历、SCC 或 cursor 编解码；用 `graph-index.ts`、`architecture-delta.ts`、`encodeCursor`（M1-37 的同类教训是别复制管线）。
- 不要用路径/名字猜语义移动、依赖方向或规则结论；差异只报结构 key 与 digest 证明的事实。
- 不要绕过注入的 `GoalRecordTransactionPort` 写记录，也不要手改受保护状态字段；状态写入只经 `state/`（`AGENTS.md` 第 9 条、M1-01）。
- 不要重排事件字段、改校验顺序或给旧格式补默认值；编解码走本层唯一注册（M1-37、CS-01）。
- 不要把缺失、损坏或不可读的 catalog/body 读成空事实或 `not_found`（FP-05、M1-12、MH-06）。
