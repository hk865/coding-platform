# src/core/work-graph/persistence：记录/事件编解码、提交编译与读取失败映射（L1）

## 负责什么，不负责什么
- L1，只依赖 `model`；不 import `state`、`sessions`、`queries`、`tasks` 等上层。
- 拥有记录与事件的 schema 注册、纯 encode/decode、`PreparedCommit` 的纯编译、索引完整分页读取，以及 Store 失败/游标比较到领域拒绝的映射。
- 只做形状、身份与版本校验；授权、容量、占用、业务选择和状态迁移规则都由上层 owner 决定。
- 不写 SQL、不开事务、不改变持久化字节：事件 JSON 的字段与顺序就是存储契约，不能用 canonical-key 序列化替代。
- 状态迁移仍只经 `src/core/work-graph/state/`；这里看到状态字段也只校验形状。

## 文件
- `command-executor.ts` — 写入执行器：一次原子写的唯一顺序（身份/指纹→回执查找→事实→决定→片段→guard 合并→提交前检查→一次提交→冲突映射/重试→严格结果投影）；唯一的 R2 哈希 `commandIdentity`/`commandKeys` 也在这里，执行器和推进写入共用；导出 `Keys`、`CommittedReceipt`、`CommitFragment`、`CommandRejection`、`CommandResult`、`WriteCommand`、`executeWriteCommand`，owner 只保留自己的事实、决定、片段与结果投影。
- `commit-compiler.ts` — Goal 创建的纯编译：identity/fingerprint、`GoalCreated` 事件、revision-1 快照与 guard 的 `PreparedCommit`，以及 caller version pins。
- `control-record-codecs.ts` — `ControlIntentSnapshot@1`、提交/观察事件、控制状态形状检查与注册。
- `decision-record-codecs.ts` — 决定写事件（`GoalSettingsChanged`、`WorkspaceNoticeSeenChanged`）、notice origin 解码与决定证明校验。
- `task-node-commit-codecs.ts` — `TaskNodeCommit@1` 的字段表 codec 与注册：`taskNodeCommitCodec`、`TaskNodeCommitted@1` 事件 codec `taskNodeCommittedCodec` 和 `TASK_NODE_COMMIT_SCHEMAS`；一条记录（`task-node-commit-by-goal` lookup）、一条事件。
- `goal-interruption-codecs.ts` — `GoalInterruption@1` 的字段表 codec 与注册：`goalInterruptionCodec`、`GoalInterruptionChanged@1` 事件 codec 和 `GOAL_INTERRUPTION_SCHEMAS`；一条记录、一条事件。
- `goal-delivery-codecs.ts` — `GoalDeliveryAcceptance@1` 的字段表 codec 与注册：`GOAL_DELIVERY_ACCEPTANCE_SCHEMA_ID`、`GOAL_DELIVERY_ACCEPTED_EVENT_TYPE`、`GOAL_DELIVERY_SCHEMAS`（一条记录、一条 `GoalDeliveryAccepted` 事件）、编解码 `encodeGoalDeliveryAcceptance`/`decodeGoalDeliveryAcceptance` 与 `encodeGoalDeliveryAcceptedEvent`/`decodeGoalDeliveryAcceptedEvent`（事件带整条记录，重放只读事件），以及 ref 键 `goalDeliveryAcceptanceRefKey`；没有 lookup，按完整 ref 的 canonical key 读。
- `dispatch-counter-codecs.ts` — `DispatchCounter@1` 的字段表 codec 与注册：`dispatchCounterCodec`（check/encode/decode/注册）和 `DISPATCH_COUNTER_SCHEMAS`（一条记录、零事件）；键是完整 ref 的 `canonicalJson`。
- `event-codec-factory.ts` — 事件 codec 工厂：固定“外层→解析→内外层一致→body”管线。
- `event-envelope.ts` — 外层事件信封编码。
- `event-validation.ts` — 外层信封、内外层一致、actor 与事件 body 校验。
- `evidence-record-codecs.ts` — 验证轮/证据/任务证据索引记录与轮事件 codec、相关查询索引。第 9 片加 VR-16 的入账事件 `VERIFICATION_REVIEW_EVIDENCE_RECORDED_EVENT_TYPE`（结果 `{evidenceRef}`，`a2RoundEventProblem` 核 Evidence ref）。
- `execution-entry-codecs.ts` — 执行进入的嵌套事实校验与授权/开始/进入/结果/对账事件 codec。
- `execution-history-codecs.ts` — `RunExecutionHistoryV1` 校验与 `ExecutionHistoryRecorded` 事件 codec。
- `field-table-codec.ts` — 字段表格式（`src/contracts/data-format.ts`）的 RecordStore 适配：由一份格式得到记录/事件 codec（check、encode、decode、注册、lookup）和 `formatSchemas`；encode 原样 stringify 调用者的对象，decode 不补值；事件复用 `event-codec-factory.ts` 的管线。本层不拼任何 bundle：组合根 `src/composition/create-platform.ts` 的 `schemas` 把每个 bundle 的 `records`/`events`/`lookups` 三行分别合并（7D2 的 `ROLE_LINE_ORCHESTRATION_SCHEMAS` 也是这三行），两后端只拿到这一份。
- `graph-repository.ts` — Goal 图仓库：一次读快照、幂等查找、单次提交、按 receipt cursor 重放恢复。
- `initialization-binding-codecs.ts` — `InitializationBinding@1` 的字段表 codec 与注册：`initializationBindingCodec`（check/encode/decode/注册/两条 lookup）和 `INITIALIZATION_BINDING_SCHEMAS`（一条记录、零事件）；键是完整 ref 的 `canonicalJson`。
- `initialization-adoption-codecs.ts` — `InitializationAdoption@1` 的字段表 codec 与注册：`initializationAdoptionCodec`（check/encode/decode/注册，键是完整 ref 的 `canonicalJson`，无 lookup）、两个重放事件 codec `initializationAdoptionAcceptedCodec`/`initializationAdoptionAdvancedCodec` 和 `INITIALIZATION_ADOPTION_SCHEMAS`（一条记录、两个事件）；进度规则调用 `C/validation/initialization-adoption.ts` 的同一份。
- `line-settings-codecs.ts` — `WorkspaceLinePinsChanged@1` 事件 codec。
- `line-record-codecs.ts` — 线记录 `Line@1` 的字段表 codec `lineCodec`、两个结果事件 `LineRegistered@1`（`lineRegisteredCodec`，登记和同一文件夹换分支）与 KLS-3b 的 `LineChanged@1`（`lineChangedCodec`，线结束），都带回答的整条线，重放只靠事件，和 `LINE_RECORD_SCHEMAS`（一条记录、两个事件、一条按项目的 lookup）；线的唯一读法：`lineRecordKey`、项目（或一个工作区）的线按建线时间排的 `readProjectLines`（带读位置 `watermark`，按它判定的写 CAS 在上面）、一个文件夹的线 `readLineRecord`；新 Goal/Session 取线的唯一规则 `lineForWrite`（给了文件夹就取这个工作区那个文件夹的线，不是这个工作区的线就拒 `not_found`；没给就取主线，工作区没有线为 null，多条线也不拒；已 `merged`/`removed` 的线也照取：平台为已有工作建的 Session——下一个 Task 的、问询副本、换手后继、成员线——照常进行，KLS-3b 裁定 2、lead 11-14 Q3）；点名一条已关闭的线的新活——Goal，或没有前任、建线意图和 Task 链接的 Session——由 `closedLineRefusal` 拒 `invalid`“a closed line does not take new work”（产品规则：关闭的线不接新活，旧记录照读、已有 Goal 照常领任务；Goal 和 Session 的 owner 在各自的回执查找之后调，合回前成功的创建照样重放，KLS-3b Astra 1）。放在这里是因为 `tasks`、`sessions`、`configuration` 都要用。
- `lookup-all.ts` — 等值索引完整候选集的稳定窗口分页。
- `knowledge-record-codecs.ts` — 知识写日志 `KnowledgeWrite@1` 和完成事件 `KnowledgeWritesCompleted@1` 的字段表 codec 与注册：一次知识写的每个文件改动一条日志（线键、路径、种类、模块文件的项目视图模块号、写前写后 blob、`since` 绑到携带这个文件内容的那个事件），状态 `pending`（在途）、`unconfirmed`（对账交给人的恢复项）、`completed`；两条 lookup `knowledge-writes-by-line-state`（project、lineRef、state）和 `knowledge-writes-by-state`（project、state）；`unconfirmed` 的事件 `KnowledgeWritesUnconfirmed@1`；`KNOWLEDGE_RECORD_SCHEMAS` 是一条记录、两个事件。
- `lookup-ordered-all.ts` — 有序索引完整分页读取。
- `module-overlap-gate-codecs.ts` — `ModuleOverlapGate@1` 的字段表 codec 与注册（记录 4）：`ModuleOverlapGateFormat` 定义 ref/revision/waiting/waitingAttempt/moduleId/running/planRevision/basisDigest/incomplete/noteRequest/release/since，导出值类型 `ModuleOverlapGateV1`、共享的 `NOTE_REQUEST_FIELDS`、`moduleOverlapGateCodec`（check/encode/decode/注册）、三个事件 codec `moduleOverlapGateOpenedCodec`/`moduleOverlapNoteRequestedCodec`/`moduleOverlapGateReleasedCodec` 和 `MODULE_OVERLAP_GATE_SCHEMAS`（一条记录、三个事件）；唯一的 `noteRequest` 规则只收两臂：有收件人时必带 `duty` 与 `messageRef`，收件人为 `null` 时只能带 `reason: 'no_adviser_or_secretary'`；lookup `overlap-gate-by-goal` 按 project/workspace/goal 等值、`since` 升序。
- `note-record-codecs.ts` — Note 记录/事件/索引 codec，含 cursor-bound 记录先例；Agent 来源的 `queryRunRef` 按字段表片段检查（null 或完整的 `QueryRunRef`）。注记头的 `structuralAutoApproved`（121-109）只能缺省或为 `true`，解码整对象透传，旧记录照读。
- `owner-record-read.ts` — 单条 owner 记录读的正本 `readOwnerRecord`（`OwnerRecordRead`）：一次 `readMany`、解码，缺失和坏记录分开；放在这里是为了 `sessions` 也能 import，`tasks/owner-record-read.ts` 只再导出。
- `plan-record-codecs.ts` — PlanProposal/PlanRevision 记录与事件 codec、proposal 链位置比较。`candidate_v2` 必须带 `catalogPin`（`KnowledgePinV1` 或 `null`，缺了就是坏记录，不补默认值；形状是 `contracts/knowledge.ts` 的 `KnowledgePinShape`，旧的 `{catalogRef, baseline}` 拒收、不迁移；钉不带项目，不再核“指向本项目”，L3）；`candidate_v2.sourceMessageRef` 必填，必须是 `null` 或完整的 `SessionMessageRef`（缺字段即坏记录）；`PlanProposalRecordedEvent` 同样必填可空的 `sourceMessageRef`，其可选 `acknowledgement` 由 `SessionMessageRefShape` 检查（7A §3.5）；`PLAN_PROPOSAL_SCHEMA_ID` 仍是 `PlanProposal@2`，两个 plan proposal 编码器原样带上该字段；`plannedFiles` 的四句格式检查；`requiredReadPaths` 只查形状（存在时必须是字符串数组，不查路径本身），因为 `plans/propose` 和 Agent 的 `propose_future_plan` 不经工具 schema 就到这个 codec，非数组值会让开轮时抛异常。
- `query-activity-codecs.ts` — `QueryActivity@1` 记录与 `QueryActivityRecorded` 事件 codec；tally 规则全部调用 `run-activity-codecs.ts` 的同一份校验器。
- `read-result-failures.ts` — Store 失败到 `CoreRejection` 的映射与游标下限检查。
- `receipt-lookup.ts` — 唯一的已提交回执存储查找：按 identity/fingerprint 精确 `lookupCommit` 并分类 found/missing/conflict/invalid/unavailable（抛错也记为 unavailable）；另有只按 identity 的 `lookupCommittedReceiptByIdentity`（found/missing/invalid/unavailable，坏行→unavailable）。导出 `CommittedReceipt`（`receipt-lookup.ts:4`）、`ReceiptLookup`（`receipt-lookup.ts:6`）、`lookupCommittedReceipt`（`receipt-lookup.ts:18`）。
- `record-guards.ts` — 全仓唯一的 guard 合并：同 key 不同 revision 立即 `revision_conflict`，绝不静默去重。
- `record-codecs.ts` — Goal 家族记录/事件 codec、`canonicalRefKey`、Goal/Workspace 设置校验。
- `rework-codecs.ts` — 返工/引用/notice origin 等纯形状校验（actor、Run、Session、Task 等 ref）。
- `run-activity-codecs.ts` — `RunActivity`/`ActivityRecording` 记录与事件 codec；`ActivityRecording` 的当前格式带 `querySince`（null = 还没有 Query epoch），facts/span/ref 校验器导出供 Query codec 复用；两种记录的 SessionRef 都用 `rework-codecs.ts` 的正本 `sessionRefProblem`。
- `run-record-codecs.ts` — `RunSnapshot@1`/`QueryRunSnapshot@1` 的纯校验唯一实现：两个 schema id、Run/QueryRun 形状检查、`decodeRun` 与 `Decoded`，以及 Run、任务 manifest、envelope 共用的工作区 pin 校验 `runWorkspacePinProblem`（带 `line`，经 `contracts/line.ts` 的 `lineRefProblem`）；`materials/record-readers.ts` 只保留注册和同名委托，`materials/run-snapshot-decoder.ts` 只保留 `decodeRun` 再导出。
