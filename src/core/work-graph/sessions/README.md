# src/core/work-graph/sessions：Session 目录、生命周期、消息与记录编解码（L3）

## 负责什么，不负责什么
- L3，允许依赖 `model`、`state`、`persistence`、`materials`、`architecture`；不得 import `queries`、`tasks`、`notes`、`evidence`、`communication`、`views`、`agent-runtime`、`app`、`business`、`composition`。
- 拥有 Session/CoreOperation/SessionWorkLink 的正式创建、注册与读取，以及 link/archive/reactivate、健康观测、责任转移和 Session/消息 codec。
- 状态迁移不在本层决定：生命周期、占用、归档与健康写入都经 `state/session-availability.ts` 的构造器和守卫，这里只收集事实、加 guard、提交。
- `tasks` 的事实只能经窄端口注入（如 `SessionResponsibilityBasisPort`），不能直接 import `tasks`；模块目标经 `architecture` 的 `readCatalogModuleFacts`。
- 不做 Query/Note/Evidence 的读取、调度或界面投影。

## 文件
- `lifecycle-contracts.ts` — link/archive/reactivate 的端口与 store 依赖类型，无运行时导出。
- `lifecycle-record-codecs.ts` — SessionWorkLink/归档/健康/责任事件 codec，复用既有 Session/WorkLink 记录 schema。
- `message-body-envelope.ts` — SessionMessage body 信封与用户决定 answer body 的编解码。
- `message-record-codecs.ts` — `SessionMessage@1` 记录/事件 codec 与消息查询索引；消息里的决定来源按 `DecisionSubjectShape` 校验（只有 `subject`，不再有并列的 `goalRef`），K3 已答复按来源 Goal 的索引路径是 `decision.source.subject.goalRef.goalId`。
- `recipient-executions.ts` — 撤回的收件方开放执行窗口读取。
- `session-activity.ts` — Session 活动记录（`SessionActivity@1`）：codec 与 schema 注册、ref/guard 助手、纯推进 planner 与读端口；只编码一条记录，状态写入仍由 `state/` 构造。
- `session-directory.ts` — Session 目录：Session 的正式创建/注册，写 SessionRecord/SessionWorkLink/CoreOperation/Kernel 映射 claim，并提供 Session 卡读取。
- `session-handoff-fence.ts` — 每个 workspace 的交接闸门：`secretaryHandoffClaimKey` 是前缀加 Session 聚合 ref 的规范 JSON（唯一键体）；`readHandoffFence` 按未完成阶段完整分页 `CORE_OPERATION_BY_WORKSPACE_PHASE_LOOKUP` 一次，取该 Session 的 `progress.fence.state === 'held'` 的交接操作，没有则是 `{held:false, operation:null}`，坏记录/读失败是 `unavailable`；`handoffFenceGuard` 是真实开始提交合并的空槽 CAS。它不返回 guards（开始提交的 claims 携带闸门）。
- `session-handoff-service.ts` — 交接 owner 的接受（`handoff.accept`）、归档 owner 的接受（`secretaryArchive.accept`）、推进（`handoff.advance`）和手动归档推进（`secretaryArchive.advance`）：经共用写入执行器记一条操作；拒绝顺序是 `state/session-handoff.ts` 的 `admitHandoff`/`admitSecretaryArchive`。`createSecretaryArchiveService` 的推进每次只提交一个父写，逐项按“已提交回执 → 未提交才查/调子”的顺序走；归档前写保存完整 `GraphWrite`（含 condition），登记读回原回执对；交接的归档臂在 `savedInput` 为 null 时遇到任何待处理归档请求都零写等待、停在 `incomplete`（此时那条请求必是别的请求；之前冻结只会钉住被释放移动的 revision 并换来 `busy`），那条请求完成或被放掉之后的下一趟才冻结新 pin。手动归档臂在同一窗口先用 handoff facts 的 `checkArchiveCondition` 预检，`ok:false` 只写 `archive:-:after:<g>` 和 `lastRefusal`、不保存 GraphWrite、不放行，重复失败重放同一标记；预检通过后才保存 `archive:-:before:<g>`。`advanceArchive` 只做前后父写，不调用 `append`/`archiveLineInternal`。同一文件还导出唯一的推进写入 key 构造 `advanceWriteKeys`（R2 哈希来自 `command-executor.ts`）、保存 principal 的 `savedHostPrincipal`/`handoffContextOf`、归档子步上下文 `archiveContextOf`、交接事件描述 `handoffRecordedEvent`，以及 `createSessionHandoffAdvanceService`：一次调用只提交一个父写，重放走 identity 读、继续按冻结阶段选一步，绝不调用子 writer。交接在通向归档的每个出口（后继完成、最后一条具名转移、routing 关闭）用已读的源卡和 `openResponsibleLinkOf` 检查分配之外仍开着的 responsible 链：有残留只写 `transfer:-:refused:<g>` / `routing:-:refused:<g>` 的阶段级标记（fingerprint 不含 horizon），停在 `transfer`/`routing`、带 `lastRefusal`、`archiveRequest` 仍 null、源仍 active、闸门仍持有；残留清除后同一操作经 `transfer:-:after:<g>` 继续，routing 只在残留清除后写一次 `routing:-:after:<g>`。归档的 partial 标记之后，若源仍拥有 processing 请求根，归档臂经同一次 horizon 读重开 routing：第一条 routing before 写 `raises:true` 只提一次 generation，登记、回执和保存的 `GraphWrite` 全部保留，新的 routing 关闭后再重放原 `GraphWrite`。本层不读 Note：简报的 saved refs 由 facts 层经注入的 `HandoffBriefRefsReadPort` 给出。
- `session-handoff-brief.ts` — D 在 entered 确认里调用的 `HandoffBriefPort`：只读操作、核对它仍持有未消费的 ready 简报，再经 `state/session-handoff.ts` 的 `consumeHandoffBrief` 给出要合并的记录和 guard；不写事件、不另存简报。
- `session-health.ts` — Host reconcile 的 Session 健康探测结果观测与写入。
- `session-lifecycle.ts` — link/archive/reactivate 写服务，精确 CAS Session 与 link。最终归档提交（首次尝试和崩溃后的恢复走同一 `runArchiveStepAttempt`）对存下的可信条件调用注入的 `SecretaryArchiveConditionPort`，把检查给的一个片段并进提交：`guards`（source 和 `SessionActivity` revision）经 `mergeGuards` 合并，fence claim 进 `claims`，第一次读的水位进 `PreparedCommit.ledgerHorizon`（绝不进 guards）；非 null 条件而没有注入端口是 `unavailable`，从不静默成功。`createSessionLifecycleService` 的依赖类型因此多一个可选的 `archiveCondition`。
- `session-links.ts` — 一个 Session 自身 work links 的完整读取（有上限，超限明确 `capacity`）。
- `session-record-codecs.ts` — Session 家族 schema 注册、纯 encode/decode、聚合键、provenance 等形状校验；`CoreOperation` 按 `action.kind` 分派到手写的创建分支或两张字段表，并检查顶层 `workspaceId`、每个嵌套 `projectId` 和只有创建才有的 observation。
- `session-responsibility-service.ts` — 责任转移与归档责任处置，绑定同一 commit cursor；`transferPinsOf` 是四 pin 顺序的唯一构造，`responsibleLinkRef` 是 responsible 链引用的唯一构造，`readTransferReceipt` 只读重放已提交的转移。
- `session-targets.ts` — 创建/链接目标的正式校验：Task 走 Goal+当前已采纳 Plan，Module 走当前架构目录。
- `trusted-context.ts` — 可信 Host 入口、写请求同步隔离、身份/指纹/事件 ID 助手。

## 不要做
- 不要 import 上层模块；本层只允许 `model, state, persistence, materials, architecture`。
- 不要复制 actor 校验：正本是 `src/core/work-graph/persistence/rework-codecs.ts:98` 的 `actorRefProblem`；`src/contracts/validation/identity.ts:5` 的 `validateActor` 是另一条规则（`void` 并追加 `ValidationIssue`，契约层也不能 import WorkGraph），二者不能互换（FP-17）。
- `sessionRefProblem` 正本在 `src/core/work-graph/persistence/rework-codecs.ts:154`；`src/core/work-graph/sessions/session-record-codecs.ts:163` 的 `checkPlainSessionRef` 是 planned 输入的报错适配器（S06，两种固定文字），不是它的副本，也不能换成它（CS-11、M1-31）。
- `sessionAggregateRefKey` 只有 `src/core/work-graph/sessions/session-record-codecs.ts:1157` 这一份；`secretaryIntakeKey`（`src/core/work-graph/model/request-contracts.ts:74`）仍内联序列化、带 `secretary-intake:` 前缀，是认领槽键（S10），不是它的副本，不要改写成它（M1-32）。
- 不要绕过 `state/` 写生命周期、占用或健康；所有受保护状态写入只经状态构造器（M1-01、M1-36）。
- 不要用裸 local id 拼 key 或另写聚合 key；用 `sessionAggregateRefKey` 等完整 key（M1-32）。
- 不要把失败读当空卡、把截断当完整列表、或把 intake claim 释放当 Session 释放（FP-05、M1-13、M1-36）。
