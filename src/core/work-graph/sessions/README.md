# src/core/work-graph/sessions：Session 目录、生命周期、消息与记录编解码（L3）

## 负责什么，不负责什么
- L3，允许依赖 `model`、`state`、`persistence`、`materials`、`architecture`；不得 import `queries`、`tasks`、`notes`、`evidence`、`communication`、`views`、`agent-runtime`、`app`、`business`、`composition`。
- 拥有 Session/CoreOperation/SessionWorkLink 的正式创建、注册与读取，以及 link/archive/reactivate、健康观测、责任转移和 Session/消息 codec。
- 状态迁移不在本层决定：生命周期、占用、归档与健康写入都经 `state/session-availability.ts` 的构造器和守卫，这里只收集事实、加 guard、提交。
- `tasks` 的事实只能经窄端口注入（如 `SessionResponsibilityBasisPort`），不能直接 import `tasks`；模块目标经 `architecture` 的 `readCatalogModuleFacts`。
- 不做 Query/Note/Evidence 的读取、调度或界面投影。

## 文件
- `lifecycle-contracts.ts` — link/archive/reactivate 的端口与 store 依赖类型，无运行时导出。
- `lifecycle-record-codecs.ts` — SessionWorkLink/归档/健康/责任事件 codec，复用既有 Session/WorkLink 记录 schema。
- `message-body-envelope.ts` — SessionMessage body 信封与用户决定 answer body 的编解码。
- `message-record-codecs.ts` — `SessionMessage@1` 记录/事件 codec 与消息查询索引；消息里的决定来源按 `DecisionSubjectShape` 校验（只有 `subject`，不再有并列的 `goalRef`），K3 已答复按来源 Goal 的索引路径是 `decision.source.subject.goalRef.goalId`。7B-1 注册两个消息查找名：`S7B_WAITS_BY_SENDER_SESSION_LOOKUP`（一个发送方 Session 的已放行/开放等待，按 `since` 排）与 `S7B_DUE_WAITS_LOOKUP`（一个工作区到期的等待，按 `deadline` 排），以及单独的 `S7B_SESSION_MESSAGE_LOOKUP_INDEXES` 数组（最后一个 spread，历史索引测试不动）；发送方索引等 S 的等待读取消费，本层只注册。
- `recipient-executions.ts` — 撤回的收件方开放执行窗口读取。
- `session-activity.ts` — Session 活动记录（`SessionActivity@1`）：codec 与 schema 注册、ref/guard 助手、纯推进 planner 与读端口；只编码一条记录，状态写入仍由 `state/` 构造。
- `session-directory.ts` — Session 目录：Session 的正式创建/注册，写 SessionRecord/SessionWorkLink/CoreOperation/Kernel 映射 claim，并提供 Session 卡读取；成员子线的创建提交在写 SessionCreated 后再写 MemberCreated（回执最后一条），`readOriginalSession` 只额外接受这一种两事件形状并按事件 id 从上一个游标读回 SessionCreated，`getSessionOperation` 按记录自己的 project/workspace 返回每个分支（成员操作也走这条通用读，创建入口自己拒绝非创建分支）；`normalizeCreationInput` 对 `consultation` 先校验 `mode` 与 `facts` 的两个互斥规则，再把载荷带进指纹与操作字面量。
- `duty-recipient.ts` — 按固定职责找收件人的唯一解析器：`createDutyRecipient` 的 `adviser`/`secretary`/`scribe` 三个臂都只留 `active` 和该职责；scribe 臂逐字保留旧闭包的行为（分页、按 `sessionId` 取最小、无健康过滤），职责读失败时 scribe 跳过该卡，adviser/secretary 返回 `unavailable`。`notes.resolveScribeRecipient` 保持同一公开面并调用它。
- `session-handoff-fence.ts` — 每个 workspace 的交接闸门：`secretaryHandoffClaimKey` 是前缀加 Session 聚合 ref 的规范 JSON（唯一键体）；`readHandoffFence` 按未完成阶段完整分页 `CORE_OPERATION_BY_WORKSPACE_PHASE_LOOKUP` 一次，取该 Session 的 `progress.fence.state === 'held'` 的交接操作，没有则是 `{held:false, operation:null}`，坏记录/读失败是 `unavailable`；`handoffFenceGuard` 是真实开始提交合并的空槽 CAS。它不返回 guards（开始提交的 claims 携带闸门）。
- `session-handoff-service.ts` — 交接 owner 的接受（`handoff.accept`）、推进（`handoff.advance`）、`handoff.decide`（审批卡的应用命令）与 `hand_off` 已提交回执查找（`lookupToolCommit`），归档 owner 的接受（`secretaryArchive.accept`）和手动归档推进（`secretaryArchive.advance`）：经共用写入执行器记一条操作；接受按源线固定 duty 与开着的 module `responsible` 链算 `short`/`long`，`tool` 触发再按源任务 Goal 的 autonomy 用唯一决定表得 `needs_decision`/`automatic_notice`，只有 `needs_decision` 写 `progress.approval`（pin 是接受 revision）；`decideHandoff` 只在 pin 未移动且仍 pending 时改 `approved`/`rejected`（拒绝把操作置 `failed`、源不动），`commandId` 即应用命令重放键；推进在所有阶段之前对 pending approval 零写停止；拒绝顺序是 `state/session-handoff.ts` 的 `admitHandoff`/`admitSecretaryArchive`。`createSecretaryArchiveService` 的推进每次只提交一个父写，逐项按“已提交回执 → 未提交才查/调子”的顺序走；归档前写保存完整 `GraphWrite`（含 condition），登记读回原回执对；交接的归档臂在 `savedInput` 为 null 时遇到任何待处理归档请求都零写等待、停在 `incomplete`（此时那条请求必是别的请求；之前冻结只会钉住被释放移动的 revision 并换来 `busy`），那条请求完成或被放掉之后的下一趟才冻结新 pin。手动归档臂在同一窗口先用 handoff facts 的 `checkArchiveCondition` 预检，`ok:false` 只写 `archive:-:after:<g>` 和 `lastRefusal`、不保存 GraphWrite、不放行，重复失败重放同一标记；预检通过后才保存 `archive:-:before:<g>`。`advanceArchive` 只做前后父写，不调用 `append`/`archiveLineInternal`。同一文件还导出唯一的推进写入 key 构造 `advanceWriteKeys`（R2 哈希来自 `command-executor.ts`）、保存 principal 的 `savedHostPrincipal`/`handoffContextOf`、归档子步上下文 `archiveContextOf`、交接事件描述 `handoffRecordedEvent`，以及 `createSessionHandoffAdvanceService`：一次调用只提交一个父写，重放走 identity 读、继续按冻结阶段选一步，绝不调用子 writer。交接在通向归档的每个出口（后继完成、最后一条具名转移、routing 关闭）用已读的源卡和 `openResponsibleLinkOf` 检查分配之外仍开着的 responsible 链：有残留只写 `transfer:-:refused:<g>` / `routing:-:refused:<g>` 的阶段级标记（fingerprint 不含 horizon），停在 `transfer`/`routing`、带 `lastRefusal`、`archiveRequest` 仍 null、源仍 active、闸门仍持有；残留清除后同一操作经 `transfer:-:after:<g>` 继续，routing 只在残留清除后写一次 `routing:-:after:<g>`。归档的 partial 标记之后，若源仍拥有 processing 请求根，归档臂经同一次 horizon 读重开 routing：第一条 routing before 写 `raises:true` 只提一次 generation，登记、回执和保存的 `GraphWrite` 全部保留，新的 routing 关闭后再重放原 `GraphWrite`。本层不读 Note：简报的 saved refs 由 facts 层经注入的 `HandoffBriefRefsReadPort` 给出。
- `session-handoff-brief.ts` — D 在 entered 确认里调用的 `HandoffBriefPort`：只读操作、核对它仍持有未消费的 ready 简报，再经 `state/session-handoff.ts` 的 `consumeHandoffBrief` 给出要合并的记录和 guard；不写事件、不另存简报。
- `session-health.ts` — Host reconcile 的 Session 健康探测结果观测与写入。
- `session-lifecycle.ts` — link/archive/reactivate 写服务，精确 CAS Session 与 link。最终归档提交（首次尝试和崩溃后的恢复走同一 `runArchiveStepAttempt`）对存下的可信条件调用注入的 `SecretaryArchiveConditionPort`，把检查给的一个片段并进提交：`guards`（source 和 `SessionActivity` revision）经 `mergeGuards` 合并，fence claim 进 `claims`，第一次读的水位进 `PreparedCommit.ledgerHorizon`（绝不进 guards）；非 null 条件而没有注入端口是 `unavailable`，从不静默成功。`createSessionLifecycleService` 的依赖类型因此多一个可选的 `archiveCondition`。
- `session-links.ts` — 一个 Session 自身 work links 的完整读取（有上限，超限明确 `capacity`）。
- `module-maintainer-service.ts` — 模块维护者 owner：`createModuleMaintainer` 发布 `ModuleMaintainerPort`；`maintainerOf` 走既有 module 索引并按执行者线过滤，`assignModuleMaintainer` 经共用写入执行器一次提交关闭旧 owner 链接并打开新链接（`already_owner` 零写重放），`applyMaintainerAssignmentDecision` 从存储操作输入重建检查绑定、推进 `done`/`rejected` 并返回阶段回执，`requestAssignment` 在每步确认模式建 `maintainer_assignment` 操作与卡、自动模式直接指定并写项目通知；不另建记录或第二份读。
- `session-record-codecs.ts` — Session 家族 schema 注册、纯 encode/decode、聚合键、provenance 等形状校验；另导出存储 `maintainer_assignment` 操作的唯一点读 `readMaintainerAssignmentOperation`（缺失 `null`、损坏 `unavailable`、别的 action 种类 `null`）；`CoreOperation` 按 `action.kind` 分派到手写的创建分支、`member_create` 分支（`state/member-creation.ts`）或两张字段表，并检查顶层 `workspaceId`、每个嵌套 `projectId` 和只有创建才有的 observation；task scope 的 TaskTriple 走 `contracts/data-format-refs.ts` 的 `checkShape(TaskTripleShape, …)`；创建意图的 scope 有 project/task 两臂，`delegationCeiling`/`secretaryCreated` 在创建意图和 Session 记录上都是可选片段；MemberCreated 的正式 proof 复用 `persistence/decision-record-codecs.ts` 的 `decisionChangeProofProblem`；`checkConsultationCreate` 检查创建 arm 的六键冻结载荷、两个 mode 的 `facts`/`reason` 规则、三条列表与四类事实（`event` 只有形状、7B-3 无生产者）。
- `role-line-record-codecs.ts` — R1 角色线记录/事件 codec：`SessionRoleFacts`、`RoleLineAllocation`、`ProjectRoleLimits`、`ProjectNotice` 四个记录和 `ProjectRoleLimitsChanged`、`ProjectNoticeCreated` 两个事件，注册组 `ROLE_LINE_RECORD_SCHEMAS`；字段表与规则在 `contracts/role-lines.ts`。
- `role-line-facts-writer.ts` — 注册提交的角色事实贡献：`roleFactsContribution`（`RoleFactsWriteInputV1` → `RoleFactsContributionV1`，`null` 表示 `roleFactsOf` 决定不写）只补读具名父操作或借座来源的事实；记录本身由 `state/role-facts.ts` 的 `sessionRoleFactsRecord` 构造，随注册提交写一条记录和 absence guard；`unavailableReadOf` 把两个补读的非 ready 结果统一映射成 `unavailable`，分配读共用这一份。
- `role-limits-service.ts` — 项目额度 owner：`RoleLimitsPort` 的 `readRoleLimits`/`setRoleLimits`，由 `createRoleLimitsService`（`RoleLimitsServiceDependenciesV1`）装配；读缺失时回答默认值和 revision 0，写走 `executeWriteCommand`，候选记录先在 `state/role-limits.ts` 构造再用 `projectRoleLimitsCodec.check` 拒绝非法额度。
- `role-scope-commit.ts` — 角色线与分配提交的唯一构造器：角色线 claim、guards、编码记录、游标绑定以及分配的 guard/记录都只在这里形成（`roleLineCommitContribution` 吃 `RoleLineCommitInputV1`，返回一个 `CommitFragment`），并声明 `planReanchorHook` 缝。
- `allocation-read.ts` — 准入的一次读与额度规则正本：`createAllocationRead` 一次 `readMany` 读分配与项目额度（缺键是 `null` 值加 expectedRevision 为 `null` 的 guard；坏记录、读失败或非 ready 是 `unavailable`），`openLimitOf` 取该 duty 的 open 上限（没有额度记录时用默认），`seatAtCap` 是唯一的满座判定（holders + reservations < open，否则 `capacity` 并报出四项事实）。
- `allocation-retry.ts` — 分配与额度 CAS 的唯一争用界：`ALLOCATION_ATTEMPTS`（4，首次加三次）、`allocationOnlyConflict`（只有每个观察版本都是那两份内部记录才重读；调用方 pin 的冲突立刻返回）、`retryAllocationCommit`（可重试的 store 失败才重读，最后一次 only-allocation 冲突是 `busy`，不是 `revision_conflict`）。
- `session-responsibility-service.ts` — 责任转移与归档责任处置，绑定同一 commit cursor；`transferPinsOf` 是四 pin 顺序的唯一构造，`responsibleLinkRef` 是 responsible 链引用的唯一构造，`readTransferReceipt` 只读重放已提交的转移。
- `session-targets.ts` — 创建/链接目标的正式校验：Task 走 Goal+当前已采纳 Plan，Module 走当前架构目录。
- `trusted-context.ts` — 可信 Host 入口、写请求同步隔离、身份/指纹/事件 ID 助手。
