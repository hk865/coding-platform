# src/core/work-graph/communication：决定答复与 Session 邮箱的事实 owner

## 负责什么，不负责什么
- 负责：决定答复（`answerDecision`）、已答复决定的应用证明/记录/回放、`DecisionSourceV1` 的正式来源重建，以及 SessionMailbox 的发信（`sendMessage`）、回复（`respondMessage`）、撤回（`withdrawMessage`）、释放（`releaseMessage`，允许/拒绝两臂）、收件箱/发件箱与两个视图读、ack、consultation 派生、accepted input、wait 处置。
- 依赖只允许 `model, state, persistence, materials, sessions, queries, tasks` 和 `RecordStore` 端口；另只在 `decision-source-facts.ts` 和 `decision-source/types.ts` 以类型引用 `WorkspaceToolsPort`（可选的文件摘要 seam）。不得 import `notes`、`evidence`、`views`、`agent-runtime`、`app`、`business`、`composition`。
- 消息状态（status/readAt/response/acceptedInputs/derivation）只由 `state/message-machine.ts` 的纯迁移和记录构造器写；本层收集事实、guards、effects，再走一次 RecordStore 提交。
- 消息正文字节只存 MaterialPort，状态与事件走 RecordStore；不另建消息中间件、第二份历史或第二个写入路径。
- 不启动 Agent、不唤醒/抢占 Session、不改占用或归档生命周期；不判断 Task/Goal 完成。生命周期写仍只经 `src/core/work-graph/state/`。
- 读失败原样返回，不折成空收件箱、空来源或“没有读者”。

## 文件
- `decision-service.ts` — 决定答复 owner：`answerDecision`、`recordDecisionApplication`、`readDecisionAnswer`，加消息 pin 读、应用回放与工具提交查询；项目卡的答复消息存项目 `subject` 且 `goalRef: null`，答复的唯一占位按整个项目算（各工作区都列出同一张项目卡）。 7C-1 的已保存答案读者把 `member_creation`/`rework_request` 也列为卡片链，不为它们点名保存答案的 Session。
- `decision-source-facts.ts` — 从正式记录重建决定来源的 Goal/对象/选项/pins/closed/允许读者，并接应用证明读法；`subject` 的形状先在这层检查（先于任何 Goal 读），Goal subject 读它的 Goal，项目 subject 不读 Goal、只接 `note_review` 分支（越界项目 `forbidden`）；`role_capacity` 读开着的容量 episode（关了或上限变了是 `source_stale`），`role_line_change` 读存下的角色线操作，请求的 subject 必须是操作自己的 `goalRef`（没有为项目），对不上是 `invalid`，不读请求方给的另一个目标；canonical source 的 subject 按分支读到的事实重建（Goal subject 取分支实际读到的 Goal，项目 subject 取绑定的项目），不照抄调用方的。 7C-1 的 `SourceDependencies` 与 `decision-source/types.ts` 加可选的 `reworkRequests`（只取 R 的 `readRequest`），并新增 `member_creation`/`rework_request` 两个 switch arm：前者读 M 的操作，后者读 R 的请求；缺 reader 时显式 `unavailable`，不推断卡片。
- `decision-source/` — 每种来源一个 handler，每个返回完整分支事实；原文件保留工厂、共同前置检查、分派、最终 pin 复核与结果组装。`message-release.ts` 是 `message_release` 来源：消息记录、它的 Goal 与卡片事实（`tasks/message-release-card.ts`），派生块是读的 DTO，不在分支事实里；冲突卡的来源核对经 `goalFootprints` 读冲突读的足迹（计划和执行两半），没接时只看计划足迹。
- `decision-application.ts` — 只从正式 receipt/event 证明一次已记录的决定应用（事件白名单，拒绝调用方自报版本）；导出共用的正式回执检查 `readFormalReceiptEvent`，以及五个 effect 行共用的 `decodeProofEvent`/`EffectProofV1`（party、post-effect version、acknowledgement）；`MemberCreated` 一行从同一提交读新 Session 的版本，损坏→`unavailable`、无版本→`invalid`，acknowledgement 可选；容量卡的三种应用 `ProjectRoleLimitsChanged`、`SessionResponsibilityChanged`、`SessionArchived` 各一行，事件不带 proof 是 `incomplete`，proof 坏了是 `unavailable`。
- `decision-source/member-creation.ts` — `member_creation` 来源的完整分支事实与唯一纯卡片投影：按 identity 的 operationRef 重读成员操作，核对 Goal/Task/revision，`closedReasonOf` 只把 `done`/`rejected`/`stale` 关成 `source_resolved`，`openedAt` 取操作自己的 `requestedAt`；来源注册留给 L1。
- `message-apply.ts` — 应用一条消息的事实 owner：`createMessageApplyOwner` 返回 `MessageApplyPort`（`applyMessage`），读 `MessageApplyInput`（`messageRef` + `ApplicationProofV1`）的 `MessageApplyDependencies`（回执/消息读、唯一写入 `prepare`、本提交的时钟），先做形状检查，再复用 `readFormalReceiptEvent`/`decodeProofEvent` 比较回执与 effect，最后走唯一消息写入的 `prepare` 与 `messageWriteResult`；事件沿用写信人的 actor（D8-16 (c)），`appliedAt` 取 effect 的时间。
- `mailbox-service.ts` — 入口：保留两个工厂 `createSessionMailbox`/`createMessageWriteOwner`、`MailboxContext` 的创建、22 个端口绑定，并按原名显式转出搬出的公开名字（调用者和测试的原导入路径不变）；完整的 `SessionMessageCommandPort` 实现（窄的 `SessionMailboxPort` 加四个写命令与两个视图读）与唯一消息写入 facade（body → record → event → receipt 一次提交）；`createRecipientExecutions` 在 `sessions/recipient-executions.ts`，给撤回读收件方未结束执行；消息读带派生的释放块，发件箱按页项收集同序的 `releaseBlocks`（收件箱为 `null`），`releaseBlockOf`（定义在 `mailbox-basis.ts`）是这两处唯一的派生（已批准、未撤回、未释放才派生；没有 dispatch basis 读时 `unsupported`）。
- `mailbox-types.ts` — 邮箱的全部类型别名（含 `MailboxPrincipal`、`Owned`、`OwnedContext`、`SessionMailboxWithUserSend`）加唯一新增的 `MailboxContext`（`deps`/`records`/`messageWrites` 三个只读引用）；只有写入工厂内的 `WriteReceipt` 留在入口。跨文件用 `export`，入口仍从原路径转出 4 个公开类型。
- `mailbox-common.ts` — 共同组：小纯函数、可信上下文、身份键、单条消息读与分页基座。搬出的原内层命名函数统一为普通函数，第一参数是 `mailbox: MailboxContext`；原顶层函数保持原签名。入口仍从原路径转出 10 个公开函数名。
- `mailbox-write.ts` — 写入组：正文存储（`readCurrentWorkspaceSource`/`verifyStoredMessageBody`/`storeScopedMessageBody` 与 `readWorkspaceSource`/`storeMessageBody`/`storePlannedBody`）、回执重放与复核、机器写入的计划与一次提交（`replaySessionMessageReceipt`–`commitPreparedSessionMessage`）、`messageCommitPlan`，以及两个模块级结果对象（保持原对象身份，入口转出同一个绑定）。入口仍从原路径转出 4 个公开函数名。
- `mailbox-basis.ts` — 派工依据和释放伴随项：`sameBasis`/`dispatchCurrentOf`/`basisPinsOf`/`basisConflictCurrent` 与释放的伴随记录 `releasedMessageCompanions`；加从 `message-release.ts` 原样搬入的阻塞原因投影 `releaseCandidateBlockedReason`（本文件直接调用同文件的 `sameBasis`）和消息读/发件箱的 `releaseBlockOf`。入口仍从原路径转出 5 个公开函数名，`message-release.ts` 也按原名转出投影。
- `mailbox-identity.ts` — 执行身份、秘书身份和 Query 事实：`readFreshWorkRunFacts`/`readWorkRunIdentity`/`deriveWorkRunSender`/`authorizeNewWorkRunAction`（Run、claim 与 Session 的一致身份读和新动作授权）、`resolveSecretaryRound`/`secretaryReader`（秘书轮与读取准入）、四个 Query 事实读（`loadQueryJob`/`loadQueryRun`/`loadQueryAnswer`/`readQueryAnswerFacts`）、`interventionSourceFormallyEnded`，加搬来的 `consultationBindingOf`/`readStoredQueryRecord` 与公开的 `respondReceiptIdentityOf`。入口从本文件导入 11 个内部函数，并按原路径转出公开名字 `respondReceiptIdentityOf`。
- `mailbox-access.ts` — 单条读取组：`canReadMessage`/`ownsInbox`/`messageReadRight` 的单条读权限、`readMessage`/`readMessageBody` 的单条消息与正文读、`readMessageView` 的消息视图（复用 `mailbox-identity.ts` 的身份与秘书读、`mailbox-basis.ts` 的释放块派生）。入口从本文件导入 4 个内部函数。
- `mailbox-pages.ts` — 分页组和原游标：`readInboxPage`/`readInbox`/`readInboxView`、`readOutbox`、`replyCallerKey`/`readRoutedReplies`/`readUndeliveredReplies`，以及四个 keyset 游标的编解码（收件箱/发件箱/秘书发件箱/回复）。入口从本文件导入 5 个内部函数。
- `mailbox-send.ts` — 发送组：两种发送入口 `sendMessage`/`sendUserMessage`，加它们的专用依据函数（`loadGoal`、`goalBasis`、`aggregateObjectPins`、`verifyDecisionObjectWorkspaces`、`dedupePins`、`goalRefOfDecisionObject`、`owningGoalWorkspace`、`readDecisionObjectRecord`、`verifyDecisionObjectPins`、`validOptionObjects`）和发送结果投影 `sendStatusOf`/`refuseSend`。`sendMessage` 的请求内 `companions`/`record` 闭包与 `frozenDeadline` 仍留在 `sendMessage` 内。入口从本文件导入 2 个内部函数。
- `mailbox-commands.ts` — 消息写命令组：`ackMessage`/`respondMessage`/`respondFromQueryAnswer`/`recordConsultationDerivation`/`recordInputAccepted` 与 `withdrawMessage`/`releaseMessage`；每个命令保留自己的 read/decide/build 回调和请求内状态构造器。`acceptedMessage` 在 `mailbox-common.ts`（见搬移表）。入口从本文件导入 7 个内部函数。
- `mailbox-archive.ts` — 归档等待处置组：步骤检查 `normalizeArchiveStep`/`waitChoiceForStep`、目标可读判定 `replyTargetEligible`（公开，入口按原名转出）、处置事件 `encodeArchiveWaitDisposalEvent`，以及 `readDurableArchiveRequest`/`loadStoredArchiveRequest`/`readWaitRun`/`writeArchiveWaitDisposal`/`disposeArchiveWait`。入口导入 `disposeArchiveWait` 并从原路径转出 `replyTargetEligible`。
- `mailbox-host.ts` — Host 发件箱与回执查询组：`hostSystemOutboxRefOf`/`hostOutboxAfterOf`、`readHostSystemOutbox`/`appendHostSystemOutbox`、`normalizedLookupOrigin`、`workRunSenderIdentityOf`、`lookupToolCommit`/`lookupHostSendCommit`。入口从本文件导入 4 个端口实现；`lookupHostSendCommit`（7C-1）只按原发送的 requestId/scope 与身份查 store 的 commit identity，收件人后来变了也不改答案，不读当前载荷、不写。
- `message-release.ts` — 放行 owner 与有界候选读：`createMessageReleaseOwner` 返回 `releaseApproved`（R2 命令 `message.releaseApproved`：机器判定、Goal 活动、`action_request` 的 pins 与依据、一次提交写释放伴随记录）和 `readReleaseCandidates`（一个工作区或一个 Goal 的候选页，按批准时间升序，每项带当前阻塞原因）；撤回的消息跳过，读失败原样返回。
- `message-expiry.ts` — 到期 owner：`createMessageExpiryOwner` 返回 `MessageExpiryPort` 的 `recordExpiry`（读一条消息、只调 `state/message-machine.ts` 的 `decideExpiry` 并提交，本文件没有第二个到期判定）、`readDueWaits`（一个工作区一页到期等待，按 deadline 升序）和 `readExpiryCount`（沿 `followupOf` 的有界走查，返回 `1 | 2 | 'incomplete'`；一条总预算，不饱和）。
- `project-notice-service.ts` — 项目通知的唯一可信写者 `notifyProject`：没有 caller、没有 `ctx`，固定系统 principal 和项目级 scope（`workspaceId: null`）；身份是 `(subject, kind, operation)`，subject 是调用方给的 Goal 或项目（不给是项目，不属于本项目是 `invalid`），重放返回原回执、同身份换载荷是 `idempotency_conflict`；记录/事件走 `contracts/role-lines.ts` 的字段表和 `sessions/role-line-record-codecs.ts` 的编解码，`since` 由提交绑定；本片没有生产者，读来源的接线归组合根。
- `copy-retraction.ts` — 复制取消的两个模型端口（`CopyInterventionReadPort`/`CopyInterventionRetractionPort`）的实现：按 Goal 的 `continuedFrom` 索引读副本、分页读来源干预，撤回走 mailbox 的 `withdrawMessage`；只读记录，失败是拒绝不是空页。

## 不要做
- 不要信调用方给的 `source.pins`、`actualVersions` 或“已应用”断言；来源、pins 与证明都从正式记录重建。
- 不要把失败的读折成空来源/空收件箱，也不要给缺失的读者一个默认值（FP-05、MH-06）。
- 不要另写消息写入或重放路径：`createMessageWriteOwner` 是唯一 body+record+event+receipt 写入；重放读原始 event，不用今天快照重建（M1-25、M1-26）。
- 不要自己造状态记录或直接改 status/readAt/response；用 `state/message-machine.ts` 的迁移（AGENTS 第 9 条、M1-01）。
- 不要另写 Session/Message ref 校验或聚合 key；用 `sessions` 的 codec 与 `sessionAggregateRefKey`（M1-31）。
- 不要把发送当成唤醒/占用/任务义务，也不要在本层关闭 Session、Run 或 Task（M1-36）。
