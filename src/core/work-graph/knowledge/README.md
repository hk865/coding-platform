# src/core/work-graph/knowledge：代码知识文件的唯一写入顺序

## 负责什么，不负责什么
- 代码知识落在每个工作区根的 `.workbench/` 里（`architecture.json`、`modules/<fileId>.json`、`notes/<workspaceId>/<noteId>.md`）；文件是知识。这里只有一件事：架构和注记的每个写点按同一个顺序写——取项目全部线，进写队列，拿每个检出的跨 Host 租约，服务在 `prepare` 里读当前知识、规划、校验、算出文件改动，连同每个改动一条写日志提交记录，提交成了才逐个原子落盘，落了盘的日志再补成完成，最后建索引、放租约。
- 回放的回执（`replayed`）不写新日志、不碰文件；记录提交了而文件没写成，照实回“记录已提交、知识文件没写成”，不当成功，没落盘的日志留 `pending`。
- 不读写磁盘：读写文件和租约目录的是组合根（`src/composition/line-knowledge.ts`）实现的 `LineKnowledge` 和 `KnowledgeWriteDeps.acquireLease`，端口在 `model/line-knowledge.ts`；文件格式在 `architecture/architecture-file.ts` 和 `notes/note-file.ts`。
- 依赖 `model`、`persistence`、`state`（`docs/refactor/module-target.json`）：写日志和完成事件的 codec 在 `persistence/knowledge-record-codecs.ts`。`architecture`、`notes` 依赖本层，放进这里的文件不得 import `architecture/`、`notes/`，否则成环；要用那两层的规则（携带事件、路径种类、模块号）经 `KnowledgeWriteDeps.files` 注入（`notes/knowledge-files.ts`）。

## 文件
- `knowledge-write.ts` — 一次知识写的顺序 `writeKnowledge`、检出租约 `withKnowledgeLeases`、写点交回的提交 `knowledgeCommit`、文件没写成时的原因 `knowledgeFilesNotWritten`，以及 `KnowledgePrepared`/`KnowledgeWriteOutcome`/`KnowledgeWritePlan` 等形状。读线之后整个 `prepare`、提交、落盘、补完成和索引都在 `write.queue.run(projectId, 排好序的 folder)` 和每个检出的租约里；测试缝 `write.hold` 不为 null 时在提交之后（`committed`）、全部落盘之后（`applied`）各停一次；全部落盘后一个索引事务交 `write.indexFile`，注记文件再记 `setNoteState`，这一步出错吞掉、不改写入结果。
- `write-log.ts` — 写日志：`writeLogExtras` 给每个文件改动出一条 `pending` 的 `KnowledgeWrite@1`（守卫“必须不存在”、`since` 绑到携带事件的下标），并进写点的同一次提交；`completeKnowledgeWrites` 一次提交把一组日志补成 `completed`（每条按读到的 revision 守卫，带一个 `KnowledgeWritesCompleted@1`，身份是排好序的 writeId）；`completeLandedWrites` 读回落了盘的日志再补完成；`markKnowledgeWritesUnconfirmed` 同样一次提交把对账交给人的 `pending` 日志改成 `unconfirmed`（带一个 `KnowledgeWritesUnconfirmed@1`）。补完成失败不改变调用者的结果。
- `reconcile.ts` — 一条线的知识对账 `reconcileKnowledgeLine(write, line, trigger, projectLines)`（kls-design §2.2.5、R18、R22）：在写队列和这条线的检出租约里，读 `line.readKnowledgeFiles()` 的完整清单和 git 状态，和索引上一轮比；R18：这条线 `pending` 的写日志文件等于写后就补完成，否则（还没有恢复项时）出一个 `write_unconfirmed` 恢复项、日志改成 `unconfirmed`，`unconfirmed` 的日志文件后来等于写后也补完成；R22：变或删的路径回到旧内容（删了、等于 HEAD 或更早的快照）就是撤回，恢复内容取上一轮内容的快照、没有取最新一份；这一轮读到 `pending` 或 `unconfirmed` 写日志的路径照常分类、建索引，但不算撤回（不标待核实的仍只是 `pending` 的路径）；恢复项先写进快照库、再出一条项目通知（`knowledge_write_unconfirmed`、`knowledge_reverted`，summary 只带个数，身份是种类、线和按路径排好的项）；这个通知身份已经有恢复项，就不再加项、不再通知，结果里的 `reverted` 只数这一轮新加的；新、变、删的路径一个索引事务交 `write.indexFile`，不是平台刚写的注记标待核实（已提交 `merged`，否则 `external_edit`）；第 8 步 `write.conflictsOf` 判这条线模块文件之间的冲突，每轮都用第 1 步读到的同一份字节拼一次整图（`line.architectureOfDisk`，不再读盘，一轮只看一个磁盘状态；stk16：人在一轮中途改的文件曾多出一条通知），读不成的原因记在 `architecture.json` 名下（只有“这条线现在没有 `architecture.json`、项目的记录里也从没采用过架构”是没有图，不算问题；记录里最后采用的 catalog 和 baseline 是 `write.recordedArchitecture`（组合根接 `readRecordedCatalogWindow`；没有是 `null`），在这一轮改任何东西之前读，读失败整轮 `unavailable`，不拿磁盘和上一轮索引代替；b2 Astra 1）；本线读得通且 `projectLines` 读齐时再做一次项目级合并核对（`write.projectArchitectureOf`），失败的原因也记在 `architecture.json` 名下（4-4）；读不成的文件和冲突合出一条 `knowledge_conflict` 项目通知，通知前先给每个坏文件挑一次恢复来源（最新一份能读的快照、HEAD 里和坏字节不同且能读的版本、平台记录；通知的行第一次写下时挑一次，同一通知的各轮不再读快照、git 和记录），逐处问题行写进快照库（`recordProblems`，`lineProblemsOf` 从同一份字节算），再给有来源的坏文件写 `unreadable` 恢复项（序号同问题行的 `itemNo`），最后发通知（`conflictNoticeOf`：身份是按路径排好的问题和冲突，同样的问题不重复通知；summary 是“知识文件有 n 处问题：”加去重排好的路径，n 是路径数，截到 512 字节）；三种通知的身份同一个算法；最后给未提交的文件存快照、干净且和上一轮相同的清快照，记对账时间，删平台留下的 `*.tmp-*`。目录读不了整轮 `unavailable`、不动索引和文件。
- `ops.ts` — `createKnowledgeOps(lines, asks)`：`platform.knowledge` 的实现，`reconcile(ctx, workspaceId, trigger)` 取这个工作区当前检出的线交给 `reconcileKnowledgeLine`；结果有冲突时，按 `asks.regionAdvisersOf`（组合根接：记录里最后采用的那份 catalog 读一次，有效区域参谋也认）找每处冲突第一个模块的区域参谋，再经 `asks.beginConflictRepair` 按 notice id 开（重试就重放）一轮 `knowledge_conflict` 修复轮：一条通知只开一轮，由拿到该处第一个模块的区域参谋处理，不发给每个认领者；正文由 `conflictRepairText` 按 `asks.maxTextBytes`（组合根给邮箱的 16 KiB）逐处列原因和文件、点名 `propose_architecture_revision`，开头和动作指示总在，每处一行按顺序整行装到装不下为止，一行都装不下就截断它，再写明还有几处没列出（字节数用 `contracts/utf8.ts`；b2 Astra 2）；发信人固定是 `knowledge-conflict` 系统身份、工作区是被对账的那个，没有参谋或读失败不开，只有通知。`problems(ctx, {noticeId})` 是 `knowledge/problems` 的端口：按 noticeId 读本项目快照库里存下的问题行，一项都没有回 `not_found`，输入在这里核。不管哪个触发调的都在这里发：`reconcile` 是 `createKnowledgeOps` 里的局部函数，恢复之后的 `'recovery'` 对账也调它（b2 F-9）。`recover(ctx, {noticeId, itemNo})`、`recoveryItems(ctx, {noticeId})` 是两条恢复路由的端口，路由把输入原样转来，在这里核（`noticeId` 非空字符串、`itemNo` 从 1 起的整数，不对回 `invalid`），再交给 `recover.ts`。第三个参数 `localOnly(repoKey)` 是 R21 的“只留在本机”（组合根接 Host 设置，按检出键；不经 Host 恒 false）。`status(ctx, workspaceId)`（R21）：只经 `lines.line` 取线（不是本项目登记的工作区原样拒），回 `line.status()` 的分支、处数、文件数加 `localOnly`。`commit(ctx, {workspaceId, message?})`（R21）：输入在这里核（`message` 只能是字符串、null 或不给）；这个检出“只留在本机”时回 `forbidden`“架构图和注记设置为只留在本机”、不动 git；否则在写队列和这条线的检出租约里（`withKnowledgeLeases`，同写和对账）调 `line.commit`，git 的拒绝原样回；成功后、队列和租约放开之后，调本文件的 `reconcile(…, 'after_commit')` 一次（它自己进队列；把已提交的文件编进索引、清它们的快照），对账失败不改提交结果；不写记录，所以回 `ready`、不回 `committed`。`markJoinedCheckout(ctx, workspaceId)`（R6）：在写队列里，把这条线索引里的每个注记文件在本项目标 `needs_verification`/`joined_existing_checkout`（一个索引事务），回标了几个；不碰文件、记录和别的项目。
- `recover.ts` — 人点“恢复”（[2C1-19]、[2C1-20]）和读一条通知的恢复项（[2C1-23]）。`recoveryItemsOf` 按 noticeId 读本项目快照库的恢复项，只给 `{itemNo, kind, path}`，一项都没有回 `not_found`（别的项目的 noticeId 在这里也读不到）。`recoverKnowledgeItem` 先读恢复项（没有回 `not_found`），按恢复项的 `lineRef` 找工作区和它当前检出的线，在写队列和这条线的租约里：线的键对不上回 `revision_conflict`（“检出的分支已经变了”，勘误 2c1#15）；当前文件的 blob 不恰好等于 `expectedBlob`（都不在也算等）回 `revision_conflict`；`write_unconfirmed` 读写日志、按它的 `since` 调 `records.eventAt` 读那一个事件，经 `write.files.knowledgeFileOfEvent` 以当前文件为底重建，重建不出或 blob 不是 `afterBlob` 回 `unavailable`，不猜；`reverted` 取它选中的那份快照；`unreadable` 按通知当时写下的来源取：快照按 key、HEAD 按 blob、平台记录当场重算（注记没有文件作底）。原子写（`applyChange`）之后补完成日志、经 `indexLanded` 当平台自己的写建索引（勘误 2c1#6）、删这一行恢复项（通知照旧在）；放开队列和租约之后、返回之前，经调用方给的 `reconcileLine` 对这个工作区对账一次（`'recovery'`）。不重跑 service、不写业务事件，失败照原样回、不重试。回 `{path, blobSha}`（删除时 `blobSha` 为 null）；不写业务记录，`cursor` 取恢复之后记录库读到的位置。只有这里读事件（[2C1-21]：读路径永不 `eventAt`）。
- `pin.ts` — 计划的钉（L3，[2C2-02]、[2C2-03]）：`readPlanPin` 在提案窗之前、紧跟当前目录的文件读，取 Goal 所在工作区的线和计划用到的每个模块所在的线（模块的工作区按 `rawModuleId`，没有前缀是主工作区），每条线只对落在它上面的模块调 `LineKnowledge.pin`（Goal 那条线没有就是 `pin([])`），按 `lineRef` 排好；任何一条线读不成就整个回拒绝。用到的模块 = 任务挂的模块（目录里有的）加计划文件在 Goal 工作区的归属模块（`catalogForWorkspace` 投影后 `pathOwnershipOf`，平手和没有归属不算；不在项目视图上直接比，否则主工作区的 `.` 会认领别的工作区的文件）。`planPinOf` 在窗里对模块事实检查过的任务（去掉不变的终结任务）重算用到的模块，只留 Goal 的线和这些模块的线、dirty 线的 `modules` 只留这些模块，所以窗里不读文件（121-93）。只用 contracts 和 model；`tasks` 不能直接 import 本层，经 `architecture/catalog-service.ts` 转出。
- `write-queue.ts` — 进程内写队列 `createKnowledgeWriteQueue`：先项目键、再排好序的 folder 键，调用时同步登记全部键，先来先走、不会死锁；不替代 CAS。Host 只建一个，经 `knowledgeWriteQueue` 交给每个项目的平台。

## 内部用
`KnowledgeWritePlan`、`KnowledgeCommitExtras`、`KnowledgeExtrasOf`、`KnowledgePrepared`、`KnowledgeWriteOutcome`、`KnowledgeCommitThrow` 是本层的形状；`writeLogExtras`、`completeLandedWrites` 只有 `writeKnowledge` 调，`markKnowledgeWritesUnconfirmed` 只有对账调，`recordedBytesOf` 只有对账挑来源和坏文件恢复调。

## 不要做
- 不要在 `prepare` 外读规划要用的当前知识，也不要在提交前写文件。
- 不要把文件写失败吞掉或当成功；不要重试。
- 不要拿写前 blob 和索引比，也不要另存读依据：读当前知识和规划都在租约里的 `prepare`。
