# src/business/workflow：业务流程编排层，只选下一步并调用一个核心 owner

## 负责什么，不负责什么

- 负责业务流程：`advanceWork` 按已采纳的 Goal/Plan 选下一步，每次 `perform` 只调用一个 owner，并把 owner 的完整结果作为 `receipt` 交回 Host；另提供初始规划、request intake、归档、维护、决定、咨询、活动回填入口，以及 Host wake loop 驱动的两条请求队列处理器。
- 允许依赖 `WorkGraph`、`AgentRuntime`、`WorkspaceTools` 和 `src/contracts`；不得 import `RecordStore`、`src/app`、`src/composition`。
- 只选择流程意图与顺序；存储、索引、状态机、读取器都在 `src/core/work-graph/`，本层不得重写，也不保存 Workflow 数据库、去重表或第二个控制循环。
- 状态迁移只交给 `src/core/work-graph/state/`，本层不得直接改受保护字段（根 AGENTS 第 9 条）。
- 不负责：Host 路由与接线（`app/`、`composition/`）、记录编解码、Task/Goal 完成裁决（`tasks/completion.ts`）、UI 读模型（`views/`）。

## 文件

- `activity-backfill.ts` — 两个活动回填批次（Host 启动的近期窗口与人工区间），Work Run 与 Query 共用一张合并候选；计数分别走 `countRunActivity`/`countQueryActivity`，写回分别走 `recordRunActivity`/`recordQueryActivity`；缺 Query 一侧的依赖只让 Query 分支答 `unsupported`，Work 分支不变。
- `consultation.ts` — 一条已保存信箱输入 → 一条确定性只读 Query；复用已有 Query/Answer，不重跑发送者的 Work；新的咨询在回复位检查前先过共用的送达规则（注入的 `deliveryFacts` 走 `deliveryEligibility`），按 `code`/`reason` 拒绝，拒绝结果用导出的 `asRejection` 映射、不另写一份；已保存的 Query 结果仍先重放，提交时同一条消息 revision 由现有 `consultationMessageGuard` 复核；阶段链交给 `query-stage-driver.ts`。归档/退役的源线也受理；载荷经 `consultationCreateOf` 决定并冻结在创建操作上，重试先读同一操作，`execution.consultation.operation` 指向它。
- `consultation-facts.ts` — 咨询创建的唯一模式决定：先按 `stableSessionCreationIdentity` 派生并读同一创建操作，找到已冻结载荷就原样复用、不再采集；否则按完成边界选 `kernel`/`platform_facts`，经注入的采集端口跑一次；没有采集器时保留原来的边界路径。
- `request-candidate.ts` — 选过思路后的请求轮出口 `proposeFromPlanTurn`：按冻结 `manifest.answerShape === 'plan_round'` 读答案、解析、规范化，取 Goal 当前 `activePlanRevision`、读请求候选头并 `proposePlan`（确定性 id 重放）；`reason` 是 summary + answer bodyRef + 模型 `affectedTaskIds` + 可选 `objective`；首版保留 `request_followup` origin，后续版本用 `mergeStageRefinement`。不新写候选循环、不注入 `queries`。
- `query-stage-driver.ts` — 一条 Query attempt 的唯一阶段链：按 `executionState.phase` 认领请求轮、准备并启动、只观察已开始或 `unknown` 的 attempt，并把每个 owner 的结果映射成 `progressed`/`terminal`/`blocked`。启动被 `busy/running_cap` 拒绝时只报 `blocked('on_change','running_cap')`，不当作放弃的 attempt、不进入 `replacedAttempt`。
- `contracts.ts` — Workflow 的调用/步骤/推进/归档/回填 DTO 与 `WorkflowOperation`、`WorkflowAdvanceResult`；交接组合的注入契约 `HandoffWorkflowDependencies`（两个操作 owner、源未完成操作的读口、事实读、子 owner 与 D 的请求端口，7D2 O2b 加必需的 `duty: SessionDutyReadPort`；`HandoffWorkflowDependencies` 在 `src/business/workflow/contracts.ts:476`）也在这里。
- `decision-actions.ts` — 有限决定协调：先提交答案，再做结构化冲突动作，最后记录应用；另有只读 `orderGoalAdvances`。各卡的第②步适配器也在这里，7D2 的两个是 `role_capacity`（解析存下答复的四个选项，交容量服务）和 `role_line_change`（转给角色线写者）。
- `index.ts` — 对外 barrel：`createWorkflow` 与 Workflow 端口/调用契约类型。
- `intervention.ts` — 干预入口 `createInterventionHandler`（`src/business/workflow/intervention.ts:47`）：读来信与线事实，按消息的 `taskRef` 或该线最近的 Work Task 分支。既有未完成任务认领经 `workflow.ts` 的 `claimIntervention` 用 `{ kind: 'intervention' }`（`existing_task`，认领判断是 B 的）；另有两条 V 分支：Goal 已 `COMPLETED` 时经 `requestIntake.submitInterventionGoal` 追加无目标请求（答 `requested`/`goal_completed`，依赖未注入时仍答 `queued/no_task`）；Goal 活跃且线上无未完成任务时，在线上跑一条只读 `intervention_planning` Query → 按 `{ kind: 'intervention', messageRef }` 读答案 → 规范化 → `proposePlan`（带 `sourceMessageRef`）→ 首份计划留给人、未来细化按 autonomy 采用，答 `progressed`（stage `query`/`proposal`/`adoption`）或 `awaiting_decision`。收尾由 Host 编排通知、关联和撤回，关联步骤由 handler 调既有邮箱 owner：`answer_ready`（`reason` 为 `invalid_plan`/`declined`/`questions`，正式 Answer 由 Host 关联成原消息回复；`questions` 只出卡、不发通知；答卡不另开规划轮）、`no_answer`（正式终结且没有 Answer，Host 先发固定通知再撤回源消息）、`responded`（Host 的第二步 `completion: 'associate_answer'`，幂等关联正式 Answer）与 `awaiting_decision`；读失败、缺依赖、来源/版本冲突和串线仍原样拒绝。Goal 还带着 Host 重启的 `interruption` 时答 `busy`。
- `line-ask.ts` — 人用 `queries/ask` 的唯一编排：校验 `commandId`/问题（复用 `queryTextProblem`）/线头，读线取 Goal（复用导出的 `sourceGoalRef`），先发一条 `intent: 'inquiry'` 的人消息，再把同一消息交 7B 的 `createConsultationConsumer`；只返回确定性的 `round`，不复制副本或 Query 逻辑，无目标线也走同一条只读派生。
- `line-creation.ts` — 带稳定 `commandId` 的工作线创建/重放与只读 `findLine`；项目线或任务线（任务线写 responsible 初始链接），可选 `delegationCeiling`/`secretaryCreated` 随创建意图存入；容量由 Session 目录的计数准入判定。
- `plan-round.ts` — 规划轮的纯规则（§5.1.4、§5.2.2–§5.2.3、§5.2.7）：`planOnlyTargetOf` 从 Goal 等待依据取唯一的规划者目标（stage 占位或 goal 级占位任务，缺失/空串即没有标记）、`refinementRoundOf` 按调用方给的目标与 Plan revision 组一轮 refine、`systemRoundSendInput` 组一轮完整的邮箱发送请求（复用 `SessionMessageSendInputV1`；正文首行必须是 request id，`planresume:` 正文固定为头、原 Query 引用与固定请求句）、`planningAnswerShapeOf` 按发送方身份与收件线 duty 定提交工具形状（未知组合是普通文本答案）。只读轮事实、不读 store、不跑 Host 调用、不保存状态；唯一的发送包装是 `src/app/system-round.ts` 的 `sendSystemRound`。
