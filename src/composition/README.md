# src/composition：唯一装配根——把受信任配置和各模块 owner 接成可关闭的 TargetPlatform

## 负责什么，不负责什么
- 装配层：可以接各模块并构造服务；只装配/接线，不复制领域规则，不把业务选择写进这里。
- 生产代码唯一构造平台的地方（`openTargetPlatform`；`createTargetPlatform` 是只取 platform 的一层包装）；Host 只经它拿公开端口，不能另建服务图。
- 不写状态：任何状态迁移只经 `src/core/work-graph/state/`（AGENTS 第 9 条）。
- 不被 `src/core`、`src/business` 反向 import；`src/app` 可以依赖本层。
- 默认值只作显式 seam：不发明 secretary profile、容量上限或 wake driver。
- 记录格式只在 `schemas`（`src/composition/create-platform.ts:1180`）注册一次：每个 codec 文件的 schema 束按 records、events、lookups 三段展开，内存和 SQLite 两种后端用同一份；Session 活动记录的 `SESSION_ACTIVITY_SCHEMAS`（`src/core/work-graph/sessions/session-activity.ts:39`）、初始化绑定的 `INITIALIZATION_BINDING_SCHEMAS`（`src/core/work-graph/persistence/initialization-binding-codecs.ts:9`，带两条 lookup）和初始化 adoption 的 `INITIALIZATION_ADOPTION_SCHEMAS`（`src/core/work-graph/persistence/initialization-adoption-codecs.ts:209`）也在其中。新格式只加进这三段，不另建 schema 集。
- 目标卡的接线：初始化绑定读只建一个（`createInitializationBindingReader`，`src/composition/create-platform.ts:1493`），请求事实、Plan owner、决定来源、规划问题读、草稿确认和发布的 `bindings` 共用它；`goals` 上加草稿确认 `confirmDraft`、复制预览 `readGoalCopyDraft` 和复制确认 `confirmGoalCopy`（`src/composition/create-platform.ts:2642`），都经 `trackedCall`；复制用的目标理解读 `readGoalUnderstandingFrom`（`src/composition/create-platform.ts:1048`）在注记读模型之上，注记读模型建得更晚，所以经一个晚绑定的持有者转发（与 `boundNoteDecisionSource` 同一做法）。草稿确认的 `GOAL_CONFIRM_SCHEMAS` 和复制的 `GOAL_COPY_RECORD_SCHEMAS` 在同一处 `schemas` 注册。`bindings` 不可枚举。7A-2 的放行组 `messageRelease`（release owner、候选读和可信入口，逐成员经 `trackedCall` drain）与 Workflow 依赖的 `messageRelease` 共用同一个 `messageWrites` 和 `dispatchBasis`；复制干预的两个端口 `interventions`/`retractions` 进 `createGoalCopyService`，`goals` 上发布 `readCopyInterventions`（无路由）；`createMessageApplyOwner` 发布为 `platform.messages.applyMessage`，G 的 `message_release` 卡片来源和申请行在同一装配。`messageRelease` 不可枚举。初始化 adoption 的操作 owner 只建一个（`createInitializationAdoptionService`，`src/composition/create-platform.ts:2662`），和 `bindings` 共用同一个绑定读、Plan owner、catalog 和 policy owner，五个方法经 `trackedCall` 发布为 `initializationAdoption`；`confirmInstalledChecks`（`src/composition/create-platform.ts:2689`）只读 `currentCheckConfiguration` 的登记表（含静态回退），不读设置文件：没有配置时修订和摘要都是 null，`settings` 总是 null。两者都不可枚举，Host 的设置对象和 adoption 组合按属性读。

- `project-store-location.ts` — 项目库放哪：目录名只由 projectId 定（sha256 的前 16 位），工作区路径只用来找候选和查盘。主工作区根在 git 工作树里，候选是 `<git common dir>/workbench/projects/<hash>`（`git-common`，所有工作树共用、git 不跟踪）；不在，候选是 `<根>/.workbench/local/projects/<hash>`（`workspace-local`，不偷偷 `git init`）。候选定了才查它所在的盘（最近的已存在祖先、realpath；只有路径不存在才往上找，别的读错如 `EIO`、`ESTALE` 或根也解析不了都算判断不了）：Linux 读 `/proc/mounts` 取最长前缀的挂载类型（`9p`、`drvfs`、`cifs`、`smb3`、`smbfs`、`nfs`、`nfs4` 不可靠），Windows 的 UNC 不可靠、盘符读 `Win32_LogicalDisk.DriveType` 的数字（4 不可靠，2、3、6 可靠）；不可靠或判断不了（读不到、别的平台）一律退到本机数据目录 `<用户数据根>/projects/<hash>`（`user-data`），`reason` 写一句原因；不读本地化文字，不抛错、不挡启动。用户数据根：Windows `%LOCALAPPDATA%\coding-platform-next`，其他 `$XDG_DATA_HOME/coding-platform-next` 或 `~/.local/share/coding-platform-next`；都没有时回 `unavailable`（只在走到本机数据目录时才会碰到）。
- `project-runtime.ts` — 每个项目一个 runtime 的注册表。`open` 的顺序：已开的原样返回；memory 存储不算位置、不建目录、不查旧布局；算位置（主工作区是第一个）；项目库目录不在而 Host 存储目录里有旧单库的 `ledger.sqlite` → `unsupported`（不加载、不迁移，79-1；在建目录之前查）；不在且不许新建 → `unavailable`（不建目录、不取锁）；新建目录（`workspace-local` 且这次新建时补 `<根>/.workbench/.gitignore` 的 `local/` 一行，原有内容不动）；确保 Kernel 目录在；经注入的 `acquireLease` 取这个库目录的锁（别人持有也照样打开，runtime 如实带 `lease`）；经注入的 `createPlatform` 开一次 platform，开失败先放锁再回 `unavailable`。`close` 先 platform 后锁、重复调用同一个 Promise；`closeAll` 先清表再 `allSettled`。注册表不登记 Kernel 入口，只交 Kernel 目录。生产路径还没有调用方（允许清单 `kept-for`）。
- `plan-adoption-stop.ts` — PS 的采用前停止包装：人的 `plans/apply` 先调 raw `applyPlanChange`；只有 TASK-19 的 `busy` 且 `reworkActorClassOf` 判 human 才读只改处置任务的全部 `starting`/`running` Run，逐个提交 `cancel`（`plan-change:<proposalId>:<taskId>:<runId>`、`stopping_affected_work`、现读 Run 的 pin）并投递；指针已 `cancelled` 的 Run 直接投递现有意图，`busy`/`revision_conflict`/`idempotency_conflict` 先按同一身份读既有 `ControlIntent`；`busy` 不再重交，只有 `revision_conflict`/`idempotency_conflict` 才对仍活着且无既有意图的 Run 用同一请求号和新 pin 重交（`MAX_CONTROL_SUBMISSIONS = 3`，含首次），耗尽或其它拒绝原样返回；停了至少一个返回 `busy`/`stopping_affected_work`，否则原样返回 raw 拒绝，计划零写。
- `session-duty.ts` — 受信任 Session duty 解析：pinned RoleSpec、精确 legacy template、配置的执行者回退；一次没有回答的读为 `unavailable`，没有平台职责才为 `unknown`。
- `tool-commit-lookup.ts` — 按固定 tool 名表把已提交调用查询派给 mailbox/decision/plan/notes/CRR owner。
- `work-line-conversation.ts` — line conversation 分页：按 segment 顺序读原始 Session 历史，链变化为 source_stale。

- duty/legacy 判断只有 `createSessionDutyResolver` 一份（`legacyTemplateIsSecretary` 不存在）；`src/app/secretary-profiles.ts` 委托本正本，不要再写 duty/legacy 判断（FP-02、MH-01）。
- 不要复制领域规则或状态迁移：状态写入只经 `src/core/work-graph/state/`（AGENTS 第 9 条）。
- 不要另建第二个平台/服务图，也不要把某项业务选择（哪个 owner 做决定）写进装配层。
- 不要在别处拼项目库的文件名、Kernel 目录或 Kernel 入口（只用 `projectStorePaths`、`kernelStoreDirectory`、`kernelStoreEntry`）；不要把 `records` 挂到 `platform` 上，也不要为一个项目另开第二个 backend。
- 不要绕过 `trackedCall`（`src/composition/create-platform.ts:2401`）发布异步端口；关闭时用同一 drain，detached work 走 `trackDetached`（`src/composition/create-platform.ts:2401`）（MH-07）。
- 不要给未配置 `secretaryProfiles` 的 Host 发明 secretary：默认 profile 端口是 `defaultSecretaryProfiles`（`src/composition/create-platform.ts:3059`）的显式 null（FP-15、MH-02、FP-12、MH-12）。

- 新增 Host 选项必须声明、校验、转发、重开都走：`secretaryProfiles` 在 `src/composition/create-platform.ts:4426` 声明（FP-15、MH-02）。
