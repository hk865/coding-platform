# src/composition：唯一装配根——把受信任配置和各模块 owner 接成可关闭的 TargetPlatform

## 负责什么，不负责什么
- 装配层：可以接各模块并构造服务；只装配/接线，不复制领域规则，不把业务选择写进这里。
- 生产代码唯一构造 `createTargetPlatform` 的地方；Host 只经它拿公开端口，不能另建服务图。
- 不写状态：任何状态迁移只经 `src/core/work-graph/state/`（AGENTS 第 9 条）。
- 不被 `src/core`、`src/business` 反向 import；`src/app` 可以依赖本层。
- 默认值只作显式 seam：不发明 secretary profile、容量上限或 wake driver。
- 记录格式只在 `schemas`（`src/composition/create-platform.ts:1016`）注册一次：每个 codec 文件的 schema 束按 records、events、lookups 三段展开，内存和 SQLite 两种后端用同一份；Session 活动记录的 `SESSION_ACTIVITY_SCHEMAS`（`src/core/work-graph/sessions/session-activity.ts:39`）、初始化绑定的 `INITIALIZATION_BINDING_SCHEMAS`（`src/core/work-graph/persistence/initialization-binding-codecs.ts:9`，带两条 lookup）和初始化 adoption 的 `INITIALIZATION_ADOPTION_SCHEMAS`（`src/core/work-graph/persistence/initialization-adoption-codecs.ts:209`）也在其中。新格式只加进这三段，不另建 schema 集。
- 目标卡的接线：初始化绑定读只建一个（`createInitializationBindingReader`，`src/composition/create-platform.ts:1293`），请求事实、Plan owner、决定来源、规划问题读、草稿确认和发布的 `bindings` 共用它；`goals` 上加草稿确认 `confirmDraft`、复制预览 `readGoalCopyDraft` 和复制确认 `confirmGoalCopy`（`src/composition/create-platform.ts:2371`），都经 `trackedCall`；复制用的目标理解读 `readGoalUnderstandingFrom`（`src/composition/create-platform.ts:965`）在注记读模型之上，注记读模型建得更晚，所以经一个晚绑定的持有者转发（与 `boundNoteDecisionSource` 同一做法）。草稿确认的 `GOAL_CONFIRM_SCHEMAS` 和复制的 `GOAL_COPY_RECORD_SCHEMAS` 在同一处 `schemas` 注册。`bindings` 不可枚举。7A-2 的放行组 `messageRelease`（release owner、候选读和可信入口，逐成员经 `trackedCall` drain）与 Workflow 依赖的 `messageRelease` 共用同一个 `messageWrites` 和 `dispatchBasis`；复制干预的两个端口 `interventions`/`retractions` 进 `createGoalCopyService`，`goals` 上发布 `readCopyInterventions`（无路由）；`createMessageApplyOwner` 发布为 `platform.messages.applyMessage`，G 的 `message_release` 卡片来源和申请行在同一装配。`messageRelease` 不可枚举。初始化 adoption 的操作 owner 只建一个（`createInitializationAdoptionService`，`src/composition/create-platform.ts:2363`），和 `bindings` 共用同一个绑定读、Plan owner、catalog 和 policy owner，五个方法经 `trackedCall` 发布为 `initializationAdoption`；`confirmInstalledChecks`（`src/composition/create-platform.ts:2385`）只读 `currentCheckConfiguration` 的登记表（含静态回退），不读设置文件：没有配置时修订和摘要都是 null，`settings` 总是 null。两者都不可枚举，Host 的设置对象和 adoption 组合按属性读。
- 内部 owner 挂在 `platform` 上但不可枚举（`src/composition/create-platform.ts:4231`），公开 key 表不变，路由层按属性读。秘书生命周期是一个 owner 组：`sessionHandoff`（`src/composition/create-platform.ts:4112`）由 accept（`createSessionHandoffService`，`src/core/work-graph/sessions/session-handoff-service.ts:241`）和 advance（`createSessionHandoffAdvanceService`，同文件 `:728`）两个 owner 组成；`sessionArchive`（`src/composition/create-platform.ts:4113`）是手动归档的 accept+advance（`createSecretaryArchiveService`，同文件 `:1925`），对外的两个方法经 `trackedCall` 发布、raw owner 留在内部；同一处还发布 `readHandoffFence`、`listUnfinishedOperations`、`readSecretaryHandoffBasis` 三条读，全部经 `trackedCall`；`listUnfinishedOperations` 只答 handoff 和 secretary-archive 两臂并带种类（`{operation, revision, kind}`），别的未完成操作不是可继续的交接。 7C-1 的 `overlapGates`（`src/composition/create-platform.ts:3158`）是同一个门 owner 的 drained 包装：Workflow 拿 raw owner，两条 overlap 路由拿经 `trackedCall` 的端口，`releaseOverlapGate` 只从人的路由进入；它不可枚举。手动归档的预检由 `handoffFacts.checkArchiveCondition` 注入归档 owner（`src/composition/create-platform.ts:2846`）。条件由 `sessionLifecycle` 的持有者（`src/composition/create-platform.ts:1883`）在装配完成后直接收 `handoffFacts.checkArchiveCondition`（`src/composition/create-platform.ts:2766`），不另设条件分派器。H 的 brief 端口 `createHandoffBriefPort`（`src/core/work-graph/sessions/session-handoff-brief.ts:22`）注入 D 的 `brief`（`src/composition/create-platform.ts:1361`），`createHandoffNoticeSource` 的 `handoffNotices`（`src/core/work-graph/views/handoff-notices.ts:176`）进 `noticeSources`（`src/composition/create-platform.ts:1847`）；它们和 owner 共用 `sessionDirectory` 与 `sessionDutyResolver`（`src/composition/create-platform.ts:1242`）。

## 文件
- `architecture-reminder-facts.ts` — 当前正式 catalog 版本进观察提醒事实；读失败原样返回，abort 为 cancelled。
- `commit-observer.ts` — 包住共享 `records.commit`，上报真正追加事件的 commit；观察器失败被吞掉。
- `create-platform.ts` — 唯一平台装配：storage/body store、Kernel stores、Workspace、Runtime、WorkGraph owner、Workflow、秘书准备事实端口、秘书生命周期 owner（交接/手动归档、事实、brief、通知、交接 basis 与未完成操作的读）、提示词包与关闭 drain。 7C-1 还在这里接 M 的成员 owner（`createMemberService`，复用同一套 records/commit identity/容量与建线/请求事实/秘书轮/duty/Session 选人）、R 的返工请求 owner（`createReworkRequestService`，复用 requeue/evidence）、N 的唯一门 owner（`overlapGates`，同时交给 Workflow 和两条路由）和 P 的 pick 读（`pickReads`，含 A-07 的 `createPreClaimAuthorization` 预认领授权，不造 Run）。公开 `plans` 在构造处装好 PS 的采用前停止包装（整个 adopt 一次 `trackedCall`，raw apply/目标读/controls/`runtime.port` 同一次 drain；新公开目标读单独 `trackedCall`）；Workflow 的自动采用仍绑 raw `planService`。注记的工作区读在这里接齐：第二档的引用分析器 `createReferenceAnalyzer`（`src/core/workspace/reference-analyzer.ts:55`）和唯一的 Python/C++ 单文件查 `createNativeSingleFile`（`src/core/workspace/native-single-file.ts:105`）各建一个（`referenceAnalyzer`、`nativeSingleFile`，`src/composition/create-platform.ts:2907`、`:2909`），连同句柄的 `readWorkspaceFiles` 接进共用的 `noteWorkspace`（`src/composition/create-platform.ts:2906`），注记模块经 `noteCheckWorkspace` 换成平台身份再调；两者用到时才起线程和进程，平台关闭时在 `workspace.close()` 之前关掉（`src/composition/create-platform.ts:4294`）。Runtime 端口另有一份内存计数（`inFlight`/`countInFlight`，在 `runtimePort` 之前，`src/composition/create-platform.ts:2633`）：`startRun`/`startQuery` 的公共包装和给 Workflow 的 `rawRuntime` 都过它，按 ref 记还没返回的调用数，`idleSince` 记 map 变空的注入时钟；平台对象以不可枚举的 `runtimeInFlight`（`src/composition/create-platform.ts:4077`）交给 Host。`notes` 上另发布只读内存的 `doubtfulLinks`（`src/composition/create-platform.ts:3111`），供 Host 的后台批量读 R8 的存疑队列。
- `plan-adoption-stop.ts` — PS 的采用前停止包装：人的 `plans/apply` 先调 raw `applyPlanChange`；只有 TASK-19 的 `busy` 且 `reworkActorClassOf` 判 human 才读只改处置任务的全部 `starting`/`running` Run，逐个提交 `cancel`（`plan-change:<proposalId>:<taskId>:<runId>`、`stopping_affected_work`、现读 Run 的 pin）并投递；指针已 `cancelled` 的 Run 直接投递现有意图，`busy`/`revision_conflict`/`idempotency_conflict` 先按同一身份读既有 `ControlIntent`；`busy` 不再重交，只有 `revision_conflict`/`idempotency_conflict` 才对仍活着且无既有意图的 Run 用同一请求号和新 pin 重交（`MAX_CONTROL_SUBMISSIONS = 3`，含首次），耗尽或其它拒绝原样返回；停了至少一个返回 `busy`/`stopping_affected_work`，否则原样返回 raw 拒绝，计划零写。
- `session-duty.ts` — 受信任 Session duty 解析：pinned RoleSpec、精确 legacy template、配置的执行者回退；一次没有回答的读为 `unavailable`，没有平台职责才为 `unknown`。
- `tool-commit-lookup.ts` — 按固定 tool 名表把已提交调用查询派给 mailbox/decision/plan/notes/CRR owner。
- `work-line-conversation.ts` — line conversation 分页：按 segment 顺序读原始 Session 历史，链变化为 source_stale。

## 不要做
- duty/legacy 判断只有 `createSessionDutyResolver` 一份（`legacyTemplateIsSecretary` 不存在）；`src/app/secretary-profiles.ts` 委托本正本，不要再写 duty/legacy 判断（FP-02、MH-01）。
- 不要复制领域规则或状态迁移：状态写入只经 `src/core/work-graph/state/`（AGENTS 第 9 条）。
- 不要另建第二个平台/服务图，也不要把某项业务选择（哪个 owner 做决定）写进装配层。
- 不要绕过 `trackedCall`（`src/composition/create-platform.ts:2150`）发布异步端口；关闭时用同一 drain，detached work 走 `trackDetached`（`src/composition/create-platform.ts:2161`）（MH-07）。
- 不要给未配置 `secretaryProfiles` 的 Host 发明 secretary：默认 profile 端口是 `defaultSecretaryProfiles`（`src/composition/create-platform.ts:2761`）的显式 null（FP-15、MH-02、FP-12、MH-12）。
- 不要假设 wake driver 已存在：`createRequestIntake`（`src/business/workflow/request-intake.ts:193`）的 `wake` 来自平台选项 `requestWake`，没有它就什么都不接，提交的轮留在记录上等 Query 路由或下一个 Host；平台自己不推进任何轮。`requestRounds` 的 `open` 与 `unassigned` 一样经 `trackedCall` 发布，队列按页读、不写状态。
- 请求轮的授权预算只有一处：`createAuthorizeQueryConfiguration`（`src/composition/create-platform.ts:930`）的 `requested` 取 `queryExecutionBindingOf(input.job, input.run).runtimeBudget`（请求轮是认领时冻结的 profile 预算，普通 Query 与旧的 Job intent 相同）；不要在别处再读 Job intent 的执行预算。
- 新增 Host 选项必须声明、校验、转发、重开都走：`secretaryProfiles` 在 `src/composition/create-platform.ts:527` 声明（FP-15、MH-02）。
