## 先看这一页要确认什么

根本设计问题是：**哪些工作应在同一段持续演进的 Context 中完成，何时继续、刷新、换手或结束，以及后续怎样继承这段工作的理解。**记忆组织和书记职责从这条生命周期推导。**还必须一起确定这些 Context 之间由谁编排、如何交流、如何处理跨工作包冲突，以及架构／接口变化怎样经秘书／参谋向人汇报并形成决定。**只有生命周期与记忆不足以定义完整协作系统。

建议一起确认五个方向：

1. **Context 跟随连贯工作持续。**一次模型回复、工具调用或暂时等待，不自动结束工作 Context；同一工作中的调查、实现、测试和相关返工可以连续积累理解。
2. **工作可以跨 Context 接续。**容量、故障或范围变化需要换手时，保留工作前沿和关键理由，重新核对当前事实与权限；已完成工作也留下可供后续相关任务继承的记录。
3. **执行者记录，书记整理，参谋辅助取舍。**先明确职责和输出，初版允许同一协调 Agent 分别承担书记与参谋职责，不要求新增常驻 Agent 或独立记忆存储。

4. **多个包工头有明确的分工与冲突处理路径。**按工作包组织执行者，跨包分歧由相关负责人参与澄清，指定集成职责负责收敛；不能靠最后一份报告覆盖前者，也不能只有测试失败才触发协调。
5. **秘书／参谋贯穿执行反馈。**发现需要改变架构、模块职责或接口契约时，汇总双方依据、选项与影响向人上报；已有授权内的处理也必须可见，需要新取舍时等待人的决定，再经框架更新规范、计划和受影响 Context。

接受这五个方向后，下文默认规则及验收场景作为下游修订依据。若只认可部分，可指出对应编号或表格行；本次确认仅针对这份设计，不自动等于批准整个 P0/P1 或启动后续实现。

## 用户意图与当前工作位置

用户以“Agent 本质是一段 Context 加调用”解释连续工作主体；生命周期关注的是这段 Context 被持续使用、扩充的时间。执行者创建或修改模块状态，状态加上变更取舍构成其工程理解的重要部分，应该可以在后续近似恢复。用户期望需求经协商形成文档、拆成开发粒度、自动执行，需要新的取舍时向人说明；任务图允许在执行反馈中调整。

来源：[此前完整对话记录](执行agent生命周期与执行记忆-对话记录与答复.md)，以及本轮用户明确“各个 LLM 的 Context 生命周期才是根源”、要求先改人类文档再改 Ticket。后续补充明确：需要覆盖包工头间的交互冲突、架构／接口变更上报，以及语义面和控制面的编排交互再确认，不能将反馈缩减为测试失败。

目前不是从零重新设计：P1-03 已有派发和有界输入的实现证据，P1-06 已有同任务 A→B 换手的实现证据。分别见 [P1-03 证据](../verification/p1-03-implementation-evidence.md)、[P1-06 证据](../verification/p1-06-implementation-evidence.md)。这些证据证明原验收范围，不自动证明本稿新增行为；也不因新增需求而抹去。

## 生命周期中需要区分的对象

| 对象 | 在本稿中的含义 | 与其他对象的关系 |
| --- | --- | --- |
| 单次 LLM 调用 | 模型基于当次材料生成一次响应 | 一段工作 Context 可服务多次调用 |
| 工作 Context | 围绕连贯工作持续更新的输入、工具结果、假设、理由与工作前沿 | 本稿的讨论用语；是否需要独立持久标识，留给确认后的契约设计 |
| ContextBundle | 按权限、版本和预算选出的输入材料 | 是初始化或接续的材料，不能据其大小上限推断完整运行 Context 的生命周期 |
| AgentRun | 逻辑执行者的一次实际运行 | 内含多次模型／工具调用；其与压缩、暂停、换手的映射需要明确，不能预设一次调用就是一个 Run |
| 连续工作责任 | 执行或协调一段工作的责任及身份关联 | 可以跨 Run 和 Context；任务变更或转交时显式更新 |
| 持久记录 | 当前工程事实、开发轨迹、关键理由、未解项及来源 | 可以长于任务与 Context 的活跃期；按适用范围被后续工作读取 |

**有界指每次使用的材料受预算约束，不表示会话、身份或历史不能长期保存。**归档消息可作为来源，但不要求整体回放；“继续原会话”和“用材料建立新会话”都须核对当前工作、版本与权限。

## 各类 Context 建议跟随什么工作

以下按职责列默认行为，职责不等于独立进程，也不强制每种职责永久拥有一个 Context。

| 职责 | 连续使用范围 | 正常结束／接续条件 | 必须留下的内容 |
| --- | --- | --- | --- |
| 执行者／Coder | 一段可验收开发工作中的调查、实现、测试与相关返工 | 验收后结束活跃责任；取消或转交时交代前沿；范围实质变化或运行不可恢复时重建 | 变更与版本、验证依据、关键取舍、未解项和下一步 |
| 规划／集成者（包工头） | 一个明确工作包内的分工、反馈、集成和调整 | 工作包完成、撤销或转交；等待期间可休眠，恢复前刷新事实 | 分工依据、依赖与冲突、计划调整理由、待接收结果及跨包协商事项 |
| 秘书／参谋 | 初始需求及执行中架构／接口冲突等决策议题的多轮协商 | 决定形成、议题搁置或转移；相关追问继承议题记录 | 需求、约束、选项、理由、决定来源与待确认项 |
| 书记 | 一次汇报议题及必要的前次汇报背景 | 简报交付后可结束；持续跟踪保存上次覆盖的位置，下一次读取新增事实 | 带来源的摘要、分歧、未验证结论与覆盖范围 |
| 调查／QueryJob | 一个明确问题的调查与有界澄清 | 答复、预算耗尽或材料缺口明确时结束；新问题建立关联的工作 | 答案、依据、覆盖不足及未解决问题 |
| Reviewer | 对明确版本与验收范围的审查 | verdict 或明确缺口后结束；修订后重新核对范围，允许参考前次审查 | 审查依据、问题、结论和未覆盖项 |

Ticket 与 Module 是多对多关系：一次工作可穿过少量 Module，一个 Module 会经历多次工作。记录同时关联工作、受影响模块／接口和版本，避免以“模块永久归某个执行者所有”作为接续条件。

## 什么事件应该如何处理

| 事件 | 建议默认行为 |
| --- | --- |
| 一次模型回复或工具完成 | 在当前工作 Context 中继续，不机械地重建 Agent |
| 等待工具、其他 Agent 或人的答复 | 保留工作关联和必要恢复材料；等待本身不等于任务结束，也不要求进程常驻 |
| 同一范围内验证失败、需要返工 | 保留相关理解并补入失败证据；若框架需要新任务／版本，显式关联此前工作，不让“新任务”自动丢失理由 |
| 多个包工头发现接口假设不一致或模块职责冲突 | 保留各方依据，经有界讨论和必要调查形成影响判断；需要架构／接口变化时送秘书／参谋向人上报，不等待测试失败 |
| 已提出架构／接口变更，等待人决定 | 保存问题、选项、版本和受影响工作前沿；停住依赖未定选择的修改，不受影响工作可继续；沉默不构成接受 |
| Context 接近容量或重复探索明显 | 先在安全点检查材料质量与工作范围；可压缩、刷新或换手，不把容量信号直接当作失败 |
| 暂停后恢复 | 能安全继续原运行时先刷新必要事实；原运行不可恢复时通过新 Run 接续，不能把恢复伪装成原进程一直存活 |
| 目标、计划或规范变更 | 判断受影响工作；更新或重建受影响 Context，标明旧假设的适用性；不受影响工作继续 |
| 故障或责任转交 | 从已经持久化的事实恢复；若缺少理由或工具结果则明确缺口，未知副作用保持未知 |
| 验收、取消或议题结束 | 结束活跃工作，保留必要记录；正常退出整理记录，崩溃恢复不依赖执行者最后成功写出总结 |
| 后续相关新任务 | 加载当前代码／规范，加上适用历史与关键理由；保留继承来源，不复活旧授权或旧完成状态 |

同一工作内的正常继续与反馈是基本行为；原会话恢复、压缩等具体能力由运行内核声明。缺少能力时使用有界接续或明确报告不可用，不能假设内核必然支持。

## 平台、内核与记忆的分工

- 平台中的语义协调提出分工、Context 使用与冲突处置方案；确定性控制依据当前授权和版本校验、登记、派发与维护状态。涉及新架构／接口取舍的行为按下节人类汇报与决定路径处理。
- 执行内核处理单次 Run 内的模型／工具循环和已支持的 Context 管理、安全点及恢复。平台通过 WorkerRuntime 使用这些能力，不另写一套内核循环。
- Data Plane 保存并提供原始工程事实、开发轨迹和语义提示；ContextCompiler 根据当前工作编译材料，不自行启动模型或决定谁接手。
- 执行者在关键选择发生时留下简短理由。必记项是影响接口／行为、后续维护、失败重试路线及未解风险的选择；普通机械步骤无需逐一解释。
- 书记可以归并、标注冲突并请求补充依据，不能事后把推测写成原执行者的理由。参谋使用这些材料提出选择与影响；架构／接口变化必须向人上报，需要新授权或业务取舍时等待决定。上报与逐项审批的区别见下节。

建议留痕包含：选择及简要理由、必要的备选或放弃项、来源与适用版本、不确定性、结果或待验证项。记录可属于普通工作笔记；改变规范、授权或验收仍走正式决定路径。共享的是工程理解，作者与执行身份用于追溯，不构成独占访问权。

这使执行者能以“持续的工作责任＋可接续的理解”长期存在；活跃 Context、运行资源与持久历史各自结束或保留，不强制同步销毁。

## 编排与交互需要一并确认

### 语义判断与确定性控制各做什么

本稿的“语义面”指现有 Control Plane 内的 Semantic Coordination，不新增一个独立 Plane；“控制面”在下表特指其中的确定性控制职责。角色提出方案和判断，框架校验并执行受理后的动作，两者共同完成编排。

| 参与方 | 负责什么 | 交给谁／不能替代什么 |
| --- | --- | --- |
| 人 | 明确需求与取舍，决定新的架构／接口选择及必要授权 | 决定须绑定具体方案版本，不直接改写运行状态 |
| 秘书／参谋 | 持续接收执行反馈，组织跨包影响分析；可请求调查；向人说明问题、选项、建议和影响，并传回决定 | 通过框架派发调查、登记提案与决定；不能将建议当成人已接受 |
| 包工头／规划集成者 | 负责明确工作包的分工、局部方案、执行跟踪与汇合；与其他包工头协商接口、依赖和资源冲突 | 向框架提出工作／交流请求；跨包问题交指定集成职责收敛，架构／接口变化交秘书／参谋上报 |
| 执行者 | 执行任务、调查实现，主动报告假设失效、接口缺口、架构问题和验证结果 | 不必等测试失败才报告；不能自行把临时方案变成正式跨包契约 |
| 书记 | 保存可追溯的各方报告，整理一致项、分歧与未解项，供参谋、包工头和人阅读 | 可标出冲突并请求补充，不裁决哪方正确，不成为每条通信都必须经过的串行节点 |
| 确定性控制 | 校验角色、工作范围、授权、版本、预算、真实依赖与写入资格；持久登记、路由、派发、安全点控制和状态归约 | 不判断业务方案优劣；缺少语义结论时请求相关角色，缺少授权时不执行未获授权的变更 |
| Data／ContextCompiler | 保存来源、工作与议题记录，为各参与者提供权限内的相关材料 | 不分配责任、不接受方案、不自动启动 Agent |

### 正常编排和多个包工头怎样协作

1. 人与秘书／参谋形成需求、架构和已接受计划。协调者据此提出工作包、负责人、必要输入输出与集成安排，框架校验并登记后派发。任务图是当前版本的工作结构，允许通过反馈修订。
2. 每个包工头在明确范围内组织执行者，也可提出调查或有限协作请求。每次派发都由框架校验权限、预算和输出要求；不预设所有包工头共用一个长 Context，也不允许无界自行扩展组织层级。
3. 相关包工头可通过有界问题、报告和讨论直接协商。消息携带工作／议题、来源版本、期望答复和预算；框架负责登记与投递，在安全点加载需要影响执行的指令。只读查询仍使用独立路径，不隐式插话源 Worker。
4. 跨工作包问题指定一个负责收敛的集成职责，参与方保留各自依据。若已有共同集成负责人则复用；否则由协调角色提出责任安排，经框架接受。收敛责任表示组织讨论、形成结论或升级，不意味着拥有架构变更批准权。
5. 普通澄清、契约内调整和已授权返工可形成可追溯提案并继续执行。报告本身不建立阻塞依赖；只有后续动作确实依赖未定选择或缺失产物，才由控制路径暂停或阻塞该部分工作。

### 冲突如何进入秘书／参谋和人类决定路径

冲突可来自执行调查、包工头讨论、代码／规范对账或人主动提出问题，不要求先出现测试失败。例如：两个工作包对接口错误语义理解不同；既定接口缺少完成需求所需的信息；原模块职责分配造成无法解决的耦合。

| 步骤 | 可观察行为 |
| --- | --- |
| 发现并汇集 | 执行者或包工头提交问题、各方主张和来源。书记整理可读摘要并保留分歧，不以后到报告覆盖此前判断 |
| 澄清与调查 | 集成职责组织相关包工头有限讨论；需要新事实时，包工头或参谋经框架请求有界调查。超时或预算耗尽留下明确未解项，不无限循环 |
| 区分处置 | 若只是对现有契约理解错误，按契约澄清并记录；若提出修改已接受架构、模块职责、跨模块接口签名或行为契约，必须进入秘书／参谋上报路径 |
| 向人上报 | 参谋呈现为何原方案不够、各方依据、可行选项、推荐及理由、受影响模块／接口／任务、验证和迁移成本、当前暂停与可继续范围；书记负责事实依据与分歧可追溯 |
| 接受或退回 | 新取舍或授权不足时，人可接受、修改、拒绝或延后；决定关联具体方案版本。已有明确授权覆盖时，仍上报处理依据和影响，可在该授权内受理，不要求重复批准 |
| 正式更新 | 框架校验决定、授权和当前版本，经适用的规范／baseline／计划变更及验证门禁登记或激活；不能只改会话中的理解就当作契约更新完成 |
| 通知并接续 | 把被接受的变化、理由和影响送回所有受影响包工头与执行者，确认执行材料已刷新或 Context 已重建后再继续相关动作；旧依据和迟到结果不得推进新版本状态 |

**架构／接口变化必须上报人类。**上报不能仅留下数据库记录等待人自行发现：应进入统一界面的变更汇报或待决事项。上报不等于所有内部函数重构都逐项审批，也不意味着存在笼统的自动变更授权；本稿不新授予任何此类权限。已有授权内变更的通知形式和时机，确认后在交互契约中细化，不能将其优化为无反馈。

审阅时曾识别 P1-11／14 与正式规范尚缺此路径；现已按专项确认同步，当前条款见 [人类交互契约](../interfaces/human-design-status.md)，实现与验证仍由相应票完成。

### 交互如何影响 Context 与记忆

- 每个持续讨论的问题保留议题关联、参与职责、来源版本、各方观点、待答复事项与结果；这些是普通工作记录的组织要求，尚不要求新建独立存储或状态机。
- 执行者保留实现 Context，包工头保留组织工作的 Context，秘书／参谋保留跨包取舍议题的 Context。各自只加载相关材料，记录引用连接这些 Context。
- 等待决定可以休眠或换手，交接必须包含“在等谁、什么决定、哪些动作不能继续”；恢复后先核对是否已有新决定。
- 拒绝或延后的提案保留原因，不能因换了 Agent 就重新当成已获准方案执行；新证据需要重新提案时说明变化。
- 变更完成后，把当时分歧、最终选择、适用范围和验证结果写回工作与议题记录。下一次相关开发能理解“为什么改成现在这样”，也能判断旧理由是否仍成立。

## 用一个完整场景确认是否符合预期

1. 人与秘书／参谋经过多轮讨论形成需求、架构选项和决定；框架接受相应规范与计划。秘书／参谋在后续执行中继续承担反馈和决策支持。
2. 协调者划分两个相关工作包，明确包工头甲、乙的范围和集成责任；两者经框架组织各自执行者。执行者在连续 Context 中调查、实现、测试并留下关键理由。
3. **即使测试尚未失败**，甲发现既定接口缺少必要字段，乙认为增加该字段会破坏其模块职责。双方保留依据并开展有限澄清；集成负责人请求调查，确认需要调整接口或架构，而非单纯修复实现。
4. 书记整理双方观点、证据和未解项；秘书／参谋说明选项及对模块、任务、验收和迁移的影响并向人上报。先走一次拒绝或延后，验证拟议变更未被偷偷应用、依赖该选择的修改停住、独立工作可继续。
5. 人修改或接受具体方案后，框架校验当前版本和授权，经适用门禁更新规范／baseline／计划。甲乙及相关执行者收到决定与理由，刷新或重建受影响 Context。另注入旧版本决定及迟到报告，验证它们不能推进新状态。
6. 新版本执行中再制造一次普通测试失败，验证授权内返工可沿原工作理解推进，不把所有问题都升级给人；独立 Reviewer 依据当前契约验证。
7. 在“等待决定”及“执行中”分别测试暂停恢复、Context 换手和崩溃。接续者知道当前前沿、待决项与禁止继续的动作；缺失总结或未知工具结果如实保留；某个包工头换手不让独立 Worker 随之停止。
8. 工作验收后归档，平台重启。后来出现相关新任务，执行者读取当前模块及此前接口变更的分歧与理由；人为改变一个旧前提，验证能指出不再适用之处。
9. 人通过书记简报及秘书／参谋解释看见变更、依据、已处理事项与尚需选择的问题；额外验证已有明确授权覆盖的架构／接口变更也会主动上报，不因无需重复批准而消失。

验证既包括近似恢复，也包括编排交互：能否保留关键约束和理由、识别陈旧前提、把跨包冲突送到正确职责、把架构／接口变化上报人、把决定送回全部受影响工作。不会以“新模型说自己记得”、模型自称达成共识或一轮测试通过代替这些结果。

## 审阅时的施工建议（已由正式规划承接）

现在一起确定生命周期、编排与交互基本行为，不等全部 Ticket 完成后再补。复杂检索、自动压缩阈值优化和独立书记进程可后续按证据决定。

| 范围 | 确认后如何处理 |
| --- | --- |
| PRODUCT／CONTEXT／ARCHITECTURE | 落实连续性承诺、跨包编排、架构／接口变化上报义务，以及语义协调／确定性控制／内核分工 |
| 运行时协作及相关 Module | 明确角色通信、冲突收敛、待决与通知、Context 事件语义及兼容性；已有 schema 有变化时显式升级 |
| P1-03、P1-06 | 对照既有实现证据检查差距；保留原验收，追加有界扩展或补充票，不追溯声称新增行为已通过 |
| P1-09、P1-10、P1-11 | 分别落实查询、暂停恢复和计划变更的 Context 规则，冻结消费者契约前明确行为 |
| P1-15 | 整合多个包工头协作、秘书／参谋贯穿执行、书记汇报、冲突升级与决定反馈；避免承接全部底层生命周期实现 |
| 已完成工作供后续任务继承 | 建议独立纵向切片，具体编号与依赖确认后安排；不因编号靠后就默认排在所有票之后 |
| P1-12、P1-14 | 核对架构／接口变更的发现、简报、人的决定与激活；与 P1-11／15 共同覆盖执行中提出变更的路径，不限于事后漂移或测试失败 |
| P1-04、07、08、13 | 核对审查独立性、并行隔离、变更上报展示与授权内修复；仅修改确有影响的条款 |
| MVP、P0-06、DAG／ROADMAP | 同步接续场景、审阅范围和真实产物依赖，独立工作不增加无根据的阻塞边 |
