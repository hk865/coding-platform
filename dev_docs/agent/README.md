# Agent 执行与维护入口

职责以 [文档职责与权威关系](../document-ownership.md) 为准。人类入口是 [human/README](../../human/README.md)。

## 按任务读取

建立项目、派发实现任务或迁移目录时，先读取 [项目位置与建项入口](project-location.md)，分别定位代码根目录、文档根目录和执行内核。

| 当前任务 | 必读材料 | 完成产物 |
| --- | --- | --- |
| 实现、评审或集成 | [AGENTS](../../AGENTS.md)、当前 Ticket、直接引用的 Module／Interface、相关规范条款和上游产物 | 实现、验证与有界 Handoff |
| 承接需求／架构／验收变更 | 修改的正文、本页流程、受影响文档 | 同步修改、影响记录与检查结果 |
| 调整计划 | 已接受范围、[ROADMAP](../planning/ROADMAP.md)、当前 DAG 与相关 Ticket | 依赖、验收和写入范围明确的计划 |
| 更新图或入口 | 对应正式来源 | 可追溯的投影与导航 |

## 上游修改后的更新流程

1. 确认依据：记录用户指令或决定、源文档及变更条款，区分文字修订和行为变化。文档整理本身不代表阶段批准。
2. 查找影响：搜索链接、契约名及相关行为术语，覆盖 Module、Interface、DAG、Ticket、验收与展示图。仅有显式链接不足以证明没有影响。
3. 同步定义：在权威位置更新约束并处理重复或冲突。已授权细化直接完成，缺少业务选择时提供具体差异和影响。
4. 同步执行材料：更新受影响 Ticket 的输入、输出、Acceptance、Verification 和真实 blocking edges；记录需要复核的进行中任务，独立分支可继续执行。
5. 核对执行依据：派发与集成前对照当前规范和上游产物。相关依据变化时，在安全检查点重新评估，更新实现及必要验证后再交付。
6. 验证与交接：运行文档检查及适用测试，列出已同步文件、复核后无影响的项目、未决事项和依据。完成条件是受影响对象均有明确处置；结构检查通过不证明语义一致。

有当前变更 Ticket 时在票内保存影响记录；没有时在 `verification/` 保存本次有界记录，从交接结果链接。历史证据保留原依据，新验证追加记录。

## Context 与并行边界

实现者加载实际消费的规则、接口和相关全局约束，结合必要相邻 Ticket 与精确上游产物。维护者为识别影响可以搜索全库，随后收敛到受影响材料。

并行工作分别核对接口兼容性和写入范围，共享契约变化在消费者集成前协调。人类交接提供结果、必要裁决和证据入口，技术细节保存在维护材料中。

在产品根目录运行 `node dev_docs/verification/validate-docs.mjs`。影响识别和执行中依据复核目前是 Agent 执行的流程，尚未实现自动拦截。

## 开发工作的 Context 与留痕

单张 Development Ticket 内连续推进调查、实现与验证；跨 Ticket 默认新 Context，读取自包含任务及适用上游记录。关键取舍及时记入该票关联的产物／交接，正常结束交付结果、理由、验证、未解项和版本；记录不能替代有效 Evidence。跨模块冲突由编排／集成职责组织澄清，架构或接口变更向人说明选项与影响，决定后同步规范和所有受影响执行材料。

本节是开发流程；产品运行时的实际机制须由 [Context 生命周期](../interfaces/context-lifecycle.md) 及其消费者实现，不能以手工遵循文档声称运行时已具备。
