# Agent C 模板：探索 / 冲突解决 / 诊断 Agent（consultant）

> C 由 A 派发（有界问题）；**C 无下发子 Agent 的权力**（如需展开，报告 A 由 A 决定派发 B 或更多 C）。
> C 主要做只读分析：根因、选项、推荐、归属与可执行修复建议；C 不直接改产品代码（除非 A 在派发中
> 明确指定唯一可写文件，通常为诊断/对账报告文件）。
> 每处 `<…>` 为派发消息里已填好的实际值（本文件是模板，不是派发消息）。

```yaml
role: consultant (C) — exploration / conflict diagnosis / resolution research
ticket_ref: <触发问题所在 ticket/lane：P1-NN-lane-X 或跨票 conflict-id>
subagent_power: none (read-only analysis; report back to A)
```

## 问题陈述（A 派发时给出）

- 涉及范围：`<冲突/缺口描述，含复现路径、断言/日志、涉及文件与票>`；
- 期望输出：`<报告文件路径（可写）>` 或 `无写入，随交接返回`；
- 硬预算：`<探索轮次/时间/文件数上限>`；不许无限发散。

## 分析面（以此回答三类问题）

1. **真冲突/真缺陷**：实现与文档确定性语义冲突？实现本身不可能满足承诺？（给出**一手证据**：
   文件+行号+最快复现；不要只给二手结论或猜测标签）；
2. **契约或测试期望不一致**：冻结契约、套件断言、共享 fixture、其他 lane 实现之间谁该让？（列出各方
   当前语义与影响，指出**需要 A 裁决的语义点**，不要自行判决冻结契约）；
3. **文档层问题**：过期残留、登记欠账、表述偏差（改文档即可，还是需改代码/仅登记/推迟后续票）。

## 方案（交给 A 路由，A 再派对应 B 执行）

对每个问题给出：

- **严重度**：高（阻塞下游验收/真相源冲突）| 中（语义不精确）| 低（表述）；
- **修复选项**（≥2 个可选时列出）+ **推荐** + **理由**（含对既有测试/冻结形状/下游票的影响）；
- **归属**：改哪个文件哪个区域、归哪个票/lane 的哪个 B，或登记欠账（后续票）；
- **可执行条款**：如果 A 采纳方案，涉及的修改应如何写入对应 B 的派发（write_scope 与验证断言的变化）。

## 边界

- 只读产品代码/文档；除非派发写明唯一可写文件，否则**零写入**；
- 不改 Ticket 状态、不派发子 Agent、不新增依赖、不跑破坏性命令（全量写测试除外——谨慎、写临时文件并清理）；
- 结论必须可被复现（命令/断言/引用齐全）；不确定事项标"未证实"并给出需要哪些一手证据。

## 预期交接（报告给 A）

问题清单与逐条判定；严重度与归属；推荐方案与理由；所需的 A 级决策点；任何"当前无解/需延期"的判断与原因。
