1. P1-05（另一 session）与 P1-06（本 session）从同一基线 `5a278cb` 并行；P1-05 在以 `5a278cb` 为基的 **main 工作树内直接工作**（未隔离 worktree），P1-06 也在同一 worktree 先写契约文件；
2. P1-06 首次 `read` 到 events.ts 时**未察觉文件已被 P1-05 修改**（"file changed since it was read" 守卫被 write 全量覆盖绕过）——P1-06 用 `write` 全量重写 events.ts，**丢掉了 P1-05 的 GoalPhaseUpdatedEvent**；
3. 用户观察到风险后暂停；P1-05 完成后恢复；P1-06 在隔离 worktree（`agent_platform-p1-06`，branch `p1-06-int`，基于 `d1c6595`）重建，并：
   - 恢复被覆盖的 P1-05 内容（git checkout）→ 重建分支 → rebase 到 P1-05 最终版；
   - rebase 产生 3 文件 7 处文本级冲突，逐一按"双方皆保留、版本化追加"机械合并；

## 为什么没有语义分歧

- 层面不同：P1-05 = Goal 级（GoalPhase 聚合/视图/reducer），P1-06 = Task 级（HandoffPacket/ReplacementAttempt 聚合；复用 P1-03 冻结的 dispatch 形状）；
- 命名空间不重叠：聚合（GoalPhase vs HandoffPacket/ReplacementAttempt）、事件、commitKind（goal-reduction vs handoff-record/replacement-claim）互不引用；
- P1-06 明确**不修改** P1-05 任何文件，只做共享面追加。

## 解决方案与验证

1. events.ts / ledger.ts / validation.ts 均保留双方内容，P1-06 块整体置于 P1-05 块之后（P1-05 的 validateReduceGoalCommand 逐字节保留）；
2. 两个新事件为创建型（aggregateRevision=1），不进 `isActivationEvent`（与 P1-05 的 GoalPhaseUpdated 不同，该语义由 P1-06 套件覆盖）；
3. 验证：typecheck 0 errors；`pnpm vitest run` = 64 files / 539 tests PASS（P1-05 53 个测试零漂移）；只读 diff 对 P1-05 专属文件为空。

## 给并行流程的教训（control-plane）

1. **并行 session 必须隔离 worktree**——main 工作树是共享写入面，任何 session 不得在其中直接工作（这是本事故根因）；
2. **只追加、不全量重写共享文件**：`write` 全量覆盖会静默丢掉并发修改；读后变更守卫（"file changed since it was read"）是保护信号，应 re-read 而不是绕过；
3. **共享面（events/ledger/validation/ledger-validation/modules/index）的并发追加天然冲突**：并行窗口内，先到者优先，后到者在"上游已含先到者"的新基线上追加（rebase）而不是在共享树内直接改；
4. **本次"文本级冲突、语义无冲突"的判定依据**（层不同/命名空间不重叠/单向追加）应成为后续任何两票并行的 pre-flight 检查表；
5. 冲突/事故记录（本文件）与验收证据分离存放，带标签供记忆检索。
