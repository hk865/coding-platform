## 1. 产品决策

本方案把经历 M0—M6 建立可运行基线的 `coding-agent` 视为 **Execution Kernel / Worker Runtime**，
并在其上新建独立产品 **Agent Platform**。

这不是一次命名调整。新产品新增了自己的：

- 长期用户入口与交互模型；
- Goal、Task Graph、Task State、Plan Revision 等领域对象；
- 数据面、控制面、调度与验证闭环；
- Agent 生命周期、预算、并发、Handoff 和恢复语义；
- Query/Command API、Read Model 与展示界面。

这些对象的生命周期跨越多个 Agent、Run 和 Context Window，不能由某个 Worker 的
transcript、Todo 或进程内状态承载。

## 2. 要解决的问题

### 2.1 用户问题

长任务或多 Agent 工作时，用户经常无法可靠回答：

- 当前目标被拆成了哪些任务，它们为什么有依赖；
- 哪个 Agent 正在做什么，是否卡住或已经失联；
- 某项任务为何显示完成，验收证据在哪里；
- 用户修改目标后，旧 Run 的结果是否仍然有效；
- Agent 或进程中断后，下一执行者从哪里继续；
- Todo、聊天文本、实际代码和测试结果冲突时，哪一个是真的。

### 2.2 现有 Todo 的根因

典型 Todo/Plan 工具只是模型可修改的结构化笔记。`update_plan` 与 read、edit、test
等动作对模型是平级工具调用，它不会机械阻止模型跳过步骤，也不会根据工具事实自动验收任务。
因此模型在结尾一次性勾选全部项目，是当前架构的自然结果，不是再增加一句提示词就能根治的问题。

本产品固定以下关系：

```text
Plan          = 对未来如何做的可变方案
Task Graph    = 要完成什么以及任务之间的依赖
Task State    = 控制面根据已提交事实归约出的真实状态
Todo List     = Task Graph + Task State 的 UI 投影
Context View  = 为当前 Worker 裁剪的任务状态视图
```

即：

> `Plan ≠ Task Graph ≠ Task State ≠ Todo ≠ Context`。

Todo 不接受独立写入，也不承担真相源职责。

## 3. 产品愿景与核心假设

### 3.1 一句话愿景

> 用户通过一个长期 Human Interaction Layer（暂称 Secretary），在同一应用中对话、查看仪表盘、讨论方案并安全纠偏；后台 Project、Workspace 和 Agent 可以切换、并行或恢复，但状态始终可追溯、可验证且不依赖模型自报。

### 3.2 首要产品假设

第一版要验证的不是“多个 Agent 能否同时聊天”，而是：

> 单一控制入口能否可靠管理多个隔离的 Project/Workspace 和可替换执行者，让用户以低认知成本看清真实计划、Agent 动态、阻塞原因、完成证据与需要自己裁决的事项。

### 3.3 设计原则

1. **观测事实不被叙述覆盖。** 测试、工具结果、Artifact 和 Workspace revision 是事实；人类可以修改目标、接受风险或停止工作，但不能把一个失败观测改写成成功。
2. **LLM 提议，证据驱动归约。** Planner 生成 `PlanProposal/PlanPatch`；Worker 只提交 CompletionClaim；静态检查、动态检查和 Reviewer 产生 Evidence；Controller 按当前版本化策略唯一推进状态。
3. **期望状态与当前状态分离。** 用户表达 active/paused/cancelled 等 desired state；Reconciler 推动 current state 收敛。
4. **执行者可替换。** Goal/Task/Decision/Evidence 不挂在单个 Agent、Run 或 Context Window 上。
5. **Command 与 Query 分离。** 机械查询只读 Read Model；语义咨询可显式创建只读 QueryJob；暂停、继续、取消和纠偏进入 Command API。
6. **Todo 只做投影。** 即使 Worker 从不调用 `update_plan`，界面也必须显示正确进度。
7. **先受控并行，再并行写。** MVP 同时验证 Worker 换手和双只读 Worker 的真实并行；目标 checkout 仍由唯一 Writer 修改。
8. **仓库内知识可发现、可校验。** 文档是地图，schema、状态机、测试和事件才是可执行约束。
9. **期望架构持续与实际代码对账。** 每个 ArchitectureBaseline revision 不可变；active baseline 只能通过带 CAS guard、且匹配 accepted Decision 授权目标的 BaselineActivation 前进，不能为当前实现自证。切换 Project 默认 baseline 不会追溯性改变已存在 Plan。
10. **控制模型领域中立，首个 Runtime coding-first。** 领域差异由 Tool、Role、Policy 和 Verifier 扩展，不污染 Goal/Task/Run 的通用生命周期。

## 4. 目标用户体验

用户面对的是同一应用壳中的主对话与可切换面板，而不是彼此割裂的多个产品。

### 4.1 下达与修改目标

- 用自然语言创建 Goal；
- 查看系统提出的 Task Graph 和验收条件；
- 接受、修改或拒绝 PlanPatch；
- 在执行中追加约束、改变优先级或取消部分任务；
- 修改 Goal 时默认只暂停受影响子图，在安全点保存状态与副作用结果，展示影响分析，经用户确认或低风险策略放行后创建新 revision。

### 4.2 查询真实状态

Human Interaction Layer 能回答：

- “现在做到哪里了？”
- “为什么还没完成？”
- “谁正在做这项任务？”
- “这项完成结论有什么证据？”
- “如果现在暂停，之后从哪里继续？”

机械状态回答必须来自 Read Model，不依赖某个对话 Agent 的记忆。若问题需要工程判断，平台可以从已提交的
`ContextTaskView`、Artifact 和 `WorkspaceSnapshot` 创建只读 QueryJob；工作中的 Agent 不暂停，QueryJob
也不能读取隐藏思维链、刷新原 Run 的 lease 或修改原 Task。

### 4.3 控制执行

用户可以 pause、resume、cancel、steer、approve 或 reject。命令持久化后由控制面处理，
UI 不直接操作 Worker 进程或 Runtime 内存。

“打断”必须按意图区分：

| 意图                    | 默认行为                                                                |
| ----------------------- | ----------------------------------------------------------------------- |
| `query/discuss`         | 不暂停；从 Read Model 回答，必要时创建只读 QueryJob                     |
| `remind/context_add`    | 排队到下一个 Runtime 声明的安全边界，同一 Attempt 继续                  |
| `steer`                 | 目标与验收不变时在安全边界注入，Worker 必须确认收到                     |
| `amend_goal/task`       | 暂停受影响子图、保存快照、影响分析与确认，然后创建新 Goal/Plan revision |
| `emergency_stop/cancel` | 立即尽力停止，并对已发生或未知的外部副作用进行对账                      |

### 4.4 主动协作与工具

- 系统可以在出现业务信息缺口、工程 trade-off、高风险/不可逆动作、证据冲突、长期 blocker 或预算异常时主动提醒；
- 重大或含糊的 ArchitectureFinding、反复漂移和过期 ArchitectureDeviation 以 ArchitectureDecisionBrief 进入 Decision Inbox；低风险自动修复只进入摘要，避免通知噪声；
- Advisory 能帮助用户讨论方案、解释 Agent 决策并提出 PlanPatch，但无权自行提交新 Goal 或绕过审批执行高风险动作；
- 用户可以从控制台发起代码分析等工具；只读工具可直接形成 QueryJob，任何状态变更或外部副作用仍走 Command、权限和审计链；
- 询问正在工作的 Agent 不等于中断它；所谓“副本”是从已提交快照组装的新 Context，不是复制隐藏内部状态。

### 4.5 查看六个稳定面板

1. **Conversation / Advisory**：自然语言命令、查询、讨论、提醒和多结果回传；
2. **Portfolio / Workspace Dashboard**：跨 Project/Workspace 的总览、切换、冻结与恢复；
3. **Plan Graph / Todo**：任务、依赖、状态与计划版本；
4. **Active Agents**：执行者、Run、预算、租约与当前动作；
5. **Task Detail**：目标、验收条件、约束、证据、Artifact、阻塞和历史 Attempt；
6. **Timeline / Decision**：命令、状态变化、工具结果、验证、恢复和人工决策。

这些是一个统一控制台内的面板/模式，共享同一 Read Model，不是六套独立状态。

### 4.6 恢复与交接

Context 耗尽、Run 结束、Worker 崩溃或改由其他 Agent 执行时，新执行者通过有界、可追溯的
`HandoffPacket` 获取任务前沿；原始事实仍保留，可按引用回查。

## 5. 权威术语

| 对象                          | 含义                                                                           | 生命周期所有者             |
| ----------------------------- | ------------------------------------------------------------------------------ | -------------------------- |
| `Project`                     | 长期业务/工程目标、策略和隔离边界                                              | Platform                   |
| `Workspace`                   | 可执行环境；代码仓库、branch/worktree、文件系统与环境配置的组合                | Platform                   |
| `WorkspaceSnapshot`           | 某 Workspace 在一次安全边界上的可恢复 revision 与 Artifact 清单                | Data Plane                 |
| `Goal`                        | 用户希望最终达成的结果                                                         | Platform                   |
| `PlanRevision`                | 一版可审计的任务图方案                                                         | Planner 提议，Control 接受 |
| `ArchitectureBaseline`        | 当前已接受的 Module、Interface、Seam、允许依赖与不变量；每个 revision 不可变   | Project                    |
| `CodeGraphSnapshot`           | AST、符号与依赖分析得到的实际代码结构快照                                      | Evidence Builder           |
| `ArchitectureDelta`           | 指定 baseline 与 CodeGraphSnapshot 之间纯机械、不可变的结构差异                | Evidence Builder           |
| `ArchitectureFinding`         | Policy/Reviewer 对结构 Delta 或运行时/语义 Evidence 的分类、风险、置信度和建议 | Architecture Reconciler    |
| `ArchitectureChangeProposal`  | 带候选 baseline ref/patch digest 的期望架构变更提案，不是已接受事实            | Architecture Reconciler    |
| `Decision`                    | 记录 subject、outcome、选项、authorized target、actor、理由和 authority        | Policy/Human + Control     |
| `BaselineActivation`          | accepted Decision + CAS 推进默认 ref；genesis 从空 ref 启动且不要求迁移 Gate   | Controller                 |
| `PolicyActivation`            | 匹配 kind/target/from ref 的 human accepted Decision + CAS；支持空 ref genesis | Controller                 |
| `ArchitectureDeviation`       | 经 Decision 授权、有适用范围、责任人和期限的临时偏离                           | Controller                 |
| `ArchitectureEvolutionPolicy` | 自动修复 allowlist、等价 proposal、升级和漂移预算的不可变版本策略              | Project + guarded Decision |
| `ArchitectureDecisionBrief`   | 帮助人恢复决策上下文的 Read Model/Artifact，不是状态真相源                     | Read Model                 |
| `Stage`                       | Task 的交付成熟度维度，不是 lifecycle phase，也不会隐式产生执行门禁            | PlanRevision               |
| `Task`                        | 带模块范围、阶段、真依赖、义务级别和完成契约的工作单元                         | Control Plane              |
| `AcceptanceObligation`        | 当前 PlanRevision 中必须满足的结果或不变量；不等同于专属测试                   | PlanRevision               |
| `Gate`                        | `taskKind=gate` 的特殊 Task；scope 决定 Module/Stage/Goal 汇合门禁             | Control Plane              |
| `CompletionPolicy`            | 将任务类型、风险和证据要求解析成 VerificationPlan 的版本化策略                 | Project/Goal + Control     |
| `TaskAttempt`                 | 某 Task 在指定 WorkspaceSnapshot 上的一次领取和执行尝试                        | Scheduler/Control          |
| `AgentInstance`               | 能力 Profile 与长期身份的逻辑执行者                                            | Platform                   |
| `AgentRun`                    | 一次实际 Worker 或 QueryJob 执行                                               | Runtime Adapter + Control  |
| `QueryJob`                    | 不改变源 Task 的短期只读语义咨询                                               | Interaction + Control      |
| `ContextWindow`               | 某次模型调用链的有界工作集                                                     | Worker Runtime             |
| `Evidence`                    | 绑定 revision 和覆盖范围的静态、动态、语义、人工或实时观测                     | Data Plane                 |
| `Artifact`                    | patch、报告、日志、截图等大内容                                                | Data Plane                 |
| `HandoffPacket`               | 跨 Context/Run/Agent 的有界、持久化状态交接                                    | Context/Handoff Service    |
| `TodoView`                    | Task Graph 与 Task State 的展示投影                                            | Read Model                 |

必须始终满足：

```text
Platform > Project
Project > Workspace > WorkspaceSnapshot
Project > Goal > Task > TaskAttempt > AgentRun > ContextWindow
```

每个 `AgentRun` 只能由一个 `TaskAttempt` 或 `QueryJob` 拥有。MVP 中一个 Goal 只作用于一个
Workspace，TaskAttempt 绑定一个 WorkspaceSnapshot；未来若支持跨 Workspace Goal，必须引入显式边界协议，
不能靠共享 transcript 或隐式文件访问实现。

`Session` 是执行记录容器，不等于其中任何一个业务对象。

## 6. MVP 范围

### 6.1 MVP 必须包含

- 单用户、单机控制面，可登记、切换、冻结和恢复多个隔离的 Project/Workspace；
- 一个长期 Human Interaction Layer：主对话、全局仪表盘、主动提醒、讨论与控制入口；
- 持久化 Project、Workspace、WorkspaceSnapshot、Goal、Task、TaskEdge、PlanRevision 和 DomainEvent；
- 机械 Task 状态机、依赖门禁、revision 与幂等命令；
- 从同一状态投影出的 Portfolio、Workspace、Plan Graph、Todo、Task Detail、Active Agents 和 Timeline；
- 机械 query、显式只读 QueryJob、pause、resume、cancel、steer 和 approve/reject；
- 一个现有 `coding-agent` 适配器；
- 证明 Worker A 在 Run/Context 结束后可由 Worker B 仅靠持久状态和有界 Handoff 接续；
- 两个只读 Worker 的真实并发、Evidence 汇总和唯一 Writer，作为 MVP 发布门禁；
- 有界、带来源的 Handoff；
- 任务提交、验证、失败返工和最终完成门禁；
- ArchitectureBaseline 与增量 CodeGraphSnapshot 的持续对账，并将 raw ArchitectureDelta 解释为 ArchitectureFinding；
- 一个命中确定性 allowlist 的局部漂移经正常 Controller/Scheduler/Writer 链进入 RemediationTask，一个重大/含糊变化进入 ArchitectureDecisionBrief；
- 崩溃后恢复，不把未知执行结果猜成成功或失败。

### 6.2 MVP 可采用的简化

- SQLite 单库，不先引入图数据库或消息队列；
- 单进程 Reconciler/Scheduler，不做分布式共识；
- 每个 Goal 首版只绑定一个 Workspace，跨 Workspace 的 Task dependency 和 Artifact 注入不进入 MVP；
- 同一组 Task 以 `moduleScope + stage` 形成二维投影；TaskHierarchy 保存 `parent_of`，ExecutionDAG 只保存带版本化输出要求的 `depends_on`；
- 不做并行写入，同一 Workspace/checkout 只有一个 Writer；
- 先使用结构化/关键词检索，不先上向量数据库；
- Planner 只生成受限 schema，不实现通用工作流 DSL；
- 领域模型保持中立，但首个 Runtime、工具和验收场景只面向 coding；
- UI 先服务状态理解与控制，不做完整 IDE。

### 6.3 明确非目标

- 不把 `coding-agent` 内部 Runtime 重写进 Platform；
- 不让 Planner 或 Human Interaction Layer 直接修改数据库状态；
- 不允许 Worker 或 Reviewer 自己把 Task 写成 `SATISFIED`；
- 不让多个写 Agent 并发修改同一 checkout；
- 不支持 Agent 间自由点对点聊天，也不支持跨 Project/Workspace 的 Agent 消息、Task 依赖或隐式 Artifact 注入；
- 同一 Goal/Workspace 内的 Evidence、Artifact 与 Handoff 只能通过 Platform 持久化和审计后传递；
- 不实现无限层级的自主 spawn；
- 不实现跨机器分布式调度、HA 或多租户权限系统；
- 不以完整 transcript 共享代替 Handoff；
- 不把 Memory、RAG 或知识图谱做成万能状态容器；
- 不展示或持久化模型隐藏思维链；
- 不因目标架构完整而一次生成全部目录和抽象。

## 7. 二维任务图与证据驱动完成

同一组 Task 同时按模块空间和交付成熟度投影；Stage 本身不产生依赖。GateTask 总是参与相应范围的完成归约，但只有下游 Task 在 ExecutionDAG 中显式 `depends_on` 它时才阻塞调度。ModuleProgress、StageProgress 与 Goal phase 均由当前 `PlanRevision` 的 Task、GateTask、Evidence 和 revision 重建。

Module 回答空间上“有哪些责任边界”，Stage 回答计划上“交付成熟到哪一层”，ExecutionDAG 回答“真实前置条件是什么”，Task phase 才回答“现在处于哪个生命周期状态”。四者不得互相代替。

Worker 只能提交 `CompletionClaim`。默认 coding-first 验证链为：

```text
增量 AST / CodeGraph / 架构边界检查
  → 复用已有 build、affected tests、contract/smoke/integration 证据
  → 普通语义变更组装紧凑 ReviewPacket；无语义变化任务可按策略快放
  → Controller 按 CompletionPolicy 归约
```

测试属于功能、模块、Interface 或集成边界，不要求每个 Task 新写专属测试。能形式化的业务规则应在项目初始化以及后续 Decision/复盘中持续进入测试、契约或架构规则；全量测试在 IntegrationTask、StageGate 或 GoalGate 运行。

`AUTO/REVIEW/HUMAN/EXTERNAL` 不再是每条 criterion 的强制标签。Project/Goal 持有可继承的 `CompletionPolicy`，系统依据 task scope、diff、风险和 Stage 编译 `VerificationPlan`。Worker 只接收当前任务的完成契约；Reviewer 只接收架构切片、变更摘要、静态/动态证据、Worker 主张和按需 Artifact 引用。

普通实现和验收默认由系统闭环。系统持续检查耦合、性能、逻辑、权限和抽象质量：结构变化先产生 raw ArchitectureDelta，再解释为 ArchitectureFinding；没有结构 Delta 的性能、逻辑、权限或第三方问题也可由运行时/语义 Evidence 直接形成 Finding。只有确定性 allowlist 内的局部可逆漂移才可经正常控制链转成 RemediationTask；可能代表合理架构演进的变化形成 ArchitectureChangeProposal。仅当规范性变化未被当前 Baseline、Goal/Plan 或已有 Decision 预授权，且涉及 Module/Interface/Seam、公共 schema、依赖方向、信任边界、重要性能预算或业务行为时，才需要人类裁决。

人类还处理审美、真实用户反馈、未编码的重要 trade-off 与高风险授权。Secretary 必须以 ArchitectureDecisionBrief 带上原始架构理由、历史 Decision、当前差异、影响范围、方案和延后后果，帮助人恢复决策上下文。容器、staging、健康检查和第三方 probe 默认仍由系统取证；External 是证据来源，不是裁决主体。

`Task SATISFIED` 要求当前 VerificationPlan 为精确 task/workspace/baseline/policy revision 解析出的 EffectiveEvidenceSet 覆盖所有 required evidence，且其中没有 FAIL 或 INCONCLUSIVE。历史 FAIL/STALE 仍可审计，但不永久进入当前 guard；STALE 是相对当前 plan 的派生 applicability。ModuleProgress/StageProgress 是派生视图；`Goal COMPLETED` 要求当前 revision 的所有 required executable work Task、required obligations 与 required Module/Stage/Goal GateTask 全部满足，且没有未对账的高风险副作用。required 的 blocked/deferred/cancelled 都不等于完成；若义务不再需要，必须创建新 revision。

详见[任务图与完成判定](../design/任务图与完成判定.md)。

## 8. MVP 成功标准

### 8.1 真相源一致性

- UI 不接受直接状态写入；所有视图来自同一 Task/Event 数据；
- 进程重启、Context 切换和 Agent Handoff 后，requirementLevel/disposition/phase、完成契约和 Evidence 不丢失；
- 让 Worker 全程不调用 `update_plan`，Task/Todo 仍按事实正确推进。

### 8.2 状态与并发

- 依赖未完成时启动 Task 被确定性拒绝；同 Stage、不同模块且无真依赖的 Task 可以并行；
- 两个 Worker 竞争同一独占 Task 时最多一个 claim 成功；
- 重复、乱序或过期命令不会重复完成或回退状态；
- 当前 revision 的 required executable work Task、required obligations 与 GateTask 未全部满足前，Goal 不得显示 completed；删除义务必须先创建新 revision。
- active PlanRevision、required obligation 及其 required verification requirements 均不得为空；无需改动时也以带 Evidence 的 AlreadySatisfied GoalGateTask 表达。

### 8.3 完成真实性

- 每个 `SATISFIED` 可追溯到 CompletionPolicy、Evidence、verification event 和执行者；
- 测试或静态检查失败不能因 Worker/Reviewer 自称完成而变绿；
- ModuleProgress、StageProgress 与 Goal phase 可由 Task、GateTask、Evidence 和 revision 重建；
- BaselineActivation 只更新新 Plan 的默认 baseline，不会改写既有 Plan 或让其 Evidence 失效；只有显式 PlanRebase/新 PlanRevision 才重新计算受影响 EvidenceBinding 的 applicability，并触发局部复验。旧 FAIL 始终保留；
- 多个 Plan/Baseline revision 后，平台仍能回答当前架构、为何如此、未解决漂移和上次复盘结果。
- PlanPatch 不删除既有完成事实或 Evidence，历史 revision 可审计。

### 8.4 产品价值

在一个真实中大型代码任务中，与单一长会话基线相比：

- 用户能从一个入口查询并控制多个 Project/Workspace 的后台工作；
- Worker A 的 Run/Context 结束后，Worker B 可仅依靠持久状态和有界 Handoff 接续；
- 两个只读子任务可真实并行并返回可汇总、可追溯的 Evidence/Handoff；
- 最终只有一个 Writer 修改目标 checkout，并在 IntegrationTask/GoalGate 运行全量测试；
- 任务成功率不下降，状态查询准确率达到 100%；
- 重复探索、人工追问次数、等待时间和总 Token 有完整度量；
- 任一失败都能解释是计划、执行、验证、权限、预算还是恢复问题。

MVP 先优化状态真实性、人的可控性、长期连续性、任务拆分质量和有效推进速度；Context、Token、缓存命中从首版
开始度量，并行吞吐后置。P0 不固化“窗口使用到某个百分比就退化”等经验值，也不预先承诺 Token 或耗时提升，
阈值应由基线实验决定。

拆分质量同时衡量 active Context 健康度与调度/Handoff/验证/合并开销；任务不是越细越好。
