## 1. 阶段定位

P0 是新产品 `Agent Platform` 的设计冻结阶段，不是 `coding-agent` 的 M7，也不是实现 Sprint。本文 YAML 的 `status: current` 只表示 P0 阶段计划正在生效；产品定义、总体架构和任务图仍是待确认的 `draft`，不表示设计已经获批或实现。

本阶段的一句话目标：

> 先把“用户面对什么、谁拥有状态、各层如何闭环、MVP 必须证明什么”裁决清楚，再写关键流程伪代码，最后从目标架构切出最小可验证产品。

本阶段遵循：

```text
研究收敛
  → Target Architecture v0.3
  → 用户裁决产品语义
  → 关键流程伪代码
  → MVP Architecture 与路线图
  → Implementation Readiness Review
```

不能把其中某个技术 spike（例如跨 Run continuity）直接称为产品 MVP；它只能在完整设计中作为风险验证切片排序。

## 2. 前置事实

1. `coding-agent` 的 M0—M6 已形成可运行的单 Agent 执行内核；它仍有真实 Provider baseline、长任务性能和大型仓库能力需要继续验证。
2. 原 M7 同时包含 Context/Artifact/Compaction 等内核数据面能力，以及 Inbox/Scheduler/多 Agent/合并等平台能力，产品边界混杂。
3. Todo 不更新的根因不是提示词不足，而是 Todo 不是 Runtime/Control Plane 的状态真相源。
4. 验证权责已经裁决；Task/Goal 汇总形成 v0.3 收敛方案、仍待最终确认。精确 schema、归约伪代码、Command/Query 契约和 RuntimePort 尚未冻结。
5. 因此 P0 期间不得把任何目标架构图描述成已实现能力。

## 3. 本阶段范围

### 3.1 必须完成

- 确认 Agent Platform 是独立产品层；
- 确认 `coding-agent` 是 Execution Kernel，而非平台控制器；
- 冻结统一术语和层级边界；
- 冻结 Task/Plan/Todo/State 的真相源与写权限；
- 画出 Target Architecture 与 MVP Architecture；
- 定义 Project、Workspace、Goal、Task、Attempt、Agent、Run、QueryJob、Context、Evidence、Handoff 的生命周期；
- 定义 command path、机械/语义 query path、reconcile path 和 verify path；
- 由用户裁决会改变产品含义的分歧；
- 裁决后编写关键流程伪代码；
- 从总体设计切出一个可证伪的产品 MVP；
- 给出实现顺序、阶段门禁和首个真实场景。

### 3.2 明确不做

- 不创建 Agent Platform 代码仓库或完整目录骨架；
- 不实现 Task Store、Scheduler、Planner、Human Interaction Layer 或 Web UI；
- 不修改 `coding-agent` Runtime 行为；
- 不先做数据库 schema、消息队列、图数据库或向量库选型；
- 不将原 M7 的所有条目换个编号后整体搬入新产品；
- 不提前写大量接口、ADR、测试计划或兼容层；
- 不把对话记录当长期真相源。

### 3.3 不改动范围

- `coding-agent` M0—M6 的完成定义；
- 现有 Runtime、Tool、Permission、Approval、Sandbox、Session 和 Checkpoint 实现；
- 用户尚未提交的 M7 数据面/压缩预研；
- 参考项目源码和历史学习资料。

并给出以下端到端时序：

1. 用户创建新 Goal；
2. 用户查询机械状态，或通过不打断源 Worker 的 QueryJob 进行语义咨询；
3. 用户修改正在执行的目标，受影响范围先静默和保存，经影响分析/确认后再激活新 revision；
4. Context 即将耗尽并 rollover；
5. Worker 崩溃后由新 Worker 接续；
6. 同 Stage 的两个只读 Worker 在不同模块/调查方向并行，并返回可追溯的冲突结论；
7. CompletionClaim 经过静态结构、适用动态检查和语义变更 Reviewer，随后归约 Task/Goal 并投影 Module/Stage progress；
8. IntegrationTask/GoalGateTask 运行全量测试，真正主观或高风险事项升级给用户；
9. raw ArchitectureDelta 先形成 Finding，运行时/语义 Evidence 也可直接触发非结构性 Finding；allowlisted drift 经 Controller/PlanPatch/Scheduler/Writer 链形成 RemediationTask；重大或含糊变化带历史理由和选项升级，migration Plan 通过后才以 CAS 更新新 Plan 的默认 Baseline。既有 Plan 只有经显式 PlanRebase/新 PlanRevision 才迁移，并只复验受影响子图；
10. 用户暂停、继续或取消整个 Goal。

完成条件：若任何一步无法唯一回答“谁读取什么、谁能写什么、写入哪类事实、失败后处于什么状态”，则返回 P0-02/P0-03 修订，而不是用模糊 Service 名称掩盖。

### P0-05 MVP 切分与风险验证

根据伪代码把目标架构分成：

- MVP 必需；
- 第一个技术 spike；
- MVP 后优化；
- 明确不做。

暂定 MVP 形态：

```text
单用户、单机控制面，可登记/切换/冻结多个隔离 Project/Workspace
一个长期 Human Interaction Layer：主对话 + 全局仪表盘 + 主动提醒 + Advisory
持久化 Project / WorkspaceSnapshot / Goal / PlanRevision / Task / Evidence / Event
ArchitectureBaseline / CodeGraphSnapshot / ArchitectureDelta / ArchitectureFinding
Decision / BaselineActivation / PolicyActivation / ArchitectureDeviation
TaskHierarchy / ExecutionDAG / PlanMatrix
ArchitectureEvolutionPolicy + Architecture Reconciler + RemediationTask / ArchitectureDecisionBrief
机械 Task Reconciler + 简单 Scheduler + CompletionPolicy
一个 coding-agent Adapter
Worker A → B 换手恢复
两个并行只读 Worker + Evidence 汇总 + 唯一 Writer
静态结构检查 + 复用动态证据 + 语义变更 Reviewer + Integration/Goal Gate
结构化 Handoff
Portfolio / Workspace / Plan Graph / Task Detail / Active Agents / Timeline
机械 query / 只读 QueryJob / pause / resume / cancel / steer / approve
```

候选首个技术 spike：

> 同一 Task 在旧 Run/Context 结束后，仅依靠持久 Task State 与有界 Handoff，由新 Run 继续并通过验收。

它只验证“状态能否跨执行实例连续”，不代表整个产品 MVP 已完成。

完成条件：

- 每个 MVP 能力都能追溯到一条产品假设或验收场景；
- 每个被延期能力都有明确理由；
- spike 有可失败的对照基线和停止条件。

### P0-06 Implementation Readiness Review

检查：

- 产品定义、架构、伪代码和路线图术语一致；
- 首个 vertical slice 不要求先实现全图；
- 状态机、revision、idempotency、Evidence 与 stale result 已覆盖；
- Command/Query 与 RuntimePort 边界可测试；
- 首个真实场景和 evaluator 能区分成功、失败与未知；
- 不存在“靠 prompt 保证”的关键不变量；
- Worker/Reviewer 不能通过修改 Baseline 为同一 CompletionClaim 自证；
- CompletionPolicy 与 ArchitectureBaseline 不形成反向版本引用环；
- Decision 必须记录 subject、outcome 与 authorized target；advance BaselineActivation 以 matching accepted Decision、当前 from ref、migration Gate 和 expected Project revision 做 CAS 激活；
- genesis Activation 只在 active ref 为空时成立，须 human accepted setup Decision + CAS；Baseline genesis 不要求 migration Gate；
- BaselineActivation 只更新新 Plan 的默认值；既有 Plan 只有经显式 PlanRebase/新 PlanRevision 才重算 EvidenceBinding applicability，且不抹除历史失败；
- PolicyActivation 必须匹配 Decision 的 policy kind、authorized target 与当前 from ref；MVP 只能由 human accepted Decision + CAS 激活，不能由旧 Policy 自我替代；
- Goal reducer 统计所有 required executable Task；TaskHierarchy 的 parent/leaf 身份不改变完成义务；
- active Plan、required obligation 与 required verification requirements 有非空 guard；no-change 由带 Evidence 的 AlreadySatisfied GoalGateTask 表达；
- Goal reducer 是全函数，GateTask 和 EffectiveEvidenceSet 有确定性语义；
- 没有提前创建无消费者的抽象。

通过后才能创建正式代码仓库和首个实施计划。

## 5. P0 完成定义

- 产品边界经用户明确接受；
- 产品定义和总体架构状态为 `current`；
- 关键流程伪代码覆盖主路径与关键失败路径；
- MVP 路线图包含目标、非目标、依赖、验收和停止条件；
- 原 M7 的平台能力已经迁移，新旧文档不存在双重 current；
- `coding-agent` 与 Platform 只有一个窄执行协议边界；
- Todo/Graph/UI 可以完全从同一 Task State 投影；
- 至少选定一个真实中大型代码任务作为产品验收场景；
- 用户可以指出哪些设计已接受、哪些仍是假设。

P0 不以“代码可运行”验收，因为本阶段明确不写产品实现。

## 6. P0 之后的候选开发顺序

以下仅用于验证架构是否可分步施工，不是 P0 期间的实施授权；编号将在 P0-05 后正式冻结。

| 候选阶段                | 结果                                                                               | 关键门禁                                  |
| ----------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------- |
| P1 Data Plane           | Project/Workspace、Event、Goal/Task、不可变 Baseline/Policy revision               | 无 LLM 时可重放得到一致状态               |
| P2 Plan & Structure     | TaskHierarchy、ExecutionDAG、PlanMatrix、CodeGraphSnapshot、raw Delta              | 层级、真依赖与 raw delta 可确定性重建     |
| P3 Control Plane        | Task Reconciler；Architecture Reconciler 只做机械 Finding/report，接 Fake Worker   | 不靠模型推进状态机；尚不自动修复          |
| P4 Runtime Integration  | RuntimePort + CodingAgentAdapter                                                   | 单 Task dispatch/cancel/event/result 闭环 |
| P5 Handoff & Continuity | Context Task View + Handoff + 新 Run 接续                                          | 不回放全 transcript 仍保留约束与前沿      |
| P6 Planner              | Goal → PlanProposal/PlanPatch                                                      | Planner 无法绕过 Control 直接改状态       |
| P7 Multi-Agent Slice    | 两个只读 Worker → EffectiveEvidenceSet/Reviewer → 唯一 Writer                      | 冲突、超时、取消和来源可追溯              |
| P8 Human + Architecture | Query/Command、ArchitectureDecisionBrief、Remediation/迁移 Plan、Baseline CAS 激活 | 自动修复与人工裁决都走唯一写路径          |
| P9 Control UI           | 全局仪表盘与六个稳定面板                                                           | UI 刷新/重启不产生状态漂移                |
| P10 Harness & Hardening | 评测后的 ArchitectureReviewProfile、漂移预算校准、周期性 cleanup                   | 多 revision 长期运行仍能发现并解释漂移    |

## 7. 真实验收场景要求

P0-05 必须选择一个不是玩具的仓库任务。场景至少包含：

- 模糊症状到可验证任务图；
- 至少两个已登记 Workspace，并明确本 Goal 绑定的目标 Workspace；
- 包含同一 Stage 中两个可并行的只读模块或调查方向；
- 一个唯一写入修复；
- 至少一次用户纠偏或暂停/继续；
- 至少一次不打断源 Worker 的语义 QueryJob；
- 至少一次 Context/Run 切换；
- Task 级静态/受影响检查与 Integration/Goal 级全量测试；
- 至少一个真正主观或高风险事项正确升级给用户；
- 一次 allowlisted 局部架构漂移经正常控制链自动修复，以及一次重大/含糊架构演进由 ArchitectureDecisionBrief 帮助用户裁决；
- 至少跨两个 Baseline/Plan revision，且旧失败事实仍可追溯、旧 Plan 仍解析到其固定 baseline；
- 迟到结果或验证失败之一；
- 完整的状态、Evidence、Artifact、Handoff 和 Timeline。

比较基线：

1. 当前单一长会话 `coding-agent`；
2. Platform MVP；
3. 必要时增加“全历史回放”作为 Context 成本对照。

记录任务成功率、状态查询准确率、用户介入次数、总时间、Token、工具调用、重复探索、
Handoff 采用率和恢复结果。P0 只定义协议，不伪造性能收益。
