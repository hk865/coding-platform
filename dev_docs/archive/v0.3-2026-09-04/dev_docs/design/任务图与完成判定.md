## 1. 本文裁决什么

本文把原 P0-03 的“Task 如何汇总为 Goal”和“Reviewer/用户如何裁决”合并为一个问题：

> 同一组 Task 如何在模块空间与执行时间上组织，并由低成本、可追溯的证据证明完成。

核心规则是：

> Task Graph 不是线性 Todo。系统保存结构、执行与证据三类事实；静态分析、适用的动态检查和普通语义变更的目标化 Agent 审查产生 Evidence，Controller 按当前版本化 CompletionPolicy 唯一推进状态。

Worker 的完成报告只是 CompletionClaim，不是完成事实。Reviewer 的 verdict 是一种 Evidence，也不能直接写 Task State。

## 2. 为什么既不能只跑测试，也不能只让 Agent 审计

只跑测试的问题是：

- 测试只能覆盖已经表达为断言的行为；
- 小 Task 与测试不是一一对应，一个测试常覆盖多个 Task；
- 为每个 Task 新写专属测试，会放大开发与维护成本；
- 模块边界、依赖方向、API 形状和未编码语义需要其他证据。

只让 Agent 审计的问题是：

- 结论容易受 Worker 自报和上下文遗漏影响；
- 同一输入可能得到不一致判断；
- 无法替代编译、类型、测试和真实运行结果；
- Reviewer 容易成为串行瓶颈。

因此 coding-first 的默认路径是：

```text
静态结构证据
  + 复用的测试/运行时证据
  + 普通语义变更的目标化 Reviewer 审查
  → Controller 确定性归约
```

全量测试仍然是阶段或 Goal 的重要门禁。项目初始化时应尽可能把已确定的业务规则编码成测试、契约或架构规则；不要求每个执行 Task 都重新发明一套测试。
这些规则还要在后续 Decision、集成复盘和架构复盘中持续维护，而不是只初始化一次。

## 3. 内部不是一张二维表，而是四个关联模型

用户看到的“模块 × 阶段”二维图是 Read Model。存储层不把不同关系压进一种边：

```text
ArchitectureBaseline   设计中的模块、接口、允许依赖与不变量
CodeGraphSnapshot      AST、符号、导入和调用分析得到的实际结构
ExecutionDAG           当前 PlanRevision 的真实执行依赖
EvidenceGraph          Evidence 覆盖哪些 Task、契约、Gate 和 revision

                     ↓ projection

PlanMatrix             Module × Stage 的进度和并行前沿
```

四者职责不同：

- ArchitectureBaseline 回答“系统应该是什么结构”；
- CodeGraphSnapshot 回答“当前代码实际是什么结构”；
- ExecutionDAG 回答“哪些工作必须先发生，哪些可以并行”；
- EvidenceGraph 回答“完成结论由哪些事实支持”。

这里的“空间 × 时间”必须再拆成四个正交概念：

```text
Module          空间责任边界：谁拥有哪组职责与 Interface
Stage           计划中的交付成熟度：contract / implementation / integration
ExecutionDAG    真实前置条件：哪些输出不到位就不能安全推进
Task.phase      当前运行状态：pending / running / verifying / blocked / satisfied
```

所以 `Module × Stage` 只是计划坐标，不是执行顺序，也不是完整生命周期。两个不同 Module 的
implementation Task 可以并行；同一 Stage 也可以同时出现一个 `running` Task 和一个 `verifying` Task。

ArchitectureBaseline 是一族长期、版本化工件：每个 revision 不可变；Project 的 active baseline 只能通过带 CAS guard 的 BaselineActivation 前进，并消费匹配授权目标的 accepted `Decision(subjectType=architecture_baseline, actor=policy|human)` 与已满足的 migration GateTask。它只改变新 Plan 的默认 baseline；ExecutionDAG 随 PlanRevision 变化，PlanMatrix 可从同一组 Task 重建，不形成第二真相源。

## 4. Module、Stage 与 Task

### 4.1 Module

Module 是可独立理解的工程边界，至少声明：

- path、package 或 symbol selector；
- 对外接口与所需接口；
- 允许的依赖方向；
- 适用的架构不变量；
- 默认 CompletionPolicy 引用。

跨模块工作应建为 BoundaryTask 或 IntegrationTask，不能任意归到其中一个模块。

### 4.2 Stage

Stage 表示计划中的交付成熟度，例如 contract、implementation、integration；它不表示墙钟时间或 Task 的当前 lifecycle phase。

Stage 是分组与汇总维度，不自动产生全局依赖。不同 Stage 的 Task 只要真实输入已经满足，也可以并行。只有显式 StageGate 才形成阶段 barrier。

### 4.3 Task

Task 是最小可调度、可交付、可独立归约的工作单元。建议最小字段：

```text
taskId, goalId, planRevision,
taskKind: work | gate,
scopeKind: module | boundary | stage | goal,
moduleScopeRefs[], stageId,
objective, outputContracts[],
requirementLevel: required | optional,
disposition: active | deferred | cancelled | superseded,
phase: pending | ready | running | verifying | blocked | satisfied | failed,
completionPolicyRef, verificationOverride?,
readSet[], writeSet[], conflictScope[],
activeAttemptId?, revision
```

requirementLevel、disposition 与 phase 是正交维度，不能塞进一个状态枚举。当前 PlanRevision 中每个 Task 都必须属于一个 Stage；BoundaryTask、IntegrationTask 和 GateTask 也分别落入 contract、integration 或 release 等 Stage。

Gate 首版建模为 `taskKind=gate` 的特殊 Task，而不是只存在于文档里的布尔值。它同样拥有 phase、AcceptanceObligation、Evidence 与依赖边；`scopeKind` 决定它是 ModuleGate、StageGate 还是 GoalGate。StageGate 只阻塞显式依赖该 GateTask 输出的下游 Task，不会按 Stage 编号自动封锁整个后续阶段。

## 5. 只为真实依赖建边

`parent_of` 只属于 TaskHierarchy，表达工作分解，不参与 readiness、环检测或依赖满足判定。MVP 没有纯展示用 `group` Task：父 work Task 仍是 executable Task，必须自行满足完成契约；`parent_of` 不会把它从 Goal reducer 中排除。ExecutionDAG 只包含带版本化输入/输出要求的 `depends_on`；即使首版在同一 TaskEdge 表保存二者，读取模型和 reducer 也必须分开。

只有满足下面条件才建立硬边 A → B：

> 没有 A 产生的某个可标识、可版本化输出时，B 无法安全开始，或者开始后无法有效验收。

依赖必须指向所需输出，而不只是“B 排在 A 后面”：

```text
A.outputs  = InterfaceSchema@v3
B.requires = InterfaceSchema@v3
```

推荐依赖类型：

- CONTRACT：需要已冻结的接口或协议；
- ARTIFACT：需要上游生成物；
- DECISION：需要已提交的业务或架构决定；
- ENVIRONMENT：需要特定 WorkspaceSnapshot 或环境；
- GATE：需要集成、阶段或发布门禁。

同属一个 Stage、位于相邻模块、可能写冲突、希望一起 Review，都不是业务依赖。写冲突由 conflictScope 与 lease 控制。

若两个模块都依赖一个共同接口，应先创建 ContractTask，再让两个实现 Task 并行：

```text
             ┌─→ Module A Task
ContractTask ┤
             └─→ Module B Task
```

每个 PlanRevision 的硬依赖图必须是 DAG。出现环时，应抽出共同契约、增加显式 Gate，或合并成不可分割的复合 Task。

## 6. CompletionPolicy，而不是每条 criterion 的四类标签

不再要求每条验收条件重复声明 AUTO、REVIEW、HUMAN、EXTERNAL。这个分类混合了验证方法、证据来源和裁决主体，也会污染 Agent Context。

Project 或 Goal 激活一份版本化的 CompletionPolicy，Task 默认继承，只在例外时 override：

```text
ProjectContract
  contractRevision
  requirementRefs[]
  architectureBaselineRef
  completionPolicyRef
  humanOracleRefs[]        # 通常为空

Task
  taskRevision
  contractSliceRefs[]
  scopeRefs[]
  verificationOverride?   # 只有例外才出现
```

Verification Orchestrator 根据以下输入编译本次 VerificationPlan：

- 当前 Task contract slice；
- 相关 ArchitectureBaseline slice；
- Task/Plan 绑定的 architectureBaselineRevision；
- 变更 diff 与 CodeGraph delta；
- Task 类型、Stage、影响面和风险；
- 已有测试、Gate 与运行环境能力。

Worker 只看到本 Task 的 CompletionContract 和立即可执行检查，不读取全项目验证策略。Reviewer 和 UI 也各自使用不同投影。

## 7. 完成判定流水线

```text
Worker CompletionClaim
        │
        ▼
Evidence Builder
├─ diff / changed symbols / raw CodeGraph delta
├─ 模块、接口、依赖和架构规则
├─ build / lint / typecheck
├─ affected tests / contract / smoke / integration tests
├─ 必要运行时 trace、容器、staging 或外部 probe
└─ Worker 声明的改动、缺口和风险
        │
        ▼
Verification Orchestrator
├─ 明确失败 ─────────────────────────→ REJECT
├─ 已证明无语义变化且策略允许快路径 ─→ PASS
├─ 普通代码语义变更 ─────────────────→ Reviewer
└─ 契约变化、主观 oracle 或授权 ─────→ Human Decision
        │
        ▼
Controller / Reducer 唯一写入 Task State
```

### 7.1 静态层

静态层优先做低成本、增量式检查：

- 编译、类型、lint 与 schema；
- AST、symbol、import/call graph delta；
- 模块边界与允许依赖；
- API/接口形状和变更范围；
- 生成物、文件和 Artifact 完整性。

AST/code graph 能快速证明“结构是否符合预期”，但不能单独证明运行时业务行为。

### 7.2 动态层

动态证据复用工程已有能力，不与 Task 一一绑定：

- 开发时优先运行 affected tests、contract tests 和 smoke；
- 模块 join 或 StageGate 运行 integration tests；
- GoalGate 对可测试功能运行全量测试；
- 容器、沙箱、record/replay、staging 和 probe 尽量把环境及第三方行为变成自动证据。

Docker 和沙箱解决可复现性与隔离，但不能凭空证明未被模拟的真实第三方状态。真实 API、部署健康和遥测仍可由系统自动采集为 live evidence；只有凭证、费用、不可逆动作或业务风险需要人授权。

### 7.3 语义层

普通代码语义变更在静态与动态检查后进入独立 Reviewer；只有已经机械证明无语义变化且 CompletionPolicy 明确允许的任务才走快路径。Reviewer 不重复完整开发过程，也不重新读取全部仓库，其审查单位优先是模块变更集或集成边界，而不是每个微型 Task。

## 8. Reviewer 的最小 Context

ReviewPacket 初始只包含：

```text
taskContractSlice
relevantArchitectureSlice
changeManifest
codeGraphDeltaSummary
gateSummary
workerClaimAndKnownGaps
focusQuestions
lazyArtifactRefs
workspaceRevision
architectureBaselineRevision
completionPolicyRevision
architectureEvolutionPolicyRevision
```

Worker 报告用于定位“它声称做了什么、知道哪些风险”，属于待验证主张，不是独立完成证据。检查要点主要来自契约、架构不变量、diff 影响分析和运行场景，Worker 自报只提供补充线索。

完整 AST、完整 CodeGraph、原始日志、全部历史对话和大段测试输出不进入初始 Context；Reviewer 需要时按引用读取。

## 9. 谁负责什么

| 主体                    | 负责                                                   | 无权                                 |
| ----------------------- | ------------------------------------------------------ | ------------------------------------ |
| Worker                  | 实现、提交 CompletionClaim、改动清单、已知缺口         | 直接标记完成、修改契约               |
| Evidence Builder        | 运行静态/动态检查并保存不可变 observation              | 发明业务要求                         |
| Reviewer Agent          | 根据契约切片和证据审查剩余语义                         | 修改契约、直接写 Task State          |
| Architecture Reconciler | 对照期望架构与实际代码，分类漂移并提出动作             | 静默移动基线以迁就当前实现           |
| Controller              | 根据当前版本化策略与 verdict 机械归约状态              | 猜测语义、覆盖失败事实               |
| Human                   | 裁决重大需求/架构演进，提供主观 oracle，批准风险与例外 | 把已经失败的 observation 改写为 PASS |
| External System         | 提供部署、第三方 API、监控等 observation               | 直接裁决 Task                        |

人类的日常职责不是逐 Task 点绿。如果边界和策略已有 active revision，普通任务应自动完成闭环。平台还要持续复盘，避免长任务中的实现、文档和架构理解逐渐漂移。人主要在以下情况进入控制回路：

- 审美、真实用户反馈等没有机器 oracle 的输入；
- 需要改变 Module 职责、Interface、Seam、依赖方向、权限或重要性能预算；
- 重要但尚未编码的业务 trade-off；
- 高风险、付费或不可逆操作的授权；
- Evidence 冲突且既有策略无法消解。

未来架构变化不是一种“验收模式”，而是新的 Decision + PlanRevision。

## 10. 持续架构对账、复盘与防漂移

架构是否“好”不能只在项目开始时裁决一次。平台保存的不是一张永不变化的图，而是以下对象：

```text
ArchitectureBaseline       当前已接受的期望 Module / Interface / Seam / 不变量
CodeGraphSnapshot          指定 Workspace revision 的实际 AST、符号和依赖结构
ArchitectureDelta          两者之间纯机械、不可变的结构差异
ArchitectureFinding        Policy/Reviewer 对 Delta 或 runtime/semantic Evidence 的分类、风险、置信度和建议
ArchitectureChangeProposal 带 proposed target/digest 的候选 baseline 变化，不是已接受事实
Decision                   subject / outcome / selected option / authorized target / actor / authority
BaselineActivation         advance 消费 matching Decision + Gate + CAS；genesis 消费 human setup Decision + empty-ref CAS
PolicyActivation           消费匹配 policy kind/target/from ref 的 human accepted Decision + CAS；支持 empty-ref genesis
ArchitectureDeviation      经 Decision 授权、有 scope、owner、expiry 的临时例外
```

每次 Task 提交或 merge 做便宜的增量对账；Module/Stage/Goal Gate 做范围复查；重复返工、漂移预算超限、重要 Interface/依赖变化或长周期节点再触发全局 Architecture ReviewJob。结构变化走 raw Delta 路径；性能、逻辑、权限或第三方行为也可由 executable/live/semantic Evidence 直接形成 ArchitectureFinding。循环是：

```text
Workspace change
  → incremental CodeGraphSnapshot
  → compare(Plan/Workspace effective ArchitectureBaseline revision)
  → raw ArchitectureDelta
  → ArchitectureEvolutionPolicy / Reviewer 生成 ArchitectureFinding
     ├─ conformant                         → 记录
     ├─ allowlisted deterministic drift    → RemediationRequested
     ├─ mechanically equivalent metadata   → ArchitectureChangeProposal
     ├─ material architecture evolution   → ArchitectureDecisionBrief → Decision
     └─ ambiguous                         → 报告，不猜修复方向
```

机械检查与 Agent 语义审查互补：

| 关注点 | 机械层优先证明                                | Agent 需要判断                               |
| ------ | --------------------------------------------- | -------------------------------------------- |
| 耦合   | 禁止依赖、环、跨层调用、所有权规则            | 职责泄漏、抽象层级是否失配、概念是否错误捆绑 |
| 性能   | benchmark/SLO、调用次数、复杂度、回归阈值     | 工作负载假设、数据结构和访问模式是否仍合理   |
| 逻辑   | type/schema/contract、可编码不变量、数据流    | 不变量归属、遗漏或重复实现                   |
| 权限   | capability manifest、访问矩阵、taint/approval | 业务必要性和信任边界是否应改变               |

P0 文档暂用 deep-module 词汇描述候选语义审查 rubric：评审 Module 的 depth、leverage 与 locality，以 Interface 为主要测试面，用 deletion test 判断 Module 是否值得存在；新增 Seam 必须对应真实变化点。该 rubric 尚未实现或评测为 ArchitectureReviewProfile。
仓库级 skill 未来可作为版本化 ArchitectureReviewProfile provider 接入，但不是 MVP 依赖。它只提供可审计的 Finding 信号，输出仍须归一化为 Evidence、ArchitectureFinding 或 ArchitectureChangeProposal，不能直接修改 Baseline 或 Task State。

权限边界必须严格分成两条链：

- **修代码符合架构**：Worker/Reviewer 只提交 ArchitectureFinding 或 RemediationSuggested；仅 allowlist 中的确定性规则可触发 RemediationRequested。Controller 决定复用新 Attempt，或通过 PlanPatch 在新 PlanRevision 创建 RemediationTask；Scheduler 再按正常 lease、预算和唯一 Writer 规则派发；
- **改架构符合代码**：只有路径/符号映射、等价重命名等可机械证明语义等价的小更新，经过独立 check 和 accepted `Decision(subjectType=architecture_baseline, actor=policy)` 后，才可原子激活新 revision。只有**未被当前 Baseline、Goal/Plan 或已有 Decision 预授权**的 Module 拆并、Interface/schema、依赖方向、权限、安全、性能预算、跨 Workspace 或业务行为变化，才形成 ArchitectureDecisionBrief 交人裁决。

Worker/Reviewer 不能用修改 Baseline 为同一个 CompletionClaim 自证。Remediation 按 `(architectureBaselineRevision, findingDigest, ruleId)` 去重，同一 Finding 最多一个 active remediation；超过失败阈值必须升级。BaselineActivation 只改变新 Plan 的 Project 默认值，不会追溯性改写既有 Plan 或其 Evidence；只有显式 PlanRebase/新 PlanRevision 才让受影响 EvidenceBinding 相对新 VerificationPlan 派生为 STALE，并暂停、rebase 和复验受影响子图。

ArchitectureDeviation 只能由 Controller 根据授权 Decision 创建或续期，至少绑定 `decisionRef、architectureBaselineRevision、workspace/goal scope、allowedFindingRefs、owner、expiresAt、status`；过期或越界后不再豁免 Gate。

为避免污染 Context，Worker 只得到相关 architecture slice、相对其已知 revision 的 compact delta、有效 Decision 和 open Finding。Secretary 对低风险自动处理只做摘要；真正需要人介入时给出 ArchitectureDecisionBrief：原始理由、当前差异、引入它的 Task/revision、受影响目标、推荐方案、替代方案、延后后果和 Evidence 链接。它是 Read Model/Artifact，承担“恢复人的决策上下文”，不是新的状态真相源。

## 11. Task、Module、Stage 与 Goal 的归约

Controller 先为当前 Task revision 解析有效证据集，历史 Evidence 不会被删除，但也不会永久参与当前 guard：

```text
EffectiveEvidenceSet(taskRevision)
= VerificationPlan 为精确 task / workspace / policy / baseline revision 选择的
  尚未 superseded、applicability != STALE、且覆盖范围仍有效的最新 required Evidence
```

除非 CompletionPolicy 明确要求累计历史，旧 Attempt 的 FAIL/STALE 只保留为审计事实，不阻止后续已通过的新 Attempt。

Task 满足条件：

```text
Task SATISFIED
= 属于当前 PlanRevision
  AND disposition = active
  AND 每个 required verification requirement
      都在 EffectiveEvidenceSet 中至少有一个当前适用的 PASS
  AND 其 scope 内没有按策略阻断的未处置 ArchitectureFinding
  AND EffectiveEvidenceSet 中不存在 FAIL 或 INCONCLUSIVE 的 required verdict
```

失败与阻塞必须区分：

- FAIL 表示实现或验收不满足，Attempt 被拒绝并返工；
- BLOCKED 表示缺少权限、输入、环境或外部条件；
- STALE 表示某个 EvidenceBinding 相对当前 VerificationPlan 已不再适用；Evidence 本身仍不可变；
- deferred/cancelled 不等于完成；
- superseded 不参与当前 revision 汇总。

Module 与 Stage 是领域/计划维度；可重建的是它们的进度投影：

```text
ModuleProgress SATISFIED
= 当前 revision 中该 Module 的 required Task 全部 SATISFIED
  AND required ModuleGate Task 全部 SATISFIED

StageProgress SATISFIED
= 当前 revision 中该 Stage 的 required Task 全部 SATISFIED
  AND required StageGate Task 全部 SATISFIED
```

Goal 必须直接从当前 revision 的底层义务归约，不能只看几个缓存的 Module/Stage 枚举：

```text
Goal COMPLETED
= 当前 PlanRevision 的所有 required executable work Task 全部 SATISFIED
  AND required acceptance obligations 全部满足
  AND required ModuleGate / StageGate / GoalGate Task 全部 SATISFIED
  AND 不存在未对账的高风险或 outcome_unknown 副作用
```

Plan Validator 必须保证 active PlanRevision 至少包含一个 required executable Task 和一个 required AcceptanceObligation；每个 required executable Task（`taskKind=work|gate`）至少映射一个 required AcceptanceObligation；每个 required AcceptanceObligation 必须存在负责取证/归约的 work Task 或 GateTask，并编译出至少一个 required verification requirement。只有该非空 requirement 集都被当前适用 PASS Evidence 覆盖时，义务才满足，防止任一层空集合让 Goal 假完成。

若系统判断目标已经满足、无需改动，也不能提交空 Plan；它必须生成一个 required `AlreadySatisfied GoalGateTask`，以当前适用 Evidence 证明 no-change 结论。所有 MVP Task 都是 executable；TaskHierarchy 中是否为叶节点不改变其完成义务。Goal reducer 必须是覆盖所有合法状态组合的全函数；P0-04 将冻结精确优先级，当前语义边界为：

- 用户放弃整个 Goal：`CANCELLED`；
- desired state 为 paused 或目标变更尚未激活：`PAUSED` / `CHANGE_PENDING`；
- 上述完整完成公式成立：`COMPLETED`；
- 仍有 required Task/Gate 可运行、运行中或验证中：`RUNNING`，另带独立 attention flags；
- required Task 被 deferred/cancelled、存在必须由人裁决的 ArchitectureFinding，或未知副作用需人处置：`NEEDS_DECISION`；
- 剩余 required 前沿全部被真实 Blocker 卡住：`BLOCKED`；
- required Task/Gate 终局失败、重试与 replan 策略耗尽，且没有待决的人类选择：`FAILED`。

单个 Task/Gate blocked 不必使整个 Goal blocked；只要还有不依赖它的 required 前沿可推进，Goal 仍是 RUNNING。optional Task 不阻止 Goal 完成，但其 omitted/deferred/cancelled 结果必须显式展示。

## 12. 避免 Reviewer 成为瓶颈

- 静态检查和测试先跑，明确失败不启动 Reviewer；
- 无语义变化的格式、文档和机械重构可走快速路径；
- Review 单位优先是模块变更集或集成边界，不是每个微型 Task；
- 同阶段不同模块可由多个 Reviewer 并行；
- 跨模块语义在 DAG join 或 IntegrationTask 处审查一次；
- 结果按 workspaceRevision + scopeDigest + architectureBaselineRevision + completionPolicyRevision + reviewer/toolVersion 缓存；
- 返工只复审失败项和受影响依赖；
- Worker 可继续执行不依赖 Review 结论的其他 Task。

## 13. MVP 必须证明什么

多 Agent 作为 MVP 发布门禁，必须同时通过：

1. Worker A 的 Run/Context 结束后，Worker B 只靠持久状态和有界 Handoff 接续；
2. 两个只读 Worker 在同一 Stage 的不同模块或调查方向真实并行；
3. 两者的 Evidence、冲突结论和来源可汇总；
4. 最终只有一个 Writer 修改目标 checkout；
5. 普通代码语义变更经过静态结构分析、适用动态证据和目标化 Reviewer 后自动归约；
6. IntegrationTask 或 GoalGate 对可测试功能运行全量测试；
7. 至少一个真正主观或高风险事项正确升级给用户，而不是把普通验证推给用户；
8. 一个局部、可逆且命中 allowlist 的 ArchitectureFinding 经正常 Controller/Scheduler/Writer 链形成 RemediationTask 并闭环；
9. 一个 material/ambiguous ArchitectureFinding 不能被 Worker 自行洗白，而是形成带历史理由和选项的 ArchitectureDecisionBrief。

这证明并发调度、隔离、汇总和完成闭环，不宣称 MVP 已解决多个 Writer 的并行开发与自动合并。

## 14. 与 OpenAI Harness Engineering 实践的关系

本设计吸收的是以下工程方向：

- 仓库中的架构、计划和决策是 Agent 可发现的版本化工件；
- 架构边界和确定性规则尽量交给机械检查；
- 通过可读取的测试、日志、UI 和运行结果缩短反馈回路；
- 计划与验证必须产生可审计、可重放的状态变化。
- 周期性 Review/cleanup、版本化 ArchitectureReviewProfile 与漂移预算提供可审计的防漂移信号，其有效性由场景评测验证。

同时，OpenAI 的模型使用指导明确建议按改动风险校准测试，不为可逆、低影响且只是复述实现的改动机械增加测试；运行与改动相称的测试，只在有理由时扩大范围。它也建议明确何时以及如何委派子 Agent。由此可推导：不应把每个 Task 串成“实现后写专属测试再排队 Review”，而应按真实依赖并行，并把更重的验证放在模块 join、StageGate 和 GoalGate。
