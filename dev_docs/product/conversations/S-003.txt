# 2. 「计划图」到底是什么

这是现在最应该先定义清楚的。

我认为计划图**不是 Agent 的思维链，也不是 execution trace，更不是知识图谱**。

它表示的是：

> **系统当前认为应该完成什么、任务之间是什么关系、每件事目前处于什么状态。**

因此它其实同时包含两个维度：

```text
             Goal
              │
       ┌──────┴──────┐
       │             │
     Task A        Task B
       │             │
     Task C ← depends_on B
       │
    Verify D
```

第一种边是：

```text
parent / child
```

表达任务分解。

第二种边是：

```text
depends_on
```

表达执行依赖。

首版只需要这两种。

**不要一开始造通用 Graph DSL。**

---

## Plan Node

我建议最小结构直接类似：

```text
Task
├── id
├── parent_id
├── objective
├── acceptance_criteria
├── desired_state
├── current_phase
├── revision
├── priority
├── assigned_agent?
├── blocked_reason?
├── artifact_refs[]
├── evidence_refs[]
└── created_from
```

其中最重要的是把：

```text
desired_state
```

和：

```text
current_phase
```

分开。

例如：

```text
Task T13

desired_state = ACTIVE
current_phase = BLOCKED

reason = waiting for T8
```

这一下就把 **计划图** 和 **控制面** 接起来了。

控制器干的事情本质上就是：

```text
Desired State
      │
      │ compare
      ▼
Current State
      │
      ▼
What action should happen next?
```

这就是 Kubernetes / controller 那套思想真正值得借鉴的地方。

# 3. 计划图不是数据库里的「图数据库」

这点我反而建议你明确写进设计。

逻辑上它是 Graph：

```text
Task ─depends_on→ Task
Task ─parent_of─→ Task
```

物理实现第一版完全可以是：

```text
task
task_edge
```

两张 SQLite/Postgres 表。

然后：

```text
PlanGraph = projection(task + task_edge + runtime state)
```

所以：

> **Graph 是数据模型和展示方式，不意味着 Neo4j。**

这和你之前研究代码图、知识图谱时容易混淆。

这里的 Task Graph 非常稳定、结构非常简单，根本不需要图数据库。

# 4. 数据面：不要再设计一个「Memory 模块」

你前面的判断其实是对的：

> Memory 不是一个东西。

平台真正应该保存的是**事实和可检索对象**。

我建议数据面分成两类。

| 类型 | 内容 | 可信度 |
|---|---|---|
| Mechanical State | Task 状态、Run、Agent 状态、工具结果、commit、测试结果、workspace revision | 强事实 |
| Semantic State | Decision、Summary、Hypothesis、Handoff、Notes | Agent/用户产生，有 provenance |

例如：

```text
Mechanical
──────────
Task T3 = RUNNING
Agent A = RUNNING
Run R7 = ACTIVE
workspace_commit = abc123
test_result = 38/38 passed


Semantic
────────
Decision:
  不采用方案 X

Reason:
  会破坏 backwards compatibility

Source:
  Run R4 / message 38
```

这两类数据不能混。

尤其不能让 Agent 写一句：

```text
"任务差不多完成了"
```

然后平台就把：

```text
Task.status = DONE
```

这应该经过验收条件/控制器。

# 5. Memory 应该变成数据面的多种「投影 + 检索」

这样你之前关于 Memory 的很多困惑会自然消失。

```text
                        Canonical Data
                             │
        ┌────────────────────┼─────────────────────┐
        ▼                    ▼                     ▼
 Task State Projection   Decision Index       History Index
        │                    │                     │
        ▼                    ▼                     ▼
 当前做什么              为什么这样做          原始发生过什么

        ┌────────────────────┼─────────────────────┐
        ▼                    ▼                     ▼
 Agent State           Artifact Index        Retrieval Index
```

所谓 Memory Retrieval 就变成：

```text
1. ID / relation 精确查询
2. 当前 Task / Agent State 查询
3. Artifact / Decision 查询
4. keyword / BM25
5. semantic retrieval
6. 必要时 Agent 帮你继续查
```

而不是：

```text
所有东西
    ↓
Embedding
    ↓
向量数据库
    ↓
祈祷召回正确
```

这个对于你的系统特别重要。

# 6. Control Plane：机械框架必须是主人

这里我建议非常明确地划边界。

**LLM 可以提出计划。**

但是：

> LLM 不应该直接拥有生命周期。

也就是说：

```text
Secretary / Planner Agent
           │
           │ propose
           ▼
       PlanPatch
           │
           ▼
    deterministic validator
           │
           ▼
       State Store
           │
           ▼
      Reconciler
```

而不是：

```text
Manager Agent
     │
     ├─ spawn agent
     ├─ kill agent
     ├─ overwrite state
     ├─ modify DAG
     ├─ merge code
     └─ decide everything
```

后者早晚会失控。

# 7. Control Plane 真正负责什么

可以把它理解成六个机械控制器：

```text
Plan Controller
     │
     ├── Task Lifecycle
     ├── Agent Lifecycle
     ├── Scheduler
     ├── Budget / Limits
     ├── Recovery
     └── Verification
```

例如每次 reconciliation：

```text
for task in task_graph:

    if task.desired_state == CANCELLED:
        cancel_active_runs(task)

    if task.phase == PENDING
       and dependencies_satisfied(task):

        task.phase = READY

    if task.phase == READY
       and resources_available():

        agent = select_agent(task)
        dispatch(agent, task)

    if run.finished:
        evaluate_result()

    if acceptance_criteria_passed:
        task.phase = DONE

    else:
        task.phase = REVIEW / FAILED / READY
```

这就是你的**控制面核心**。

其实并不需要特别智能。

真正智能的是：

```text
“该拆成哪些任务？”
“这个结果意味着什么？”
“现在应该改变计划吗？”
```

这些可以交给 Agent。

# 8. 编排不是独立于控制面的第四个大系统

我会把「编排」定义成：

> **控制面里决定“下一步执行什么、谁来执行、能不能并行”的部分。**

但它内部需要分两层。

### Semantic Orchestration

LLM 擅长：

```text
用户目标
   ↓
理解意图
   ↓
任务分解
   ↓
依赖分析
   ↓
PlanProposal / PlanPatch
```

例如：

```text
目标：修复这个大型项目中的 race condition

Planner:
    T1 调查调用链
    T2 调查线程模型
    T3 复现 bug

    T4 设计修复
        depends_on T1,T2,T3

    T5 实施
        depends_on T4

    T6 测试
        depends_on T5
```

### Mechanical Orchestration

系统负责：

```text
ready = tasks whose dependencies are satisfied

schedule(ready)

T1 → Worker A
T2 → Worker B
T3 → Worker C

wait

T4 → Planner/Executor
...
```

所以：

```text
Planner 决定：
"What should be done?"

Controller 决定：
"What is allowed to happen?"

Scheduler 决定：
"What runs now?"

Worker 决定：
"How do I execute this task?"
```

这是我认为你整个系统最重要的一组边界。

# 9. Agent 可以修改计划，但只能「提案」

否则动态 Agent 系统会非常容易把图搞乱。

Worker 发现：

```text
T3 无法继续
因为还需要调查 module X
```

它不要直接：

```text
INSERT Task T3.1
```

而应该：

```text
PlanProposal {
    parent: T3
    action: ADD_TASK
    objective: "inspect module X"
    reason: ...
    evidence: ...
}
```

然后：

```text
Planner / Plan Controller
        ↓
接受 / 修改 / 拒绝
        ↓
Plan revision++
```

这个机制以后对多人、多 Agent、用户修改目标都会非常重要。

# 10. `revision` 应该成为核心字段

这个小东西能解决很多问题。

假设用户说：

```text
不要再重构整个模块了，
只做最小 bug fix。
```

于是：

```text
Task T7 revision:
17 → 18
```

而旧 Worker 还在执行：

```text
task_revision = 17
```

它回来提交结果时，控制面发现：

```text
worker revision = 17
current revision = 18
```

于是不能机械接受。

进入：

```text
STALE_RESULT
```

再由 Planner / 用户判断是否还能利用。

这比让 Agent 自己“记得用户后来改过主意”可靠得多。

你之前这里确实纠结了很久。

现在我认为可以正式固定：

```text
AgentInstance
=
Profile
+ Task reference
+ State reference
+ Session reference
```

AgentInstance 是一个**逻辑执行者**。

下面：

```text
AgentInstance A
       │
       ├── Run A1
       │     ├── Context 1

       │     └── Context 3

       └── Run A2
```

这和之前材料里的结论一致。跨 Run / 跨 Context 本质上都是“任务状态不能依附于当前执行窗口”。fileciteturn1file7L477-L517

# 12. Context Manager 的定位现在也可以固定了

它不应该管理：

```text
Task
Agent lifecycle
Plan
Session lifecycle
```

它只负责：

> **从 Data Plane 中，为下一次模型调用选择一个有限工作集。**

即：

```text
ContextRequest
├── task_id
├── agent_id
├── run_id
└── token_budget
          │
          ▼
Context Manager
          │
          ├── personality / profile
          ├── tools
          ├── current task
          ├── constraints
          ├── decisions
          ├── current workspace state
          ├── relevant artifacts
          ├── handoff
          └── relevant history
          │
          ▼
     Model Context
```

所以你之前说：

> Context Manager 似乎把 Agent 是什么都管了？

问题就解决了。

它不是管理这些对象。

它是：

```text
State → Context
```

的 **selection/admission layer**。

# 15. Secretary 的作用也因此非常清楚

Secretary 是：

```text

```

的接口。

用户说：

> 现在做到哪里了？

不应该触发一个 Agent 到处搜索。

应该：

```text

        ↓
```

用户说：

```text
TaskCommand {
    task = UI
    desired_state = PAUSED

```

这才需要：

```text
Intent Compiler
     ↓

```

所以查询路径和命令路径要分开。这一点你之前的总体设计清单已经明确要求同时设计“命令路径与查询路径”。fileciteturn1file0L10-L33

# 16. 展示层建议只做四种视图

第一版其实非常简单：

| View | 回答的问题 |
|---|---|
| Plan Graph | 要做什么、依赖是什么 |
| Active Agents | 谁正在干什么 |
| Task Detail | 这个任务为什么处于现在的状态 |
| Timeline / Trace | 到底发生了什么 |

Secretary Chat 是第五个“入口”，但不应该是唯一的状态表达。

这非常关键。

否则又会变成：

```text
所有系统状态
       ↓
塞进聊天
       ↓
LLM 给你解释
```

然后真实状态和 Agent 叙述开始漂移。

# 18. 我认为你现在最需要避免的四件事

1. **不要建立一个万能 Manager Agent。**  
   Manager Agent 可以做语义规划，但机械控制权必须在框架手上。

2. **不要建立万能 Memory Service。**  
   先建立事实、对象、索引和 projection。

# 九、Control Plane 的实现不要从 Scheduler 开始

最应该先实现：

```text
Reconciler
```

因为它才是整个控制面的中枢。

逻辑：

```ts
async function reconcileTask(taskId: TaskId) {
  const task = await state.getTask(taskId);

  if (task.desiredState === "cancelled") {
    await cancelRuns(task);
    return;
  }

  if (task.desiredState === "paused") {
    await pauseRuns(task);
    return;
  }

  if (
    task.phase === "pending" &&
    await dependenciesSatisfied(task)
  ) {
    await state.setPhase(task.id, "ready");
  }

  if (
    task.phase === "ready" &&
    await scheduler.canDispatch(task)
  ) {
    await dispatch(task);
  }

  if (task.phase === "review") {
    await verify(task);
  }
}
```

这就是：

```text
State
 ↓
Reconcile
 ↓
Action
 ↓
New State
```

# 十、Scheduler 第一版也不要聪明

第一版：

```text
READY tasks
    ↓
priority
    ↓
available worker
```

最多判断：

```text
read-only worker
writer
reviewer
```

不要上：

```text
RL scheduler
模型动态选择
复杂 token optimization
全局 DAG critical path
```

这些都是实验优化。

# 十一、Orchestration 怎么开发

这一层才允许 LLM。

输入：

```text
User:
"先调查整个系统为什么跨 context 会丢状态，
然后给方案，确认后再实现。"
```

输出必须是结构化：

```json
{
  "goal": "...",
  "tasks": [
    {
      "temp_id": "T1",
      "objective": "调查现有跨 Context 状态行为",
      "acceptance_criteria": [
        "明确当前状态来源",
        "明确丢失点"
      ]
    },
    {
      "temp_id": "T2",
      "objective": "设计 continuation 方案",
      "depends_on": ["T1"]
    }
  ]
}
```

之后：

```text
LLM output
   ↓
schema validation
   ↓
semantic validation
   ↓
PlanPatch
   ↓
Control Plane
```

LLM 不直接写 DB。

# 十二、Handoff 的统一实现

你现在应该直接把之前的 Continuation Packet 提升成：

```text
HandoffPacket
```

例如：

```ts
interface HandoffPacket {
  taskId: TaskId;
  taskRevision: number;

  objective: string;

  completed: string[];
  unresolved: string[];

  constraints: ConstraintRef[];
  decisions: DecisionRef[];

  artifacts: ArtifactRef[];
  evidence: EvidenceRef[];

  workspaceRevision?: string;

  recommendedNextStep?: string;

  sourceRefs: SourceRef[];
}
```

然后统一服务于：

```text
Context 1 → Context 2
Run 1 → Run 2
Worker A → Worker B
Worker → Reviewer
Worker → Secretary
```

你们之前的 `ContinuationPacketV1` 已经强调了机械生成、有大小上限、来源可追溯和不复制全文历史。fileciteturn1file5L374-L398

所以没必要再为 multi-agent 设计另一套 memory handoff。

# 十四、OpenAI Harness Engineering 最值得你照搬的东西其实是“机械约束”

文章中特别值得你吸收的一点不是目录，而是：

> 架构规则必须机械执行。

OpenAI 给每个 domain 固定依赖层级，并通过 lint/structure test 强制，而不是写在文档里希望 Agent 记住。citeturn297458view0

```text
 ↓

 ↓
runtime ports

 ↓

```

禁止：

```text
domain → control

coding-agent → platform UI

data → secretary

runtime → orchestration

context → control lifecycle
```

# 十七、开发流程：不要一次先把平台骨架全生成

这一点其实 Harness Engineering 也有明确经验。

他们采用的是：

> 大目标 → 小 building block → 能力解锁 → 再向前。

而不是先生成整个百万行框架。citeturn297458view0

所以你的开发应该是垂直切片。

# Phase 7：两个 Worker

第一个真正 multi-agent 场景：

```text

                     ▼
```

# 二十、每个阶段都必须采用同一种开发循环

这也是我从 Harness Engineering 最建议你借的一点。

每个任务：

```text
1. Plan
   ↓
2. Implement
   ↓
3. Deterministic Test
   ↓
4. Scenario Test
   ↓
5. Agent Review
   ↓
6. Fix
   ↓
7. Update Docs / Plan
   ↓
8. Merge
```

不是：

```text
Agent 写代码
↓
看起来能跑
↓
下一个模块
```

OpenAI 的实际工作流已经进化到：

```text
agent implementation
→ local self review
→ additional agent reviews
→ respond to feedback
→ tests
→ PR
→ repeat until accepted
```

并且把可观察性、UI、日志、测试能力也做成 Agent 能直接读取和验证的工具。citeturn297458view0

# 二十一、你这个项目现在真正应该从哪里开始

所以如果按照你前面说的：

> 先总体设计 → 我澄清 → 伪代码 → 切 MVP → 实现。

我认为现在应该正式进入：

```text
D0   Overall Architecture
     ↓
D1   Object Model
     ↓
D2   Data Plane
     ↓
D3   Plan + Control semantics
     ↓
你裁决
     ↓
P0   核心流程伪代码
     ↓
MVP0 数据面
     ↓
MVP1 Plan/Reconciler
     ↓
MVP2 coding-agent integration
     ↓
MVP3 Context/Handoff
     ↓
MVP4 multi-agent
     ↓
MVP5 Secretary/UI
```

而不是继续沿原来的：

```text
M7 = compaction + artifact + inbox + agent manager + ...
```

横向铺。

你当前实施计划本来把 M7 定义成 Context/Artifact/Compaction、Inbox、子 Agent 控制等一整个大集合。fileciteturn0file0L40-L55

我现在会建议你**把 M7 重写成平台化阶段**，而且里面以：

> **Data → Plan → Control → Runtime → Context → Multi-Agent → Interaction**

作为纵向施工顺序。

## 最终一句话

Harness Engineering 给你的最大启示不是“OpenAI 用了什么目录”，而是：

> **Agent 的能力上限越来越由它周围的可读状态、机械约束、工具、反馈回路和计划系统决定。**

因此你这个项目的主角也不应该再是 `AgentManager`。

真正的主干应该变成：

```text
                 PLAN
                  │
         desired / current state
                  │
              CONTROL
                  │
              SCHEDULE
                  │
               AGENT
                  │
                DATA
                  │
           projection/index
                  │
           CONTEXT + UI
```

而你已经做出来的 `coding-agent`，恰好可以作为这套系统下面相对成熟的 **Execution Kernel**。这会比继续在单 Agent 上堆 Context/Memory/Multi-Agent 特性清晰很多。
