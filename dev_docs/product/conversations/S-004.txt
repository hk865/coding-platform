# 1. 先把 Grok Bot 的架构抽出来

xAI 自己给 Grok Bot 定义了五个核心 primitive：

> **Bot / Chat / Prompt / Tool / Artifact**

其中 Bot 才是一等对象，而不是 Chat。Bot 拥有自己的 identity、memory、runtime 和 tools；Chat 只是人与 Bot 交互的一个 interface。citeturn0view0

把整篇文章转换成我们最近讨论的“数据面 / 控制面 / 编排 / 展示层”，大概就是：

```text
                         USER
                           │
                           ▼
                ┌────────────────────┐
                │  Chief of Staff Bot│
                │   / Coordinator    │
                └─────────┬──────────┘
                          │
                 task / query / decision
                          │
             ┌────────────┴─────────────┐
             ▼                          ▼
       ┌───────────┐              ┌───────────┐
       │ Agent A   │              │ Agent B   │
       │ Engineer  │              │ Researcher│
       └─────┬─────┘              └─────┬─────┘
             │                          │
      ┌──────▼──────┐            ┌──────▼──────┐
      │ Agent State │            │ Agent State │
      │ Memory      │            │ Memory      │
      │ Routines    │            │ Routines    │
      │ Runtime     │            │ Runtime     │
      └─────────────┘            └─────────────┘

             └──────────┬──────────┘
                        │
                  Shared Project
                    Context
                        │
                  Group Chat
                        │
             ┌──────────▼─────────┐
             │ Account Capability │
             │ Tools              │
             │ Skills             │
             │ Connectors         │
             └────────────────────┘
```

这已经非常接近你最近画的东西。

# 2. 最像你的地方：Agent ≠ Session

这是我觉得最关键的一点。

Grok Bot 明确说：

> Chats are disposable.

真正长期存在的是 **Bot**。

Bot 有自己的：

- identity
- memory
- runtime
- tools
- conversation history
- computer

所以明天回来还是同一个 Bot，而不是重新开一个 session。citeturn0view0

这恰好就是你前几天一直纠结的：

> Run 到底是什么？
>
> Session 到底是什么？
>
> State 到底属于谁？
>
> Context Manager 到底应该管理什么？

Grok Bot 给出的产品层答案其实很清楚：

```text
Agent / Bot        persistent
│
├── Identity       persistent
├── Memory         persistent
├── Routines       persistent
├── Runtime
│
├── Chat #1
│   └── Run...
│
├── Chat #2
│   └── Run...
│
└── Chat #3
    └── Run...
```

所以你之前说：

> run 管一次执行；
> state 管多次 context；
> agent 才是真正长期存在的主体。

这个判断基本就是 Grok Bot 现在采用的模型。

---

# 3. 更离谱的是：他们也搞了你的 Secretary

你最近定义 Secretary 的时候说，它不应该自己承担所有工作。

它应该：

- 掌握所有 Agent 状态；
- 帮人查询状态；
- 分发任务；
- 处理 Agent 间协调；
- 主动提醒；
- blocked 时把问题交给人；
- 让人只处理真正需要 judgment 的东西。

Grok Bot 的文章直接出现了：

> **Chief of Staff Bot**

用户创建一个 Chief of Staff，让它负责 coordinating several specialists。

这样用户：

> give direction to one Bot instead of checking each one and routing every task themselves.

而且 xAI 明确说，他们考虑过：

- dashboard
- assignment board
- explicit handoff controls

最后认为：

**这些东西反而把 coordination work 又推回给用户了。**

所以最终选择：

> coordinating Bots handle routine routing and bring the user in when a decision requires judgment. citeturn1view0

这基本就是你前面定义 Secretary 的那句话：

> **人应该掌握状态，但不应该自己负责 Agent 调度；Secretary 应该把需要真实业务信息、技术 trade-off、工程 trade-off 和人类判断的问题暴露给人。**

两边几乎是同一个设计结论。

---

# 4. 甚至“Memory 不是一个东西”也撞上了

这是另一个非常值得你注意的地方。

你前几天一直强调：

> Memory 不应该是一个统一的大 Memory。

因为实际上有：

```text
项目静态状态
Agent state
历史轨迹
Agent memory
任务状态
共享状态
检索结果
```

Grok Bot 也明确拒绝把这些全部混成一个大 memory。

他们做了一个非常重要的 separation：

```text
Account level
────────────────────
Tools
Skills
Capabilities

Agent level
────────────────────
Memory
Routines
Role context

Project / Group level
────────────────────
Shared context
Conversation
Artifacts
```

xAI 的原话概念非常明确：

> capabilities can be shared broadly while context remains with the role that needs it. citeturn1view0

也就是说：

**能力共享，状态/上下文隔离。**

这实际上可以直接变成你平台一个非常重要的设计原则。

# 5. Group Chat ≈ 你说的 Workspace / 项目状态

这里也非常像。

Grok Bot 没有让所有 Agent 共用一个 global memory。

而是：

```text
Engineer Memory ─────┐
                     │
Researcher Memory ───┼── Project Group Chat
                     │      │
PM Memory ───────────┘      │
                            ▼
                     Shared Context
```

每个 Agent 保持自己的 specialized memory。

只有项目需要的信息进入 group context。citeturn1view0

这跟你最近讨论的：

> Agent State + Project State + Global State

其实是一回事。

而且他们还有另一篇非常值得你看的文章：

urlHow I run multiple teams of Grok Botsturn1search0

这篇甚至已经开始出现你最近讲的 **Task Graph / Project Manager / 状态板** 了。

他们的实验性做法是：

```text
Project
│
├── Channel
│
├── Bot roster
│
└── Notion
    ├── Projects DB
    └── Tasks DB
```

然后有一个 **Projects Manager Bot**：

```text
Projects Manager
      │
      ├── create project
      ├── create channel
      ├── select agents
      ├── maintain project DB
      └── maintain task DB
```

Bot 卡住之后：

```text
Task
 ↓
Blocked
 ↓
PM / Bot
 ↓
ping human
```

作者自己最后甚至说：

> 越做越像原本为人类设计的系统：board、manager、specialists claiming tasks、blocked column、channel。citeturn1search0

这与你最近关于 **Task Graph + Agent 状态 + Secretary + 多 Agent 并行** 的讨论已经非常接近了。

# 7. Grok Bot 反而验证了你最近一个非常重要的判断

你之前一直想搞一个很复杂的 dashboard。

后来逐渐变成：

> 用户真正需要的是一个 Secretary + 状态暴露。

Grok Bot 的设计研究恰好得出了同样的结论。

他们**主动删除** dashboard、assignment board 和 explicit handoff controls，因为这些东西意味着用户又开始管理 Agent。

他们的目标是：

> **delegate，而不是 operate。** citeturn1view0

所以 UI 最终只暴露：

```text
Bot
├── identity
├── status
├── current action
├── result
├── blocked
└── needs human
```

底下：

```text
scheduler
task graph
memory
runtime
tools
sandbox
context
events
```

全部藏起来。

这个其实对你非常有启发。

你的：

> 数据面 / 控制面 / 编排层

**应该非常复杂。**

但是：

> Secretary / UI

**反而应该非常简单。**

这两件事并不矛盾。

# 8. 还有一个我觉得你应该直接抄的东西：Presence

你之前一直问：

> 人怎么知道 Agent 到底在干嘛？

Grok Bot 没有把完整 execution trace 全塞给用户。

它只定义几个状态：

```text
Idle
Thinking
Working
Waiting
Blocked
Done
```

需要的时候 hover 才看 current action。citeturn0view0

甚至 Agent computer 都是三级：

```text
Status
  ↓
Preview
  ↓
Takeover
```

默认只知道：

> 它在工作。

想知道更多：

> Preview。

Agent 真解决不了：

> Takeover。 citeturn0view0

这跟你 Secretary 的信息层级可以直接对应：

```text
Level 0
Agent status

Level 1
Current task / progress / blocker

Level 2
Execution trace / artifact / logs

Level 3
Human takeover
```

我认为这比做一个巨大的“Agent 监控 Dashboard”合理很多。

# 9. Routines 其实就是你控制面的 Trigger

Grok Bot 还有一个容易被忽略、但从系统架构角度很重要的设计：

Agent 不一定由 user prompt 启动。

可以由：

```text
User Prompt
Schedule
Webhook
GitHub Event
Slack Event
Linear Event
Another Bot
```

触发。citeturn1view0

于是：

```text
Trigger
   │
   ▼
Event
   │
   ▼
Scheduler / Orchestrator
   │
   ▼
Agent Runtime
   │
   ▼
Run
```

这其实就是你一直说的：

> **Agent 不应该等同于 Run。**

因为如果 Agent = Run：

schedule/event 根本不好解释。

但如果：

```text
Agent = persistent actor
Run   = execution instance
```

所有东西一下就顺了。

# 10. 所以现在重新看你的项目，我会稍微改变之前给你的定义

以前我们一直叫：

> **多 Agent 平台**

现在这个名字其实太宽泛了。

因为 Grok Bot 已经证明：

**“persistent multi-agent workspace” 本身已经可以成为成熟产品。**

你真正值得继续做的差异化应该往下一层：

> **Agent Control Plane + State Plane + Workspace**

也就是：

```text
Human
  │
  ▼
Secretary
──────────────────── Product Interface
  │
  ▼
Orchestrator
──────────────────── Coordination Plane
  │
  ▼
Task Graph / Scheduler / Lifecycle
──────────────────── Control Plane
  │
  ▼
Agent Runtime × N
──────────────────── Execution Plane
  │
  ▼
State / Event / Artifact / CodeGraph
──────────────────── Data Plane
```

Grok Bot 可以成为你的**产品层参考实现**。

而你真正需要研究的是：

> **Grok Bot 没公开讲出来的下面三层到底应该怎么做。**

尤其你最近正在讨论的 **Task Graph completion 判定、static analysis + agent semantic judge、并行任务 DAG、Agent lifecycle、state retrieval、CodeGraph、项目状态与 Agent 状态分离**，这些才开始真正进入你的差异区。

所以你的感觉没有错：

**你确实在“撞 Grok Bot”。**

但更准确地说，是你自己从 Coding Agent → 多 Agent → State → Control Plane → Secretary 这条路线推演下来，最后推到了和 Grok Bot 非常接近的**产品形态**。

现在反而不用继续花很多时间证明“产品应该长什么样”了——xAI 这篇东西已经替你做了一次很好的外部验证。

下一步更值得做的是：**把 Grok Bot 公开暴露出来的全部设计对象逐个映射到你现有架构，然后找出 Grok Bot 没有公开解决、而你的系统必须解决的技术空白。**这会非常直接地告诉你：哪些东西可以抄 Grok Bot，哪些东西才值得你自己造。memcite

第一类是**产品/概念层的重新发现**。比如 persistent Agent、Agent ≠ run、Secretary/Coordinator、共享能力但隔离上下文、Agent 状态展示、用户不应该手动调度每个 Agent。这部分和 Grok Bot 高度重合。**如果一开始就看到这篇文章，可能能省掉你一两天甚至更多的概念争论。**

第二类是**把概念推到系统架构层**。你这几天真正花大量时间纠结的是：

```text

  │     └── Run

      Context

Multi-Agent
  │
  ├── Data Plane
  ├── Control Plane
  ├── Lifecycle
  ├── Orchestration
  └── Workspace / Secretary
```

这部分 Grok Bot 那篇设计文章**没有替你完成**。它告诉你用户看到什么、Bot 应该是什么，但没有给你一套可以拿来实现的 control plane。


所以现在最危险的反应反而是：

> “靠，别人做了，那我这几天全浪费了。”

然后换方向，再重新研究一个星期。

你最近自己也发现了这个问题：前面做 Coding Agent 时已经因为过度设计、同时研究多个方向，损失了一些实现时间。现在不应该再来一次。

> **凡是 Grok Bot 已经验证过的产品抽象，停止争论。**

比如 Agent 是否 persistent、是否需要 coordinator、是否应该让用户自己 dispatch、Agent 与 Chat 是否应该分离——**这些先冻结。**

> **如果我要实现 Grok Bot 这种体验，底下那个没有公开的 Agent control plane 到底怎么实现？**

这样你这几天的东西反而一下串起来了：

```text

                        │

        │                              │

        └──────────────────────────────┘
```

甚至你今天刚刚讨论的 **Task Graph 怎么判断完成、为什么不能阶段串行而应该模块并行、static analysis + agent semantic judgment**，已经明显不是 Grok Bot 那篇 UX 文章解决的问题了。

所以我会给这几天一个比较准确的评价：

**你大概花了一部分时间重新发现了 persistent multi-agent workspace；但在重新发现过程中，把问题一路向下挖到了 control plane。前者现在可以停止研究，后者才应该成为项目主体。**

而且有个很现实的好处：以后你介绍这个项目，不必再花半天解释产品形态。

可以直接一句：

> **“上层交互形态类似 Grok Bot，但我做的重点是其下层的 multi-agent control plane：task graph、state management、lifecycle、verification、parallel orchestration 和 coding-specific CodeGraph。”**

> **当机器可以同时做几十件事时，怎么让一个人仍然能够有效地控制它们？**

这会自然推出你们现在看到的架构。

### 1. 真正的瓶颈从 Agent 能力转向人的注意力

假设一个人同时运行 20 个 Agent：

```text
传统 Agent

Human
 ├─ Agent 1
 ├─ Agent 2
 ├─ Agent 3
 ├─ ...
 └─ Agent 20
```

理论算力提高了 20 倍，但人马上成为瓶颈：

```text
查看结果
理解上下文
回答问题
判断失败
重新分配任务
处理冲突
确认完成
```

于是实际上：

\[
Throughput \le Human\ Attention\ Bandwidth
\]

再增加 Agent 数量没有意义。

所以必然需要中间层：

```text
                    Human
                      │
              goals / decisions
                      │
                      ▼
                ┌───────────┐
                │ Secretary │
                └─────┬─────┘
                      │
           summarized world state
                      │
             ┌────────▼────────┐
             │  Control Plane  │
             └────────┬────────┘
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
      Agent         Agent         Agent
        │             │             │
        └─────────────┼─────────────┘
                      ▼
                   World
```

**Secretary 的真正作用不是“又一个 Agent”。**

而是一个：

> **Attention Interface。**

它负责把机器世界巨大的状态空间压缩成人能够处理的信息流。

- Agent 不知道的真实业务信息；
- blocked 的事情；
- 必要的时候可以追问 Agent。

现在可以把它概括成一个非常漂亮的原则：

> **默认隐藏执行，主动暴露决策。**

```text
 │ 🟠 Blocked           │
 │ 🟡 Risk / anomaly    │
 │ 🟢 Important result  │
 └──────────────────────┘
            │
            ▼
          Human
```

```text
 └── Context Manager
```

想成核心。

```text
                  DATA PLANE

              Persistent State
                     │

                     │
```

**Context 不是事实源。**

Context 是：

Context_t =

```text
Persistent State
   ↓

   ↓
select
   ↓
project
   ↓

   ↓

```

**Compression 只是 projection/retrieval 的一种手段，不应该承担系统持久状态。**

这跟你前几天自己得出的“compression 只是兜底”完全接上了。
