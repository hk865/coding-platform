The plan's fields (the platform fills schemaVersion, kind and every task's phase):
- stages: array of {stageId, title, description?}. A task references a stage only through its own stageId.
- tasks: array of {taskId, stageId?, title, requirementLevel, taskKind, disposition, scope, executionIntent?, sizeClass?, estimatedLines?, plannedFiles?, replacedByTaskId?}. requirementLevel is "required" or "optional". taskKind is "work" or "gate". disposition is "active", "deferred", "cancelled" or "superseded". Every task of a NEW plan starts "pending". scope is {kind:"goal"}, {kind:"stage",stageId} or {kind:"module",stageId,moduleRef}. Task scope.moduleRef is a non-empty STRING containing the moduleId, NOT the {projectId,moduleId} object used in the architecture catalog. executionIntent is "plan_only" or "request_execution" and may appear on a work task only. sizeClass is "small", "medium", "large" or "explore"; a placeholder task carries it too. estimatedLines is a positive integer line estimate; when unsure, say so or leave it out instead of inventing a precise number. plannedFiles (optional, work task only) lists the files this task expects to change, as workspace-relative paths such as "src/a/b.ts": no leading "/" or "./", no ".." or backslash, no directory or wildcard, each path once, at most 50. A file the task will create may be listed; a rename lists both paths. It is a hint for people and other tasks, not a limit: the executor may change other files without asking, and those show as not in the plan. List only the files you are fairly sure of, or leave it out; never pad the list. A task that already ran keeps its list. replacedByTaskId points a superseded task at its successor. A task that already ran changes only its disposition (superseded plus replacedByTaskId); its frozen definition and the obligations it carries stay byte-identical. To change acceptance, add a NEW obligation (new obligationId and new requirementId) carried by the replacement task; keep the old obligation and add the replacement task to its taskIds.
- assignments: array of {taskId, role, instruction}. A work task with executionIntent "request_execution" needs exactly one assignment whose role is one of the AVAILABLE roles/templateId shown in this context; a work task with executionIntent "plan_only" may omit it; a gate task must never carry an assignment or an executionIntent, because a gate conclusion comes from the formal evidence reduction, not from an execution run. A future work task with executionIntent "plan_only" may omit assignment, obligations/acceptance and dependencies; its incompleteness alone is not a reason to answer with questions instead.
- obligations: array of {obligationId, title, requirementLevel, taskIds, verificationRequirements}. taskIds lists only work/gate tasks of this same plan. Every verificationRequirements entry is {requirementId, requirementLevel, kind, description, requiredReadPaths?}; requirementLevel is "required" or "optional" and kind must be one of the requirementKinds of the effective CompletionPolicy shown in this context. requiredReadPaths is an optional array of workspace-relative paths that a required witness requirement must read. A required obligation needs at least the policy's minimum number of required verification requirements.
- taskHierarchy: {parentOf:[{parentTaskId, childTaskId}]}. It only expresses display grouping.
- executionDag: {dependsOn:[{taskId, dependsOnId, requires:{kind, label}}]}. requires.kind is "artifact", "environment-revision" or "gate-result"; use a real versioned input/output dependency, keep the DAG acyclic and never make a task depend on itself.
- taskRelations: Optional: array of {fromTaskId, toTaskId, kind, note}; kind is "coordination" or "expected_dependency". It is advisory only and never a dispatch prerequisite.
A plan may carry checks (array of {checkId, kind, command, cwd, timeoutMs, taskIds}, kind "static" or "dynamic") that its tasks need and no installed check runs, taskIds listing its own tasks; adopting the plan installs them, so a later goal proposes its own checks; a plan the platform adopts by itself needs each new check to fail on the workspace as it is before this change.
