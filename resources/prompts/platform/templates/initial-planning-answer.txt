plan (schemaVersion 2) has these fields:
- stages: array of {stageId, title, description?}; a task names its stage only by its stageId.
- tasks: array of {taskId, stageId?, title, requirementLevel, taskKind, disposition, scope, executionIntent?, sizeClass?, estimatedLines?, plannedFiles?, replacedByTaskId?}. requirementLevel "required"|"optional"; taskKind "work"|"gate"; disposition "active"|"deferred"|"cancelled"|"superseded". scope is {kind:"goal"}|{kind:"stage",stageId}|{kind:"module",stageId,moduleRef}; moduleRef is a non-empty STRING with the moduleId, not a {projectId,moduleId} object. executionIntent "plan_only"|"request_execution", work only. sizeClass (optional) "small"|"medium"|"large"|"explore", placeholders too. estimatedLines (optional) a positive integer; omit when unsure. plannedFiles (optional, work only): expected workspace-relative files like "src/a/b.ts", no leading "/" or "./", no ".." or backslash, no directory/wildcard, unique, max 50; created files and both sides of a rename may be listed. A hint, not a limit; list only files you are sure about, never pad. An already-run task keeps its list, changing only its disposition (superseded + replacedByTaskId to its successor); its frozen definition and obligations stay byte-identical. To change acceptance add a NEW obligation (new obligationId/requirementId) on the replacement, keep the old and add the replacement to its taskIds. To cancel set that task (same taskId) "cancelled"; never add one starting "cancelled"; make an obligation only it carries optional or change acceptance as above; drop checks only it needed. A new task's checks must not need a cancelled task's output or contradict a remaining task/gate (see below).
- assignments: array of {taskId, role, instruction}. "request_execution" needs exactly one assignment with an AVAILABLE role/templateId; "plan_only" may omit it; a gate never carries an assignment or executionIntent. A future plan_only task may omit assignment, obligations/acceptance and dependencies; that alone does not justify needs_decision.
- obligations: array of {obligationId, title, requirementLevel, taskIds, verificationRequirements}; taskIds lists only this plan's work/gate tasks; each entry {requirementId, requirementLevel, kind, description, requiredReadPaths?}, requirementLevel "required"|"optional", kind from the effective CompletionPolicy's requirementKinds shown here; a required obligation needs the policy's minimum required verification requirements.
An explore task (sizeClass "explore", executionIntent not "plan_only") is inspect-only: the obligation that maps only that task needs one required "witness" requirement; when the input files are known, list their workspace-relative paths in requiredReadPaths, else omit; a witness requirement needs "witness" in the effective CompletionPolicy's requirementKinds.
- taskHierarchy: {parentOf:[{parentTaskId, childTaskId}]}; display grouping only.
- executionDag: {dependsOn:[{taskId, dependsOnId, requires:{kind, label}}]}; requires.kind "artifact"|"environment-revision"|"gate-result"; a real versioned input/output dependency, acyclic, never self-dependent.
- taskRelations (optional): array of {fromTaskId, toTaskId, kind, note}; kind "coordination"|"expected_dependency"; advisory only, never a dispatch prerequisite.
A planning round's checks are a top-level list beside plan; an initial plan puts them in setup.checks. Each entry is {checkId, kind, command, cwd, timeoutMs, taskIds}: kind is exactly a policy requirement kind ("static"|"dynamic", NO coverage); taskIds "all" for a project-wide entry, else exactly the tasks it checks; every required non-reviewer/witness requirement needs an entry of that kind; the command must really run (no assumed test file, unrelated command, always-passing command, empty list to force a PASS); it runs in bash on this workspace, where git works and only the untracked .workbench/ is hidden from git's view; double quotes eat one backslash, so put variables in double quotes and regexes in single quotes; wrap a node -e or python -c script in single quotes and use double quotes inside it.
When the request asks for only this segment, output only its stages, tasks, assignments, obligations and dependencies; do not restate other segments; the platform merges it. A task you leave out stays as it is and is not dropped: when the change replaces or drops what a task does, list that task with its own taskId as "cancelled", or "superseded" with replacedByTaskId.
Do not include planId, planRevision, goalId or origin: identity comes from the saved Job project/goal/intentId, provenance from revisions and digest.
Each stage and plan has exactly one gate: a required "gate" task with scope {kind:"stage",stageId} in the taskIds of its stage acceptance obligation, and a required, active task with taskKind "gate" and scope {kind:"goal"} in a required goal acceptance obligation. Include them: the reviewer checks, the platform never adds. A segment keeps existing gates and obligations; a new stage brings its gate. A stage gate covers only its own stage's stage- or module-scoped work; goal-scoped work counts for no stage gate, so scope each stage's work to its stage (a stage gate that covers no work never passes).
A gate's obligations carry only general checks; put feature requirements on the work tasks that build them.
When a change touches an adopted gate's requirements: until the person clearly changes what the goal or stage must meet, keep the gate and its obligations and ask a real open decision through questions; once they do (drop/rewrite a gate requirement), mark that gate superseded with replacedByTaskId naming a new gate, carry the new acceptance in new obligations on it, and leave out the obligations only the old gate carried (obligations only; a task left out stays active); only the person's adoption accepts this.
Every required "request_execution" work task is listed in the taskIds of a required obligation; a "plan_only" placeholder may stay unlisted.
Choose every stage, task, scope, role, instruction, obligation, requirement, dependency from the request and sources. Apart from the stage gates, the goal gate and their obligations, never invent a gate, dependency, assignment, acceptance, verification requirement or role the request did not ask for, never default a missing decision; ask it through needs_decision.
