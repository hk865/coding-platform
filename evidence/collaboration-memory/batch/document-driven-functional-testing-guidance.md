# S 后、I 系列前后的文档驱动功能测试指导

日期：2026-09-14。性质：用户委托编写的执行指导；不是验收报告，不声明当前功能通过，也不修改既有票据的范围或状态。本次只编写文档，未执行产品测试。

## 1. 目标与阶段安排

先把业务行为、责任模块和公开接口理清，再根据产品承诺与接口契约设计测试。用测试发现实现、接线和证据缺口，最后按既有 I01–I04 完成产品集成验证。

S01–S05 证明结构整理的质量：模块清楚、规则维护位置集中、实际接口与架构一致。它不证明整个产品可用。已有测试通过也只证明其覆盖场景；历史 PASS 不能代替当前集成版本的功能结论。

核对 PLAN 后明确：I01 已负责同一用户场景的端到端行为和真实模型样例，I02 已负责跨入口、旧库和恢复集成。因此，I 前增加的是准备工作，不再新增一套必须先完成全部 E2E 才能进入 I01 的门禁。

| 顺序 | 工作 | 输出与边界 |
| --- | --- | --- |
| S 收尾 | 按原始对话核对职责、公开接口、共享规则、命名和生产装配 | 接纳的结构快照；明确保留项与限制 |
| I 前准备 | 文档义务映射、测试覆盖盘点、补基础契约/模块集成测试、准备真实环境和故障注入 | 测试矩阵、缺口表、I 用例与环境；可做最小启动冒烟，不要求提前重复完整 I01 |
| I01 | 同一 Coding 场景贯通用户操作、协作、记忆、决定与恢复 | 确定性流程及真实模型样例；按真实生产入口运行 |
| I02 | 各类运行入口组合、权限失效、并发、取消、恢复和旧数据兼容 | 当前集成版本的组合反例与故障证据 |
| I03 | 计划修改完成后固定最终集成版本，集中回归 | 同源码/配置/构建产物的全量、类型、边界、构建、文档和浏览器证据 |
| I04 | 独立产品验收与交接 | 逐项覆盖结论、缺陷、真实模型效果边界、迁移/恢复说明 |

不要以“再加一个准备阶段”为由无限推迟 I；每个准备项都应说明它具体使哪条 I 用例可执行。

## 3. 先形成可追溯的测试矩阵

不以测试文件数量、覆盖率百分比或通过总数作为功能完成标准。每项近期义务至少建立一行，下列字段不可仅填一个测试目录：

| 字段 | 内容 |
| --- | --- |
| 需求来源 | 产品/Interface 章节、PLAN V 编号、适用票据与用户纠正 |
| 用户行为与预期 | 谁触发、前置状态、操作后应观察到什么 |
| 责任与入口 | Module、公开操作、真实 Host/UI 调用者 |
| 权威与禁止行为 | 正式记录来源、权限/版本条件，以及绝不能出现的结果 |
| 用例 | 正常、拒绝、重复、并发、失效/恢复；不适用须说明理由 |
| 测试层级 | 契约、模块集成、跨入口、浏览器、真实模型；区分生产与替身 |
| 实际证据 | 测试文件及用例名、命令、快照、配置、日志与断言位置 |
| 缺口及归属 | 未实现、未接线、未测试、环境阻断、需求待裁决；分别处理 |
| 结论 | 待核对/通过/失败/未执行/明确延期；跳过不能算通过 |

先读已有用例的断言，判断是否真的覆盖要求，再决定补测试。一个仅检查 HTTP 200 或返回非空的用例不能证明工作完成、材料采用或恢复正确。

## 4. 功能测试应覆盖什么

下面是从已读产品与批次规范提取的起始范围，执行者仍须逐项展开 V01–V22 和有效核心义务，不能把本表当成完整用例清单。

| 行为 | 必须观察的结果与反例 | 主要依据/阶段 |
| --- | --- | --- |
| 目标、计划、执行、验证与完成 | 从正式入口创建工作；证据与当前义务对应。模型自称完成、空计划、过期证据不能使 Task/Goal 完成 | PRODUCT 状态真实性/证据驱动完成；I01/I02 |
| 共享材料与有限通信 | 两个授权 Work 可读；第三个无权 Work 不可读；相同 digest 不串权限。订阅开始/取消、乱序、重复、有限重放不产生重复有效投递 | V01/V02；I 前契约、I02 组合 |
| 等待与后继 | event-before-wait 与反向时序、all/any、超时/取消、前驱结束顺序均符合资格；至多一个合法后继，迟到报告可追溯 | V03/V04，M06；I02 |
| 调度、积压与取消 | 只读任务确有时间重叠；同 checkout 写冲突只有合法 Writer；公平/退避/积压可见。取消请求、确认与未知可区分 | V03/V05、M01/M05；I02 |
| Query/Reviewer/Handoff/Rework | Query 无写权限；Reviewer 资格和输出版本正确；换手不双启动；重复返工触发不重复受理；不同运行类型权限不被统一函数抹平 | M02–M04、V06/V16；I02 |
| 持久记忆与下一回应 | 明确保存、纠正、删除；去掉原话并重启后，下一相关回应取当前 revision；一次性例外不变长期偏好 | V08/V11/V18；I 前确定性测试、I01 实模型 |
| 用户随行与项目隔离 | 用户偏好随项目切换；A 项目习惯不自动流入 B；显式复制选定版本不继承授权或完成状态 | V21；I01/I02 |
| 局部经验 | 有来源、条件和版本；下一次相关协作实际消费；条件变化或与正式规范冲突时停用 | V19；I01 |
| 架构冲突与决定 | 测试前冲突可主动上报；接受/修改/拒绝/延后绑定版本；全影响集回流；旧决定、重复点击和单 Work 失败可见 | V13/V20；I01/I02 |
| 界面真实性 | UI 的状态、记忆、投递/决定回执及 freshness 可与持久事实核对；刷新/重启后不显示虚假成功 | V12/V14；I01/I03 |
| 来源、撤权与输入 | selection、bind、provider submit 边界分别更新来源/撤权；旧材料不继续获得授权；记录实际请求版本 | PLAN §9、V03/V09 近期部分；I02 |
| 双读模型与性能 | 同事件序列的公开视图与预期一致；SQLite 整页失败回滚、重建/重启一致；增长数据下耗时/读取/内存有测量 | 原始讨论、S03；继承有效证据，I03 按影响回归 |
| 旧数据和生产默认 | 旧库按已有兼容约定读取/迁移；旧调度入口无第二启动权；缺真实能力明确失败或 unsupported，不能退回 Fake 成功 | M05、V16/V22；I02 |

双适配器相互一致仍可能共同出错，必须另有从契约推导的预期结果。测试“没有双启动”要观察实际 Runtime/工具调用数量或副作用记录，不能只数最终 Run 行。

## 5. 各层测试怎样设计

**契约和模块集成：** 优先从公开入口驱动并检查可观察结果。Control 的受理反例与 Ledger 的事务反例分别保留；用真实 SQLite 连接验证 CAS、事务回滚和重开。直接访问私有字段的白盒测试只补充内部性质，不能成为主要产品证据。

**并发与恢复：** 用 barrier 或明确故障钩子固定竞态，避免只靠 sleep 碰运气。在正式提交后/wake 前、外部动作后/回执前、投影页中间、决定落账后/回流前等契约边界注入故障。恢复使用新进程及持久数据，检查无丢待办、无重复外部动作、过期租约不可提交。结果未知应保持显式待对账/隔离，不能把无法判断改成自动重试或成功。

**确定性流程：** 可替换模型响应来稳定制造正常与失败分支，但使用真实 Host、路由、Ledger、Vault、Context 与调度接线；报告明确替换哪一层。测试从旁路直接写最终快照，不算端到端用户操作。

**真实模型：** 使用真实产品启动方式、实际内核和已配置模型。分别记录材料被检索、编译、绑定、调用获授权、实际尝试及可获得的回执/行为见证；捕获请求不等于证明模型采用。效果检查使用预先写明的评分依据，如回应信息密度、解释目的、进度组织；保留失败样例。单个乘法调用只证明模型连通，不能证明产品协作。脱敏证据不保存密钥。

**浏览器：** 从产品 UI 完成可见操作，检查真实后端与持久状态；页面可达或截图美观不能代表业务闭环。浏览器用例覆盖正常、拒绝、过期、不可用、刷新及恢复后的状态。

**性能：** 固定环境和数据集，对正常规模与增长规模记录重复测量、耗时分布、读取范围/次数和内存；比较相同工作量的基线与当前版本。阈值依据产品要求或可解释基线，不能临时放宽只求 PASS。没有测量依据不增加 Redis。

## 6. I 前具体交付与进入条件

复用现有 batch coverage 和证据目录，避免再维护互相矛盾的状态表。新增内容只需三份相互引用的材料：

1. 测试矩阵：覆盖全部近期 V 项及承接的核心产品义务，标出已有可靠测试和待补项。
2. 缺口台账：每项记录复现、影响、责任模块、所需修复/接线/测试和目标阶段；源码缺陷不能只靠改测试期望关闭。
3. I 执行方案：I01 同一场景与分支、I02 故障组合、I03 命令与产物、I04 证据索引；包含数据初始化、模型配置、实际运行环境和恢复方法。

进入 I01 前：S 接纳基线可识别；近期义务已映射；基础契约/模块集成的已知阻断问题已处理；测试环境可启动；关键故障和观察入口可用。I01/I02 本来要探索的组合行为标为待验证，不要求预先全部通过。若规范或接线不足以执行某条用例，先形成具体缺口并处理；不能以一个局部缺口无限阻塞无关用例。

用户提供的项目只能作为候选数据集；执行时核对项目类型、工作树与依赖，使用隔离副本/工作区保护原项目。不要同时改主产品源码、重建同一内核产物并运行依赖它的验收。

## 7. 回归、快照与结论

中间只跑受影响定向测试及必要类型/边界检查。I01/I02 发现问题后集中修复、定向确认；计划内修改完成后构建并记录产物来源，冻结源码/配置/上游版本，在 I03 集中回归。失败后是否再次全量依据改动影响和交付要求决定，记录理由，不为每处注释重跑全集。

每次报告记录实际命令、退出码、测试/跳过数量、环境、模型或替身、源码指纹、配置的脱敏标识与产物来源。发生源码变化后，说明哪些证据仍适用、哪些需补测，不能把旧结果直接标作新快照运行结果。

纯注释等价检查可辅助判断差分，但 TypeScript 指令注释、构建器注释、代码生成注释等可能影响行为；不能仅删除所有注释后 token 相同就作绝对保证。内部改名由类型/引用及行为测试验证，运行字符串和持久标识按契约影响处理。

独立验收方按需求矩阵核当前精确快照，核对真实调用链、证据层级和未执行项。实施方不能自行给出独立 PASS。产品功能测试不能证明所有场景都无错；结论须说明已覆盖场景及剩余限制。

## 8. 可直接转交主执行模型的指令

> S01–S05 按原始对话完成并接纳后，先开展文档驱动的测试准备。依据当前 PRODUCT、ARCHITECTURE、Module/Interface、模块状态、有效核心义务和 PLAN V01–V22，建立需求—行为—公开入口—权威事实—用例—证据矩阵。先核已有断言，再补缺失的基础契约与模块集成测试，区分未实现、未接线、未测试和环境阻断，处理已知阻断项。明确 I01 同一产品场景、I02 跨入口与故障组合、I03 固定版本集中回归、I04 独立验收的执行方案。完整 E2E 和真实模型样例仍归 I01，不新造重复验收阶段。中间定向验证，计划修改收口后集中回归；结构 PASS、模型连通和单票历史 PASS 均不冒充完整产品功能 PASS。保留用户改动、历史证据与明确延期范围。
