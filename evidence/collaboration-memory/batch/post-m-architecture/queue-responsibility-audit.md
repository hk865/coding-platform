# S01/S04 生产队列职责审查

本表按原始对话要求逐一回答三个问题：进程退出后如何恢复、并发时谁保证唯一、取消请求／确认／未知如何表达。文本扫描线索保存在 [queue-candidates.txt](queue-candidates.txt)；只有实际保存或串行化工作的结构列入本表，领域状态字段中名为 `queued`／`waiting` 的记录不当作内存队列。

| 位置／用途 | 内存职责 | 重启后的待办来源 | 竞争时的唯一性 | 取消／确认／未知 | 结论 |
| --- | --- | --- | --- | --- | --- |
| `DurableWake`／planning、rework、review recovery | 按 key 合并同时到达的扫描请求；扫描中再次 wake 会再跑一遍 | Ledger 中的 Plan、问题、ReviewWork 等；启动扫描和周期扫描重新发现 | queue 只合并本进程调用；Control 准入和 Ledger CAS 决定唯一提交 | close 停止新扫描并等当前扫描；领域取消仍走持久 ControlIntent | 保留，名称与注释已明确“不保存工作记录” |
| `DispatchWake` | 发起有界 dispatch page、安排 retry deadline、等待宿主关闭 | Dispatch outbox／CommunicationIntent／retry 时间字段 | Dispatch 的 claim、lease 和 Ledger 事务；多个 wake 可并发但不能重复启动 | close 清 timer、等 active；unknown 由 RuntimeDispatch 对账 | 保留，本地 timer 不成为 deadline 权威 |
| `ExecutionSlots.active/waiting` | 单进程容量、同 workspace 读写冲突和 writer 公平性 | pending outbox；进程退出后等待数组可丢弃，下一 Host 扫描重选 | 进程间由 Control/Ledger lease；本结构只减少可预见竞争 | 不表示取消；slot 中执行由 runtime／ControlIntent 处理，最终 finally 释放 | 保留，不扩大为任务状态队列 |
| `RuntimeDispatch.reconciliations` | 同一 Run 的结果对账串行化 | Runtime observation + Ledger Run／authorization | key 是 canonical Run ref；正式事实由 Ledger 决定 | 失败或观察不明写 `outcome_unknown`，绝不自动重跑外部动作 | 保留，范围只到单 Run reconciliation |
| `DispatchEngine.inFlight` | 同一进程内按 DispatchOutbox ref 合并普通派发；离开 `driveOrdinary` 的 `finally` 即释放 | Ledger 的 pending DispatchOutbox；新进程从 `pendingDispatchIntents` 重新选择 | set 只防止同一实例重复进入；`authorizeRuntimeEntry`、Control claim／start 与 Ledger CAS 才签发唯一启动权 | 不表达取消。ControlIntent 与正式 Run fact 区分取消请求、结束确认和 `outcome_unknown`；失败的无副作用准备会写持久 retry | 保留为局部去重，不作为 outbox 消费确认 |
| `HandoffDrive.inFlight` | 同一进程内按 replacement DispatchOutbox ref 合并换手派发 | co-committed ReplacementAttempt + pending DispatchOutbox；重启后重新扫描 | ReplacementAttempt 归属守卫、公共 execution slots、Control／Ledger 的运行准入共同裁决；set 没有跨进程权威 | set 不表示取消或完成；运行终态／未知仍写正式 Run fact，安全的准备失败按 outbox retry 恢复 | 保留；换手资格和上下文规则仍与普通派发分开 |
| `ReviewerDispatch.active` | 同一 ReviewWork 在一个进程共享正在执行的 Promise | ReviewWork、outbox、Run、output binding 和 runtime observation | Ledger claim／run fact／output bind；active map 只是本地去重 | 恢复先读 canonical output 和观察；不明保持 awaiting／unknown，不伪造报告 | 保留，审查资格与普通任务不同 |
| `ReworkDriveEngine.queue` | 同一实例的触发串行，避免两次同时读取同一组 open issues | Verification open issues、PlanProposal／Decision／PlanRevision | Control 每步准入 + Ledger CAS；queue 不是预算或问题权威 | 无运行取消语义；人的拒绝、预算和不可用均为持久／显式结果 | 保留；后续可按 scope 缩窄，但没有正确性需要时不改造 |
| `RuntimeObservationJournal.writes` | 按 Run 或全局串行原子文件写，防止本进程覆盖 | journal 文件本身；Runtime 初始化重新读取 | 单 Host 内写序；跨进程不支持共同写同一 journal，产品按 Run owner 使用 | 写失败向调用者传播；运行结果另由 Ledger 对账，不能把 journal 成功当完成 | 保留 ArtifactVault 存储职责，并记录单 writer 使用条件 |
| `CodingAgentRuntime.active`／`ReadOnlyQueryRuntime.active` | 进程、AbortController、完成 Promise 和 wake；代表当前进程可控制的外部执行 | prepared spec／公开 observation + Ledger Run／QueryJob；重启不复活隐藏进程 | Runtime run id + Dispatch／Control 授权；active map 防本进程重复绑定 | cancel 只发信号；最终事件确认结束；宿主中断或副作用不明写 unknown | 保留为 Runtime 实例状态，不作为 canonical task 状态 |
| `ReadOnlyQueryRuntime.starting`／`cancelled` | `starting` 按 QueryRun key 合并相同 fingerprint 的本地启动；`cancelled` 记住当前实例在启动竞态中已收到取消信号 | QueryJob／QueryRun、runtime observation 与 ControlIntent；进程退出后两个集合都可丢弃，新实例从正式记录判断关闭、恢复或 unknown | fingerprint 冲突立即拒绝；map/set 不签发只读权限，Query drive、Control/Ledger 与 runtime run identity 仍决定唯一启动 | set 只保证启动与取消同实例竞态不漏信号；正式 cancelled／failed／answered／unknown 在持久记录，不能把 set membership 当取消确认 | 保留为 Runtime 启动临界区，已从 `active` 行独立列出 |
| service `projectionQueue` | 串行推进同一 ReadModel cursor | Ledger event stream 和持久 read-model cursor | ReadModel advance 的 cursor／事务；queue 避免本 Host 重叠 advance | 无领域取消；关闭前排空，失败后下次从 cursor 继续 | 保留 Host 投影接线 |
| service action `serial` | 将同一 scoped service 的用户写动作与投影推进排序 | 动作本身已经进入 Ledger 后可恢复；尚未执行的进程内 HTTP 请求不会凭空持久化 | Control/Ledger 为正式唯一性；serial 只给调用者稳定的 read-after-write | 关闭先停止接收并排空已接受 action；领域取消走正式命令 | 保留；注释改为 Host action ordering |
| service `reviewDrives` | 按 ReviewWork ref 合并本 Host 的独立审阅启动 Promise | ReviewWork、review outbox、Run、output binding 与 observation；启动恢复和周期扫描重新调用 `launchReview` | ReviewerDispatch 的 claim／Run／output bind 与 Ledger 事务；map 只避免同一 Host 重复调用 | map 删除只代表 Promise 结束；审阅拒绝、不完整、结果未知和正式报告仍由持久事实表达 | 保留为 Reviewer 专用本地去重，不并入普通任务队列 |
| service `background` | 汇集已接受的规划、返工、审阅、派发、恢复和投影 Promise，使 Host close 能等待它们收尾 | 不用于发现工作；每种工作分别从 Ledger／outbox／observation 恢复 | 不授予执行资格，只跟踪已经由相应入口发起的 Promise | close 先置 `closing`、停止 wake／timer，再 `allSettled`；各领域的取消／未知由自己的正式记录表达 | 保留为 Host 生命周期集合 |
| service `recoveryTimer`／`DispatchWake.timer` | 周期唤醒恢复扫描，并按持久 `availableAt` 安排最近一次派发重试 | timer 丢失不丢待办：启动时立即 wake，周期扫描与 Ledger deadline 会重新建立下一次唤醒 | timer 可重复触发；实际 claim／lease／CAS 和 in-flight 去重裁决唯一执行 | clear timer 只停止 Host；不写“已取消”。到期、取消确认和未知结果仍从持久记录读取 | 保留；时间字段是权威，timer 只是唤醒机制 |
| `QueryJobDrive.refs`／`cursor` | 从事件流增量维护 QueryJob→QueryRun 的可重建本地索引，避免每次 drive 全量扫描 | 新实例从 `cursor = null` 重放 Ledger 事件，重新得到 refs；没有仅存于 map 的 QueryJob | map/cursor 不 claim 工作；QueryJob 提交、绑定 Run、回答和关闭由 Control/Ledger 幂等与 CAS 约束 | QueryJob 的 cancelled／failed／answered 等关闭事实在 Ledger；单次 deadline timer 只终止等待并生成显式 timeout 结果 | 保留为派生缓存；游标不推进或读取失败必须停止，不能把不完整 refs 当全量答案 |
| `VerificationRounds.starting` | 按 goal scope + requestId 合并同一进程同时发起的轮次创建，并让后到调用复读首个操作结果 | `round-*.json` 中的固定 scope／fingerprint／configuration／material identity；新实例由 VerificationJournal 加载，已有 requestId 走正式 replay | map 不签发检查资格；显式 `allowExecute`、固定材料、child identity，以及 Control/Ledger 的 Evidence／归约 CAS 决定可执行和可提交 | 不表示取消或轮次完成；失败传播后删除 map，正式 round status／gaps 留在 journal | 保留为创建临界区；不能把 map 存在写成 round 已创建 |
| `VerificationRounds.running` | 阻止同一 VerificationEngine 实例同时 advance 同一 round | `round-*.json` 与 `check-*.json`；init 把遗留 running 改为 interrupted，并要求显式 resume 先对账，未知命令不得重跑 | set 只拒绝本实例重入；轮次固定身份、检查 lease／lifecycle、Control Evidence 准入和 Ledger CAS 是正式守卫 | set 删除只表示本次 advance 返回；interrupted／execution_interrupted、租约和副作用 unknown 写入持久记录 | 保留为本地执行互斥，恢复不能依赖它 |
| `ReviewerVerification.operations` | 按 goal scope + requestId 串行 start／recover／resume，避免同一实例重复创建或归约 ReviewWork | `review-*.json`、ReviewWork／Run／output binding／result admission；重启从 journal 与 canonical ledger 复读当前阶段 | map 只合并同一请求；Reviewer profile／资格、精确 descriptor、Control claim／result admission 与 Ledger CAS 决定合法性 | map 不表达撤权、取消或完成；rejected／gap／awaiting_result／reduction 状态及 unknown 由 journal 和正式事实保存 | 保留 Reviewer 专用生命周期临界区，不并入普通任务执行 |
| `ReworkVerification.running` | 按完整 rework scope 合并本实例同时触发的重验编排 | 正式 rework origin、旧失败 round／review、当前 Plan 和 `round-*.json`；新实例重算确定性 requestId 后 start/replay/resume | map 不选择失败义务或授权检查；来源接纳、版本、承担者变化、轮次固定身份及 Control/Ledger 决定 | 无取消或终态语义；操作结束即删除，未完成／中断由 Verification round/check journal 恢复 | 保留局部去重；不得把普通失败或相似配置猜成返工 |
| `VerificationJournal.pending` | 缓存已经先写入 `pending-<id>.json` 的 benchmark candidate 草稿，支撑正式 patch record 前后的幂等对账 | `pending-*.json` 本身是持久来源，init 全量恢复；成功形成 `candidate-*.json` 后才删除 pending 文件和 map 项 | fingerprint、canonical patch record、workspace revision 和 Control/Ledger 提交决定唯一候选；map 只是已加载索引 | 不代表执行排队、取消或验证完成；写入／unlink 失败显式传播，遗留 pending 在重启后继续对账 | 保留持久 staging 索引；名称虽为 pending，也不能归类为纯内存工作队列 |
| `VerificationJournal` 的 checks／rounds／reviews／candidates／attempts 与 `checkFiles` | 把各类 `*.json` 读入当前实例，供验证生命周期按 scope、request 和来源身份查找；WeakMap 保留已加载 check 的真实文件 id | 每一项都来自原子 journal 文件，init 重新加载；running round/check 转为 interrupted／reconciliation_required 并先落盘，避免把重启当成功或安全重跑 | 内存数组不授予命令执行权；request fingerprint、固定材料、lease lifecycle、Control admission 与 Ledger CAS 决定正式唯一性 | journal 状态记录 interrupted、recovery、terminal rejection 和 gaps；没有通用“清空即取消”，删除内存对象不能改变文件或 Ledger 事实 | 保留 VerificationEngine 的持久 lifecycle store；它不是 StateLedger 的替代品，也不能漏出“内存数组就是权威”的结论 |
| service project registry queue | 串行新增 project/workspace 与 service map 更新 | 每个项目数据库和启动配置；未完成的 UI 请求由调用者重试 | 目录／bootstrap 守卫 + 单 Host queue | close 等 queue，再关闭服务；不涉及运行取消 | 保留 Host 注册表职责 |
| workspace tool registry queue | 串行更新工作区工具配置文件和内存读取 | 原子配置文件 | 原子写 + 单 Host 串行；不授予任务执行权 | 写失败返回错误；无领域取消 | 保留配置存储职责 |
| model settings queue | 串行模型配置读写，防止并发丢更新 | 原子设置文件；密钥从配置重新加载 | 单 Host 串行 + 原子写 | 写失败传播；不代表模型调用发生 | 保留配置存储职责 |
| `LedgerScopeCatalog.queue` | 缓存目录扫描／登记顺序 | Ledger canonical scope 和可重建缓存 | Ledger bootstrap／scope 事实，queue 仅保护本地缓存 | 无领域取消；失败不更新权威 | 保留 StateLedger adapter 内部职责 |

第二轮没有只复用 `queue|waiting|inFlight` 关键词，而是另查生产源码中保存 Promise／AbortController 的 Map、所有私有 Map／Set／数组和 `Promise.resolve()` 串行链。由此补出了 VerificationEngine 的四类状态，并复核 ReadOnlyQueryRuntime 的 `starting/cancelled` 已属于上面的 runtime 行：前者合并相同 fingerprint 的本地启动，后者只记当前进程取消信号；QueryJob／QueryRun／ControlIntent 仍是恢复和取消权威。ContextCompiler 的单次 `scan` Promise、ReadModel 投影 Map、WorkspaceReader 索引缓存和 SQL statement cache 不保存待执行工作，故明确排除。`HandoffControlAdapter.runs` 保存当前进程可控 Run 上下文，已归入 Runtime 实例状态。

审查没有发现由纯内存队列独占“任务是否存在、是否已经执行”的生产路径。所有执行、等待、返工和审查待办都能从 Ledger／outbox／持久观察或 Verification journal 重新发现；跨进程竞争继续由 Control 与 Ledger 的版本和事务守卫裁决。当前限制是 Runtime observation journal 按单 writer 使用，不把它写成跨进程队列；该限制必须保留在运行装配和文档中。
