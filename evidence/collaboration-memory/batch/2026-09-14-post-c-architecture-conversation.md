### 助手——回复

你的思路有可取之处：**分清对外接口和内部实现，按业务职责组织文件，再提取真正重复的行为。** 我建议调整一下先后顺序：先确定“每条规则由谁负责”，再决定文件夹和公共函数怎么划分。否则目录整理好了，同一条规则仍可能散在多个地方。

我抽查了当前源码，下面把已看到的问题和可选方案展开说。这轮没有修改代码；这些是整理建议，不是已经完成的全面审计。

**1．模块内部平铺：问题不是文件夹少，而是一次修改需要了解太多无关内容。**

例如协调功能涉及参与关系、消息投递、订阅、等待和后继启动。全部平铺时，模型或开发者需要先看很多文件，才能判断“修改等待条件应该动哪些地方”。

你的“按功能划分文件夹”适合解决这个问题。可以考虑下面这种结构，名字只是示意：

```text
control-engine/
  control-engine.ts       对外入口
  participation/          建立、结束参与关系
  communication/          请求、订阅和投递
  waiting/                等待条件与后继受理
  architecture/           架构决定
  memory/                 记忆维护
```

这里的原则是：**经常一起修改、共同维护一组规则的代码放在一起。** 小而清楚的模块可以继续平铺，不必强制十二个模块都有同样的目录层级，也不必为每个函数建文件。

**2．区分模块间与模块内接口：你的建议正确，但不用给每个内部函数再套一层接口。**

“对外接口”是其他模块必须知道的东西，包括输入、结果、失败原因，以及使用条件；“内部接口”只服务于本模块的实现。

整理后的效果应该是：外部调用者只需要知道“提交一个架构决定”，不需要自己按顺序调用“检查版本、计算影响集、组装事件、提交账本”等内部步骤。

项目已经有 `src/contracts`，因此可以先：

- 核对哪些契约确实被多个模块使用，保留在正式契约位置。
- 把只用于某个模块内部的辅助类型留在该模块。
- 检查跨模块导入，避免调用方直接依赖内部文件。
- 保留明确允许的共享规则入口，而不是把所有导出都封进一个巨大入口文件。

**接口分离的价值，是让内部可以调整，而外部调用者不用跟着改。** 只增加一个转发函数、转发类，却不隐藏任何复杂性，反而会增加阅读负担。

**3．协调控制和账本校验太集中：应该按规则拆，但要保留两层不同的检查。**

当前协调控制文件承载多类行为，账本校验文件也集中处理多种提交。问题是修改一种行为时，很容易碰到其他行为的代码。

可以把账本校验按提交职责分开，例如参与关系、等待受理、投递、运行事实，各自负责事件、快照和版本条件的一致性。最终仍由原来的账本入口统一执行。

但这里特别容易“去重去错”：

> Control 检查的是“根据当前情况，这个请求能不能接受”；Ledger 检查的是“到真正提交这一刻，条件是否仍成立，以及这批记录是否一致”。

比如两个执行者都先检查到“工作无人领取”。如果删掉账本事务中的竞争检查，两个人可能都成功领取。

所以可以共享“身份是否相同”“引用是否合法”等确定性判断，**不能因为两处都检查版本，就删除提交时的复核。** 同样的判断可能需要在不同时间执行，承担不同责任。

**4．两个读模型适配器都很大：可以进一步共享业务解释，保留不同的存储实现。**

读模型负责把账本事件变成界面能显示的状态。当前内存版和 SQLite 版都承载不少投影逻辑。

风险是：一种事件的显示规则改了，内存版修好，SQLite 版漏改，测试和实际产品就可能显示不同结果。

我在源码中已经看到它们共享了审查投影、基线变更投影等函数，说明这个方向已经有基础。可以逐项继续：

```text
读取事件和已有状态
        ↓
共享规则：计算应该产生哪些视图变化
        ↓
内存版写入内存 / SQLite 版在事务中写入数据库
```

适合提取的是“这个事件意味着什么变化”。数据库事务、索引、查询效率和持久化方式，仍应由各自适配器负责。不要为了共用代码，要求 SQLite 把所有数据先读进内存。

验证时，给两种实现相同的事件，比较最终视图；再单独检查 SQLite 的事务和重启恢复。

**5．多条调度路径和内存队列并存：这是行为整理，不能仅靠抽函数解决。**

目前确实能看到 `RuntimeDispatch` 的队列，以及应用中的规划、语义返工队列。不过，**队列存在本身不代表错误**：它可能只是避免本进程内同时执行同一个动作。

真正要查的是：任务“该不该执行、是否已经执行、重启后怎么继续”，到底由持久记录决定，还是偷偷依赖某条内存队列。

建议沿 M01–M05 逐个入口整理：

- 普通任务、查询、审查、返工各自保留必要的资格和业务规则。
- 领取、启动记录、重复请求识别、结果落账和恢复，复用已经验证的机制。
- 内存队列只保留局部互斥职责；进程重启后，持久记录仍能找回待处理工作。
- 旧调度入口完成迁移后再停用，避免新旧入口同时具有启动权。

**这里能共享的是可靠执行机制，不是把所有任务变成同一种任务。** 审查者资格、只读查询权限、换手条件都不能被一个“万能执行函数”抹掉。

**6．生产依赖名为 `harness` 的装配入口，以及历史票号命名：主要影响理解和职责识别。**

应用确实从 `harness` 导入持久化装配和返工组合逻辑。这个名字通常让人以为是测试设施，但这里承载了真实生产职责。

可选方案是把实际生产装配放进明确的应用装配目录，测试再使用它并注入替身。迁移前先核对内容，避免只是改名，却把测试默认配置一并当成生产配置。

历史票号也类似：运行时代码应优先使用当前业务名字；票号、当年的分工和冻结说明留在历史证据里。否则模型为了理解一个类，还得追查那张旧票到底是什么。

**关于你问的“能不能新造函数提高复用率”：可以，判断标准应当是重复的责任，而不只是相似的代码。**

| 情况 | 建议 |
|---|---|
| 多个地方执行同一条规则，修复时必须一起改 | 适合提取共享函数 |
| 内存和 SQLite 对同一种事件作相同解释 | 适合共享投影计算 |
| 代码长得相似，但权限、失败处理或事务要求不同 | 先保留差异 |
| 提取后需要很多布尔开关，调用方还得了解内部步骤 | 抽象可能选错了 |
| 新函数仅转发一次调用，没有隐藏规则或步骤 | 通常收益很小 |

对模型而言，真正减少负担的是：**找到一个业务入口，就能看懂这项行为；修改一条规则，大部分改动集中在一个地方。** 公共函数越多、文件越短，并不必然更容易理解。

我建议先拿“读模型的一类投影”或“协调功能的一组规则”做小范围整理样板，确认调用更简单、修改更集中，再推广到其他模块。调度与恢复则跟随 M01–M05 按真实入口收敛，最后通过 I 阶段检查组合效果；不需要先把十二个模块全部搬一次家。

这样既能落实你要求的整理，也能让结构调整经受真实调用、并发和恢复场景的检验。

**先明确你的接口思路。** :codex-annotation{index="6"}

你说的是从架构图出发：

**业务行为 → 负责的模块 → 对外提供的接口 → 模块内部实现。**

这个方向成立，我之前把重点放在“不要包装内部函数”上，没有完整回应你的意思。

例如，“请求取消工作”应当有清楚的对外入口，说明谁能请求、返回什么结果、什么时候算取消成功。内部怎样登记取消意图、通知执行者、处理未知结果，由负责模块完成。其他模块不应自行拼接这些步骤。

不过，接口不必统一成一个全能服务：**按职责提供少量清楚的操作，并保留十二个模块之间已经确定的依赖关系。** 架构图里的运行流程箭头也不能直接当成源码导入许可，两者要分别核对。

**新增的准备环节，建议只产出两份简短清单。**

第一份是“行为与接口表”，覆盖 M01–M05 涉及的入口：

| 应核对的内容 | 要回答的问题 |
|---|---|
| 业务行为与触发者 | 谁发起普通执行、查询、审查、换手、返工和取消？ |
| 责任模块与对外入口 | 谁负责接受请求？调用方需要知道什么？ |
| 持久状态权威 | 谁判定已经领取、已经启动、已经结束？ |
| 重复与恢复规则 | 重复请求、进程退出、结果不明确时怎么办？ |
| 当前路径与迁移目标 | 有哪些实际调用方？哪个旧入口会停用？ |
| 验证方式 | 什么场景能够证明迁移正确？ |

第二份是“整理项分配表”：把接口收口、文件归组、重复规则提取、命名清理分别分配到 M01–M05，避免每张票临时扩大范围。发现与这些入口无关的问题，单独登记。

**可以边集成审查，边优化结构。关键是按一条完整行为推进。** :codex-annotation{index="2"}

每张 M 票可以采用下面的顺序：

1. 查清该入口目前的实际调用链和行为要求。
2. 明确对外接口，整理内部职责，提取已确认相同的规则。
3. 迁移真实调用方，停用被替代的旧入口。
4. 对重复启动、权限、取消和恢复做定向验证。
5. 审查通过后继续下一项，最终统一冻结并回归。

“边做”不意味着把移动文件、改变业务语义和存储迁移混在无法区分的大改动里。它们可以在同一张票内完成，但差分应能看清：哪些仅改变组织，哪些改变行为。

正式独立验收仍需针对固定快照；验收期间继续改动的源码，不能沿用该快照的通过结论。

**队列是否保留，应按业务正确性判断。** :codex-annotation{index="3"}

建议用三个具体问题检查每个队列：

- 进程退出、内存队列清空后，系统能否从持久记录找回待办？
- 两个入口或两个进程同时触发时，是否仍只有一个合法启动者？
- 取消请求是否已持久记录，并能区分“请求取消”“确认取消”和“结果未知”？

符合这些要求的本地互斥队列可以保留。若某队列独自决定“任务存在不存在、是否执行过”，就需要迁移这部分责任。**不能仅因为出现多个 queue 就判定重复，也不能仅抽出一个公共队列就认为收敛完成。**

**目录和抽象需要可执行的判断规则。** :codex-annotation{index="5"}

可以要求实施方遵守这几条，并在审查中举出实际依据：

| 规则 | 如何判断 |
|---|---|
| 按业务职责归组 | 修改同一业务规则通常涉及的文件，应尽量集中。 |
| 对外入口明确 | 跨模块调用通过已声明入口；直接导入内部实现须有明确理由并符合依赖规范。 |
| 相同规则只有一个维护位置 | 两处代码若必须同步修改，检查能否共享；只是写法相似不算。 |
| 不同执行时点保留必要复核 | Control 的受理检查与 Ledger 的事务检查不能因相似而删除。 |
| 抽象减少调用方知识 | 提取后，调用方应少理解步骤、条件或状态；仅增加转发层不算收益。 |
| 文件拆分有责任名称 | 以“等待受理”“投递投影”等职责命名，避免堆进 `utils`、`common`、`manager`。 |
| 不为统一外形强行改造 | 不要求十二个模块都有同样目录，也不以文件行数或函数数量作为完成标准。 |

结构改善的证据可以很具体：原来修改一个规则要同步改三处，现在只改一处；原来调用方需要协调五个步骤，现在通过一个职责明确的入口完成。

**注释清理与术语统一，应当列为必须交付项。** :codex-annotation{index="1"}

建议在准备环节先核对现有权威术语，M01–M05 随改随清，最后统一检查：

- 运行时代码名称表达当前业务职责，清理含义不明的历史票号命名。
- 删除或更新已经失实的“暂不支持”“冻结不可改”“由某 lane 补齐”等注释。
- 保留解释不变量、失败原因和重要设计取舍的注释。
- 历史票号与当时分工留在证据记录，需要追溯时使用链接。
- 持久化字段、事件名称、数据库结构和外部接口名称，不能作为普通术语替换直接改动；涉及它们要明确兼容方案。

这项工作是纠正当前源码的解释，不是删除历史证据。

**性能要纳入，但 Redis 暂时只作为候选。** :codex-annotation{index="4"}

读模型整理时，应同时观察查询耗时、投影更新耗时、数据库读取次数、内存占用，以及数据增长后的表现。优先确认是否存在重复扫描、缺少索引、不必要的全量读取或重复计算。

共享投影规则不能要求 SQLite 每次把所有数据加载到内存；要保留数据库查询和事务的优势。

若测量证明需要缓存，再评估 Redis 或其他方案，并明确缓存失效、权限变化、来源更新和缓存不可用时的行为。**本轮可以要求“不得引入明显性能退化”，无需提前决定增加 Redis。**

你可以把下面这段作为给主执行模型的补充要求：

> 性能以测量和避免退化为依据，不预设引入 Redis。中间采用定向验证；完成计划内修改后冻结，开展集成回归与独立验收。与当前迁移无关的结构问题单独登记，不扩大为全仓重写。

**这个新增环节负责明确整理依据；真正的结构改进和正确性证明，仍由 M01–M05 一起交付。**
