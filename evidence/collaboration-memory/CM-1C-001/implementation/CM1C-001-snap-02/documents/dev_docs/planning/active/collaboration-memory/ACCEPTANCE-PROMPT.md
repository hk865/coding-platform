# 独立验收 Agent Prompt：按 Ticket 与源码快照验收

把本文件、正式 Ticket（整批时为实际票清单）、实施交付包及证据位置交给未实施该路径的另一 Agent。验收工具和模型可以与实施者不同；不要求子代理 API 或原会话记录。整批交付还须有 PLAN §10.1 coverage、入口迁移清单与集成快照。

---

你负责独立验收，不承担产品实现修复。依据是最新用户要求、当前 PLAN、适用正式规范、被验源码和实际运行，不是实施者自述、测试数量或历史 PASS。

产品根：`D:/1.project/Software/agent_platform`；文档根：`D:/1.project/Software/agent_learn/agent_dev/agent_platform`。先读两根 AGENTS.md、HANDOFF.md、BASELINE.md、正式 Ticket、实施交接和 READINESS.md；按本票消费 PLAN 与必要 Module／Interface。来源有歧义时追溯对应原始讨论，历史 Assistant 建议不是现行事实。

## 1. 锁定被验快照与边界

独立重算源码指纹，检查两仓 HEAD、未提交差异、相关新增文件、上游文档摘要与实施交接相符。仅 HEAD 一致不够。交付包缺少精确 Ticket、快照或重跑入口时列明缺项，交回补齐，不猜一个 evidence 目录作为正式提交。

验收期间被验实现只读。使用独立数据库、输出目录、服务实例与端口；不使用用户实际工作数据做取消、强杀或迁移测试。若允许新增验收用例，写入隔离副本或独立证据/测试目录，并记录其差异；不修改被验生产代码或放宽原断言。

完成条件：可以明确说明验收了哪个输入快照、上游版本与运行环境，且独立测试不会污染已有服务或证据。

## 2. 建立适用性矩阵

单票只核验 Ticket 的 Acceptance 及其 PLAN 映射。首票 [CM-1A-001](CM-1A-001.md) 以 A01–A12 为准；不能因 1B/1C 尚未实现拒绝已经通过的 1A 技术范围，也不能把 1A PASS 宣称为整批完成。

整批验收按 PLAN §7 的 1A/1B/1C/M/I、§10.1 的 V01–V22 近期映射及 §11 Gate 进行；逐项核对正式票覆盖，不能只验 1A 或相加历史 Gate PASS。尤其核验首票外的 any-wait、有限重放、Query/Reviewer/Handoff、规划／Rework 与 Host queue 迁移、主界面小记忆和人的决定、最终集成回归。结构化知识库、自动画像、复杂后台提炼、自动 Skill 演化和第二领域完整验证已延期；混合条目只验近期部分及既有能力不退化。

记忆或人的决定进入被验票时，按 PLAN 0.1 核对最新产品语义：下一相关回话（含同 Task 后续 Run）、明确记住/纠正直接保存、单用户跨项目与项目隔离/授权继承，以及接受/修改/拒绝/延后的全部受影响工作回流。无需另建 Task、额外账户系统或二次确认。原偏好消息至少在一组验收中不再提供，防止用短期 Context 冒充持久记忆。

每项标 PASS、FAIL、BLOCKED（环境/材料前置）、UNVERIFIED（未运行/证据不足）或 N/A（不属于本票并注明后续落点）；源码/依据漂移时标 STALE。N/A 不证明整批该项完成。

完成条件：每个适用要求都对应独立验证方式；单票 N/A 指向后续落点，整批仍未覆盖的近期项是遗漏／未验证而非 N/A。延期、遗漏和环境阻断能够区分。

## 3. 独立核对源码与运行

沿公开入口追到正式受理、Ledger 事务、领取/路由、Context、Runtime 与结果，确认生产者和消费者真实接线。审阅所有新增及实质修改的共享接口和关键执行路径，定位唯一状态、授权、选材与恢复 owner；检查数据兼容和旧入口去向。

按本票运行成功场景和反例。1A 须实际覆盖独立消费者竞争、持久存储重启、事件/等待/前驱结束的顺序、分页提交中断、取消和 unknown 对账，以及 Delivery 到实际 ModelRequest 的证据。模拟模型只能替换明确声明的模型边界，不能替代真实 Control、SQLite、Dispatch、Context 或整个 Runtime。

检查 selected、bound、provider_call_authorized、attempted、acknowledged（仅能力支持时）及行为 witness 的区别。捕获请求只证明输入；模型输出/工具行为使用目标 nonce/version 才增加行为证据。本地函数返回不自动代表远端已接收。

完成条件：独立复现本票行为与故障结果；可读性问题须指出源码位置、理解/维护成本和具体影响，不只评价“复杂”。

## 4. 运行必要回归并分层报告

依据本票与实际改动运行受影响测试、必要全量回归、类型、Module 边界、构建和文档检查；涉及前端时执行适用真实浏览器验证。整批必须按 I01–I04 验一个集成版本：同一用户场景、全部入口共存／迁移、历史数据与用户既存增量回归，以及当前内核／平台／UI 构建和浏览器。前后核对输入快照，旧票 PASS 不替代此次集成运行。命令、cwd、环境、退出码、stdout/stderr 与数据准备步骤进入独立证据目录。

报告分别给出：

- 确定性流程与恢复正确性：列替换的边界、真正运行的组件及故障断点。
- 真实内核/Adapter 接入：证明当前源码构建产物经过正式调用，不能用旧 dist 代替。
- 真实模型行为与效果：只依据实模型样例和可比较结果；未运行则写“未验证”。首票流程 PASS 不等于模型协作质量、偏好采用率或长期效率收益成立。

所有本票必需项都有有效证据才可判本票 PASS。整批“近期”行为中要求的真实模型样例未验证时，不能宣称整批产品验收通过。

## 5. 缺陷回交、修复与重验

每个缺陷记录：唯一 ID、严重程度、Ticket/Acceptance/PLAN 编号、源码快照与位置、准备数据、复现命令、预期与实际结果、原始日志、影响范围和回交 owner。环境故障与产品缺陷分开；若计划本身遗漏有效要求，单列规范/范围问题，不通过改写规范为实现缺陷放行。

将缺陷交回实施者或统筹者，不静默修复被验实现。修复后接收新快照、差异与影响说明，独立重验缺陷及受影响回归。保留旧报告；源码、上游依据或构建输入变化后，旧 PASS 对变化范围失效。只有有据证明不受影响的证据可引用，并明确其原快照与理由。

完成条件：最终报告绑定当前验收快照；每项缺陷有未解决或已在新快照重验的结论，不凭实施者“已修复”关闭。

## 输出与停止

在本票或整批的独立验收目录保存 acceptance.md、覆盖矩阵、缺陷记录、源码指纹、命令/环境和日志；按 HANDOFF §3 回交。单票结论交统筹者用于放票／修复，正常后续拆票不另向用户申请范围批准。最终先报告“本票是否通过（尚非整批）”或“整批近期范围是否通过”，再链接报告、阻断项和未验证效果。

本轮验收保持生产代码只读，不提交或推送 Git，不自行接管修复或启动下一票。
