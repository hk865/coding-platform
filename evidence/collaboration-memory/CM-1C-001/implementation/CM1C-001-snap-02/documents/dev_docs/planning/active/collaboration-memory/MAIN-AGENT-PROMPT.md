# 统筹 Agent Prompt：以纵向 Ticket 推进整批近期范围

将本文件与 [交接入口](HANDOFF.md)、[PLAN](PLAN.md) 及首张正式 Ticket 一起交给用户选定的统筹者。任何能读取文件、修改代码并执行本地命令的开发工具都可使用；没有子代理能力时同一 Agent 兼任统筹和实施，按 Ticket 串行工作。本文不依赖原会话记忆，也不单独授权施工；当前准备回合在交付后停止。

---

你负责 Agent Platform **整批近期范围**的基线核对、Ticket 派发、接口裁决、集成和独立验收交接。执行委托采用本包时，目标是 PLAN §7 的 1A、1B、1C、入口迁移 M、整批集成 I 全部近期结果，而非只完成第一张票。首票为 [CM-1A-001](CM-1A-001.md)；后续票由你在前置证据成立后自主细化并继续推进，不要求用户反复批准拆票。CM 分组仍是需求簇，不能直接横向派发。

单票实施者按 IMPLEMENTATION-PROMPT 交验并回到你处；你依据当前证据选择下一张就绪票、处理缺陷和剩余范围。只在整批独立验收完成、遇到无法安全继续的真实阻断、或用户明确改变委托时交付相应结果／检查点；1A PASS 不是整批停点。

产品根：`D:/1.project/Software/agent_platform`。文档根：`D:/1.project/Software/agent_learn/agent_dev/agent_platform`。WSL 路径及实有工具链见 [BASELINE](BASELINE.md)；换机器时映射同一两仓，不假定任何工具自带 Node、子代理或浏览器。

## 1. 接受现有成果并核对开工基线

先读两根 AGENTS.md、HANDOFF.md、BASELINE.md、首票、READINESS.md，以及 PLAN 的 0.1、§7 整批路线、§10.1 映射和 §11 放票条件。每次制票再读其阶段正文及必要 Module/Interface。源码事实按 CURRENT-CALLCHAIN-EVIDENCE.md 定位；进入 1B 时读 MEMORY-REUSE-EVIDENCE.md 的复用单位，进入 1C 时读 human-design-status 及对应正式决定 Interface。仅当条款冲突或来源有歧义时追溯对应原始对话，不重新全量调查。

记录当前两仓 HEAD、必要未提交差异、相关未跟踪文件与源码指纹，对照准备基线。保留已有 RoleSpec、WorkMemory、协作选材等增量。基线有变化时只复核受影响路径，记录采用的新基线及影响；不能仅凭 HEAD 相同沿用旧 PASS。

建立整批 coverage/release-log（位置按 HANDOFF §3），将 PLAN 阶段结果映射到已生成正式票、owner、依赖快照、独立结论与剩余项；未生成后续票的范围仍为待推进，不是 N/A 或已延期。

完成条件：整批范围、当前票、唯一实现 owner、源码输入和所需环境可识别；无未处理的重叠写入或合并冲突。缺失材料先做安全本地核对，只有不能自行解决的具体阻断才上报。

## 2. 收敛首票必要决定，而不是冻结全产品

依 CM-1A-001 的 D01–D05，在产品代码修改前完成最小技术裁决并写入本票证据中的 decision-log：Task outbox 的兼容演进、前驱 Run 公开结束与后继受理、Agent principal／Host 工具接入、claim/cancel/unknown 对账、旧入口组合。

以 PLAN 的推荐语义和当前源码为依据，正常技术细化自主决定。字段、表结构、分页大小与局部函数由实际消费者和失败测试收敛；发现方案不能成立时，比较有实据的替代方案并同步受影响 Interface。只有新的产品取舍、重大职责冲突或超出当前授权才向用户提出具体差异、影响和问题。

完成条件：每项必要决定有 owner、版本／事务边界、兼容策略和可证伪方法；没有把核心语义分别留给不同实施者猜测。D01–D05 不是用户逐项审批清单。

## 3. 一名 owner 贯通第一条纵向实现

由你本人或一名集成实施代理贯通 CM-1A-001 的生产者、Control、Ledger、Dispatch、Context、Runtime 和故障用例。同一时期这些未稳定的共享契约只有一个实现 owner；不能按通信、存储、Context、UI 横向派给不同实现者。

可并行安排有界只读调查、失败场景设计和独立方案／源码审阅。每次派发提供：

- ticket_id、ticket_path、role、workspace_root；
- upstream_artifact_refs（路径、版本／摘要及所需章节）；
- write_scope、问题、交付物、完成条件和回交对象。

调查与审阅默认 write_scope=none；需要保存报告时只授予独立证据目录。子代理工具可用时使用，不可用时通过文件交接或串行执行；工具限制不改变职责。验收独立性仍要求另一 Agent，不以实施者自审替代。

完成条件：本票公开入口到可审计结果及失败路径接通；候选接口经过真实消费者验证，核心规则集中在所属 Module，没有重复状态或竞争调度。

## 4. 集成与按证据放票

收件时核对实际差异、生产者／消费者、持久权威、恢复路径与运行证据，不接受“已完成”消息作为 PASS。共享契约变化由你统一裁决、通知受影响消费者，并同步本票和正式 Interface；保留数据兼容、旧入口去向及未验证范围。

按 PLAN §7、§11 的实际依赖与 Gate，记录“证据支持释放什么、尚不能释放什么”，自主生成下一张正式票。每张后续票补全信封、生产者／消费者、状态权威、兼容／恢复、输出、适用 B/C/M/I 与 V 验收、交接条件及当时写入范围；未验证字段保留候选。1B/1C 的范围已在整批委托内，不作为新的产品选项重问用户，也不提前生成全产品所有票。

Gate A 的成熟通信／调度部分不等待 B/C；B 只依赖回应 Context／正式写入口；C 依赖投递／版本／接续，偏好化解释在与 B 合流时补验。入口迁移按 M01–M06 持续收口，尤其首票未覆盖的 any-wait、Query/Reviewer/Handoff、队列退出与生产并行；它们不是可选扩展。未稳定的跨模块消费者仍由同一纵向 owner 负责。

每次交验或修复后更新剩余项：有就绪票则继续实施；有缺陷则安排 owner 修复和新快照重验；部分等待独立证据时可推进无依赖的安全工作。无子代理时同一 Agent 串行兼任统筹／实施；独立验收仍交另一 Agent。不得因单票“交付待验收”就把整批委托标完成。

独立工作树也必须包含必要未提交基线。共享目录时登记唯一 owner；构建产物、测试数据库、服务端口和证据目录隔离。移交 owner 时暂停该路径写入，先交可识别快照。

完成条件：每个放票决定引用当前源码快照和实际 Gate 证据，近期剩余项均有去向；I01–I04 负责跨票合流而不是相加各票 PASS。正常技术协调由你完成，只有新增产品取舍／权限需求向用户列具体问题。

## 5. 交给另一 Agent 独立验收

先停止对被验源码的修改，再按 HANDOFF §3 交付正式 Ticket、基线到交付差异、源码指纹、decision-log、验证矩阵、命令／环境、日志和重跑入口。把 [ACCEPTANCE-PROMPT](ACCEPTANCE-PROMPT.md) 交给没有实施该路径的另一 Agent；其执行工具和模型可以不同。

独立验收可串行发生在同一工作目录，但使用独立证据与测试数据，不能与该被验快照的实现写入并行。每票只验适用标准；整批按 PLAN §10.1 的全部近期部分与 I01–I04，对最终集成快照重跑必要回归、构建、浏览器和真实模型样例。单票 N/A 仍须在整批被相应后续票覆盖。

缺陷按可复现记录回交实施 owner。修复产生新快照，验收者重验受影响范围及必要回归；旧日志保留，旧 PASS 不迁移到新快照。跨票影响由你收口，不让用户反复承担日常技术协调。

完成条件：交付快照有独立结论；范围内未解决问题和真实模型未验证效果明确。实施者只提交验收申请，开发流程据证据更新票，产品 Task/Goal 状态仍由 Control 归约。

## 整批交付与真实停点

按 HANDOFF 格式交整批差异／源码快照、覆盖矩阵、入口迁移清单、Interface/模块状态同步、独立验收及恢复说明。只有 §10.1 的全部近期结果在最终集成版本上通过，才报告整批完成；延期内容保持后续，不偷偷补造知识库、自动 Skill 或第二领域。

工具不能主动交给另一 Agent 时，输出明确的外部验收交接点、所需证据与恢复入口；若已无不依赖该证据的安全工作，可以暂停等待外部验收，但必须列整批未完成范围。收到结论后继续拆票／修复／推进，无需用户重新授权既定近期范围。新的产品取舍或权限阻断同样说明影响与可继续部分，不以“1A 做完”代替这一判断。

沿用当前授权、工具链和既有预算，不自行增加累计 Token／调用／时长预算。本文不含 Git 提交、推送、清空工作树或覆盖用户改动的授权。
