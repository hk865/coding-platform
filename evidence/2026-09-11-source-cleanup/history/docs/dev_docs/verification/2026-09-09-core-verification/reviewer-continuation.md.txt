## 1. 下一票应交付的完整消费者

建议下一张实施票覆盖：真实 Task 的已持久工具轮次 → 当前来源/权限/报告取材 → 正式独立 Reviewer Run → 有定位与义务覆盖的语义报告 → Verification 验证报告资格 → Control 接纳 verdict/归约 → FAIL 问题关联到已授权修复工作 → 新来源下重跑工具并重新审阅 → 保留原 FAIL、修复关系和正式回执。应用、SQLite、Vault、ReadModel 和现有工作台同步消费同一链路。

[VerificationEngine](../../modules/control/verification-engine.md) 组织工具和 Reviewer；[ContextCompiler](../../modules/data/context-compiler.md) 只取材并检查来源、权限和容量；[DispatchEngine](../../modules/control/dispatch-engine.md) 驱动正式意图与 Run；[WorkerRuntime](../../modules/execution/worker-runtime.md) 承载模型和工具；[ControlEngine](../../modules/control/control-engine.md) 独占授权与 canonical 归约。不得让 Context 启动模型、让 Runtime 判断审阅通过，或由 UI 改 Task phase。

[完成策略 §4](../../interfaces/completion-policy.md#4-completionpolicy-与分层验证) 已要求明确 static/dynamic FAIL 先返工，不启动昂贵 Reviewer。因此入口须区分工具 FAIL、INCONCLUSIVE/缺料、工具覆盖已通过且仅缺 Reviewer；不能只测 `round.outcome === PASS`，因为现有正常待审轮次总体就是 INCONCLUSIVE。审阅可以有多轮，但不把轮次数/调用数设置为用户未配置的累计预算。

## 3. 必须在实施票冻结前解决的接口差异

### 3.1 审阅对象、执行工作与独立身份

ReviewPacketV1 的 taskId/runRef 未区分“被审 Task/Coder Run”与“执行审阅的工作/Reviewer Run”。实际组装器在第 170 行要求审阅 Run 已有 envelope，然后只引用它自己的 bundle；常规 Dispatch 又必须先得到 bundle 才能 startRun。这个历史测试顺序不能直接用作首次真实 Reviewer 的启动序列。

建议主线冻结一份由 Control 受理的审阅工作身份：至少关联 subjectTask、subjectRun/attempt、精确 roundId/聚合摘要/配置摘要、review work/attempt/Run、角色版本、权限来源、提交人及稳定请求身份。执行审阅的 Run、session 和角色绑定必须与 Coder 分开，内容独立取材；同一个模型/同一供应商可以承载不同 Run，不靠虚构不同模型保证独立。模型输出不能自行改 subject、权限、coverage 或完成条件。

现有普通 `claimTask` 会读取 TaskLease 和 live TaskReduction：[claim.ts:79](/mnt/d/1.project/Software/agent_platform/src/control/control-engine/claim.ts#L79)、[dispatch-facts.ts:31](/mnt/d/1.project/Software/agent_platform/src/control/control-engine/dispatch-facts.ts#L31)。[普通 eligibility:60](/mnt/d/1.project/Software/agent_platform/src/control/control-engine/policies/task-eligibility.ts#L60) 与 [replacement eligibility:47](/mnt/d/1.project/Software/agent_platform/src/control/control-engine/policies/replacement-eligibility.ts#L47) 仅允许 pending/ready；工具完成后被审 Task 已 blocked/failed，且旧 TaskLease 仍承担最新 Attempt 关联。因此不能重领原 Task 或将 Reviewer 作为 Coder replacement，后者还会改变 Task reducer 读取的最新 Run 信号。

优先评估“正式 review 工作/意图关联被审 Task，拥有独立执行 Attempt/Run 与读 lease”的版本化扩展，复用 Dispatch 起止和事实协议，保留原 TaskLease/eligibility。它不是当前已有接口，必须由 Control/Dispatch owner 定义实际记录与守卫。若选择向 Plan 增加独立审阅 Task，则需明确 Plan 变更授权、重建工具来源锚、非循环的输出依赖以及审阅 Task 自身的完成义务，不能暗加一个不受完成策略约束的假 Task；不推荐为了接一次审阅直接改旧 Plan。

### 3.2 当前材料与 Reviewer 的实际输入

下一版有界包至少需要：被审 subject/producer、review 工作/Run 身份、冻结 VerificationRoundMaterialIdentity、VerificationPlan 与精确 required Reviewer coverage、原工具报告清单和聚合引用/摘要、policy/baseline 正文或已授权的精确引用、实际源码摘录及路径/版本、真实变化比较证明/gaps、规范审查点、权限与容量清单。必要材料缺失或超过上限显式 needs_material；可有界索引加精确按需读取，不静默裁剪报告或义务。旧 32 KiB ReviewPacket 与 64 KiB Reviewer capability 是不同现存上限，不可无声统一扩大。

[runtime-context.ts:49](/mnt/d/1.project/Software/agent_platform/src/data/context-compiler/runtime-context.ts#L49) 验证的是 Task bundle schema；旧 Review bundle 外壳 `{schemaVersion,packetId,packet,note}` 不能直接作为 TaskEnvelope.bundleRef 通过它。当前 runtime material selection 还固定 consumer=executor、前驱必须来自已应用的探索操作者 PASS。需要独立的 Reviewer 材料扩展与实际模型输入验证，不继承这条探索前驱假设；最终模型请求中不能塞入完整 Coder transcript 或 reasoning。

`resolveRound` 第 101 行拒绝同 Workspace 任意 prepared/running/outcome_unknown observation。Reviewer 自己一旦 prepare/start，原口就会拒绝。下一票需提供用途明确的 currentness 检查：仍复核被审 Run/源身份，并只豁免已由 canonical review binding 证明、权限精确为 readonly 的本次 Reviewer；不得接受 caller 给任意 runId 排除清单，也不得忽略外部 Writer/unknown Run。执行前、材料读取前后、模型报告返回后、接纳/恢复时都复核，来源 I/O 后再核对 canonical。读 lease 不是源内容原子快照。

### 3.3 跨主体报告授权与来源格式

工具原报告与聚合当前归 Coder Run 拥有；`VerificationContext.openReport(ref, owner)` 的 owner 读取用于既有检查恢复/历史，保持其语义。新的 Reviewer current use 要求以 Reviewer Run 调 `Vault.open`，带精确 basis 和 usage=current；由 Dispatch 经 Control 对所需原引用签发 grant，Context 不签授权。实际 grant 撤销、源 pin 改变、canonical 计划/工作区变化必须令下一次 current 读取及接纳失败。原 owner 仍能看旧报告；历史解释授权不能变成当前审阅依据。

现服务注入的 source applicability 是 [ExplorationSourceApplicability:68](/mnt/d/1.project/Software/agent_platform/src/data/workspace-reader/exploration-source.ts#L68)，其 pin 标记 exploration-source-v1；VR-01 则保留 Candidate digest。两者不可赋值互换。下一票可提供明确的 Reviewer sourcePin provider 或可审计的两种身份关联，持久保存各自含义，保证路径范围与实际审阅来源一致。不得给旧 digest-only grant 自动补可信 pin，不得为适配权限改写旧 sourceDigest。非 Git、外层 Git 子目录、原忽略产物都需继续支持；只有真实当前来源不可完整读取才缺料。

### 3.4 运行、报告与 Evidence admission

[RunSpec.mode:5](/mnt/d/1.project/Software/agent_platform/src/contracts/runtime-preparation.ts#L5) 当前只有 explore；[CodingAgentRuntime.start:92](/mnt/d/1.project/Software/agent_platform/src/execution/worker-runtime/coding-agent-runtime.ts#L92) 对非 explore 要求 write + `*`，execute 也以该模式决定编辑/shell、工作目录安装等。新增 Reviewer readonly 路径必须落到正式 runtime 能力/权限检查和实际工具注册；复用 observed-model-run，不能开 write 权限后仅在 prompt 写“不要修改”。现 [service.ts:83](/mnt/d/1.project/Software/agent_platform/src/app/service.ts#L83) 只为 explore 提供额外材料，宿主需要接新的公开口；不存在真实 Reviewer provider 可直接换名启用。

建议 ReviewReport 新版本绑定 reviewId/packetDigest、exact subject/round/source/角色/producer，包含每条被要求 Reviewer VR 的 PASS/FAIL/INCONCLUSIVE、理由、引用的代码/工具证据、定位问题、影响与未知项。报告中的覆盖声明需与冻结 rubric 一致：缺项、重复、陌生 VR、把 Reviewer 覆盖写到 static/dynamic、无据 PASS、空文本、错误版本、正文摘要/大小/owner 不符均不能接纳。模型输出仅形成原报告事实；保存正文后，由 Verification 解析并复核资格，再用稳定身份请求 Control。

[Evidence 校验:1555](/mnt/d/1.project/Software/agent_platform/src/contracts/validation.ts#L1555) 对 verdict 目前主要要求 RunRef 形状；[Evidence intake:78](/mnt/d/1.project/Software/agent_platform/src/control/control-engine/evidence-intake.ts#L78) 读取 anchor Plan 与 coverage；[Ledger 校验:628](/mnt/d/1.project/Software/agent_platform/src/contracts/ledger-validation.ts#L628) 核对事件/命令 actor 与不可变内容，但没有上述审阅独立性与正文语义守卫。下一票必须明确 Control 如何检查正式 review authorization/result 关联，Verification 如何提供已验证报告，不让普通用户传 `{kind:verdict,outcome:PASS}` 冒充这条正式消费者。保留旧历史 Evidence 与通用入口兼容，不全量重写历史资格。

持久进度至少区分：请求已受理、材料/授权待齐、启动意图已存、Run 未知/运行中、原报告已存、报告拒绝/过期、Evidence 待回执/已接纳、归约待回执/完成。字段名称由实施票确定。幂等键在每一步副作用前落盘；同键异载荷拒绝；回执丢失先查 canonical/原记录；缺最终报告或未知 Run 不自动重新调用模型。新审阅工作和新修复工作使用新身份，原始失败不复用为“再试一次”成功记录。

## 4. FAIL 后授权返工与新来源重验

这里有三种不同历史，下一票不可合并：工具检查 FAIL、Reviewer 语义 FAIL、Coder Run crashed/outcome_unknown。前两者的原报告/问题应关联修复工作；unknown 先对账，不能以修复 Run 掩盖未知副作用。

现有 [RemediationTask:101](/mnt/d/1.project/Software/agent_platform/src/contracts/remediation.ts#L101) 针对 ArchitectureFinding + ArchitectureEvolutionPolicy allowlist，不是普通语义缺陷修复。它的 resolved guard 目前检查 payload evidenceRefs 非空/result.verified/PASS/版本数，见 [remediation.ts:322](/mnt/d/1.project/Software/agent_platform/src/control/control-engine/remediation.ts#L322)；不能把传入 verified=true 当真实重验。现 [GoalChange:211](/mnt/d/1.project/Software/agent_platform/src/control/control-engine/goal-change.ts#L211) 仍复用 sourcePlan.tasks，amendment 不表达新增修复任务。WorkContext 只留工作关联，同样不代替受理修复的政策。

建议后继票将问题 → 修复授权 → 修复工作/Run → 新工具轮次 → 新审阅 → 问题处置结果贯穿为正式关联：原 Task/Run、失败 report/evidence/finding ID、来源身份、问题覆盖、授权策略/决定、允许修复范围、产出新 source/Workspace revision、重验配置、替代关系和回执。普通已授权的 in-scope 修复/重验自动受理；改变 requirement/acceptance/baseline 才走精确决定。不能通过删除失败、重置 TaskReduction、弱化测试或关闭 required 义务解除阻塞。

新来源必须经有实际变化依据的 Control 版本受理，再执行新轮次及新 Reviewer；仅 requestId 变了、报告里声明“已修复”或重复旧 sourceDigest 都不足。若修复采用新 Task，必须说明它如何合法处置原 required failed Task，以及如何继承义务而不继承完成；若采用原 Task 的修复 Attempt，必须新增经授权的重开/修复守卫，不能放宽普通 replacement。

[Evidence applicability:42](/mnt/d/1.project/Software/agent_platform/src/control/control-engine/policies/evidence.ts#L42) 当前只比较 plan/workspace/policy/baseline revision tuple，没有真实 sourceDigest；后到同 tuple PASS 可占有效位置。VR-01 的 stale View 不会自动撤销已接纳 Evidence。完整“修复后正确重验”必须在下一票明确正式来源推进/绑定与 supersession 规则：新源码不得沿用旧工具或旧 Reviewer PASS，旧 FAIL 仍可查。此处需提出兼容扩展，不在准备阶段修改共同 Evidence schema。

[task-reducer.ts:79](/mnt/d/1.project/Software/agent_platform/src/control/control-engine/task-reducer.ts#L79) 取 TaskLease 指向的最新 Run 信号，且第 136 行 unresolvedFindings 当前传空数组。后继 Reviewer 问题不能只显示在 UI 而不参与正式守卫；将 Reviewer 挂为最新 Coder Attempt 也会污染失败/未知运行归约。上述两点都必须有真实 Control 反例。

[CoordinationPolicyContentV1:87](/mnt/d/1.project/Software/agent_platform/src/contracts/human-role-collaboration.ts#L87) 存在旧 maxAutonomousReworks/maxClarifications 数字字段，但它不代表本用户配置了次数限制。[旧 P1-15 测试:144](/mnt/d/1.project/Software/agent_platform/tests/control/p1-15-role-rework-loop.test.ts#L144) 的 ONE rework 是测试内计数和 FakeRuntime crash→completed，没有正式工具 FAIL 后独立审阅的消费者。不可继承其中默认“1 次返工”。沿用 [RuntimeBudget](/mnt/d/1.project/Software/agent_platform/src/contracts/runtime-budget.ts#L1) 的未配置累计项 null、实际用量计量和显式单次容量；授权策略的新差异先由实施票确认。

Task 满足与 Goal 完成仍分开。当前普通计划还含 required GoalGate，工具/Reviewer Evidence 的 subject 是精确 Task，不能仅因 obligation ID 同名就复制为 Gate PASS。下一票若不实现 Gate 取证，就必须如实保留 Goal 未完成；若承诺 Goal 完成，需要将 Gate 当前来源与真实 Evidence 路径一并纳入验收。
