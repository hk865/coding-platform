## 接续结论

首先接通**按当前 Task、来源版本和固定策略组织的通用验证轮次**，复用现有真实检查与报告恢复实现。随后以同一组版本事实贯通独立 Reviewer、结构化问题、授权返工、新版本检查和重新审阅。公开补料与 WorkContext 消费为这些角色补齐连续输入，再接安全点控制、新 Run 接续、决定反馈、记忆管理和统一展示，最后做真实项目与对照评测。

这不是重新建设已验证的 Ledger、Vault、QueryJob 或初始规划。当前缺失主要是既有确定性底座之间的**生产消费者与结果回流**；部分需要版本化事实扩展，不能靠应用按钮、角色名称或新的包装类补齐。

## 第一项可完整实施的具体范围

建议下一个 Development Ticket 定为“真实 Task 的通用验证轮次”，owner 为 VerificationEngine，直接协作者为 Context、Control、WorkspaceReader、HumanCollaboration/ReadModel；沿既有 12 Module，不新增流程 Module。完整结果是：用户从真实任务发起一次验证，平台取得当前材料、执行既定检查、保存可重开的结果、接纳有效 Evidence，界面显示其覆盖与仍缺的 Reviewer；任一过期/缺料/未知副作用都阻止错误完成。

输入固定为一个已受理 Plan 中的一项真实 Task/Run、精确 Workspace/源码来源、当前 policy/baseline pin、明确注册的 static/dynamic 检查配置及请求身份。检查注册与运行配置须可追溯，不从自由文字义务猜命令；未配置检查返回具体缺口。先用受控小仓库的真实检查实现，不要求提前购买服务或拉取 benchmark 镜像。

实现应覆盖以下同一条消费者路径：

1. Context 基于正式 scope/Run/Plan/pin 编译验证材料；WorkspaceReader 提供实际来源身份和有根据的变更范围。既有 `changeScope` 调用字段保留兼容，来源不充分时显式缺料，不以任意声明生成 no-change 快放。
2. Verification 使用现有纯 `compileVerificationPlan` 和真实 CheckPort 注册表组织该 Task 的全部适用检查，复用 CommandCheckLifecycle/Provider 的副作用、报告及恢复行为。支持多检查时补明确的每项持久进度/结果关联，而非复制整套命令执行代码。
3. 稳定轮次身份绑定 task、plan、policy、baseline、来源和检查配置；原身份重试返回原轮次，同键异载荷冲突。新源码产生新轮次，保留旧报告。逐项检查结果、原始报告引用、接纳回执与待审阅义务都能重开读取。
4. 原报告经 Verification 提交 Control Evidence，按原政策覆盖和适用性决定是否归约。Reviewer 尚未运行时明确等待，语义任务不能仅靠工具 PASS 满足；纯机械快放仅在已固定政策与实际无变化证明允许时成立。一般 verify 的 ready 不扩义为 completed。
5. 应用/harness 只接真实 registry 和正式模块端口，移除该入口的恒 incomplete 注入；无配置仍返回具体 incomplete。现有检查工作台显示同一轮次的有效覆盖、过期/拒绝、报告来源与恢复操作，不另做一套状态推断。

完成验收必须走正式入口到真实命令、Vault、Control、SQLite、ReadModel/UI：成功/失败/不确定检查；缺少检查配置；需要 Reviewer 的任务保持未满足；来源在执行前/中/报告后变化；部分检查已存后重开；同请求重放不重跑命令；坏摘要/撤销/旧版本拒绝；原始 FAIL 留存。真正进程强杀恢复和真实 Reviewer 语义质量可作为随后的专门消费者验收，不能将首项结果包装为 A4/A5 全部通过。

必须避免两个假完成：把现有单命令按钮改名为“通用验证”；把默认 Reviewer capability 或人工探索 PASS 当成独立 Reviewer Evidence。该首项的验收边界是可实际使用的工具验证轮次，后继 Reviewer 任务从其持久结果直接接入。

## 依赖次序与确定阻塞

1. 架构固定快照终审/回归由主线完成后，再启动新源码 Ticket；其结论与源码身份在新票引用。本文件静态核对不代替终审。
2. 验证轮次、角色/工作绑定与反馈记录属于确定底座，可按不同独占范围安排；新的共同字段先确定正式 Interface。不要先启动模型，再靠事后文字补齐来源和身份。
3. 独立 Reviewer 和授权返工消费验证轮次；补料闭环消费现有 Query 与新工作关联；真实重规划必须实际表达新增/修订任务，不能滥用当前有限 amendment。
4. 新 Run 接续消费工作记录、来源/权限和真实运行能力；人的决定回流消费议题/受影响工作与 Context 刷新；Memory 消费已建立的工作/来源生命周期。UI 与各实际路径同步，不拖到最后统一做占位卡片。
5. 架构迁移 Gate 消费真实验证 Evidence，不能早于检查 provider 完成；跨包决定与激活反馈依赖上述刷新机制。语言深度按真实任务需求扩展，通用语言覆盖不是全链验收的替代品。
6. 真实仓库先覆盖 A1/A2/A4/A8，再独立覆盖 A5/A6，最后按已锁定 [评测材料](../2026-09-08-framework-acceptance/benchmark-research.md) 准备官方镜像和同模型基线。该材料是既存研究记录，本次未联网复核其时效，实施时重新核对环境/镜像与执行规则。

当前确定的软件缺口已在表中给出；模型凭据、可用模型、真实仓库选择、Docker/镜像可用性与实测资源情况**本次未检查**，不能擅自报告不可用或已就绪。候选 benchmark 的镜像 digest 未锁定是既存验收记录的明确未完成项，不妨碍首项本地确定性实现。
